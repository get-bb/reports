#7509 · Detached cancellation loses plugin ownership when its stack has no frames

Bug High Effort: Medium plugins · 2026-11-13 · GitHub issue

Trusted base: 88cf8f644c81fca797ad80bc31bb36a61ce5cc9b, fetched directly from get-bb/bb main.

Verdict: REPRODUCED · Root-cause confidence: high for the containment gap; unknown for the original source of cancellation. Reproduction label: confirmed-repro.

1. TL;DR

A plugin's detached cancellation can escape the server's plugin-error containment if the thrown exception has no stack frames. A new regression case loads a real plugin through the existing service harness, creates a native aborted signal, and throws its reason from a detached callback. With normal frames, the runtime claims the exception; with stack capture temporarily disabled during signal creation, it does not. The server's production exception listener exits with code 1 whenever that runtime returns false. Two separate clean checkouts reproduced the same gap without changing production code; neither run establishes which operation caused the reported desktop incidents.

5. Root cause

Service runs establish AsyncLocalStorage ownership. The general plugin invocation path records event-loop work but does not establish that service context. The test starts its detached callback from a CLI handler, outside a background-service run.

Without a service instance, the runtime falls back to plugin code locations in the error stack:

const instance = serviceContext.getStore();
if (instance === undefined) return containPluginError(error);

For a non-stale error, that containment path returns false when pluginOwningStack(error) cannot find a registered code location. A single-line native cancellation has no such location. The framed control has one, and is correctly contained.

The server's production listener makes an unclaimed exception fatal: it first checks pluginService.handleUncaughtException(error), returns only if true, writes the exception text to stderr, then calls process.exit(1). The reproduction observes the same false result rather than killing its test worker. It does not test Node's unhandled-rejection promotion or identify the original rejected promise.

Diagnostic error serialization already follows cause chains when present. uncaughtExceptionMonitor writes a diagnostic regardless of later containment; it is not an exit verdict.

6. Proposed fix and simple-fix assessment

Preserve trustworthy plugin ownership at execution boundaries instead of relying exclusively on exception formatting. First define how ownership transfers when a plugin invokes core work: a broad inherited plugin context would claim unrelated core failures. The existing core-work negative control intentionally returns false, and passes in both runs.

Do not swallow all AbortErrors or all frameless errors globally. Their names and missing frames do not establish provenance, and keeping the process alive after an arbitrary unowned core exception changes the existing fatal-error policy. Catch cancellation where the responsible operation is known; add structured owner/context diagnostics where ownership is available, without guessing an owner.

No pull request: the upstream abort source is unknown, and safe generalized containment requires an ownership/policy decision. That fails the autopilot requirement that a simple fix need no product or architecture decision. No production fix, branch, or dependency was introduced. The local regression extension is 45 added text lines in one test file; its expected failure is evidence, not a passing fix.
