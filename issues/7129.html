#7129 · Installation discovery invokes diagnostics

BugPriority: MediumEffort: Lowprovidersprovider-claude-codeconfirmed-repro

GitHub issue · November 5, 2026 · trusted origin/main fa30b0a7dcdf745f7baf8e41721f754b7d3198fe

Verdict: REPRODUCED · Root-cause confidence: high for command dispatch. Real authentication effects are unverified.

1. TL;DR

Checking whether Claude Code needs an update also starts a diagnostic subprocess. The installation-status function launches the CLI with doctor whenever update discovery is enabled, including its default invocation. Two clean source checkouts reproduce that extra command using dummy executables and the real subprocess-dispatch code; the compatibility-only control starts only the version probe. This verifies dispatch, not a live logout, credential mutation, or the authentication internals of the real diagnostic. The diagnostic output also controls release-channel selection and update ownership, so removing it is not a behavior-neutral deletion.

5. Root cause

The bridge's installation-status request handler forwards its checkUpdates value directly to the provider maintenance function. The function defaults checkUpdates to true and launches five probes concurrently. The fifth probe is not gated on an explicit health check, update action, or any detected need for an update:

export async function getClaudeProviderInstallationStatus(
  checkUpdates = true,
): Promise<ProviderInstallationStatus> {
  const command = await claudeExecutable();
  const [
    resolvedExecutable,
    versionOutput,
    tagsOutput,
    npmGlobal,
    doctorOutput,
  ] = await Promise.all([
    resolveExecutablePath(command),
    commandOutput(command, ["--version"]),
    checkUpdates
      ? commandOutput(npmCommand(), [
          "view",
          CLAUDE_NPM_PACKAGE,
          "dist-tags",
          "--json",
        ])
      : null,
    checkUpdates
      ? probeNpmGlobalPackage(CLAUDE_NPM_PACKAGE)
      : { npmBin: null, npmGlobalPackageVersion: null },
    checkUpdates ? commandOutput(command, ["doctor"]) : null,
  ]);

The commandOutput helper really executes the subprocess and catches its errors. Returning null on failure cannot undo process startup or any subprocess side effect. Compatibility discovery avoids the branch only because it passes false.

The deeper coupling is intentional data use, not a dead probe: claudeDoctor parses install method and release channel; those values determine latestVersion, needsUpdate, and whether an update action is offered. Existing channel-aware test cases require an update for the latest channel but not the stable channel when the installed version equals the stable tag. Without another source of channel data, removing the diagnostic cannot retain both outcomes.

6. Proposed fix and simple-fix gate

Separate passive installation discovery from diagnostic execution. Use a documented authentication-neutral source of installation method and channel, or explicitly accept an unknown-channel policy that only offers updates safe for either channel and only for an identified installer. Preserve the separate health and usage paths. Test divergent release channels, nonstandard native executable paths, and externally managed packages before shipping.

No automatic fix PR: the decision-free simple-fix gate is not satisfied. The only channel and native-installer metadata currently comes from the diagnostic. Deleting the call changes update eligibility and installer ownership; replacing the metadata source or accepting those behavior changes needs a product decision. No production patch, branch, commit, or push was attempted for the target repository. The line/file limits and post-fix test gates therefore do not apply. This is not a duplicate-PR skip: the linked PR is closed and unmerged, and the open-PR search found no link to this issue.

7. Linked PR review

PR #7128 — static review only

GitHub metadata marks #7128 closed and unmerged. Its diff was read only after the independent reproduction was authored. No code, fixture, or branch from it was executed.

It removes the diagnostic and parser, uses a known target version only when stable and latest agree, and limits native update actions to the conventional executable location while retaining npm-global detection. Static conclusion: it addresses the verified dispatch mechanism, but approval depends on intentional update-policy tradeoffs.

  • Medium, provider-maintenance.ts / latestVersion and needsUpdate: for divergent tags, latest-channel users at the stable version no longer receive the update previously offered. Trusted-main tests demonstrate the old distinction; the diff intentionally replaces that behavior.
  • Medium, provider-maintenance.ts / canRunUpdate: native installs outside the conventional path lose update actions without the diagnostic's install-method proof. This is conservative but not behavior preserving.
  • Tests executed for this report apply only to trusted main; no claim that the linked PR passes tests is made.
