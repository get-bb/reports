1. TL;DR

The report describes browser discovery failing in a BB Codex session on macOS while the desktop upstream application can access the browser. This investigation had only Linux, not the Mac, its desktop applications, or the exact upstream executable. It therefore does not reproduce or refute the reported symptom. A new boundary probe against unchanged trusted-main production code shows that BB's Codex bridge passes arbitrary synthetic inherited context to an actual child process and leaves missing context absent. That supports an unresolved host-lifecycle or launch-provenance question, not a demonstrated environment-filtering defect. Both clean checkouts passed the same three probe cases plus 13 existing launch/connection tests.

Investigation-only probe

import { mkdtemp, readFile, rm } from "node:fs/promises";
import { tmpdir } from "node:os";
import { join } from "node:path";
import { afterEach, expect, it, vi } from "vitest";
import { experimental_createBridgeJsonRpcTestHarness as createBridgeJsonRpcTestHarness } from "@get-bb/plugin-sdk/provider-bridge/testing";
import { experimental_killAllChildrenForTests, handleLine } from "./bridge.js";

const probeChild = `
const { writeFileSync } = require("node:fs");
const { createInterface } = require("node:readline");
writeFileSync(process.argv[1], JSON.stringify({
  pipe: process.env.SYNTHETIC_HOST_PIPE ?? null,
  identity: process.env.SYNTHETIC_HOST_IDENTITY ?? null
}));
createInterface({ input: process.stdin }).on("line", (line) => {
  const message = JSON.parse(line);
  if (message.id === undefined) return;
  const result = message.method === "model/list"
    ? { data: [{ id: "synthetic-model", model: "synthetic-model", isDefault: true }], nextCursor: null }
    : {};
  process.stdout.write(JSON.stringify({ id: message.id, result }) + "\\n");
});
`;

let harness: ReturnType<typeof createBridgeJsonRpcTestHarness> | undefined;
let temporaryDirectory: string | undefined;

afterEach(async () => {
  experimental_killAllChildrenForTests();
  harness?.restore();
  vi.unstubAllEnvs();
  if (temporaryDirectory) {
    await rm(temporaryDirectory, { recursive: true, force: true });
  }
});

it.each([
  { label: "inherited pair", pipe: "synthetic-pipe", identity: "synthetic-identity" },
  { label: "missing identity", pipe: "synthetic-pipe", identity: undefined },
  { label: "absent pair", pipe: undefined, identity: undefined },
])("observes $label at the app-server process boundary", async ({ pipe, identity }) => {
  temporaryDirectory = await mkdtemp(join(tmpdir(), "bb-host-context-probe-"));
  const outputPath = join(temporaryDirectory, "synthetic-context.json");
  vi.stubEnv("SYNTHETIC_HOST_PIPE", pipe);
  vi.stubEnv("SYNTHETIC_HOST_IDENTITY", identity);
  vi.stubEnv("BB_CODEX_BRIDGE_APP_SERVER_COMMAND", process.execPath);
  vi.stubEnv("BB_CODEX_BRIDGE_APP_SERVER_ARGS", JSON.stringify(["-e", probeChild, outputPath]));
  harness = createBridgeJsonRpcTestHarness(handleLine);
  harness.sendRequest(1, "model/list", {});
  const response = await harness.waitForResponse(1);
  expect(response.error).toBeUndefined();
  expect(JSON.parse(await readFile(outputPath, "utf8"))).toEqual({
    pipe: pipe ?? null,
    identity: identity ?? null,
  });
});

5. Root cause: not established

Only the following mechanisms are established at the recorded commit:

  1. The provider runtime builds its child environment from the inherited sanitized environment plus explicit runtime and adapter overrides. That upstream-to-bridge boundary was inspected, not dynamically exercised by this probe.
  2. The normal Codex launcher selects codex app-server unless a launch override is set. This does not prove which binary the reporter ran.
  3. The Codex bridge copies its inherited environment, overlays selected supported per-request values, then sanitizes it:
    const env: NodeJS.ProcessEnv = { ...process.env };
...
return withoutBridgeRuntimeEnv(
  sanitizeInheritedChildProcessEnv({
    env: appServerLaunchEnv(envVars),
  }),
);
  4. The shared sanitizer removes undefined entries, NODE_ENV, and BB_-prefixed keys; it otherwise copies values. The bridge-runtime filter removes Electron's Node-launch flag and the bridge recording directory.
  5. The bridge constructs the launch and passes that environment to the app-server child. The probe exercises this path, not a parallel helper implementation.

Inference, not a confirmed cause: an upstream desktop-managed host may require launch context or a lifecycle that a standalone app-server process does not have. The test cannot distinguish unsupported upstream integration, a missing host lifecycle, the wrong executable, an earlier-parent environment difference, or a platform-specific restriction. There is no basis here to copy identities, bypass checks, add environment forwarding, or assert that Chrome permissions are responsible.

6. Proposed next experiment and fix gate

Not confident enough to propose a production fix. On an isolated consenting Mac, first establish the exact BB-launched executable and version. Compare presence-only diagnostics at the host daemon, provider bridge, and app-server process boundaries against the supported desktop launch; do not log values, identities, or private tab data. Determine from the supported upstream contract who initializes and owns the host, and whether that host may be reused by a standalone client. Only then decide whether BB needs an actionable prerequisite message or an authorized integration.
