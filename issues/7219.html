#7219 · Legacy update responses crash Settings

BugHigh priorityMedium effortuiGitHub issueNovember 7, 2026

Verdict: REPRODUCED · Root-cause confidence: high · Reproduction label: confirmed-repro

Trusted main base: 88c78686805e828dda9f8d61fd5cd29aca26c138.

1. TL;DR

The current Settings update row crashes when an older server returns update status without scheduling fields. The row checks that scheduled is not null, but an absent field is undefined, which passes that check. It then reads requiredIdleMs from undefined and throws the exact reported exception. A focused test against unchanged main reproduced this twice, including once in a second clean checkout. This verifies the rendering defect and legacy-response trigger, not the reporter's exact installed client/server combination or the claim that every thread was affected.

5. Root cause

The current update row assumes a present nullable field:

if (status.scheduled !== null) {
  ...
  scheduledAppUpdateCaption(
    status.runningThreadCount,
    status.scheduled.requiredIdleMs,
  )
}

For a legacy response, undefined !== null is true. The branch therefore dereferences an absent object. This is independent of whether update-when-idle is enabled: the row performs the check whenever it renders idle update status.

The SDK appUpdate implementation forwards decoded JSON without normalizing old response shapes. Its TypeScript return type does not add missing JSON fields. The current contract requires scheduling metadata, but that is not a runtime guarantee for an older server.

Historical supporting evidence was read, not executed: the 0.48.0 contract has no scheduled, autoUpdate, or availableSkipped. Scheduling was added in b4b1e4a85e. Mixed client/server versions can therefore expose a genuine previously shipped payload, rather than an arbitrary malformed fixture. The report does not claim proof of which version pairing the reporter was running.

6. Proposed fix and verification

Treat both null and an absent scheduling object as no scheduled update at this rendering compatibility boundary:

- if (status.scheduled !== null) {
+ if (status.scheduled != null) {

This keeps valid scheduled responses on the existing path and does not change public contracts, SDK types, server policy, persisted data, or daemon messages. The regression protects the user-visible Update control using the existing real component test harness; existing cases already cover non-null scheduled updates and cancellation.
