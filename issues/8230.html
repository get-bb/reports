#8230 · Unchanged browser tasks bypass Turbo caching

Bug Priority: Low Effort: Low plugins, perf GitHub issue · November 26, 2026

Trusted base: b0ddaad731565d7e4de68d824120d802fc78f7d5

REPRODUCED · Root-cause confidence: high · Reproduction label: confirmed-repro

1. TL;DR

Developers rerunning this plugin's build and tests pay the execution cost even when no input changes. Two unchanged runs successfully build the plugin and pass all 109 tests, but both tasks explicitly bypass the cache with identical hashes. The package's Turbo configuration disables caching for these tasks. The same result occurs in a second clean checkout at the identical trusted main commit; this is a build-efficiency defect, not failing browser functionality.

5. Root cause

The package task overrides set cache: false for both build and test. Turbo resolves both tasks as non-cacheable; a valid unchanged hash does not enable reuse. This explains the repeated cache bypass, force executing messages despite successful previous executions.

    "build": {
      "dependsOn": ["@get-bb/plugin-sdk#build:types", "@bb/cli#build"],
      "cache": false
    },
    "test": {
      "dependsOn": [
        "//#ensure-native-modules",
        "@get-bb/plugin-sdk#build",
        "topo"
      ],
      "inputs": [
        "$TURBO_DEFAULT$",
        "$TURBO_ROOT$/packages/plugin-registry/flavors/**"
      ],
      "cache": false

The build override lists SDK declarations and the CLI build but omits a direct topo edge. The test override already includes topo and explicit flavor inputs. The package scripts and dependencies identify the real build/test commands and shared-ui dependency. A cache-enabling change should preserve dependency invalidation, not merely remove the symptom.

6. Proposed fix

Restore the inherited caching policy for build and test while retaining disabled caching for real-browser smoke tasks. Ensure the build has a direct dependency-hash path for source it bundles, then verify unchanged reruns, output restoration, and shared-ui/flavor input invalidation. No fix is applied in this investigation because open PR #8231 already links this issue; opening a second PR would duplicate that work.

10. Appendix and limitations

The first cold plugin-only build in each checkout failed because the built SDK runtime was absent: Could not resolve "@get-bb/plugin-sdk/process". The build task only depends on SDK declarations. Building the SDK through Turbo resolves this setup prerequisite; subsequent plugin builds and all four measured runs succeed. This separate prerequisite gap is not repaired or attributed to caching, and no unrelated source changes are made.
