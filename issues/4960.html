#4960 · Session identity is missing from the provider child environment

BugMedium priorityLow effortprovidersprovider-codexconfirmed-reproIssue2026-10-05 · base c5b97d7aa265becdfed89ec837fdc6f20a4f3e06

Verdict: REPRODUCED · Root-cause confidence: high

1. TL;DR

A provider-launched tool cannot obtain the serving thread's identity from its parent process when that identity never reaches the parent. The Codex bridge accepts a session environment and sends its four thread-context values in shell configuration, but omits them from the environment of the app-server subprocess. A reproduction using the real bridge and a real spawned Node subprocess observed an empty identity object, while all four values were present in the shell-policy request. The same failure occurred in a second clean checkout. This verifies BB's process-boundary defect; upstream Codex MCP environment forwarding was not exercised.

5. Root cause

  1. The runtime constructs session-owned identity in buildThreadShellEnvironment: thread, environment, and optional project/storage values.
  2. appServerLaunchEnv and buildAppServerEnv use the parent process environment, overlaying only the account-pool variables from session options. They never overlay session identity. The inherited environment sanitizer then drops every BB-prefixed value.
  3. sanitizeInheritedChildProcessEnv intentionally scrubs all inherited BB_* values and NODE_ENV. Merely merging identity before that sanitizer would still lose it.
  4. spawnChildConnection supplies the resulting environment to the actual portable subprocess spawn. The separate recordThreadId field is used for recording; it does not export thread identity to the process.
  5. buildCodexConfig supplies identity through shell_environment_policy.set.*, explaining the passing shell-policy assertions despite the empty parent environment.
function buildAppServerEnv(
  envVars: Readonly<Record<string, string>> | undefined,
): NodeJS.ProcessEnv {
  return withoutBridgeRuntimeEnv(
    sanitizeInheritedChildProcessEnv({
      env: appServerLaunchEnv(envVars),
    }),
  );
}

The deeper distinction is session-owned environment versus inherited daemon/runtime environment. Shell configuration handles the former; the app-server launch path handles only the latter, plus its narrow pool-routing exception.

6. Proposed fix and automation safety

After sanitizing inherited runtime state, a reviewed provider-local change could explicitly restore an agreed allowlist of session-owned identity keys for thread-bound app-servers only. Never copy arbitrary BB-prefixed session or parent variables, never fall back to stale parent identity, and preserve thread-free model/maintenance isolation. Tests should cover absent optional context, unrelated session and inherited variables, and repeated thread launches.

No automatic fix PR: this would expand what the sanitized provider-child environment exposes to downstream tool processes. It changes a process-isolation/security boundary, which the autopilot's simple-fix conditions expressly exclude. No production code was modified, committed, or pushed. Low effort describes the likely implementation size; it is not authorization to bypass this safety gate.
