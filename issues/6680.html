#6680 · Dispatch admission and replay safety

BugPriority: MediumEffort: Highplugins · tasksGitHub issueOctober 30, 2026

Verdict: REPRODUCED · Root-cause confidence: high

Trusted base: 6c9c7cca66afe48b2da6ecdb3290bf441dfb3280, fetched directly from get-bb/bb main. Reproduction label: confirmed-repro.

1. TL;DR

The real Tasks control sends two delegate RPCs when two click events enter before React commits its pending state. The real delegate handler independently requests a new thread for every delivery, including overlapping requests and a request replayed after a simulated lost reply. A simulated ambiguous SDK failure also leaves no attached row or retained dispatch outcome, so a retry requests another thread. The existing request contains no attempt identity: identical inputs can mean either a retry or an intentional second dispatch, so globally deduplicating task/preset pairs would break supported behavior. These results were repeated by the same investigator in a second clean trusted checkout; real provider execution, browser double-click timing, and process-crash recovery were not tested.

5. Root cause

UI state is not a synchronous admission guard

DispatchControl, lines 156–182 sets React state then immediately sends the RPC. It does not synchronously record that an invocation has been admitted. The rendered disabled state only takes effect after commit, so another event batched before that commit enters the same function.

const dispatch = async (presetId: string) => {
  setDispatching(true);
  try {
    await rpc.call("delegate", { taskId, presetId });
  } finally {
    setDispatching(false);
  }
};

This excerpt omits only the error-reporting catch. The independently authored UI test uses the existing real app slot and one of the two responsive copies of the actual dispatch control; it does not substitute a fake React component.

Server spawning precedes persistence and has no replay key

delegate, lines 298–366 reads task/preset context, awaits environment selection, and calls bb.sdk.threads.spawn. Only after that await succeeds does a SQLite transaction attach the returned thread and create comments. There is no pending admission entry, completed-attempt lookup, or unknown-outcome record before spawn. Different returned thread IDs create distinct attached rows. Transactional attachment cannot undo or deduplicate an external spawn effect that already happened.

The strict delegate input schema contains only taskId, presetId, and optional instructions. It cannot identify a retry of a particular dispatch attempt. The CLI dispatch path calls this same handler without any attempt identity, so a UI-only lock cannot provide server retry safety.

6. Proposed fix and simple-fix decision

Add a synchronous, per-control pending latch to close the batched-event admission gap and release it in a finally path. Separately design explicit dispatch-attempt identity across UI, RPC, and CLI so retries can reuse an identity and deliberate dispatches can create a fresh one. A durable attempt record should reserve before spawn, replay completed results, reject payload mismatches, and preserve ambiguous outcomes instead of automatically spawning again. A plugin record alone cannot atomically commit an external core spawn; recovery and user-visible unknown-outcome behavior require an explicit policy.

No automatic fix PR: the complete retry-safe repair needs a request-contract change and durable stored state or a broader core idempotency design, plus an unknown-outcome policy. Those violate this rule's no-schema/no-stored-data/no-architecture-decision simple-fix conditions. A task/preset in-memory mutex alone would neither survive restart nor distinguish a legitimate new dispatch. A UI-only patch would leave the verified server retry defect unresolved. No production fix branch, commit, or push was made.
