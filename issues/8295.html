#8295 · Successful catalog refresh discards previously advertised models

BugPriority: MediumEffort: Mediumprovidersprovider-acp GitHub issue2026-11-27 · base b0ddaad731565d7e4de68d824120d802fc78f7d5

Verdict: REPRODUCED at the server catalog boundary. Root-cause confidence: high for replacement and persistence; the upstream OpenCode startup trigger remains unverified.

1. TL;DR

A successful refresh containing fewer models replaces the cached catalog, even when the provider launch fingerprint has not changed. An isolated reproduction begins with two picker models and one selected-only model, then supplies a successful response containing just one picker model. The server removes both omitted models from its response and SQLite row, advances the freshness timestamp, reports success without a model-load error, and emits one picker invalidation. An otherwise identical failed refresh retains all three models and the original row, demonstrating that failure fallback does not protect this case. The same agent repeated this result in a second clean checkout; this report does not claim to have reproduced OpenCode's location-plugin activation race.

5. Root cause

The store has a last-good fallback for reported failures, but a successful response takes a different branch. Success is not checked for completeness before replacing the cached arrays. Matching fingerprints preserve previously known reasoning metadata only for models still present in the new response; they do not preserve omitted model IDs.

6. Proposed fix and safety decision

First establish how this provider can distinguish an incomplete discovery response from an intentional model removal. Prefer a provider-supported readiness or completeness signal, then preserve the last good catalog only when the response is demonstrably incomplete. If bounded repeated-observation handling is chosen instead, its acceptance threshold, cooldown, restart behavior, and treatment of mixed additions/removals must be defined as product policy.

No automatic fix PR: a blanket subset guard would also hide legitimate removals. Choosing how long to retain missing models, or introducing a completeness contract, requires a product or protocol decision. Therefore the simple-fix condition that forbids such decisions is not met. No production patch was made, committed, or pushed.

The local reproduction changes one test file with 65 additions and no deletions. There are no binary changes; git diff --check passes. Its expected failing assertions document the reported retention requirement, not an already specified authoritative-shrink policy. Follow-up coverage should distinguish temporary incomplete discovery from genuine removal, changed launch fingerprints, and mixed model additions/removals.
