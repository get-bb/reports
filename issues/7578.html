1. TL;DR

The mobile sender puts registered devices into requests by count, not by Expo project. When the transport rejects a mixed-project request, the sender abandons every device in that request and returns only the other delivery channels. A focused regression exercises registration, the actual plugin send RPC, status CLI, and read-dismissal events with a deterministic Expo transport substitute. It fails on trusted main in two clean checkouts. A ten-line sender repair splits only cross-project-rejected batches into smaller requests; all 67 plugin tests, lint, and typecheck then pass. This is not evidence of live Expo acceptance or on-device OS delivery.

5. Root cause

Subscription batching and outcome aggregation create one delivery per subscription and split solely at the 100-message request limit:

    const deliveries: Delivery[] = rows.map((subscription) => ({
      subscription,
      message: {
        to: subscription.expoPushToken,
        title,
        body,
        data: { ...data, subscriptionId: subscription.id },
        sound: "default",
        channelId: "threads",
        priority: "high",
      },
    }));
    let sentCount = 0;
    let failure: string | null = null;
    for (const batch of chunks(deliveries, EXPO_PUSH_BATCH_SIZE)) {
      const result = await sendBatch(batch);
      sentCount += result.sentCount;
      failure ??= result.failure;
    }
    await setLastOutcome(
      failure === null
        ? { status: "sent", at: now(), sentCount }
        : { status: "failed", at: now(), reason: failure },
    );
    return sentCount > 0 ? [...channels, "mobile"] : channels;

The request-error branch treats every error code as terminal and returns no accepted deliveries:

    if (parsed.data.errors && parsed.data.errors.length > 0) {
      const codes = parsed.data.errors.map((error) => error.code ?? "unknown");
      bb.log.warn(
        `Expo push request was rejected with codes ${codes.join(", ")}`,
      );
      return { sentCount: 0, failure: "relay rejected the request" };
    }

Thus a mixed-project rejection affects unrelated valid devices together. Individual tokens carry no locally stored Expo-project partition, and the sender neither learns a partition nor narrows a rejected request. Read-dismissal pushes share the same batch sender, so fixing only notification creation would miss that path.

6. Proposed fix and verification

For PUSH_TOO_MANY_EXPERIENCE_IDS only, split a rejected batch in half and retry its two halves. Stop splitting at one subscription. Preserve each delivery object so ordinary ticket indexing, unregistered-device removal, accepted-ticket counts, and failure aggregation still work. Other request failures and network failures retain their existing behavior. Successful homogeneous batches are not resent.

This avoids new project metadata, persisted state, schema changes, public protocols, dependencies, or external response-details parsing. The tradeoff is extra relay requests whenever a batch mixes projects: a completely interleaved batch can use up to 2n − 1 requests including failed parents; recursion depth is logarithmic, and each original batch has at most 100 deliveries. An optimization that caches project partitions is intentionally outside this contained fix.

Local repair: 10 production additions and 141 test additions across two files, 151 total changed text lines. The regression checks successful alert delivery and diagnostic counts, dismissal delivery, ticket failure propagation, removal of the correct unregistered row after splitting, and token-free logs. Two guard cases prove no repeated request for an already-singleton cross-project rejection or an unrelated request error.
