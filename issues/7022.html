#7022 · Unregistered providers survive thread creation

BugPriority: MediumEffort: LowprovidersthreadsIssue #70222026-11-04

Base: d060de8e30f3310417054a74510a774dd2909e2b · Verdict: REPRODUCED · Root-cause confidence: high

1. TL;DR

The thread-creation API accepts a provider ID that does not exist in its provider registry. With an explicit model, creation returns HTTP 201 and persists the invalid ID. Advancing the real server provisioning path puts that thread into an error state, and sending its next message returns HTTP 409 with provider_bridge_unavailable. The defaults resolver rejects disabled and failed registrations, but accidentally permits a missing registration. Rejecting that case before persistence is a contained server-side repair; existing invalid threads are outside its scope.

Complete reproduction test

import { getThread } from "@bb/db";
import { threadSchema } from "@bb/domain";
import { describe, expect, it } from "vitest";
import { advanceThreadProvisioning } from "../../src/services/threads/thread-provisioning.js";
import { readJson } from "../helpers/json.js";
import {
  seedEnvironment,
  seedHostSession,
  seedProjectWithSource,
} from "../helpers/seed.js";
import { withTestHarness } from "../helpers/test-app.js";

describe("provider admission reproduction", () => {
  it("persists an unregistered provider and rejects its first send", async () => {
    await withTestHarness(async (harness) => {
      const providerId = "unregistered-provider";
      expect(harness.deps.providerRegistry.get(providerId)).toBeNull();
      const { host } = seedHostSession(harness.deps);
      const { project } = seedProjectWithSource(harness.deps, {
        hostId: host.id,
      });
      const environment = seedEnvironment(harness.deps, {
        hostId: host.id,
        projectId: project.id,
        status: "ready",
      });
      const response = await harness.app.request("/api/v1/threads", {
        method: "POST",
        headers: { "content-type": "application/json" },
        body: JSON.stringify({
          origin: "sdk",
          projectId: project.id,
          providerId,
          model: "test-model",
          input: [{ type: "text", text: "ok" }],
          environment: { type: "reuse", environmentId: environment.id },
        }),
      });
      console.log("create status:", response.status);
      expect(response.status).toBe(201);
      const thread = threadSchema.parse(await readJson(response));
      expect(getThread(harness.db, thread.id)?.providerId).toBe(providerId);
      console.log("persisted provider:", thread.providerId);
      await advanceThreadProvisioning(harness.deps, { threadId: thread.id });
      console.log("thread status:", getThread(harness.db, thread.id)?.status);
      const sendResponse = await harness.app.request(
        `/api/v1/threads/${thread.id}/send`,
        {
          method: "POST",
          headers: { "content-type": "application/json" },
          body: JSON.stringify({
            input: [{ type: "text", text: "ok" }],
            mode: "queue-if-active",
          }),
        },
      );
      const sendBody = await readJson(sendResponse);
      console.log("send status:", sendResponse.status);
      console.log("send body:", JSON.stringify(sendBody));
      expect(sendResponse.status).toBe(409);
      expect(sendBody).toMatchObject({
        code: "provider_bridge_unavailable",
      });
    });
  });
});

5. Root cause

The request schema accepts any nonempty providerId string. That is appropriate for dynamically registered providers, but it requires a registry membership check at the server boundary.

The shared defaults policy selects an explicit ID as-is, rejects disabled IDs, then checks only registrations which are not null:

const registration = registry.get(providerId);
if (registration !== null && !registration.info.available) {
  throw new ApiError(409, "provider_unavailable", ...);
}
return { providerId, providerFallbackCandidates: ... };

A missing registration therefore passes. Explicit models skip catalog default resolution, so supplying a model does not incidentally catch the bad ID. Thread creation persists the selected provider and the HTTP route returns 201.

Later the startup command builder requires a bridge. An absent registration resolves to no bridge; the bridge guard throws HTTP 409. Provisioning catches startup errors and records failure. This is a deterministic admission-validation gap, not a provider-login or host-bridge installation failure.

6. Proposed fix

In the existing shared creation defaults policy, reject registration === null with the existing 400/invalid_request response before returning execution defaults. Include registered IDs in the diagnostic. Keep existing disabled/unavailable responses unchanged; do not hard-code aliases or change SDK/daemon schemas. A focused API regression asserts 400 plus zero created threads and fails before the fix with expected 201 to be 400; pre-fix evidence appears in the appendix.

No stored-data migration or automatic repair of existing invalid threads is proposed. Registered but temporarily unhealthy providers remain governed by their existing policies.
