#6325 · Provider fork uses the wrong transcript environment

BugHighEffort: Mediumproviders · threads · provider-claude-codeIssueOctober 26, 2026 · base 3540a699e29034b53da32bb7efa6f5b4055209eb

Verdict: REPRODUCED · Root-cause confidence: high · reproduction label: confirmed-repro

1. TL;DR

A fork request cannot locate a valid Claude transcript when its directory is supplied through project execution options rather than the bridge process environment. The bridge invokes the real SDK's in-process fork before applying the environment used for the resumed session. Two runs of a focused test against unchanged production code return JSON-RPC error -32000 with Session … not found. A positive control forks the exact same synthetic history successfully when the SDK process points at the transcript directory. This confirms the provider-boundary bug without real accounts or model calls; it does not independently confirm the claimed subsequent empty conversation in a running UI or CLI.

5. Root cause

Execution options are converted to the internal config without modifying the bridge's process environment: plugins/provider-claude-code/src/session-params.ts:59 and plugins/provider-claude-code/src/session-params.ts:102.

function buildClaudeCodeConfig(
  envVars?: Record<string, string>,
): Record<string, unknown> | undefined {
  if (!envVars) {
    return undefined;
  }
  const overrides = buildShellEnvOverrides(envVars);
  return Object.keys(overrides).length > 0 ? { envVars: overrides } : undefined;

The session attachment builds a subprocess environment from this config: plugins/provider-claude-code/src/bridge/bridge.ts:2336. Its environment helpers merge config overrides into a new object rather than changing process.env: plugins/provider-claude-code/src/bridge/bridge.ts:1729.

function buildSessionEnv(
  envOverrides: Record<string, string>,
): NodeJS.ProcessEnv {
  const sessionEnv: NodeJS.ProcessEnv = {
    ...withoutBridgeRuntimeEnv(process.env),
    ...envOverrides,
    CLAUDE_CODE_ENTRYPOINT: "cli",
  };
  delete sessionEnv.CLAUDE_AGENT_SDK_CLIENT_APP;
  return sessionEnv;
}

const sessionConfigEnvVarsSchema = z.record(z.string(), z.string());

function readConfigEnvOverrides(
  config: Record<string, unknown> | undefined,
): Record<string, string> {
  const parsed = sessionConfigEnvVarsSchema.safeParse(config?.["envVars"]);
  return parsed.success ? parsed.data : {};
}

However, fork lookup happens first, inside the bridge process. Only the checkpoint is passed to the SDK; neither the configured environment nor a session store is applied: plugins/provider-claude-code/src/bridge/bridge.ts:2457.

  let forkedProviderThreadId: string;
  try {
    const forkResult = await forkSession(params.sourceProviderThreadId, {
      ...(params.sourceProviderCheckpointId !== undefined
        ? { upToMessageId: params.sourceProviderCheckpointId }
        : {}),
    });
    forkedProviderThreadId = forkResult.sessionId;
  } catch (error) {
    const message = error instanceof Error ? error.message : String(error);
    sendError(id, -32000, message);
    return;
  }

  attachThreadSession(id, params, forkedProviderThreadId, true);
}

SDK 0.3.245 resolves filesystem transcript storage from its own process environment. The positive control establishes this dynamically, without relying only on SDK source inspection. Passing a working-directory selector alone cannot supply a different config root; a safe fix must consistently use the session's transcript environment without leaking one project's environment into another concurrent request.

Separate retry mechanism

The retry service replays unaccepted original input, which can be empty for a fork: apps/server/src/services/threads/turn-retry.ts:108. For an already provisioned environment, dispatch does not restore the interrupted startup context: apps/server/src/services/threads/dispatch-attempt.ts:346. A ready start defaults to fork: null: apps/server/src/services/threads/thread-send.ts:658. The command builder only emits a fork descriptor when one is present: apps/server/src/services/threads/thread-commands.ts:285.

The contract explicitly permits empty input only for a fork: packages/host-daemon-contract/src/commands.ts:289.

The daemon turns failed message validation into the reported generic RPC error: apps/host-daemon/src/server-connection.ts:597. This mechanism is supported by static tracing and a real schema probe, not a full retry integration run. Relaxing the schema is unnecessary: preserving fork intent is the safer next experiment.

6. Proposed fix and automation safety gate

Make fork lookup use the same session-specific transcript environment as the resumed process, while preserving checkpoint truncation and isolating concurrent projects. Candidate designs are a per-call SDK store adapter or a subprocess-owned fork/resume lifecycle. Do not simply leave process.env changed around an awaited SDK operation: the bridge can handle concurrent work. Separately, preserve the original fork descriptor when retrying a failed initial fork rather than dispatching an empty normal start.
