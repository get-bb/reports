1. TL;DR

The report concerns a native HTML select menu allegedly appearing at the origin of the Android WebView on large windows. The trusted dependency sources contain a plausible explanation: a React Native container terminates child layout requests, and the patched WebView does not explicitly replay its own child layout. Those facts were checked twice at the same trusted main commit. This host has no Java executable, Android device bridge, or emulator, so no Android popup was opened and no visual behavior was reproduced. NOT REPRODUCED describes this investigation's limitation, not evidence that the reported defect is absent. An existing open fix PR means no duplicate fix is appropriate.

5. Root cause

Plausible mechanism, not runtime-confirmed: the shell embeds the WebView in an animated native View. React Native's installed ReactViewGroup requestLayout method has no executable body, so a WebView-owned child can request layout without the normal parent traversal completing. RNCWebView has no requestLayout override to arrange an explicit local measure/layout pass. If Chromium creates a popup anchor child under these conditions, missing layout could leave it at the WebView origin. This investigation did not establish whether Chromium actually creates that anchor in this app/window, its bounds, or the exact wide-window threshold.

  • Shell frame and WebView placement, line 312.
  • ShellWebView renders the third-party WebView, line 399.
  • Android frame renders Animated.View, line 32.
  • Existing WebView patch adds inset handling, but not child-layout replay, line 45.
  • Trusted dependency manifest; dependency code below was inspected after the frozen install, not fetched from issue links.
