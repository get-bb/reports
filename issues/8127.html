#8127 · Unchanged marketplace refresh downloads Git repositories again

BugPriority: MediumEffort: Mediumplugins, perfGitHub issueNovember 24, 2026

Trusted origin/main: 83368cff5166aa01ff4706056995a7626e859555

Verdict: REPRODUCED · Root-cause confidence: high · Reproduction label: confirmed-repro

1. TL;DR

A Git-backed marketplace refresh downloads and checks out a fresh repository even when the registered branch still identifies the same commit. A real-service regression using a real SQLite database and a local Git fixture recorded one clone on registration and another on an unchanged refresh. A separate file-transport probe confirmed that materialization checks out a file unrelated to the catalog and removes Git metadata afterward. The same agent repeated both checks in a second clean checkout of the exact trusted base commit. The reported large-repository timings were not benchmarked here.

5. Root cause

The refresh service persists the resolved commit, but omits it from the cached materialization input. performRefresh cache input supplies only the manifest and HTTP validators. materializeMarketplace passes that cache to HTTPS handling but never passes it to Git handling.

materializeGit unconditionally creates a fresh checkout, runs an unfiltered, non-shallow clone, resolves a commit from that already-downloaded repository, checks out the full tree, and deletes .git. There is no remote-ref comparison before the clone. Resolving the commit after the download cannot save transfer time. The real service then stores the same commit again at the refresh transaction and disposal.

clone --quiet --no-checkout <source> <fresh-checkout>
rev-parse --verify --end-of-options <ref>^{commit}
checkout --quiet --detach <commit>
rm(checkout/.git)

The direct probe establishes whole-tree checkout independently of command interpretation. The source establishes that no depth or object filter limits the clone. The test protects the observable download cost at the Git subprocess boundary rather than merely checking source strings.

6. Proposed fix (first principles)

Pass the persisted Git commit into materialization, resolve the requested remote ref before transfer, and reuse the validated stored catalog when the commit matches. Preserve existing cached icon bytes on that path. For changed commits, bound history and objects and materialize only the catalog and required local assets where supported. Preserve branch/tag/commit resolution and current path validation; remote capability failures and malformed cache contents need explicit fallback tests. These are proposals, not a fix verified by this report.
