#7647 · Pi confirmation validation synthesizes cancellation

BugPriority: MediumEffort: Mediumprovidersprovider-piconfirmed-repro

GitHub issue2026-11-16Base: 2fef0456de9bd1ea25205c7bc9ca5e42859b2c26

Verdict: REPRODUCED · Root-cause confidence: high

1. TL;DR

The Pi bridge rejects confirmation details longer than 8,192 JavaScript string code units before asking bb to show an interaction. It immediately returns {cancelled:true}, even though no user has made a decision. The Pi RPC implementation maps that cancellation response to false for confirmation dialogs. A new test at the real bridge coordinator reproduces the premature cancellation at 8,193 and 32,768 code units, while the 8,192-unit control waits for a runtime response and accepts true. The same test gives the same results in a second clean checkout at the trusted main commit.

This is a direct bridge-level reproduction, not a replay of the reporter's extension or an end-to-end model session. No production bb data, real account, network model, or live instance was used.

it.each([8192, 8192 + 1, 32768])(
  "waits for a user decision for a %i-code-unit confirmation",
  (length) => {
    const interactions: InteractionUiRequest[] = [];
    const responses: PiExtensionUiResponseFields[] = [];
    const message = "r".repeat(length);
    const coordinator = createExtensionUiCoordinator({
      sendInteractionRequest: (request) => interactions.push(request),
    });

    coordinator.handle({
      scope: {},
      request: {
        id: "confirmation-boundary",
        method: "confirm",
        title: "Review pending update",
        message,
      },
      threadId: "thr_boundary",
      providerThreadId: "pi_boundary",
      respond: (_requestId, fields) => responses.push(fields),
    });

    console.info(
      JSON.stringify({
        length,
        interactionCount: interactions.length,
        responseBeforeUserDecision: responses,
        retainedMessageLength:
          interactions[0]?.params.payload.data.message?.length ?? null,
      }),

    expect(responses).toEqual([]);
    expect(interactions).toHaveLength(1);

    expect(interaction.params.payload.data.message).toBe(message);

        id: interaction.id,
        result: { kind: "request_answer", value: true },
      }),
    ).toBe(true);
    expect(responses).toEqual([{ confirmed: true }]);
  },

5. Root cause

  1. The actual provider routes extension UI requests through the tested coordinator. See bridge.ts:429–443.
  2. The request schema sets message: boundedText(8192).optional(). The bound is JavaScript string length, so ASCII characters in this test each occupy one UTF-16 code unit. See extension-ui-contract.ts:11–30.
  3. When validation fails, the coordinator immediately calls args.respond(id, { cancelled: true }) and returns. It never reaches pending-map insertion or sendInteractionRequest. See extension-ui.ts:85–133.
  4. The transport writes those response fields unchanged into an extension_ui_response. See rpc-child.ts:286–293.
  5. In the pinned Pi dependency, dist/modes/rpc/rpc-mode.js, line 85, confirmation response parsing uses "cancelled" in r && r.cancelled ? false : "confirmed" in r ? r.confirmed : false. Thus a bridge validation failure is indistinguishable from a negative confirmation at the extension's boolean API. The dependency version is fixed in the provider package manifest.

The deeper defect is semantic: an adapter failure is encoded as a user cancellation, discarding the validation reason. The shared payload schema also picks the same bounded message field from the request schema, and the app parses it. Therefore relaxing only a bridge call site would not safely solve the contract end to end. See payload schema and app payload parsing.

6. Proposed fix and autopilot safety gate

Keep validation distinct from user intent. For valid large confirmation details, preserve the full message through the bridge, interaction payload, and renderer rather than silently truncating the material a user is asked to approve. If a request cannot be supported, surface a specific adapter/validation failure rather than claiming the user declined. Add boundary tests for forwarding, explicit acceptance, explicit refusal, and rejected requests; assess resource limits and compatibility before choosing the accepted size policy.

No fix PR was opened. The direct full-detail fix changes the shared request/payload schema. A distinct error result instead requires a supported error contract rather than the current boolean/cancellation response. Schema/protocol changes and the corresponding product decision are explicitly outside this autopilot's simple-fix allowance. No production patch, fix branch, or push to get-bb/bb was attempted. GitHub metadata showed no linked open PR and an open-PR search for this issue returned none.
