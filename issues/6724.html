#6724 · Request progress is excluded from the gate deadline

BugMedium priorityLow effortbug · remote · connectGitHub issue2026-10-30

Verdict: REPRODUCED · Root-cause confidence: high

Investigation base 7877c1c7316e6f68dec3bb1f337158e4a55cd9dd; fix base a0e513398f02d47ec5df874b89fec4edfc248894. No connect-next files changed between these commits.

1. TL;DR

The remote-access gate starts one fixed timer before routing, uploading, and waiting for the server's headers. It does not reset that timer when upload bytes arrive or when forwarding finishes. A healthy tunnel therefore cannot save a request that is actively uploading or whose origin needs longer than the initial budget. Real frps and frpc reproduced both failures twice, in separate clean checkouts; fast controls succeeded. A gate-local repair now tracks upload progress, keeps stalled uploads bounded, and adopts the ten-minute connected-tunnel wait policy already present in trusted main's Cloudflare gate.

5. Root cause

serve, lines 775–805 enters withDeadline before access resolution and forwarding. withDeadline, lines 676–703 arms exactly one timer and races it against the whole operation:

timer = setTimeout(() => resolve(STALLED), deadlineMs);
const work = run();
const winner = await Promise.race([work, stalled]);

No request-body progress can refresh that deadline. At upstreamFetch, lines 386–400, the stage is set to response-head before body.pipe(outgoing), so an upload timeout is misreported as waiting for the origin's headers. Once the same timer wins, the gate aborts the upstream request and emits its own 504. Tunnel presence is not consulted by the timeout path.

Constants and path selection explain why ordinary requests use 30 s and voice transcription uses 90 s at the baseline. Changing that special case alone cannot distinguish progress from inactivity.

6. Fix and safety

The repair stays in connect-next's existing gate and fixtures, plus its documentation: five files, 262 changed text lines (additions plus deletions). It adds a request-body stage, timestamps incoming body progress, and starts a fresh head budget when the outgoing request finishes forwarding. Only an authenticated, routed HTTP request with a known subdomain may keep waiting beyond the head budget, and only while the directory still locates its tunnel. The timer enforces a ten-minute ceiling even when progress or tunnel presence continues.

The ten-minute ceiling is not a new product decision: trusted main already establishes it for the Cloudflare gate. Routing and WebSocket handshakes retain their original bounded behavior. The voice exception is removed in favor of this same rule. No dependency, lockfile, generated file, migration, persisted data, public protocol, schema, access-control rule, or release mechanism changes.

All 6 focused regressions pass after the repair. Relevant existing suites, build, and typecheck:

Not verified: a Fly staging deployment, real image generation/transcription, production proxy limits, or silent-dead-frp detection timing. The presence check uses frp's existing directory lifecycle, not an independent per-request heartbeat. The hard cap bounds that uncertainty.
