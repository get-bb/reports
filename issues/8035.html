#8035 · Spending controls exclude unused Codex capacity

BugPriority: MediumEffort: Mediumproviders · provider-codex · partial-repro GitHub issue2026-11-23 · base 796cdcc0f4bf8a55e23664035c54e8db6fe9d272

Verdict: PARTIALLY REPRODUCED · Root-cause confidence: high for the local exclusion mechanism; upstream spending semantics remain unverified.

1. TL;DR

A reached spending control causes Account Pooler to refuse a Codex account even when its observed primary window is allowed and completely unused. A focused test loading the real plugin entry returns the pool's own HTTP 429 and records zero upstream inference calls. The same agent repeated both spending-control variants in a second clean checkout at the same trusted main commit. This establishes the local refusal, not whether the provider would authorize included usage for the affected real account. Existing documentation and tests deliberately specify the current hard stop, so automatically relaxing it would require a product-policy decision and stronger upstream evidence.

5. Root cause

  1. codexQuotaFromUsage turns either spend_control.reached === true or an individual remaining percentage at or below zero into an account-wide usageRestriction. It also records extra usage as rejected. Neither branch consults the allowed primary window.
  2. isUsageRestricted and accountStatus treats an unexpired restriction as exhaustion before considering window capacity.
  3. AccountPoolHub.select removes usage-restricted accounts before the included-capacity selection tiers, so an otherwise allowed window cannot rescue the account.
  4. No-eligible-account response returns the pool-generated 429 when enabled accounts exist but none can be selected. This explains zero inference calls and an unchanged last-use timestamp.
const restriction =
  control?.reached === true ||
  (individual != null && individual.remaining_percent <= 0)
    ? { reason: "spend_control_reached", ... }
    : ...;

This is an intentional repository contract, not an accidentally ignored field: routing guidance explicitly says reached spending controls block below-threshold routing. existing credit-fallback tests already requires 429 for capped spending with a primary window at 10% utilization. existing observation tests requires the spending restriction and explicit recovery. The mechanism is present in trusted history at 41b9f1f6ec.

6. Fix proposal and safety gate

No production fix or PR is published. The report is partial because it cannot establish that upstream permits the affected account to consume included capacity after its spend control is reached. Changing the documented workspace hard-stop policy fails the simple-fix rule that no product decision be required.

The next decisive experiment is a sanitized, consented direct-provider request paired with the same account's usage observation at the same time, or an authoritative upstream contract separating included usage from spending controls. If included requests are authorized, distinguish credit-fallback availability from plan eligibility in the Codex observation layer, preserve explicit workspace hard stops, account for persisted prior restrictions, and update the shared routing documentation and owner-boundary tests together. Do not indiscriminately ignore all usage restrictions or buy credits.
