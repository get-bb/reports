#7032 · Catalog discovery creates short-lived Claude helpers

2026-11-04 · Type: Bug · Priority: Medium · Effort: Medium · providers, host, provider-claude-code

Verdict: PARTIALLY REPRODUCED · Root-cause confidence: medium · Reproduction label: partial-repro

1. Summary

The reported symptom is repeated Windows console flashes while BB runs inside WSL. This investigation confirms a narrower prerequisite on current trusted main: Claude model and command catalog discovery each start a separate real SDK child process, then close it. An immediate repeated request is cached; cache expiration or creating a fresh pair of bridge memos starts new helpers. The measured cumulative startup counts were 2 → 2 → 4 → 6, repeated in a second clean checkout.

This is not an end-to-end reproduction of the Windows symptom. The machine available here is Linux, not Windows/WSL; the CLI fixture deliberately contains no registry queries and no Windows executables. Neither visible flashes, focus theft, registry subprocesses, nor Antigravity probing were reproduced. No synthetic screenshot is offered as visual evidence.

        available_output_styles: ["default"]

`, { mode: 0o755 });
  const env = {
    PATH: path.dirname(process.execPath),
    HOME: directory,
    BB_CLAUDE_CODE_EXECUTABLE: executable,
    BB_REPRO_START_LOG: starts,

  const makeCatalogs = () => ({
    models: createClaudeCodeBridgeModelListMemo({
      list: () => listClaudeCodeBridgeModels(env),
      now: () => currentTime,
      ttlMs: 120_000,

    commands: createClaudeCodeBridgeCommandListMemo({
      list: (cwd) => listClaudeCodeBridgeCommands(cwd, env),

5. Root cause and code evidence

Verified helper-creation mechanism: probeClaudeInitialization calls SDK query(), waits for initialization, then unconditionally closes that query. It does not reuse a long-lived initialization session.

Model discovery and command discovery separately invoke that helper. The bridge constructs separate two-minute memos, so these two cold calls do not coalesce with each other.

The model memo and working-directory-keyed command memo each retain settled results and share concurrent calls within their own lifetime. This rules out claiming every request starts a helper.

As a separate static observation, maintenance runtimes have a 60-second default idle timeout and retire when idle. A retired worker cannot retain its in-memory catalog caches. The reproduction does not run this timer or establish that it explains the reporter's cadence.

The core provider inventory filters disabled IDs. There is no evidence here to remove or redesign that filter.

Confidence: high for the measured launch/cache mechanism; medium for its contribution to the reported symptom, because the downstream Windows interop and actual provider behavior remain unverified.

7. Fix proposal and safety gate

First reproduce with an isolated Windows 11 + WSL environment using a real Linux-installed Claude CLI and the relevant provider plugin. Capture a real desktop recording together with process creation counts for one catalog refresh, a cache hit, an expiry, and idle-worker retirement. Repeat with that provider disabled to distinguish core inventory requests from plugin-owned polling. Only then decide whether the appropriate owner is catalog reuse, maintenance-worker lifetime, third-party provider polling, or Windows executable resolution.

A possible reduction is to share one initialization result between model and command discovery only when their environment and working-directory semantics match. Model discovery currently uses the bridge working directory while commands are project-specific; blindly sharing a global session would risk stale project commands. Extending cache TTLs or keeping helpers alive indefinitely also changes freshness or resource policy and has not been justified by this partial reproduction.

No fix PR: the reported Windows behavior was not reproduced on trusted main. The available test measures a prerequisite rather than failing for the actual user-visible defect, so the required failing-before/passing-after simple-fix gate is not met.
