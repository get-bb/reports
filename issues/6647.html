#6647 · Cross-provider skill deduplication preserves a single provider owner

BugPriority: LowEffort: LowprovidersIssue2026-10-30 · base a1bf55b6a04c7948ae5ae0dcfcbdec27d2b507a2

Verdict: REPRODUCED · Root-cause confidence: high · reproduction label: confirmed-repro

1. TL;DR

A skill file discovered by both Cursor and Codex is returned only once by the project Skills API, but incorrectly retains Cursor as its owner. The same trusted code and reproduction fail in two separate checkouts. The reported symptom is real, but the proposed explanation is not: native skill IDs already include the provider. The actual loss of attribution happens later, when the server sorts registrations and collapses equal skill names and content hashes without merging their provider ownership. Cursor sorts before Codex, so this is not simply whichever scan happened first.

For the two matching user-scope registrations, Cursor therefore sorts before Codex. The shared helper keeps the complete first record rather than merging provider attribution:

packages/skill-index/src/index.ts:45
export function firstPerIdentity<T>(
  items: readonly T[],
  identity: (item: T) => string,
): T[] {
  const seen = new Set<string>();
  return items.filter((item) => {
    const key = identity(item);
    if (seen.has(key)) return false;
    seen.add(key);
    return true;
  });

This yields a single correctly deduplicated file with incorrect exclusive ownership. The CLI consumes the server's provider field (apps/cli/src/commands/skill.ts:187); UI provider filters also derive directly from it (apps/app/src/components/tools/SkillsCollection.tsx:53). Even after server ownership is corrected, those surfaces need an explicit Shared presentation instead of treating null as bb.

6. Proposed fix

Merge provider attribution at the server stage that actually groups name/content-equivalent registrations, preserving one stable registration for read/edit operations while using null when multiple distinct provider readers are represented. Do not remove provider qualification from discovery IDs as a cosmetic workaround. Preserve existing precedence for bb-owned and configured shared roots, distinguish provider identity from editability, and add Shared rendering in the existing UI/CLI taxonomy. Keep single-provider skills unchanged.

The primary regression should be this real discovery-to-API scenario, not two hand-constructed records that reuse an ID. Also test different files with identical names/content, different content with identical names, project versus user precedence, and single-provider roots. This report does not implement a repair.
