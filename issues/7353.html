#7353 · Preserve the original send failure

Bug Medium priority Low effort cli · GitHub issue · 2026-11-10 · base 7c1353d80729983b86ea1555d18b42407f320406

Verdict: REPRODUCED · Root-cause confidence: high

1. TL;DR

A failed message send can print an unrelated thread-lookup error instead of explaining that the workspace was destroyed. The CLI fetches thread metadata to add a recovery hint after receiving the original HTTP 409 error. If that secondary request fails, its rejection escapes and replaces the original diagnostic. A deterministic command/output regression reproduces this for HTTP 404, HTTP 503, and a rejected transport promise in two clean checkouts at the same trusted main commit.

The complete test file includes the existing command registration and transport harness. Added regression:

  it.each([404, 503, "transport"] as const)(
    "bb thread send preserves the send error when the hint lookup fails with %s",
    async (failure) => {
      stubServerApi({
        "v1.threads.:id.$get": async () => {
          if (failure === "transport") {
            throw new Error("Thread lookup connection closed");
          }
          return new Response(
            JSON.stringify({ message: "Thread lookup failed" }),
            { status: failure, headers: { "Content-Type": "application/json" } },
          );
        },
        "v1.threads.:id.send.$post": async () =>
          new Response(
            JSON.stringify({
              code: "thread_environment_unavailable",
              message: "Thread environment is unavailable",
              details: { reason: "destroyed", environmentStatus: "destroyed" },
            }),
            { status: 409, headers: { "Content-Type": "application/json" } },
          ),
      });
      await expect(
        runCommand(["thread", "send", "thread-gone", "hello"], register),
      ).rejects.toThrow("process.exit:1");
      expect(
        vi.mocked(console.error).mock.calls.map((call) => String(call[0])),
      ).toEqual(["Error: HTTP 409: Thread environment is unavailable"]);
    },
  );

5. Root cause

The send catch block and hint builder await a metadata request while already handling an error. The hint builder has no rejection handler around this line:

const { canRestoreEnvironment } = await sdk.threads.get({ threadId });

Consequently throw await withRestoreEnvironmentHint(...) rejects with the lookup failure rather than throwing its original argument. The CLI action wrapper prints that replacement error. The server error constructor confirms the original 409 code, message, and destroyed status used by the regression. This is a diagnostic failure in the CLI, not proof that sending succeeded or that the server lost data.

6. Proposed fix

Make recovery metadata best effort. If the thread request rejects, return the original error unchanged; when it succeeds, retain the existing restore/non-restore hints. This needs no SDK, protocol, data, or permission change. Keep the optional ready-to-run new-thread command out of this minimal defect repair.
