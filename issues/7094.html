#7094 · Native provider questions retain the turn indefinitely

BugHighEffort: Mediumproviders · threads · provider-claude-codeGitHub issue

Verdict: REPRODUCED · Root-cause confidence: high

1. TL;DR

A native provider question can hold a turn indefinitely when nobody answers. The server records it without a deadline and schedules no expiry callback, while the queue treats the pending interaction as a turn blocker. A focused test advances the real server lifecycle's clock by 31 minutes: the question remains pending, still blocks the turn, and sends no end-request message to the daemon. The same test fails in a second clean checkout. This is a server-boundary reproduction using real migrated SQLite, not a live Claude model or a desktop reproduction.

import { expect, it, vi } from "vitest";
import { createUserQuestionPayload } from "../helpers/pending-interactions.js";
import { createMockHubSocket } from "../helpers/mock-hub-socket.js";
import {
  seedEnvironment,
  seedHostSession,
  seedProjectWithSource,
  seedThread,
  seedTurnStarted,
} from "../helpers/seed.js";
import { withTestHarness } from "../helpers/test-app.js";

it("releases an unanswered native provider question after thirty minutes", async () => {
  await withTestHarness(async (harness) => {
    const { host, session } = seedHostSession(harness.deps);
    const { project } = seedProjectWithSource(harness.deps, { hostId: host.id });
    const environment = seedEnvironment(harness.deps, {
      hostId: host.id,
      projectId: project.id,
    });
    const thread = seedThread(harness.deps, {
      projectId: project.id,
      environmentId: environment.id,
      providerId: "claude-code",
    });
    const socket = createMockHubSocket();
    harness.deps.hub.registerDaemon(session.id, host.id, socket);
    const turnId = "turn-expiry-repro";
    const providerThreadId = "provider-thread-expiry-repro";
    seedTurnStarted(harness.deps, { threadId: thread.id, turnId, providerThreadId });
    vi.useFakeTimers({ toFake: ["Date", "setTimeout", "clearTimeout"] });
    try {
      const created = harness.deps.pendingInteractions.registerPendingInteraction({
        interaction: {
          threadId: thread.id,
          turnId,
          providerId: "claude-code",
          providerThreadId,
          providerRequestId: "request-expiry-repro",
          payload: createUserQuestionPayload(),
        },
      });
      expect(created.outcome).toBe("created");
      if (created.outcome === "rejected") throw new Error(created.reason);
      expect(
        harness.deps.pendingInteractions.hasTurnBoundPendingThreadInteraction(thread.id),
      ).toBe(true);
      await vi.advanceTimersByTimeAsync(31 * 60 * 1000);
      const current = harness.deps.pendingInteractions.getThreadInteraction({
        threadId: thread.id,
        interactionId: created.interaction.id,
      });
      const blocksTurn =
        harness.deps.pendingInteractions.hasTurnBoundPendingThreadInteraction(thread.id);
      const endedRequests = socket.messages
        .map((message) => JSON.parse(message))
        .filter((message) => message.type === "interactive-requests.end");
      console.log("after 31 minutes", {
        status: current.status,
        expiresAt: current.expiresAt,
        blocksTurn,
        endedRequests: endedRequests.length,
      });
      expect(current.status).toBe("interrupted");
      expect(blocksTurn).toBe(false);
      expect(endedRequests).toHaveLength(1);
    } finally {
      vi.clearAllTimers();
      vi.useRealTimers();
    }
  });
});

5. Root cause

  1. plugins/provider-claude-code/server.ts:82–92 declares native question support. plugins/ask-user-question/src/server.ts:129–141 omits the plugin tool for that capability. Its configurable timeout and 30-minute default are plugins/ask-user-question/src/server.ts:19–52.
  2. plugins/provider-claude-code/src/bridge/bridge.ts:2040–2103 creates a promise, stores its resolver, and forwards a user_question. It resolves on an answer or cancellation; there is no elapsed-time completion here.
  3. apps/server/src/services/interactions/pending-interactions.ts:483–526 creates provider-origin rows with expiresAt: null and no timer. Contrast the plugin's deadline and timer at apps/server/src/services/interactions/pending-interactions.ts:540–580.
  4. apps/server/src/services/interactions/pending-interactions.ts:417–422 consults the active turn-bound interaction. apps/server/src/services/threads/queued-message-dispatch.ts:408–420 will not clear the interaction queue wait while it remains active. With no answer or external interruption, no timeout path removes this condition.
  5. Existing interruption plumbing can end the wait: apps/server/src/services/interactions/pending-interactions.ts:1105–1146 sends interactive-requests.end and notifies settlement. apps/host-daemon/src/interactive-request-registry.ts:216–232 rejects the matching request with the supplied reason. This transport was inspected, not exercised with a live model.

Source excerpt from provider registration:

originKind: "provider",
providerRequestId: interaction.providerRequestId,
payload,
expiresAt: null,

The generic cancellation API accepts plugin interactions, not ordinary native questions (apps/server/src/services/interactions/pending-interactions.ts:698–713). Its exact error differs by payload kind, so the report does not rely on the issue's quoted cancellation text.

6. Proposed fix

Add bounded server-owned expiry for unanswered native user_question interactions only, using the existing interruption and daemon-end paths. A timer derived from the existing creation time can preserve the deadline over a restart without changing stored-data formats. Clear it when an answer enters resolving or the question settles; do not expire approvals or answers already being delivered. Recover pending deadlines at start, and defer mutation while a server move is frozen. Test expiry, restart, answer races, and approvals before considering the fix safe. The plugin's configurable timeout remains a separate policy surface; this report does not claim its settings currently apply to native providers.
