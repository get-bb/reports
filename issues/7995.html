#7995 · Delegated Cursor credentials are treated as missing

BugPriority: MediumEffort: Mediumprovidersprovider-acppartial-reproGitHub issue

November 21, 2026 · trusted origin/main 35a03bbbb3f4d8dc814c1a152db5a463102b4250

PARTIALLY REPRODUCED · root-cause confidence: high for the credential-reader limitation

1. TL;DR

BB's Cursor maintenance reader cannot distinguish credentials delegated to a Linux OS store from a missing login. In two fresh trusted checkouts, a temporary auth file containing a store reference but no inline token produced a null account and unauthenticated usage, without requesting dashboard data. An inline synthetic-token control reached the dashboard boundary successfully. The full reported scenario—an actually authenticated Cursor CLI and real encrypted OS-store credentials—was not exercised, so this is a partial rather than end-to-end reproduction. No account data, secret store, real credentials, or running BB instance was accessed.

5. Root cause

Credential location and acquisition, lines 30–81: the Linux path comes from XDG_CONFIG_HOME. The keychain helper has an explicit non-macOS null return. The file schema accepts an optional accessToken but has no delegated-store resolution path; a JSON object without accessToken becomes null. Missing files, malformed input, and unavailable credentials all collapse to the same value.

if (process.platform !== "darwin") return null;
const cursorFileCredentialsSchema = z.object({
  accessToken: z.string().min(1).nullish(),
});
return parsed.success ? (parsed.data.accessToken ?? null) : null;

Account and usage token gates, lines 424–438: readAccount returns null and readCursorUsage returns unauthenticated before making a request. The positive control rules out malformed dashboard responses or a network failure as the cause of the negative result.

SQLite email lookup, lines 112–130: this path reads only cursorAuth/cachedEmail. A cached email cannot supply an access token, and the account path does not even consult the email when token acquisition fails.

Cursor dialect selects this maintenance implementation. Bridge health and usage requests route through the same owner. The reproduction invokes that owner's exported methods directly; it does not claim a UI or wire-level test.

6. Proposed fix and safety decision

First establish a provider-supported Linux credential-resolution mechanism in a disposable signed-in environment. Verify its behavior for a valid store entry, a locked store, no entry, an expired token, and an unavailable secret-service executable, without printing token values. Reuse the verified resolver for account and usage, retain existing plaintext/macOS behavior, and distinguish resolution uncertainty from a proven missing login where the existing contract permits.

No production patch or pull request was opened. The fully authenticated scenario remains unverified, and adding a new secret-store lookup or decryption path changes authentication/credential handling, which is explicitly excluded from this automation's simple-fix scope. A superficial change to the displayed status would not restore usage acquisition. The issue had no open cross-referenced pull request and no open PR search match at investigation time.
