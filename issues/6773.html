#6773 · Persistent service retains a session-only executable

Bug High Effort: Low host · GitHub issue · October 31, 2026

Trusted main: 916d684ac23d0b0de82c09cfc7553a50287d2188

Verdict: REPRODUCED · Root-cause confidence: high

1. TL;DR

The machine installer writes the shell's current Node lookup path into a persistent service. If that path passes through a temporary session symlink, deleting the symlink leaves the service unable to execute Node even though the real Node installation still exists. The reproduction runs the actual trusted installer against isolated service-management and enrollment fixtures, reads its generated systemd unit, removes the temporary Node link, and tries its executable. That attempt fails with ENOENT in two clean checkouts. This confirms the executable-path defect; it does not claim a real WSL reboot or a live systemd journal capture.

5. Root cause

Executable selection at the recorded base checks Node's presence and version, then retains its shell lookup path:

node_bin=$(command -v node)

Systemd serialization at the recorded base escapes that string but does not resolve symlinks before persisting it:

escaped_node_bin=$(systemd_escape "$node_bin")
ExecStart="$escaped_node_bin" "$escaped_bb_app" host-daemon ...

The service outlives the shell session, but its executable locator need not. Once the session link disappears, the kernel cannot follow the saved path, so the daemon cannot even begin starting. The fixture's executable symlink reproduces the same filesystem lifetime failure as an ephemeral parent-directory symlink; it does not reproduce fnm's session manager itself.

The same variable is used for the CLI shim's PATH and the macOS launch agent. The Windows installer already uses process.execPath for its executable (existing sibling implementation).

6. Proposed fix

Capture the running Node executable with node -p 'process.execPath' instead of persisting command lookup. This follows the existing Windows installer and script-launcher convention and resolves the session symlink on the affected POSIX systems. Keep the regression at the installer/unit boundary and run the complete POSIX installer suite. This does not promise survival if the actual versioned Node installation is subsequently deleted; rerunning installation would then be necessary.
