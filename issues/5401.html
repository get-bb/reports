#5401 · Session restoration rejects explicitly authorized ACP requests

BugMedium priorityEffort: Medium providersprovider-acpconfirmed-repro Issue2026-10-12 · base 406c009502ad0f961fc6ce9c75c1d262cb3e3e7c

Verdict: REPRODUCED — BB bridge permission rejection during restoration. Root-cause confidence: high.

1. TL;DR

BB supports restoring an ACP conversation through session/load. An agent can request permission before that restoration finishes, but BB rejects the request because no conversational turn is active yet. This happens even when the caller has explicitly selected full access, and BB creates no approval interaction. A local wire-level fixture reproduces the rejection in two clean checkouts while the identical permission is allowed during a normal full-access turn. The provider-specific downstream failure and old approval projection claims were not tested.

import { appendFileSync } from "node:fs";
import { createInterface } from "node:readline";

let pendingRequest;
let heldPrompt;
let cancelled = false;

function send(message) {
  process.stdout.write(`${JSON.stringify({ jsonrpc: "2.0", ...message })}\n`);
}

function requestPermission(message, phase) {
  pendingRequest = { message, phase };
  send({
    id: "fixture-permission",
    method: "session/request_permission",
    params: {
      sessionId: "restored-session",
      toolCall: {
        toolCallId: "fixture-tool",
        title: "Read status",
        kind: "read",
        status: "pending",
      },
      options: [
        { optionId: "yes", name: "Allow once", kind: "allow_once" },
        { optionId: "no", name: "Reject once", kind: "reject_once" },
      ],
    },
  });
}

createInterface({ input: process.stdin }).on("line", (line) => {
  const message = JSON.parse(line);
  if (message.id === "fixture-permission" && pendingRequest) {
    appendFileSync(
      process.env.OUTCOME_LOG,
      `${JSON.stringify({ phase: pendingRequest.phase, response: message.result })}\n`,
    );
    const result =
      pendingRequest.phase === "load" ? {} : { stopReason: "end_turn" };
    send({ id: pendingRequest.message.id, result });
    pendingRequest = undefined;
    return;
  }
  switch (message.method) {
    case "initialize":
      send({
        id: message.id,
        result: {
          protocolVersion: 1,
          agentCapabilities: { loadSession: true },
        },
      });
      break;
    case "session/new":
      send({ id: message.id, result: { sessionId: "restored-session" } });
      break;
    case "session/load":
      requestPermission(message, "load");
      break;
    case "session/prompt":
      if (cancelled) {
        send({ id: message.id, result: { stopReason: "end_turn" } });
      } else if (["stop", "cancel"].includes(process.env.CASE_PHASE)) {
        heldPrompt = message;
        appendFileSync(process.env.READY_FILE, "ready\n");
      } else {
        requestPermission(message, "turn");
      }
      break;
    case "session/cancel":
      if (heldPrompt) {
        cancelled = true;
        requestPermission(heldPrompt, process.env.CASE_PHASE);
        heldPrompt = undefined;
      }
      break;
  }
});

5. Root cause

The bridge creates the session with the caller's permission policy already assigned, no active prompt, and no stop/cancel request. Restoration marks the session as loading and awaits session/load without activating a turn. The fixture emits a schema-valid permission request during that await.

After validating the incoming request, handlePermissionRequest treats every non-turn request like a stopped or cancelled turn. Because activePromptKind is null during restoration, this branch immediately returns cancelled. Neither the full-access decision nor pending-permission/interaction creation is reachable.

The deeper distinction is restoration authorization versus active-turn lifecycle. A correct repair cannot simply make all out-of-turn requests allowable. It must retain the stop/cancel exclusions and bind any restored request to the intended session. During construction, providerThreadId has not yet been assigned; loadingSessionId holds the intended restored identity.

6. Proposed fix and autofix safety

Preserve stop/cancel guards and fail-closed defaults; explicitly admit a matching restoring-session permission request under full access before rejecting other out-of-turn requests. Validate session identity against the restoring session, not the not-yet-assigned providerThreadId. Decide restricted-mode restoration interaction ownership separately.

No production fix or pull request. The verified repair changes when permission requests may be approved. This is permission/security-boundary behavior, explicitly excluded from this rule's simple-fix eligibility even if the patch would be small. No branch was started, pushed, or submitted. The report and regression artifacts are preserved for a permission-aware review.
