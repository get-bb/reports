#5273 · Composer service tier crosses provider selections

BugPriority: MediumEffort: Mediumproviders · ui · provider-codex · provider-claude-codeGitHub issue2026-10-09

Trusted base: 8395b050a14d7207cef9aee914af6a60cd8f5ba4 (fetched canonical main).

Verdict: REPRODUCED · Root-cause confidence: high

1. TL;DR

Choosing Fast for Codex in a new-thread composer leaves that choice active when the same composer switches to Claude Code. The actual composer hook returns Claude Code with serviceTier: "fast" and marks that tier as an explicit input, despite no Claude-specific Fast selection. Tier preferences are tab-scoped but not provider-scoped; provider switching remembers model and reasoning, not service tier. Both providers advertise the same Fast identifier, so capability reconciliation accepts the carried-over value. This is a verified composer-state defect, not a claim that a live paid Claude turn or its bill was measured.

5. Root cause

  1. One serviceTierAtom for all providers and its parameterless preference hook contrast with provider-keyed model/reasoning atom families. The tier storage key has no provider component.
    const serviceTierAtom = atomWithStorage<StoredServiceTier>(
  SERVICE_TIER_STORAGE_KEY,
  "",
  createTabScopedStorage<StoredServiceTier>(...),
  { getOnInit: true },
);
  2. rawServiceTier resolves the single stored value regardless of which provider is selected. setProviderModelReasoning switches provider/model/reasoning without clearing or replacing that tier.
  3. Tier reconciliation checks destination support and reconcileServiceTier retains any advertised matching identifier preserve Fast when the destination also advertises Fast. Claude Code declares Fast.
  4. Submission includes the selected service tier and source classification turns that leaked selection into an explicit request. Server tier resolution uses one global eligibility gate; it does not know which provider the user's earlier toggle targeted.
    const serviceTier = getAppSettings(deps.db).allowFastServiceTier
  ? resolveProviderServiceTier(deps.providerRegistry, {
      providerId: thread.providerId,
      requested: args.input.serviceTier,
      inherited: lastExecution?.serviceTier ?? projectExecution?.serviceTier,
    })
  : DEFAULT_SERVICE_TIER;
  5. The Claude bridge maps Fast to SDK settings faithfully translates the request:
    fastMode: params.serviceTier === "fast"
    This is not a translation bug in that bridge.

The absence of provider-specific eligibility is also visible in the app settings schema and the global settings control. A deeper adjacent persistence issue remains: project_execution_defaults is unique on projectId only and its upsert overwrites provider and serviceTier on that project row. This investigation did not execute that downstream persistence path.

6. Proposed fix and simple-fix gate

Choose and document the product contract first: provider-specific eligibility (enforced on server-originated turns too), or provider-scoped remembered composer tiers with explicit default-inheritance rules. The latter should follow the existing provider-keyed model/reasoning design and specify what happens to an old tab-wide tier. Correct project-level per-provider defaults separately if needed, rather than concealing that data model with a UI-only toggle.

No automated fix PR: these options require a product decision and changes to settings or persisted preference semantics. Changing the project-default key additionally requires a stored-data/schema migration. A reset-on-switch shortcut would silently replace saved preferences and is a third policy choice, not an established contract. Those conditions fail the no-product-decision/no-stored-data-change simple-fix gate. No production patch, branch, commit, or push was attempted in get-bb/bb. No open linked PR was found by issue timeline or open-PR search.
