#6392 · Repository sync silently loses issues outside its first page

BugMedium priorityMedium effortplugins · github · confirmed-repro GitHub issue · 2026-10-27 · base 7125b90a6f7812e40d8e8509f53cecd301c84881

Verdict: REPRODUCED · Root-cause confidence: high

1. TL;DR

The current GitHub plugin successfully refreshes a repository containing 101 synthetic open issues but exposes only 100 through its real list RPC. In a second scenario, issue 1 is present with 100 open issues, then disappears from the plugin cache when issue 101 is added, although issue 1 remains open upstream. The plugin requests a single creation-descending page and treats it as the complete repository snapshot. Its transaction replaces all existing cached rows with that page. This removes only local cached entries, not issues on GitHub.

This is a deterministic backend reproduction against trusted main, not a desktop/browser reproduction or a live GitHub request. The external GitHub process boundary is faked; the production plugin, validation, synchronization, SQLite storage, and RPC handlers all run.

5. Root cause

The repository query requests a single page for each connection, ordered by creation time descending. It does not select pageInfo or supply a cursor:

  repository(owner: $owner, name: $name) {
    hasIssuesEnabled
    openIssues: issues(first: ${ISSUE_PAGE}, states: [OPEN], orderBy: {field: CREATED_AT, direction: DESC}) {
      nodes { ${listFields} }
    }
    closedIssues: issues(first: ${CLOSED_ISSUE_PAGE}, states: [CLOSED], orderBy: {field: CREATED_AT, direction: DESC}) {
      nodes { ${listFields} }
    }
    openPrs: pullRequests(first: ${PR_PAGE}, states: [OPEN], orderBy: {field: CREATED_AT, direction: DESC}) {
      nodes { ${listFields} }
    }
    closedPrs: pullRequests(first: ${CLOSED_PR_PAGE}, states: [CLOSED, MERGED], orderBy: {field: CREATED_AT, direction: DESC}) {
      nodes { ${listFields} }
    }
  }
}`;

fetchRepoItems runs that query once, validates the returned nodes, and maps those nodes only. A page that is full but valid is accepted as successful; there is no distinction between a complete snapshot and a prefix.

replaceRepoRows then atomically deletes all cached rows for the repository and inserts only the fetched rows:

  function replaceRepoRows(repo: string, items: CachedItem[]): void {
    const insert = db.prepare(
      `INSERT INTO items (repo, number, kind, title, state, author, labels, assignees, url, body, updated_at)
       VALUES (?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?)`,
    );
    db.transaction(() => {
      db.prepare("DELETE FROM items WHERE repo = ?").run(repo);
      for (const item of items) {
        insert.run(
          item.repo,
          item.number,
          item.kind,
          item.title,
          item.state,
          item.author,
          JSON.stringify(item.labels),
          JSON.stringify(item.assignees),
          item.url,
          item.body,
          item.updatedAt,
        );
      }
    })();
  }

syncAll calls replacement after the fetch succeeds. This is good failure isolation for transport/schema errors, but a valid truncated page does not throw, so it overwrites an older, more inclusive cache.

listItems returns those cached rows. The app's useItems hook consumes them without a completeness field. The missing row is already absent at the server boundary; this is not a CSS filter or rendering-only issue.

6. Proposed fix and simple-fix assessment

Before implementing, choose whether the plugin should mirror all open work or deliberately present a bounded recent snapshot. For complete synchronization, request and validate pageInfo, follow per-connection cursors, accumulate all pages, and replace a repository only after the complete fetch succeeds. Preserve the old cache if a later page fails. Tests should cover a page boundary, later-page failure, and progress/termination. For a bounded snapshot, return explicit completeness metadata and expose that limitation consistently in the UI, SDK/RPC, and CLI.

No automatic PR: this is not merely an accidental lost cursor in an otherwise paginated path. The current README explicitly promises one bounded request per repository, and the batching change deliberately preserved the result limits to reduce polling work. Unbounded pagination reverses that documented fetch policy and needs a rate/resource-budget decision; truthful truncation instead needs an explicit user-facing contract. The autopilot rule forbids fixes needing such a product decision. No production patch, dependency, branch, push, or PR was created.
