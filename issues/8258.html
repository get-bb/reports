#8258 · Disposed tunnel sessions still dispatch incoming frames

BugHighEffort: Mediumplugins · connect GitHub issueNovember 26, 2026 · base b0ddaad731565d7e4de68d824120d802fc78f7d5

PARTIALLY REPRODUCED · Root-cause confidence: high for the disposal defect

1. TL;DR

A tunnel session continues dispatching newly received requests after its owner disposes it. Two regression cases using real local WebSocket connections fail on trusted main, and the same cases fail again in a second clean checkout. This is a concrete lifecycle defect that can call Connect's loopback-origin resolver after its plugin API has been invalidated. The error propagation and stale-API connection are supported by source inspection; this investigation did not run a production plugin reload or reproduce a whole-server restart. Current main explicitly contains stale plugin errors, so a warning alone does not establish a crash.

import { once } from "node:events";
import { describe, expect, it, vi } from "vitest";
import { WebSocket, WebSocketServer } from "ws";
import { encodeFrame, type Frame } from "@bb/tunnel-contract";
import { TunnelSession, type StreamOriginResult } from "../src/session.js";

describe("tunnel session disposal", () => {
  it.each(["open-http", "open-ws"] as const)(
    "ignores late %s frames while the transport is still open",
    async (type) => {
      const server = new WebSocketServer({ host: "127.0.0.1", port: 0 });
      await once(server, "listening");
      const address = server.address();
      if (address === null || typeof address === "string") {
        throw new Error("expected a TCP address");
      }
      const connected = new Promise<WebSocket>((resolve) => {
        server.once("connection", resolve);
      });
      const tunnel = new WebSocket(`ws://127.0.0.1:${address.port}`);
      await once(tunnel, "open");
      const peer = await connected;
      const resolveOrigin = vi.fn((): StreamOriginResult => ({
        kind: "unregistered",
      }));
      const onActivity = vi.fn();
      const session = new TunnelSession({
        tunnel,
        log: { warn: () => {} },
        resolveOrigin,
        onActivity,
      });
      const receive = async (frame: Frame) => {
        const received = once(tunnel, "message");
        peer.send(encodeFrame(frame));
        await received;
      };
      session.start();
      try {
        await receive({
          type: "open-http",
          streamId: 1,
          method: "POST",
          path: "/pending",
          headers: [],
          hasBody: true,
        });
        expect(session.snapshot(Date.now()).openHttpStreams).toBe(1);
        session.dispose();
        onActivity.mockClear();

        await receive(
          type === "open-http"
            ? {
                type,
                streamId: 2,
                method: "GET",
                path: "/late",
                headers: [],
                hasBody: false,
              }
            : {
                type,
                streamId: 2,
                path: "/ws",
                headers: [],
                protocols: [],
              },
        );

        expect(resolveOrigin).not.toHaveBeenCalled();
        expect(onActivity).not.toHaveBeenCalled();
        expect(session.snapshot(Date.now()).openHttpStreams).toBe(0);
      } finally {
        session.dispose();
        tunnel.terminate();
        peer.terminate();
        await new Promise<void>((resolve) => server.close(() => resolve()));
      }
    },
  );
});

5. Root cause

TunnelSession.start and dispose installs anonymous message and close handlers, but disposal only clears heartbeats and stream collections. It never unregisters those handlers. Incoming frames therefore still reach onFrame and start work using callbacks belonging to the old session.

tunnel.on("message", (data, isBinary) => { ... this.onFrame(decodeFrame(data)); });
tunnel.on("close", () => this.dispose());

dispose(): void {
  if (this.heartbeat) clearInterval(this.heartbeat);
  ...
  this.httpStreams.clear();
}

ConnectTunnel.teardown disposes the session and then gracefully closes its socket, with forced termination after a grace period. Disposal and transport closure are distinct lifecycle events; queued or late data must not re-enter a disposed session.

The traced consequence is concrete: resolveStreamOrigin calls getLoopbackBaseUrl; the plugin callback reads bb.server.loopbackBaseUrl outside the local-cloud override; assertLive throws when the API is invalidated. HTTP frame dispatch discards executeHttp's promise, while executeHttp resolves the origin before its try block. A synchronous resolver exception becomes a rejected promise outside the intended request catch.

Crash limit: stale-error containment and stopped-service containment already handle those plugin failures on current main. The reported crash/restart remains unverified, not a tested consequence of this reproduction.

6. Proposed fix and verified repair

Give the session stable references to its own message and close handlers, unregister only those handlers at the start of dispose, then retain the existing abort and cleanup behavior. Do not remove other owners' socket listeners, change the wire protocol, or suppress stale-handle validation. This prevents the old session from accepting new work during Connect's graceful-close window.

The local repair changes three files in one existing subsystem: the session, its regression test, and its shared-worker test configuration. Total changed text: 109 additions + 20 deletions = 129 lines. No dependency, generated artifact, schema, persisted data, protocol, authorization, packaging, or release change is included.
