#6110 · Deferred rename focus in the iOS shell

BugPriority: MediumEffort: MediummobileuiGitHub issue2026-10-22

Trusted base: 9c3c56fa2b864b45104080a3a89ed39fb3196f0a

PARTIALLY REPRODUCED · Root-cause confidence: medium

1. TL;DR

The reporter describes selecting a thread title without getting the iPad software keyboard. The real inline rename component creates its input during rename, but does not focus or select it until a later animation frame. That timing is confirmed twice on unchanged production code; it can explain DOM selection without a keyboard in a WebView that requires user interaction for keyboard display. The native shell leaves the pinned WebView dependency's default user-action keyboard requirement unchanged. No iOS device or simulator is available on this Linux host, so native keyboard suppression is a supported hypothesis, not a reproduced native result. No production fix or pull request is safe on this evidence alone.

Complete timing reproduction test
// @vitest-environment jsdom

import { act, cleanup, fireEvent, render, screen } from "@testing-library/react";
import { afterEach, expect, it, vi } from "vitest";
import { InlineRenameEditor } from "@bb/shared-ui/inline-rename-editor";
import { useInlineRename, useRenameController } from "@bb/shared-ui/inline-rename";

function RenameHarness() {
  const controller = useRenameController();
  const { editor, isEditing, startEditing } = useInlineRename(
    {
      kind: "thread",
      id: "thr_repro6110",
      name: "Synthetic thread",
      label: "Thread name",
      onSave: async () => {},
    },
    { controller, Editor: InlineRenameEditor },
  );
  return (
    <div onDoubleClick={startEditing}>
      {isEditing ? editor : "Synthetic thread"}
    </div>
  );
}

afterEach(() => {
  cleanup();
  vi.unstubAllGlobals();
});

function beginRename() {
  const frames: FrameRequestCallback[] = [];
  vi.stubGlobal("requestAnimationFrame", (callback: FrameRequestCallback) => {
    frames.push(callback);
    return frames.length;
  });
  vi.stubGlobal("cancelAnimationFrame", vi.fn());
  render(<RenameHarness />);
  fireEvent.doubleClick(screen.getByText("Synthetic thread"));
  const input = screen.getByRole<HTMLInputElement>("textbox", {
    name: "Thread name",
  });
  return { input, frames };
}

it("records that inline rename only focuses and selects in a later frame", () => {
  const { input, frames } = beginRename();
  expect(document.activeElement).not.toBe(input);
  expect(frames).toHaveLength(1);
  act(() => frames[0]!(0));
  expect(document.activeElement).toBe(input);
  expect(input.selectionStart).toBe(0);
  expect(input.selectionEnd).toBe("Synthetic thread".length);
  console.log("Before frame: editor exists but is not focused. After frame: focused with complete title selection.");
});

it("diagnostic: rename focus is available before returning from the input gesture", () => {
  const { input } = beginRename();
  expect(document.activeElement).toBe(input);
});

5. Root cause and limits

Confirmed mechanism: inline rename schedules both focus and select inside requestAnimationFrame from a React effect. These are not performed synchronously while handling the title gesture. An ordinary DOM can still end up with a focused input and selected text; showing an iOS software keyboard is a separate native behavior not represented by those DOM assertions.

packages/shared-ui/src/components/ui/inline-rename-editor.tsx:22

6. Proposed fix and simple-fix gate

Next experiment: on a clean trusted iOS build, with no hardware keyboard, test a wide iPad viewport and a compact viewport. Compare header double-click, actions-menu rename, and directly tapping the resulting input. Record activeElement, selection range, and the actual keyboard in both cold and warm editor-load cases.

If that confirms the hypothesis, preserve trusted-gesture focus through editor creation/menu closure while avoiding the delayed first focus. Merely swapping useEffect for useLayoutEffect may not be enough because the editor itself is lazy and the menu completes later. Separately evaluate coarse-pointer dialog behavior; do not silently change its intentional keyboard policy.

No fix was started: only the scheduling portion is reproduced on trusted main, not the reported native keyboard defect. A meaningful regression that fails before and passes after an actual iOS repair cannot be demonstrated here. Globally disabling the WebView keyboard user-action requirement would affect more than this rename interaction and is not justified by this evidence.
