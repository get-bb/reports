#7909 · Modified shortcut layout ambiguity

BugPriority: MediumEffort: MediumuiGitHub issue2026-11-20

Trusted base: fab82665a3299fae8910f55d7519a3b034a03b9a

Verdict: PARTIALLY REPRODUCED · Root-cause confidence: high for the shortcut matcher; native event generation and composer Undo remain unverified.

1. TL;DR

The shortcut matcher rejects a physical S binding when an Option-modified event carries an ASCII Z character. A focused test against unchanged trusted main demonstrates this failure in two separate clean checkouts. The Alt branch only falls back to the physical key when the event character is not ASCII alphanumeric, so it does not recognize this event as S. The Linux environment cannot establish which native events macOS produces or whether a real editor consequently performs Undo. This is therefore a partial reproduction, not an end-to-end confirmation.

5. Root cause

The normalizer and key matcher branch on the modified character:

const usePhysicalKey = input.altKey
  ? !isAsciiAlphanumeric(input.key)
  : isNonLatinCharacter(input.key);

For Alt plus ASCII Z, the physical fallback is disabled, and the layout result remains Z. matchesAppShortcutKey compares that result to S and returns false. Its secondary layout comparison is also disabled with Alt. The full shortcut matcher requires the key comparison as well as the modifiers.

The command provider skips non-matching bindings before dispatch and only calls preventDefault() after a successful dispatch. Thus this binding cannot consume the event. Another binding or editor could still handle it; an actual Undo cannot be inferred solely from these functions.

The deeper limitation is missing layout context: AppShortcutInput carries the modified character, physical code and modifiers, not the active layout's unmodified base character. An ASCII character on a different physical letter does not by itself identify a non-Latin layout. The same key-matching route is exposed through the public experimental plugin shortcut event contract, so behavior and compatibility across callers must be considered.

6. Proposed fix and safety gate

Obtain reliable active-layout base-character information at the keyboard event boundary, and retain typed-letter matching for Latin layouts while permitting physical fallback for non-Latin layouts whose modified output becomes ASCII. Validate that information on the desktop macOS runtime, define behavior when it is unavailable, and handle input-source changes. Keep the shortcut recorder, core commands and public plugin helper consistent. A blanket physical-key fallback for all Alt events is unsafe: it would break the passing Latin rearranged-letter control.

No fix branch or pull request: the report only partially reproduces the native bug, and the current input contract cannot safely distinguish the relevant layouts. A layout-aware repair needs cross-caller/platform validation and a fallback decision rather than an unvalidated local predicate change. No production change was made or pushed. GitHub timeline metadata and open-PR searches found no open pull request linked to #7909 at investigation time.
