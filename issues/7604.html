#7604 · Blank voice responses enter the failure path

Bug Priority: Low Effort: Low ui GitHub issue 2026-11-15 · base da3e60b81d560e114a2bec724bb59c997aaaae7f

Verdict: REPRODUCED · Root-cause confidence: high for the core state-handling defect. Device capture and mobile text clipping were not verified.

1. TL;DR

A transcription service can successfully finish without returning any words. The voice-input hook converts that response into an exception, retains the audio as failed, and exposes it to the composer's Retry/Download card. Repeating the request with another empty response leaves the same error. If the composer unmounts while the response is pending, an error toast is also emitted. Four regression cases reproduce this at the real hook and recording-store boundary in two clean checkouts; all 23 pre-existing hook tests pass in both runs.

5. Root cause

normalizeTranscript collapses whitespace and trims it. runTranscription at lines 415–440 then throws for a zero-length normalized response; its catch block classifies the thrown exception as a failed transcription.

        const text = normalizeTranscript(transcript);
        if (!signal.aborted && text.length === 0) {
          throw new Error("Voice transcription returned an empty result.");
        }
        await beforeDelivery?.();
        return signal.aborted
          ? { kind: "cancelled" }
          : { kind: "transcript", text };
      } catch (error) {
        return signal.aborted ||
          (error instanceof DOMException && error.name === "AbortError")
          ? { kind: "cancelled" }
          : { kind: "failed", message: resolveRecordingErrorMessage(error) };
      }

settleTranscription at lines 445–478 persists the failure in the live recording store, or does that plus a toast after unmount when recordings are persistent.

      if (result.kind === "failed") {
        if (mountedRef.current) {
          failVoiceRecording(recording.id, result.message);
        } else if (persistRecordings) {
          failVoiceRecording(recording.id, result.message);
          appToast.error("Couldn't transcribe your recording", {
            description: "It's saved in its composer so you can retry.",
          });
        } else {
          void deleteVoiceRecording(recording.id);
        }
        return;

failVoiceRecording marks the recording failed and notifies subscribers. VoiceInputTextarea renders the failed list, while FailedVoiceRecordings supplies the visible error, Retry and Download. The hook itself returns idle, so idle alone does not mean the error entry is gone. The retry path runs the same transcription decision and therefore repeats the error.

6. Proposed fix

Classify a successfully normalized empty response as an intentional no-op rather than as an exception. Settle it by removing the audio entry, without invoking transcript delivery, completion animation, or an error toast. Preserve error retention for service/transport failures and existing cancellation semantics. Exercise both completion choices, retry, and delayed resolution after unmount. No public API, wire protocol, schema or dependency change appears necessary.
