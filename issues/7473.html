#7473 · Retry supersession repeatedly scans request history

Bug High priority Low effort threads perf

GitHub issue · November 12, 2026 · base 7794941da1b6e2baf017e5f7ab65b5f223fcaf54

Verdict: REPRODUCED · Root-cause confidence: high for the synthetic database/API stall on current trusted main. The historical production duration is not verified.

1. TL;DR

When a new prompt overtakes an outstanding retry, the server asks whether the provider already accepted that retry's input. On a long thread, the database repeatedly searches request history for each accepted input. A newly authored reproduction with 2,000 requests and 1,999 accepted inputs blocks inside the synchronous queue API for 7,624.882 ms; the same agent reproduces it in a second clean checkout. The retry still reaches the correct superseded state, so this is a latency defect rather than evidence of lost input. Removing the correlation reduces the same operation to 9.536 ms in the first patched run.

it("supersedes an unaccepted retry without repeatedly walking long request history", () => {
  const db = createMigratedConnection();
  try {
    const host = upsertHost(db, noopNotifier, { name: "retry-history" });
    const { project } = createProject(db, noopNotifier, {
      name: "retry-history",
      source: {
        type: "local_path",
        hostId: host.id,
        path: "/tmp/retry-history",
      },
    });
    const thread = createThread(db, noopNotifier, {
      projectId: project.id,
      providerId: "codex",
    });
    const requestCount = 2_000;
    const requestId = (value: number) =>
      encodeClientTurnRequestIdNumber({ value });
    const insert = db.$client.prepare(`INSERT INTO events
      (id, thread_id, scope_kind, turn_id, sequence, type, data, created_at)
      VALUES (?, ?, ?, ?, ?, ?, ?, 0)`);
    db.$client.transaction(() => {
      for (let index = 1; index <= requestCount; index++) {
        insert.run(
          `request-${index}`,
          thread.id,
          "thread",
          null,
          index * 2,
          "client/turn/requested",
          JSON.stringify({
            requestId: requestId(index),
            input: [
              { type: "text", text: "history ".repeat(256), mentions: [] },
            ],
          }),
        );
        if (index < requestCount) {
          insert.run(
            `accepted-${index}`,
            thread.id,
            "turn",
            `turn-${index}`,
            index * 2 + 1,
            "turn/input/accepted",
            JSON.stringify({ clientRequestId: requestId(index) }),
          );
        }
      }
    })();
    const retry = createQueuedThreadMessage(db, noopNotifier, {
      threadId: thread.id,
      content: [],
      model: "gpt-5",
      reasoningLevel: "medium",
      permissionMode: "full",
      serviceTier: "default",
      waitingOn: null,
      sendAt: null,
      payload: {
        kind: "retry",
        retryOfTurnRequestId: requestId(requestCount),
        attempt: 1,
        reason: "retry-history",
      },
      systemNotice: null,
    });
    const started = performance.now();
    const superseded = db.transaction(
      (tx) =>
        supersedeQueuedRetriesInTransaction(tx, {
          threadId: thread.id,
          retryOfTurnRequestId: null,
        }),
      { behavior: "immediate" },
    );
    const elapsed = performance.now() - started;
    expect(superseded).toBe(1);
    expect(getQueuedThreadMessage(db, retry.id)?.waitingOn).toBe(
      JSON.stringify({ kind: "superseded" }),
    );
    console.info(
      JSON.stringify({ requestCount, superseded, elapsedMs: elapsed }),
    );
    expect(elapsed).toBeLessThan(500);
  } finally {
    db.$client.close();
  }
});

5. Root cause

hasAcceptedQueuedRetryInput starts with accepted events and asks an EXISTS subquery to locate a request whose ID equals the current accepted event's clientRequestId. The request eligibility condition also selects the retry root or requests whose retryOfRequestId equals that root. With no accepted match, all candidate accepted inputs must be considered, and each candidate repeats a JSON-filtered request lookup. The thread/type index limits each lookup to the thread and event type but does not index the compared JSON request IDs.

json_extract(chainRequest.data, '$.requestId') =
  json_extract(accepted.data, '$.clientRequestId')

supersedeQueuedRetriesInTransaction invokes the lookup for eligible overtaken retries. Claimed and already-superseded rows are excluded before this call. The new-request event append invokes supersession; the send path wraps it in an immediate write transaction. The database adapter invokes the underlying synchronous statement.get. Consequently JavaScript cannot service other work until this database call returns. No actual HTTP request was timed here.

6. Proposed fix and verified repair

Compute the eligible root/direct-retry request IDs in an uncorrelated subquery, then test the accepted input ID for membership. Keep the accepted-event thread/type filters, LIMIT 1, eligibility checks, and queue transitions unchanged. Positive WHERE membership preserves the existing treatment of absent/null IDs and duplicates for the text request IDs used by the domain; this is not recursive retry ancestry.

The repair changes only the queued-message database subsystem: two files, 237 additions and 3 deletions, 240 total text lines. There are no dependencies, generated files, schema changes, migrations, stored-data changes, public contracts, or provider changes. No test-only production seam is added.
