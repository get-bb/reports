#6301 · Skill refresh terminates idle provider descendants

BugHigh priorityMedium efforthost · providers · provider-codex

Verdict: REPRODUCED · Root-cause confidence: high · Reproduction label: confirmed-repro

1. TL;DR

A provider can have no active turn while its subprocesses are still doing work. Changing an injected skill then asking the runtime manager for the same thread replaces the entire runtime, stopping those descendants. This test runs the real runtime manager, real agent runtime, production Codex bridge, and real operating-system processes; only the Codex app-server protocol backend is the repository's fake fixture. An unchanged-catalog control preserves the runtime and watcher, while the changed-catalog case destroys both. The central lifecycle failure reproduces twice; the reporter's macOS shell commands and historical timeline are not independently verified.

5. Root cause

Idle skill-catalog invalidation shuts down the whole runtime; provider subprocess descendants are not counted as active work and are terminated by process-group cleanup.

The activity predicate counts terminals, active/pending turn IDs, and BB-tracked background work. It does not inspect running descendants.

apps/host-daemon/src/runtime-manager.ts:609

  private entryHasActiveRuntimeWork(entry: RuntimeEntry): boolean {
    return (
      entry.terminals.size > 0 ||
      entry.runtime.getLiveThreadIds().length > 0 ||
      entry.runtime.hasOpenBackgroundWork()
    );
  }

A catalog mismatch takes the retention branch only while work is active. Otherwise replacement removes the environment and awaits runtime shutdown.
