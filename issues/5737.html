#5737 · Enrollment cancellation and address recovery

Bug Priority: Medium Effort: Low remote · GitHub issue

2026-10-19 · trusted public repository get-bb/bb · base 9937c46f5c7e369de3563eb864c8cbc4c3b9c231

Verdict: PARTIALLY REPRODUCED · Root-cause confidence: high for configuration gating and cancellation control flow; the reported desktop experience is not fully verified.

1. TL;DR

The address editor is absent from the add-machine dialog once a non-local direct address is configured, even when that address is unreachable. Closing the dialog cancels its pending launch; reopening starts a fresh launch immediately rather than waiting for the fifteen-minute deadline. The configured server address is a shared saved setting, not enrollment-local state, so cancellation does not reset it. This reproduces the address-recovery/discoverability problem but does not reproduce an uncancellable fifteen-minute onboarding lock. No production fix or pull request is proposed as a verified timer fix.

5. Root cause

Configuration gating, not a timer lock. machineServerAccessReady treats a direct address as ready when it is non-null and not local-only. It does not test whether another machine can actually reach that address. AddMachineContent only renders MachineAccessControls when that readiness predicate is false. A syntactically acceptable typo or wrong protocol can therefore bypass the only in-dialog address editor.

return access.effectiveUrl !== null && !isLocalOnlyUrl(access.effectiveUrl);

The address control persists machineServerUrl through a general-settings mutation. The server reads that saved value, so enrollment cleanup cannot undo a previously saved address.

await update.mutateAsync({ machineServerUrl: url || null });

Conversely, closing unmounts AddMachineContent. ManualMachineSetup cleanup aborts its controller, clears its creation key and deletes pending hosts. Existing server cancellation coverage verifies DELETE aborts creation and reaches the destroyed phase with a removed teardown.

The manual provider's fifteen-minute wait explicitly receives a cancellation signal. It is an enrollment deadline, not evidence that dismissal must wait. This cleanup predates the report: blame attributes it to commit b3c5434da8 from September 11, 2026, so this report does not claim a newly shipped fix.

6. Proposed fix and autopilot decision

A correction affordance should reuse the existing machine-access controls or navigate to their settings surface while cancelling the pending enrollment. It should preserve the shared server URL unless the user explicitly edits it; silently clearing that setting on every dismissal could affect other clients. The existing Mobile apps settings surface already mounts the address controls, which explains why recovery exists but is difficult to discover from Machines.

No automatic PR: the claimed uncancellable timer failure was not reproduced, and there is no demonstrated failing timer/cancellation regression to fix. The confirmed remainder is address-correction discoverability, not a verified cancellation defect. A follow-up should choose the correction UX and add a failing interaction test for that precise behavior before changing production code.
