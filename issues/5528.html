#5528 · Installer launch failure does not cancel native quit

BugHighEffort: Mediumdesktop · partial-reproOctober 15, 2026 · base d722659a2c89fdf371fdb5d9f09fdd1ba3d0cba7

PARTIALLY REPRODUCED · Root-cause confidence: high for launch/quit ordering

1. TL;DR

A failed Windows installer launch can race the updater's scheduled application shutdown. A Linux process-boundary regression drove bb's real adapter and the locked electron-updater 6.8.3 NSIS/BaseUpdater implementation: both ordinary and elevated launches still called the app's quit callback after a controlled asynchronous launch error. Errors delivered before acceptance rejected bb's installation promise but did not cancel quit; errors delivered later left that promise resolved. The same four regression failures occurred in two clean checkouts of trusted main. This verifies the code-level ordering defect, not an installed Windows outage, persisted failed result, or usable Retry; those outcomes remain unverified.

5. Root cause

The dependency's NSIS doInstall starts spawnLog asynchronously, installs a rejection handler, and returns true immediately. BaseUpdater treats true as accepted installation and schedules a setImmediate callback that emits before-quit-for-update and calls app.quit. An EIO rejection dispatches an error separately; it does not retract that scheduled callback. The elevated branch has the same early-true return. These are the exact dependency files resolved by the trusted lockfile, with identical hashes in both checkouts.

6. Proposed fix / next experiment

Make the Windows launch/quit boundary acknowledge actual process launch before committing to application shutdown, while keeping an early rejection from scheduling shutdown. Do not treat a Promise rejection, delay timer, or native acceptance event alone as a cancellation mechanism. Verify ordinary launch, elevation, permission fallback, successful install, application shutdown, saved failure, and retry in an isolated Windows build. No dependency patch, launch override, or product change is proposed as verified here.

No automatic fix PR: native Windows shutdown and recovery remain unverified. Changing installer ownership/acceptance without that lifecycle proof is not a safely validated simple fix. No production edits, branch, commit, or push were made to get-bb/bb.
