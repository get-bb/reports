#7772 · Provider plan metadata ignores profile plan fields

BugPriority: LowEffort: Mediumprovidersprovider-claude-codeGitHub issueNovember 18, 2026 · base 48c3a7848866

Verdict: PARTIALLY REPRODUCED · Root-cause confidence: high for the BB metadata path; upstream cache provenance and refresh timing remain unverified.

1. TL;DR

The Claude Code provider derives its plan label and plan identifier exclusively from the account returned by SDK initialization. A synthetic test changes a real isolated profile file from one plan to another while holding that initialization account stale; both provider usage and health still report the old plan. This result repeats in a second clean checkout of the same trusted main commit. It confirms that refreshing the profile file alone cannot correct BB's output if the SDK continues returning the old account value. It does not establish that the reported Claude Code version actually returns stale data after its daily refresh, or where that version obtains its subscription type. No production account, token, credential file, or user runtime was inspected.

5. Root cause

The usage probe returns initialization.account. The provider plan normalizer formats account.subscriptionType and does not consult any profile plan field. The profile schema keeps only oauthAccount.accountUuid; the reader returns that UUID, not plan metadata.

const name = account.subscriptionType?.replace(/^claude\s+/iu, "").trim();
...
const accountUuid = await readAccountUuid(args.env);
...
...normalizeUsage(usage.rate_limits, account)

Successful usage emits both the label and the structured plan from that same SDK account. The consumer normalizer can derive its display label from the structured plan ID, and the UI renders the resulting plan label. Thus a future repair must keep plan ID and display label consistent; changing the label alone is insufficient.

The conditional BB mechanism is established with high confidence. The deeper assertion about a particular Claude Code version's credential cache remains unverified: the test supplies that stale initialization account instead of proving that the CLI creates it. The experiment therefore warrants partial-repro, not confirmation of the full real-world refresh claim.

6. Proposed next test and simple-fix decision

Next, use an isolated, explicitly authorized test account to compare SDK initialization metadata with a documented current-plan signal before and after a controlled subscription change and the CLI's refresh. Establish which fields are authoritative and how they bind to the probed account, including alternate configuration directories and externally supplied accounts. Prefer an upstream correction or a documented SDK signal rather than assuming internal organization names are a stable plan contract.
