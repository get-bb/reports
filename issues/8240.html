1. TL;DR

The report describes an image disappearing when a native skill is invoked. A deterministic probe of bb's actual ACP bridge preserved the image for a native skill command, a raw slash command, an ordinary message, and an image-only message. Composer draft serialization also preserved both image and file attachments with slash-command text. Both checks passed again in a second clean checkout without any production change. This does not disprove the Windows/Kimi symptom: that provider and platform were not exercised. The location where the reported content disappears is therefore unconfirmed; a provider-internal wire log alone does not identify bb's outbound ACP request.

5. Root cause analysis

The reported loss has no confirmed root cause in this investigation. The measured boundary behaved correctly on unchanged production code.

  • Draft serialization appends every local image/file after the text, without excluding slash commands.
  • Configured bb skill rewriting rewrites only the text of matching configured bb skills; it neither expands arbitrary native skill files nor replaces the input list.
  • ACP block construction walks every input part. A readable local image becomes an image block when the peer reports image support, independent of slash-command text.
  • ACP outbound request sends these blocks using session/prompt. Its image block has type: "image", not an image_url part. A log named turn.prompt with image_url parts is not, by itself, a capture of this exact boundary.
  • ACP plugin host entry re-exports this bridge via the SDK ACP bridge export.

Other known branches (peer declares no image support, missing local image) emit text fallbacks; those do not depend on slash-command syntax and were not asserted to be the cause here. Source history attributes image emission to the long-standing ACP implementation, not a demonstrated fix after this issue.
