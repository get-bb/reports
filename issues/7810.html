#7810 · Platform-specific skill status hashes

BugPriority: LowEffort: Lowhost · cliGitHub issue2026-11-19

Verdict: REPRODUCED at the server API boundary · Root-cause confidence: high

Trusted main commit: 755a265098fa4c9269b9b79fce3a0b87dc8546e3. Both reproductions use this exact commit with only the regression test added, not a pull-request branch.

1. TL;DR

The server can call a byte-identical CLI skill installation outdated solely because its files have Windows-style modes rather than the source tree's POSIX modes. The skill-tree digest includes permissions, and the status service compares the daemon's installed digest directly with the server's source digest. A real server route, migrated SQLite database, real files and the existing RPC test boundary reproduce the mismatch twice. The proposed repair computes the expected digest in the connected daemon's platform semantics for status only. Neither the install manifest nor the host protocol needs to change.

async function writeBuiltinCliSkill(harness: TestAppHarness): Promise<void> {
  const skillDirectory = join(
    harness.deps.config.builtinSkillsRootPath,
    "bb-cli",
  );
  await mkdir(skillDirectory, { recursive: true });
  await writeFile(
    join(skillDirectory, "SKILL.md"),
    "---\nname: bb-cli\ndescription: Control bb from the CLI.\n---\n",
  );
}

async function expectedCliSkillTreeHash(
  harness: TestAppHarness,
): Promise<string> {
  const entry = (
    await resolveServerOwnedSkillCatalogEntries({
      builtinSkillsRootPath: harness.deps.config.builtinSkillsRootPath,
      dataDir: harness.deps.config.dataDir,
      logger: harness.deps.logger,
      skillTreeRegistry: harness.deps.skillTreeRegistry,
    })
  ).find(({ runtimeSource }) => runtimeSource.name === "bb-cli");
  if (entry?.runtimeSource.kind !== "tree") {
    throw new Error("The built-in bb-cli skill did not resolve to a tree");
  }
  return entry.runtimeSource.treeHash;
}

The regression guards the externally observable status returned by the route. It uses no added production export or test-only hook. The RPC responder supplies a digest computed from a separate real installed directory rather than mocking the status decision. Existing coverage only compared arbitrary matching and stale hashes, so it missed cross-platform mode representation.

5. Root cause

The shared digest serializes relative path, file mode, size and content SHA. The daemon walks each installed tree and hashes the mode it can observe. The status service constructs one expected digest per skill from the source tree without considering which platform supplied the installed digest. Thus 0644 and 0666 yield different digests even when the bytes match.

packages/host-daemon-contract/src/skill-tree.ts:8

export function hashSkillTreeFiles(
  files: readonly HostDaemonSkillTreeFile[],
): string {
  const hash = createHash("sha256");
  hash.update("bb-skill-tree-v2");
  for (const file of [...files].sort((left, right) =>
    compareStringsByCodePoint(left.path, right.path),
  )) {
    hash.update("\0file\0");
    hash.update(file.path);
    hash.update("\0");
    hash.update(file.mode.toString(8));
    hash.update("\0");
    hash.update(String(file.sizeBytes));
    hash.update("\0");
    hash.update(file.sha256);
  }
  return hash.digest("hex");
}

function resolveMachineSkillStatus(args: {
  entries: HostGlobalSkillsStatusResult["entries"];
  skills: readonly HostInstallGlobalSkill[];
}): CliSkillMachineStatus {
  const expectedByName = new Map(
    args.skills.map((skill) => [skill.name, skill.treeHash]),
  );
  const relevant = args.entries.filter((entry) =>
    expectedByName.has(entry.name),
  );
  if (relevant.length === 0 || relevant.every((e) => e.treeHash === null)) {
    return "missing";
  }
  return relevant.every(
    (entry) => entry.treeHash === expectedByName.get(entry.name),
  )
    ? "installed"
    : "outdated";
}

6. Proposed fix

Keep source hashes and install RPCs unchanged. For a connected win32 daemon, derive the expected status hash from the registered source files with writable modes represented as 0666 and read-only modes as 0444. Continue comparing exact source modes on Linux/macOS, and continue detecting changed content or read-only state. The daemon's already-available platform identifies which expected hash to use. No files are chmod'ed by this repair, no security or permission enforcement changes, and no wire or stored-data contract changes.

The regression table includes writable, executable and read-only source modes; changed content; unexpected read-only destination state; and Linux/macOS permission mismatch controls.

9. Appendix: execution and trust
