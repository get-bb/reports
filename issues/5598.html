#5598 · Parent resolution uses a thread-wide access path

BugPriority: MediumEffort: Lowthreads · perf · confirmed-repro GitHub issue2026-10-16 · base 4363ba27d6f942d6b42ae61c8f85800e756b9085

Verdict: REPRODUCED · Root-cause confidence: high

1. TL;DR

Opening a timeline can require looking up parents that are not in its current window. The database lookup for several parent IDs returns correct rows, but SQLite chooses an index that searches only by thread, not by item ID. That access path can visit the thread's entire event history even when the requested parents have no qualifying rows. A new test of the real exported lookup, using the real migrated SQLite schema, fails at the query-plan assertion in two clean trusted checkouts; its preceding row-content and ordering assertions pass. This proves the access-path defect, not the reported multi-second timing or every cause of server stalls.

5. Root cause

The timeline caller collects unresolved parent IDs and calls listStoredDelegatingItemRowsByItemIds without restricting the lookup to the visible sequence window. That unrestricted history lookup is necessary to find older parents, but it must seek the requested item IDs.

The exported lookup deduplicates IDs, discards empty IDs, and uses this shape:

FROM events
WHERE thread_id = ?
  AND item_id IN (...)
  AND item_kind IN ('toolCall', 'delegation')
  AND type IN ('item/started', 'item/completed')
ORDER BY sequence

With several item IDs, the planner chooses events_thread_sequence_idx, which delivers sequence order but constrains only thread_id. Filtering item IDs then happens while walking that thread's index entries. If none of the requested IDs qualify, it still must traverse the whole thread range to establish absence; the SQL has no LIMIT to bound that work.

The existing partial index instead begins with thread_id and item_id, followed by sequence and item_kind, and uses the same literal kind predicate. That access path can seek each requested ID but may need a temporary sort across matches. The emitted EXPLAIN result demonstrates the selected access path; it is not a wall-clock benchmark or a count of VM steps.

The connection uses better-sqlite3, and this query ends in a synchronous .all(). Consequently, extra work occurs on the executing server thread. The implication for event-loop responsiveness follows from the synchronous call; unrelated-request delays were not measured here.

6. Proposed fix from repository evidence

Constrain this narrow parent-resolution query to the existing delegating-item index while preserving the literal partial-index predicate, lifecycle-type filtering, deduplication, sequence ordering, and inline output cap. This repository already uses INDEXED BY events_delegating_item_lookup_idx for another delegating-item query. For a raw indexed FROM expression, use the existing SQL row projection helper so Drizzle retains the stored-row shape and capped-output expression. No index, migration, wire field, or caller contract needs to change.

Risks: an unavailable or incompatible required index makes preparation fail, and requests for many matching IDs could have a different optimal plan. Keep a real migrated-database plan regression and row-semantic assertions for capped and uncapped output. A broader performance claim requires a separate representative workload measurement.
