Reports · Issue #4445

The 59-row fixture is windowed on current main

2026-09-30 · Bug · Medium priority · Medium effort

NOT REPRODUCED in the tested current-main synthetic scenario. High confidence in the functional threshold result; limited confidence in generalizing timings to the original thread. The remaining real-thread latency claim is unresolved.

Tested claim and result

The issue combines a former 60-row desktop threshold with lag in a rich thread, including lag after windowing starts. This experiment mounts the actual ThreadTimelineRows renderer in an optimized browser fixture. Both clean runs show no virtual spacer at 2 or 19 rows and bounded mounting with a virtual spacer at 20 and 59 rows. The 59-row desktop and compact captures each initially mount 10 rows, containing 1,270 timeline descendant elements and 320 rendered synthetic command-output lines. It does not mount all 59 rows.

The current threshold behavior is directly verified, rather than inferred from a merged PR. The source change removing the old top-level overrides is present in the tested base. No old-revision timing run was performed. The browser fixture did not reproduce scroll long tasks, but it cannot establish that the broader reported latency is fixed. No issue closure or whole-issue ALREADY FIXED claim is made.

Dataset and meaningful limits

At 59 input rows, the fixture alternates 30 assistant Markdown messages and 29 command-work rows. Each message contains eight sections with headings, formatted paragraphs, a two-row table and a two-item list. Each command row has 80 lines of synthetic output and is initially expanded. Smaller datasets use the same row generator, truncated to 2, 19 or 20 rows. Command text is display data only and is never executed.

This is an actual component render with the production React compiler, app CSS, font assets, routing/query providers and a controlled scroll context. It is not a complete bb app, live provider, server timeline build, 20-segment fetch/pagination, original 0.44.0 desktop package or reconstruction of the reporter’s private content. It has no iframes, images, streaming updates or real user data. Its 1,270-node initial 59-row DOM is a different workload from the original reported 6,616-node unwindowed DOM. The supplied bottom-anchor actions are no-ops; real bottom anchoring, search/navigation and history loading are not tested.

No production code was changed and no dependency was added.

Measurement method

Per checkout: four dataset sizes × three fresh-document samples plus three warm-scroll samples = 24 samples, with 30 scroll steps each (720 steps). Across both checkouts: 48 samples and 1,440 steps. Fresh-document means navigation with HTTP cache disabled and a fresh React mount in the existing browser process; it is not cold OS/process/cache startup. Warm-scroll means three further sweeps of the same mounted component. The first browser had a visual setup probe before measurement. Neither run uses CPU throttling or a dedicated performance machine.

Mount time runs from the synthetic mount-button click to the third animation frame. After a 350 ms settling interval, the script records DOM/windowing state. A scroll sweep resets to the top, waits 150 ms, then advances through 30 fractions of the current scroll extent; each step waits three animation frames. Long Tasks API entries overlapping the sweep are counted. The roughly 50 ms step baseline is deliberately imposed by that three-frame wait; it is not event-handler CPU time, input latency, a frame-rate claim or directly comparable to the issue’s 215 ms per-step statistic. Mount timing is separate from scroll long-task collection. No server latency is measured.
