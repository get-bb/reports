Reports · Issue #4463

Built-in question answers persist on the tested main revision

2026-09-30 · Bug · Medium priority · Medium effort

NOT REPRODUCED · High confidence for the tested built-in submission and database persistence path. The installed desktop 0.44.0 symptom and transcript rendering remain unresolved; this is not an assertion that the entire issue is fixed.

Claim and scope

The issue claims that a built-in AskUserQuestion answer reaches the agent but the interaction resolution stores only its kind. This test installs the actual repository built-in through the server plugin installer, invokes its registered AskUserQuestion tool, submits a synthetic option plus free text through the server interaction service, and reads the resulting interaction and lifecycle event from real SQLite tables. It then backs up that isolated database to disk, opens a new SQLite connection, and repeats both reads.

Both clean runs retain the answer in description.title, description.detail and description.payload, in addition to returning it to the tool caller. A separate synthetic plugin request with no describeSubmission callback produces exactly the bare plugin_submitted resolution while returning its answer in memory. That control establishes the distinction between delivery and persistence; it does not prove that a missing callback caused the installed-app incident.

The fixture uses the real plugin registration/API/lifecycle and database code. Synthetic host, project and thread rows provide context, with no connected host daemon, external provider session, browser, desktop bundle or real user data. The harness database begins in memory; the separate file backup and reopened connection validate database contents, not crash durability or a running server restart. No UI behavior is claimed, so no screenshot is presented.

Expected and actual

Expected: answering “Which display color?” with “Blue” and free text “with large text” preserves the answer. Actual in both runs: tool execution succeeds; interaction status is resolved; the interaction row and lifecycle event contain the title “Answered Which display color? — Blue; with large text”, matching detail and structured answer payload. The reopened database has identical records. The no-description control stores only the kind. The full actual output appears below.

apps/server/test/services/plugins/issue-4463.test.ts

import { join } from "node:path";
import { eq } from "drizzle-orm";
import { expect, it, vi } from "vitest";
import { createConnection, pendingInteractions, events } from "@bb/db";
import { createTestAppHarness } from "../../helpers/test-app.js";
import { seedEnvironment, seedHostSession, seedProjectWithSource, seedThread } from "../../helpers/seed.js";

it("4463 submits the actual built-in form and reads its description from a reopened database", async () => {
  const harness = await createTestAppHarness();
  try {
    const { host } = seedHostSession(harness.deps, { id: "host-synthetic-form" });
    const { project } = seedProjectWithSource(harness.deps, { hostId: host.id });
    const environment = seedEnvironment(harness.deps, { hostId: host.id, projectId: project.id });
    const thread = seedThread(harness.deps, { projectId: project.id, environmentId: environment.id });
    const installed = await harness.pluginService.install("builtin:ask-user-question", { kind: "root" });
    expect(installed.status).toBe("running");
    const found = harness.pluginService.findAgentTool("AskUserQuestion");
    expect(found).toBeDefined();
    const call = harness.pluginService.invokeAgentTool({
      ...found!, input: { questions: [{ question: "Which display color?", header: "Color", multiSelect: false,
        options: [{ label: "Blue", description: "Blue display" }, { label: "Green", description: "Green display" }] }] },
      ctx: { threadId: thread.id, projectId: project.id, signal: new AbortController().signal },
    });
    await vi.waitFor(() => expect(harness.deps.pendingInteractions.listPendingThreadInteractions(thread.id)).toHaveLength(1));
    const [pending] = harness.deps.pendingInteractions.listPendingThreadInteractions(thread.id);
    const selected = { answers: { q0: { selected: ["q0o0"], freeText: "with large text" } } };
    const submitted = await harness.deps.pendingInteractions.respondToPluginInteraction({
      interactionId: pending!.id, threadId: thread.id, value: selected,
    });
    const toolResult = await call;
    expect(toolResult.success).toBe(true);
    expect(JSON.stringify(toolResult)).toContain("Blue; with large text");
    const read = (db: typeof harness.db) => {
      const row = db.select({ status: pendingInteractions.status, resolution: pendingInteractions.resolution })
        .from(pendingInteractions).where(eq(pendingInteractions.id, pending!.id)).get()!;
      const lifecycle = db.select({ type: events.type, data: events.data }).from(events)
        .where(eq(events.threadId, thread.id)).all().filter(row => row.type === "system/interaction/lifecycle")
        .map(row => JSON.parse(row.data)).at(-1);
      return { status: row.status, resolution: JSON.parse(row.resolution!), lifecycleResolution: lifecycle?.interaction?.resolution };
    };
    const expectedDescription = { title: "Answered Which display color? — Blue; with large text",
      detail: "- Which display color? — Blue; with large text" };
    const direct = read(harness.db);
    expect(direct.status).toBe("resolved");
    expect(direct.resolution).toMatchObject({ kind: "plugin_submitted", description: expectedDescription });
    expect(direct.lifecycleResolution).toMatchObject({ kind: "plugin_submitted", description: expectedDescription });
    expect(submitted.resolution).toEqual(direct.resolution);
    const snapshot = join(harness.config.dataDir, "synthetic-persisted.sqlite");
    await harness.db.$client.backup(snapshot);
    const reopened = createConnection(snapshot);
    let durable;
    try { durable = read(reopened); expect(durable).toEqual(direct); }
    finally { reopened.$client.close(); }
    console.log(JSON.stringify({ phase: "actual-builtin-persistence", toolResult, direct, reopened: durable }));
    const fallback = harness.deps.pendingInteractions.requestPluginInteraction({
      pluginId: "synthetic-no-description", threadId: thread.id, rendererId: "color", title: "Color",
      payload: { colors: ["Blue", "Green"] }, describeSubmission: null, timeoutMs: 10000,
    });
    const [control] = harness.deps.pendingInteractions.listPendingThreadInteractions(thread.id);
    await harness.deps.pendingInteractions.respondToPluginInteraction({ interactionId: control!.id, threadId: thread.id, value: { color: "Blue" } });
    expect(await fallback).toEqual({ outcome: "submitted", value: { color: "Blue" } });
    const controlRow = harness.db.select({ resolution: pendingInteractions.resolution }).from(pendingInteractions)
      .where(eq(pendingInteractions.id, control!.id)).get()!;
    expect(JSON.parse(controlRow.resolution!)).toEqual({ kind: "plugin_submitted" });
    console.log(JSON.stringify({ phase: "no-description-control", resolution: JSON.parse(controlRow.resolution!) }));
  } finally { await harness.cleanup(); }
}, 60000);

Source evidence and precise uncertainty

  • Built-in describeSubmission callback parses the submitted response and constructs the description.
  • Answer description builder includes human-readable title/detail and the structured tool result.
  • Plugin UI API normalizes and forwards the callback; runtime bridge forwards it to the interaction lifecycle.
  • Submission persistence computes the description, serializes it into the resolution and persists the resolved interaction.
  • Description fallback omits the description if the callback is absent, throws, times out or fails validation. Only the absent-callback case was exercised as a control; the other branches are source observations.

No root cause for the installed 0.44.0 incident is established. The current trusted implementation does persist the tested built-in description. A source-history observation alone cannot establish ALREADY FIXED, and the bare resolution alone cannot identify which fallback or version mismatch occurred. This report does not test the timeline suppression/rendering claims or retrospectively recover earlier records.

Proposed next test and fix direction

No production fix was applied or justified for the passing current-main path. Next, use an isolated matching desktop release to record whether the built-in callback runs, whether description validation or its two-second deadline fails, and what the API/database returns before testing transcript rendering. If an omission is confirmed, preserve a safe diagnostic reason or correct the callback propagation/validation path. Do not indiscriminately persist raw values from arbitrary plugin forms; the plugin-supplied description is the intended persistence boundary.
