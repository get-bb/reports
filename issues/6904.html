#6904 · Codex routing changes persisted provider identity

BugHigh priorityMedium effortprovidersprovider-codexpartial-repro

Issue #6904 · November 3, 2026 · trusted base dbb247c60f46494579adb40b80efa7c8a861b35c

Verdict: PARTIALLY REPRODUCED · Root-cause confidence: high for provider-identity coupling and pool-to-local failure. The exact forward-direction error reported with Codex 0.166.0 was not reproduced with the available 0.159.0 binary.

1. TL;DR

Account pooling is a transport choice, but BB expresses it as a different Codex model provider. Fresh synthetic sessions created through the actual BB launch resolver save openai without pooling and bb-account-pool with pooling. On Codex 0.159.0, a pooled session cannot resume after the pool launch configuration disappears: Codex cannot resolve its saved provider. A direct session resumed with pooling enabled instead keeps openai, and its local HTTP requests lack the pool header. This confirms the persistence/transport coupling, but not the exact newer-version refusal or the claim that every pre-existing chat fails the same way.

5. Root cause

A transport decision changes a persisted domain identifier

The Account Pooler environment contribution supplies the pool endpoint and machine hub token. In the Codex launch resolver, missing either value leaves the default provider alone; both values add a separately named provider and its header and authentication settings:

  const poolBaseUrl = env[CODEX_POOL_BASE_URL_ENV];
  const poolToken = env[CODEX_POOL_AUTH_TOKEN_ENV];
  if (!poolBaseUrl || !poolToken) return { command: command ?? "codex", args };
  return {
    command: command ?? "codex",
    args: [
      ...args,
      "-c",
      `openai_base_url=${JSON.stringify(poolBaseUrl)}`,
      "-c",
      'model_provider="bb-account-pool"',
      "-c",
      'model_providers.bb-account-pool.name="OpenAI"',
      "-c",
      `model_providers.bb-account-pool.base_url=${JSON.stringify(poolBaseUrl)}`,
      "-c",
      'model_providers.bb-account-pool.wire_api="responses"',
      "-c",
      "model_providers.bb-account-pool.requires_openai_auth=true",
      "-c",
      "model_providers.bb-account-pool.supports_websockets=false",
      "-c",
      'model_providers.bb-account-pool.env_http_headers.x-bb-account-pool-token="CODEX_POOL_AUTH_TOKEN"',
    ],

The custom definition exists only in launch-time overrides. Real Codex thread metadata retains its provider across restart. When pooling is disabled, the saved custom id remains but the launch-time definition is absent, so the next resume cannot load configuration.

Resume does not reconcile the stored identity with the selected route

The shared construction and resume path supplies the thread id and execution settings without an explicit provider-identity compatibility strategy:

On the installed Codex version, direct-to-pool resume retains the original built-in provider instead of selecting the pool-defined provider; therefore the pool-specific header is absent. The hub authentication boundary expects its own token in the pool header or bearer authorization. The synthetic server intentionally accepts both cases, so this report does not claim an observed live-hub HTTP rejection.

Git blame attributes introduction of the launch-time custom-provider identity to commit 5551197af46; disabling pool-provider WebSockets was added later. Existing launch tests explicitly expect the separate id and do not exercise persisted sessions across a routing-mode change.

6. Proposed fix and simple-fix safety decision

Decouple the stable persisted Codex provider identity from pool endpoint selection. Validate that any stable-identity approach preserves the environment-backed hub header, ChatGPT/OAuth authentication behavior, HTTP versus WebSocket routing, and the disabled-pool path. Include compatibility coverage for existing chats saved under both provider ids; a change that only affects newly created chats is incomplete.

No automated fix PR: the supported approaches require an authentication-routing compatibility decision or a stored-provider repair. Authentication/security-boundary and stored-data changes are expressly excluded from this rule's simple-fix allowance. The reported 0.166.0 forward-direction behavior also remains unverified. No fix branch, production patch, stored-data change, push, or PR was made.

Next experiment: run the same isolated RPC reproduction with the reported Codex release and synthetic ChatGPT authentication, then verify both routing directions and historical provider ids against the actual hub boundary before choosing an implementation.
