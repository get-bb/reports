#8066 · Checkout-provider admission accepts an unavailable provider

BugMediumEffort: Lowworkspaces Issue2026-11-23 · base 48f57bc89633f1f7cb2c679922195cc2f25e4b0b

Verdict: REPRODUCED · Root-cause confidence: high · Reproduction label: confirmed-repro

1. TL;DR

A new thread requesting an unmanaged project checkout is accepted even when its required environment provider is absent. The server persists a starting thread with no environment instead of returning an actionable admission error. The new-request path silently defers provider selection, and the provisioning loop waits for registration in thirty-second increments. The focused regression below reproduces that acceptance in two clean trusted-main checkouts using real migrated SQLite databases. Rejecting the unavailable checkout provider before persisting the request fixes the tested defect without changing recovery of already accepted work.

5. Root cause

  1. Unmanaged-path placement unconditionally chooses the built-in checkout provider without a registration check.
  2. resolveCompleteProviderSelection accepts an absent record by returning an unresolved selection:
const record = getEnvironmentProvider(environmentProviderId);
if (record === undefined) {
  return { ...selection, selectionResolved: false };
}

Thread creation receives that placement and proceeds rather than rejecting the request.

The provisioning resolver subsequently treats the absent provider as transient:

const record = getEnvironmentProvider(intent.environmentProviderId);
if (record === undefined) {
  scheduleEnvironmentProvisioning(deps, thread.id, Date.now() + 30_000);
  return { kind: "waiting" };
}

This recovery behavior is useful for previously accepted work when a plugin temporarily disappears, but the checkout-path admission route wrongly lets a new request enter that recovery state. The existing default-provider policy already rejects unavailability (requireDefaultEnvironmentProvider).

6. Proposed fix and verification

Before host workspace preparation in the unmanaged-path branch, require the checkout provider to be registered. Reuse the existing invalid-request refusal mechanism and identify the provider in its message. Leave provider retry behavior for accepted requests untouched.

The local patch changes only server-side admission and one focused regression. No dependencies, stored-data changes, public contracts or wire fields change. Registered-checkout validation and existing-request recovery are covered by the relevant existing tests.
