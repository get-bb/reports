#7230 · Live ACP forks cross the owning process

BugPriority: MediumEffort: Mediumproviders · threads · provider-acpGitHub issueNovember 7, 2026

1. TL;DR

A live ACP session can belong to one provider process, with that process responsible for deciding whether it is safe to copy. The bridge instead starts a different process and asks that process to fork the source. A real-child-process regression test reproduces the resulting ownership rejection twice on trusted main, with no production changes. The test provider uses exclusive filesystem markers and a process-local ownership set; it is not Kimi. Kimi-specific version behavior, its external plugin declaration, the reported HTTP response, and a successful real-provider handoff were not verified, so the overall verdict remains partial.

5. Root cause

The ACP bridge sends session/fork through a newly spawned target connection instead of the live source connection, bypassing process-local ownership and quiescence. The source session is indexed inside the bridge, but that index is used for returned-ID collision detection rather than selecting the owner to perform the fork. A child with process-local session ownership therefore cannot safely acquire the still-live source. The normal fork branch immediately treats its result as the target session and never releases that fork in the owner or reopens it in the target.

  • New child connection is created for session construction.
  • Target initialization and fork capability check.
  • Fork is sent through connection, then its ID is accepted directly.
  • Existing source-provider-ID lookup.
  • The capability decoder already understands fork, close, and resume.
  • Ordinary resume can fall back to session/new after a restore error. A new fork-handoff path must not reuse that fallback policy.
  • Separate core provider-capability guard and Custom ACP definitions declare no fork support. These are separate from the bridge ownership bug.

6. Proposed fix and duplicate-fix check

Use the live source connection to perform the native fork when the owner supports releasing the new fork and the target can restore it. Let the provider enforce active-turn rejection; do not disable its lock. Validate the returned ID before closing only the fork, then restore it in the target and fail the operation if restore fails. Preserve the ordinary non-live-source fork path for compatible providers. Test source continuity, process ownership, release-before-acquire, and fatal restore failure.
