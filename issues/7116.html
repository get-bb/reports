#7116 · Concurrent catalog bridge retirement

BugHighEffort: Lowhost · providers · provider-claude-code · confirmed-repro

Issue #7116 · November 5, 2026 · trusted main fa30b0a7dcdf745f7baf8e41721f754b7d3198fe

Verdict: REPRODUCED · Root-cause confidence: high (runtime-level reproduction, not a live Claude session).

1. TL;DR

Two concurrent session starts can cancel one another before a user message reaches the provider. Different skill-root snapshots intentionally select different child bridge processes, even when the provider and bridge artifact are identical. The runtime incorrectly interprets an unregistered sibling process as an obsolete bridge and shuts it down. Two clean checkouts reproduce failed starts using the repository’s scripted echo bridge, while the identical-catalog controls succeed and deliver messages. Depending on scheduling, one or both starts fail; a clean child exit is a consequence of the runtime’s requested shutdown, not evidence of a healthy session.

import { mkdirSync, mkdtempSync, rmSync } from "node:fs";
import { tmpdir } from "node:os";
import { join } from "node:path";
import { expect, it } from "vitest";
import type { ThreadEvent } from "@bb/domain";
import { createAgentRuntime } from "./runtime.js";
import { promptTextInput } from "./test/prompt-input.js";
import {
  createScriptedEchoLaunch,
  fullRuntimeOptions,
  waitForThreadAgentMessageText,
} from "./test/runtime-test-harness.js";

it.each([false, true])(
  "keeps concurrent sessions usable with distinct catalogs: %s",
  async (distinctCatalogs) => {
    const workspacePath = mkdtempSync(join(tmpdir(), "bb-catalog-concurrency-"));
    const bridgeLaunch = createScriptedEchoLaunch();
    const events: ThreadEvent[] = [];
    const runtime = createAgentRuntime({
      workspacePath,
      skillRoots: [],
      onEvent: (event) => events.push(event),
      onToolCall: async () => ({ contentItems: [], success: true }),
      onProcessExit: (exit) => {
        console.info("bridge exit", JSON.stringify(exit));
      },
    });
    const skillPath = join(workspacePath, "alternate-skills");
    mkdirSync(skillPath);
    const sessions = [
      { threadId: "catalog-empty", skillRoots: [] },
      {
        threadId: "catalog-alternate",
        skillRoots: distinctCatalogs
          ? [{ id: "alternate", path: skillPath, skills: [] }]
          : [],
      },
    ];
    try {
      const results = await Promise.allSettled(
        sessions.map((session) =>
          runtime.startThread({
            ...session,
            bridgeLaunch,
            environmentId: "env-catalog-test",
            projectId: "project-catalog-test",
            providerId: "fake",
            options: fullRuntimeOptions,
          }),
        ),
      );
      console.info(
        "session outcomes",
        JSON.stringify(
          results.map((result) =>
            result.status === "fulfilled"
              ? { status: result.status }
              : { status: result.status, reason: String(result.reason) },
          ),
        ),
      );
      expect(results.map((result) => result.status)).toEqual([
        "fulfilled",
        "fulfilled",
      ]);
      for (const session of sessions) {
        const text = `usable ${session.threadId}`;
        await runtime.runTurn({
          clientRequestId: "creq_abcdefghjk",
          threadId: session.threadId,
          input: [promptTextInput({ text })],
          options: fullRuntimeOptions,
        });
        await waitForThreadAgentMessageText({
          events,
          providerId: "fake",
          runtime,
          text,
          threadId: session.threadId,
        });
      }
    } finally {
      await runtime.shutdown();
      rmSync(workspacePath, { recursive: true, force: true });
      rmSync(bridgeLaunch.dataDir, { recursive: true, force: true });
    }
  },
);

5. Root cause

  1. packages/agent-runtime/src/runtime.ts:365–380 appends a skill-root hash to the process key. Empty roots versus one alternate root therefore select different bridge processes of the same provider and launch.
  2. packages/agent-runtime/src/runtime-provider-process.ts:246–272 runs stale-bridge retirement after startup. It identifies candidates by different full process key, same provider, and zero currently registered threads:
processKey !== args.processKey &&
providerProcess.providerId === args.providerId &&
providerProcess.identity.threadIds.size === 0
  1. packages/agent-runtime/src/runtime.ts:1544–1574 awaits that retirement before registering the new thread. A concurrent bridge can therefore exist without a registered thread and still be required by a start in progress.
  2. packages/agent-runtime/src/runtime-provider-process.ts:298–328 marks the retirement as expected and terminates the selected child. The concurrent caller then finds a missing/exited process or receives rejection of its pending request.

The predicate confuses a different session catalog with a superseded bridge launch. The snapshot of candidates can also become stale before termination: a bridge can acquire a thread after it was selected. This explains why the visible failures and victim counts vary without requiring a provider crash.

6. Proposed fix

Retain and compare the existing bridge-launch fingerprint separately from the catalog-specific process key. A sibling using the same launch must not be treated as superseded solely because its skill snapshot differs. Preserve retirement of genuinely obsolete artifact/configuration launches and existing last-thread release behavior. The fingerprint implementation is already available at packages/agent-runtime/src/bridge-launch-process-key.ts:42–53.

The inline test protects concurrent session usability at the runtime boundary, without mocks or new production seams. It should pass after the retirement discriminator is repaired. Existing coverage must continue to retire obsolete launch artifacts and preserve live sibling sessions.
