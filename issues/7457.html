#7457 · Plugin interaction creation skips parent attention notifications

Bug Priority: Medium Effort: Medium threads ask-user-question

Issue #7457 · 2026-11-12 · base 030b1b729f28acedc6f86cd65a71cb3678da8124

Verdict: REPRODUCED · Root-cause confidence: high

1. TL;DR

A child can display a plugin-owned question and keep working without waking its idle parent. The server persists the question and emits the plugin pending event, but does not queue the existing child-needs-attention notice. Provider-owned approvals use a different registration path that does queue that notice. This is a missing call in plugin interaction creation, not a failure of the auto/stuck notification-mode filter. The regression fails in two separate clean checkouts at the trusted main commit, and passes after a server-only fix.

import { describe, expect, it } from "vitest";
import {
  seedEnvironment,
  seedHostSession,
  seedProjectWithSource,
  seedThread,
  seedThreadRuntimeState,
  seedTurnStarted,
} from "../helpers/seed.js";
import { waitForQueuedCommand } from "../helpers/commands.js";
import { withTestHarness } from "../helpers/test-app.js";

describe("plugin interaction parent notifications", () => {
  it.each(["auto", "stuck"] as const)(
    "notifies a parent in %s mode while the child keeps running",
    async (parentNotifications) => {
      await withTestHarness(async (harness) => {
        const { host } = seedHostSession(harness.deps, {
          id: `host-plugin-question-${parentNotifications}`,
        });
        const { project } = seedProjectWithSource(harness.deps, {
          hostId: host.id,
        });
        const environment = seedEnvironment(harness.deps, {
          hostId: host.id,
          projectId: project.id,
        });
        const parent = seedThread(harness.deps, {
          environmentId: environment.id,
          projectId: project.id,
        });
        seedThreadRuntimeState(harness.deps, {
          environmentId: environment.id,
          providerThreadId: "provider-parent",
          threadId: parent.id,
        });
        const child = seedThread(harness.deps, {
          environmentId: environment.id,
          parentThreadId: parent.id,
          parentNotifications,
          projectId: project.id,
          status: "active",
        });
        seedTurnStarted(harness.deps, {
          providerThreadId: "provider-child",
          threadId: child.id,
          turnId: "turn-child-question",
        });
        const controller = new AbortController();
        const pending =
          harness.deps.pendingInteractions.requestPluginInteraction({
            pluginId: "ask-user-question",
            threadId: child.id,
            rendererId: "ask-user-question",
            title: "Choose storage",
            payload: {
              questions: [
                {
                  id: "storage",
                  prompt: "Which storage should the worker use?",
                  shortLabel: "Choose storage",
                  multiSelect: false,
                  allowFreeText: true,
                  options: [
                    { value: "sqlite", label: "SQLite" },
                    { value: "files", label: "Files" },
                  ],
                },
              ],
            },
            presentation: {
              label: { pending: "Asking a question", completed: "Asked" },
              icon: { glyph: "MessageQuestion" },
            },
            describeSubmission: null,
            timeoutMs: 10_000,
            owner: { pluginId: "ask-user-question" },
            signal: controller.signal,
          });
        try {
          expect(
            harness.deps.pendingInteractions.listPendingThreadInteractions(
              child.id,
            ),
          ).toMatchObject([
            { origin: { kind: "plugin" }, status: "pending", turnId: null },
          ]);
          expect(
            harness.deps.pendingInteractions.hasTurnBoundPendingThreadInteraction(
              child.id,
            ),
          ).toBe(false);
          const notification = await waitForQueuedCommand(
            harness,
            ({ command }) =>
              command.type === "turn.submit" && command.threadId === parent.id,
          );
          expect(notification.command).toMatchObject({
            type: "turn.submit",
            input: expect.arrayContaining([
              expect.objectContaining({
                type: "text",
                text: expect.stringContaining(`@thread:${child.id}`),
              }),
            ]),
          });
          expect(JSON.stringify(notification.command)).toContain(
            "Choose storage",
          );
          expect(
            harness.deps.pendingInteractions.listPendingThreadInteractions(
              child.id,
            ),
          ).toMatchObject([{ status: "pending" }]);
        } finally {
          controller.abort();
          await pending;
        }
      });
    },
  );
});

5. Root cause

The built-in question tool requests server UI input. The plugin runtime forwards interaction requests to requestPluginInteraction.

Plugin creation writes the timeline and emits interaction.pending, but has no parent attention dispatch:

    try {
      appendPendingInteractionTimelineEvent(this.deps, interaction);
      notifyInteractionChanged({
        deps: this.deps,
        threadId: interaction.threadId,
      });
      emitPluginInteractionPending(thread, interaction);
    } catch (error) {

The provider registration route explicitly performs the missing action:

      if (registered.outcome === "created") {
        requestChildThreadNeedsAttentionNotification(deps, {
          blockerSummary: buildChildThreadBlockerSummary(
            registered.interaction,
          ),
          childThreadId: registered.interaction.threadId,
        });
      }

The existing parent policy already allows needs-attention under auto and stuck, suppresses off, and excludes fork/plugin-origin children. Thus no new notification mode, protocol, persisted field or provider transport behavior is needed.

6. Proposed fix and local validation

Move the existing parent attention request helper into the existing child-thread notification service. Keep the provider registration caller and call the same helper once after a plugin interaction is announced. Supply the request title and interaction ID; preserve non-blocking semantics and the existing parent-policy checks. The fix does not forward submitted answers or introduce a new resolution event.

The two regression cases pass with this fix. The relevant lifecycle, provider registration, summary formatting, child notification and parent-policy suites pass: 6 files, 81 tests. Server lint and typecheck pass. No public schema, protocol, dependency, stored data or UI change is required.

7. Verification

The same investigator repeated the corrected regression in two clean temporary worktrees named baseline and verify, both detached at the exact recorded commit. Each was separately installed and fully built; each test run allocated fresh harness storage. Production files remained unchanged. No ports needed changing because these tests do not listen on network ports.

Command in each checkout: pnpm exec turbo run test --filter=@bb/server -- test/services/interaction-parent-notifications.test.ts. Both returned exit 1, with two failures caused by the missing parent submission. These are repeated checks by the same agent, not independent verification.

Investigation correction: an initial test fixture used an invalid thread-status spelling caught by typecheck. It was corrected to the domain value active, then both clean-baseline reproductions and the fixed suites were rerun. The final published artifact contains only the corrected test.
