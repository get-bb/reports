#5373 · Marketplace checkout rejects remote-only branch names

BugPriority: LowEffort: LowpluginsGitHub issueOctober 12, 2026 · base 4b12265e5fb82c01ea67e67cfe8d935533406937

Verdict: REPRODUCED · Root-cause confidence: high · Reproduction label: confirmed-repro

1. TL;DR

BB cannot read a Git marketplace when the requested branch exists only as a remote-tracking branch after cloning. Its detached checkout asks Git to resolve a short branch name, which triggers Git's automatic local-branch creation. Git rejects creating a branch and detaching HEAD in the same operation, so BB never reads the manifest. A real local repository with a valid, branch-specific marketplace manifest reproduces this in two clean checkouts of main. Remote-qualified names, annotated tags, and full commit hashes work in the same test.

          await run("git", ["commit", "-qam", "refresh catalog"], { cwd: repo });
          const refreshedCommit = (
            await run("git", ["rev-parse", "HEAD"], { cwd: repo })
          ).stdout.trim();
          await run("git", ["checkout", "-q", "main"], { cwd: repo });

          const [refreshed] = await catalog.refreshMarketplaces({
            name: "acme-plugins",
          });

          expect(refreshed).toMatchObject({
            ok: true,
            marketplace: { resolvedCommit: refreshedCommit },
          });
          expect(await catalog.search("Acme Notes")).toEqual([
            expect.objectContaining({ entryId: "refreshed-notes" }),
          ]);

5. Root cause

materializeGit clones without checkout, then requests a detached checkout of the unqualified source ref:

clone --quiet --no-checkout <source-url> <checkout>
checkout --quiet --detach <source-ref>

The clone creates a local branch for the source repository's default branch and remote-tracking refs for its other branches. For catalog-next, no local branch exists, so Git's checkout guessing tries to create it from origin/catalog-next. That implicit branch creation conflicts with --detach. A remote-qualified ref already resolves to a commit and avoids branch creation.

The actual entry path is CLI marketplace add → SDK → POST /marketplaces → catalog service → materializeMarketplace → materializeGit. The server catches materialization failures and returns HTTP 422. Catalog refresh uses the same materializer (performRefresh). Existing Git lifecycle coverage calls only @main and therefore misses the remote-only short-name case (existing lifecycle test).

6. Proposed fix

Resolve the requested ref to a verified commit before detached checkout, falling back to refs/remotes/origin/<ref> only when direct resolution fails. Peel annotated tags to commits and checkout the resulting object ID. This preserves the existing clone behavior, origin-qualified refs, tags, and hashes without requiring a new fetch policy or public contract. The regression must fail before this repair and pass after it; run the existing plugin-catalog suites and server typecheck as well.
