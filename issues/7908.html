5. Root cause

Confirmed local mechanism, high confidence: the upstream generated MCP item contract includes both result and error. BB's MCP boundary schema validates the error message but leaves result as an untyped passthrough property. Passthrough does not delete it. The loss happens in the MCP translation branch, which constructs a new tool shape without any result field:

shape: {
  type: "tool",
  server: parsedItem.server,
  tool: parsedItem.tool,
  ...(parsedItem.arguments === undefined
    ? {}
    : { args: parsedItem.arguments }),
  ...(parsedItem.error?.message === undefined
    ? {}
    : { error: parsedItem.error.message }),
  ...
}

The shared assembler already copies a supplied result into normalized tool items. It cannot recover a result the provider plugin omitted. The existing MCP completion test supplies a null result, so it does not guard non-null diagnostics.

Incident attribution remains uncertain: the reporter did not supply the original Codex app-server notification. A raw tool response is not proof of which app-server item type or result/error field BB received. This test therefore does not establish that this omission caused the particular URL-policy incident, and it does not identify the policy engine. That is why the overall verdict is partial and overall confidence is medium.

6. Proposed fix and simple-fix decision

A narrow diagnostic improvement would validate MCP results at the provider boundary and preserve the received result in the existing tool-item path, retaining explicit transport errors. Tests should cover textual and structured results, empty results, and transport errors without inventing provider policy metadata.

No pull request: a safe resolution of this issue's policy-provenance and recovery request needs the original event shape and an upstream/product decision about supported recovery. Neither is established by the partial reproduction. Do not guess that a permission toggle exists, label the restriction permanently non-recoverable, or offer a way around it. No production fix, branch, or target-repository push was made.

Next evidence: obtain a privacy-scrubbed completed app-server item for the original failure, including only item type, status, result, and error fields; compare it with the normalized item. Then determine whether details were lost locally or never provided upstream. Do not include the denied URL or account information unless necessary and explicitly authorized through an appropriate private support route.
