#5964 · Plugin continuation errors escape process containment

BugHighEffort: MediumpluginsGitHub issue

2026-10-21 · trusted main commit 06ae8f039a7198a6aad2b9b6e030efb88f8dd923

Verdict: REPRODUCED · Root-cause confidence: high

1. TL;DR

A plugin CLI invocation can leave asynchronous work running after the invocation returns or its instance reloads. If that work touches its old API, the runtime throws a stale-context error. The process-level containment hook recognizes background service contexts only, so it declines the error and the server's fallback exits with code 1. An isolated child-process reproduction exits the same way for both a thrown exception and an unhandled rejected promise; the same test fails again in a second clean checkout. Ordinary detached CLI errors also escape containment even without a reload.

import { existsSync } from "node:fs";
import { setTimeout as delay } from "node:timers/promises";
export default function plugin(bb) {
  bb.cli.register({
    name: "containment",
    summary: "Exercise containment",
    async run([gate, kind, lifecycle]) {
      while (!existsSync(gate)) await delay(5);
      const fail = () => {
        if (lifecycle === "reload") bb.realtime.publish("changed", {});
        else throw new Error("detached CLI failure");
      };
      for (let attempt = 0; attempt < 2; attempt += 1) {
        setTimeout(() => {
          if (kind === "rejection") void Promise.resolve().then(fail);
          else fail();
        }, attempt * 20);
      }
      return { exitCode: 0 };
    },
  });
}

5. Root cause

PluginContextStaleError is generated by assertLive and realtime.publish uses that guard. The exception therefore originates in real API lifetime enforcement, not the fixture.

Service attribution wraps only background-service starts. handleUncaughtException begins:

const instance = serviceContext.getStore();
if (instance === undefined) return false;

There is no stale-error special case. invokeWrapped catches awaited exceptions but does not preserve plugin attribution into detached asynchronous descendants. CLI dispatch uses that common wrapper, as do HTTP, RPC and event invocations.

The server fallback calls process.exit(1) when containment declines. With no unhandled-rejection listener, Node's default escalation reaches this same hook. The lifetime guard is correct; the missing attribution and containment at the process-error boundary cause the crash.

6. Proposed fix

Attach internal plugin and instance identity to the stale error, recognize it before service-context lookup, and deduplicate warnings weakly per disposed instance. Run the existing shared invocation wrapper in AsyncLocalStorage carrying the exact API handle and invocation label. Contain detached errors, mark only the still-current matching instance degraded, and do not degrade a replacement instance. Keep service restart/abort supervision unchanged and continue declining unrelated core errors.

An independently authored local candidate in the existing server plugin subsystem passed all seven final regression cases and 58 existing tests (65 total across nine files), plus the server typecheck. Coverage includes context-free stale errors and unrelated core errors. No SDK contract, wire protocol, dependency, persisted data, or packaging change was required.
