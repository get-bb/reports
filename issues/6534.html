#6534 · Delayed preference broadcasts restore superseded sidebar state

BugPriority: LowEffort: LowuiIssue #65342026-10-29

Trusted base: 3bacfac9ed69d42392076e5b3da2815bec822cd8 (origin/main fetched directly from get-bb/bb).

Verdict: REPRODUCED · Root-cause confidence: high · Reproduction label: confirmed-repro

1. TL;DR

A quick collapse and expand should leave a sidebar project expanded. The preference synchronization layer instead accepts an old broadcast after the corresponding save request has finished, briefly restoring the collapsed state before accepting the newer broadcast. A focused test against the real production preference atoms and synchronization code reproduces the extra state pair in two clean trusted checkouts. A separate test also demonstrates two simultaneous writes for the same preference key. These tests reproduce the underlying state regression; browser animation and relayed-network frequency were not directly verified.

import { createStore } from "jotai";
import { afterEach, expect, it, vi } from "vitest";
import {
  applyRemotePreferenceSignal,
  attachPreferencesStore,
  hydratePreferences,
  resetPreferencesSyncForTest,
  setPreferencesMirrorStorageForTest,
  type PreferencesRpc,
} from "./preferences-sync.js";
import { createSyncedPreferenceAtom } from "./synced-preference-atom.js";
import { defaultPreferences } from "../../shared/preferences.js";

afterEach(() => {
  resetPreferencesSyncForTest();
  setPreferencesMirrorStorageForTest(undefined);
  vi.useRealTimers();
});

it("keeps the last local selection when acknowledged writes echo later", async () => {
  vi.useFakeTimers();
  setPreferencesMirrorStorageForTest(null);
  const store = createStore();
  attachPreferencesStore(store, "thread-list");
  const rpc: PreferencesRpc = {
    async call(method: string, input: unknown) {
      if (method === "listPreferences") {
        return { preferences: defaultPreferences() };
      }
      setTimeout(() => applyRemotePreferenceSignal(input), 400);
      return input;
    },
  };
  await hydratePreferences(rpc);
  const collapsed = createSyncedPreferenceAtom("collapsedProjects");
  const history: string[][] = [store.get(collapsed)];
  const unsubscribe = store.sub(collapsed, () => {
    history.push(store.get(collapsed));
  });
  store.set(collapsed, ["project-fixture"]);
  await vi.advanceTimersByTimeAsync(250);
  store.set(collapsed, []);
  await vi.advanceTimersByTimeAsync(700);
  unsubscribe();
  console.log("Observed collapsed-project states:", JSON.stringify(history));
  expect(history).toEqual([[], ["project-fixture"], []]);
});

it("keeps each key serialized while its first save is unresolved", async () => {
  vi.useFakeTimers();
  setPreferencesMirrorStorageForTest(null);
  const store = createStore();
  attachPreferencesStore(store, "thread-list");
  const saves: unknown[] = [];
  const settle: Array<() => void> = [];
  const rpc: PreferencesRpc = {
    async call(method: string, input: unknown) {
      if (method === "listPreferences") {
        return { preferences: defaultPreferences() };
      }
      saves.push(input);
      await new Promise<void>((resolve) => settle.push(resolve));
      return input;
    },
  };
  await hydratePreferences(rpc);
  const collapsed = createSyncedPreferenceAtom("collapsedProjects");
  store.set(collapsed, ["project-fixture"]);
  await vi.advanceTimersByTimeAsync(250);
  store.set(collapsed, []);
  await vi.advanceTimersByTimeAsync(250);
  const outstanding = saves.length;
  for (const resolve of settle) resolve();
  await vi.advanceTimersByTimeAsync(0);
  for (const resolve of settle) resolve();
  await vi.advanceTimersByTimeAsync(0);
  console.log("Outstanding saves before first response:", outstanding);
  expect(outstanding).toBe(1);
});

5. Root cause

The pending-write guard ends at RPC completion, allowing delayed self-broadcasts to overwrite newer local preferences; per-key writes can also overlap.

  1. Preference persistence and publish: every successful write stores the parsed value and publishes the key/value pair. There is no writer correlation in the signal.
  2. Production realtime subscription: the live plugin connects its preference channel directly to applyRemotePreferenceSignal.
  3. Remote-value pending guard: applyValues skips a key only while it is present in pendingWrites.
  4. Signal application and save completion: a valid remote signal applies its value; the request completion deletes the pending key as soon as no debounce timer remains. HTTP completion does not establish delivery of the corresponding realtime signal.
  5. Per-key flush and scheduling: inFlight is assigned but never checked before issuing a new request. Two request completions therefore share one mutable pending entry.
  6. Project collapse preference consumer and Project row collapsed prop: project collapse is derived from that preference, so stale preference transitions reach the row's collapsed state.
if (state.pendingWrites.has(key)) continue;
store.set(valueAtomFor(key), value);

pending.inFlight = true;
void rpc.call("setPreference", { key, value })
  ...
  state.pendingWrites.delete(key);

The excerpt is abbreviated; the linked source includes validation, error handling and timer checks. The issue is ordering and correlation, not an invalid payload or a CSS transition. A finite post-save timeout would only move the race rather than identify obsolete self-echoes.

6. Proposed fix

Correlate writes with their originating window, ignore that window's own echoes, and serialize writes per preference key while retaining the latest queued value. Keep other windows' changes flowing once no local write owns the key. Ensure a first request's completion cannot discard a newer queued value. Cover late self-echoes, overlapping saves, failed saves, other-window changes, and originless CLI writes. A correlation field changes the plugin RPC/realtime contract, so it is not merely a CSS repair.
