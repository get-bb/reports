#5421 · Visibility-only read tracking acknowledges unattended attention

BugPriority: MediumEffort: Mediumthreads · remote · confirmed-reproIssue #54212026-10-13 · base e9dafb6c0245a37c6972dffa71134d546f3d497e

Verdict: REPRODUCED · Root-cause confidence: high

1. TL;DR

A thread can lose its unread attention even though nobody has interacted with the app. The shared read-tracking hook treats document visibility as sufficient evidence that the user saw new attention. In an independently authored reproduction, the real app mutation sends a read request both when the visible document lacks focus and when it has focus but receives no input. The hidden-document control correctly avoids the request. Existing push-sender tests and its flush logic establish that a read timestamp covering the event prevents notification delivery; native desktop/mobile behavior and actual device delivery were not exercised.

5. Root cause

Visibility is not presence

The document visibility store subscribes to visibility, pageshow, and focus notifications, but its eligibility snapshot only checks document.visibilityState === "visible". A focus notification refreshes the snapshot; it does not establish focus or user activity.

export function isDocumentVisible(): boolean {
  return (
    typeof document === "undefined" || document.visibilityState === "visible"
  );

Read tracking's entry gate returns only for a nonvisible document or missing thread. A new attention timestamp clears manual-unread suppression and permits the mutation. The mutation invocation has no window-focus, input-recency, or pane-presentation requirement.

    if (!isVisible) {
      return;
    }
    if (!thread) {
      return;
    }

    const marker = `${thread.id}:${thread.latestAttentionAt}`;
    const isOpenedThread =
      previousSnapshot === null || previousSnapshot.threadId !== thread.id;
    const hasNewAttention =
      previousSnapshot?.threadId === thread.id &&
      previousSnapshot.latestAttentionAt !== thread.latestAttentionAt;
    if (isOpenedThread || hasNewAttention) {
      suppressedManualUnreadKeysRef.current.clear();

useMarkThreadRead immediately starts the optimistic read transaction and forwards the request to the SDK. The reproduction exercises this implementation instead of replacing it with a fake hook callback.

Why notifications disappear

flushThread rereads the thread at delivery time and intentionally suppresses already-read attention. The comparison requires the read timestamp to cover both the current attention and the queued event; merely comparing to attention would be an incomplete description.

    const lastReadAt = thread.lastReadAt ?? 0;
    if (lastReadAt >= thread.latestAttentionAt && lastReadAt >= entry.eventAt) {
      return;
    }

The normal coalesce default is 2,000 ms. The existing sender suppression test uses a shorter controlled interval and changes a queued thread's read state before flush. It confirms this suppression independently of a real device. The reporter's exact latency statistics are unnecessary to establish the faulty automatic request.

Mounted is not shown

SplitTree keeps maximization-hidden panes mounted and supplies timelineEnabled={!isHiddenByMaximize}. ThreadDetailView invokes the read hook without a shown-pane flag. EmbeddedThreadChat uses the same hook. This is a second eligibility concern, statically supported but not reproduced in a rendered split layout here.

6. Proposed fix and simple-fix decision

Separate new-attention detection from eligibility to acknowledge it. A shared presence source should model focus and actual input, notify consumers when eligibility changes, and allow pending unread attention to be acknowledged on later eligible input. The thread view must also provide whether it is actually shown. Preserve explicit manual-unread behavior, retry behavior, cancellation, and page restoration semantics.

No automated production fix or PR. A focus-only gate does not address the second reproduced scenario. A complete correction needs a product decision about the activity/idle window and which visible panes count as attended, plus validation of focus/input semantics in supported native/mobile shells. Those choices are not established by existing policy, and adopting a reporter-proposed number would exceed the rule's decision-free simple-fix boundary. The existing pageshow-only automatic-read test also encodes behavior that a presence policy must intentionally revise. No fix branch was created or pushed.

No open PR linking #5421 was found by both the open-PR search and issue connection/cross-reference metadata. No linked PR code was run.
