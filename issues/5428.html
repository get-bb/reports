#5428 · Codex maintenance loses executable identity

BugMedium priorityLow effortproviders · provider-codexGitHub issueOctober 13, 2026

Verdict: PARTIALLY REPRODUCED · Root-cause confidence: high · Reproduction label: partial-repro

1. TL;DR

The provider correctly discovers an absolute Codex executable path but drops it when constructing the update command. A new public maintenance-boundary regression fails on trusted main in two clean checkouts: discovery returns the scratch executable, while the run plan returns codex. The daemon passes that command directly to node-pty, so the plan cannot preserve a native executable extension or an explicitly discovered installation. This confirms the command-selection defect, but this Linux investigation does not reproduce native Windows process startup or a real vendor update. An open pull request already closes this issue, so no duplicate fix was pushed.

5. Root cause

The update-command helper hardcodes executable identity:

const args = ["update"];
return {
  command: "codex",
  args,
  displayCommand: formatCommand("codex", args),
};

Status discovery resolves and returns executablePath. The public run-plan path nevertheless invokes the parameterless helper rather than preserving that field.

The daemon spawner calls spawnPty(args.command, args.args, ...). The lost executable identity therefore reaches process startup. A Windows extension-resolution mismatch is consistent with this mechanism, but its exact startup error was not observed here.

The shared discovery helper already recognizes Windows executable extensions. Repair belongs in the provider's plan construction, not a second daemon discovery mechanism.

6. Proposed fix

Pass the discovered path to the existing update helper for both action display and execution; retain the bare-name fallback only when discovery returns null. Keep update separate and use the existing formatter for paths with spaces. No protocol or schema change is needed.

A locally authored experimental implementation passed the maintenance suite: 16 tests, including native-Windows-shaped path and null-fallback cases. It was created from trusted source, not copied from a PR. It was stopped, restored, and not committed or pushed once the open PR was found. This validates the mechanism, not that PR's branch.
