#6818 · Desktop startup during incomplete payload installation

BugHighEffort: Mediumdesktoppartial-repro Issue · 2026-11-02 · base 916d684ac23d0b0de82c09cfc7553a50287d2188

Verdict: PARTIALLY REPRODUCED · Root-cause confidence: medium

1. TL;DR

A desktop launch can fail if its server-side payload is not complete. On the trusted base, the packaged Windows runtime selection launches its bridge directly; an early child exit leads to the startup-error view without an installation-completion retry. A real child-process simulation demonstrates that a missing imported file exits with code 1, writing that file does not revive the old process, and an explicit new launch succeeds. This is not a native Windows/NSIS reproduction: the host is Linux, the child executable is Node, and the payload is a two-file fixture. The reported installer timing, missing npm package, launcher source, and daemon-lock history remain unverified.

Complete reproduction test

import assert from "node:assert/strict";
import { mkdtemp, rm, writeFile } from "node:fs/promises";
import { tmpdir } from "node:os";
import { join } from "node:path";
import { it } from "vitest";
import {
  resolveBbAppProcessRuntime,
  startBbAppProcess,
  type BbAppProcess,
} from "../src/bb-process.js";

it("records partial-payload startup failure and successful explicit relaunch", async () => {
  const scratch = await mkdtemp(join(tmpdir(), "bb-6818-payload-"));
  const bridgePath = join(scratch, "bridge.mjs");
  const payloadPath = join(scratch, "payload.mjs");
  const children: BbAppProcess[] = [];

  function launch(): BbAppProcess {
    const child = startBbAppProcess({
      bridgePath,
      cwd: scratch,
      env: { HOME: scratch, USERPROFILE: scratch, PATH: process.env.PATH },
      logLineLimit: 50,
      runtime: resolveBbAppProcessRuntime({
        env: {},
        isPackaged: true,
        platform: "win32",
        processExecPath: process.execPath,
      }),
    });
    children.push(child);
    return child;
  }

  try {
    await writeFile(
      bridgePath,
      'import { ready } from "./payload.mjs";\nconsole.log(ready);\n',
    );
    const incomplete = launch();
    const firstClosed = new Promise<void>((resolvePromise) =>
      incomplete.childProcess.once("close", resolvePromise),
    );
    const firstExit = await incomplete.exit;
    await firstClosed;
    assert.equal(firstExit.code, 1);
    assert.match(incomplete.logs.text(), /ERR_MODULE_NOT_FOUND/);
    assert.equal(incomplete.logs.text().includes("PAYLOAD_READY"), false);

    await writeFile(payloadPath, 'export const ready = "PAYLOAD_READY";\n');
    assert.equal((await incomplete.exit).code, 1);

    const complete = launch();
    const secondClosed = new Promise<void>((resolvePromise) =>
      complete.childProcess.once("close", resolvePromise),
    );
    const secondExit = await complete.exit;
    await secondClosed;
    assert.equal(secondExit.code, 0);
    assert.match(complete.logs.text(), /PAYLOAD_READY/);

    console.log(JSON.stringify({
      runtimeSelection: "packaged win32 direct / electron-node",
      executionHost: process.platform,
      node: process.version,
      incompletePayload: {
        exitCode: firstExit.code,
        missingModule: true,
        ready: false,
      },
      afterPayloadWritten: { originalProcessExitCode: (await incomplete.exit).code },
      explicitRelaunch: { exitCode: secondExit.code, ready: true },
    }, null, 2));
    console.log("PASS: incomplete payload fails immediately; completing files only helps a new launch.");
  } finally {
    for (const child of children) {
      await child.stop({
        signal: "SIGTERM",
        timeoutMs: 1000,
        killSignal: "SIGKILL",
        killTimeoutMs: 1000,
      });
    }
    await rm(scratch, { recursive: true, force: true });
  }
});

5. Root cause

The verified mechanism is missing coordination between an incomplete on-disk payload and a terminal early-exit path. The package explicitly unpacks its bridge and node_modules, so successful loading of the Electron main entry does not itself establish that the server dependencies have all arrived.

The bridge imports the bb-app payload, and packaged Windows chooses the direct Electron-as-Node process mode. The child starts immediately; no completion marker or installer wait is an argument to this path.

export function resolveBbAppProcessRuntime(

): BbAppProcessRuntime {
  if (args.isPackaged) {
    const appImagePath = args.env.APPIMAGE?.trim();
    const appDirPath = args.env.APPDIR?.trim();
    if (

      appImagePath !== undefined &&
      appImagePath.length > 0 &&
      appDirPath !== undefined &&
      appDirPath.length > 0

        mode: "electron-node",

The desktop startup races readiness against child exit. When the child exits first, it presents the startup error and returns null, with no retry in this branch. This makes a transient missing dependency persist as a failed launch even after files are complete.

6. Proposed fix and safety decision

Establish a bounded, crash-safe installer/launcher completion handshake before consuming the unpacked runtime, or provide a narrowly scoped, bounded recovery path that distinguishes installation from genuine missing-package failures. A stale marker must not block startup forever, different installation channels must not interfere, and retry must not spawn duplicate servers.

The next required experiment is a native Windows update slowed during extraction, with a deliberate external application launch, installer process/file trace, and post-completion health check. Repeat that experiment for stale completion state and genuine non-install module errors.

No production fix or PR: only a Linux process-boundary simulation was reproduced. A native Windows installation-coordination change is not validated by this test and may alter packaging/update behavior, which is explicitly outside the simple-fix gate. No production branch was created or pushed. No open PR was linked by the issue timeline or the open-PR search at investigation time.
