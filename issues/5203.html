#5203 · Panel tab clicks activate unintended drags

Bug Priority: Medium Effort: Low ui · GitHub issue · October 8, 2026

Trusted base: f135a001e72942cee9118d2693208ec0725e2f18 (origin/main).

Verdict: REPRODUCED · Root-cause confidence: high

1. TL;DR

Panel tab selection and tab closing can be mistaken for dragging. A real rendered tab-strip/container reproduction shows that 5 pixels of movement suppresses selection, 8 pixels of vertical movement creates a second panel pane, and a close-button press with 16 pixels of vertical movement also creates a pane instead of closing. Sortable reordering starts above 4 pixels, while an independent panel-splitting recognizer starts above 7 pixels. The close button blocks mouse and touch-start bubbling but not pointer-down bubbling, so the splitting recognizer starts from the close affordance. The same test reproduces the failures in a second clean trusted checkout; an intentional tab drag remains functional.

function gesture(target: HTMLElement, deltaY: number) {
  fireEvent(
    target,
    new MouseEvent("pointerdown", {
      bubbles: true,
      button: 0,
      clientX: 100,
      clientY: 20,
    }),
  );
  fireEvent.mouseDown(target, { button: 0, clientX: 100, clientY: 20 });
  fireEvent(
    window,
    new MouseEvent("pointermove", {
      bubbles: true,
      clientX: 100,
      clientY: 20 + deltaY,
    }),
  );
  fireEvent.mouseMove(document, { clientX: 100, clientY: 20 + deltaY });
  fireEvent(window, new MouseEvent("pointerup", { bubbles: true }));
  fireEvent.mouseUp(document);
  fireEvent.click(target);
}

it.each([5, 8])(
  "selects a tab instead of splitting or suppressing the click after %spx of jitter",
  (distance) => {
    const { onSelect, onReorder } = renderTabs();
    gesture(
      screen.getByRole("button", { name: "beta.ts", exact: true }),
      distance,
    );
    expect(screen.queryAllByRole("separator")).toHaveLength(0);
    expect(onSelect).toHaveBeenCalledWith("tab-b");
    expect(onReorder).not.toHaveBeenCalled();
  },
);

it("closes a tab instead of splitting when the close press moves vertically", () => {
  const { onClose } = renderTabs();
  gesture(screen.getByRole("button", { name: "Close beta.ts" }), 16);
  expect(screen.queryAllByRole("separator")).toHaveLength(0);
  expect(onClose).toHaveBeenCalledWith("tab-b");
});

it("still splits a tab after an intentional vertical drag", () => {
  const { onSelect, onClose } = renderTabs();
  gesture(screen.getByRole("button", { name: "beta.ts", exact: true }), 16);
  expect(screen.getAllByRole("separator")).toHaveLength(1);
  expect(onSelect).not.toHaveBeenCalled();
  expect(onClose).not.toHaveBeenCalled();
});

5. Root cause

  1. Sortable activation is 4 pixels. dnd-kit's real MouseSensor starts above that threshold and installs capture-phase click suppression; the app also suppresses clicks during drag.
  2. The tab wrapper pointer-down handler forwards all pointer-down events to onBeginTabDrag, including ones bubbling from the close button.
  3. Close-button event handlers stop mouse-down and touch-start only. Pointer-down is a separate, earlier event; stopping mouse-down cannot undo the already-started split session.
  4. The split gesture owner uses its own 7-pixel activation constant and engages for predominantly vertical movement or movement outside the header. It accepts close-origin presses.
  5. Pointer-move engagement resolves an edge zone using the real target/fallback. On release, the split session swallows the next click and calls onDrop. The container moves the tab into a new pane, causing both the missing callback and new separator.

The two activation thresholds are independent. Changing the sortable sensor alone cannot repair close-event leakage or accidental splitting.

6. Proposed fix

Stay within panel tab gestures. Reuse the existing 8-pixel mouse-activation convention used by useReorderDnd, sharing that internal distance between tab sorting and splitting. Exclude pointer-down originating within [data-tab-pill-close] at the tab-strip gesture boundary. Preserve deliberate dragging, touch hold/delay behavior, fixed tabs, stored layout format, SDK, and wire contracts. No new setting or dependency is necessary.

The regression must fail before and pass after the repair. Existing tab-strip, split-container, layout, and split-session tests must also pass. A personal sensitivity setting would be a separate product decision, not part of this contained fix.
