#8026 · Completion timestamps are absent from sibling ordering

BugPriority: MediumEffort: Mediumuiconfirmed-reproGitHub issue2026-11-22 · base 796cdcc0f4bf8a55e23664035c54e8db6fe9d272

Verdict: REPRODUCED · Root-cause confidence: high

Scope: real migrated SQLite lifecycle writes and the production sidebar tree model. No desktop or browser rendering claim is made.

1. TL;DR

A child that finishes most recently can remain below an earlier-finishing sibling in the sidebar model's default Updated at order. The database records the completion transition time, but successful child completion deliberately does not advance the separate unread-attention clock. The inactive-thread comparator sorts by that attention clock, and the public sidebar data does not expose the durable transition time. Three fresh scenarios fail identically at the recorded trusted main commit, including a grandchild pair and children of a pinned parent. This is a reproduced data/model defect; a running desktop build was not exercised.

function childrenOf(items: ProjectThreadItem[], parentId: string): string[] {
  for (const item of items) {
    if (item.kind !== "thread") continue;
    if (item.node.thread.id === parentId) {
      return item.node.children.flatMap((child) =>
        child.kind === "thread" ? [child.node.thread.title ?? ""] : [],
      );
    }
    const found = childrenOf(item.node.children, parentId);
    if (found.length > 0) return found;
  }
  return [];
}

5. Root cause

  1. Updated at is the descending updated sort option; the updated comparator selects compareStandardThreads.
  2. statusChangeNeedsAttention excludes successful child completion returns false for active-to-idle transitions with a non-null parent. The same writer always records statusChangedAt for actual transitions. Thus completion is persisted without changing attention.
  3. Inactive threads sort by latestAttentionAt, then creation time. Since Second has attention 11000 and First has attention 10000, First's completion at 30000 cannot affect this comparison.
  4. Pinned trees use the same child comparator. Pin-root sorting does not repair the descendant comparison.
  5. The public thread projection omits statusChangedAt; the list response spreads that projection. Realtime status metadata also exposes attention and updatedAt, not the transition clock. The SDK timestamp contract and the app sidebar adapter have no separate completion/activity timestamp.

Relevant comparator excerpt

const latestAttentionAtDelta =
  right.latestAttentionAt - left.latestAttentionAt;
if (latestAttentionAtDelta !== 0) {
  return latestAttentionAtDelta;
}
return compareByCreatedAtDescending(left, right);

The underlying mismatch is conflating attention-worthy events with ordering activity. A comparator-only change cannot recover a timestamp that never reaches its input. Using updatedAt would count metadata changes: updateThread assigns the current update time before changing metadata.

6. Proposed fix and simple-fix decision

Carry the existing durable transition/activity timestamp through the server list and realtime paths, client cache, and sidebar SDK contract, then use an appropriate attention/activity maximum for inactive descendants. Preserve active-first behavior, ordinary root ordering, and unread semantics. Keep reading or renaming out of the activity signal; test list/realtime consistency and metadata changes as distinct contracts.

No automatic fix or new pull request: the missing signal crosses the server/domain, client-cache, and public plugin SDK contracts. That violates this run's single-subsystem and no-public-contract-change safety gates. Changing the unread clock instead would alter product behavior; using updatedAt would be a symptom-level workaround. The fix was stopped before any production edit, branch, commit, or push to get-bb/bb. There is therefore no before/after fix claim.
