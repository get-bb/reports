#7827 · Directory clipboard items enter the attachment pipeline

BugPriority: MediumEffort: Mediumdesktop · ui · partial-reproIssue2026-11-19 · base df9619d8e8aac4aff00c0c3ff9b8ef4e2823e4f2

PARTIALLY REPRODUCED · Root-cause confidence: medium

1. TL;DR

The report concerns a folder copied in Finder being treated as an attachment instead of useful prompt text. A mounted real composer on trusted main sends a synthetic directory-shaped clipboard item to its attachment callback without inspecting its directory metadata. With no text representation on the clipboard, the editor remains empty. This exact routing result repeats in a second clean checkout; regular-file and image controls pass in both runs. The machine runs Linux, so Finder’s actual clipboard payload, native file-read failure, and the macOS error toast were not reproduced. The verdict is therefore partial, not a claim of an end-to-end macOS reproduction.

describe("SlopCop 7827 directory clipboard boundary", () => {

        },
      });

      console.log(

The current clipboard IPC is write-only and validates the sender against known application windows. An absolute-path read bridge would need equivalent trust restrictions, not an unrestricted clipboard read capability.

apps/desktop/src/desktop-clipboard.ts:5

export function registerDesktopClipboardIpc(
  applicationWindowWebContentsIds: ReadonlySet<number>,
): void {
  ipcMain.handle(
    BB_DESKTOP_WRITE_CLIPBOARD_CHANNEL,
    async (event, payload: unknown) => {
      if (!applicationWindowWebContentsIds.has(event.sender.id)) {
        throw new Error("Clipboard writes are limited to bb windows");
      }
      const { text, html } = bbDesktopClipboardContentSchema.parse(payload);
      if (html === undefined) {
        await clipboard.writeText(text);
        return;
      }
      await clipboard.write([
        new ClipboardItem({ "text/plain": text, "text/html": html }),
      ]);
    },
  );
}

6. Proposed fix and automation decision

First capture a folder paste on macOS using only a disposable directory and record item kinds, available text formats, getAsFile behavior, and whether directory-entry metadata is available during paste. Then separate directories from file attachments and, if no usable text path is supplied, design a narrowly scoped desktop path resolver for the trusted originating window. Preserve ordinary file/image uploads, mixed selections, filenames containing spaces, and paste/undo behavior. Do not infer a directory from an empty MIME type or zero byte size: ordinary files can share those properties.

No automatic fix or PR: the verdict is partial, so the required trusted-main end-to-end reproduction gate is unmet. Satisfying the full-path behavior would additionally require reviewing the desktop bridge contract/security boundary and local-vs-remote path semantics, outside a simple single-subsystem patch. No production fix was attempted, no branch pushed, and no pull request opened. Open-PR metadata/search for issue 7827 returned none.
