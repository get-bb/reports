Verdict: NOT REPRODUCED · Root-cause confidence: high for the environment-inheritance mechanism.

1. TL;DR

The issue infers that an agent-directory setting disappears because it is absent from the provider registry's environment object. That object contains only explicit overrides, not the complete environment of the spawned process. The process manager first copies the sanitized daemon environment, and the sanitizer retains PI_CODING_AGENT_DIR. A real bridge worker received a synthetic directory value without adding it to the Pi declaration. Both the configured case and the unset control passed in two separate clean checkouts; no authenticated Pi session was started.

5. Root cause of the misleading reproduction

The real Pi declaration omits the directory variable, and the server registration forwards that declared list. The registry picks those keys into the adapter's environment overlay. This much agrees with the issue's intermediate observation.

The missing step is the actual process spawn:

const env: NodeJS.ProcessEnv = {
  ...sanitizeInheritedChildProcessEnv({ env: process.env }),
  ...this.args.env,
  ...processConfig.env,
};
const managed = spawnManagedProcess({
  command: processConfig.command,
  args: processConfig.args,
  cwd: this.args.workspacePath,
  env,
});

The sanitizer removes NODE_ENV and BB_* values, not this PI_* setting. An absent property in a later object spread does not erase a property already inherited from the daemon. BB-prefixed bridge command overrides need explicit passthrough because they are sanitized; the non-BB agent-directory variable does not. There is no confirmed production root cause for a missing child value on this trusted base.

6. Proposed fix / next experiment

No production change is justified for the stated inheritance failure. If a real Pi deployment still uses the wrong directory, first verify that the actual daemon process was launched with the intended value, then inspect Pi's own directory handling in an isolated session. Merely exporting a value in a different shell does not alter an already-running daemon. That is a next diagnostic step, not an observed cause in this issue.
