#7390 · Unsupported reasoning effort breaks Codex helper requests

BugPriority: MediumEffort: Lowprovidersprovider-codexIssue

November 10, 2026 · trusted origin/main 7c1353d80729983b86ea1555d18b42407f320406

Verdict: REPRODUCED at the real client / simulated HTTP service boundary. Root-cause confidence: high. No live workspace policy or production credentials were accessed.

1. TL;DR

Codex helper tasks construct every text request with reasoning effort none. A service that permits low but not none rejects that request before it can generate a title or commit message. A focused regression exercised the real authentication-file reader, request builder, HTTP client, and response/error handling with synthetic credentials and a transport stub that enforces that policy. Both configured helper models failed with HTTP 403 on unchanged production code, and the same test failed again in a second clean checkout. Changing the helper request to low makes both cases pass without changing authorization, error classifications, or model fallback policy.

5. Root cause

The request builder hardcodes the same effort regardless of the selected helper model:

reasoning: { effort: "none" }

completeCodexInference reads credentials, constructs that request, sends it, and throws for a non-OK response. HTTP error classification maps a normal 403 to request_failed. The two-model retry policy and completion loop only retry rate limiting, service unavailability, and invalid responses. Merely trying the second model would still send the same disallowed effort.

Title generation and commit-message generation use the shared AI-task dispatch. This explains why multiple helper surfaces can show the same failure, although neither UI surface was driven in this investigation.

The provider already uses a standard reasoning ladder beginning at low in its default model metadata. Catalog discovery belongs to the separate provider bridge; the helper HTTP client does not currently consume that catalog.

6. Proposed fix

Use low instead of none for these existing helper models, and update the local request type and existing payload assertions. This is the smallest repair for a service that allows low but forbids none. Keep generic 4xx behavior unchanged: broader permission retries and configurable or catalog-derived helper effort are separate policy/design work, not necessary to eliminate this invalid request.

This bounded repair does not claim to support an arbitrary workspace that also forbids low. Reasoning-enabled requests can have different latency and token usage; no live latency, billing, or 5-second helper deadline benchmark was performed.
