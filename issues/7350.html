#7350 · Native transport failures leave requests pending

Bug Priority: Medium Effort: Low mobile confirmed-repro

REPRODUCED · Root-cause confidence: high

1. TL;DR

A page asking the native shell to share or copy content does not promptly learn that its message could not be sent. The generated bridge catches a synchronous transport exception, but leaves the request promise and deadline intact. A deterministic execution of the actual injected script keeps share pending for its configured 10-second deadline and clipboard pending for 30 seconds, before rejecting with a misleading timeout. Both the observed behavior and the failing regression test were repeated by the same agent in a second clean checkout. Actual device navigation was not exercised; this confirms the reported failure path, not its frequency on hardware.

5. Root cause

The fire-and-forget sender is also used by request/reply calls. In inject.ts:63–70, the sender catches every exception, so request callers cannot distinguish delivery failure from successful delivery. The request path inject.ts:143–153 first creates a timeout and stores its resolve/reject pair, then invokes that swallowing sender. Since no response can follow a failed send, only the timeout eventually settles the promise.

var timer = setTimeout(function () {
  delete pending[id];
  reject(new Error("native request timed out"));
}, kind === "clipboard" ? 30000 : 10000);
pending[id] = { resolve: resolve, reject: reject, timer: timer };
post({ type: "request", id: id, request: { kind: kind, payload: payload } });

The API's public post signature returns void. Fire-and-forget calls should stay non-throwing; request/reply calls need explicit failure cleanup without changing that signature or the wire format.

6. Proposed fix and local validation

Share a private throwing serializer/transport helper between the existing non-throwing post wrapper and request. Catch send errors in request itself, remove its pending record, cancel its deadline, and reject immediately. This keeps best-effort haptics harmless and preserves existing normal reply and timeout behavior.

A local implementation changes two existing mobile-bridge files: 41 added lines and 6 deleted lines, 47 total. No dependency, generated output, protocol, schema, or stored data changes. The focused regression passes both cases after the repair. Existing successful replies, explicit native errors, fire-and-forget behavior, and 10/30-second unanswered-request cases are covered by the passing package suite.
