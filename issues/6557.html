1. TL;DR

The reported failure is an unbounded chain of CLI launches when an automation's CLI override resolves back to the public launcher. Historically the app entry followed that override on every invocation, leaving each parent waiting for another copy. Trusted main already contains the guard from merged PR #6436: mark the first override hand-off and ignore the override on re-entry. Two clean source checkouts each completed a bounded real-launcher probe with exactly two app-entry visits and one successful version result. No duplicate fix is warranted.

5. Root cause

resolveBbBinary selects the host toolchain's bb executable. Toolchain lookup prefers the public launcher over the direct CLI. The script runner sets BB_CLI to that path. This is safe only if entry-point delegation is loop-safe.

The generated direct launcher replaces its shell with the app CLI runtime. The app CLI entry calls runBbCli, which delegates through runBundledCliCommand. Historically this honored BB_CLI every time without remembering the prior hand-off. A launcher-valued override therefore recursively launched the same path, leaving a waiting parent at each step.

Current main prevents this at the app-entry owner boundary:

const cliOverride =
  args.env[CLI_REEXEC_ENV_NAME] === "1"
    ? null
    : (toOptionalString(args.env.BB_CLI) ?? null);
...
if (cliOverride !== null) {
  env[CLI_REEXEC_ENV_NAME] = "1";
}

The marker is BB_CLI_REEXEC. After one override hand-off, re-entry selects the bundled CLI. The CLI's own handler respects the same marker. Trusted merge 544e49c1fe71f6374ce42dd65838446c133cdea2 added app-entry protection and its regression on October 28, 2026 at 19:07 UTC, before this issue was filed on October 29, 2026.
