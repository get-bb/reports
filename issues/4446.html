Reports · Issue #4446

Tasks project-default dispatch fails when the sole project source belongs to another host

2026-09-30 · Bug · Medium priority · Medium effort

REPRODUCED · High confidence in the Tasks-to-server host-selection failure. Remote workspace creation and model execution are outside the tested boundary.

Claim and exact observed result

Two synthetic connected hosts are seeded in the real server test database. One is primary; the project has a single default local-path source on the other. The actual Tasks delegation handler sends its project-default preset to the actual server thread-creation API through a test adapter. The server returns HTTP 404 with code invalid_request and message “Project has no local-path source for host”. Tasks keeps the task in todo with no attached thread.

This is a failure before successful dispatch, not evidence that work actually started on the wrong machine. With an explicit secondary-host worktree preset, the server returns 201 and records a provisioning intent naming that secondary host. A project whose source is on the primary host also succeeds with project-default. Explicitly choosing the wrong primary host for the secondary-only project fails with 409. Both clean runs produce the same results.

Expected: project-default can select the project’s usable default source host when the primary host has no source, while existing primary-host projects keep their current destination. The regression asserts successful secondary-host selection for the failing case; both assertions fail in both runs.

Fixture boundaries

The fixture executes actual Tasks storage, preset selection, RPC delegation and task updates, plus the real server API, source resolution and thread-provisioning records. Both Tasks and server use real isolated SQLite databases. The SDK testing host routes its threads.spawn method into an in-process server request; this adapter forwards the project, environment and synthetic prompt under a test Codex provider. It does not exercise network transport, real plugin installation, provider-specific execution options or a Tasks CLI/browser.

Hosts and sessions are synthetic database entries, and Git inspection responses come from the repository host-RPC test harness. A fake git-worktree environment provider holds provisioning in a waiting state. Thus a 201 and destination intent prove selection and thread attachment, not worktree creation or actual execution on a remote machine. No real filesystem workspace, enrolled host, user runtime, external model or network listener is used. No UI claim or screenshot is needed for the reproduced 404 boundary.

it("4446 routes project-default Tasks dispatch to the project source host", async () => {
  const server = await createTestAppHarness();
  const observations: unknown[] = [];
  const plugin = createFakePluginHost({ pluginId: "tasks", sdk: {
    system: { config: async () => ({ primaryHostId: "host-synthetic-primary" }) },
    threads: {
      spawn: async args => {
        const response = await server.app.request("/api/v1/threads", { method: "POST", headers: { "content-type": "application/json" },
          body: JSON.stringify({ projectId: args.projectId, providerId: "codex", origin: "plugin", originPluginId: "tasks",
            input: [{ type: "text", text: args.prompt }], environment: args.environment }) });
        const body = await response.json();
        if (response.status !== 201) {
          observations.push({ environment: args.environment, status: response.status, error: body });
          throw Object.assign(new Error(body.message), { status: response.status, code: body.code });
        }
        const intent = getThreadProvisionContext(server.db, body.id)?.request.environmentIntent;
        observations.push({ environment: args.environment, status: response.status, intent });
        return { id: body.id };
      },
      get: async args => {
        const response = await server.app.request(`/api/v1/threads/${args.threadId}`);
        return response.json();
      },
    },
  } });
  try {
    installFakeGitWorktreeProvider();
    const primary = seedHostSession(server.deps, { id: "host-synthetic-primary" });
    const secondary = seedHostSession(server.deps, { id: "host-synthetic-secondary" });
    seedPrimaryHost(server.deps, primary.host.id);
    const onSecondary = seedProjectWithSource(server.deps, { hostId: secondary.host.id, name: "Secondary fixture", path: "/synthetic/secondary-project" });
    const onPrimary = seedProjectWithSource(server.deps, { hostId: primary.host.id, name: "Primary fixture", path: "/synthetic/primary-project" });
    expect(onSecondary.source.isDefault).toBe(true);
    const store = createStore(plugin.bb);
    registerDelegation(plugin.bb, store);
    const preset = (kind: "project-default" | "new-worktree", machineId: string | null) => store.tasks.createPreset({
      name: `Synthetic ${kind} ${machineId ?? "default"}`, providerId: "codex", modelId: "gpt-5", reasoningLevel: "high", serviceTier: null,
      permissionMode: "full", environmentKind: kind, baseBranch: null, machineId, instructions: "", builtin: false,
    });
    const defaults = preset("project-default", null);
    const explicitSecondary = preset("new-worktree", secondary.host.id);
    const explicitPrimary = preset("new-worktree", primary.host.id);
    const dispatch = async (linkedBbProjectId: string, presetId: string, name: string) => {
      const project = store.tasks.createProject({ name, prefix: name.slice(0, 10), color: "blue", linkedBbProjectId });
      const task = store.tasks.createTask({ projectId: project.id, title: "Synthetic routing check", status: "todo" });
      let succeeded = false; let message: string | null = null;
      try { await plugin.harness.callRpc("delegate", { taskId: task.id, presetId }); succeeded = true; }
      catch (error) { message = error instanceof Error ? error.message : String(error); }
      return { name, succeeded, message, taskStatus: store.tasks.getTask(task.id)?.status,
        attachedThreads: store.tasks.listTaskThreads(task.id).length, dispatch: observations.at(-1) };
    };
    const missingPrimarySource = await dispatch(onSecondary.project.id, defaults.id, "REMOTEDEFAULT");
    const secondaryControl = await dispatch(onSecondary.project.id, explicitSecondary.id, "REMOTEEXPLICIT");
    const primaryControl = await dispatch(onPrimary.project.id, defaults.id, "PRIMARYDEFAULT");
    const wrongExplicitControl = await dispatch(onSecondary.project.id, explicitPrimary.id, "WRONGEXPLICIT");
    console.log(JSON.stringify({ phase: "tasks-host-routing", primary: primary.host.id, soleDefaultSourceHost: onSecondary.source.hostId,
      missingPrimarySource, secondaryControl, primaryControl, wrongExplicitControl }));
    expect(secondaryControl.succeeded).toBe(true);
    expect(secondaryControl.dispatch).toMatchObject({ status: 201, intent: { machine: { hostId: secondary.host.id } } });
    expect(primaryControl.succeeded).toBe(true);
    expect(primaryControl.dispatch).toMatchObject({ status: 201, intent: { machine: { hostId: primary.host.id } } });
    expect(wrongExplicitControl.succeeded).toBe(false);
    expect(missingPrimarySource.taskStatus).toBe("todo");
    expect(missingPrimarySource.attachedThreads).toBe(0);
    expect.soft(missingPrimarySource.succeeded).toBe(true);
    expect.soft(missingPrimarySource.dispatch).toMatchObject({ status: 201, intent: { machine: { hostId: secondary.host.id } } });
  } finally { await plugin.harness.dispose(); await server.cleanup(); }
}, 60000);

An initial first-checkout setup attempt reused a preset name and hit the Tasks database uniqueness constraint before dispatch. The fixture was corrected to unique preset names and valid project-prefix lengths; that setup attempt is not counted as bug evidence. The final fixture is unchanged across both reported runs.

Root cause and source permalinks

  • Tasks preset environment selection returns only type:project-default for that preset kind; an explicit worktree preset includes its selected host.
  • Tasks spawn call forwards that environment with the linked BB project.
  • Project-default host selection selects the connected primary host before resolving the project source. It does not try the project default source on another host.
  • Host-constrained source resolution searches that host and throws the observed 404 when no matching local-path source exists.

Fix proposal and next test

Resolve a suitable project source and its connected host before choosing the environment: preserve the primary host when it has a usable source, otherwise consider the project’s usable default source with an explicit deterministic policy. Preserve explicit-host requests and clear errors for offline or ambiguous sources. Keep the personal/projectless policy separate. No production fix was applied.

Add regression cases for primary-source preference, secondary default-source fallback, disconnected sources and multiple eligible sources. After a policy change, use two isolated real host daemons to verify worktree provisioning and execution reaches the selected host. Do not treat the fixture’s 201 as proof of that remote execution.
