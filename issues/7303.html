#7303 · Historical plugin failures override compatible range review

BugMedium priorityLow effortpluginsGitHub issue

2026-11-09 · trusted base f725841e324846711029f9e96924e603f04b3cb5

Verdict: REPRODUCED · Root-cause confidence: high · label: confirmed-repro

1. TL;DR

An earlier failed plugin activation suppresses a later compatible release that requires reviewing a new version range. The update data can contain both a valid range candidate and an historical failure; those values are not mutually exclusive. The release button rejects every candidate when a failure exists, and the dialog independently prioritizes the failure screen. A new end-to-end component regression fails on unchanged trusted main in two separate clean checkouts. Removing the two obsolete precedence restrictions restores explicit review and submits the selected range and version only after confirmation.

5. Root cause

The server intentionally serializes persisted release discovery and activation history independently: updateStateForRow includes both rangeUpgrade and lastFailure. The discovered range candidate comes from range upgrade resolution. A previous failed version therefore does not imply that the newer candidate is unavailable.

reviewableRangeUpgrade already checks the actual admission policy: no ordinary in-range candidate, a range-upgrade candidate, and no compatibility-blocking reasons. It intentionally does not reject historical failures.

The release control adds an unrelated failure veto:

if (availableVersion === null) {
  if (rangeUpgrade === null || failure !== null) return null;
  ...
}

The dialog's first branch also returns historical failure details unconditionally. Its later range branch separately requires no failure:

if (failure !== null) { ... }
...
const rangeUpgrade = reviewableRangeUpgrade(plugin);
if (failure === null && rangeUpgrade !== null) { ... }

Both checks must change. Fixing just the button leaves the user at a stale failure screen. The tested defect is presentation-state precedence, not resolver compatibility, activation rollback, stored data, or a public protocol defect.

6. Proposed fix and verification

Use the existing reviewable-range predicate for the release button even when failure history exists. Compute it before selecting dialog content and show historical failure only when there is no reviewable candidate. Keep the existing explicit confirmation, compatibility checks, and in-range retry path. Do not erase failure history.

The implementation changes three files within plugin management, with 77 additions + 4 deletions = 81 changed text lines. It introduces no dependency, lockfile, generated module, migration, persisted-data change, public protocol/schema, security or packaging change.
