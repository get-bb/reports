5. Root cause

Demonstrated gap: native-shell setup does not establish a scale-1 page policy. Probable symptom mechanism: WKWebView is allowed to use its normal page-zoom behavior. Confidence is medium for the reported native symptom and high only for the observed missing viewport constraint.

  1. apps/mobile/src/lib/shell/shell-url.ts constructs the shell URL from the paired server, not the public marketing site.
  2. apps/server/src/start-server.ts selects the app distribution; apps/server/src/server.ts serves its index.html.
  3. apps/app/index.html contains the app viewport: 
    <meta name="viewport"
  content="width=device-width, initial-scale=1.0, viewport-fit=cover, interactive-widget=resizes-content" />
    Initial scale determines startup scaling, not a locked scale.
  4. apps/mobile/src/screens/webview/ProfileWebViewScreen.tsx supplies scrolling, media, and inset options and injects buildBridgeInjectionScript. None of those options explicitly constrains page zoom. Its apps/mobile/src/screens/webview/ProfileWebViewScreen.tsx wrapper only forwards the props and source.
  5. packages/mobile-bridge/src/inject.ts finishes installation immediately after assigning the native API: 
    native.__apply(handshake);
root.native = native;
    The probe confirms successful installation without any viewport policy being applied. Inspection of the locked WebView native implementation found no BB page-zoom override in its existing patch.

The marketing route apps/web/src/routes/__root.tsx is not used as root-cause evidence. Its permissive viewport is not proof about the paired-server shell.
