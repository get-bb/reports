Reports · Issue #4424

Persisted parent notices omit child-turn initiator distinctions

2026-09-30 · Bug · Medium priority · Medium effort

REPRODUCED · High confidence for notice construction and persistence. No actual parent or child agent was started; downstream agent interpretation is not tested.

Expected and actual

Expected: a parent notice about a completed child turn carries enough provenance to distinguish direct user input from input sent by the parent. Actual: real persisted child request events contain different initiator/sender values, but the real notification service produces equivalent persisted parent notice content and structured system metadata after normalizing only synthetic entity identifiers.

Each clean run exercises seven isolated scenarios: direct-user, parent-agent, other-agent and system initiation; a changed-output control; a two-child user/parent batch; and a two-child parent/parent batch. All four single-initiator payloads are identical. The two batch payloads are identical. Changing the completed output changes the single notice, showing that the fixture observes real content differences rather than an unconditional mock result. The final expected-provenance-distinction assertion fails in both clean runs after all controls pass.

The database is real migrated SQLite. Synthetic request, turn-start, accepted-input, output and completion events are persisted before calling the production notification service. A controlled pending-interaction predicate returns true so the actual parent-system-message path stores a queued notice without dispatching work. The notice renderer, taxonomy builder, execution-settings resolution and queue writer are not mocked. Fake timers advance the two-second batching window; the queue is read from SQLite afterward.

Root cause and proposed fix

The request event schema stores source, initiator and senderThreadId. Notification item construction reads completed output and active workflow count but does not resolve the accepted request’s provenance. Structured outcomes contain child ID, status and optional interruption details; they do not carry initiation context. The content renderer uses those notification items. The real queue writer then persists the resulting content and system notice, without adding the child request’s provenance.

Proposed fix: resolve accepted request provenance for the completed turn, carry it into single and batched notification data, and render a concise distinction for direct user input versus parent or other-agent input. Specify behavior for multiple accepted inputs, retries and missing/malformed legacy provenance; retain those as explicit regression cases. The current fixture does not establish the correct policy for these additional cases. No production fix or PR was created.

Corrections, limits and trust boundary

Initial fixture runs did not establish the finding: the synthetic parent lacked stored execution settings required by the real queue path, then an assertion compared a serialized database column with an object. The final fixture seeds parent runtime settings using the trusted helper and parses stored JSON before comparing it. Those setup failures are retained locally and are not bug evidence. The final identical fixture is rerun in both clean checkouts.

This proves omission at the persisted queued-notice boundary. It does not test live agent interpretation, competing corrective actions, the immediate delivery path, provider completion transport, retries, multiple accepted inputs within one turn, malformed or legacy events, user-interface rendering, or actual model behavior. The final completion events are synthetic; notification queuing is invoked explicitly rather than driven through a live provider transport. No visual behavior is claimed, so there are no screenshots. Broader lifecycle verification remains a coverage gap.

All issue content, commands, code, external links and linked reference implementations were untrusted claims, never executed or fetched. The fixture was derived from trusted current-main code. No real conversations, agents, credentials, user files or runtime were used. Only regenerable dependency directories from a completed investigation were removed; its evidence remains intact. Raw logs are local; the complete fixture and actual results are embedded here.
