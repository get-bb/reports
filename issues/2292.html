#2292 · prompt history: empty-array rows persisted then skipped at read (zod too_small; 11 rows observed)

Bug Priority: Low Effort: S (suggested in issue) threads open on GitHub 2026-08-24 · base 494f66526

Verdict: REPRODUCED (live on a dev instance and with a unit test at the exact write path) · Root-cause confidence: high

1. TL;DR

bb remembers every prompt a user sends so the composer can recall it later ("prompt history", table prompt_history_entries). A thread can legitimately be started without a prompt: bb thread fork <id> with no --prompt, the SDK's threads.fork without input, or the side-chat panel's launcher fork, all clone the source provider session and leave the new thread idle. For those starts the server still writes a prompt-history row whose stored input is the JSON string []. When history is read back, the row is parsed with a schema that requires at least one item, so it fails validation, is dropped, and a WARN Skipping malformed prompt history row is logged on every read for as long as the row exists. Nothing crashes and the user sees nothing wrong (the app also drops empty drafts client-side); the defect is a wasted row plus perpetual log noise. The cause is that the single write funnel recordAcceptedPromptHistoryEntry persists args.input unconditionally, and a no-prompt fork is user-initiated and root-level (forks are not hierarchy children), so it resolves to the project scope and is written. PR #2295 adds an input.length === 0 guard at that funnel; I verified it fixes the write path in unit tests and live.

5. Root cause

Mechanism, end to end:

  1. A fork request may carry no prompt. forkThreadRequestSchema.input is .min(1).optional() (threads.ts#L177); createThreadForkFromRequest defaults it to [] (thread-fork.ts#L109-L115). It only marks the start as agent-initiated (startedOnBehalfOf) when there is an agentContextSeed and no visible input (isSeedOnlyIdleFork, #L144-L146). A fork with neither stays initiator: "user". createThreadRequestSchema accepts the empty array because originKind !== null (#L146-L152).
  2. Forks are not hierarchy children. createThreadFromRequest sets hierarchyParentThreadId = originKind === null ? requestInput.parentThreadId : undefined (thread-create.ts#L612-L617; comment at #L644: "Forks and side chats are not hierarchy children"). The new thread therefore has parentThreadId: null — confirmed in the live output.
  3. requestThreadProvision appends the client/turn/requested event and then unconditionally calls the history funnel with the same input (thread-provisioning.ts#L254-L260).
  4. recordAcceptedPromptHistoryEntry decides the scope purely from initiator, target.kind and parentThreadId (prompt-history.ts#L159-L175): user + thread-start + root → "project". It never looks at the input, and persists it as-is (#L249-L270); createPromptHistoryEntry JSON-stringifies [] (db/prompt-history.ts#L51-L75).
  5. Reads parse every row with z.array(promptInputSchema).min(1) (#L24) inside buildPromptHistoryEntries, whose catch block drops the row and logs the warn (#L134-L157). The row is never cleaned up, so the warn repeats on every read.

Why this is the real cause and not a read-side bug: the write and read sides disagree on the invariant. The read side encodes "a remembered prompt has at least one item" (which is the right invariant: there is nothing to recall from an empty prompt, and the runtime never even runs a turn for it — thread-lifecycle.ts#L731-L736). The write side treats "a user-initiated thread-start request was accepted" as sufficient, which became false when empty-input forks were introduced. Per AGENTS.md ("validate at the boundary, then pass typed values"), the row should never be written.

Which real surfaces trigger it: bb thread fork <id> without --prompt/--file/--image/--agent-context-seed (fork.ts#L72); SDK threads.fork({sourceThreadId}); the side-chat launcher fork ("no anchor, no seed", side-chat/app.tsx#L345) and any side chat whose anchor equals the source's last message (resolveReplySeedText returns null → no seed, side-chat/server.ts#L201-L213). Side chats that do get a seed start as initiator: "agent" and never write a row. The web app's "fork from message" flow navigates to the composer and submits a real prompt, so it is not affected.

Deeper observation (not this bug): the same funnel records the full input, so a fork that carries both an agentContextSeed and a visible prompt stores the agent-only seed item in project prompt history. promptInputToDraft does not appear to filter on visibility (only threadQueuedMessages.ts does). I did not drive that path; it is a candidate for a separate issue if recall of agent-only text is undesirable.

6. Proposed fix (first principles)

Reject empty input at the single write funnel — exactly what PR #2295 does — so every call site (provisioning, reprovisioning, send, queued flush) is covered and the stored invariant matches the read schema:

// apps/server/src/services/prompt-history.ts, recordAcceptedPromptHistoryEntry
if (args.input.length === 0) {
  return false; // no prompt was sent, so there is nothing to recall
}

Keep the read-side skip as defense in depth for rows that already exist. Optionally add a one-off Drizzle migration DELETE FROM prompt_history_entries WHERE input = '[]' so users who already have bad rows (the issue's 11) stop getting a warn on every history read; the rows carry no information, so deleting them cannot lose anything. What could go wrong: nothing observable — the return value is ignored by all callers (grep confirms no caller reads it), new-turn targets already require min(1) input at the API boundary, and the guard does not alter scope resolution. No wire shape changes, so HOST_DAEMON_PROTOCOL_VERSION does not need a bump.

Scope resolver (base)

function resolveAcceptedPromptHistoryScope(args) {
  if (args.initiator !== "user") return null;
  if (args.target.kind !== "thread-start") return "thread";

  return "project";
}
