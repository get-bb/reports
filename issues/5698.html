1. TL;DR

The reported symptom is interrupted microphone input when the iOS application is no longer visible. This investigation confirms a necessary configuration gap: Expo's real native-config pipeline produces an iOS Info.plist with notification background support, but without background audio, in both production and development variants. The result repeats byte-for-byte in a second clean checkout of the same trusted main commit. No iPhone or iOS simulator is available on this Linux host, so microphone mute/unmute events, locked-screen behavior, and whether the proposed capability change is sufficient remain unverified. This is a verified partial result, not an end-to-end reproduction or a proof that the issue's proposed fix works.

const { resolve } = require("node:path");

  readFileSync(resolve(mobileDirectory, "package.json"), "utf8"),

const revision = spawnSync("git", ["rev-parse", "HEAD"], {
  cwd: repository,
  encoding: "utf8",

if (revision.status !== 0) throw new Error("Cannot identify repository revision");
const environment = { ...process.env };
delete environment.GOOGLE_SERVICES_JSON;
delete environment.EXPO_DEBUG;
delete environment.EXPO_CONFIG_PLUGIN_VERBOSE_ERRORS;
const results = [];
for (const variant of ["production", "dev"]) {
  const generated = spawnSync(
    "pnpm",
    ["exec", "expo", "config", "--type", "introspect", "--json"],
    {
      cwd: mobileDirectory,
      encoding: "utf8",
      env: { ...environment, BB_MOBILE_VARIANT: variant },
      maxBuffer: 16 * 1024 * 1024,
    },
  );
  if (generated.status !== 0) {
    throw new Error(`Expo introspection failed for ${variant}`);
  }
  const configuration = JSON.parse(generated.stdout);
  const infoPlist = configuration?._internal?.modResults?.ios?.infoPlist;
  if (!infoPlist || typeof infoPlist !== "object") {
    throw new Error("Expo did not produce an introspected iOS Info.plist");
  }
  const modes = infoPlist.UIBackgroundModes;

5. Root cause

Confirmed configuration cause: the iOS manifest declares a microphone usage description but only the notification background mode:

"NSMicrophoneUsageDescription": "bb records voice input and transcribes it into your prompt."
...
"UIBackgroundModes": ["remote-notification"]

The dynamic config spreads the base config; the dev-variant adjustments do not supply a separate iOS audio declaration. The executed Expo introspection additionally proves that the final plugin-modified iOS plist does not acquire audio support elsewhere.

The WebView permits media capture, but that permission is distinct from native background execution. Apple's recording-session documentation, found independently of the issue's links, describes native background audio configuration as necessary for recording after backgrounding or screen lock. It does not prove that WebView capture will work after that configuration is added.

The voice recorder creates a Web Audio graph from the input stream. That graph cannot recover microphone samples that the native platform stops delivering. The recorder's visibility callback reacquires a wake lock on return to visibility; this callback does not establish a native background capability.

Limit: attributing the precise mute event to a particular WebKit gate remains a hypothesis. Confidence is high for the missing generated declaration and medium for its causal relationship to the reported runtime symptom. This report does not assert that all audio features, network connections, or iOS versions behave identically.

6. Proposed next experiment and fix scope

First reproduce on a physical iPhone using a native build of the recorded main commit. Start built-in voice recording, background the application and lock the screen, then return and inspect captured audio for gaps. Capture input-track events and audio samples independently of the output graph. Repeat using a locally built application with background audio enabled while retaining notification support; compare the recordings and OS behavior.

The smallest candidate change is in the native iOS background-mode declaration. It changes packaged background capabilities and should receive product/privacy review plus real-device checks for deliberate stop, permissions, interruption by calls, and foreground/background transitions. No native-session override is justified by this report's evidence.
