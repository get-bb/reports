#5824 · Notification preview block filtering

BugPriority: LowEffort: LowremoteIssue

2026-10-20 · trusted origin/main: 7e4232ef241b5cdfb7d272cee044fe6f82702c70

Verdict: REPRODUCED · Root-cause confidence: high · reproduction label: confirmed-repro

1. TL;DR

The notification text builder can select app-only markup instead of a later readable sentence. Five synthetic cases fail against unchanged main: a leading directive, a leading table, a JSON object, a JSON array, and a directive-only reply that should allow the existing fallback. Three controls pass. The same eight cases produce the same five failures in a second clean checkout tested by the same agent. Existing notification tests all pass because their preview coverage does not exercise these block forms.

5. Root cause

firstParagraph, lines 13–35, recognizes fences, headings, horizontal rules, and blank lines but treats all other nonempty lines as prose. It joins those lines and returns the first such paragraph, so later prose is never considered. Inline Markdown cleanup and notificationPreviewText do not recognize structured blocks either.

const text = line.replace(BLOCK_MARKER_PATTERN, "").trim();
...
lines.push(text);
...
return lines.join(" ");

The app recognizes the leaf marker separately in markdown-message-directives.tsx; registered inline-vis syntax is exercised in the trusted inline-vis tests. The notification path does not use that block interpretation.

Sender lines 349–380 compute one body using preview || FALLBACK_BODIES[resolved.kind], then reuse it for both delivery paths. A directive-only preview is truthy, so the existing turn-finished fallback cannot apply.

The trusted existing preview test at server.test.ts lines 492–525 covers headings, inline formatting, and thread references, not these block forms.

6. Proposed fix

Keep the change inside the notification text subsystem: skip standalone app directives and recognized table blocks, ignore complete valid JSON object/array paragraphs, and continue looking for readable prose. Return an empty string if none remains, preserving the existing sender fallback. Preserve prose, thread references, fences, and inline formatting. Avoid treating every pipe-prefixed prose line as a table or discarding malformed JSON-like prose.

No production fix was made here: GitHub metadata confirms ready, open PR #5825 already closes this issue. The duplicate-PR guard therefore stops fix work before creating a branch.
