#8178 · Redundant validation in terminal send paths

Bug Priority: Medium Effort: Medium host perf · GitHub issue · November 25, 2026

Trusted origin/main base: fb045a046653cc127656ca3c7243d44ae4c94f3f

Verdict: REPRODUCED · Root-cause confidence: high.

1. TL;DR

Large terminal output pays for synchronous payload validation on its way out of both the host daemon and the server. The sender traverses the full base64 string again even though the daemon produced it from a Buffer and the server receives it through an already-validated daemon message. An independently authored diagnostic exercised the actual send methods: each output scanned the base64 payload once, and a 64-chunk replay scanned it 64 times before the daemon even checked whether it had a connection. Repeating the diagnostic in a second clean checkout produced the same scan counts and comparable timings. This confirms avoidable synchronous work, not the issue's particular Node 26 performance ratios or an end-to-end terminal throughput measurement.

5. Root cause

Validation is attached to outbound serialization rather than restricted to external input boundaries for the verified terminal-output paths. Its cost scales with base64 characters, and it runs synchronously on the sender's JavaScript thread.

  1. terminal-manager.ts:962–994 slices local Buffer data into at most 64 KiB chunks and calls dataBuffer.toString("base64"), then sends terminal.output.
  2. server-connection.ts:200–216 unconditionally calls hostDaemonDaemonWsMessageSchema.parse(message) before checking the sequencer or encoding. The terminal output/replay members include the chunk schema (chunk; message members).
  3. terminal.ts:9–10 defines the anchored base64 regex. terminal.ts:65–76 installs it in terminalDataBase64Schema together with length and decoded-size checks.
  4. daemon-protocol.ts:285–303 passes incoming daemon data through parseSocketValue with the full schema. This remains an essential trust boundary.
  5. terminal-session-lifecycle.ts:346–353 copies seq and dataBase64 without mutation; live forwarding and replay forwarding send those chunks to the hub.
  6. hub.ts:531–558 calls JSON.stringify(terminalServerMessageSchema.parse(message)) in both send methods. The server chunk schema uses the same base64 validator. Finally, the browser transport safe-parses messages on receipt.

Consequently a live output chunk encounters two avoidable outbound regex scans in addition to the server's inbound check and the browser's receive check. A replay's daemon parse scans every included chunk synchronously; the server's replay-forwarding loop then validates every outbound output chunk again. The disconnected daemon probe isolates the validation cost, not the full connected-send cost.

6. Proposed fix

Skip full outbound validation only for daemon terminal.output and terminal.replay built by the audited local producers, and for server output created from validated daemon chunks. Preserve inbound server/browser validation and keep existing parsing for other message kinds, whose schemas can strip unknown fields or provide other behavior. Preserve exact serialization, queueing, replay ordering, and backpressure. Do not broadly remove the outbound guard from unrelated messages.

No production patch or new fix branch was created here: open PR #8179 already links to #8178. The autopilot's duplicate-PR gate stops fix work regardless of whether a small patch might otherwise qualify.
