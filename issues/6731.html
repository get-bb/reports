#6731 · Scheduled recipients remain ineligible after completion

BugPriority: Medium Effort: Lowplugins · automations · confirmed-repro Issue #67312026-10-30

Trusted base: a0e513398f02d47ec5df874b89fec4edfc248894. Verdict: REPRODUCED · Root-cause confidence: high.

1. TL;DR

An ordinary thread can receive a scheduled prompt without being created by an automation. The Automations plugin nevertheless records that recipient in the same history used to classify automation-created threads. After the run finishes and its schedule is paused, the creation guard still rejects follow-up work from the recipient. Both agent and script follow-ups failed in two separately cloned trusted-main checkouts using real plugin SQLite storage. This confirms the server-side lifecycle defect, not the reporter's specific desktop installation.

5. Root cause

plugins/automations/src/run.ts:223–235 associates an existing recipient with the run and writes an automation-thread mark before sending the prompt.

  setAutomationRunThread(db, {
    runId: args.run.id,
    threadId: args.targetThreadId,
  });
  markAutomationThread(db, {
    automationId: args.automation.id,
    runId: args.run.id,
    threadId: args.targetThreadId,
    now: Date.now(),
  });
  await bb.sdk.threads.send({
    threadId: args.targetThreadId,
    mode: "steer-if-active",

plugins/automations/src/run.ts:351–365 settles the run on idle; it does not change that historical identity classification.

plugins/automations/src/data.ts:958–968 returns true for either any retained mark or any run, without distinguishing thread provenance or terminal run status.

export function isAutomationSpawnedThread(db: Db, threadId: string): boolean {
  return (
    db
      .prepare(
        `SELECT thread_id FROM automation_thread_marks WHERE thread_id = ? LIMIT 1`,
      )
      .get(threadId) !== undefined ||
    db
      .prepare(`SELECT id FROM automation_runs WHERE thread_id = ? LIMIT 1`)
      .get(threadId) !== undefined
  );

plugins/automations/src/service.ts:144–151 uses that overbroad classification to deny creation. The guard runs before the execution-mode branch at plugins/automations/src/service.ts:650–659, explaining both failing modes.

function assertNotRecursiveCreation(
  db: Db,
  createdByThreadId: string | undefined,
): void {
  if (createdByThreadId === undefined) return;
  if (isAutomationSpawnedThread(db, createdByThreadId)) {
    throw new Error("Automation-spawned threads cannot create automations");
  }

Deleting only the mark would not solve the underlying problem: the retained run record is a second unconditional match. History is evidence that a thread received work, not proof that an automation created it.

6. Proposed fix and automation limit

Separate permanent automation provenance from temporary in-flight automation execution. Use validated core thread-origin metadata for the former and currently running plugin run records for the latter. Do not delete successful history or paused schedules to restore eligibility. Reject unavailable or mismatched creator metadata rather than silently bypassing recursion protection.

Extend regression coverage to automation-created threads without retained local history, active recipients, settled recipients, and failed metadata lookup. The supplied reproduction deliberately shows the current active-run error; a final fix may use a different diagnostic while preserving rejection.

No automatic fix PR: the required production change alters the recursion-prevention creation permission/safety guard. The rule explicitly excludes permission/security-boundary changes from simple fixes. No production code was changed, no fix branch was pushed, and no duplicate PR was opened.

7. Linked PR review

PR #6729 was closed and unmerged when inspected; GitHub metadata links it to this issue. A separate search found no open linked PR. Its untrusted diff was read only after designing the reproduction from trusted-main source.

The diff replaces history-only classification with running-run checks and validated core origin metadata, and removes obsolete mark-writing helpers without dropping history tables. That direction addresses the independently observed mechanism. Static verdict: consistent with the verified cause, but not executed or approved here. No additional defect is claimed from static inspection. The changed creation guard in service.ts requires focused fail-closed and recursion-safety review.
