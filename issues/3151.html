#3151 · ACP steering cancels the active prompt

Bug Medium Effort: Medium threads provider-acp open on GitHub 2026-09-05 · base 39636049b3d6

Verdict: REPRODUCED · Root-cause confidence: high

1. TL;DR

Sending a steer to an active ACP-backed thread cancels the provider’s current session/prompt request. BB then sends only the steer text in a second session/prompt, so an ACP agent can abandon unfinished work from the original request and respond only to the new message. A focused fake-agent test records both prompt requests and proves that session/cancel appears between them on trusted main. The same test failed identically in a second clean checkout.

6. Root cause

The turn/steer handler first appends the new input to queuedInputs, then immediately calls requestSteerCancel. That helper marks the live prompt cancelled and sends an ACP session/cancel notification. See the steer handler and the cancellation helper.

session.queuedInputs.push({ input: params.input, ... });
requestSteerCancel(session);

session.connection.notify("session/cancel", {
  sessionId: session.providerThreadId,
});

After the cancelled request resolves, the turn loop shifts the queued input and starts a new session/prompt carrying only that input. It does not combine the unfinished original input with the steer. See the prompt loop. The bridge also advertises steerMode: "queue" in its capabilities, but implements an interrupting cancel-then-prompt sequence. This behavior was deliberately introduced by merged PR #1477 because ACP v1 has no native mid-prompt injection.

7. Proposed fix (first principles)

Choose and document one ACP-specific contract. To preserve the active request, leave the steer in queuedInputs, wait for the current session/prompt to finish, and then submit the queued input as the next prompt without calling session/cancel. That matches the bridge’s advertised queue mode, but it means a hung ACP prompt cannot be interrupted by steering. Alternatively, retain hard-steer cancellation and expose that limitation clearly in the product. Selecting between responsiveness and preservation is a product/architecture decision, so no production patch should be made automatically.
