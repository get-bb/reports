#4957 · Daemon WebSocket transport bypasses the environment proxy agent

BugMedium priorityMedium efforthost · connect · confirmed-reproGitHub issue2026-10-05

Verdict: REPRODUCED — core WebSocket defect. Root-cause confidence: high.

Trusted base: ca232e1507ff2b7b6b71d931cbbe1f102a9e95d3, fetched from the target repository's main branch; still current at the final source check.

1. TL;DR

The daemon's server WebSocket constructor does not route through an environment-declared HTTP proxy, even when Node's native HTTP proxy support is enabled. A local deterministic fixture exposes an origin hostname that cannot resolve directly and a working proxy that can handle its requests. Native HTTP reaches the proxy, and native HTTPS sends CONNECT, but all four daemon WebSocket variants attempt direct DNS and fail with ENOTFOUND. The cause is more precise than a missing environment lookup: ws supplies a custom createConnection function, causing Node to skip its global agent unless an agent is explicitly selected. The report's separate assertion about machine-auth HTTP upstreams does not hold on Node 24.5.0 with native environment proxy support enabled.

5. Root Cause

The server connection adapter selects createNodeWebSocketConstructor(headers). That constructor either returns ws unchanged or passes only headers:

if (!headers) return NodeWebSocket;
super(address, protocols, { headers });

The installed ws dependency selects a direct TCP/TLS socket creator in websocket.js:752–753. In the actual Node 24.5.0 runtime, ClientRequest:211–220 selects the global agent only when no custom createConnection function is present:

let agent = options.agent;
const defaultAgent = options._defaultAgent || Agent.globalAgent;
if (agent === null || agent === undefined) {
  if (typeof options.createConnection !== 'function') {
    agent = defaultAgent;
  }
}

Thus native environment proxy initialization cannot help the default ws dial: it bypasses that agent and directly resolves the target. On a proxy-only network, direct resolution or dialing fails, preventing the server WebSocket from opening. This is not a provider fetch issue.

The connect tunnel's default dial follows the same ws pattern. In contrast, machine-auth upstream HTTP requests do not specify createConnection, so they use the environment-aware global agent on the tested runtime.

6. Proposed Fix and Autopilot Safety

Select an explicit proxy-aware agent at the daemon's WebSocket dial boundary and share the selection between the server and connect-tunnel sockets. Preserve end-to-end TLS verification, established authentication headers, local bypass behavior, and error redaction. Add real local proxy tests for successful ws/wss tunnels, NO_PROXY, proxy refusal, and credential isolation; this report supplies the failing routing contract.

No automatic fix branch or PR is safe under this rule. The supported runtime baseline is Node 22.19.0, so merely selecting Node 24.5's environment-aware global agent is not a complete supported-runtime solution. The daemon has no direct proxy-agent dependency; a complete dependency-free implementation would own CONNECT/TLS, proxy credentials, and loopback/NO_PROXY routing policy. That requires security-boundary and product-policy review, expressly outside the simple-fix allowance. No production files were changed or pushed.
