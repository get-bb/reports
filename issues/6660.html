#6660 · Active voice capture is discarded by composer teardown

Bug High Effort: Medium ui · GitHub issue · 2026-10-30

Trusted main: a1bf55b6a04c7948ae5ae0dcfcbdec27d2b507a2

Verdict: REPRODUCED · Root-cause confidence: high · Reproduction label: confirmed-repro

1. TL;DR

A composer that disappears while its microphone is still recording loses the audio already captured. Its cleanup deliberately treats disappearance like cancellation: it disables transcription and clears the in-memory audio buffer. The recoverable-recording store is reached only later in the accepted stop path, so this cleanup never creates an entry to retry. A regression probe against the real React hook reproduces zero transcription requests, zero transcript deliveries, zero recoverable recordings, and zero error notifications after unmount. Explicit Stop succeeds and explicit Cancel discards, using the same delayed recorder fixture.

5. Root cause

Unmount cleanup, useVoiceInput.ts:365–383 reads whether a recording was already accepted. An active recorder instead has transcription disabled before stop:

if (recorder && recorder.state === "recording") {
  shouldTranscribeRef.current = false;
  try {
    recorder.stop();
  } catch {}
}
...
if (!acceptedRecordingPending) {
  chunksRef.current = [];
  startedAtMsRef.current = null;
  promptContextRef.current = undefined;
}

Data and stop handlers, useVoiceInput.ts:556–619: data events only push into the component ref. The stop handler sees disabled transcription, clears the buffer again, sets idle, and returns before file creation or saveVoiceRecording. The same result therefore occurs even when the recorder delivers its final chunk asynchronously after unmount.

Recording store, voice-recording-store.ts:138–178: the recovery store can only retain audio once a file has been saved into it. It has no ownership of an actively recording composer's chunk buffer. This is why existing failed-recording retention cannot rescue this path.

Existing upstream test, useVoiceInput.test.tsx:458–469 expressly requires unaccepted recordings to be discarded. The problem is not merely a missed ref assignment; the lifecycle currently encodes destructive product policy.

The question field has an additional lifetime constraint: VoiceInputTextarea.tsx:40–54 selects an ephemeral key, throws an AbortError when unmounted around the request, and ignores transcript delivery afterward. Ephemeral cleanup deletes recordings for that key. Unlike persisted composer draft delivery, this input does not have a durable destination once its question closes.

6. Proposed fix and simple-fix decision

First choose whether leaving a recording should stop and retain audio or keep an app-level recording alive. Keep explicit cancellation destructive. A stop-and-retain implementation for persisted composers can reuse accepted recording/draft delivery, but it must preserve duration, context, pending-stop ordering, and audio until the final recorder event. Ephemeral question inputs additionally need a recoverable owner or an explicit navigation guard, not a callback into an already removed field.

No automatic pull request. Changing the expressly tested discard-on-unmount policy, and deciding ownership for disappearing question fields, requires a product decision. That fails the rule's simple-fix gate even if a narrow code change would fit the line limit. No production patch, source branch, or source push was made. GitHub cross-reference metadata and an open-PR search for the issue number returned no linked open PR at investigation time.
