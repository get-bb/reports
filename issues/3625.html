1. TL;DR

The report describes tools becoming undiscoverable during a long-lived Claude session. A focused test on current main found that the BB MCP server still lists its registered tool after a simulated compact event and an unchanged session resume. This exercises the real BB bridge and MCP server, with the Claude SDK query replaced by the repository's controlled test harness. It does not exercise Claude ToolSearch, a real daemon disconnect, or a long-lived authenticated Claude process. The original symptom remains unverified, and the actual root cause is unresolved.

5. Root cause

Unresolved. The code establishes a construction-time tool set, but that does not by itself explain loss from a previously working Claude catalog.

  • Runtime resume returns early when hasThread is true; otherwise it forwards resumeContext.dynamicTools.
  • Turn submission forwards input, options, contributed environment, and instructions; no dynamicTools refresh occurs.
  • Session attachment builds the bridge only for nonempty tools:
    if (params.dynamicTools && params.dynamicTools.length > 0) {
  const mcpServer = buildBridgeMcpServer(params.dynamicTools, ...);
  sessionOptions.mcpServers = { [BB_BRIDGE_MCP_SERVER_NAME]: mcpServer };
}
  • Compact boundary handling refreshes context usage; the probe found no BB-side removal of tools.
  • MCP list handler maps the supplied tool definitions to the response.

6. Proposed next experiment

Use a disposable authenticated Claude process to record tool names at attachment, then exercise actual compaction and daemon reconnection separately while checking ToolSearch before and after each event. A BB MCP list response and Claude's deferred catalog are distinct observations. No production fix is justified until a faithful failing test identifies which layer loses the tools.
