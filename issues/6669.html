#6669 · Usage throttling has no shared cooldown

Bug Medium priority Medium effort providers provider-claude-code GitHub issue 2026-10-30 · base 9662c45478f4a74f33f11b70187657d97f1e14a7

Verdict: REPRODUCED · Root-cause confidence: high · label: confirmed-repro

1. TL;DR

Claude usage checks can repeatedly fail even while other provider functionality remains usable. In deterministic tests against main, two immediate reads both contact a synthetic endpoint despite its 300-second Retry-After header. The server also makes two host probes for two sequential error reads, and the provider-owned resource makes a third collection immediately after caching a failure. A prior successful 42% usage window disappears from that resource response while its last-success timestamp survives. These observations establish the missing cooldown and lost resource data; they do not establish how Anthropic dynamically extends throttling in production.

5. Root cause

No retry deadline at the provider boundary

The provider always fetches after resolving credentials. A 429 becomes a generic error message: the response headers are not inspected and no retry state is stored. This alone permits back-to-back requests.

The server deliberately gives errors zero TTL

The server coalesces concurrent calls, but an error gets zero lifetime. Therefore sequential readers start a new host RPC. Importantly, an existing server test explicitly enshrines immediate retry for generic errors: blindly increasing every error TTL would change that behavior rather than selectively handling throttling.

Existing generic-error recovery test

Successful-only caching overwrites the last good resource measurement

The provider resource reuses a cached value only when status is ok. It sets observedAt to the previous success time on failure, then replaces the same cache entry with the error. Its error schema has no windows or explicit stale-measurement field. A timestamp without the matching value cannot reconstruct the last successful limits.

6. Proposed fix and simple-fix gate

A complete repair should distinguish retryable throttling from ordinary failures, bound and share a retry deadline by the correct host/provider/account identity, and preserve last-successful windows with an explicit stale age. Specify whether forced refresh can bypass cooldown, how account changes invalidate cached data, how Retry-After seconds and dates are parsed, and how malformed or missing headers fall back. Keep genuine fresh errors distinguishable from stale successful values.

No automatic PR: the verified full defect spans the provider bridge, server cache, and public resource contract. The typed provider error exposes no retry deadline; the resource error schema exposes no last-good value. Implementing explicit stale results and shared selective cooldown requires contract/semantics and product-policy decisions, which are outside the rule's simple-fix allowance. A generic error TTL alone would leave retry timing and lost data unfixed and would contradict the existing recovery test.

Provider usage wire contract. No production fix, dependency, schema change, branch, commit, or PR was made in get-bb/bb.
