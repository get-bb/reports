1. TL;DR

An attachment request with a multipart header but no body reaches the real upload route and returns HTTP 500 with the generic internal-error message. That server symptom was reproduced twice from clean trusted-main checkouts. The SDK also skips reading bytes when the input is already a Blob with matching MIME metadata; a diagnostic confirms that branch, while ordinary Node File serialization still transmits all bytes. This environment is Linux, not iOS: no iPhone drag, Safari, Photos source, mobile wrapper, or Connect transport was exercised. The proposed WebKit-specific trigger is plausible but not established by these tests; the overall issue therefore remains only partially reproduced.

5. Root cause

The composer drop handler forwards dropped files into its attachment callback. The upload mutation passes the File to the SDK unchanged.

The SDK upload implementation reuses matching Blob inputs; only the other branch invokes the byte-reading helper. The diagnostic directly measures the resulting read counts. This confirms the missing normalization step alleged by the report, but not that such normalization is universally necessary or sufficient on iOS.

const file =
  input.clientFile instanceof Blob && input.clientFile.type === mimeType
    ? input.clientFile
    : new Blob([await attachmentBytes(input.clientFile)], {
        type: mimeType,
      });

The server upload route calls context.req.formData() before validating fields, without translating parser failure into an input error. The exception reaches the generic error handler, which returns 500 and the internal-error envelope seen in both runs. This independently explains the server symptom for an empty multipart body. It does not establish why the client body was empty.

6. Proposed fix and safety decision

First verify on a real iPhone that a byte-backed replacement Blob prevents the dropped File from becoming an empty request; include picker and MIME-override controls, byte preservation, filename, large-file memory cost, and read-error handling. If confirmed, normalize inputs once at the SDK upload boundary rather than adding composer-only handling. Separately, convert malformed multipart parser failures into an explicit client-input response at the upload route without masking unrelated failures.

No automated fix branch or PR was created. Only the server symptom and SDK branch were reproduced here; the native iOS failure required by the report was not. A server-only error-message repair would not fix attachment delivery, and a synthetic Node test must not be presented as proof of a WebKit fix.
