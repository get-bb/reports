#6175 · Interactive registration under Connect transport failures

BugPriority: MediumEffort: Mediumproviders · remote · provider-claude-code · connectGitHub issue2026-10-23 · base 1e80ca7b44bccd06c6da75ed9ca6ba497bd380f5

PARTIALLY REPRODUCED · Root-cause confidence: low · Label: partial-repro

1. TL;DR

The reported failure is an HTTP error while BB registers an approval, not evidence that a shell command ran or that Claude denied it. A transport-fault test on trusted main reproduces the exact error after six injected Connect 502 responses. The same test shows that one transient 502 recovers automatically, including when the server saved the request before its response was lost; only one pending interaction exists. Repeated failures can leave either zero or one persisted interaction, so the error alone cannot settle the request's history. The original Connect exception, the reported live session, and the successful plan-approval control remain unverified; no production tunnel or provider account was accessed.

Complete diagnostic test
import { listPendingInteractionsByThread } from "@bb/db";
import type { PendingInteractionCreate } from "@bb/domain";
import { describe, expect, it } from "vitest";
import {
  createServerClient,
  ServerResponseError,
} from "../../../host-daemon/src/server-client.js";
import { createCommandApprovalPayload } from "../helpers/pending-interactions.js";
import { seedThreadFixture, seedTurnStarted } from "../helpers/seed.js";
import {
  createTestDaemonHostKey,
  withTestHarness,
} from "../helpers/test-app.js";

function gateFailure(): Response {
  return Response.json(
    {
      code: "connect_gate_error",
      message: "bb connect hit a temporary problem. Try again in a moment.",
    },
    { status: 502, statusText: "Bad Gateway" },
  );
}

describe("interactive registration under injected gate failures", () => {
  it.each(["before persistence", "after persistence"])(
    "recovers a single 502 %s without duplicating or approving the request",
    async (failurePoint) => {
      await withTestHarness(async (harness) => {
        const { host, session, thread } = seedThreadFixture(harness, {
          thread: { providerId: "claude-code" },
        });
        const interaction: PendingInteractionCreate = {
          threadId: thread.id,
          turnId: "turn-connect-recovery",
          providerId: "claude-code",
          providerThreadId: "provider-connect-recovery",
          providerRequestId: "request-connect-recovery",
          payload: createCommandApprovalPayload({
            itemId: "item-connect-recovery",
            command: "git push",
            cwd: "/tmp/project",
            reason: "Needs approval",
          }),
        };
        seedTurnStarted(harness.deps, interaction);
        let attempts = 0;
        const logger = {
          debug: () => {},
          info: () => {},
          warn: () => {},
          error: () => {},
        };
        const client = createServerClient({
          serverUrl: "https://bb.example.test",
          hostKey: createTestDaemonHostKey({ hostId: host.id }),
          getSessionId: () => session.id,
          logger,
          fetchFn: async (input, init) => {
            attempts += 1;
            if (attempts === 1 && failurePoint === "before persistence") {
              return gateFailure();
            }
            const response = await harness.app.request(
              new Request(input, init),
            );
            expect(response.status).toBe(200);
            if (attempts === 1) {
              await response.text();
              return gateFailure();
            }
            return response;
          },
        });

        const response = await client.registerInteractiveRequest(interaction);
        expect(attempts).toBe(2);
        expect(response).toMatchObject({
          outcome:
            failurePoint === "before persistence" ? "created" : "existing",
          status: "pending",
        });
        const persisted = listPendingInteractionsByThread(harness.db, {
          threadId: thread.id,
        });
        expect(persisted).toHaveLength(1);
        expect(persisted[0]).toMatchObject({
          id: response.interactionId,
          status: "pending",
        });
      });
    },
  );

  it.each(["before persistence", "after persistence"])(
    "exhausts six 502 responses %s with persistence determined only by server state",
    async (failurePoint) => {
      await withTestHarness(async (harness) => {
        const { host, session, thread } = seedThreadFixture(harness, {
          thread: { providerId: "claude-code" },
        });
        const interaction: PendingInteractionCreate = {
          threadId: thread.id,
          turnId: "turn-connect-outage",
          providerId: "claude-code",
          providerThreadId: "provider-connect-outage",
          providerRequestId: "request-connect-outage",
          payload: createCommandApprovalPayload({
            itemId: "item-connect-outage",
            command: "git push",
            cwd: "/tmp/project",
            reason: "Needs approval",
          }),
        };
        seedTurnStarted(harness.deps, interaction);
        let attempts = 0;
        const logger = {
          debug: () => {},
          info: () => {},
          warn: () => {},
          error: () => {},
        };
        const client = createServerClient({
          serverUrl: "https://bb.example.test",
          hostKey: createTestDaemonHostKey({ hostId: host.id }),
          getSessionId: () => session.id,
          logger,
          fetchFn: async (input, init) => {
            attempts += 1;
            if (failurePoint === "after persistence") {
              const response = await harness.app.request(
                new Request(input, init),
              );
              expect(response.status).toBe(200);
              await response.text();
            }
            return gateFailure();
          },
        });

        await expect(
          client.registerInteractiveRequest(interaction),
        ).rejects.toMatchObject({
          name: ServerResponseError.name,
          message:
            "Failed to register interactive request: 502 Bad Gateway - bb connect hit a temporary problem. Try again in a moment.",
          status: 502,
          code: "connect_gate_error",
          retryable: true,
        });
        expect(attempts).toBe(6);
        const persisted = listPendingInteractionsByThread(harness.db, {
          threadId: thread.id,
        });
        expect(persisted).toHaveLength(
          failurePoint === "before persistence" ? 0 : 1,
        );
        if (failurePoint === "after persistence") {
          expect(persisted[0]).toMatchObject({ status: "pending" });
        }
      });
    },
  );
});

5. Root cause: known mechanism, unknown incident trigger

What produces the text

gateErrorResponse emits the common 502 JSON response. The worker fetch handler catches an exception around routing/tunnel forwarding and logs bb connect: request failed with method, path, and exception. Many exceptions can reach this path; the response text does not identify which one occurred or whether the origin handled the request. The test injects that response shape, not a real Cloudflare failure.

What the current daemon does

5xx classification treats this response as retryable. Registration retains the same request identity and retries, using five retries after the initial attempt. The retry hook logs the attempt number and retries left. Thus a single injected failure is not sufficient to produce the final error on this base.

return status < 400 || status >= 500;
const INTERACTIVE_REQUEST_REGISTRATION_RETRIES = 5;

Why retrying the same registration is not retrying the shell command

The registration transaction looks up the provider ID, provider thread ID, and provider request ID. A matching live request and payload returns the existing row; a conflicting payload or already-handled identity is rejected. This guards registration retries, not arbitrary user resubmission: a new provider turn or tool request can have a new identity and is not automatically deduplicated with the old one.

return {
  outcome: "existing" as const,
  row: existing,
};

Why no active interaction does not settle the history

Registry failure handling rejects the provider wait and calls the failure hook. The daemon hook enqueues an interrupt for the provider's interactions in the thread. Server interrupt handling settles those rows, while the active list includes only pending/resolving rows. A previously persisted row can therefore disappear from the active list after cleanup. This cleanup explanation is a static trace, not a measured assertion about the reporter's session or a full-daemon cleanup reproduction.

Incident root cause remains unconfirmed. Nothing in these tests establishes a command-specific transport defect, a missing Claude callback, a permission bypass, or a newly introduced regression. The original exception and its timing relative to server persistence are the missing evidence.

6. Safe reconciliation and next experiment

Do not approve a stale card or resubmit a potentially side-effecting tool merely to discover whether the old registration existed. First correlate the original request using read-only evidence. Registration alone does not authorize or execute a command, but this report cannot determine the original tool's execution state.

  • Inspect the affected thread's active interactions and event history through the authenticated UI/SDK or bb thread interactions list THREAD_ID --json and bb thread log THREAD_ID --json --all. These commands are suggested for the owner; they were not run against a real account here. Redact history before sharing because it can contain prompts and tool arguments.
  • If the original interaction ID is known, use bb thread interactions show INTERACTION_ID THREAD_ID --json to read its stored status, including a terminal status. An empty active list is not a history lookup.
  • Collect a narrow UTC time range and the BB server/daemon build identifiers; the host, thread, turn, provider-thread, and provider-request IDs; and any interaction ID. Use stable redacted aliases when sharing publicly. Do not share credentials, cookies, host keys, full environment dumps, or complete command payloads.
  • Correlate the daemon's registration retry attempts and final error with server registration/interrupt events and a targeted read-only lookup by provider request identity. Prefer read-only API/CLI evidence; any operator database inspection must remain read-only and local.
  • Ask the service operator to retrieve the matching bb connect: request failed entry from stored Workers Logs or Analytics, preserving the exception and request correlation metadata. Do not attach production wrangler tail or dashboard real-time logs; attaching or detaching can reset live tunnels.
  • Only after the old request and provider wait are reconciled should the owner choose a fresh harmless test. Do not assume a fresh provider request shares the original registration's idempotency identity.

No production fix is proposed yet. The next experiment is to locate the stored gate exception for the original UTC interval and compare it with the daemon's six-attempt sequence and the server's request/interrupt history. Main already retries and deduplicates registration. Changing retries, lifecycle cleanup, or approval behavior without that evidence risks masking the trigger or changing a permission-sensitive path.
