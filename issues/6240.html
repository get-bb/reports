#6240 · Asset trees abort skill staging

BugHighEffort: Mediumhost · threads · confirmed-reproGitHub issue

2026-10-24 · trusted origin/main 9eb0c09254a21482c0cfd935e0a9908049333e93

Verdict: REPRODUCED · Root-cause confidence: high

1. TL;DR

The daemon rejects a valid skill tree solely because its supporting asset exceeds a fixed 10 MiB budget. A fresh, correctly hashed two-file tree with a 12 MiB supporting file aborts catalog staging even when a healthy skill is included in the same request. The same test with a 2 MiB asset succeeds and both staged skills are readable. The error is rethrown before runtime preparation can complete; the failure does not depend on sending asset text to a model. This was reproduced at the real exported host-staging boundary in two separate clean source checkouts, not in a desktop UI or a real provider turn.

  1. Save this independently authored test as apps/host-daemon/src/issue-6240.repro.test.ts. It targets an existing exported production boundary and adds no production seam:
import { createHash } from "node:crypto";
import { mkdtemp, readFile, rm } from "node:fs/promises";
import os from "node:os";
import path from "node:path";
import type {
  HostDaemonInjectedSkillSource,
  HostDaemonSkillTree,
} from "@bb/host-daemon-contract";
import { describe, expect, it } from "vitest";
import { stageInjectedSkillSources } from "./injected-skills.js";

function payload(name: string, assetBytes: number): HostDaemonSkillTree {
  const entries = [
    {
      path: "SKILL.md",
      mode: 0o644,
      contentBase64: Buffer.from(
        `---\nname: ${name}\ndescription: Isolated staging probe\n---\n\nSupporting files remain on disk.\n`,
      ).toString("base64"),
    },
    {
      path: "assets/support.dat",
      mode: 0o644,
      contentBase64: Buffer.alloc(assetBytes, 7).toString("base64"),
    },
  ];
  const hash = createHash("sha256");
  hash.update("bb-skill-tree-v1");
  for (const entry of entries) {
    const bytes = Buffer.from(entry.contentBase64, "base64");
    hash.update("\0file\0");
    hash.update(entry.path);
    hash.update("\0");
    hash.update(entry.mode.toString(8));
    hash.update("\0");
    hash.update(String(bytes.length));
    hash.update("\0");
    hash.update(bytes);
  }
  return { treeHash: hash.digest("hex"), entries };
}

function source(name: string, treeHash: string): HostDaemonInjectedSkillSource {
  return {
    kind: "tree",
    sourceType: "data-dir",
    name,
    description: "Isolated staging probe",
    treeHash,
    entryPath: "SKILL.md",
  };
}

describe("issue 6240 asset staging", () => {
  it.each([2, 12])(
    "stages a %i MiB supporting asset alongside a healthy skill",
    async (assetMiB) => {
      const dataDir = await mkdtemp(path.join(os.tmpdir(), "bb-6240-probe-"));
      const healthy = payload("a-healthy", 16);
      const assetTree = payload("z-asset", assetMiB * 1024 * 1024);
      const trees = new Map([
        [healthy.treeHash, healthy],
        [assetTree.treeHash, assetTree],
      ]);
      try {
        const staged = await stageInjectedSkillSources({
          workspacePath: null,
          dataDir,
          injectedSkillSources: [
            source("a-healthy", healthy.treeHash),
            source("z-asset", assetTree.treeHash),
          ],
          fetchSkillTree: async (treeHash) => {
            const tree = trees.get(treeHash);
            if (!tree) throw new Error("Unexpected tree request");
            return tree;
          },
          logger: {
            debug() {},
            warn(context, message) {
              console.log(message, JSON.stringify(context));
            },
          },
        });
        expect(staged.skillRoots).toHaveLength(1);
        for (const root of staged.skillRoots) {
          expect(
            await readFile(path.join(root.path, "a-healthy", "SKILL.md"), "utf8"),
          ).toContain("a-healthy");
          expect(
            await readFile(path.join(root.path, "z-asset", "assets", "support.dat")),
          ).toHaveLength(assetMiB * 1024 * 1024);
        }
      } finally {
        await rm(dataDir, { recursive: true, force: true });
      }
    },
  );
});

5. Root cause

  1. The server collector recursively reads ordinary supporting files, not only the entry document. readSkillsRoot registers their hash and returns kind: "tree"; user skills use sourceType: "data-dir".
  2. The daemon defines a private fixed budget and validatedTreeEntries sums decoded bytes before persisting a received tree:
const MAX_STAGED_SKILL_BYTES = 10 * 1024 * 1024;

const bytes = decodeTreeEntryContent(entry.contentBase64, entry.path);
totalBytes += bytes.length;
if (totalBytes > MAX_STAGED_SKILL_BYTES) {
  throw new Error(
    `Skill tree exceeds max byte count ${MAX_STAGED_SKILL_BYTES}`,
  );
}
  1. writeFetchedTreeToStore invokes that validator. stageInjectedSkillSources logs then rethrows the error for a required fetched tree, so no usable partial catalog is returned. By contrast, the workspace-path branch warns and skips failures.
  2. resolveRuntimeSkillConfig returns this staging operation, and ensureEnvironmentOnce awaits it before even looking up an existing runtime entry. Therefore the same global tree can prevent preparation for unrelated threads and for an existing runtime. This last turn-level consequence is source-traced, not independently exercised with a live provider.

The defect is the combination of a fixed resource budget that counts on-disk supporting assets and mandatory whole-catalog failure propagation. It is not a model text-window limit. The current warning already includes the skill name; the thrown error lacks that context, actual size, and any supported override.

6. Proposed fix and automation safety

Decide an owner-controlled resource policy first: bounded/configurable transfer, storage, and staging behavior, or an asset-aware delivery design. Carry any selected budget through the supported server, SDK, CLI, and daemon surfaces, validate it at boundaries, and report the skill identity, measured bytes, configured budget, and recovery action. Preserve path, symlink, hash, depth, and file-count protections. Test both received and local trees, complete-store reuse, aggregate failures, and any size-limit override.

Do not merely increase the private constant, remove the only decoded-tree byte guard without a replacement policy, or swallow every required-tree error. An existing required-pull regression test explicitly requires transport failures to propagate. Distinguishing optional oversized assets from missing required instructions is a product decision, not a safe blanket catch.

No fix PR: removing or configuring this resource safeguard, or changing whether required instruction trees may be omitted, requires a resource/failure-policy decision. Those changes fail the autopilot simple-fix gate. No production code was changed, no fix branch was pushed, and no failing regression test is proposed for merge by itself.
