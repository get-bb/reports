#5862 · Embedded browser native drag regions

Bug Priority: Medium Effort: Low desktop · 2026-10-20 · GitHub issue

Verdict: NOT REPRODUCED · Root-cause confidence: low · Reproduction label: no-repro

Verification was blocked by the host environment, not by a successful native interaction test. This verdict does not refute the report. Neither run reached an Electron window, and no claim is made that this is already fixed.

1. TL;DR

The report describes third-party page styles turning an embedded browser pane into a handle for the surrounding desktop window. Trusted main does create a native WebContentsView inside the host window and contains no app-region handling in the browser manager or its page preload. This makes the proposed mechanism plausible, but source inspection cannot establish native mouse hit-testing. Both clean-checkout attempts stopped before Electron startup because a required shared library is absent. No fix or pull request is proposed as verified, and the macOS interaction remains untested.

5. Root cause

No runtime root cause has been confirmed. The leading hypothesis is native drag-region propagation from untrusted embedded page content to a frameless host window. The following source facts support investigating that hypothesis:

  • Window options make macOS application windows frameless with a hidden-inset title bar.
  • createEntry creates and attaches the native child view: 
    const view = new WebContentsView({
  webPreferences: {
    ...hardenedWebPreferences(),
    backgroundThrottling: args.backgroundThrottling,
    ...(pagePreloadPath === null ? {} : { preload: pagePreloadPath }),
  },
});
...
wireWebContents(args.hostWindow, args.tabId, entry);
args.hostWindow.contentView.addChildView(view);
  • WebPreferences hardening enables sandboxing, isolation, and web security, and disables Node integration. These settings do not themselves demonstrate any drag-region filtering.
  • Page preload exposes an isolated-world messaging bridge and contains no style normalization.

The actual verified failure in the investigation is the loader error for libglib-2.0.so.0. It is not a product-root-cause finding. The investigation did not trace Electron or Chromium native hit testing and did not test other products or websites.
