#5742 · Windows file-manager path serialization

BugPriority: LowEffort: LowhostIssue2026-10-19 · base 9937c46f5c7e369de3563eb864c8cbc4c3b9c231

Verdict: REPRODUCED at the command-construction boundary. Root-cause confidence: high. Native Windows Explorer behavior was not executed on this Linux host.

1. TL;DR

The Windows file-manager launcher receives slash-delimited paths used by the app and passes them verbatim into the environment consumed by Explorer's file-selection command. A focused test of the real production launcher fails for drive-letter, UNC, and mixed-separator file paths on current main; an already-native path passes. The same failures were repeated by this agent in a second clean checkout. This establishes the missing native-path conversion without running any reporter-supplied script. The specific Explorer fallback folder and installed-release behavior remain unverified here.

4. Minimal reproduction

  1. In a clean get-bb/bb checkout, check out the recorded trusted main commit.
  2. Run pnpm install --frozen-lockfile --prefer-offline.
  3. Save the authored regression test below as packages/local-open-targets/test/windows-file-manager-paths.test.ts.
  4. Run pnpm exec turbo run test --filter=@bb/local-open-targets -- windows-file-manager-paths.

Expected: the Explorer environment contains native Windows separators for every file. Actual representative assertion output, verbatim:

Expected: "C:\projects\review notes\draft.md"
Received: "C:/projects/review notes/draft.md"
Tests  3 failed | 1 passed (4)

Already-native separators, apostrophes, and shell metacharacters form the passing control. The test also protects the existing invariant that the file path stays out of the PowerShell command string.

import { expect, it } from "vitest";
import { buildWindowsFileManagerOpenInvocation } from "../src/windows-open-targets.js";

it.each([
  {
    input: "C:/projects/review notes/draft.md",
    expected: "C:\\projects\\review notes\\draft.md",
  },
  {
    input: "//fileserver/shared/review notes/draft.md",
    expected: "\\\\fileserver\\shared\\review notes\\draft.md",
  },
  {
    input: "C:\\projects/review notes\\draft.md",
    expected: "C:\\projects\\review notes\\draft.md",
  },
  {
    input: "C:\\projects\\it's & notes.md",
    expected: "C:\\projects\\it's & notes.md",
  },
])("passes a native Windows path to Explorer for $input", ({ input, expected }) => {
  const invocation = buildWindowsFileManagerOpenInvocation({
    env: undefined,
    existingPath: { path: input, type: "file" },
  });

  expect(invocation.env?.WORKSPACE_OPEN_TARGET_PATH).toBe(expected);
  expect(invocation.args.join(" ")).not.toContain(input);
});

Complete output: first run; second run; baseline build summary. No visual evidence is manufactured: this is a command-generation regression, not a Windows UI verification.

5. Root cause

  1. apps/app/src/components/ui/markdown-local-file-link-normalize.ts:412 converts Windows link destinations to forward slashes.
  2. apps/app/src/views/thread-detail/ThreadDetailView.tsx:2102 passes the parsed link path to the chosen open target.
  3. apps/host-daemon/src/local-api.ts:141 preserves the local request path.
  4. packages/local-open-targets/src/index.ts:1057 validates file existence but returns the original string.
  5. packages/local-open-targets/src/index.ts:1980 selects the Windows file-manager invocation builder.
  6. packages/local-open-targets/src/windows-open-targets.ts:46 stores the unchanged path in WORKSPACE_OPEN_TARGET_PATH, consumed by the Explorer selection command.

The defect is missing OS-native serialization at the final Windows tool boundary. Validation of a filesystem path and serialization for a platform-specific shell tool are different contracts. The app's portable link format need not change. The test demonstrates the incorrect bytes delivered to the launcher; it does not establish which folder a particular Windows version chooses after receiving them.

6. Proposed fix

Normalize only the Windows file-manager invocation's path with the existing Node Windows-path utility. Keep the environment-based argument handling, existing PowerShell script, other targets, API fields, and daemon wire contract unchanged. Exercise drive-letter, UNC, mixed-separator, native-separator, and special-character cases; update the existing runtime integration assertions to expect native separators.
