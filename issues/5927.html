#5927 · Automation CLI rejects unresolved execution options

BugPriority: MediumEffort: Mediumcli · plugins · automationsIssue #59272026-10-20 · base bd93d18896bab97c950c4fa3451b621c1e0569c1

Verdict: REPRODUCED · Root-cause confidence: high · Reproduction label: confirmed-repro.

1. TL;DR

The automation creation handler refuses an agent prompt unless both execution flags are explicit. A real calling thread and remembered project defaults do not help: the handler rejects the request before looking up either source. A regression test through the real loopback HTTP server, bundled plugin entry, registered CLI, SDK, and SQLite persistence reproduces the rejection. A control with both flags creates a paused automation successfully, ruling out a broken plugin install or unavailable provider registry. The same agent repeated the test in a second clean checkout at the same trusted commit.

Complete regression test

import {
  createThread,
  setThreadExecutionOverride,
  upsertProjectExecutionDefaults,
} from "@bb/db";
import { PERSONAL_PROJECT_ID } from "@bb/domain";
import { expect, it } from "vitest";
import { z } from "zod";
import { startTestServer } from "../../helpers/test-app.js";

const cliResultSchema = z.object({
  exitCode: z.number(),
  stdout: z.string().optional(),
  stderr: z.string().optional(),
});

it("creates paused agent automations with execution flags omitted", async () => {
  const server = await startTestServer();
  try {
    server.pluginService.bindSdk({ baseUrl: server.baseUrl });
    const entry = await server.pluginService.install("builtin:automations", {
      kind: "root",
    });
    expect(entry.status, entry.statusDetail ?? undefined).toBe("running");
    const thread = createThread(server.db, server.deps.hub, {
      projectId: PERSONAL_PROJECT_ID,
      providerId: "codex",
      status: "idle",
    });
    setThreadExecutionOverride(server.db, {
      threadId: thread.id,
      modelOverride: "gpt-5",
    });
    upsertProjectExecutionDefaults(server.db, {
      projectId: PERSONAL_PROJECT_ID,
      providerId: "codex",
      model: "gpt-5",
      reasoningLevel: "medium",
      permissionMode: "auto",
      serviceTier: "default",
    });

    async function create(options: {
      name: string;
      flags: string[];
      threadId?: string;
    }) {
      const response = await fetch(
        `${server.baseUrl}/api/v1/plugins/automations/cli`,
        {
          method: "POST",
          headers: { "content-type": "application/json" },
          body: JSON.stringify({
            argv: [
              "create",
              "--project",
              PERSONAL_PROJECT_ID,
              "--name",
              options.name,
              "--in",
              "2h",
              "--prompt",
              "Inspect repository status",
              "--disabled",
              "--json",
              ...options.flags,
            ],
            ...(options.threadId ? { threadId: options.threadId } : {}),
          }),
        },
      );
      const body: unknown = await response.json();
      expect(response.status, JSON.stringify(body)).toBe(200);
      return cliResultSchema.parse(body);
    }

    const control = await create({
      name: "Explicit execution control",
      flags: ["--provider", "codex", "--model", "gpt-5"],
      threadId: thread.id,
    });
    expect(control.exitCode, JSON.stringify(control)).toBe(0);
    const storedControl: unknown = JSON.parse(control.stdout ?? "null");
    expect(storedControl).toMatchObject({
      enabled: false,
      execution: { providerId: "codex", model: "gpt-5" },
    });
    console.log("Explicit control: exitCode=0; disabled automation persisted");

    for (const scenario of [
      {
        name: "Thread without execution flags",
        flags: [],
        threadId: thread.id,
      },
      {
        name: "Thread without model flag",
        flags: ["--provider", "codex"],
        threadId: thread.id,
      },
      {
        name: "Thread without provider flag",
        flags: ["--model", "gpt-5"],
        threadId: thread.id,
      },
      { name: "Terminal without execution flags", flags: [] },
    ]) {
      const result = await create(scenario);
      console.log(JSON.stringify({ scenario: scenario.name, ...result }));
      expect
        .soft(result.exitCode, `${scenario.name}: ${JSON.stringify(result)}`)
        .toBe(0);
      if (result.exitCode === 0) {
        const stored: unknown = JSON.parse(result.stdout ?? "null");
        expect.soft(stored).toMatchObject({
          enabled: false,
          execution: { providerId: "codex", model: "gpt-5" },
        });
      }
    }
  } finally {
    await server.pluginService.stop();
    await server.close();
  }
}, 60_000);

5. Root cause

In plugins/automations/src/cli.ts:639, buildExecution reads only the option values and unconditionally rejects either missing field before constructing an environment or calling provider validation:

if (hasAgent) {
  const provider = options.provider;
  const model = options.model;
  if (!provider || !model) {
    throw cliError(
      "Agent automations require --provider and --model alongside --prompt.",
      "missing_required",
    );
  }
  ...
}

The CLI proxy forwards calling-thread context, and the server CLI route preserves that context. The creation handler passes it into buildExecution, but no execution-default lookup occurs on the agent path before the guard. Thus this is missing default resolution in the plugin handler, not missing transport context.

The server already exposes remembered project execution defaults and resolved execution options for an existing thread. Their existence explains how a plugin could obtain typed defaults, but this report does not assert that calling them alone fully implements every provider-routing edge case.

6. Proposed fix

Resolve omitted creation-time provider/model values through the existing SDK defaults before enforcing a complete execution configuration. Explicit flags must win; an inherited model must belong to the selected provider. Keep persisted execution fully resolved and retain provider availability, environment routing, permission validation, and partial-update semantics. Update CLI help and the owning skill together. Verify thread overrides, remembered project defaults, user/provider defaults, cross-provider overrides, unavailable model catalogs, and requests outside a thread.

No production fix was attempted: GitHub metadata confirms that an open pull request already closes this issue. Opening another would duplicate that work.
