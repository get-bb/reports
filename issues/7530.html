#7530 · Oversized ACP catalogs prevent MCP subprocess launch

Bug Priority: Medium Effort: Medium providers provider-acp confirmed-repro

GitHub issue · November 13, 2026 · Trusted main: 05199007ecad513b714b244e46b0ab2a9a06279f

REPRODUCED · Root-cause confidence: high

1. TL;DR

The ACP configuration builder serializes the entire selected tool catalog into one process-environment entry. On the tested Linux host, a single entry of 131,073 bytes cannot be passed to a new process, even though a larger aggregate environment split over multiple entries works. An independently authored test launches BB's actual MCP child: a two-tool catalog starts and returns the exact tools; a 192-tool catalog produces a 263,721-byte entry and fails at process creation with E2BIG. The same test produces the same result in a second clean worktree at the trusted main commit. This confirms the catalog-size defect, not the precise circumstances of any earlier user session.

import { spawnSync } from "node:child_process";
import { fileURLToPath } from "node:url";
import { describe, expect, it } from "vitest";
import { buildAcpMcpServerConfig } from "./tool-proxy-mcp.js";

describe.skipIf(process.platform !== "linux")("ACP catalog launch boundary", () => {
  it.each([2, 192])("starts the real MCP child with %i tools", (toolCount) => {
    const tools = Array.from({ length: toolCount }, (_, index) => ({
      name: `catalog_probe_${index}`,
      description: "catalog description ".repeat(64),
      inputSchema: { type: "object", properties: {} },
    }));
    const config = buildAcpMcpServerConfig({
      command: process.execPath,
      bridgeArgs: [
        "--conditions=source",
        "--import",
        import.meta.resolve("tsx"),
        fileURLToPath(new URL("./bridge.ts", import.meta.url)),
        "--mcp-stdio",
      ],
      dynamicTools: tools,
      runtimeEnv: [],
      host: "127.0.0.1",
      port: 1,
      token: "catalog-probe-fixture",
      threadId: "catalog-probe",
    });
    const result = spawnSync(config.command, config.args, {
      env: Object.fromEntries(config.env.map(({ name, value }) => [name, value])),
      input: `${JSON.stringify({ jsonrpc: "2.0", id: 1, method: "tools/list" })}\n`,
      encoding: "utf8",
      timeout: 15_000,
      maxBuffer: 4 * 1024 * 1024,
    });
    const largestEntryBytes = Math.max(
      ...config.env.map(({ name, value }) =>
        Buffer.byteLength(`${name}=${value}\0`),
      ),
    );
    console.log(JSON.stringify({
      toolCount,
      largestEntryBytes,
      exitCode: result.status,
      launchError: result.error?.code ?? null,
    }));
    expect(result.error, "MCP child must launch").toBeUndefined();
    expect(result.status, result.stderr).toBe(0);
    const response: unknown = JSON.parse(result.stdout.trim());
    expect(response).toMatchObject({
      id: 1,
      result: { tools },
    });
  });
});

5. Root cause

The session MCP configuration path forwards every selected dynamic tool to the builder. The builder places the serialized catalog into a single launch-environment string:

{ name: ENV_TOOLS, value: JSON.stringify(args.dynamicTools) }

The child startup reader requires that entry, parses its JSON, and validates the catalog. Its validation cannot help here: the operating system rejects the launch before any child JavaScript runs. The byte count includes the environment variable name, equals sign, UTF-8 value, and terminating null. In the failing fixture it is 263,721 bytes, beyond the directly measured single-entry limit of 131,072 bytes.

The underlying problem is using process startup metadata as a bulk-data transport without a size-independent catalog handoff. Increasing stdout buffers, retrying the provider, changing connection timeouts, or changing JSON validation cannot make that launch succeed. Splitting across environment variables would address the measured per-string limit only; the aggregate environment and argument limits would remain.

6. Proposed fix and safety gate

Move the catalog out of startup arguments and environment strings. One possible design is to retrieve it through the existing authenticated local bridge after the MCP child starts. However, the current request schema supports only initialization notices and tool calls, and the current handler has no catalog-read operation. Adding it requires a request-schema change and a thread-scoped ownership/lifetime contract. A private temporary-file alternative needs file-permission, deletion, session-reuse, and reconnect behavior defined and tested.

No pull request was opened: a robust transport repair exceeds this automation's no-schema/security-boundary/architecture-decision safety gate. No partial production fix was pushed. 9. Appendix: operating-system control

A separate authored control launches an empty Node process with precisely sized artificial environment entries, excluding inherited variables. It distinguishes the per-entry limit from an aggregate-size explanation:

{"entrySizes":[131072],"exitCode":0,"error":null}
{"entrySizes":[131073],"exitCode":null,"error":"E2BIG"}
{"entrySizes":[96000,96000],"exitCode":0,"error":null}
{"entrySizes":[192000],"exitCode":null,"error":"E2BIG"}
import assert from "node:assert/strict";
import { spawnSync } from "node:child_process";

const cases = [
  { entrySizes: [131072], expectedError: null },
  { entrySizes: [131073], expectedError: "E2BIG" },
  { entrySizes: [96000, 96000], expectedError: null },
  { entrySizes: [192000], expectedError: "E2BIG" },
];
for (const { entrySizes, expectedError } of cases) {
  const env = Object.fromEntries(entrySizes.map((bytes, index) => {
    const name = `CATALOG_PROBE_${index}`;
    return [name, "a".repeat(bytes - Buffer.byteLength(name) - 2)];
  }));
  const result = spawnSync(process.execPath, ["-e", ""], { env });
  const error = result.error?.code ?? null;
  console.log(JSON.stringify({ entrySizes, exitCode: result.status, error }));
  assert.equal(error, expectedError);
  if (expectedError === null) assert.equal(result.status, 0);
}

Save this standalone control as launch-limit-probe.mjs and run node launch-limit-probe.mjs on the described Linux host. It exits zero only if all four controls match the recorded outcomes.
