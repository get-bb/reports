#5192 · Incremental maintenance monopolizes the event loop

BugPriority: HighEffort: Lowperf · host GitHub issueOctober 8, 2026 · base 8d9195d8e0f123ea32b21eb9eb1104b35d97b916

Verdict: REPRODUCED · Root-cause confidence: high · Reproduction label: confirmed-repro

1. TL;DR

The hourly server maintenance job performs one synchronous SQLite vacuum covering up to 20,000 pages. While that native call runs, queued event-loop callbacks cannot execute, so unrelated request handling can wait behind maintenance. A purpose-built test against unchanged trusted main reclaimed exactly 20,000 pages and delayed queued work for 243 ms on a fresh 259 MiB in-memory database. The same agent repeated the test from a second clean checkout with a newly created database: queued work waited 240 ms and ran only after maintenance completed. This verifies the starvation mechanism, not the reporter's specific production durations or terminal-disconnection correlation.

Complete reproduction test

import {
  createConnection,
  DATABASE_INCREMENTAL_VACUUM_MAX_PAGES,
  getDatabaseFreelistStats,
  migrate,
  type SlowDbQueryLogFields,
} from "@bb/db";
import { performance } from "node:perf_hooks";
import { expect, it } from "vitest";
import { runDatabaseMaintenanceSweep } from "../../src/services/system/periodic-sweeps.js";
import type { ServerLogger } from "../../src/types.js";

it("serves queued event-loop work before a large maintenance sweep completes", async () => {
  const vacuumQueries: SlowDbQueryLogFields[] = [];
  const db = createConnection(":memory:", {
    slowQueryThresholdMs: 0,
    slowQueryLogger: {
      info(fields) {
        if (fields.sql.startsWith("PRAGMA incremental_vacuum")) {
          vacuumQueries.push(fields);
        }
      },
    },
  });
  const warnings: string[] = [];
  const logger: ServerLogger = {
    debug() {},
    error() {},
    info() {},
    warn() {
      warnings.push("maintenance warning");
    },
  };
  try {
    migrate(db);
    db.$client.exec(
      "CREATE TABLE responsiveness_payloads (id INTEGER PRIMARY KEY, payload BLOB NOT NULL)",
    );
    const insert = db.$client.prepare(
      "INSERT INTO responsiveness_payloads (payload) VALUES (?)",
    );
    const payload = Buffer.alloc(64 * 1024, 65);
    db.$client.transaction(() => {
      for (let rowIndex = 0; rowIndex < 4_096; rowIndex += 1) {
        insert.run(payload);
      }
    })();
    db.$client.exec("DELETE FROM responsiveness_payloads WHERE id % 3 != 0");
    const before = getDatabaseFreelistStats(db);
    expect(before.freelistCount).toBeGreaterThan(
      DATABASE_INCREMENTAL_VACUUM_MAX_PAGES,
    );
    let maintenanceComplete = false;
    const startedAt = performance.now();
    const queuedWork = new Promise<{
      observedCompletion: boolean;
      freelistCount: number;
      delayMs: number;
    }>((resolve) => {
      setImmediate(() => {
        resolve({
          observedCompletion: maintenanceComplete,
          freelistCount: getDatabaseFreelistStats(db).freelistCount,
          delayMs: Math.round(performance.now() - startedAt),
        });
      });
    });
    await runDatabaseMaintenanceSweep({ db, logger });
    maintenanceComplete = true;
    const sweepDurationMs = Math.round(performance.now() - startedAt);
    const after = getDatabaseFreelistStats(db);
    const observation = await queuedWork;
    console.log(
      JSON.stringify({
        before,
        after,
        sweepDurationMs,
        observation,
        vacuumQueries: vacuumQueries.map(({ sql, durationMs }) => ({
          sql,
          durationMs,
        })),
        warnings,
      }),
    );
    expect(warnings).toEqual([]);
    expect(after.freelistCount).toBeLessThan(before.freelistCount);
    expect(observation.observedCompletion).toBe(false);
    expect(observation.freelistCount).toBeGreaterThan(after.freelistCount);
  } finally {
    db.$client.close();
  }
});

5. Root cause

The maintenance job uses a one-hour cadence (cadence constant) and registers the same sweep directly (job registration). Its incremental branch chooses a single native operation, with no scheduling boundary inside it:

periodic-sweeps.ts:207–229 at the recorded commit

    try {
      const result = runIncrementalVacuum(deps.db, {
        maxPages: DATABASE_INCREMENTAL_VACUUM_MAX_PAGES,
      });
      deps.logger.info({ result }, "Incremental database vacuum completed");
    } catch (error) {
      deps.logger.warn({ err: error }, "Incremental database vacuum failed");
    }
    return;

The configured page budget is 20,000. The database helper issues two checkpoints surrounding one synchronous better-sqlite3 exec:

maintenance.ts:411–431

export function runIncrementalVacuum(
  db: DbConnection,
  args: RunIncrementalVacuumArgs,
): IncrementalVacuumResult {
  return runWithMaintenanceBusyTimeout({
    db,
    work: () => {
      const before = getDatabaseFreelistStats(db);

      db.$client.exec("PRAGMA wal_checkpoint(PASSIVE)");
      db.$client.exec(`PRAGMA incremental_vacuum(${args.maxPages})`);
      db.$client.exec("PRAGMA wal_checkpoint(PASSIVE)");

      return {
        after: getDatabaseFreelistStats(db),
        before,
      };
    },
  });
}

The 242.2 ms and 238.8 ms vacuum calls account for nearly the entire measured sweep delay. Awaiting the enclosing sweep from a job runner cannot preempt an already running synchronous native call. The maintenance busy-timeout helper limits lock waiting; it is not a wall-time limit on vacuum execution. The defect occurs without a second database connection or contending process.

The incremental branch returns before the full-compaction idle gate. That confirms the code-path distinction, but adding an idle gate alone does not fix the non-yielding operation and could starve maintenance on busy servers.

6. Proposed fix

Keep the existing total page budget, but execute smaller bounded chunks and yield with a real event-loop scheduling boundary between them. Stop once the freelist is exhausted and retain existing bounded lock-wait/error handling. Keep the chunking policy in the existing server maintenance subsystem, leaving the synchronous database primitive as a small operation.

Use the ordering regression above to verify that queued work runs before the final chunk. Also retain the WAL-reader and WAL-writer tests. A fixed page count per chunk does not guarantee a universal 100 ms deadline on every disk and database; validate worst-case chunk and checkpoint times before promising one.
