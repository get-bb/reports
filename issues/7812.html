1. TL;DR

The report describes another app's music stopping when recording begins in the iOS composer. Trusted source and two executable traces confirm that the app opens its microphone through browser getUserMedia, followed by browser MediaRecorder, including when the page is inside the mobile shell. The inspected shell and bridge have no native voice-recording route or explicit audio-mixing policy. This makes recording-session ownership in WebKit a plausible explanation, but neither the interruption nor the proposed missing native mixing option was observed on iOS here. A physical-device capture and audio-session experiment is required before claiming a working fix.

5. Root cause

Confirmed architecture

The voice start callback invokes:

const stream = await requestAudioInputStream(
  navigator.mediaDevices,
  preferredAudioInputDeviceId,
)

The constraint builder produces either { audio: true } or a selected device ID. The capture helper passes those constraints to mediaDevices.getUserMedia; the trace exercises exactly this function. The hook subsequently constructs a browser MediaRecorder.

The mobile WebView grants capture and enables inline playback. Those props do not themselves establish an app-owned audio-mixing policy. The bridge request union has application-opening, sharing, and clipboard requests, but no recording request; the shell request handler likewise contains no voice recorder. The mobile dependency list has no dedicated expo-audio recorder.

Likely mechanism, not yet established

If external playback is interrupted at capture activation, the confirmed ownership boundary points toward the native audio session activated by WebKit, rather than the subsequent server transcription request. However, the exact session category/options and the causal interruption were not observed. It would be incorrect to claim that this investigation proved a missing mixWithOthers option or proved that a page-level change cannot help on all supported OS versions.

6. Proposed fix and automation safety

Not confident enough to implement a verified fix yet. First run the device experiment and measure the actual session configuration. If WebKit's capture session is responsible, design a capability-negotiated native recording path whose owner explicitly manages audio mixing, permission outcomes, file transfer, cancellation, failed startup, and session restoration. Preserve the browser path on shells that do not support the capability. Avoid assuming that a successful JavaScript mock test demonstrates preservation of another app's playback.

No automatic fix or new PR: the audible defect was not reproduced on trusted main, so there is no faithful failing-before/passing-after regression. A native recorder would also span the web hook, shell, and bridge contract; a new dependency or protocol change is outside the simple-fix allowance. No fix branch was created or pushed.

Classification rationale: Bug for unexpected recording behavior; Medium priority because recording itself is not reported broken and the impact is limited to external playback; High effort because a likely native-capture solution introduces a cross-shell interaction and requires device-level lifecycle verification.
