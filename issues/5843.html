#5843 · Resident turns discard updated dynamic-tool definitions

BugPriority: MediumEffort: Mediumproviders · host · provider-claude-code

GitHub issue · October 20, 2026 · trusted base e0f6fda5a02332bd4eb44183542a57f34f3263d7

PARTIALLY REPRODUCED · root-cause confidence: high for the verified resident-update defect

1. TL;DR

When an already-attached thread receives a later turn with new tool definitions, the daemon drops those definitions before calling the agent runtime. The same turn succeeds, but the runtime can only retain its initial tool snapshot. A focused test reproduces both an initially empty snapshot and a stale tool definition; releasing the session first makes both controls pass. The Claude bridge already detects changed construction settings, including tools, when explicitly resumed, and a second probe verifies that this rebuild restores its bridge configuration without changing the provider conversation identity. The exact macOS plugin-reload timing and real Claude CLI tool-search behavior were not reproduced; the verdict is therefore partial rather than a claim of full end-to-end reproduction.

5. Root cause

The server constructs turn submissions with current tools inside resumeContext (see server payload construction). At the daemon, an already-present thread bypasses the only path which forwards that tool set:

  const { resumeContext } = command;

    return;

This is not merely a missing SDK call in Claude's turn handler: runtime turn/steer arguments and canonical turn fields do not declare a tool-set update. The fresh definitions are never delivered on that path.

Claude snapshots dynamicTools in construction configuration and creates the MCP bridge only for a nonempty initial tool set:

6. Proposed fix and simple-fix decision

Refresh construction-scoped tool definitions at the resident runtime boundary before accepting a new turn. Compare normalized definitions (including name, description, schema and presentation), avoid restarting unchanged sessions, preserve provider conversation identity, and reuse the existing Claude resume/rebuild path when tools change. Keep the runtime's cached configuration synchronized so later process recovery also sees the new definitions. Steering and active-turn behavior need explicit lifecycle coverage across providers.

No production patch or pull request: the verified gap is in daemon-to-runtime resident-configuration delivery, not just the provider subsystem. A safe repair needs coordinated daemon/runtime lifecycle work, outside this rule's one-existing-subsystem simple-fix limit. The exact live plugin-reload trigger is additionally unverified. No fix branch was created or pushed; no public protocol or data was changed.
