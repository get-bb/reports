#7505 · Usage artwork receives a resource key instead of a provider key

Bug Priority: Low Effort: Low providers partial-repro

GitHub issue · 2026-11-13 · trusted origin/main 88cf8f644c81fca797ad80bc31bb36a61ce5cc9b

Verdict: PARTIALLY REPRODUCED · Root-cause confidence: high for the source identity mismatch.

1. TL;DR

A usage resource and its provider have different identities: several resources may belong to one provider. The account heading passes the resource identity to an artwork component whose contract requires the provider identity. A fresh test rendering the real usage card confirms this error, while the same card's provider tabs send the correct identities. The failure repeats in a second clean checkout of the same trusted main commit, and all 23 existing provider-usage tests pass. This is source-level SDK-boundary evidence, not a screenshot or verification of the reported desktop installation; the final artwork and third-party icon registration remain unverified.

5. Root cause

  1. The usage server intentionally creates a namespaced resource identity while retaining the underlying providerId. This permits several measured resources to belong to one provider: resourceProvider. 
    id: `${pluginId}:${resource.id}`
  2. The account heading passes the whole usage resource object directly to the icon API: account icon call site. 
    <ProviderIcon
  providerKind="agent"
  provider={account}
  fallback="Bot"
/>
  3. The artwork component treats that object's id as a provider identity and looks for a registration with an equal providerId: lookup and declared fallback. 
    const { id: providerId, logoUrl, icon } = provider;
entry.providerKind === providerKind &&
entry.providerId === providerId
  4. The tab grouping already adapts the identity to account.providerId instead: provider grouping. This explains why the two surfaces can disagree.

The deeper mistake is structural compatibility between a usage resource and a provider artwork descriptor: both have an id string, but those strings inhabit different identity domains. Neither the transport nor the stored usage identity needs to change. With an unmatched registration and no declared artwork, the inspected fallback path selects Bot; that visual consequence has not been exercised in a live application.

History check: the account call site dates to commit 9f745c64629. The latest fetched origin/main was still the recorded base after verification; this is not an already-fixed report.

6. Proposed fix

Adapt the icon input at the account heading so its id identifies the provider, just as the existing tab grouping does. Keep the original resource id unchanged for resource selection, React keys, and usage bookkeeping. This is a contained provider-usage presentation fix with no new API or stored-data contract. The focused regression should continue covering multiple resources for one provider and a second provider with absent declared artwork.

No duplicate fix was attempted: open PR #7506 already links to this issue. The autopilot fix path stops at that check; no source branch, source commit, source push, or new pull request was created.
