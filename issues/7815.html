BugPriority: MediumEffort: Lowui · perf · partial-reproGitHub issue

Verdict: PARTIALLY REPRODUCED. Root-cause confidence: high for the redundant-measurement mechanism. The Safari/WebKit event cadence, actual style mutation rate, blank frames, and cursor behavior were not verified.

1. TL;DR

The report describes terminal flicker when WebKit uses the DOM renderer. Trusted main registers a font-loading listener that invokes a terminal measurement on every completion event, without checking which font faces completed or whether they were already measured. A direct test of the real application helpers delivered ten duplicate events for the same face and observed ten unnecessary measurements and twenty additional font-family writes. The same agent repeated the test in a second clean checkout and got the same failure. This confirms the event-amplification mechanism, not the complete browser rendering symptom: no usable browser backend was available, so this report deliberately remains partial.

5. Root cause

The font-loading observer (lines 373–392) registers its unconditional refresh callback for every loadingdone event and also for fontSet.ready. It does not inspect event font faces or remember faces already handled:

fontSet.addEventListener("loadingdone", refresh);
void fontSet.ready.then(refresh);

The terminal's production caller (lines 875–884) turns every callback into forced measurement and a scheduled fit. Forced measurement (lines 360–371) deliberately changes the font family twice:

const fontFamily = terminal.options.fontFamily;
terminal.options.fontFamily = `${fontFamily} `;
terminal.options.fontFamily = fontFamily;
terminal.clearTextureAtlas();
terminal.refresh(0, terminal.rows - 1);

These are distinct option values, so xterm's OptionsService emits changes even though the final family is unchanged. In the installed dependency, src/browser/renderer/dom/DomRenderer.ts:91 subscribes to option changes; _handleOptionsChanged at line 493 calls _updateDimensions and _injectCss. Those methods replace style text (lines 171 and 312). This is source-level corroboration, not an observed browser mutation count.

The missing duplicate-face guard therefore amplifies repeated notifications into real renderer work. Whether that work causes WebKit to schedule the next notification, and whether paint suppression explains the blank frames, still requires a WebKit experiment.

6. Proposed fix

Make the existing observer coalesce completion notifications for already processed FontFace objects, recording a face before calling code that can trigger another font event. Preserve the initial ready measurement, measurements for genuinely new late-loading faces, and disposal behavior. Do not remove late-font support or rely on a timer that merely slows the loop. Add a regression for duplicate completion notifications alongside the existing lifecycle tests, then verify with WebKit and the real DOM renderer, including a late theme font.

No fix was attempted here: the overall issue is only partially reproduced and an open linked pull request already covers it.
