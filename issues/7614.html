1. TL;DR

Provider model discovery has a request-scoped environment channel, but installation status and health do not. The real Claude bridge ignores a supplied request executable for those maintenance calls and instead reads its process environment. A controlled unavailable-fallback probe returns “not installed” even though a usable version-probe executable was supplied in the request; pointing the process environment at the same executable works. The host command validator also rejects contributed environment on both maintenance commands. This report verifies the backend discrepancy twice, but not the original clean macOS machine, third-party plugin, thread launch, or visible composer behavior.

5. Root cause

  1. The server assembles maintenance commands without resolving contributed provider environment: installation requests and health requests.
  2. The host command schemas require contributedEnv for models, but both maintenance schemas are strict and have no such field. Adding it to current maintenance commands fails validation.
  3. The daemon maintenance argument path and installation dispatch likewise carry no contributed environment.
  4. The real bridge handlers pass envVars to model discovery but call maintenance functions without request environment.
  5. claudeExecutable() reads only process.env.BB_CLAUDE_CODE_EXECUTABLE before default resolution. Both installation status and health use it.
async function claudeExecutable(): Promise<string> {
  const explicit = process.env.BB_CLAUDE_CODE_EXECUTABLE?.trim();
  if (explicit) return explicit;
  return (await resolveExecutablePath("claude")) ?? "claude";
}

The UI’s host CLI status query uses session-static policy. However, realtime invalidation includes a dedicated provider-cli-status-changed event, and the server emits that event when cached status is replaced by a different value. It is inaccurate to describe this cache as refreshing only after install/update. Automatic environment-change invalidation still warrants a separate live regression.

6. Proposed fix and safety gate

Resolve provider contributions on the server with the target host context, carry explicit typed environment through maintenance commands and runtime requests, and have Claude maintenance resolve executable/configuration from that request rather than mutating shared process.env. Include environment fingerprints in affected caches, and invalidate host CLI status when relevant configuration changes. Preserve cross-host and concurrent-request isolation; test contributions changing while a bridge stays alive.

No autopilot pull request: an end-to-end repair must change the server/daemon wire contract and crosses server, daemon/runtime, bridge, and possibly UI cache owners. The rule forbids a simple fix that changes protocols or spans subsystems. No production patch or source branch was made. No linked open PR was found in the issue timeline or open-PR search for 7614 at review time.
