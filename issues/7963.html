#7963 · Scheduler progress in a desktop watcher test

BugPriority: MediumEffort: LowdesktopIssue2026-11-21

Trusted main commit: 4e45c9bc12fbed430f2e804fb827ac46089fc582

REPRODUCED · Root-cause confidence: high · Reproduction label: confirmed-repro

1. TL;DR

A desktop unit test can fail even though the watcher has correctly queued another lock check. The test drives its own manual scheduler only twice, then waits using real timers; waiting alone cannot execute callbacks in that manual scheduler. If the initial filesystem read is still pending when the fallback poll runs, the poll asks for a later recheck instead of reading the newly written marker immediately. A deterministic filesystem-completion gate reproduces the original zero-callback assertion in two clean checkouts without changing production code. Driving the scheduler during the wait makes all 51 tests in the file pass in the first checkout.

5. Root cause

The manual scheduler takes a snapshot of its current callbacks when flush() is called. It neither waits for asynchronous checks nor runs callbacks queued after that snapshot. The watch-error test performs its last flush before entering vi.waitFor.

Inside the watcher, a second check arriving while checking is true only sets recheckRequested. After the first check returns no marker, another debounced check is scheduled:

async function checkLock(): Promise<void> {
  if (checking) {
    recheckRequested = true;
    return;
  }
  ...
  if (recheckRequested && active) {
    recheckRequested = false;
    scheduleCheck();
  }
}
  1. The first flush starts a real read of a missing marker and leaves checking true.
  2. The watch error closes the watch handle and queues a fallback poll. The test writes a valid marker.
  3. The second flush fires the poll while the first read result is still pending. The poll requests a recheck and queues its next recurring poll.
  4. The initial missing-file result is released. checkLock queues the debounced recheck after that second flush.
  5. Two manual callbacks remain. Real-time waiting never drives them, so onMove stays at zero calls.

The underlying problem is test-driver progress, not evidence of a broken real-timer polling algorithm. The actual marker read and validation are delegated through readServerMovedLock and readServerMovedFile. No production change is needed to explain or remove this test failure.

6. Proposed fix and control experiment

Make progress on the test's manual scheduler while waiting for the exactly-once move callback, rather than assuming one snapshot flush drains asynchronous follow-up work. Keep the watch-close, warning, delivery, and cleanup assertions. A permanent test should use the existing scheduler harness; avoid adding sleep delays or new production injection hooks.

For a distinct local control, the following interval was added around the original callback wait after the same gated ordering. This drives only the existing test scheduler and is not a proposed production change:

const timerPump = setInterval(() => harness.timers.flush(), 5);
try {
  await vi.waitFor(() => {
    expect(harness.onMove).toHaveBeenCalledExactlyOnceWith(CONNECT_MOVE);
  });
} finally {
  clearInterval(timerPump);
}
