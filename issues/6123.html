#6123 · Background tasks lose their terminal event on owner exit

BugPriority: MediumEffort: Mediumhost · threads · provider-claude-code GitHub issue · October 22, 2026 · base c7a10f237eb5b941dfaf79cbb65f246c66eeddcb

Verdict: REPRODUCED · Root-cause confidence: high · reproduction label: confirmed-repro.

1. TL;DR

A background task can outlive the foreground turn, so an idle thread may correctly have unfinished background work. When its provider process is subsequently shut down or killed, the runtime forgets that work without emitting the terminal background-task event. Two focused cases reproduce this on unmodified main production code using the repository's real scripted-echo bridge subprocess: graceful runtime shutdown and SIGKILL of that bridge worker. Both cases fail again in a second clean checkout of the same commit. This verifies the missing lifecycle event, not the reporter's particular machine, timer screenshot, cloud billing, or resume history.

import { mkdtempSync, rmSync } from "node:fs";
import { tmpdir } from "node:os";
import { dirname, join } from "node:path";
import { expect, it } from "vitest";
import type { ThreadEvent } from "@bb/domain";
import { createAgentRuntime } from "./runtime.js";
import {
  createScriptedEchoLaunch,
  createScriptedEchoProcessLog,
  fullRuntimeOptions,
  scriptedEchoBridgeModulePath,
  waitForRuntimeState,
  waitForThreadTurnCompleted,
  withBridgeLaunch,
} from "./test/runtime-test-harness.js";
import { promptTextInput } from "./test/prompt-input.js";

it.each(["shutdown", "bridge-kill"] as const)(
  "settles an idle background task after %s",
  async (exitMode) => {
    const workspacePath = mkdtempSync(join(tmpdir(), "bb-owner-exit-repro-"));
    const processLog = createScriptedEchoProcessLog();
    const launch = createScriptedEchoLaunch();
    const events: ThreadEvent[] = [];
    let processExited = false;
    const runtime = withBridgeLaunch(
      createAgentRuntime({
        workspacePath,
        bridgeBundleDir: dirname(scriptedEchoBridgeModulePath),
        env: processLog.env,
        onEvent: (event) => events.push(event),
        onProcessExit: () => {
          processExited = true;
        },
      }),
      launch,
    );
    const threadId = "owner-exit-thread";
    try {
      await runtime.startThread({
        environmentId: "env-repro",
        projectId: "project-repro",
        providerId: "fake",
        threadId,
        options: fullRuntimeOptions,
      });
      await runtime.runTurn({
        clientRequestId: "creq_abcdefghjk",
        threadId,
        input: [promptTextInput({ text: "bg_task" })],
        options: fullRuntimeOptions,
      });
      await waitForThreadTurnCompleted({ events, threadId });
      expect(runtime.getActiveTurnId(threadId)).toBeNull();
      expect(runtime.hasOpenBackgroundWork()).toBe(true);
      const started = events.find(
        (event) =>
          event.type === "item/started" && event.item.type === "backgroundTask",
      );
      if (started?.type !== "item/started") {
        throw new Error("The real provider did not start a background task");
      }
      expect(started.item.status).toBe("pending");
      const taskPidEntry = processLog
        .read()
        .find((line) => line.startsWith("bg_task/open:"));
      const taskPid = Number(taskPidEntry?.split(":")[1]);
      expect(Number.isSafeInteger(taskPid) && taskPid > 0).toBe(true);
      if (exitMode === "shutdown") {
        await runtime.shutdown();
      } else {
        process.kill(taskPid, "SIGKILL");
        await waitForRuntimeState({
          label: "background task owner exit",
          predicate: () => processExited,
        });
      }
      expect(() => process.kill(taskPid, 0)).toThrow();
      expect(runtime.hasOpenBackgroundWork()).toBe(false);
      const completions = events.filter(
        (event) =>
          event.type === "item/backgroundTask/completed" ||
          (event.type === "item/completed" &&
            event.item.type === "backgroundTask"),
      );
      console.log(
        JSON.stringify({
          exitMode,
          activeTurn: runtime.getActiveTurnId(threadId),
          runtimeHasOpenWork: runtime.hasOpenBackgroundWork(),
          taskStartCount: 1,
          taskCompletionCount: completions.length,
          ownerAlive: false,
        }),
      );
      expect(completions).toContainEqual(
        expect.objectContaining({
          item: expect.objectContaining({
            id: started.item.id,
            status: "interrupted",
            taskStatus: "stopped",
          }),
        }),
      );
    } finally {
      await runtime.shutdown();
      rmSync(workspacePath, { recursive: true, force: true });
      rmSync(dirname(processLog.path), { recursive: true, force: true });
      rmSync(launch.dataDir, { recursive: true, force: true });
    }
  },
);

5. Root cause

The owner lifecycle and timeline lifecycle are disconnected. RuntimeBackgroundWorkState stores only task IDs and clears sets without producing events. Its state can therefore say there is no background work while the event stream still contains an unmatched start.

clear(): void {
  this.openTaskIdsByThreadId.clear();
}

clearThread(threadId: string): void {
  this.openTaskIdsByThreadId.delete(threadId);
}
  • Runtime shutdown clears background work before shutting provider processes down, without emitting a completion.
  • Provider stdout delivery is suppressed during shutdown; the exit handler also returns early during shutdown. A late provider completion is not a reliable fallback.
  • On unexpected bridge exit, the detach callback clears the same state without a terminal event. Daemon exit-event construction skips an idle thread with no pending turn start, so its turn-level error handling does not supply the missing background-task completion.
  • Runtime manager shutdown calls each runtime's shutdown. The daemon shutdown sequence still flushes its event sink after that call: there is an opportunity to deliver a synthetic terminal event, but none is produced.
  • Machine suspension waits for daemon shutdown then proceeds to suspension without task settlement here. Ordinary disconnect handling closes the session and updates display state, but does not call task reconciliation. Existing reconciliation also runs for replacement by a different daemon instance, and on host removal/import cleanup; it is not an immediate response to this owner stopping.

The related Claude SDK stream-end callback has a comparable missing settlement operation. A resumed translator also ignores unknown task notifications. Those paths were inspected only, not executed in this report. Why the reporter's particular new daemon instance did not reconcile is not established by these tests.

6. Proposed fix

Retain the information needed to close each pending background task and emit its existing terminal event when its actual owner stops. Use the same settlement operation for runtime shutdown and provider detachment, preserve task identity and scope, and never emit a second completion for tasks already settled. Ensure daemon event flushing follows settlement. Handle a Claude CLI stream ending while its bridge remains alive separately, since the runtime has not observed bridge death in that case.

Do not treat a brief transport disconnect as proof that a process died; a machine that preserves memory can retain legitimate background work. Any server suspension fallback should require a reliable shutdown acknowledgement. Abrupt daemon loss and restart recovery require separate coverage.
