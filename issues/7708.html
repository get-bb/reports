Reports · Issue #7708

Recurring automation retry consent has a pre-association race

Bug · Priority: Medium · Effort: Medium · plugins, automations, provider-retry
November 17, 2026 · trusted main: 1320c88e8abdd3f145bc9a5c305eace269fb2f28

Verdict: PARTIALLY REPRODUCED · Root-cause confidence: medium for the reported incident; high for the demonstrated race.

1. TL;DR

A scheduled automation normally declines provider retries, but it cannot recognize its new thread until the thread-spawn SDK call returns. When a failure and retry-consent request arrive before that response, the real automations plugin answers allow, and the real provider-retry plugin submits a retry. The same request is declined immediately after the spawn response. The early failure notification also misses the automation run; restarting its sweep service with the failed thread state reconciles the run and submits a fresh automation spawn. This controlled interleaving reproduces competing retry submissions, not the reporter's full macOS wake sequence or three completed prompts.

5. Root cause

  1. executeAgentRun awaits spawn before persisting the thread ID. Thus the run exists but cannot yet be queried by that thread.
  2. answerRetryConsent looks up the run by thread ID and allows a missing run. The fixture uses a matching request ID and thread-start target, so the missing association, not a parse error, causes consent.
  3. askSender calls the sender's consent RPC and the handler only suppresses retry on an explicit decline. A valid allow answer falls through to the existing SDK retry submission path.
  4. failure settlement also depends on the thread/run association. The first failure event finds no run, leaving it running after spawn eventually returns.
  5. startup reconciliation settles running rows using the thread's failed state. recurring failures schedule bounded quick retries, allowing a fresh spawn even though provider-retry has already submitted its retry.

Core schedules thread provisioning before returning the admitted thread; provisioning advances asynchronously. This supports the plausibility of an earlier lifecycle notification, but the reproduction intentionally forces that ordering at the SDK boundary. It does not prove that the real HTTP transport and lifecycle event dispatcher produce it during a macOS wake.

6. Proposed fix and safety decision

Associate automation ownership with the first request before provider execution can emit lifecycle events, and ensure a settlement cannot be lost during thread creation. Keep the request-ID and schedule/manual distinctions; blanket refusal of all automation retries could break one-shot and manual turns.

No fix PR: only a controlled boundary interleaving is confirmed, not the full reported transport sequence. A safe repair needs verified early run/thread ownership across spawn and lifecycle delivery; no under-500-line, single-subsystem repair with a passing regression has been established. The next experiment is a core integration test delaying the real spawn HTTP response while provisioning emits a structured 503, with durable queue state inspected before and after plugin restart.

The second checkout built the SDK first and completed the broad build successfully.

The controlled spawn response has already allocated its thread fixture before emitting failure. Recovery is an explicit restart of the registered automation-sweep service, not a real machine wake or process restart. SDK retry delivery returns a queued receipt fixture; the durable queue and provider continuation are not exercised. These limits are why the verdict is partial and root-cause confidence for the reported incident is medium.
