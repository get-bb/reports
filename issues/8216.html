#8216 · Bounded path ranking evaluates dominated candidates

BugPriority: MediumEffort: Lowhostperfconfirmed-repro

GitHub issue · November 26, 2026 · base b0ddaad731565d7e4de68d824120d802fc78f7d5

Verdict: REPRODUCED · Root-cause confidence: high

1. TL;DR

Searching workspace paths can spend substantial CPU scoring results that cannot enter the requested top 17. The shared matcher receives the result limit but applies it only after all ranking passes. On a deterministic 12,000-file fixture, a directory query feeds all 12,000 paths to plain fuzzy scoring even though every result has a dominant directory score. A slash query performs 48,000 unnecessary segment-candidate evaluations after already finding enough exact-directory-prefix matches; its 12,000 exact-prefix tail evaluations are separate and necessary in this implementation. The same agent repeated both failures in a second clean checkout; no live app, filesystem walk, or linked-PR code was used.

Original resource regression probe

The proxy only counts candidate arrays and forwards construction to the real fzf implementation. It does not implement matching, replace scores, introduce a production seam, or use wall-clock thresholds. Resource counters are isolated with Vitest's existing mock-aware shared worker configuration. This guards unnecessary ranking work, which the existing output-only tests do not measure.

import { expect, it, vi } from "vitest";
import { fuzzyMatchPaths } from "../src/index.js";

const work = vi.hoisted(() => ({ plain: 0, structured: 0, exactPrefix: 0 }));

vi.mock("fzf", async (importOriginal) => {
  const original = await importOriginal<typeof import("fzf")>();
  return {
    ...original,
    Fzf: new Proxy(original.Fzf, {
      construct(target, args) {
        const [candidates] = args;
        if (!Array.isArray(candidates)) {
          throw new Error("Expected an array at the ranking boundary");
        }
        const [first] = candidates;
        if (typeof first === "string") {
          work.exactPrefix += candidates.length;
        } else if (typeof first === "object" && first !== null) {
          if ("segment" in first) {
            work.structured += candidates.length;
          } else if ("path" in first) {
            work.plain += candidates.length;
          }
        }
        return Reflect.construct(target, args);
      },
    }),
  };
});

it.each([
  { query: "engine", minimumScore: 1_000_000 },
  { query: "engine/mod", minimumScore: 3_000_000 },
  { query: "engine/", minimumScore: 3_000_000 },
])("avoids dominated scoring for $query", ({ query, minimumScore }) => {
  const items = Array.from(
    { length: 12_000 },
    (_, index) => `engine/module${String(index).padStart(5, "0")}.ts`,
  );
  const limit = 17;
  work.plain = 0;
  work.structured = 0;
  work.exactPrefix = 0;
  const started = performance.now();
  const matches = fuzzyMatchPaths({
    items,
    query,
    getPath: (path) => path,
    limit,
  });
  const elapsedMs = Number((performance.now() - started).toFixed(2));
  console.log(JSON.stringify({ query, limit, paths: items.length, ...work, elapsedMs }));
  expect(matches.map((match) => match.item)).toEqual(items.slice(0, limit));
  expect(matches.every((match) => match.score >= minimumScore)).toBe(true);
  expect(work.plain + work.structured).toBe(0);
});

Uninstrumented 100,000-path benchmark

This mirrors the ranking portion of rankListedPathsInChunks: ten 10,000-path chunks, limit 17 per chunk, then one final ranking. It deliberately excludes the daemon's cancellation checks and event-loop yields, so these are in-process ranking costs, not measured UI response times. The benchmark does not load the proxy.

import assert from "node:assert/strict";
import { fuzzyMatchPaths } from "../src/index.ts";

const items = Array.from(
  { length: 100_000 },
  (_, index) => `engine/module${String(index).padStart(5, "0")}.ts`,
);
const limit = 17;
const chunkSize = 10_000;

for (const query of ["engine", "engine/mod"]) {
  const measurements = [];
  for (let attempt = 0; attempt < 3; attempt += 1) {
    const startCpu = process.cpuUsage();
    const startWall = performance.now();
    const finalists = [];
    for (let offset = 0; offset < items.length; offset += chunkSize) {
      const matches = fuzzyMatchPaths({
        items: items.slice(offset, offset + chunkSize),
        query,
        getPath: (path) => path,
        limit,
      });
      finalists.push(...matches.map((match) => match.item));
    }
    const matches = fuzzyMatchPaths({
      items: finalists,
      query,
      getPath: (path) => path,
      limit,
    });
    const wallMs = Number((performance.now() - startWall).toFixed(2));
    const elapsedCpu = process.cpuUsage(startCpu);
    const cpuMs = Number(((elapsedCpu.user + elapsedCpu.system) / 1000).toFixed(2));
    assert.deepEqual(matches.map((match) => match.item), items.slice(0, limit));
    measurements.push({ wallMs, cpuMs });
  }
  console.log(JSON.stringify({ query, paths: items.length, chunkSize, limit, measurements }));
}

5. Root cause

The public fuzzyMatchPaths boundary normalizes/prefilters candidates and calls the internal ranking function without its limit. The limit is only used by the final result conversion:

  return rankedMatchesToFuzzyMatches(
    rankPathQueryMatches(normalizedItems, normalizedQuery),
    args.limit,
  );

The internal ranking dispatcher eagerly evaluates both relevant passes. With a non-slash query, plain fzf runs before the directory-prefix results are even computed. With a non-trailing slash query, structured matching is computed before checking whether exact-prefix results already fill the request:

  if (query.includes("/")) {
    const exactPrefixMatches = getExactDirectoryPrefixPathMatches(items, query);
    if (exactPrefixMatches.length > 0 && query.endsWith("/")) {
      return mergeRankedMatches(exactPrefixMatches);
    }

    const structuredMatches = getStructuredPathMatches(items, query);
    if (exactPrefixMatches.length > 0) {
      return mergeRankedMatches(exactPrefixMatches.concat(structuredMatches));
    }

    return mergeRankedMatches(
      rankPlainQueryMatches(items, query).concat(structuredMatches),
    );
  }

  return mergeRankedMatches(
    rankPlainQueryMatches(items, query).concat(
      getDirectorySegmentPrefixPathMatches(items, query),
    ),
  );

rankPlainQueryMatches gives the full surviving array to fzf. getPathSegmentMatch constructs a real matcher over segment candidates, called repeatedly by getStructuredPathMatch. In this two-segment fixture the structured pass submits two candidates for the first segment, one for the second, and one for the leaf: four per path, or 48,000 for 12,000 paths.

Intent tiers and getRankedScore separate the intended ranking modes by one million points. For this fixture, engine is an exact root directory segment with score 1,035,000. Its ordinary-path relevance bonus is only 1,500, and even a conservative 32 points per query character leaves plain scoring below 1,700. The exact-prefix results for engine/mod have scores at least 3,000,000; its structured segment scores remain below 2,100,000. Thus the measured lower-pass work cannot change the requested answers. Exact-prefix matching itself still calls fzf on each tail when the leaf query is nonempty: that necessary phase is explicitly excluded from the failing assertion.

The deeper cause is the absence of a limit-aware ranking budget across scoring passes, not a slow filesystem scan. The existing trailing-slash shortcut demonstrates that the subsystem already distinguishes a complete higher-tier result set in one narrow case.

6. Proposed fix

Pass the requested limit into internal path ranking. Evaluate relevant high-score matches first, then skip a lower pass or candidate group only when a conservative maximum possible score is strictly below the current kth result. Include relevance bonuses and all structured scoring components in the bound; do not assume million-point tiers are globally disjoint for arbitrary pathological paths. Preserve equality/tie ordering, item deduplication, smart-case, Unicode behavior, positions, and fallback matching when fewer than k stronger results exist. No public API, wire protocol, dependency, or stored-data change is needed.
