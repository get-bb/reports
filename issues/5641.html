1. TL;DR

The trusted Claude provider emits an extra background-task item for a foreground Bash call. A hermetic test exercises the real translator and event assembler, not a replacement implementation, and reproduces this with both missing background metadata and explicit foreground metadata. The task type is treated as proof of background execution even though the existing command item is already running. This explains the misleading background presentation; it does not prove the reported multi-minute steer delay. No live provider session or browser was used, so SDK command scheduling and the visual appearance remain unverified.

import { expect, it } from "vitest";
import {
  createClaudeDeltaHarness,
  spawningToolUseMessage,
} from "./delta-test-harness.js";

it.each([{}, { is_backgrounded: false }])(
  "does not open a background lifecycle for a foreground shell task (%j)",
  (taskMetadata) => {
    const harness = createClaudeDeltaHarness();
    const context = { threadId: "foreground-reproduction" };
    const command = harness.translate(
      spawningToolUseMessage({
        toolUseId: "shell-tool",
        toolName: "Bash",
        input: { command: "sleep 60" },
      }),
      context,
    );
    expect(command).toContainEqual(
      expect.objectContaining({
        type: "item/started",
        item: expect.objectContaining({ type: "commandExecution" }),
      }),
    );
    const events = harness.translate(
      {
        type: "system",
        subtype: "task_started",
        task_id: "shell-task",
        tool_use_id: "shell-tool",
        task_type: "local_bash",
        description: "Wait for completion",
        ...taskMetadata,
      },
      context,
    );
    expect(
      events.filter(
        (event) =>
          event.type === "item/started" && event.item.type === "backgroundTask",
      ),
    ).toEqual([]);
  },
);

5. Root cause

isMaterializedTaskType accepts every local_bash task. The task-start handler checks whether the spawning tool was forwarded, but never consults its execution mode. It creates a tracked task and immediately opens an item. buildClaudeTaskShape hardcodes type: backgroundTask, and the presentation factory hardcodes the background label.

task_type: local_bash
  → admitted regardless of foreground/background state
  → buildClaudeTaskShape(...): type = backgroundTask
  → presentation.label.pending = Running background command

The task-start schema passes through unrecognized fields but does not type is_backgrounded. The existing Bash argument parser already derives run_in_background, but that information is not passed into task translation. The installed SDK distinguishes foreground from background at task start and reports later transitions via task_updated.patch.is_backgrounded. A repair must preserve both explicit background work and later promotion rather than discarding all shell tasks.

Separately, SdkSession.pushInput resolves its consumed promise only when the SDK asks for the message. That can explain waiting, but it is not live evidence of this issue's particular delay. Correcting classification does not make a foreground tool interruptible.

6. Proposed fix and autopilot decision

Parse the SDK foreground/background signal, fall back to the original Bash background flag only when metadata is absent, and retain foreground task state without emitting background items. Materialize a background lifecycle if an update explicitly backgrounds that task. Preserve the ordinary command item and its inline completion; suppress hidden-task progress, completion, and interruption events.

A local candidate does this in the existing Claude provider subsystem: 4 text files; 201 additions + 17 deletions = 218 changed lines. No dependencies, generated files, migrations, stored data, public protocol, or UI/SDK/CLI surface changes. The candidate is retained locally only, not shipped or published as a patch.
