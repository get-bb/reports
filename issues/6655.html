#6655 · Diagnostic Claude processes reconnect to configured MCP servers

Bug Priority: Medium Effort: Medium providers · provider-claude-code · perf GitHub issue October 30, 2026 · base a1bf55b6a04c7948ae5ae0dcfcbdec27d2b507a2

Verdict: REPRODUCED · Root-cause confidence: high · reproduction label: confirmed-repro

1. TL;DR

Reading Claude model metadata or context usage starts another Claude process, even when an existing conversation process remains active. Each diagnostic process loads the configured user MCP servers. In two clean runs, two metadata probes each opened a fresh MCP connection; the context probe also connected and then abandoned all three outstanding discovery requests. The result is unnecessary connection churn and canceled server work, without requiring a user tool call or a failed conversation. The repeatable evidence uses the real provider functions, real SDK, and its pinned native Claude executable against a synthetic local MCP server; it does not use an account or the reporter’s configuration.

5. Root cause

Short-lived SDK queries inherit user MCP configuration and close after metadata or context collection, without waiting for configured MCP discovery to finish. The metadata query does not need tool discovery, but passes all setting sources and no strict MCP configuration:

Metadata query and unconditional close

    session = query({
      prompt: promptWithoutMessages(promptEnd.signal),
      options: {
        cwd: args.cwd,
        env: args.env,
        persistSession: false,
        settingSources: ["user", "project", "local"],
        ...(pathToClaudeCodeExecutable ? { pathToClaudeCodeExecutable } : {}),
      },

The context query likewise loads user/project/local settings. Its tool denial callback prevents tool execution, not MCP startup or discovery. Setting disableAllHooks is not MCP isolation. Its only MCP readiness loop is conditional on BB dynamic tools and checks only the BB bridge, not every user-configured server:

Inherited MCP configuration and readiness/close behavior

  try {
    args.signal.throwIfAborted();
    await session.initializationResult();
    while (args.dynamicTools.length > 0) {
      const server = (await session.mcpServerStatus()).find(
        (server) => server.name === BB_BRIDGE_MCP_SERVER_NAME,
      );
      if (server?.status === "connected") break;
      if (server && server.status !== "pending") return null;
      await delay(25, undefined, { signal: args.signal });
    }
    return await session.getContextUsage();
  } finally {
    args.signal.removeEventListener("abort", close);
    close();
  }

Capture trigger schedules another isolated reader on result, initialization, and compaction events. Model and command discovery also call the metadata helper: model caller and command caller.

The native SDK’s MCP discovery is asynchronous relative to initialization and context collection. Therefore an initialize response or context result does not mean every configured MCP listing has completed; unconditional closure can terminate that work. This also explains why initialization sometimes closes before listing even begins.

6. Proposed fix and simple-fix assessment

Metadata discovery can be isolated from configured MCP servers using the SDK’s strict MCP option and an empty explicit server configuration. A dependency-backed regression should prove metadata still works and the configured fixture receives no connection. That addresses only one half of this issue.

The context path needs a design choice before a complete repair is safe: retain accurate MCP/tool accounting while avoiding repeated discovery and preserving the existing isolation from the live conversation. Silently dropping MCP changes the meaning of the report. Moving the request to the live process reverses the protection introduced in the reporting-isolation change, which was needed because a stalled token-count request could block subsequent prompts. Caching or reusing diagnostic state also needs explicit invalidation and lifecycle ownership.

No pull request was opened: the complete fix requires an architecture/product decision about context reporting, so it does not pass the requested simple-fix gate. No candidate production patch, branch, commit, dependency, or wire change was made. No linked open pull request was present in issue timeline metadata or the issue-number PR search.
