#6497 · Anchored side replies retry at an older checkpoint

BugPriority: MediumEffort: Mediumthreads · side-chat GitHub issue · 2026-10-28 · base 055e758fff353c6986f3733befd13be9b86b1274

Verdict: REPRODUCED · Root-cause confidence: high

1. TL;DR

A reply anchored inside an unfinished turn can successfully open a side chat whose provider fork descriptor points to the preceding completed turn. The core correctly rejects the requested anchor, but the Side chat plugin catches its broad unavailable-session error and retries without the anchor. The quoted text survives, so the operation looks successful while its conversation checkpoint is older. A real built-in plugin RPC and real server/database reproduction produced that mismatch twice on trusted main. This report verifies the backend decision and outgoing provider command, not an actual model response or native rollout file.

5. Root cause

  1. The anchored resolver looks up the selected message's turn and rejects it when completion is absent. The error helper uses the same unavailable-session code for multiple different causes.
  2. The plugin error predicate recognizes only this broad code, not the reason.
  3. The retry calls bb.sdk.threads.fork(forkArgs) without sourceSeqEnd, while preserving the quote and lifecycle ownership. This is the root semantic change: an exact-point operation silently becomes a tip operation.
  4. The unanchored resolver correctly chooses the last completed checkpoint for a rewind-capable provider while a newer turn is active. The caller has discarded the information that made that checkpoint inappropriate.
  5. The UI caller forwards the anchor and displays an error toast only when RPC creation fails. A successful fallback gives it no indication of degraded context. This is static source evidence; the UI was not clicked.

The completed-turn control reaches the selected turn's own checkpoint, proving this is anchor loss rather than an incorrect parent-session identity. Existing server tests cover running-turn rejection and unanchored completed-checkpoint behavior separately; existing plugin tests explicitly require a tip fallback for an anchor before any provider session. They do not combine the installed plugin with the real core error and provider-command boundary.

6. Proposed fix and simple-fix assessment

Make the unavailable-anchor reason machine-readable, and restrict any permitted fallback to the explicitly supported pre-session case. For an unfinished selected turn, propagate an actionable error through the existing UI error path (or design a deliberate deferred operation). Keep the selected checkpoint in the completed control and preserve the quoted seed.

No pull request opened. The narrow-looking deletion of all fallback handling also removes explicitly tested pre-session fallback behavior. Preserving it robustly requires a shared error-contract distinction; removing it instead needs a product decision. Error-message substring matching or guessing from current thread status would be brittle and race-prone. These alternatives fail the autopilot's no-public-contract-change/no-product-decision simple-fix gate. No production fix or branch was pushed.
