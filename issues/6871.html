#6871 · Model discovery accepts configuration without confirming its model

BugPriority: MediumEffort: Lowproviders · provider-acp · confirmed-reproGitHub issue

2026-11-02 · trusted origin/main 21ff1a47f7a1e79b408a2c95b1f9c01b90d18c6b

Verdict: REPRODUCED · Root-cause confidence: high

1. TL;DR

The model catalogue can advertise another model's reasoning choices, including a falsely confirmed empty list. The discovery loop asks an ACP peer to switch models, but records the returned reasoning and service-tier configuration under the requested model without confirming which model the reply describes. A deterministic subprocess peer, using the repository's existing ACP fixture, reproduces this through the real bridge's model/list boundary. Four focused cases fail on unchanged production code in two separate clean checkouts; all four pass with a bounded retry and model-identity check. This verifies bb's handling of such replies, not the frequency of a particular external agent's race.

5. Root cause

The discovery loop uses the requested model value as its map key immediately after a successful request:

const configState = await args.connection.request({
  method: "session/set_config_option",
  params: { sessionId: args.sessionId, configId: modelOption.id, value: model.value },
  resultSchema: acpConfigStateResultSchema,
});
supportByModel.set(model.value, {
  ...buildAcpNativeReasoningSupport(
    findAcpThoughtLevelConfigOption(configState.configOptions),
  ),
  …
});

Schema-valid configuration does not establish that its model currentValue equals the requested value. A stale reply therefore passes boundary validation but is attributed to the wrong map key. This affects both reasoning and service-tier support, which are assembled from the same snapshot.

The reasoning helper correctly treats an absent thought-level option as known-empty support. The catalogue builder already represents an absent support-map entry as unknown. Keeping unverifiable snapshots out of the map fixes the attribution without changing either helper or any public schema.

6. Proposed fix and validation

Before storing support, use the existing model-option selector to require that the reply identifies the requested model. Retry once within the existing discovery deadline; if neither reply confirms the model, leave its support absent/unknown and continue with later models. Missing identity must not count as confirmation. Apply the same guard before storing service tiers. No protocol, persistent-data, dependency, CLI, or public API changes are needed.
