#6859 · Superseded outline responses consume cache capacity

BugLow priorityLow effortthreads · perf Issue · 2026-11-02 · base d448d87f2033f7c253b64370c321ea9e7500c81d

Verdict: REPRODUCED · Root-cause confidence: high · reproduction label: confirmed-repro

1. TL;DR

The server can retain many obsolete conversation-outline responses for one evolving thread. Each new outline sequence creates a distinct response-cache key, but the old key is not removed. The 128-entry limit bounds entry count rather than the number of threads or bytes, so old responses consume capacity and can evict another thread's still-current response. A new route-level regression demonstrates that eviction on trusted main in two separate checkouts. No production heap, memory amount, or client platform claim was measured in this investigation.

5. Root cause

The route creates one LRU response map with 128 entries. Its key includes thread identity, database data version, and the outline projection key. The projection key includes the latest outline sequence. Therefore each appended outline-relevant event changes the response key.

Response-cache ownership and limit

  const conversationOutlineCache = new Map<
    string,
    ThreadConversationOutlineResponse["items"]
  >();
  const CONVERSATION_OUTLINE_CACHE_MAX_ENTRIES = 128;

Versioned lookup and insertion

    const outlineOptions = resolveConversationRowsOptions(thread);
    const { maxSeq } = outlineOptions;
    const cacheKey = JSON.stringify([
      thread.id,
      getDatabaseDataVersion(deps.db),
      buildThreadConversationOutlineProjectionKey(
        thread,
        outlineSequence,
        outlineOptions,
      ),
    ]);
    const cached = conversationOutlineCache.get(cacheKey);
    if (cached !== undefined) {
      conversationOutlineCache.delete(cacheKey);
      conversationOutlineCache.set(cacheKey, cached);
      return context.json({ items: selectItems(cached), maxSeq });
    }
    const response = loadThreadConversationOutline(deps.db, thread, {
      ...outlineOptions,
      outlineSequence,
    });
    conversationOutlineCache.set(cacheKey, response.items);
    while (
      conversationOutlineCache.size > CONVERSATION_OUTLINE_CACHE_MAX_ENTRIES
    ) {
      const oldest = conversationOutlineCache.keys().next().value;
      if (oldest === undefined) {
        break;
      }
      conversationOutlineCache.delete(oldest);
    }

Projection revision includes outlineSequence

export function buildThreadConversationOutlineProjectionKey(
  thread: Thread,
  outlineSequence: number,
  options: BuildThreadConversationOutlineOptions,
): string {
  return JSON.stringify([
    CONVERSATION_OUTLINE_PROJECTION_VERSION,
    getThreadEventRewriteGeneration(thread.id),
    outlineSequence,
    thread.providerId,
    options.providerDisplayName ?? null,
    thread.status,
    thread.title,
    thread.titleFallback,
    options.completedTurnDisplay,
    options.includeClearedContextHistory,
  ]);
}

On a miss, the route inserts another full items array and removes only the oldest global entry if the limit is exceeded. It has no per-thread replacement operation. Ordinary append-only progress cannot request those obsolete sequence keys again. The baseline regression indirectly observes the accumulated dead slots through eviction at the database boundary, without inspecting private maps or modifying global Map behavior.

6. Proposed fix

Keep the existing LRU but index it by thread ID. Store the current full revision key alongside the items. Serve a cached response only when that revision matches, and delete/reinsert the thread entry on both hits and replacements to maintain recency. Keep all existing invalidation inputs, role filtering, maxSeq behavior, and the 128-thread limit. No API, protocol, schema, dependency, or persistence change is needed.
