#8129 · Repository-wide plugin dependencies on trusted main

Bug Priority: Medium Effort: Medium plugins · GitHub issue · November 24, 2026

Trusted base: 83368cff5166aa01ff4706056995a7626e859555

Verdict: NOT REPRODUCED on trusted origin/main. Root-cause confidence: high for the baseline explanation. The proposed sparse-checkout regression remains unverified because its pull request is not merged and was not executed.

1. TL;DR

The report concerns a regression in a proposed sparse plugin checkout change, not the implementation currently on main. The trusted baseline fetches one commit shallowly but materializes its entire working tree. Consequently, plugins can still load repository files outside their selected directory, and a root directory alias has its target present after a sibling install. Five focused install checks pass in each of two clean trusted checkouts with unchanged production code. This does not disprove a regression in the unmerged proposal; no pull request branch, script, patch, or test supplied by the issue was executed.

5. Root cause and scope

There is no observed defect to attribute on this baseline. The reason the reported symptoms do not occur is that shallow history and sparse working trees are different mechanisms: fetching one commit does not omit directories from that commit's checkout.

The shared clone implementation runs fetch --depth 1 --no-tags, then checkout --detach FETCH_HEAD, with no sparse configuration. It also has a normal full-clone fallback. It removes .git only after materializing the whole tree.

"fetch", "--quiet", "--depth", "1", "--no-tags", url, commit
"checkout", "--quiet", "--detach", "FETCH_HEAD"

Installation selects the plugin after cloning, then reads its manifest and validates/builds it. The server builder bundles the selected entry, so a repository-relative import is available when the full working tree exists.

Shared-cache promotion does create the selected root's parent. A genuinely dangling symlink parent would be a distinct risk, but the direct baseline experiment does not produce that cache state: the first install already materializes the alias target. Artificially deleting its target would not demonstrate an install-generated regression on main, so that was not used as reproduction evidence.

6. Proposed fix or next experiment

No production change is justified by these baseline results. Keep the five install probes as reusable report evidence for a future trusted main containing sparse checkout. Once that implementation is merged, rerun them and add focused update/candidate probes before deciding whether dependency materialization and shared-cache promotion need changes. The alleged sparse regression itself has not been dynamically verified here.
