#8009 · Selected-model discovery never revisits persisted empty reasoning support

BugPriority: MediumEffort: Mediumproviders, provider-acp, confirmed-repro open on GitHub2026-11-22 · base 796cdcc0f4bf8a55e23664035c54e8db6fe9d272

Verdict: REPRODUCED · Root-cause confidence: high for the server catalog behavior. The reporter’s particular OpenCode/LM Studio installation was not exercised.

1. TL;DR

The model catalog can remember an empty reasoning-level answer indefinitely, even when the same provider would now return levels. The server treats an empty known result as just as authoritative as a populated one. A subsequent full catalog that reports that model as unknown inherits the old empty answer, and selecting the model never asks the host again. This state is persisted in SQLite and survives replacing the in-memory catalog store. Two clean-checkout runs demonstrate the failure after two simulated days, while a previously unprobed model immediately gets the new level.

loadStoredGood reloads the same known model data from SQLite, explaining why a new store does not repair it. persistGood saves catalog-wide fetchedAt but no per-model discovery age.

The response shape is realistic for ACP: acpNativeModelSupport explicitly classifies an empty options list as known; buildModelCatalogFromConfigOptions uses unknown for unprobed models. discoverAcpNativeModelSupport probes only selected/current model support rather than every catalog member.

The existing known-empty test explicitly requires no second probe after the failure cooldown. This is an established policy limitation, not an accidental exception or failed request.

6. Proposed fix and automation safety

Give discovered reasoning an explicit invalidation/retry policy separate from whole-catalog freshness. If time-based expiry is selected, retain the original per-model discovery time through full refreshes and process restarts; expire both known-empty discovery and the selected-request success cache, and permit a refreshed result to replace old known data without clobbering newer live answers. Preserve request deduplication and bounded retry behavior for genuinely unsupported models and failures.

Before implementation, choose the expiry interval, whether nonempty discoveries expire, and whether explicit user refresh also invalidates support. A durable per-model timestamp changes persisted data/meaning; an explicit refresh feature adds product/API/CLI decisions. These are outside this autopilot’s simple-fix conditions. No fix branch, production patch, push, or pull request was created. The report preserves a failing owner-boundary regression test for the follow-up.

The report patch is 80 added text lines in one existing test file, no deletions; git diff --check passes. That is reproduction evidence, not a proposed complete fix. Removing the known guard or retrying every selection would silently change the established no-repeat policy and can create repeated agent startup/switch-and-restore work, so neither is an acceptable automatic shortcut.
