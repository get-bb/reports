#5481 · Background-task state across provider identity replacement

BugPriority: LowEffort: Medium threadsprovider-claude-code GitHub issueOctober 14, 2026

Trusted base: a7d5dfcc8c27df1fea42847526ee62a338fe8052 (origin/main).

Verdict: PARTIALLY REPRODUCED · Root-cause confidence: medium

1. TL;DR

The real server accepts a new provider identity while retaining an earlier session's unfinished background-command item. Two clean-source runs show zero terminal task events and one active background command after the identity changes. That is enough to explain persistent activity if the old runtime has actually ended, but it does not establish how the reported message edit was admitted. The current edit service rejects this fixture with status 409 before any rewind, and that guard was already present when message editing was introduced on August 11, 2026. This report therefore verifies the lifecycle-state gap, not the historical desktop interaction or process termination.

Full reproduction test
import {
  getLastStoredProviderThreadId,
  listActiveBackgroundTaskCountsByThreadIds,
  listEvents,
  listOpenBackgroundTaskItemRowsForThread,
} from "@bb/db";
import { threadScope, turnScope } from "@bb/domain";
import {
  groupHostDaemonEvents,
  type HostDaemonEventEnvelope,
} from "@bb/host-daemon-contract";
import { expect, it } from "vitest";
import { editThreadMessage } from "../../src/services/threads/thread-edit-message.js";
import { internalAuthHeaders } from "../helpers/commands.js";
import { seedThreadFixture } from "../helpers/seed.js";
import { withTestHarness } from "../helpers/test-app.js";

it("settles an old-session background command when provider identity changes", async () => {
  await withTestHarness(async (harness) => {
    const { environment, session, thread } = seedThreadFixture(harness, {
      thread: { providerId: "claude-code", status: "idle" },
    });
    const providerThreadId = "repro-session-before";
    const postEvents = (events: HostDaemonEventEnvelope[]) =>
      harness.app.request("/internal/session/events", {
        method: "POST",
        headers: internalAuthHeaders(harness),
        body: JSON.stringify({
          sessionId: session.id,
          eventGroups: groupHostDaemonEvents(events),
        }),
      });
    const initial = await postEvents([
      {
        threadId: thread.id,
        event: {
          threadId: thread.id,
          type: "thread/identity",
          providerThreadId,
          scope: threadScope(),
        },
      },
      {
        threadId: thread.id,
        event: {
          threadId: thread.id,
          type: "turn/started",
          providerThreadId,
          scope: turnScope("repro-turn"),
        },
      },
      {
        threadId: thread.id,
        event: {
          threadId: thread.id,
          type: "item/started",
          providerThreadId,
          scope: turnScope("repro-turn"),
          item: {
            id: "repro-command",
            type: "backgroundTask",
            taskType: "local_bash",
            description: "fixture background command",
            status: "pending",
            taskStatus: "running",
            skipTranscript: false,
          },
        },
      },
      {
        threadId: thread.id,
        event: {
          threadId: thread.id,
          type: "turn/completed",
          providerThreadId,
          scope: turnScope("repro-turn"),
          status: "completed",
        },
      },
    ]);
    expect(initial.status).toBe(200);
    expect(
      listOpenBackgroundTaskItemRowsForThread(harness.db, {
        threadId: thread.id,
      }),
    ).toHaveLength(1);
    await expect(
      editThreadMessage(harness.deps, {
        environment,
        thread,
        payload: {
          operationId: "repro-edit",
          expectedRequestSequence: 1,
          input: [{ type: "text", text: "replacement", mentions: [] }],
        },
      }),
    ).rejects.toMatchObject({
      status: 409,
      message: "Wait for background work to finish before editing the message",
    });
    const replacement = await postEvents([
      {
        threadId: thread.id,
        event: {
          threadId: thread.id,
          type: "thread/identity",
          providerThreadId: "repro-session-after",
          scope: threadScope(),
        },
      },
    ]);
    expect(replacement.status).toBe(200);
    expect(getLastStoredProviderThreadId(harness.db, thread.id)).toBe(
      "repro-session-after",
    );
    const completions = listEvents(harness.db, { threadId: thread.id }).filter(
      (event) => event.type === "item/backgroundTask/completed",
    );
    const activity = listActiveBackgroundTaskCountsByThreadIds(harness.db, {
      threadIds: [thread.id],
    });
    console.log(
      JSON.stringify({
        editGuard: 409,
        replacement: replacement.status,
        completionCount: completions.length,
        activeCommandCount: activity[0]?.activeBackgroundCommandCount ?? 0,
      }),
    );
    expect(completions).toHaveLength(1);
    expect(activity[0]?.activeBackgroundCommandCount ?? 0).toBe(0);
  });
});

5. Root cause and limits

Daemon event persistence and dispatch persists incoming identity changes and dispatches their side effects. Server event side effects has no identity-transition background-task settlement branch. Open-task query treats an item as open until a matching terminal task event exists. Thread activity-count query similarly counts a pending command by thread and item, without filtering it against the latest provider identity. Consequently a newly stored identity does not invalidate the old activity record.

Background-task projection consumes task begin/progress/end events and only sets the completion timestamp on an end event: 

if (lifecycle.kind === "end" && message.completedAt === null) {
  message.completedAt = meta.createdAt;
}
This supports the explanation for a card retaining running state, but the actual desktop rendering and timer were not exercised.

By contrast, Successful stop settlement explicitly invokes Terminal background-task event writer after a successful runtime stop that does not retain an active turn. The existing helper writes item/backgroundTask/completed with item status interrupted and task status stopped for an unfinished task. That explicit teardown evidence is missing from the identity-only reproduction.

Message-edit activity guard is reached through Shared public edit-message route, so source does not establish a UI-only escape from the check. The introduction commit already contained the guard. Its presence is not evidence that the historical bug was recently fixed. The missing historical fact is why that particular edit was accepted despite background activity.

6. Proposed next experiment and fix boundary

Recreate the desktop Escape/edit interaction in an isolated current build with a real long-lived Claude background task. Record the edit request, the activity query immediately before the guard, the host stop/rewind result, and both provider identities. This distinguishes a guard bypass or race from a record whose task metadata was not counted.

If runtime teardown is confirmed without a terminal task event, reuse the existing settlement path at that confirmed teardown boundary, scoped to the retired session. Do not blindly settle all thread tasks on any identity announcement: initial/repeated announcements and already-batched new-session tasks need preservation tests. For the existing orphan, first verify the current stop path safely clears it in an isolated fixture; do not mutate the reporter's event store.

No fix PR: only the event-state portion is reproduced; the current edit trigger is blocked and old-runtime termination is not established by the synthetic event. The evidence does not yet justify changing runtime-lifecycle policy as an automatic simple fix. No production patch, branch, or dependency was created.
