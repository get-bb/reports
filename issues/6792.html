#6792 · Workflow native-default selection is rejected

BugPriority: MediumEffort: Mediumplugins · workflowsIssue · November 1, 2026

Trusted base: 916d684ac23d0b0de82c09cfc7553a50287d2188 on origin/main. Verdict: REPRODUCED · Root-cause confidence: high · Reproduction label: confirmed-repro.

1. TL;DR

A model can be fully discovered without offering a selectable reasoning effort. Workflows currently treats an empty list of selectable efforts as evidence that every setting is invalid, including the model's stored default. Both literal source validation and inherited runtime selection have this defect, so changing just one validator is insufficient. Two clean source checkouts reproduced the failure without a model backend; a contained Workflows repair now passes the regression cases and all 254 Workflows tests.

5. Root cause

Literal source validation unconditionally requires the requested effort to occur in the supported-effort list:

      if (
        !model.supportedReasoningEfforts.some(
          (effort) => effort.reasoningEffort === selection.reasoningLevel,
        )
      ) {
        throw new Error(
          `Unsupported reasoning level for literal workflow selection ${tupleDescription(selection)}`,
        );
      }

Runtime selection validation resolves inherited parent settings, then repeats the same membership-only check. No element of an empty list can satisfy either check, so both errors occur before a worker can run.

    if (
      !model.supportedReasoningEfforts.some(
        (effort) => effort.reasoningEffort === requested.reasoningLevel,
      )
    ) {
      throw new Error(
        `Reasoning level ${JSON.stringify(requested.reasoningLevel)} is not supported by ${requested.provider}/${requested.model}`,
      );
    }

This is a policy mismatch, not evidence of a failed model call. ACP catalog discovery intentionally returns the following when no configurable effort exists:

  if (supportedReasoningEfforts.length === 0) {
    return {
      reasoningDiscovery: "known",
      supportedReasoningEfforts: [],
      defaultReasoningEffort: "medium",
    };

The provider guide documents the known-empty meaning. Ordinary provider dispatch already drops a reasoning control that is absent from the cached model's advertised choices. Stored preference metadata therefore need not represent a provider control.

6. Proposed and tested repair

Share a small reasoning-selection policy between the two Workflows validators. Preserve advertised selectable efforts. For known-empty models, permit the catalog default as the explicit tuple value and normalize any inherited preference to that default. Continue rejecting unresolved empty discovery and explicit unsupported non-default choices. Return the normalized selection before cache identity and worker settings are computed; leave the existing downstream control-omission policy unchanged.

The tested implementation changes only the Workflows subsystem: five files, 161 additions plus 11 deletions, 172 changed text lines. It adds no dependency, generated file, storage migration, public API, wire field, or packaging change.
