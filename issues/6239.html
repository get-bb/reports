1. TL;DR

The report describes a Windows-only abort after otherwise complete plugin CLI output. Trusted main still fetches plugin contributions, executes the matching command, and forcibly exits with its returned status. A new repository-derived fixture exercised this exact entrypoint with compressed discovery and an uncompressed command result, plus uncompressed-discovery and explicit-command controls. All 60 child processes in each of two clean checkouts returned the intended status and complete output on Linux. This does not refute the Windows report: Windows and the reported affected Node runtime are unavailable, so neither the native assertion nor the runtime-version workaround is independently verified. No production change or pull request was made.

function invoke(direct) {
  return new Promise((resolveResult, rejectResult) => {
    const args = direct ? ["plugin", "run", "fixture", "execute"] : ["fixture", "execute"];
    const child = spawn(process.execPath, [join(checkout, "apps/cli/dist/index.js"), ...args], {
      cwd: checkout,
      env: {
        PATH: process.env.PATH,
        HOME: dataDir,
        USERPROFILE: dataDir,
        BB_DATA_DIR: dataDir,
        BB_SERVER_URL: baseUrl,
        BB_CLI_REEXEC: "1",
        NO_COLOR: "1",
      },
      stdio: ["ignore", "pipe", "pipe"],
    });
    let stdout = "";
    let stderr = "";
    let timedOut = false;
    const timer = setTimeout(() => {
      timedOut = true;
      child.kill();
    }, 15000);
    child.stdout.setEncoding("utf8").on("data", (chunk) => { stdout += chunk; });
    child.stderr.setEncoding("utf8").on("data", (chunk) => { stderr += chunk; });
    child.on("error", (error) => {
      clearTimeout(timer);
      rejectResult(error);
    });
    child.on("close", (code, signal) => {
      clearTimeout(timer);
      resolveResult({ code, signal, stdout, stderr, timedOut });
    });
  });
}

5. Root cause: confirmed boundary, unverified native mechanism

Contribution discovery fetches and decodes the contributions response. Command execution posts the invocation and decodes the command response. Top-level dispatch awaits that work, logs a nonzero result when needed, then calls:

process.exit(exitCode);

Server compression supports gzip above the minimum JSON size, and selects compression using the request's accepted encoding. This makes compressed discovery followed by a smaller plain command result a faithful condition, not a guarantee for every server response. Explicit plugin run also forces exit but skips discovery. Thus a fix that blames process.exit alone without accounting for request/decompression state would overstate the evidence.

Confirmed: BB forces shutdown after decoding network responses. Candidate native trigger: forced shutdown while runtime work associated with decompression remains pending. The assertion and the alleged upstream scheduling race were not observed here; their exact mechanism and Node-version thresholds remain unverified. A forced exit is not by itself evidence of a native runtime defect on this host.
