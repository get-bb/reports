Verdict: NOT REPRODUCED · Root-cause confidence: low

1. TL;DR

The report describes a desktop startup failure after a laptop lost power, followed by a successful second launch. On current trusted main, a 25-minute-old orphaned daemon lock was reclaimed immediately, and a real process killed with SIGKILL left a fresh lock that was reclaimed by the first acquisition after about 11 seconds. A live-owner control correctly rejected the competing acquisition instead of stealing its lock. These results repeated in a second clean checkout of the same commit. The supplied launcher output does not itself establish a lock-acquisition error: the launcher prints the daemon lock path for every daemon startup failure. No macOS power-loss reproduction was possible on this Linux host, so the original incident and its underlying cause remain unverified.

Complete investigation test

import { spawn, type ChildProcess } from "node:child_process";
import { once } from "node:events";
import fs from "node:fs/promises";
import os from "node:os";
import path from "node:path";
import { fileURLToPath } from "node:url";
import { afterEach, beforeEach, describe, expect, it } from "vitest";
import { acquireDaemonLock } from "../src/lock.js";

describe("issue 7563 daemon startup after an unclean owner exit", () => {
  let dataDir: string;
  let owner: ChildProcess | undefined;
  let release: (() => Promise<void>) | undefined;

  beforeEach(async () => {
    dataDir = await fs.mkdtemp(path.join(os.tmpdir(), "bb-7563-lock-"));
  });

  afterEach(async () => {
    await release?.();
    release = undefined;
    if (owner && owner.exitCode === null && owner.signalCode === null) {
      const exited = once(owner, "exit");
      owner.kill("SIGKILL");
      await exited;
    }
    owner = undefined;
    await fs.rm(dataDir, { recursive: true, force: true });
  });

  async function startOwner(): Promise<ChildProcess> {
    const lockModule = new URL("../src/lock.ts", import.meta.url).href;
    const child = spawn(
      process.execPath,
      [
        "--import",
        "tsx",
        "--input-type=module",
        "--eval",
        `import { acquireDaemonLock } from ${JSON.stringify(lockModule)};
         await acquireDaemonLock(${JSON.stringify(dataDir)});
         process.send("ready");
         setInterval(() => {}, 1000);`,
      ],
      {
        cwd: fileURLToPath(new URL("..", import.meta.url)),
        stdio: ["ignore", "ignore", "inherit", "ipc"],
      },
    );
    owner = child;
    await once(child, "message");
    return child;
  }

  it("reclaims an old orphan on the first acquisition", async () => {
    const lockDir = path.join(dataDir, "daemon.lock.lock");
    await fs.mkdir(lockDir);
    const lastHeartbeat = new Date(Date.now() - 25 * 60_000);
    await fs.utimes(lockDir, lastHeartbeat, lastHeartbeat);
    const startedAt = Date.now();
    release = await acquireDaemonLock(dataDir);
    console.log(
      `Old orphan: acquired on first call in ${Date.now() - startedAt}ms`,
    );
    expect((await fs.stat(lockDir)).mtimeMs).toBeGreaterThan(
      lastHeartbeat.getTime(),
    );
    expect(Date.now() - startedAt).toBeLessThan(5_000);
  });

  it("reclaims a SIGKILL owner's fresh lock without a second launch", async () => {
    const child = await startOwner();
    const exited = once(child, "exit");
    child.kill("SIGKILL");
    const [, signal] = await exited;
    expect(signal).toBe("SIGKILL");
    const lockDir = path.join(dataDir, "daemon.lock.lock");
    const orphan = await fs.stat(lockDir);
    const startedAt = Date.now();
    release = await acquireDaemonLock(dataDir);
    console.log(
      `Fresh SIGKILL orphan: acquired on first call in ${Date.now() - startedAt}ms`,
    );
    expect((await fs.stat(lockDir)).mtimeMs).toBeGreaterThan(orphan.mtimeMs);
    expect(Date.now() - startedAt).toBeLessThan(20_000);
  }, 30_000);

  it("does not steal a live owner's heartbeat-refreshed lock", async () => {
    const child = await startOwner();
    const startedAt = Date.now();
    await expect(acquireDaemonLock(dataDir)).rejects.toMatchObject({
      code: "ELOCKED",
    });
    console.log(
      `Live owner: correctly rejected with ELOCKED after ${Date.now() - startedAt}ms`,
    );
    expect(child.exitCode).toBeNull();
    expect(child.signalCode).toBeNull();
    expect(child.connected).toBe(true);
  }, 30_000);
});

5. Root cause

The original failure's root cause is not established. The ordinary stale-lock mechanism behaves as intended in the tested environment. The actual acquisition happens at the start of startHostDaemon, before authentication and daemon application construction. Default lock timing is:

const DAEMON_LOCK_STALE_MS = 10_000;
const DAEMON_LOCK_RETRY_INTERVAL_MS = 1_000;
const DAEMON_LOCK_ACQUIRE_RETRIES = 13;

The production acquisition passes the staleness threshold and fixed-interval retries to proper-lockfile. Inspection of the installed dependency confirms it compares the lock directory modification time against wall-clock time minus the stale interval, removes an old empty directory, and retries acquisition. The old-orphan test exercises immediate removal; the SIGKILL test exercises waiting out the remaining heartbeat lifetime. The existing compromise suite additionally covers reacquisition and yielding to a live contender.

A separate, verified diagnostic limitation explains why the supplied output is insufficient to identify this cause. The initial warning checks only whether a lock directory exists. The startup catch handles any daemon startup failure and calls the generic failure-context printer, which always emits the daemon lock path for a daemon failure:

log(" ", dim(`lock: ${args.context.daemonLockDir}`));
log(" ", dim(`logs: ${args.context.logDir}/`));

That is not proof that lock acquisition was the failing operation. The earlier ELOCKED excerpts are not contemporaneous evidence for this specific startup. A wall-clock discrepancy or another startup contender could change the outcome, but neither was observed here and neither is presented as the cause.

6. Proposed fix or next experiment

No speculative lock-removal fix. Preserving exclusivity is important: deleting a live daemon's lock would allow concurrent owners of a data directory. The control test demonstrates that the existing refusal is intentional.

On a controlled macOS reproduction, capture the startup-failure diagnostic from the same failed launch, reduced to the exception name/code/message/stack and launch timestamps. Record the lock directory modification time relative to wall-clock time and any other daemon or service starting during boot. Do not publish environment-variable objects, credentials, private paths, or unrelated runtime data. This would distinguish an actual ELOCKED failure from another child-startup error and test clock or competing-process hypotheses. Only then choose a focused regression and repair.
