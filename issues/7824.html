#7824 · Missing oomd avoidance in generated Linux services

1. TL;DR

The Linux installer writes a daemon service without an oomd avoidance preference. Both the normal user service and the root system service use the same incomplete template. Existing restart and OOM settings do not supply the missing selection preference. Executing the real installer inside its isolated test fixtures reproduced the omission in three Linux cases, and repeating the test in a second clean checkout produced the same failures. This report confirms the generated configuration gap, not an actual memory-pressure kill.

5. Root cause

The Linux service path selection chooses a user service directory and default target, switching to a system service directory and multi-user target when appropriate. Both paths then reach one shared unit heredoc. Its policy tail is:

Restart=always
RestartSec=2
OOMPolicy=continue

[Install]
WantedBy=$service_target

No ManagedOOMPreference entry is emitted. The omission is therefore shared by both scopes, not caused by systemctl, enrollment, a stale install, or a runtime race. The existing tests validate installation, restarts and unit contents, but never checked this preference: user-service owner test and root-service owner test.

The upstream systemd contract distinguishes ordinary ranking, avoidance and omission. An unspecified value defaults to none; avoid defers selection when another viable candidate exists. Extended-attribute support and cgroup ownership constrain when this preference is honored, including root ownership for swap-triggered selection. This does not establish immunity from OOM kills.

6. Proposed fix

Emit an explicit avoidance preference in the shared generated service section and retain output-boundary assertions in both scope cases. This should affect newly generated units; no automatic retrofit of existing installations is demonstrated. Because an open pull request already addresses and links this issue, this investigation makes no production repair and opens no duplicate PR.
