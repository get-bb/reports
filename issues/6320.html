#6320 · Runtime SDK dependencies are incorrectly normalized as development-only

BugPriority: MediumEffort: LowpluginscliIssue #63202026-10-26

Trusted main base: 3540a699e29034b53da32bb7efa6f5b4055209eb

Verdict: REPRODUCED · Root-cause confidence: high · reproduction label: confirmed-repro

1. TL;DR

The SDK pinning command treats every SDK runtime dependency as an authoring-only dependency. A plugin that needs a real SDK host export builds successfully with its SDK installed, but pin synchronization moves that dependency to devDependencies. In a clean production layout without development packages, the same host build then fails while the actual source CLI's types --check exits successfully. This is reproduced for both the provider-bridge subpath and the native-roots host contract on trusted main, and repeated in a second clean checkout by the same investigator. Restoring the existing local SDK makes both builds pass again.

async function installLocalSdk(directory) {
  await mkdir(join(directory, "node_modules/@get-bb"), { recursive: true });
  await symlink(sdkRoot, join(directory, "node_modules/@get-bb/plugin-sdk"), "dir");
}

function cliCheck(directory) {
  const result = spawnSync(process.execPath, ["--conditions=source", "--import", join(checkout, "node_modules/tsx/dist/loader.mjs"), join(checkout, "apps/cli/src/index.ts"), "plugin", "types", "--check", directory], {
    encoding: "utf8",
    env: { ...process.env, BB_CLI_REEXEC: "1", BB_CLI_ERROR_LOG: "0", BB_SERVER_URL: "http://127.0.0.1:1" },
  });
  console.log(`types --check exit=${result.status}`);
  console.log((result.stdout + result.stderr).trim());
  assert.equal(result.error, undefined);
  return result.status;
}

try {
  for (const [name, modulePath, symbol] of [
    ["bridge", "@get-bb/plugin-sdk/provider-bridge", "PROVIDER_BRIDGE_EXPORT_NAME"],
    ["native-roots", "@get-bb/plugin-sdk/host", "experimental_nativeRootsHostContract"],

    console.log(`CASE ${name}; sdk=${sdkVersion}`);
    const directory = join(scratch, name);

      name: `bb-plugin-contract-${name}`,

      assert.equal(synchronized.dependencies?.["@get-bb/plugin-sdk"], sdkVersion);
      continue;
    }
    assert.equal(checkBefore, 1);

    assert.equal(cliCheck(directory), 0);

5. Root cause

Normalization has no runtime-dependency exception

planManifest, lines 320–341 decides whether to move the SDK solely from its declaration in dependencies. It does not inspect entries or imports. An exact version does not protect a runtime declaration from being moved.

  const declaredPin = readSdkPinFrom(manifest);
  const pin =
    declaredPin.version === sdkVersion
      ? null
      : { from: declaredPin.version, to: sdkVersion };
  const movedFromDependencies = declaredPin.inDependencies;
  if (pin !== null || movedFromDependencies) {
    if (movedFromDependencies) {
      const deps = asRecord(manifest.dependencies);
      delete deps["@get-bb/plugin-sdk"];
      if (Object.keys(deps).length === 0) {
        delete manifest.dependencies;
      } else {
        manifest.dependencies = deps;
      }
    }
    manifest.devDependencies = insertDependency(
      asRecord(manifest.devDependencies),
      "@get-bb/plugin-sdk",
      sdkVersion,
    );
  }

setPluginSdkPin is the shared mutation/dry-run path. The CLI check and write actions use this planner; a null plan is treated as success without checking whether a required runtime SDK is present.

Production installation and bundling disagree with that assumption

The Git production installer omits development packages:

  await runInstallCommand("npm", [
    "install",
    "--prefix",
    rootDir,
    "--ignore-scripts",
    "--omit=dev",
    "--omit=optional",
    "--no-audit",
    "--no-fund",
  ]);

The host builder SDK shim boundary supplies the root SDK shim and only limited host fallbacks; it does not supply arbitrary provider-bridge runtime code. The native-roots contract is outside the host fallback export set, so its absence produces the dependency diagnostic observed above. Server SDK subpath resolution likewise bundles real subpath implementations from the plugin's own SDK rather than treating all subpaths as host-provided runtime.

The authoring guide's runtime dependency exception explicitly distinguishes these real runtime imports from stub-only host entries. The bug is in generic manifest normalization, not a missing provider registration or invalid import. Git history attributes the unconditional move to e6b7724fae; later edits at the recorded main base still retain it.

6. Proposed fix and safety decision

Make SDK dependency placement consistent with the builder's runtime-import contract: preserve or select dependencies for real runtime SDK subpaths, while retaining devDependencies for authoring-only/stubbed usages. Use one placement policy for check and write, cover re-exports and transitive local imports, and add both runtime-import and stub-only controls. A builder-level fallback to BB's SDK is a different packaging/design choice and should not be introduced opportunistically.

No automatic fix PR: Repairing SDK dependency placement changes plugin dependency packaging, which this SlopCop rule explicitly excludes from its simple-fix allowance. No production change, dependency change, branch, push, or PR was made in get-bb/bb. The target repository's diff is empty (0 changed text lines); no binary changes exist. No open PR linking #6320 was found in issue cross-references or a repository open-PR search.
