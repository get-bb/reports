#6169 · Account-pool threshold excludes upstream-allowed capacity

BugPriority: MediumEffort: Mediumprovidersprovider-claude-codeGitHub issue2026-10-23

Trusted base: 1e80ca7b44bccd06c6da75ed9ca6ba497bd380f5. Verdict: REPRODUCED · Root-cause confidence: high · reproduction label: confirmed-repro.

1. TL;DR

The actual Account Pooler plugin can return its own 429 without contacting an account whose upstream quota status remains allowed at 99% utilization. At the default 98% threshold, both routing and retry availability classify that account as exhausted. In a two-account synthetic reproduction, the pool instead advertises a two-hour reset belonging to the other, genuinely rejected account. Changing only the threshold to 1 immediately makes the first account routable and retry availability ready. This reproduces the routing mechanism, not the reporter's private incident timeline; importantly, current configuration documentation explicitly describes a hard cutoff, so changing that policy is not a decision-free automated fix.

5. Root cause

activeWindow uses rejection or utilization at/above the configured threshold:

status?.toLowerCase() === "rejected" ||
(utilization !== null && utilization >= threshold)

An allowed status does not override that utilization comparison. Selection filters shared and model-family exhaustion before constructing candidates; extra usage is its only exhaustion bypass. Therefore no merely above-threshold account reaches the later candidate preference and affinity logic. Account status reports the same state as exhausted.

accountAvailability evaluates the same configured-threshold predicate. For each exhausted account it computes a blocking reset, then returns the earliest account availability. In this synthetic pool, the earliest is the genuinely rejected account's two-hour reset, despite the other account continuing to serve when the threshold is raised. noEligibleResponse propagates that result to the 429 text and retry-after.

The OAuth usage-refresh-before-refusal path at refreshExhaustedUsage and the request loop does not change this eligibility rule. This reproduction uses API-key test accounts with observed headers, so it isolates routing from OAuth polling and cannot by itself verify a live usage API incident.

Policy caveat: configuration documentation explicitly says this is the fraction at which an account stops receiving matching traffic. Routing guidance describes advancement to the next eligible account; it does not explicitly promise that above-threshold accounts remain eligible. The behavior is confirmed, but a soft switch point would be a deliberate policy change rather than a mechanical correction to an already specified fallback.

6. Proposed fix and automation decision

First decide whether the pool-wide threshold is a hard reserve or a soft routing preference, and how that interacts with paid extra usage. If soft semantics are chosen, keep below-threshold accounts preferred, then permit otherwise allowed, non-held, non-errored accounts before refusing. Share the resulting eligibility contract with retry availability and account status; maintain hard provider rejections, usage restrictions, model-family limits, and reset expiration. Do not simply remove the threshold comparison everywhere, because that would erase early switching.

No pull request opened. Although a local implementation might fit the line/file limits, changing documented hard-cutoff/reserve semantics and fallback ordering requires a product decision. The automation's simple-fix conditions therefore fail before production edits. No branch was pushed and no dependency, protocol, persisted data, or production source changed.

The regression was designed from trusted repository routing code rather than copied from issue code. Existing tests do not exercise the state where every enabled account is past the preference threshold without extra usage. It requires no new production seam.
