#7573 · Pi child exit leaves the next turn on a closed session

BugPriority: MediumEffort: Lowproviders · provider-pi · confirmed-reproGitHub issue

2026-11-14 · trusted origin/main da3e60b81d560e114a2bec724bb59c997aaaae7f

Verdict: REPRODUCED (provider bridge boundary) · Root-cause confidence: high

1. TL;DR

A Pi child can exit cleanly while the surrounding bb provider bridge stays alive. bb reports that exit, but a subsequent turn in the same thread is sent to the already-closed session and fails with No active Pi session. The session records its closed state correctly; the bridge reuses it without checking that state. A deterministic regression using the repository's existing fake Pi child reproduced the exact follow-up error in two clean checkouts of the same trusted main commit. Reusing the existing session-replacement path when the session is closed makes the regression pass without replaying the failed turn.

plugins/provider-pi/src/bridge/bridge.recovery.test.ts

import { afterEach, beforeEach, expect, it } from "vitest";
import { z } from "zod";
import {
  FULL_PERMISSION_OPTIONS,
  type FakePiBridgeHarness,
  startFakePiBridge,
} from "./test-support.js";

let harness: FakePiBridgeHarness;

beforeEach(async () => {
  harness = await startFakePiBridge({
    prefix: "bb-pi-recovery-",
    initialize: true,
    processLog: true,
  });
});

afterEach(async () => {
  await harness.teardown();
});

it("resumes the same provider thread on the next turn after a clean child exit", async () => {
  const threadId = "thr_recovery";
  const started = await harness.startThread(threadId);
  const { providerThreadId } = z
    .object({ providerThreadId: z.string() })
    .parse(started.result);

  await harness.request(2001, "turn/start", {
    threadId,
    providerThreadId,
    clientRequestId: "creq_ab23456789",
    input: [{ type: "text", text: "/die", mentions: [] }],
    options: FULL_PERMISSION_OPTIONS,
  });
  await harness.waitForDelta(
    threadId,
    (delta) => delta.kind === "turn.boundary" && delta.status === "failed",
  );
  await harness.waitFor(
    () => harness.runningChildPids().length === 0,
    "the original Pi child to exit",
  );
  const before = harness.deltasOf(threadId).length;
  const messagesBefore = harness.messages.length;

  const response = await harness.request(2002, "turn/start", {
    threadId,
    providerThreadId,
    clientRequestId: "creq_cd23456789",
    input: [{ type: "text", text: "continue after exit", mentions: [] }],
    options: FULL_PERMISSION_OPTIONS,
  });
  expect(response.error).toBeUndefined();
  expect(response.result).toMatchObject({ threadId });
  await harness.waitForDelta(
    threadId,
    (delta) => delta.kind === "turn.boundary" && delta.status === "completed",
    before,
  );
  expect(harness.readProcessLog().spawned).toHaveLength(2);
  expect(harness.messages.slice(messagesBefore)).toContainEqual(
    expect.objectContaining({
      method: "thread/identity",
      params: expect.objectContaining({ threadId, providerThreadId }),
    }),
  );
}, 90_000);

This is a lifecycle-reconciliation defect in the Pi bridge. The underlying process can exit successfully; no model failure, database state, extension-specific parsing error, or daemon-protocol change is required to trigger the downstream recovery failure.

6. Proposed fix and regression evidence

Expose the existing closed state internally and include it in both reuse checks. When closed, call the existing rebuildThreadSession path with the saved construction options and existing provider-thread identity. That path resumes the same session file, retires the old child, emits the established replacement notifications, and sends only the new user input. It does not automatically retry the failed prompt.

A local patch in three files makes the focused regression pass. It changes 87 text lines total (84 additions + 3 deletions): 18 production lines and 69 regression-test lines. It adds no dependency, generated file, stored-data change, or public protocol/schema change.
