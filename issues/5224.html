1. TL;DR

When all pool accounts are exhausted, the proxy correctly returns HTTP 429 and a Retry-After delay. Its JSON error message omits the known recovery time. An existing two-account HTTP-boundary test demonstrates this for both Claude and Codex. The failure occurs in the shared hub, not the account-switching logic. A small diagnostic-only fix can reuse the timestamp already calculated for the header.

5. Root cause

AccountPoolHub.noEligibleResponse collects enabled accounts without credential errors, obtains each account's blocking reset, combines it with any hold, and selects the earliest future timestamp. It computes the Retry-After delay from that value, but passes a constant message to the provider error response adapter. The timestamp never reaches the human-readable diagnostic.

blockingResetAt chooses the latest blocking window within each account; the hub then chooses the earliest usable account. Unknown reset times are deliberately excluded. The fix must not invent an availability time from the one-second fallback header.

The canonical regression owner is the existing provider-parameterized exhaustion and session-affinity test. Previously it consumed and discarded the error body, so a correct status and header masked the missing diagnostic.

6. Proposed fix

Preserve the existing message when no reset is known. Otherwise append the earliest known UTC ISO timestamp and the already computed rounded seconds. Describe availability as expected rather than guaranteed. Keep routing, HTTP status, header values, JSON shape, stored data, and authentication unchanged. Extend the existing regression owner instead of introducing a private test seam.
