#7281 · Thread deletion yields between database purge batches

2026-11-09 · Bug · High priority · Medium effort · threads, perf · base 17c2018ab988e2ed49140821e5a8c854a8f3d3b8

Verdict: ALREADY FIXED on trusted main. Root-cause confidence: high for the historical synchronous cascade and its removal from finalization. This is not a claim about which published installer includes the fix.

1. TL;DR

A large synchronous SQLite cascade can monopolize the server's JavaScript thread. The reported direct cascade at thread finalization is no longer present on the tested main commit: finalization queues a persistent purge instead. PR #7184 merged on November 6, 2026 at 22:58:19 UTC, before this issue was created on November 9. Two fresh-checkout runs with 16,384 synthetic events each showed timers executing while only part of the event history had been deleted. No new production patch or duplicate PR is warranted.

Authored test

import { performance } from "node:perf_hooks";
import { expect, it } from "vitest";
import { sql } from "drizzle-orm";
import { getThread } from "@bb/db";
import { threadScope } from "@bb/domain";
import { threadPurgeSweep } from "../../src/services/threads/thread-purge.js";
import {
  seedHostSession,
  seedProjectWithSource,
  seedStoredEvent,
  seedThread,
} from "../helpers/seed.js";
import { withTestHarness } from "../helpers/test-app.js";

it("services timers between partial deletions of a large deleted thread", async () => {
  await withTestHarness(async (harness) => {
    const { host } = seedHostSession(harness.deps);
    const { project } = seedProjectWithSource(harness.deps, { hostId: host.id });
    const thread = seedThread(harness.deps, { projectId: project.id });
    const totalEvents = 16_384;
    harness.db.transaction(() => {
      for (let sequence = 1; sequence <= totalEvents; sequence++) {
        seedStoredEvent(harness.deps, {
          data: { text: "synthetic retention measurement ".repeat(16) },
          scope: threadScope(),
          sequence,
          threadId: thread.id,
          type: "thread/identity",
        });
      }
    });
    const countEvents = () =>
      harness.db.get<{ count: number }>(
        sql`SELECT count(*) AS count FROM events WHERE thread_id = ${thread.id}`,
      )?.count ?? 0;
    const requestStartedAt = performance.now();
    const response = await harness.app.request(`/api/v1/threads/${thread.id}`, {
      method: "DELETE",
      headers: { "content-type": "application/json" },
      body: JSON.stringify({ childThreadsConfirmed: false }),
    });
    const requestMs = performance.now() - requestStartedAt;
    expect(response.status).toBe(200);
    expect(getThread(harness.db, thread.id)?.deletedAt).toEqual(expect.any(Number));
    expect(countEvents()).toBe(totalEvents);
    expect((await harness.app.request(`/api/v1/threads/${thread.id}`)).status).toBe(404);
    let timerTicks = 0;
    let partialDeletionTicks = 0;
    let maximumGapMs = 0;
    let previousTickAt = performance.now();
    const timer = setInterval(() => {
      const now = performance.now();
      maximumGapMs = Math.max(maximumGapMs, now - previousTickAt);
      previousTickAt = now;
      timerTicks++;
      const remaining = countEvents();
      if (remaining > 0 && remaining < totalEvents) partialDeletionTicks++;
    }, 1);
    const purgeStartedAt = performance.now();
    try {
      await threadPurgeSweep(harness.deps).run(harness.deps, Date.now());
    } finally {
      clearInterval(timer);
    }
    expect(partialDeletionTicks).toBeGreaterThan(0);
    expect(countEvents()).toBe(0);
    expect(getThread(harness.db, thread.id)).toBeNull();
    console.log(JSON.stringify({
      totalEvents,
      requestMs: Math.round(requestMs),
      purgeMs: Math.round(performance.now() - purgeStartedAt),
      timerTicks,
      partialDeletionTicks,
      maximumGapMs: Math.round(maximumGapMs),
    }));
  });
}, 30_000);

5. Root cause and existing repair

The trusted merge diff for 72323b5ebc27c0aa63657c5fa4b25a085a69f42d replaces the historical direct deleteThread call with requestThreadPurge. The low-level deleteThread primitive still performs a synchronous parent DELETE; invoking it before removing a large child history is the historical root cause. This investigation did not execute the older implementation or validate the issue's exact timings.

  1. Finalization waits for storage deletion and provider work, then persists a purge request rather than deleting the history.
  2. thread_purges stores requests durably. deleteThreadPurgeBatch caps events by row count and payload bytes, then removes bounded search/history/attachment rows.
  3. Purge transactions use at most 64 event rows / 512 KiB of event data, or 128 rows from the other batched tables, before final parent deletion.
  4. The sweep loop targets 10 ms slices and awaits a timer between slices. It rests longer while clients or running threads exist. Periodic scheduling runs this as a background sweep.

These are bounded-work heuristics, not a strict maximum transaction duration. Oversized individual events, other cascade tables, filesystem stalls, or WAL checkpoint work can still cost more than the slice target. The synthetic run does not prove that all disk-heavy deletion workloads are stall-free.

6. Fix proposal and PR decision

Keep the existing paced-purge implementation. No new PR: the reported single-cascade finalization path was already replaced by merged PR #7184, and the defect is not reproduced on trusted main. If stalls persist on a build containing that commit, the next experiment is a scrubbed disk-backed database with search rows and per-transaction/checkpoint timings. FTS layout changes would need separate migration and product review, not an automatic simple fix.
