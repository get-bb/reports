#2770 · Plugin file opener props omit saved line ranges

Bug Medium Effort: Medium plugins ui open on GitHub 2026-08-31 · base f4bbc2fe81a9b7639ff9a7396e172bddd89109e4

Verdict: REPRODUCED · Root-cause confidence: high

1. TL;DR

A file opener plugin does not receive the saved line range for its file tab. A direct mount test reproduced this loss in two clean clones. The app keeps the range in the tab owner. The plugin contract and mount omit the range. Monaco cannot select or reveal a line that it does not receive.

Full reproduction test

// @vitest-environment jsdom

import { cleanup, render, screen } from "@testing-library/react";
import { afterEach, expect, it } from "vitest";
import type { PluginFileOpenerProps } from "@get-bb/plugin-sdk";
import { createPluginPanelFixedPanelTab } from "@/lib/fixed-panel-tabs-state";
import {
  resetPluginSlotStoreForTest,
  setPluginSlotRegistrations,
  type PluginRegistrationSet,
} from "@/lib/plugin-slots";
import { PluginPanelTabContent } from "./PluginPanelActions";

type ExpectedFileOpenerProps = PluginFileOpenerProps & {
  lineRange?: {
    startLineNumber: number;
    endLineNumber: number;
  } | null;
};

function registrationSet(
  overrides: Partial<PluginRegistrationSet>,
): PluginRegistrationSet {
  return {
    homepageSections: [],
    settingsSections: [],
    navPanels: [],
    threadPanelActions: [],
    composerCustomizations: [],
    sidebarFooterActions: [],
    fileOpeners: [],
    messageDirectives: [],
    ...overrides,
  };
}

afterEach(() => {
  cleanup();
  resetPluginSlotStoreForTest();
});

it("passes the owner's line range to a file opener", () => {
  function FileOpenerProbe({ lineRange }: ExpectedFileOpenerProps) {
    return (
      <output data-testid="file-opener-line-range">
        {JSON.stringify(lineRange ?? null)}
      </output>
    );
  }

  setPluginSlotRegistrations(
    "notes",
    registrationSet({
      fileOpeners: [
        {
          id: "editor",
          title: "Notes editor",
          extensions: ["md"],
          component: FileOpenerProbe,
        },
      ],
    }),
  );

  const tab = {
    ...createPluginPanelFixedPanelTab({
      actionId: "file-opener:editor",
      paramsJson: JSON.stringify({
        path: "notes/todo.md",
        source: {
          kind: "workspace",
          threadId: null,
          environmentId: "env_1",
          projectId: null,
        },
      }),
      pluginId: "notes",
      title: "todo.md",
    }),
    fileOpenerOwner: {
      kind: "workspace-file-preview" as const,
      environmentId: "env_1",
      projectId: null,
      tab: {
        lineRange: { startLineNumber: 7, endLineNumber: 9 },
        path: "notes/todo.md",
        source: { kind: "working-tree" as const },
        statusLabel: null,
      },
      threadId: null,
    },
  };

  render(
    <PluginPanelTabContent
      tab={tab}
      context={{ kind: "new-thread", projectId: null }}
      fileOpenerOriginal={<div>native preview</div>}
    />,
  );

  expect(screen.getByTestId("file-opener-line-range").textContent).toBe(
    '{"startLineNumber":7,"endLineNumber":9}',
  );
});

5. Root cause

The app stores the range in the file-opener owner. The public opener props define only the path, source, and native preview.

export interface PluginFileOpenerProps {
  path: string;
  source: PluginFileOpenerSource;
  Original: ComponentType;
  experimental_Original?: ComponentType;
}

The plugin mount then sends only those values.

<opener.component
  path={file.path}
  source={file.source}
  Original={BoundOriginal}
  experimental_Original={deprecatedOriginalAlias(BoundOriginal)}
/>

The tab state still contains the range. Therefore, the mount boundary loses the value.

The Monaco opener creates its editor without a position or reveal call. The visible navigation failure follows from the missing input.

6. Proposed fix

  1. Add one experimental line-range contract to the plugin SDK.
  2. Send the owner range through the plugin mount.
  3. Apply the range after Monaco creates its model.
  4. Apply later range changes to the current editor.
  5. Add mount and Monaco tests for initial and later navigation.
  6. Update the API audit document and the plugin API map.

This fix needs at least seven files and a public SDK contract decision. It does not meet the simple-fix rule.
