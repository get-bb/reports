#8102 · Unbounded plugin file loading serializes startup

BugHighEffort: MediumpluginsGitHub issue2026-11-24 · base 718e4e738bbb1eff83562715dbe14462012c6c0e

Verdict: REPRODUCED · Root-cause confidence: high for the shared loader failure, not the untested macOS environment.

1. TL;DR

A plugin whose server artifact never supplies bytes can prevent every later plugin, including a builtin, from starting. The configured load timeout only wraps the plugin factory: file hashing, build work and module loading occur before it. Startup awaits each plugin in identifier order, so one pending read holds up the whole pass. Safe mode persists its setting but waits for the same plugin lifecycle lock and cannot finish until the pending read returns. Both clean-checkout runs reproduced this with real filesystem I/O and a real migrated SQLite database; releasing the blocked file allowed the later builtin and safe-mode operation to finish.

5. Root cause

  1. hashFile consumes a createReadStream until EOF without a timeout or abort signal: 
    for await (const chunk of createReadStream(path)) {
  byteLength += chunk.byteLength;
  hash.update(chunk);
}
  2. resolveServerEntry hashes a compatible external prebuilt server artifact before import. The test's metadata matches the running SDK, and no writer supplies bytes to the artifact stream.
  3. The load sequence awaits entry resolution and module evaluation before calling runFactoryTimeBoxed. Its deadline cannot cover an earlier wait: 
    await raceTimeout(
  Promise.resolve(factory(api)),
  loadTimeoutMs,
  `load timed out after ${loadTimeoutMs}ms`,
);
  4. loadAll sorts every installed row by identifier and awaits each lifecycle lock in sequence, with no builtin-first partition: 
    const rows = listInstalledPlugins(deps.db).sort((a, b) =>
  a.id.localeCompare(b.id),
);
for (const row of rows) {
  if (loaded.has(row.id)) continue;
  await withLifecycleLock(row.id, () => loadOne(row));
}
  5. setSafeMode writes its setting before waiting for each affected plugin's same lifecycle lock. That explains the persisted flag and pending operation. The keyed lock waits for the previous operation's promise; it does not cancel it.

Releasing the artifact in both runs let startup complete, the builtin run, and safe mode finish with the external plugin disabled. This countercheck distinguishes the file-read stall from a broken builtin, missing SDK or database setup failure.

6. Proposed fix and simple-fix decision

Use a bounded, cancellable preparation stage for plugin filesystem/build work, with explicit ownership and cleanup of abandoned candidates. Keep unrelated plugin startup from awaiting a stalled user plugin, while preserving intentional registration ordering. Safe mode must invalidate or stop an in-progress candidate rather than just queue behind it. In-process synchronous module reads/evaluation also need an explicit containment decision: ordinary promise deadlines cannot interrupt a synchronous stall.

No automatic fix PR: this does not meet the no-architecture-decision simple-fix gate. A timeout-only race would stop waiting but leave the candidate running; the continuation can still publish registrations and install a loaded candidate after timeout or safe-mode changes. Parallel startup alone does not bound file I/O or release the blocked lifecycle lock, and rejecting just named pipes would not cover ordinary files stalled in a filesystem provider. A safe cancellation/containment contract and load-order policy are required before choosing the patch. No production files were changed and no fix branch was pushed.

No open PR linked to this issue was found in its GitHub timeline or open-PR number search during this investigation.
