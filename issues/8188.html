#8188 · Failed availability refresh is cached as an unavailable parent

Bug Medium priority Low effort providers confirmed-repro

GitHub issue · 2026-11-25 · trusted base fb045a046653cc127656ca3c7243d44ae4c94f3f

Verdict: REPRODUCED · Root-cause confidence: high

1. TL;DR

A child bb asks its parent account pool whether it can serve a provider. One timed-out availability request or one HTTP 503 replaces a previously positive answer with an all-false value. That error-derived value is cached for the same 30 seconds as a successful answer, so even a healthy parent is not queried again during that interval. Two real-HTTP reproductions on unchanged main demonstrate the loss and recovery; the availability clock is advanced through the existing injection while the HTTP timeout uses real time. No real Claude session, login failure, or retry-manager action was executed.

5. Root cause

The production defaults set a 30,000 ms availability TTL and 2,000 ms HTTP timeout. load and get collapse transport failures, unsuccessful statuses, and malformed payloads into the same UNAVAILABLE_POOL value used for a legitimate negative answer, then cache that value without distinguishing a failed read from authoritative availability.

  async get(): Promise<PoolAvailability> {
    const cached = this.cached;
    if (cached !== null && cached.expiresAt > this.options.now()) {
      return cached.value;
    }
    const value = await this.load();
    const ttlMs = this.options.ttlMs ?? DEFAULT_AVAILABILITY_TTL_MS;
    this.cached = { value, expiresAt: this.options.now() + ttlMs };
    return value;
  }

  private async load(): Promise<PoolAvailability> {
    try {
      const response = await this.options.fetch(
        `${this.options.parent.baseUrl}${AVAILABILITY_PATH}`,
        {
          method: "GET",
          headers: { [HUB_TOKEN_HEADER]: this.options.parent.token },
          signal: AbortSignal.timeout(AVAILABILITY_TIMEOUT_MS),
        },
      );
      if (response.ok) {
        return poolAvailabilitySchema.parse(await response.json());
      }
      this.options.onError?.(
        new Error(`parent availability returned HTTP ${response.status}`),
      );
    } catch (error) {
      this.options.onError?.(error);
    }
    return UNAVAILABLE_POOL;
  }

This loss of information is the underlying cause: the cache cannot tell “the parent said no” from “the child could not read the parent.” The next expiry is computed after the failed load completes, extending the interruption another full TTL beyond the timeout.

canServe returns this provider flag when proxying a parent. contributeFor uses it to decide whether to contribute routing configuration; false takes the non-serving branch. This statically explains missing pool routing, but does not itself prove the exact message or retry outcome of a real provider.

6. Proposed fix

Distinguish unsuccessful refreshes from valid availability responses, retain a bounded last successful answer through transient failures, and retry unsuccessful reads sooner than the normal successful TTL. Preserve an explicit negative response immediately, fail closed without a known successful answer, and bound staleness for a sustained outage. Error classification, especially authorization rejection versus transient transport errors, needs explicit tests. Increasing the HTTP deadline alone cannot fix caching one failure for 30 seconds.

No production patch or duplicate PR was created: GitHub metadata already links open PR #8187 to this issue.

It changes only parent-pool.ts and its existing tests, introducing last-success retention, a shorter failed-read retry interval, a bounded failure grace period, and a longer read deadline. Those changes address the reproduced information-loss and negative-cache mechanism in principle.

  • Coverage concern, medium: in the diff's ParentAvailability.get/load path, all failed reads share the same retained-answer treatment, including authorization rejection and invalid payloads; the added tests exercise timeout/503 rather than a previously successful parent later rejecting access. Verify those fail-closed semantics before landing.
  • Outage recovery consideration, low: after the grace expires, unavailable is cached for the normal TTL; a recovered parent can still remain unavailable for up to another TTL. This is visible in the diff and should be an intentional tested policy.
  • Verdict: plausibly addresses the reproduced cause; runtime correctness of that PR is not verified. Tests run here: only this report's two failing real-HTTP cases on trusted main, plus main's 13 passing existing tests.
