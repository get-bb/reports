#7770 · SDK Markdown omits message-renderer context

BugPriority: MediumEffort: Mediumplugins · uiGitHub issue2026-11-18 · base 48c3a78488667fde6883d13da7ef54f8175b4671

Verdict: REPRODUCED · Root-cause confidence: high · reproduction label: confirmed-repro.

1. TL;DR

A plugin displaying source with the SDK Markdown component cannot reproduce the inline plugin UI available in an assistant message. Both renderers receive the same text and registered slot implementations in this reproduction, but only the assistant mounts the custom fence and directive components. The SDK wrapper does not establish a code-fence host or supply a message-directive configuration, and its public props cannot supply the required message identity. This is a host rendering integration gap, not a failure to parse the source or register a plugin. Two fresh checkouts of trusted main reproduce both failures with real host components; no linked pull-request code was executed.

// @vitest-environment jsdom

import { cleanup, render, screen } from "@testing-library/react";
import { afterEach, describe, expect, it } from "vitest";
import { MemoryRouter } from "react-router-dom";
import { PluginMarkdown } from "./PluginMarkdown";
import { RouteNavigationProvider } from "../ui/app-route-anchor";
import {
  buildCodeFenceRendererRegistry,
  CodeFenceRendererRegistryProvider,
} from "../ui/markdown-code-fence-renderers";
import {
  buildMessageDirectiveRegistry,
  MessageDirectiveRegistryProvider,
} from "../ui/markdown-message-directives";
import { ConversationMessageContent } from "../thread/timeline/ConversationMessageContent";
import {
  resetPluginSlotStoreForTest,
  setPluginSlotRegistrations,
} from "@/lib/plugin-slots";
import { makePluginRegistrationSet } from "@/test/fixtures/plugins";

afterEach(() => {
  cleanup();
  resetPluginSlotStoreForTest();
});

describe("issue 7770: SDK and assistant rendering parity", () => {
  it.each([
    { kind: "fence", content: "```repro-card\ncard payload\n```" },
    { kind: "directive", content: '::repro-badge{value="ready"}' },
  ])("mounts a registered $kind in SDK Markdown", ({ kind, content }) => {
    const registrations = makePluginRegistrationSet({
      codeFenceRenderers: [{
        id: "card",
        pluginId: "repro-7770",
        generation: 1,
        languages: ["repro-card"],
        component: ({ code }) => <strong>Mounted fence: {code}</strong>,
      }],
      messageDirectives: [{
        id: "repro-badge",
        pluginId: "repro-7770",
        generation: 1,
        component: ({ attributes }) => <strong>Mounted directive: {attributes.value}</strong>,
      }],
    });
    setPluginSlotRegistrations("repro-7770", registrations);
    const fences = buildCodeFenceRendererRegistry(registrations.codeFenceRenderers);
    const directives = buildMessageDirectiveRegistry(registrations.messageDirectives);
    const expected = kind === "fence" ? "Mounted fence: card payload" : "Mounted directive: ready";
    const view = render(
      <MemoryRouter>
        <RouteNavigationProvider>
          <CodeFenceRendererRegistryProvider registry={fences}>
            <MessageDirectiveRegistryProvider registry={directives}>
              <ConversationMessageContent
                role="assistant"
                attachments={null}
                id="message-repro-7770"
                threadId="thread-repro-7770"
                turnId="turn-repro-7770"
                projectId="project-repro-7770"
                streaming={false}
                showActions={false}
                mobileActionDisplay="inline"
                text={content}
                timestamp={0}
              />
            </MessageDirectiveRegistryProvider>
          </CodeFenceRendererRegistryProvider>
        </RouteNavigationProvider>
      </MemoryRouter>,
    );
    expect(screen.getByText(expected)).toBeTruthy();
    view.unmount();
    const sdk = render(
      <MemoryRouter>
        <RouteNavigationProvider>
          <CodeFenceRendererRegistryProvider registry={fences}>
            <MessageDirectiveRegistryProvider registry={directives}>
              <PluginMarkdown content={content} />
            </MessageDirectiveRegistryProvider>
          </CodeFenceRendererRegistryProvider>
        </RouteNavigationProvider>
      </MemoryRouter>,
    );
    console.log(`SDK ${kind} actual: ${sdk.container.textContent}`);
    expect(screen.getByText(expected)).toBeTruthy();
  });
});

5. Root cause

  1. ThreadTimelineRows builds both registries from the slot store and provides them around timeline rows.
  2. The assistant assembles message directives with message identity, passes them into MarkdownPreview, and mounts CodeFenceRendererHost.
  3. PluginMarkdown, including its document branch, renders MarkdownPreview without a directive configuration and without establishing a fence host. In a standalone plugin panel, global slot registration alone is insufficient. The reproduction deliberately gives it even the registry providers, so missing registrations cannot explain the result.
  4. useCodeFenceLanguages reads only the active host:
    const registry = useContext(CodeFenceHostContext)?.registry;
return registry === undefined || registry.size === 0 ? null : registry;
    No host means ordinary code-block rendering. Separately, MarkdownPreview disables directive mounts when its explicit configuration is absent:
    if (messageDirectives === undefined) {
  return null;
}
    That is why the directive remains literal text rather than a plugin mount.
  5. The deeper API gap: MarkdownProps cannot identify a message, while the plugin message contract requires id, threadId, and explicit nullable turnId/projectId. Blindly installing registry providers cannot safely fabricate this context.

6. Proposed fix and simple-fix decision

Use a deliberate opt-in message-context contract for SDK Markdown and share the timeline's registry, host, and directive assembly path rather than implementing a second renderer. Validate runtime message context at the SDK boundary, preserve ordinary-document behavior without it, and define file-opening and streaming semantics explicitly. Cover both SDK and assistant surfaces, malformed context, and the no-context fallback. This is a public API/product-contract decision, not merely a local prop forwarding repair.

No new fix PR: open PR #7771 already explicitly links this issue. The autopilot duplicate-PR guard stops the fix path before branch creation. Moreover, a robust message-identity repair would change the public SDK contract and need a product decision, outside the simple-fix criteria. No production fix was committed, pushed, or executed, so no fix line-count or green-after claim is made.
