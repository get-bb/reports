1. TL;DR

The earlier PR gate could close an otherwise trusted collaborator's pull request for lacking a linked issue, even when its branch lived in the target repository. Contributor approval accepted COLLABORATOR, but the separate linked-issue exemption recognized only OWNER and MEMBER and ignored where the branch lived. Main now adds a head-repository inequality to the issue-check guard, landed through PR #6197 on October 23, 2026 at 23:34:05 UTC. The actual workflow shell passes nine behavior cases in each of two clean checkouts of that main commit. Removing only the added condition in a disposable negative control makes the same-repository regression case fail with closure, an issue query, and a needs-issue label.

sleep() { return 0; }

5. Root cause

The older approval predicate treated COLLABORATOR as trusted, but the older linked-issue predicate exempted only OWNER and MEMBER (plus bots and synchronize events). Consequently, an opened collaborator PR with no closing issue acquired issue_missing=yes regardless of branch origin. The final gate decision then added needs-issue, commented, and closed it even though approval passed.

The fix at main line 67 is:

if [ "$EVENT_ACTION" != "synchronize" ] && [ "$PR_AUTHOR_TYPE" != "Bot" ] && [ "$PR_ASSOCIATION" != "OWNER" ] && [ "$PR_ASSOCIATION" != "MEMBER" ] && [ "$HEAD_REPO" != "$GITHUB_REPOSITORY" ]; then

A same-repository head now skips only the linked-issue branch. The original trusted-author check and maintainer-edit check remain separate. The edited-event recovery path also benefits: a previously closed trusted same-repository PR can have needs-issue removed and be reopened on edit.
