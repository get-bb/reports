#7340 · Retention batch validation repeatedly scans the thread catalog

BugMedium priorityLow effortplugins · perf · confirmed-reproGitHub issue

2026-11-10 · trusted base 7c1353d80729983b86ea1555d18b42407f320406

Verdict: REPRODUCED · Root-cause confidence: high

1. TL;DR

The hourly retention job finds groups of old threads to archive or delete. Before processing each group it reads the complete thread catalog again, including unrelated threads. With 7,600 synthetic threads and 50 eligible roots for each action, one sweep issued 1,616 unfiltered thread-list requests and received 766,375 rows. A second clean checkout produced the same counts. The minimal snapshot-and-targeted-reread optimization reduced the load but failed the archive safety test by dispatching an archive request after a newly attached hidden lifecycle dependent should have blocked it; that local prototype was reverted, not pushed.

Complete repeatable test, including the archive fresh-membership safety check 
import { expect, it } from "vitest";
import {
  createFakePluginHost,
  makeThreadResponse,
} from "@get-bb/plugin-sdk/testing";
import plugin from "./server.js";

it("bounds full-list reads while processing both retention batches", async () => {
  const rows = new Map(
    Array.from({ length: 7600 }, (_, index) => {
      const thread = makeThreadResponse({
        id: `thr_budget_${String(index).padStart(5, "0")}`,
        updatedAt: 1,
        archivedAt: index >= 50 && index < 100 ? 1 : null,
        pinnedAt: index >= 100 ? 1 : null,
      });
      return [thread.id, thread];
    }),
  );
  let fullListCalls = 0;
  let returnedRows = 0;
  const host = createFakePluginHost({
    pluginId: "storage-retention",
    sdk: {
      threads: {
        list: async (input) => {
          const all = [...rows.values()];
          const requested = input?.threadIds;
          const selected = requested
            ? all.filter((thread) => requested.includes(thread.id))
            : all;
          if (input?.threadIds === undefined) fullListCalls++;
          const offset = input?.offset ?? 0;
          const page = selected.slice(offset, offset + (input?.limit ?? 500));
          returnedRows += page.length;
          return page;
        },
        archive: async ({ threadId }) => {
          rows.get(threadId)!.archivedAt = Date.now();
          return { archivedThreadIds: [threadId] };
        },
        delete: async ({ threadId }) => {
          rows.delete(threadId);
          return { ok: true };
        },
      },
    },
  });
  try {
    plugin(host.bb);
    await host.harness.callRpc("configure", {
      archiveAfterDays: 30,
      deleteAfterDays: 30,
    });
    await host.harness.runSchedule("retention");
    expect(await host.harness.callRpc("state", null)).toMatchObject({
      lastRun: { archivedCount: 50, deletedCount: 50, failedCount: 0 },
    });
    console.log(JSON.stringify({ fullListCalls, returnedRows }));
    expect(fullListCalls).toBeLessThanOrEqual(16);
  } finally {
    await host.harness.dispose();
  }
});

it("rechecks a newly attached lifecycle dependent before archive", async () => {
  const root = makeThreadResponse({
    id: "thr_root",
    updatedAt: 1,
    archivedAt: null,
  });
  const rows = new Map([[root.id, root]]);
  let initialRead = true;
  const host = createFakePluginHost({
    pluginId: "storage-retention",
    sdk: {
      threads: {
        list: async (input) => {
          const requested = input?.threadIds;
          const result = [...rows.values()].filter(
            (thread) =>
              requested === undefined || requested.includes(thread.id),
          );
          if (initialRead) {
            initialRead = false;
            const dependent = makeThreadResponse({
              id: "thr_new_dependent",
              lifecycleOwnerThreadId: root.id,
              parentThreadId: null,
              sourceThreadId: null,
              visibility: "hidden",
              updatedAt: Date.now(),
              pinnedAt: Date.now(),
            });
            rows.set(dependent.id, dependent);
          }
          return result;
        },
        archive: async ({ threadId }) => ({ archivedThreadIds: [threadId] }),
        delete: async () => ({ ok: true }),
      },
    },
  });
  try {
    plugin(host.bb);
    await host.harness.callRpc("configure", {
      archiveAfterDays: 30,
      deleteAfterDays: null,
    });
    await host.harness.runSchedule("retention");
    expect(host.harness.sdk.callsTo("threads.archive")).toHaveLength(0);
  } finally {
    await host.harness.dispose();
  }
});

5. Root cause

service.ts:39–42 defines candidates() as a full read followed by selection:

const threads = await readThreads(bb);
return selectCandidates(threads, policy, Date.now());

service.ts:66–86 calls this once before the loops and again for each root, even though the second result is only used to find that one root. The two action loops each cap candidates at 50. sdk-data.ts:1–16 requests pages of 500 until a short page, without a filter restricting the catalog.

Consequently the 100-root fixture invokes the complete selection 101 times. All full reads still contain at least 7,550 rows, so every read needs 16 pages: 101 × 16 = 1,616. Deletions reduce the later row counts, explaining the measured total of 766,375 returned rows rather than 101 identical 7,600-row responses. policy.ts:32–79 also rebuilds relationship indexes and traverses roots on every call.

Why targeted rereads alone are insufficient

The eligibility graph includes lifecycle ownership, parentage, and hidden source references, not just a fixed set of IDs. policy.ts:46–51 links lifecycle dependents into both archive and delete groups. For a live archive root, a dependent that appears after the initial snapshot is absent from the known-ID set; refreshing the root, its old members, and its parent/source cannot discover it. The safety test inserts exactly that new hidden dependent between selection and revalidation; main correctly skips the root.

Existing APIs do not directly provide the complete replacement graph: thread-list filters have parent/source/ID filters but no lifecycle-owner filter; descendants traversal follows parentage only; and cascade API contract deliberately omits hidden threads. archive cascade implementation does include lifecycle, child, and hidden source relationships, so missing those eligibility exemptions is unsafe.

6. Proposed fix and simple-fix decision

Separate the initial selection from fresh, bounded revalidation, but retain discovery of newly attached lifecycle dependents and hidden source threads. A scoped relationship query or a proven membership-aware invalidation design could support this. The repair must preserve policy changes, pin/unarchive exemptions, disposal handling, and the existing batch limits; continue to use the plugin's existing SDK and CLI surfaces.

The evaluated local prototype read a snapshot once, refreshed known group members plus the root's parent/source by ID, removed missing rows, and reran selection over the overlay. It passed the load budget but failed the archive safety check:

{"fullListCalls":16,"returnedRows":7700}
✓ bounds full-list reads while processing both retention batches
× rechecks a newly attached lifecycle dependent before archive
AssertionError: expected [ [ { threadId: 'thr_root' } ] ] to have a length of +0 but got 1
Tests  1 failed | 1 passed (2)

That failure records unsafe archive SDK dispatch, not mutation of real data. A time-to-live would not discover a dependent attached before that interval expires. The prototype was stopped and fully reverted because preserving behavior is a mandatory simple-fix gate. No branch was pushed and no pull request was opened. A different fresh-membership strategy needs further design/verification rather than silently weakening retention safety.
