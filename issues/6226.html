1. TL;DR

The report describes a native Codex goal remaining active while its thread stops working between turns. Two clean checkouts were used to test BB’s actual Codex bridge with the repository’s scripted app-server child. An active goal snapshot remains active after a completion, and a subsequent native turn is forwarded when the child supplies it. This establishes the event-path behavior, not the intermittent native scheduler failure: the script deliberately chooses whether a second turn exists. No authenticated native Codex goal was run, and no failing real event trace was available, so the reported defect and its root cause remain unconfirmed.

6. Proposed fix / next experiment

No production fix is justified yet. Capture a sanitized native trace with a unique thread/turn identity, BB and Codex versions, goal/budget state, turn/completed, any subsequent turn/started, child-process liveness, host runtime delivery, queue/interaction state, and idle-reaper activity. Replay the failing ordering through the bridge and server before choosing an owner. If the native process never emits a next turn, test its scheduler in isolation; if it emits a next turn that BB drops, add a regression at that proven boundary. A BB watchdog added now would be a policy decision and could duplicate native continuation or override legitimate pause/interaction/budget state.
