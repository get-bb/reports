#4387 · OpenCode v2 credential lookup in Go usage

BugMedium priorityMedium effortprovidersprovider-acpopencodeopen on GitHub2026-09-25 · base 2726ab1ee542

Verdict: REPRODUCED · Root-cause confidence: high

1. TL;DR

The Go usage collector reports an unauthenticated state when its only available key is an active OpenCode v2 credential in SQLite. A synthetic database matching OpenCode v2.0.18 produces that result on bb main in two clean checkouts. The collector opens that database but queries only the older Console account tables; its API-key fallback reads environment variables or the legacy JSON file. It never reads the v2 credential row, so it stops before requesting usage. A real service-account login and remote quota response were unavailable for this test.

5. Root cause

readAccount lines 44–79 opens opencode.db read-only, checks only account and account_state, and returns null when those tables are absent. readApiKey lines 81–109 searches an explicit environment key, optional JSON content, and auth.json; it has no SQLite credential query. The collector lines 123–132 then maps two null results to unauthenticated. OpenCode v2.0.18 defines the credential table and a key value tagged type: "key". Its credential service can keep multiple rows and marks one active, so selecting a key requires respecting that state.

6. Proposed fix (first principles)

At the host-local collector boundary, validate the v2 credential table shape and JSON key value, select only the active key for the Go integration (with the shared OpenCode integration as an intentional fallback), and preserve the existing explicit-key and Console-account precedence. Keep SQLite read-only and never expose the key in usage results or errors. Test active versus inactive rows, malformed values, legacy fallback, and the existing quota request path. This changes credential selection, an authentication and security boundary, so it does not meet this autopilot rule's simple-fix criteria; no PR was opened.
