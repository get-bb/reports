#5340 · Embedded composer project fallback

BugPriority: MediumEffort: Lowui, pluginsGitHub issue2026-10-10

Trusted main base: e9ad6b0e3473628f96fa98378cf8528aac8984d2

Verdict: REPRODUCED · Root-cause confidence: high · reproduction label: confirmed-repro

1. TL;DR

A plugin-hosted new-thread composer can hand its caller a request for the personal project even when the root composer remembers another project. Omitting the plugin's project seed initializes a local null selection; the shared composer interprets it as personal. An explicit project seed missing from a fresh, successful project list is also converted to personal, and programmatic submission succeeds with a personal-workspace environment. Both request-boundary failures repeat on unchanged production code in a second clean checkout. Loading and replayed lists are a narrower case: the existing replay protection preserves an unknown seed and blocks submission until it is known.

  it("issue 5340 uses the remembered project when the plugin omits its seed", async () => {

5. Root cause

Missing seed has no remembered-project initialization

PluginNewThreadComposer.tsx:29–38 initializes and re-seeds project state using the prop or null. PluginNewThreadComposer.tsx:60–69 then passes that local value to the shared composer. In contrast, RootComposeView.tsx:397–436 reads the remembered root hook; root-compose-selection.ts:12–34 defines the persistent project key.

const [pickedProjectId, setPickedProjectId] = useState<string | null>(
  defaultProjectId ?? null,
);

Fresh-list reconciliation silently changes the target

NewThreadComposer.tsx:521–534 turns null into the personal id and returns personal when a non-placeholder list does not contain the requested project. An absent project in placeholder data is deliberately preserved, explaining the passing replay control.

const requestedCandidate = requestedProjectId ?? PERSONAL_PROJECT_ID;
const replayKnowsCandidate =
  !sidebarNavigationQuery.isPlaceholderData || candidateKnown;
const projectId = useMemo(() => {
  if (isProjectlessProjectId(requestedCandidate)) return PERSONAL_PROJECT_ID;
  if (!projects || !replayKnowsCandidate) return requestedCandidate;
  return candidateKnown ? requestedCandidate : PERSONAL_PROJECT_ID;
}, [candidateKnown, projects, replayKnowsCandidate, requestedCandidate]);

NewThreadComposer.tsx:1643–1694 assembles submission using this resolved project. There is no remaining check that it matches the requested non-personal seed. thread-create-helpers.ts:90–112 inserts the request's project id, rather than consulting browser selection.

6. Proposed fix and simple-fix decision

First settle the project-defaulting contract: should an omitted plugin seed snapshot the root's remembered project, use an explicit documented mode, or remain isolated? The SDK currently documents a seed and reseeding, not a remembered-project fallback (NewThreadComposerProps contract); composer selection audit explicitly describes component-local plugin selection as leaving stored preferences untouched.

After that decision, initialize an omitted plugin project through the chosen shared policy while preserving explicit personal choice and local user edits. For an unresolved explicit seed, retain the requested identity and block or report a project-resolution error until it resolves or the user chooses a valid project. Keep the root's stale/deleted remembered-project handling deliberate rather than globally changing the shared fallback by accident. Add recovery, prop-reseed, and preference-isolation cases to the owning suite.

No pull request opened: the whole fix requires a product-policy decision about unseeded project inheritance and invalid-seed handling. That fails the rule's decision-free simple-fix gate. No production patch, branch, commit, dependency, protocol, or persisted-data change was attempted. The local reproduction-only patch adds 100 text lines in one test file and is not a proposed fix.
