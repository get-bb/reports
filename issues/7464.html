#7464 · Computer Use permission rejection

Bug Priority: Medium Effort: Medium providers provider-codex partial-repro

Issue · November 12, 2026 · Trusted main 030b1b729f28acedc6f86cd65a71cb3678da8124

PARTIALLY REPRODUCED · Root-cause confidence: low for the original Windows incompatibility; high for the rejection mechanism.

1. TL;DR

A Computer Use access request can reach BB successfully yet have no Allow button because BB has already classified its details as unsupported. On trusted main, three deliberately altered repository fixtures independently produce the same generic app-permission error and a production-rendered card with only Decline. The unmodified fixture has both offered approval choices, and unsupported requests cannot be accepted through the response encoder. This verifies the fail-closed mechanism, not a Windows-specific defect: neither the original raw native request nor a Windows execution host was available. The exact incompatible field and whether the native request was valid remain unknown, so relaxing consent validation is not justified.

// @vitest-environment jsdom

const metadata = capturedRequest.params._meta;

const cases = [
  { name: "control", params: capturedRequest.params, supported: true },

    name: "missing riskLevel",

it.each(cases)("traces $name from request through user response", async (scenario) => {
  const decoded = decodeCodexInteractiveRequest({
    ...capturedRequest,

  });
  if (!decoded || !("data" in decoded.payload)) {
    throw new Error("Expected an extension interaction");
  }
  const payload = codexMcpElicitationSchema.parse(decoded.payload.data);
  const submit = vi.fn<PluginPendingInteractionProps["submit"]>(async () => {});
  const slot = renderSlot(registration, {
    interaction: {
      id: "pint_repro_7464",
      threadId: "thr_repro_7464",
      title: decoded.payload.title,
      payload,
      createdAt: 0,
      expiresAt: null,
    },
    submit,
    cancel: vi.fn<PluginPendingInteractionProps["cancel"]>(async () => {}),
  });
  const buttons = slot.getAllByRole("button").map((button) => button.textContent);
  console.log(JSON.stringify({ scenario: scenario.name, payload, buttons }));
  if (scenario.supported) {
    expect(payload.kind).toBe("computer_use");
    expect(buttons).toEqual(["Always allow", "Decline", "Allow for this session"]);

  expect(buttons).toEqual(["Decline"]);

    action: "accept", persist: "session",
  })).toThrow("Unsupported elicitations can only be declined or cancelled.");

5. Root cause

Established mechanism: the real interactive-request decoder calls the elicitation normalizer and stores only the normalized interaction payload. Computer Use classification requires the trusted server name and connector marker; it is not inferred from the displayed title.

The Computer Use metadata and empty-form schemas require offered scopes, low/high risk, app identity, and exact display structure. Both the requested-schema object and nested app-parameter object reject unknown fields:

riskLevel: z.enum(["low", "high"]),
tool_params: z.strictObject({ app: z.string().trim().min(1) }),

const emptyFormSchema = z.strictObject({
  type: z.literal("object"),
  properties: z.strictObject({}),
});

The normalizer and catch block replace any Zod validation failure in this branch with the same unsupported reason. Consequently, the normalized record cannot distinguish missing risk metadata from extra parameters or an unsupported schema shape. None of those synthetic causes can be selected as the original Windows cause without additional evidence.

The production UI always renders Decline, but only supported variants render approval controls. The native response encoder independently rejects acceptance of an unsupported request. This is deliberate fail-closed behavior, not merely a hidden or disabled Allow button.

Not established: which raw field failed for the original report, whether that native request followed a supported contract, whether a provider update changes it, or any causal connection with the separate browser-host availability message. Confidence in a specific Windows compatibility root cause remains low.

Compare its shape against the supported native contract and retain a sanitized contract fixture only after that review. Repeat on the reported and newer provider versions. Preserve fail-closed handling, offered persistence scopes, warnings, server identity, and response validation.

No production fix or PR is safe under this automation's simple-fix rule.
