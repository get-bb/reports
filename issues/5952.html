#5952 · Archive retirement discards local edits

BugHighEffort: Mediumthreads · workspaces · confirmed-reproGitHub issue

2026-10-21 · trusted origin/main 405592c0b71b1655a6ab2e1cc7498b5beeb78caa

Verdict: REPRODUCED · Root-cause confidence: high

1. TL;DR

Archiving an idle thread in an owned managed Git worktree can discard both modified tracked files and untracked files after its environment retirement grace expires. The real archive HTTP route accepts the archive, the server schedules retirement five minutes later, and the real built-in provider forcibly removes the dirty checkout. Two clean-checkout runs reproduced this through the actual server lifecycle and plugin removal code with a real migrated SQLite database and temporary Git repository. Unpushed committed work was not deleted in either run: the source repository retained the local branch and its commit. The existing archive dialog has no worktree-loss warning, but that disclosure finding is from source inspection, not a browser session.

5. Root cause

Archiving schedules managed-environment retirement without a dirty-worktree safety check; provider removal forces Git worktree deletion and recursively removes the directory.

6. Proposed fix and simple-fix assessment

Design an archive-specific safe-retirement policy: read authoritative worktree state before destructive teardown, preserve dirty resources, surface the reason through the existing archive controls, and repeat the safety check at deletion time to avoid a stale preflight. Keep thread archival distinct from explicitly destructive environment/project/machine cleanup. Add regression coverage for tracked and untracked edits, descendant/shared environments, disconnected hosts, and edits made during the grace period. Avoid promising that unarchive can restore discarded working files.

No automatic PR. A complete safe repair spans archive confirmation, server retention policy, and the provider removal boundary. An isolated host-only refusal would also change explicit teardown behavior and can leave existing project/machine deletion flows blocked; removing --force alone is ineffective because recursive deletion still follows. Selecting retention/recovery behavior is a product/lifecycle decision, so this does not satisfy the one-subsystem, no-product-decision simple-fix gate. No production patch, fix branch, or push was made.
