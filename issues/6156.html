1. TL;DR

The signing configuration resolves to hardened-runtime macOS builds whose application and inherited signing profiles both omit camera capture permission. A new, dependency-free contract check detects that omission in two clean checkouts of the same trusted main commit; neither checkout contains a production patch. This is a concrete camera-capability defect, but it is not an end-to-end reproduction of a macOS permission prompt or camera stream. There is another relevant boundary: the built-in browser deliberately rejects video requests while supporting microphone consent, so adding signing entitlements alone cannot establish camera support for every page. The issue acquired a screen-sharing claim during investigation; tracked desktop source also lacks display-media selection wiring, but the reported screen-sharing exception remains unverified.

4. Minimal reproduction

This checks the actual resolved signing inputs, not macOS TCC. Save the following as camera-signing-contract.py. It invokes trusted repository code with an environment containing only PATH, so no signing credentials are needed or inspected.

import json
import os
from pathlib import Path
import plistlib
import subprocess
import sys


checkout = Path(sys.argv[1]).resolve()
desktop = checkout / "apps" / "desktop"
result = subprocess.run(
    ["node", "scripts/run-electron-builder.mjs", "--print-config"],
    cwd=desktop,
    env={"PATH": os.environ["PATH"]},
    check=True,
    capture_output=True,
    text=True,
)
config = json.loads(result.stdout)
mac = config["mac"]
assert mac["hardenedRuntime"] is True
print("Resolved config: hardenedRuntime=true")
failures = []
for setting in ("entitlements", "entitlementsInherit"):
    relative_path = mac[setting]
    with (desktop / relative_path).open("rb") as profile:
        grants = plistlib.load(profile)
    camera = grants.get("com.apple.security.device.camera", False)
    microphone = grants.get("com.apple.security.device.audio-input", False)
    print(f"{relative_path}: camera={camera}; microphone={microphone}")
    if camera is not True:
        failures.append(relative_path)
if failures:
    print(f"FAIL: camera capture entitlement absent from {len(failures)} signing profiles")
    sys.exit(1)
print("PASS: camera capture entitlement enabled for app and inherited signing")

5. Root cause

Camera signing capability

The macOS packaging configuration selects these two profiles and enables hardened runtime. The production config resolver preserves those settings while adjusting identity, icon, and notarization; the executed diagnostic uses its resolved configuration.

"entitlements": "build/entitlements.mac.plist",
"entitlementsInherit": "build/entitlements.mac.inherit.plist",
"gatekeeperAssess": false,
"hardenedRuntime": true

Both the application profile and inherited profile contain runtime execution exceptions and audio input, but no camera grant. Apple's Camera entitlement documentation identifies the camera capability and its use with Hardened Runtime. Missing that capability explains the source-level asymmetry with microphone access and is consistent with the claimed OS rejection; it does not prove the installed bundle's behavior on this Linux host.

Separate built-in browser consent boundary

The browser session's request and check handlers only accept a single audio media type. Video and combined requests are denied before microphone consent. The existing owner-boundary tests explicitly assert these denials. Five selected consent cases pass. This finding concerns built-in browser tabs, not a blanket assertion about every plugin renderer or default session.

Screen-sharing extension added during investigation

A tracked-source search in both clean checkouts returns no registrations of setDisplayMediaRequestHandler and no uses of desktopCapturer under apps or packages. The version-matched Electron API documentation describes a session handler that receives display-media requests and supplies selected sources. That is a separate missing integration, not something a camera entitlement can repair. Absence of this wiring is statically established; the exception type and OS behavior reported by the user were not reproduced.

6. Proposed fix and safety decision

For camera capability, grant camera capture in the signing profiles used by the app and inherited processes, and validate the final signed bundle and camera usage description. Extend the existing packaging contract to cover camera capability, then exercise permission prompting and successful capture on macOS. Do not weaken renderer permission policy as an incidental part of a signing change.

Built-in browser camera consent and display capture need explicit origin-scoped policy, deliberate user consent, navigation/lifecycle safety, and an appropriate source picker. A signed macOS build should test allow, deny, repeat request, navigation, and helper-process behavior on the actual affected surface. Do not silently select the first screen or window.

No fix branch or pull request was created. This rule forbids automatic fixes that change permissions, security boundaries, or packaging; camera-signing remediation crosses those boundaries, and display capture also requires product decisions.
