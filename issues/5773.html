#5773 · Windows detection retains macOS downloads

BugMedium priorityLow effortdesktopGitHub issue2026-10-19 · base 598e1857390a108bad2d1ad3c378ab2d38bb77f9

Verdict: REPRODUCED · Root-cause confidence: high · reproduction label: confirmed-repro

1. TL;DR

The shared download selector never identifies Windows: it only recognizes macOS and Linux. The hook begins with macOS and updates only for a non-null detection result, so Windows remains on macOS. An agent-authored regression reproduces this on unchanged trusted main, including the actual download-button renderer for nav, hero, and closer placements. All five checks fail again in a second clean checkout. This is deterministic source/component evidence, not a claim that native Windows or browser hydration was exercised.

5. Root cause

detectDesktopPlatform only returns macos, linux, or null; Windows has no recognition branch. useDesktopPlatform initializes from the macOS default and changes state only for a truthy result. Thus there is no Windows update after the effect runs.

import { useEffect, useState } from "react";

import { DEFAULT_DESKTOP_PLATFORM } from "./site";
import type { DesktopPlatform } from "./site";

type PlatformSource = {
  platform?: string;
  userAgent?: string;
  userAgentData?: { platform?: string } | null;
};

export function detectDesktopPlatform(
  source: PlatformSource,
): DesktopPlatform | null {
  const hint = source.userAgentData?.platform ?? source.platform ?? "";
  const userAgent = source.userAgent ?? "";
  if (/mac/i.test(hint) && !/iphone|ipad|ipod/i.test(userAgent)) {
    return "macos";
  }
  if (
    /linux/i.test(hint) &&
    !/android/i.test(hint) &&
    !/android|cros/i.test(userAgent)
  ) {
    return "linux";
  }
  return null;
}

export function useDesktopPlatform(): DesktopPlatform {
  const [platform, setPlatform] = useState<DesktopPlatform>(
    DEFAULT_DESKTOP_PLATFORM,
  );
  useEffect(() => {
    const detected = detectDesktopPlatform(
      navigator as Navigator & PlatformSource,
    );
    if (detected) {
      setPlatform(detected);
    }
  }, []);
  return platform;
}

Platform registry and default already includes a Windows redirect, so this is not a missing installer route. Its Windows secondary label contains Alpha, but its primary buttonLabel does not. DesktopDownloadButton uses that buttonLabel directly.

InstallOptions obtains the hook result and passes it to the shared button. The hero call site and closer call site use InstallOptions; the header call site uses the same button with its hook-derived platform. Existing Windows test codifies the wrong fallback, explaining why existing tests do not catch it. History attributes the detector to a8181f511, the Linux landing-page change.

6. Proposed fix

Recognize desktop Windows from the same platform metadata sources, retain mobile exclusions and existing macOS/Linux handling, and make the Windows primary label explicitly include Alpha. Change the old Windows fallback expectation into behavior-focused Windows selection regressions while retaining unknown-platform coverage. The existing registry and redirect contract are sufficient; no protocol, packaging, or dependency change is needed.
