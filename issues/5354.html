#5354 · Runtime replacement loses ownership under overlapping requests

BugHighEffort: Mediumhost · threads · confirmed-reproIssue2026-10-11 · base 3912f4aae

REPRODUCED · Root-cause confidence: high

1. TL;DR

Two callers asking the host daemon for the same environment can receive different runtimes during an idle-runtime replacement. A deterministic test on trusted main creates three runtimes rather than two: the original, an overlapping replacement, and the first caller's replacement. Only one replacement remains tracked, and shutting down the manager never shuts down the other replacement. Both skill-catalog invalidation and shell-generation invalidation reproduce this ownership defect. Live provider execution, duplicate commits, and lost messages were not recreated; this report confirms the runtime race, not every reported downstream consequence.

5. Root cause

Compatibility replacement removes an idle entry before awaiting its runtime's shutdown. The shell-generation branch follows the same pattern. During that await, no entry exists and no replacement promise has been registered.

this.entries.delete(args.entry.environmentId);
await args.entry.runtime.shutdown();

ensureEnvironment checks entries before compatibility work, then checks pending creation promises. An overlapping caller can finish its own creation while the first caller is waiting in shutdown. The first caller's continuation does not re-read entries; if the overlapping creation promise has already been cleaned up, it creates another runtime and overwrites the map entry.

.then((entry) => {
  this.entries.set(args.environmentId, entry);
  return entry;
})

The caller holding the overwritten runtime still has a valid runtime reference. Manager shutdown and idle maintenance only enumerate tracked entries, so they cannot see that runtime. The regression's zero shutdown count demonstrates this lost ownership rather than merely an extra factory invocation.

Turn admission checks the selected entry's runtime, not a process-wide registry. That explains how runtime ownership loss could undermine admission checks, but no two real provider turns were started in this reproduction.

6. Proposed fix

Track the entire ensure operation by environment before its first asynchronous gap, not just runtime creation. Overlapping callers await the in-flight operation and then re-evaluate compatibility against the resident runtime. Preserve pending-operation rejection: cancellation of a shared provision must reject all waiting callers rather than starting a second setup. Clear the operation by promise identity so unrelated environments remain independent and failed operations do not poison future requests.

A two-file candidate uses a private environment-keyed promise map and the existing ensure implementation. It changes no wire fields, public APIs, storage, dependencies, generated files, or release behavior. The existing environment-dispatch cancellation test caught an initial serial-queue draft that retried a cancelled setup; that draft was revised before publication. Candidate verification details follow.
