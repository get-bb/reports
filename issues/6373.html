#6373 · RPC validation diagnostics omit structured field paths

BugLow priorityLow effortpluginsIssue2026-10-27

Verdict: REPRODUCED · Root-cause confidence: high. Trusted base: b6743a36bd9eae1408c35cfc2c7ab1d2419dc79d.

1. TL;DR

A plugin's invalid RPC argument receives an informative HTTP error, but its server warning loses the failing field path. The validator supplies normalized structured issues; the boundary error's ordinary Error message contains only the generic summary, and the runtime logs only that summary. A real plugin loaded by the existing server test harness reproduces the mismatch through the actual HTTP route. Both input and output validation exhibit it. Two clean trusted checkouts reproduce the same missing-path assertions without a live BB instance or private runtime data.

Complete reproduction test

import { mkdtemp, rm, writeFile } from "node:fs/promises";
import { tmpdir } from "node:os";
import { join } from "node:path";
import { expect, it, vi } from "vitest";
import { defineRpcContract } from "@get-bb/plugin-sdk";
import { z } from "zod";
import { createTestAppHarness } from "../../helpers/test-app.js";

it.each(["input", "output"] as const)(
  "logs RPC %s validation paths without payloads or custom issue messages",
  async (phase) => {
    const harness = await createTestAppHarness();
    const rootDir = await mkdtemp(join(tmpdir(), "bb-rpc-diagnostics-"));
    const warn = vi.spyOn(harness.deps.logger, "warn");
    try {
      await writeFile(
        join(rootDir, "package.json"),
        JSON.stringify({
          name: "bb-plugin-rpc-diagnostics",
          version: "0.1.0",
          bb: {
            name: "RPC diagnostics fixture",
            description: "Validation logging fixture",
            branding: { icon: "Zap" },
            server: "./server.ts",
          },
        }),
      );
      await writeFile(
        join(rootDir, "server.ts"),
        "export default function plugin() {}",
      );
      expect((await harness.pluginService.installPath(rootDir)).status).toBe(
        "running",
      );
      const api = harness.pluginService.getApi("rpc-diagnostics");
      if (!api) throw new Error("fixture plugin did not start");
      const schema = z.object({
        entries: z.array(
          z.object({ count: z.number({ error: "private-validator-detail" }) }),
        ),
      });
      const invalid = { entries: [{ count: "private-payload-content" }] };
      const handler = vi.fn(() => (phase === "output" ? invalid : null));
      api.rpc.register(
        defineRpcContract({
          inspect: {
            input: phase === "input" ? schema : z.null(),
            output: phase === "output" ? schema : z.null(),
          },
        }),
        { inspect: handler },
      );
      const response = await harness.app.request(
        "/api/v1/plugins/rpc-diagnostics/rpc/inspect",
        {
          method: "POST",
          headers: { "content-type": "application/json" },
          body: JSON.stringify(phase === "input" ? invalid : null),
        },
      );
      const body = await response.json();
      expect(response.status).toBe(phase === "input" ? 400 : 500);
      expect(body).toMatchObject({
        ok: false,
        error: {
          code: `invalid_${phase}`,
          message: `rpc ${phase} validation failed`,
          issues: [
            {
              path: ["entries", 0, "count"],
              message: "private-validator-detail",
            },
          ],
        },
      });
      expect(handler).toHaveBeenCalledTimes(phase === "input" ? 0 : 1);
      const warning = warn.mock.calls
        .map(([message]) => String(message))
        .find((message) => message.includes("rpc inspect failed:"));
      console.log(JSON.stringify({ phase, response: body, warning }));
      expect(warning).toBeDefined();
      expect(warning).not.toContain("private-payload-content");
      expect(warning).not.toContain("private-validator-detail");
      expect(warning).toContain('["entries",0,"count"]');
    } finally {
      warn.mockRestore();
      await harness.pluginService.stop();
      await harness.cleanup();
      await rm(rootDir, { recursive: true, force: true });
    }
  },
);

5. Root cause

  1. packages/plugin-sdk/src/internal/host-policy.ts:3637 normalizes string/numeric issue paths and keeps issue.message.
  2. packages/plugin-sdk/src/internal/host-policy.ts:3688 packages a generic message alongside normalized issues on validation failure.
  3. apps/server/src/services/plugins/plugin-service.ts:473 constructs the Error with super(rpcError.message); issues remain on its separate rpcError field.
  4. apps/server/src/services/plugins/plugin-runtime.ts:827 logs only error.message. The cause is returned, not discarded.
  5. apps/server/src/services/plugins/plugin-service.ts:2142 returns the retained structured rpcError to the route; apps/server/src/routes/plugins.ts:986 serializes it and maps input/output errors to HTTP statuses.

6. Proposed fix

Append a small bounded summary of normalized issue paths to the internal boundary Error message, leaving rpcError itself unchanged. JSON-encode paths to preserve array indices and escape control characters. Cap the number of paths and summary length; represent a pathless issue as the root. Do not blindly append arbitrary Standard Schema issue messages or input/output objects: messages can contain values and are not a safe logging primitive. Unknown-key names and expected-type prose are not separate trusted metadata in this normalized issue contract; obtaining them without exposing values needs a separately designed contract, not message parsing.
