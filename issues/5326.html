#5326 · SDK scanner interprets non-import syntax as dependencies

Bug Medium priority Medium effort plugins confirmed-repro · GitHub issue · October 10, 2026

Trusted base: 59a1fcc29f4fa470e6aa4fc6067853096da6abbe (origin/main).

Verdict: REPRODUCED · Root-cause confidence: high

1. TL;DR

The public SDK dependency scanner reports violations for source files that do not import anything. It searches raw text for words such as import, require, and from, without recognizing their syntax. Consequently, object and class methods, property calls, comments, and test descriptions can be mistaken for module loads. Seven independently authored negative fixtures fail in two clean checkouts; genuine forbidden imports remain rejected. A local syntax-aware candidate fixes the scanner tests but fails the SDK's existing ESM packaging contract, so it was stopped without a push or pull request.

5. Root cause

The import and dynamic-specifier regexes match anywhere in source. A word boundary does not distinguish loader.import(...) from an import expression, or a method declaration from a call. The static regex also recognizes from inside ordinary strings and crosses the closing quote of a description containing import.

const IMPORT_SPECIFIER_PATTERN =
  /(?:\bfrom\s*|\bimport\s*\(?\s*|\brequire\s*\(\s*)["']([^"']+)["']/gu;
const DYNAMIC_SPECIFIER_PATTERN =
  /\b(?:import|require)\s*\(\s*(?!["'])([^)]+)\)/gu;

Extraction uses source.matchAll directly. The scanner then treats those captures as real imports and applies otherwise legitimate dependency policy. The bug is in extraction, not dependency resolution or fixture execution.

6. Proposed fix and simple-fix safety check

Extract actual module-bearing syntax with a JavaScript/TypeScript parser, retaining the existing allowlist, package-root checks, and dynamic-specifier rejection. Cover import declarations, re-exports, import expressions, bare require calls, import-equals declarations, and type imports; do not grant arbitrary property-name or string allowances.

A local candidate used the already-present TypeScript development dependency for syntax extraction. It changed only two SDK files, with 87 total added/deleted text lines, no binary changes, and a clean git diff --check. All 13 focused scanner tests passed. However, the full SDK suite reported 374 passed and 1 failed: the existing published-runtime contract detected a CommonJS require shim in the ./testing ESM bundle. The same runtime contract passed on unchanged production code in the second checkout.

This is a fix-caused failure, not the reported bug or an environment problem. Shipping this parser safely needs a compatible runtime parser dependency or a packaging decision/change, which the simple-fix rule prohibits. The candidate was stopped and was not committed, pushed, or submitted as a PR. No existing open PR linked to #5326 was found during this run.

A normal SDK build with the candidate succeeded, but running the standalone reproduction against its built testing entrypoint failed immediately with Error: Dynamic require of "fs" is not supported. This confirms the packaging failure affects real consumers, not only an implementation assertion in the runtime test.

Next maintainer action: select a parser that satisfies the SDK's current ESM packaging contract, then rerun both the scanner regressions and the published-runtime suite. Do not weaken the runtime test or introduce ad-hoc naming exceptions to make the candidate pass.
