1. TL;DR

The reported defect would let an unknown agent provider create an unusable thread when an explicit model bypasses default-model discovery. Current main rejects that provider before environment resolution or persistence. The rejection was added in #7023, merged November 4, 2026 at 23:36:21 UTC, three days before this issue was created. Two separate clean checkouts returned HTTP 400, created zero threads and zero new environments, and never invoked the worktree provider. The error code is invalid_request, not the issue's suggested provider_not_found; that naming difference does not recreate the dead-thread bug.

Complete report-only expanded regression test

Path: apps/server/test/public/public-threads.provider-validation.test.ts. This extends the existing primary owner-boundary regression rather than adding a permanent duplicate. The reports repository forbids committed repro files and raw logs, so the complete runnable source is embedded here; local artifacts are retained outside the reports checkout.

import { countThreads, environments } from "@bb/db";
import { eq } from "drizzle-orm";
import { describe, expect, it } from "vitest";
import { readJson } from "../helpers/json.js";
import {
  seedEnvironment,
  seedHostSession,
  seedProjectWithSource,
} from "../helpers/seed.js";
import { withTestHarness } from "../helpers/test-app.js";
import { installFakeGitWorktreeProvider } from "../helpers/environment-provider.js";

describe("thread provider validation", () => {
  it.each(["reuse", "managed-worktree"])(
    "rejects an unregistered provider before creating a thread (%s)",
    async (workspace) => {
      await withTestHarness(async (harness) => {
        const provider = installFakeGitWorktreeProvider();
        const { host } = seedHostSession(harness.deps);
        const { project } = seedProjectWithSource(harness.deps, {
          hostId: host.id,
        });
        const environment =
          workspace === "reuse"
            ? seedEnvironment(harness.deps, {
                hostId: host.id,
                projectId: project.id,
                status: "ready",
              })
            : null;
        const response = await harness.app.request("/api/v1/threads", {
          method: "POST",
          headers: { "content-type": "application/json" },
          body: JSON.stringify({
            origin: "sdk",
            projectId: project.id,
            providerId: "unregistered-provider",
            model: "test-model",
            input: [{ type: "text", text: "ok" }],
            environment:
              environment === null
                ? {
                    type: "host",
                    hostId: host.id,
                    workspace: {
                      type: "managed-worktree",
                      baseBranch: { kind: "default" },
                    },
                  }
                : { type: "reuse", environmentId: environment.id },
          }),
        });

        expect(response.status).toBe(400);
        const body = await readJson(response);
        expect(body).toMatchObject({
          code: "invalid_request",
          message: expect.stringMatching(
            /Unknown provider "unregistered-provider".*codex.*claude-code/u,
          ),
        });
        expect(countThreads(harness.db, { projectId: project.id }).total).toBe(
          0,
        );
        const projectEnvironments = harness.db
          .select()
          .from(environments)
          .where(eq(environments.projectId, project.id))
          .all();
        expect(projectEnvironments).toHaveLength(environment === null ? 0 : 1);
        expect(provider.contexts).toHaveLength(0);
        console.log(
          JSON.stringify({
            workspace,
            status: response.status,
            body,
            threadCount: 0,
            environmentCount: projectEnvironments.length,
            provisionCalls: provider.contexts.length,
          }),
        );
      });
    },
  );
});

5. Root cause

The historical gap was missing validation when registry.get(providerId) returned null. An explicit model could bypass a later default-model lookup, so it could not reliably serve as provider validation. This is a server policy concern: validating only CLI input would leave SDK and app callers exposed.

Current main fixes the gap directly in resolveCreateThreadExecutionDefaults:

const registration = registry.get(providerId);
if (registration === null) {
  const registeredProviderIds = registry
    .list()
    .map((provider) => provider.info.id)
    .join(", ");
  throw new ApiError(
    400,
    "invalid_request",
    `Unknown provider "${providerId}". Registered provider ids: ${registeredProviderIds || "(none)"}.`,
  );
}

Project execution-default resolution calls that policy before returning the requested model. Thread creation first awaits settled registrations and resolves execution defaults; only afterward does it resolve the environment. Therefore rejection cannot be bypassed by supplying a model.

The existing API regression is public-threads.provider-validation.test.ts. Git history attributes the guard and regression to dccef1db1a89d234f0c593ba75a0e5bbee517e9a via #7023. Historical behavior is inferred from the trusted-main commit diff; a pre-fix revision was not executed.

6. Proposed fix / disposition

No new fix is warranted for the reported thread-creation defect: the smallest root-cause guard is already shipped on main. Keep the existing validation and regression. Existing invalid rows are not repaired by this guard, and this investigation does not claim otherwise. Changing the stable error code or adding CLI catalog preflight would be separate changes, not necessary to prevent orphaned threads.
