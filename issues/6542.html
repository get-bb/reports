#6542 · Sidebar context updates invalidate unrelated row consumers

BugPriority: MediumEffort: Mediumui · perf · partial-reproIssue2026-10-29 · base 3bacfac9ed69d42392076e5b3da2815bec822cd8

PARTIALLY REPRODUCED · Root-cause confidence: high for the two context invalidation paths.

1. TL;DR

Two real sidebar contexts notify rows whose data has not changed. In a twelve-consumer reproduction, three edits to one title caused 33 unrelated consumer renders, while changing the selected thread caused all twelve action consumers to render. Both results repeated in a second clean checkout of trusted main. These tests exercise the production providers and hooks, but do not measure browser paints, complete row components, or user-perceived latency. The command-palette latency and the issue's exact timing claims remain unverified, so the overall verdict is partial.

// @vitest-environment jsdom

import { memo } from "react";
import { Provider, createStore } from "jotai";
import { cleanup, fireEvent, render, screen } from "@testing-library/react";
import { afterEach, expect, it } from "vitest";
import { installTestPluginRuntime } from "@get-bb/plugin-sdk/testing/app";
import {
  SidebarRenameProvider,
  useSidebarRename,
} from "../rows/SidebarInlineRename.js";
import { useCustomizeThreadRowActions } from "./customizeRowActionsContext.js";

installTestPluginRuntime();
const { ThreadListVisibility } = await import("./ThreadListVisibility.js");

afterEach(cleanup);

const rowIds = Array.from({ length: 12 }, (_, index) => `row-${index}`);
const saveName = async () => undefined;

it("keeps unrelated rename consumers idle while another row's draft changes", () => {
  const renders = new Map<string, number>();
  const Row = memo(function Row({ id }: { id: string }) {
    renders.set(id, (renders.get(id) ?? 0) + 1);
    const rename = useSidebarRename({
      id,
      kind: "thread",
      name: "Initial",
      label: `${id} title`,
      ownerKey: id,
      onSave: saveName,
    });
    return (
      <div>
        <button onClick={rename.startEditing}>Edit {id}</button>
        {rename.editor}
      </div>
    );
  });
  render(
    <SidebarRenameProvider>
      {rowIds.map((id) => (
        <Row key={id} id={id} />
      ))}
    </SidebarRenameProvider>,
  );
  fireEvent.click(screen.getByRole("button", { name: "Edit row-0" }));
  const input = screen.getByRole("textbox", { name: "row-0 title" });
  renders.clear();
  for (const value of ["N", "Ne", "New"]) {
    fireEvent.change(input, { target: { value } });
  }
  const unrelatedRenders = rowIds
    .slice(1)
    .reduce((total, id) => total + (renders.get(id) ?? 0), 0);
  console.log(
    JSON.stringify({
      probe: "rename",
      edits: 3,
      activeRenders: renders.get("row-0"),
      unrelatedRenders,
    }),
  );
  expect(input.getAttribute("value")).toBe("New");
  expect(unrelatedRenders).toBe(0);
});

it("keeps unchanged action consumers idle when the selected thread changes", () => {
  const renders = new Map<string, number>();
  const Row = memo(function Row({ id }: { id: string }) {
    renders.set(id, (renders.get(id) ?? 0) + 1);
    const customize = useCustomizeThreadRowActions();
    return <button onClick={() => customize?.(id)}>Actions {id}</button>;
  });
  const children = rowIds.map((id) => <Row key={id} id={id} />);
  const store = createStore();
  const groups: never[] = [];
  const order: never[] = [];
  const onOrderChange = () => undefined;
  function List({ selectedThreadId }: { selectedThreadId: string }) {
    return (
      <Provider store={store}>
        <ThreadListVisibility
          groups={groups}
          order={order}
          onOrderChange={onOrderChange}
          label="Threads"
          selectedThreadId={selectedThreadId}
        >
          {children}
        </ThreadListVisibility>
      </Provider>
    );
  }
  const view = render(<List selectedThreadId="row-0" />);
  renders.clear();
  view.rerender(<List selectedThreadId="row-1" />);
  const unrelatedRenders = rowIds
    .slice(2)
    .reduce((total, id) => total + (renders.get(id) ?? 0), 0);
  console.log(
    JSON.stringify({
      probe: "selection",
      rowsRendered: renders.size,
      unrelatedRenders,
    }),
  );
  expect(screen.getAllByRole("button")).toHaveLength(12);
  expect(unrelatedRenders).toBe(0);
});

5. Root cause

Rename: a whole-session value is broadcast to every consumer

useRenameController stores the session in React state. Its change handler replaces that session for every draft change and returns a new controller object:

const [session, setSession] = useState<RenameSession | null>(null);
return {
  session,
  start,
  save,
  cancel,
  change: (draft: string) => {
    const current = sessionRef.current;
    if (current && !current.pending) {
      update({ ...current, draft, error: null, cannotRetry: false });
    }
  },
};

SidebarRenameProvider publishes that controller directly, and useSidebarRename subscribes to the entire context. All rows using that hook are therefore notified even when only another row's draft changes. Returning a stable object alone would not be enough: the actual editing row and dialog must still receive draft, pending, and error changes through a correctly scoped subscription.

Selection: the row-action callback gets a new identity

ThreadListVisibility creates customizeRowActions on every render and passes it to CustomizeRowActionsContext:

const customizeRowActions = (threadId: string) => {
  setRowActionsThreadId(threadId);
};
<CustomizeRowActionsContext.Provider value={customizeRowActions}>

Changing selectedThreadId rerenders this provider even though the action callback's behavior is unchanged. A new function identity invalidates every subscriber; React.memo does not suppress a subscribed context update. The reproduction changes only that selected ID while keeping the store, group/order arrays, callback prop, and child elements stable. The separate visibility-state object is also recreated, but the probe isolates the action callback rather than attributing every invalidation to every shared object.

The real ThreadRow consumes the rename hook and the action callback context; it is memoized. This connects the measured context behavior to the production row without claiming the probe rendered the complete row.

Palette: scheduling suspicion, not a proven timing regression

Local result building runs in useMemo with raw query as a dependency. That is consistent with synchronous local work during input renders. However, useThreadSearch already debounces its server query. The claim must not be interpreted as proof that every keystroke immediately performs a server search. A browser scheduling/paint trace with a large synthetic list is still needed.

6. Proposed fix and simple-fix gate

  • Keep the row-action context callback stable across unrelated selection changes.
  • Separate stable rename actions from target-scoped session subscriptions so unrelated rows do not observe draft-only changes. Retain correct save, retry, cancel, unmount, focus, and dialog behavior.
  • Profile palette input separately; if local result building blocks input commits, decouple input value updates from expensive result computation while preserving current-query correctness and keyboard selection.

No automated fix PR: the combined issue crosses the thread-list plugin, shared rename helper, and command-palette subsystem; palette latency is not yet reproduced. It therefore fails the one-existing-subsystem simple-fix gate. No production fix, new branch, commit, dependency, or push to get-bb/bb was made.
