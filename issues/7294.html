#7294 · Credential-store health detection

BugPriority: MediumEffort: Mediumprovidersprovider-codexpartial-repro GitHub issue2026-11-09 · base 713ee7884df77729ab75c21057f15b01829db7a8

Verdict: PARTIALLY REPRODUCED · Root-cause confidence: high for the file-only backend decision. Native macOS Keychain login and desktop rendering were not reproduced.

1. TL;DR

The provider health check treats an absent credential file as a signed-out account, even when a controlled CLI fixture reports that it is logged in. Two clean runs of the real BB health function confirm this backend behavior on trusted main. Source tracing explains why onboarding then offers sign-in rather than marking the provider ready. This Linux investigation did not access a real credential store, run a native Codex login, or capture the desktop screen, so the complete macOS scenario remains unverified.

5. Root cause

  1. The file path is derived from the effective Codex home. There is no alternative credential-store query in this health path.
  2. The credential reader only opens the file and classifies ENOENT as missing: 
    raw = await fs.readFile(authPath, "utf8");
...
return errnoCode(error) === "ENOENT"
  ? { state: "missing", authPath }
  : { state: "unreadable", authPath, error: toError(error) };
  3. The maintenance adapter discards the distinction between an absent file and unusable credentials: 
    case "missing":
case "unusable":
  return null;
  4. The health function interprets null as unauthenticated: 
    const credentials = await readCredentials();
if (credentials === null) {
  return healthResult("unauthenticated", { installedVersion: version });
}
  5. The onboarding model translates this into a sign-in state; the view selects the installed-but-signed-out copy.

The deeper error is treating one storage implementation's missing artifact as authoritative evidence about the account. The provider can be installed and above the minimum version while this account check still rejects every login not represented by that file. High confidence refers to this observed branch and source chain, not to native Keychain behavior or real CLI output.

6. Proposed fix and safety gate

Have the health check ask Codex for its supported, noninteractive authenticated-account state instead of inferring sign-out solely from a missing file. First validate that interface on macOS with a disposable keyring-backed account; cover timeouts, unavailable credential stores, actual signed-out accounts, API-key accounts, and expired logins. Keep status detection separate from direct credential access used by usage fetching, and do not turn a failed probe into a false ready result.

No automatic fix or pull request. The complete native scenario was not reproduced. Changing how authenticated account state is determined also falls outside this rule's authentication-change exclusion. No production files were patched, and no fix branch was pushed. GitHub cross-reference metadata and open-PR search showed no linked open pull request for this issue at investigation time.
