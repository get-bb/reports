#6966 · Provider approval withdrawal is not forwarded

BugPriority: MediumEffort: Mediumprovidersprovider-claude-codeGitHub issue

2026-11-03 · trusted base d083003e469db9fa4b85d6abe56519e0e034b25f

PARTIALLY REPRODUCED · Root-cause confidence: high for the missing bridge cancellation; medium for the complete reported hook-to-queue sequence.

1. TL;DR

A provider can withdraw a tool-approval request after bb has already received it. The Claude bridge correctly settles its own SDK callback on withdrawal, but sends no message to the rest of bb. A focused test against unchanged production code confirms that information is lost, and a second clean checkout gives the same result. Static tracing shows why a separately persisted approval could then keep a later message waiting. The actual desktop, live Claude hook, completed MCP tool, and queued follow-up were not exercised here, so the overall verdict is deliberately partial rather than a claimed end-to-end reproduction.

5. Root cause

  1. The bridge generates its own interactive request ID. It stores a local waiter and sends interaction/request with that ID. The SDK control request ID is not a server interaction ID.
  2. The approval abort handler deletes that local waiter and settles the SDK callback, but does not call the transport sender: 
    const onAbort = (): void => {
  if (!threadSession.pendingInteractiveRequests.delete(requestId)) {
    return;
  }
  finish({
    behavior: "deny",
    message: "Interactive request cancelled",
    toolUseID: args.toolUseId,
  });
};

    The local deny here settles bb's callback after cancellation; it is not evidence that the already-withdrawn tool was denied by Claude or that a hook's result was undone.

  3. The runtime scopes the provider request ID and waits for the host interaction callback. That callback accepts the request but no AbortSignal.
  4. The daemon registers and waits for the interaction. The host registry keeps a distinct pending entry. Deleting the bridge's own Map entry cannot delete this entry.
  5. The server persists the provider interaction without an expiry. Interaction-settled queue dispatch checks for remaining turn-bound interactions. This explains how a stale persisted request can still prevent a follow-up from dispatching. This last causal chain is source-based, not an executed server-level reproduction.

The deeper gap is an absent request-withdrawal lifecycle across the bridge/runtime/host/server boundary, not a card-rendering refresh bug. The typed bridge notification vocabulary has no interaction-withdrawal entry. A sender-only notification would not suffice without a matching consumer and persisted-state transition.

6. Proposed fix and automation safety

Design a correlated provider-withdrawal path that retires exactly the pending request, carries cancellation through the runtime and daemon, settles the server interaction without granting permission, and wakes the existing queue machinery. Make it idempotent and test withdrawal racing with registration and with a user response. Preserve already-resolved interactions and avoid treating a provider cancellation as user approval. Reuse existing interruption machinery where its semantics match; explicitly assess version compatibility for enrolled daemons.
