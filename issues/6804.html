#6804 · Dependency resolutions and merge target poisoning

BugHighEffort: Mediumsecurity, dependencies, confirmed-reproGitHub issueNovember 2, 2026

Trusted base: 916d684ac23d0b0de82c09cfc7553a50287d2188.

Verdict: REPRODUCED · Root-cause confidence: high. This verdict covers the vulnerable dependency inventory and the directly tested deepmerge behavior, not a demonstrated remote exploit of bb.

1. TL;DR

A frozen installation of trusted main resolves all four reported dependency families to versions included in current GitHub advisory ranges. Loading the deepmerge installation through the mobile workspace’s Expo dependency reproduces an unwanted inherited property on the returned object. The target-copy loop assigns a special property to a normal object without the safety check present in the source-copy loop. This changes only the returned object’s prototype; the test does not modify the global Object prototype. A second freshly installed checkout produces the same failure and dependency inventory.

Scope: no bb server, real account, provider session, or user data was used. Remote reachability, harmful application behavior, and the other three advisories’ exploit mechanisms were not demonstrated. High priority reflects a verified dependency security defect needing maintenance; this is not evidence of an active outage or confirmed remotely reachable compromise.

5. Root cause

The mobile manifest selects Expo, and the Expo config snapshot selects deepmerge 4.3.1 and glob 13.0.6. The root dependency policy supplies no override or patch for these four families. A frozen install faithfully reproduces that policy; this is not a stale local node_modules artifact.

In the installed deepmerge 4.3.1 dist/cjs.js, lines 79–95 contain these relevant operations:

function mergeObject(target, source, options) {
  var destination = {};
  if (options.isMergeableObject(target)) {
    getKeys(target).forEach(function(key) {
      destination[key] = cloneUnlessOtherwiseSpecified(target[key], options);
    });
  }
  getKeys(source).forEach(function(key) {
    if (propertyIsUnsafe(target, key)) {
      return
    }
    ...
  });
  return destination
}

The target branch performs an ordinary assignment to a new {} destination. Assigning its own enumerable __proto__ target key invokes the inherited prototype setter instead of defining a normal data property. The source branch has a separate safety check, which explains why the empty-target control passes while the target-side regression fails. The marker is inherited by the result, not present as its own property, and not installed on Object.prototype.

Both frozen installations loaded identical dependency bytes. SHA-256 of the tested dist/cjs.js:

2e5160f84a1141bd927264afe4d15766f1e6cf07daef182b37ff53fea121de7d

Additional pinned evidence: glob package entries, minimatch entries, ts-deepmerge entry, and the additional provider development dependency. The installed Expo config build/Config.js also calls deepmerge with the base configuration as the first argument at line 387, but this report does not assert that bb exposes malicious configuration to that path.

6. Proposed fix and automation safety

Maintain the dependency policy as a deliberate dependency/packaging change: evaluate compatible fixed releases, regenerate the lockfile, and test each affected caller rather than assuming a cross-major override is safe. For deepmerge, a reviewed mitigation must prevent dangerous keys from changing the destination’s prototype in either copy path and preserve ordinary merges. The regression above provides a failing behavioral check for that work.

No autopilot fix or new PR: the verified cause is in locked third-party dependencies. Addressing these resolutions requires dependency/lockfile or packaging changes, explicitly outside this rule’s simple-fix conditions. No production fix was attempted, no source branch was created, and no dependency patch was applied. In particular, this report does not claim a passing after-fix test.
