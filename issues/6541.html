#6541 · Desktop restore scheduling and redundant native menus

BugPriority: MediumEffort: Lowdesktop · perf · confirmed-reproIssue

Verdict: REPRODUCED · Root-cause confidence: high (production-owner tests, not a macOS live-app reproduction).

1. TL;DR

Restoring multiple saved desktop windows waits for each page navigation before it starts creating the next window. A slow first page therefore delays every subsequent window, even though the windows can load independently. Separately, every accepted system-settings refresh asks Electron to build and replace the application menu, whether or not any displayed item or accelerator changed. Both mechanisms reproduce on trusted main in two separate checkouts using newly authored regression tests. No issue-provided code, commands, branches, or test files were executed.

5. Root cause

apps/desktop/src/desktop-window-factory.ts:439 awaits each createWindow in a loop:

    const restoredWindows: DesktopBrowserWindow[] = [];
    for (const entry of entries) {
      restoredWindows.push(
        await createWindow({
          initialUrl: restoreArgs.initialUrl,
          stateKey: entry.stateKey,
        }),
      );
    }
    return restoredWindows;

That promise includes the initial navigation (apps/desktop/src/desktop-window-factory.ts:405); construction of the next saved window is therefore gated by completion of the previous page.

apps/desktop/src/main.ts:1046 resolves accelerators and calls refreshApplicationMenu unconditionally after a successful, current settings request. apps/desktop/src/menu.ts:359 then always builds and installs a native menu:

export function installApplicationMenu(args: InstallApplicationMenuArgs): void {
  const menu = Menu.buildFromTemplate(buildApplicationMenuTemplate(args));
  const onServerMenuWillShow = args.onServerMenuWillShow;
  if (onServerMenuWillShow !== undefined) {
    for (const id of SERVER_MENU_ITEM_IDS) {
      menu.getMenuItemById(id)?.submenu?.on("menu-will-show", () => {
        onServerMenuWillShow();
      });
    }
  }
  Menu.setApplicationMenu(menu);

There is no content-equivalence check. The activation hook at apps/desktop/src/main.ts:2885, the configuration-sync open/realtime callbacks at apps/desktop/src/main.ts:1005, and the polling setup at apps/desktop/src/main.ts:1070 all reach this path. Window registration already occurs before first navigation; this is a distinct scheduling defect, not late registration.

6. Proposed fix and safety

Use Promise.all over the saved entries, preserving the returned array's persisted order while allowing navigation to overlap. Reuse the installed native menu when its serialized template and ordered server IDs are unchanged and Electron still has that same menu installed. Refresh retained callback arguments even when skipping native replacement, and always dispatch the server-open hook through the latest arguments. Invalidate the cache before radio/checkbox actions because Electron may mutate checked state even if the action fails and application settings stay unchanged.

The implemented candidate changes four desktop-subsystem files, 271 text lines counting additions plus deletions. It adds no dependency, public API, protocol, schema, stored-data, packaging, migration, or release change. The unchanged empty-state fallback is retained. The fix does not promise native show/compositor order.
