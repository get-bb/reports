1. TL;DR

The report describes a desktop copy action announcing success while a subsequent paste still contains older text. On trusted main, both thread-link copy paths await the browser write before choosing success; success is conditional on that write resolving or the editing-command fallback returning true. The related source tests pass in two clean checkouts, but those tests mock browser or Electron boundaries and cannot verify a system clipboard. A real Electron window could not be started here: its executable exits before application code because a required Linux library is missing, and this host also has no graphical display or Xvfb. The native symptom and its root cause remain unverified, so a production fix or regression-fixing PR would be speculative.

5. Root cause: not established

The following mechanism is verified from the pinned source, but is not proof of an OS clipboard failure:

  1. The core thread menu supplies the thread URL and success/failure messages to the shared helper.
  2. The sidebar menu does the same through the thread-list plugin's local clipboard helper. The reported action's exact menu was not established.
  3. The shared text helper uses the browser API first and the editing-command fallback after an unavailable or rejected API.
  4. The shared toast wrapper and plugin wrapper report success only after that helper returns true.
try {
  await navigator.clipboard.writeText(text);
  return true;
} catch {}
return copyWithEditingCommand(text);
const copied = await copyTextToClipboard(text);
if (copied) {
  if (successMessage) toast.success(successMessage);
  return true;
}
if (errorMessage) toast.error(errorMessage);
return false;

The fallback's success signal is document.execCommand("copy"); see the selection and cleanup code. Neither helper reads the native clipboard back. Therefore an underlying write API that reports success without changing the desired system buffer could produce the described notification, but no such API behavior was observed. A later external overwrite could also leave older contents; that is likewise untested.

The Electron context menu's Copy Link is a different path: it calls native clipboard.writeText directly, without this toast wrapper. Its mocked test passing does not establish the health of the renderer action.

The embedded browser-view permission policy allows sanitized clipboard writes, but it governs embedded tabs, not proof of the main application renderer's behavior. No permission-policy change is justified by this investigation.
