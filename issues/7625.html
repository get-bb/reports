#7625 · Shared storage parent in workspace permissions

BugPriority: MediumEffort: Mediumprovidershostprovider-claude-codeGitHub issue2026-11-16

Verdict: REPRODUCED · Root-cause confidence: high · reproduction label: confirmed-repro.

Trusted base: da3e60b81d560e114a2bec724bb59c997aaaae7f on origin/main.

1. TL;DR

The host daemon puts the shared thread-storage parent into an environment-wide write-root list. Claude Code's workspace-scoped session builder advertises that parent as an additional directory and, when sandboxing is enabled, puts it in the filesystem write allowlist. The thread environment instead points BB_THREAD_STORAGE at a child directory belonging to that thread. A direct harness against the real manager, runtime, and session builder reproduced the mismatch twice, including in a second clean checkout. This verifies incorrect configuration, not a particular language-model decision to save a file or an executed cross-thread sandbox escape.

5. Root cause

  1. RuntimeManager merges the shared storage parent into workspace write roots: 
    const roots = [...args.workspaceRoots];
if (args.threadStorageRootPath) {
  roots.push(args.threadStorageRootPath);
}
return [...new Set(roots)];
    Environment creation passes both that list and the shared root to the runtime. The list is not thread-specific.
  2. The provider process manager forwards the runtime-wide roots to its adapter. The registry adds them to static provider options, and Claude session-parameter assembly reads them unchanged.
  3. Workspace sandbox assembly uses the same list: 
    const allowWrite = params.additionalWorkspaceWriteRoots ?? [];
...(allowWrite.length > 0
  ? { filesystem: { allowWrite: [...allowWrite] } }
  : {})
    Additional-directory assembly also uses it: 
    const additionalDirectories = isWorkspaceWriteSession(params)
  ? (params.additionalWorkspaceWriteRoots ?? [])
  : [];
    The resulting SDK options therefore advertise the parent.
  4. In contrast, the thread-storage resolver joins the root and thread ID, thread-environment resolution supplies that child, and the shell-environment builder assigns it to BB_THREAD_STORAGE. These two paths disagree about scope.
  5. Current inline-vis resolves a thread-storage preview through that thread's storage location, not an environment-wide provider write list. Saving a file under the parent does not make it a child of the thread's artifact root. The historical absolute-path refusal is not asserted as a reproduced current UI behavior.

An existing runtime-manager test explicitly expects the shared root. This explains why the existing suite can pass despite the new isolation assertion failing.

6. Proposed fix and automation safety

Keep workspace/git-metadata roots environment-scoped, but derive a thread's artifact directory at a thread-aware session boundary. Grant and advertise that directory consistently with BB_THREAD_STORAGE without retaining the shared parent. Before implementing, verify how static adapter options interact with sessions sharing a provider process, resume/restart paths, and other providers; preserve legitimate workspace metadata access.

No automatic PR: this changes filesystem permission/security boundaries and spans host/runtime/provider responsibilities. Those are explicit exclusions from the simple-fix rule, irrespective of line count. No production patch, fix branch, or source push was made. An eventual maintainer-owned change should replace the existing parent-root expectation and demonstrate that sibling storage is not granted while each thread retains access to its own artifacts.
