1. TL;DR

The issue describes Pi catalog and thread startup failures on a Windows execution machine, despite Pi working outside bb. The current bb extension assumes Node can wrap inherited descriptor 4 with net.Socket; a synchronous constructor failure aborts extension initialization before its error listener exists. Running the real extension through Pi's real extension loader on Linux reproduced the identical loader error when descriptor 4 was deliberately closed; a real POSIX pipe control loaded successfully. The same probe produced identical results in a second clean checkout. This demonstrates the failure mechanism, not the reported Windows transport failure: no Windows machine or Pi 1.4.0 installation was available, so neither Windows handle inheritance nor the reporter's end-to-end environment is confirmed.

import assert from "node:assert/strict";
import { spawnSync } from "node:child_process";
import { mkdtempSync, readFileSync, rmSync, writeFileSync } from "node:fs";
import { tmpdir } from "node:os";
import { join, resolve } from "node:path";
import { pathToFileURL } from "node:url";
import { runInNewContext } from "node:vm";

const checkout = resolve(process.argv[2] ?? ".");
const pluginRoot = join(checkout, "plugins/provider-pi");
const runtimeRoot = join(pluginRoot, "node_modules/@earendil-works/pi-coding-agent");
const loaderUrl = pathToFileURL(join(runtimeRoot, "dist/core/extensions/loader.js")).href;
const sourcePath = join(pluginRoot, "src/bridge/bb-pi-extension.ts");
const extensionSource = runInNewContext(
  readFileSync(sourcePath, "utf8").replace("export const", "const") + "; BB_PI_EXTENSION_SOURCE",
);
const probeRoot = mkdtempSync(join(tmpdir(), "bb-6790-descriptor-"));

try {
  writeFileSync(join(probeRoot, "bb-pi-extension.mjs"), extensionSource);
  writeFileSync(
    join(probeRoot, "entry.mjs"),
    `import extension from "./bb-pi-extension.mjs";
import { closeSync } from "node:fs";
export default function probe(pi) {
  if (process.env.PROBE_CLOSE_FD === "1") closeSync(4);
  return extension(pi);
}
`,
  );
  const childSource = `
import { loadExtensions } from ${JSON.stringify(loaderUrl)};
const result = await loadExtensions([${JSON.stringify(join(probeRoot, "entry.mjs"))}], ${JSON.stringify(probeRoot)});
console.log(JSON.stringify({ extensions: result.extensions.length, errors: result.errors.map(entry => entry.error) }));
`;
  for (const closeDescriptor of [false, true]) {
    const result = spawnSync(process.execPath, ["--input-type=module", "-e", childSource], {
      cwd: probeRoot,
      env: {
        PATH: process.env.PATH,
        SystemRoot: process.env.SystemRoot,
        HOME: probeRoot,
        USERPROFILE: probeRoot,
        XDG_CONFIG_HOME: probeRoot,
        PI_CODING_AGENT_DIR: probeRoot,
        PROBE_CLOSE_FD: closeDescriptor ? "1" : "0",
      },
      encoding: "utf8",
      stdio: ["ignore", "pipe", "pipe", "pipe", "pipe"],
      timeout: 30_000,
    });
    assert.ifError(result.error);
    assert.equal(result.status, 0, result.stderr);
    const observation = JSON.parse(result.stdout.trim());
    console.log(`${closeDescriptor ? "CLOSED_FD" : "PIPE_CONTROL"} ${JSON.stringify(observation)}`);
    if (closeDescriptor) {
      assert.equal(observation.extensions, 0);
      assert.deepEqual(observation.errors, ["Failed to load extension: Unsupported fd type: UNKNOWN"]);
    } else {
      assert.equal(observation.extensions, 1);
      assert.deepEqual(observation.errors, []);
    }
  }
  console.log("PASS: original extension loads with a POSIX pipe and fails with an unrecognized fd.");
  console.log("LIMIT: deliberately closed descriptor, not a Windows inherited-pipe reproduction.");
} finally {
  rmSync(probeRoot, { recursive: true, force: true });
}

5. Root cause

Verified conditional mechanism: the Node branch of bbExtension assumes descriptor 4 is a handle type that net.Socket can attach to. The constructor can throw synchronously. Registering an asynchronous error listener on the next line cannot intercept a constructor failure, so initialization stops before normal session handlers and readiness signaling are established.

const bridgeIn = new Socket({ fd: BRIDGE_TO_CHILD_FD, readable: true, writable: false });
bridgeIn.on("error", () => undefined);
bridgeIn.unref();
readLines(bridgeIn, onBridgeLine);
  • Extension runtime split and unguarded Node Socket construction. Bun has a different stream path; this investigation exercises only Node.
  • Five stdio entries and parent-side descriptors 3/4. The launcher requesting pipes does not by itself establish that child-side Node can rewrap the Windows handle.
  • Catalog extension argument and session extension argument explain how the same initialization failure could affect both surfaces.
  • Existing Windows-only round-trip tests use a child with its own Socket reader. They were skipped on this Linux host and are not evidence of Windows success or failure here.

Still unknown: whether the reporter's Windows process loses descriptor 4, receives a valid but unwrappable handle, or encounters another launch/runtime issue. The same error is not proof that a closed Linux descriptor and a Windows inherited pipe have the same underlying cause. Confidence is medium for applying this mechanism to the reported failure; the conditional constructor failure itself was directly observed twice.

6. Proposed next test and fix constraints

First run the existing Windows round-trip test with the actual Node/Pi installation in an isolated Windows environment, then load the real bb extension through PiRpcChild and exercise bidirectional tool results plus clean shutdown. Establish whether the inherited handle is missing or merely unsuitable for Socket wrapping before changing transport code. Only then choose an existing portable read mechanism or a Windows-specific transport that preserves framing, nonblocking behavior, EOF handling, and process-exit behavior. Merely swallowing the constructor exception would leave tool results and readiness broken and is not a fix.
