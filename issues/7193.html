#7193 · Cross-host retirement starvation

Bug Priority: Medium Effort: Medium workspaces · GitHub issue · 2026-11-06

Trusted base: bcfdf1ca3c3a6ff60385ab323c5a551f943a0bff, fetched from the target repository’s origin/main.

Verdict: REPRODUCED · Root-cause confidence: medium · Reproduction label: confirmed-repro

1. TL;DR

An unused environment can remain ready / retiring after its retirement deadline because the server stops checking deadlines while an unrelated environment removal is still running. The environment lifecycle sweep awaits every removal before releasing its periodic-job running flag. Later timer ticks skip the entire lifecycle job, even when the newly expired environment belongs to another host with an available cleanup slot. A deterministic server test reproduces this on trusted main in two clean source checkouts, and an additional diagnostic verifies that explicitly requesting cleanup bypasses the blocked periodic job. The scheduling defect is established; attributing the original Windows session to this trigger remains an inference.

Scope: this is a real server lifecycle/SQLite reproduction with a deliberately delayed provider callback, not an end-to-end Windows, Connect, shell-hook, or physical worktree-removal test. It seeds the post-deletion thread state. The original session was not inspected, and clock skew there remains unverified.

it("retires an expired environment while another host is still removing one", async () => {
    vi.useFakeTimers({ toFake: ["Date"] });
    await withTestHarness(async (harness) => {
      let releaseRemoval = () => {};
      const removalGate = new Promise<void>((resolve) => {
        releaseRemoval = resolve;
      });
      let slowRemovalStarted = false;
      const fixture = setup(harness, {
        policy: { retireGraceMs: 60_000 },
        remove: async ({ path }) => {
          if (path === "/tmp/slow-retirement") {
            slowRemovalStarted = true;
            await removalGate;
          }
          return { status: "removed" };
        },
      });
      fixture.ask();
      await fixture.settled();
      const environmentId = fixture.attach();
      harness.db
        .update(threads)
        .set({
          environmentId,
          status: "idle",
          archivedAt: Date.now(),
          deletedAt: Date.now(),
        })
        .where(eq(threads.id, fixture.thread.id))
        .run();
      await sweepProviderEnvironment(harness.deps, environmentId);
      const retireAt = getEnvironment(harness.db, environmentId)!.retireAt!;
      const { host } = seedHostSession(harness.deps, {
        id: "host_slow_retirement",
      });
      const slowEnvironment = seedEnvironment(harness.deps, {
        hostId: host.id,
        projectId: fixture.context.project.id,
        path: "/tmp/slow-retirement",
        environmentProviderId: fixture.record.provider.id,
        environmentProviderPluginId: fixture.record.pluginId,
      });
      harness.db
        .update(environments)
        .set({ retireAt: Date.now() - 1 })
        .where(eq(environments.id, slowEnvironment.id))
        .run();
      const deps = {
        ...harness.deps,
        pluginSchedules: harness.pluginService,
        plugins: harness.pluginService,
      };
      const firstSweep = runPeriodicSweeps(deps);
      try {
        await expect.poll(() => slowRemovalStarted).toBe(true);
        vi.setSystemTime(retireAt + 1);
        await runPeriodicSweeps(deps);
        await expect
          .poll(() => getEnvironment(harness.db, environmentId)?.status, {
            timeout: 1_000,
          })
          .toBe("destroyed");
        expect(getEnvironment(harness.db, slowEnvironment.id)).toMatchObject({
          teardownStatus: "running",
        });
      } finally {
        releaseRemoval();
        await firstSweep;
        await expect
          .poll(() => getEnvironment(harness.db, slowEnvironment.id)?.status)
          .toBe("destroyed");
      }
    });

5. Root cause

  1. sweepProviderLifecycles enumerates candidates, starts each sweep, and waits for every returned promise:
    pending.push(sweepProviderEnvironment(deps, row.id).catch(...));
await Promise.all(pending);
    The target’s first visit sees a future deadline, so it returns without removal. A different host’s removal remains pending.
  2. runPeriodicSweepJob keeps its job-level running flag set until that entire promise resolves. Overlapping ticks return immediately for the running job:
    if (state.running) return;
state.running = true;
try { await job.run(...); }
finally { state.running = false; }
    The snippets are shortened to show the control flow; see the permalink for the complete implementation.
  3. The periodic job table uses awaited environment sweeping, whereas the adjacent machine lifecycle job already uses background mode. Thus environment deadlines that expire during a long removal are not revisited by later ticks.
  4. The environment response calls any non-destroyed environment with a retirement timestamp and no teardown status retiring; it does not itself execute cleanup. This explains the visible expired ready/retiring state.
  5. Explicit removal records teardown intent and invokes the environment’s own sweep, bypassing the periodic job’s running guard. The diagnostic confirms this distinction.

Cleanup intentionally serializes operations on each host and caps concurrent cleanup globally. This reproduction uses two different hosts so it isolates job-level starvation rather than that deliberate per-host serialization. Teardown hooks can take up to fifteen minutes before transport grace, and provider removal can also be long-running; the exact blocker in the reported session is unknown.

6. Proposed fix

Add an internal background option to the environment lifecycle sweep and enable it only for periodic dispatch, matching the existing machine lifecycle pattern. The periodic job should enumerate and dispatch eligible work, then release its job-level running flag without waiting for slow removals. Preserve default awaited behavior for direct callers, existing per-environment operation deduplication, error logging, event-loop yielding, retry policy, and per-host cleanup serialization. Keep the existing enumeration counter independent of whether promises are awaited so background dispatch still yields every 25 candidates.

The focused regression must fail before the repair and pass afterward; the existing environment orchestration, periodic-sweep, path-claim, provisioning, and public cleanup tests should remain green. No wire contract, persisted data, dependency, migration, or user-facing configuration change is needed.
