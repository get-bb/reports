#5846 · Logged background children omit Windows console suppression

1. TL;DR

The report describes an unwanted terminal window during Windows background-daemon startup. Trusted main does launch logged child processes without explicitly requesting hidden Windows consoles, and a real-child diagnostic confirmed that omission twice in clean checkouts. The installer has a separate WMI launch step that requests a hidden show state but does not set a detached-process creation flag. This investigation ran on Linux, so it cannot establish the reported Windows Terminal behavior or validate a platform-specific repair. No pull request was opened: the required full reproduction and before/after Windows regression proof are missing.

5. Root cause

Verified implementation gap: spawnLoggedProcess opens log-file descriptors and passes only the working directory, environment, and stdio configuration to Node's spawn API:

return spawn(args.command, args.args, {
  cwd: process.cwd(),
  env: args.env,
  stdio: args.ipc === true ? ["ignore", fd, fd, "ipc"] : ["ignore", fd, fd],
});

The installer invokes the launcher with supervision enabled, as seen in runDaemon. The launcher's startDaemon closure creates the managed daemon via spawnNamedManagedProcess, which delegates to this helper. The restart loop calls the same daemon-start closure again. Thus the omission exists at the actual managed-child boundary, including supervised restarts, rather than merely in an unused utility.

Separate earlier boundary: installer spawnDaemon already requests hidden detached launch for its own child. The top-level WMI creation script and its caller request a hidden show state for the created process and windowsHide: true for PowerShell itself. These are different process boundaries; suppressing one does not establish what the other requests. The logon command also uses a PowerShell hidden-window request.

Inference, not observed Windows behavior: missing console suppression on a newly launched managed child is consistent with the reported visible-console symptom. Whether the default Windows terminal host disregards the WMI show-state request, whether a new console is allocated in each launch path, and which process owns any visible window remain unverified. Root-cause confidence for the full user-visible defect is therefore medium; confidence in the missing spawn option is high.

History inspection associated the logged-process helper with the existing terminal-backpressure/log-redirection work. The current tests exercise redirected streams and failure behavior, but do not test real Windows console visibility.

6. Proposed fix and safety gate

The smallest candidate at the observed gap is to make the logged-child launch explicitly request hidden Windows console behavior while preserving file stdio and optional IPC. This is a proposal derived from the trusted helper, not an applied patch. First establish an OS-level regression on Windows that launches from a console-free parent and verifies the resulting process/window state. Exercise daemon startup, supervised restart, and the independent top-level WMI/logon path with Windows Terminal as default.

Evaluate any WMI process-creation change in a separate real Windows experiment; the reported flag-acceptance results were not verified here. Preserve child lifetime after the launcher exits, logging, IPC, daemon readiness, and normal stop behavior. Do not assume that a passing Linux option diagnostic proves any of these Windows lifecycle outcomes.
