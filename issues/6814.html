#6814 · Late terminal text insertion is not forwarded

BugHighEffort: Lowmobilepartial-reproGitHub issue2026-11-02 · base 916d684ac23d

Verdict: PARTIALLY REPRODUCED · Root-cause confidence: high for the event-order mechanism; native iOS keyboard behavior is unverified.

1. TL;DR

The issue reports that selecting a Chinese keyboard candidate on an iPhone produces no terminal input. On the current trusted main commit, the exact xterm dependency used by bb loses inserted text when the textarea is updated after its keydown timer but before keyup. An original executable test reproduces that loss in two separate clean checkouts; three nearby control cases pass in each. The underlying problem is that xterm equates a preceding keydown with input already being handled, even when its earlier textarea check emitted nothing. This is a partial reproduction because this investigation uses synthetic DOM events in jsdom, not a physical iPhone, Safari, or a live bb terminal.

async function exercise(name, mode) {
  const dom = new JSDOM('<!doctype html><div id="terminal"></div>', {
    pretendToBeVisual: true,
    runScripts: 'outside-only',
  });
  const { window } = dom;
  window.structuredClone = structuredClone;
  window.matchMedia = () => ({ matches: false, addListener() {}, removeListener() {} });

  const terminal = new window.Terminal({ cols: 32, rows: 4 });
  const received = [];
  const events = [];
  try {
    terminal.open(window.document.getElementById('terminal'));
    terminal.onData((data) => received.push(data));
    const textarea = terminal.textarea;
    assert.ok(textarea);
    for (const type of ['keydown', 'beforeinput', 'input', 'keyup']) {
      textarea.addEventListener(type, (event) => events.push({
        type,
        keyCode: event.keyCode ?? null,
        composed: event.composed,
        value: textarea.value,
        received: [...received],
      }));
    }
    const nextTask = () => new Promise((resolve) => window.setTimeout(resolve, 0));
    const release = () => textarea.dispatchEvent(new window.KeyboardEvent('keyup', {
      key: 'Unidentified', bubbles: true, keyCode: 0,
    }));
    const insert = () => {
      const options = { bubbles: true, composed: true, data: candidate, inputType: 'insertText' };
      textarea.dispatchEvent(new window.InputEvent('beforeinput', options));
      textarea.value = candidate;
      textarea.dispatchEvent(new window.InputEvent('input', options));
    };
    if (mode === 'latin') {
      textarea.dispatchEvent(new window.KeyboardEvent('keydown', {
        bubbles: true, key: 'q', code: 'KeyQ', keyCode: 81,
      }));
      release();
    } else {
      textarea.dispatchEvent(new window.KeyboardEvent('keydown', {
        bubbles: true, key: 'Unidentified', keyCode: 229,
      }));
      if (mode !== 'early') await nextTask();
      if (mode === 'released') release();
      insert();
      if (mode !== 'released') release();
    }
    await nextTask();
    const expected = mode === 'latin' ? ['q'] : [candidate];
    const result = { name, expected, actual: received, events };
    console.log(JSON.stringify(result));
    assert.deepEqual(received, expected);
    return true;
  } catch (error) {
    if (error.code !== 'ERR_ASSERTION') throw error;
    console.log('CONTRACT FAILURE: ' + name);
    return false;
  } finally {
    terminal.dispose();
    window.close();
  }
}

5. Root cause

Trusted bb source pins the dependency at apps/app/package.json:73. The terminal mounts at ThreadTerminalView.tsx:1143. Its public onData subscription at line 1281 forwards what xterm emits; it cannot recover data xterm never emits.

The following dependency excerpts are from that pinned package, not from a linked pull request. The inline source evidence records source filenames, exact line numbers, and SHA-256 hashes; dependency files themselves are not tracked in the bb repository.

  1. CoreBrowserTerminal.ts:845: keydown sets _keyDownSeen = true before calling the composition helper.
  2. CompositionHelper.ts:131: a non-composition process-key event schedules _handleAnyTextareaChanges() and returns without ordinary key processing.
  3. CompositionHelper.ts:212: the helper compares textarea values in a zero-delay timer. In the failing case both values are empty, so it emits nothing.
  4. CoreBrowserTerminal.ts:1032: the later composed input is rejected while the earlier keydown is still recorded: 
    ev.data && ev.inputType === 'insertText' &&
(!ev.composed || !this._keyDownSeen) &&
!this.optionsService.rawOptions.screenReaderMode
  5. CoreBrowserTerminal.ts:950: keyup clears the flag, but does not retry the rejected input. The candidate therefore never reaches onData.

The deeper issue is using “keydown observed” as a proxy for “text delivered.” The nearby passing controls establish that this is an ordering-dependent loss, not a generally nonfunctional terminal in the harness. Actual iOS generation of the sequence remains outside the verified boundary.

6. Proposed fix

Recover a non-composing late text insertion only when the process-key textarea check has completed without delivering input. Route it through xterm's public input path, suppress recovery if any equivalent data was already emitted, and clear pending state on composition, replacement key activity, and disposal. Do not forward all input events unconditionally: that would duplicate ordinary key and composition delivery. Extend the focused test to cover multiple candidates, real composition, cancellation, paste, and teardown, then verify on Safari with a native Pinyin keyboard.

No production change was made. Open PR #6815 already links this issue through GitHub closing-issue metadata. Opening a duplicate fix would violate the autopilot rule; moreover native-device reproduction is still incomplete.
