#5779 · Download attribution bypasses privacy signals

BugPriority: MediumEffort: MediumsecurityGitHub issue2026-10-19

Base: 57c37177e4030a3f02a531a6bc040e30cfe887b1

Verdict: REPRODUCED · Root-cause confidence: high

1. TL;DR

A browser privacy signal does not currently stop Google click IDs from being saved and attached to download links. The client carries its complete campaign allowlist without checking the signal, while the server sends attribution properties and raw request/referrer URLs without checking the request signal. Two clean checkouts of trusted main produce the same five intended failures, with four privacy-disabled/unavailable controls passing. Ordinary installer delivery and the other exercised campaign parameters still work; 19 existing download tests pass. This is a nonvisual, owner-boundary reproduction, not a live production browser or analytics-service observation.

5. Root cause

The shared campaign allowlist includes gclid. The browser owner writes every allowlisted landing parameter, reads old saved values unchanged, and appends them to download links without consulting navigator.globalPrivacyControl. If accessing storage throws, the function returns immediately, so it cannot sanitize even an existing link.

6. Proposed fix

At the client owner, use an explicitly true browser signal to remove gclid from incoming/saved attribution and direct download hrefs. Keep event registration and sanitization available when storage is blocked, and retain unrelated campaign values. At the endpoint, use Sec-GPC: 1 to sanitize request/referrer query parameters before copying attribution and URL properties. Preserve the current disabled/unavailable behavior and normal installer delivery. This is a technical fix proposal, not a legal-compliance determination; no broader tracking-policy claims are made.
