#6266 · ACP form capacity and unsupported-response ambiguity

BugPriority: MediumEffort: Mediumprovidersprovider-acpGitHub issue2026-10-25 · base a6fff60f53c615a109103075328bf7017431e792

Verdict: PARTIALLY REPRODUCED · Root-cause confidence: high for bb's field cap and missing agent-facing reason; unverified for real omp cancellation wording.

1. TL;DR

ACP forms with more than four schema properties are rejected before any user question is shown. Three or four logical choices with separate optional text companions produce six or eight properties and hit this cap. The detailed rejection reason is emitted as a bb provider warning, but the agent receives only {"action":"decline"}, with neither the reason nor an origin indicating a client limitation. Contrary to the broad cancellation claim, the bb wire response is decline, not cancel; real omp's interpretation was not exercised. Both results repeat on a second clean trusted checkout, so the report confirms the bb defects without claiming the exact external-agent wording.

5. Root cause

Capacity is a shared payload constraint, not merely a plugin-local guard

The domain constant is four. The ACP planner counts every schema property before planning the fields and does not inspect requestedSchema.required there:

  const message = readString(params, "message")?.trim() || undefined;
  const schema = params["requestedSchema"];
  const properties = isJsonObject(schema) ? schema["properties"] : undefined;
  const entries = isJsonObject(properties) ? Object.entries(properties) : [];
  if (entries.length === 0) {
    return planConfirmation(message);
  }
  if (entries.length > USER_QUESTION_MAX_QUESTIONS) {
    return {
      kind: "unsupported",
      reason: `the form has ${entries.length} fields and bb shows at most ${USER_QUESTION_MAX_QUESTIONS}`,
    };
  }

The same constant is enforced by the shared user-question payload validator and exported by the Plugin SDK. Removing only the ACP precheck still leaves payload validation. Optional companion handling could reduce the count for some schemas, but does not establish general larger-form capacity.

The diagnostic stops at the provider warning

The bridge handler takes the unsupported plan, emits a detailed warning into bb, and replies to ACP with a plain decline:

  const plan = planAcpElicitation(params);
  if (plan.kind === "unsupported") {
    emitForSession(session, ACP_WARNING_METHOD, {
      threadId: session.bbThreadId,
      summary: "The agent asked a question bb could not show",
      details: `The request was declined because ${plan.reason}.`,
    });
    responder.result({ action: "decline" });
    return;
  }

The declared ACP response union has no reason/origin field on decline or cancel. The lack of diagnostic information on this path is established; any claim about how omp renders it remains outside the tested bb boundary. Existing coverage explicitly expects the current rejection, so merely passing those tests cannot establish a repair.

6. Proposed fix and simple-fix gate

Choose either a larger supported question contract or a multi-step presentation that aggregates answers back into one ACP response. Separately choose a protocol-compatible way to distinguish an unsupported client request from an intentional user decline and deliver actionable diagnostics. Retain real-stop cancellation behavior, test optional companions, and cover answer aggregation if pagination is chosen.

No pull request is opened. The direct cap increase changes a shared SDK-visible payload constraint, while the alternative multi-step flow and agent-facing error semantics require a product/protocol decision. Those fail the automation's no-public-schema/protocol-change and no-product-decision conditions. No production fix was attempted, staged, committed, or pushed. The report-only regression test is retained as evidence, not proposed as a passing change.
