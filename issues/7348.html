#7348 · Session renewal failures are mistaken for browser failures

Bug High Effort: Low plugins GitHub issue · November 10, 2026 · base 7c1353d80729983b86ea1555d18b42407f320406

Verdict: REPRODUCED · Root-cause confidence: high · Reproduction label: confirmed-repro

1. TL;DR

Browser Automation updates a session's expiry before and after executing a browser operation. A storage failure during the first update is treated as a browser failure: the server stops the session and, when cleanup persistence succeeds, sends a host close request. A failure only during the final update instead discards the successful execution result. Three fault-injection cases reproduce these outcomes on the trusted main commit, and the same agent repeated them in a second clean checkout. Catching renewal persistence failures locally preserves operation results and session usability without weakening startup or explicit cleanup failures.

5. Root cause

Renewal persistence rejects inside the browser execution error boundary, triggering session cleanup; a second renewal in finally can replace a successful result. The renewal helper updates in-memory timestamps, then directly awaits the save. The execution try/catch/finally puts the first renewal inside the same error boundary as the host operation and the second renewal in an unguarded finally block.

try {
  await touch(record);
  const result = await host.call(...);
  return result;
} catch (error) {
  await finish(record, "stopped").catch(() => {});
  throw error;
} finally {
  ...
  if (current?.session.state === "ready") await touch(current);
}

Cleanup marks the record stopped and saves before asking the host to close. Consequently, one-shot renewal failure can close the healthy browser, while a persistent outage can stop the server's session without reaching the host. These are different failure shapes, not evidence that the browser itself failed. Startup and explicit close writes remain intentionally outside the best-effort renewal behavior.

6. Proposed fix

Keep updating the in-memory activity deadline, but catch and warn on persistence failure within renewal itself. Let genuine host execution and cleanup errors follow their existing paths. This is a server-internal change: no public contract, wire field, database schema, dependency, permission boundary, or persisted record format changes. A failed renewal may leave an older persisted expiry until the next successful save; the live record remains authoritative during the current process.

The implemented patch changes two files and 48 text lines total (47 additions, one deletion). Three focused cases pass after the repair; the plugin's complete existing suite and regressions pass: eight files, 105 tests. Turbo lint and typecheck also pass.
