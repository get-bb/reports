#5963 · Redundant skill-tree reads during catalog resolution

BugMedium priorityLow effortthreads · perfGitHub issue2026-10-21 · base 06ae8f039a7198a6aad2b9b6e030efb88f8dd923

Verdict: REPRODUCED · Root-cause confidence: high · reproduction label: confirmed-repro.

1. TL;DR

Resolving an unchanged skill catalog still reads the skill files and hashes their full contents synchronously. A two-file synthetic skill triggers three synchronous content reads on its second catalog resolution, even though the returned catalog is unchanged. The registry remembers where each tree hash lives, but does not remember the file metadata or parsed catalog candidate that produced it. The turn-runtime configuration path calls this catalog resolver, so repeated turn starts repeat this work. This report proves the redundant I/O, not a particular production latency or slowdown.

Complete baseline reproduction test
import fs from "node:fs";
import path from "node:path";
import { makeTempDir } from "@bb/test-helpers";
import { describe, expect, it, vi } from "vitest";
import {
  readSkillTreeManifest,
  resolveSkillCatalogEntries,
  SkillTreeRegistry,
} from "../../src/services/skills/injected-skills.js";
import type { ServerLogger } from "../../src/types.js";

async function createCatalog() {
  const temp = await makeTempDir();
  const rootPath = path.join(temp, "skills", "cache-example");
  fs.mkdirSync(path.join(rootPath, "references"), { recursive: true });
  fs.writeFileSync(
    path.join(rootPath, "SKILL.md"),
    "---\nname: cache-example\ndescription: Original description\n---\n# Example\n",
  );
  const referencePath = path.join(rootPath, "references", "example.txt");
  fs.writeFileSync(referencePath, "original\n");
  const logger: ServerLogger = {
    debug: () => undefined,
    error: () => undefined,
    info: () => undefined,
    warn: () => undefined,
  };
  const skillTreeRegistry = new SkillTreeRegistry();
  return {
    rootPath,
    referencePath,
    resolve: () =>
      resolveSkillCatalogEntries(logger, {
        dataDir: temp,
        skillTreeRegistry,
      }),
  };
}

describe("skill catalog freshness", () => {
  it("reuses an unchanged tree without reading any file contents", async () => {
    const catalog = await createCatalog();
    const reads = vi.spyOn(fs, "readFileSync");
    try {
      const first = catalog.resolve();
      expect(first).toHaveLength(1);
      expect(reads.mock.calls.length).toBeGreaterThan(0);
      reads.mockClear();
      expect(catalog.resolve()).toEqual(first);
      expect(reads).not.toHaveBeenCalled();
    } finally {
      reads.mockRestore();
    }
  });

  it.each(["content", "rename", "mode", "addition", "removal"])(
    "invalidates cached hashes after a file %s change",
    async (change) => {
      const catalog = await createCatalog();
      const first = catalog.resolve();
      if (change === "content") {
        const original = fs.statSync(catalog.referencePath);
        fs.writeFileSync(catalog.referencePath, "modified\n");
        fs.utimesSync(catalog.referencePath, original.atime, original.mtime);
      } else if (change === "rename") {
        fs.renameSync(
          catalog.referencePath,
          path.join(catalog.rootPath, "references", "renamed.txt"),
        );
      } else if (change === "mode") {
        fs.chmodSync(catalog.referencePath, 0o700);
      } else if (change === "addition") {
        fs.writeFileSync(path.join(catalog.rootPath, "added.txt"), "new\n");
      } else {
        fs.rmSync(catalog.referencePath);
      }
      const updated = catalog.resolve();
      expect(updated).toHaveLength(1);
      expect(updated).not.toEqual(first);
      expect(updated[0]?.runtimeSource).toMatchObject({
        treeHash: readSkillTreeManifest(catalog.rootPath).treeHash,
      });
    },
  );

  it("refreshes frontmatter and rejects invalid trees after caching", async () => {
    const catalog = await createCatalog();
    catalog.resolve();
    fs.writeFileSync(
      path.join(catalog.rootPath, "SKILL.md"),
      "---\nname: cache-example\ndescription: Updated description\n---\n",
    );
    expect(catalog.resolve()[0]?.runtimeSource.description).toBe(
      "Updated description",
    );
    fs.rmSync(catalog.referencePath);
    fs.symlinkSync("missing.txt", catalog.referencePath);
    expect(catalog.resolve()).toEqual([]);
    fs.rmSync(catalog.referencePath);
    fs.writeFileSync(catalog.referencePath, "recovered\n");
    expect(catalog.resolve()[0]?.runtimeSource).toMatchObject({
      treeHash: readSkillTreeManifest(catalog.rootPath).treeHash,
    });
    fs.rmSync(catalog.rootPath, { recursive: true });
    expect(catalog.resolve()).toEqual([]);
  });
});

5. Root cause

Tree collection and manifest hashing traverse and read every regular file and compute the tree hash without a freshness check:

entries.push({
  bytes: fs.readFileSync(entryPath),
  mode: stat.mode & 0o777,
  path: normalizeRelativePath(path.relative(rootPath, entryPath)),
});

const entries = collectSkillTreeEntries(rootPath);
return { entries, treeHash: hashSkillTreeEntries(entries) };

Candidate resolution also reads SKILL.md to parse frontmatter before asking for a fresh manifest. It then registers only the hash-to-root mapping and returns catalog metadata; the buffers are not retained for future catalog calls. SkillTreeRegistry has no candidate freshness cache.

The caller chain is thread runtime configuration → resolveSkillCatalog → resolveSkillCatalogEntries. A registry is allocated once by server startup, so its lifetime is suitable for cache reuse across turn configurations.

6. Proposed fix

Keep candidate metadata and the tree hash in the existing server-owned SkillTreeRegistry, keyed by candidate root and an ordered fingerprint of relative file names, modes, sizes, device/inode, mtime and ctime. Continue reading directory listings and lstat metadata on every scan; reject symlinks and non-regular files as before. An unchanged fingerprint can reuse frontmatter and tree hash without reading contents. Changed metadata or a failed rebuild must discard the cached candidate and retry parsing/hashing. Retain no content buffers in the cache.

The transfer endpoint must continue reading a full current manifest and verifying the requested hash; its uncached reader remains unchanged in purpose. There are no protocol, schema, permission, public API, or dependency changes. The optimization still pays traversal/stat cost, and metadata-based freshness relies on the filesystem reporting content changes through its timestamps or identity.
