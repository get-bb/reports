#7182 · Provider questions outlive their owning turn

BugHighEffort: Mediumproviders · threads · opencode · ask-user-questionGitHub issue

November 6, 2026 · trusted main 14b3293254da0a3b4c858a01c5415d91f17aa7b5

PARTIALLY REPRODUCED · Root-cause confidence: high for the shared server lifecycle defect; the reported OpenCode deadline and silent model-delivery failure remain unverified.

1. TL;DR

A native provider question remains pending after the server has accepted completion of the turn that asked it. A later answer still passes the server's resolution entry point instead of being rejected as expired. An authored regression test demonstrates both failures for interrupted, failed, and successfully completed turns, with the same result in two clean trusted checkouts. This reproduces the orphaned-question portion of the report, not the complete legacy OpenCode incident: current main ships OpenCode through ACP with native-question support declared false, and this investigation did not run OpenCode 2.2.5 or observe model delivery.

Full regression test

import { describe, expect, it } from "vitest";
import { turnScope } from "@bb/domain";
import { groupHostDaemonEvents } from "@bb/host-daemon-contract";
import { internalAuthHeaders } from "../helpers/commands.js";
import {
  createUserAnswerResolution,
  createUserQuestionPayload,
} from "../helpers/pending-interactions.js";
import {
  seedEnvironment,
  seedHostSession,
  seedProjectWithSource,
  seedThread,
  seedTurnStarted,
} from "../helpers/seed.js";
import { withTestHarness } from "../helpers/test-app.js";

describe("provider question lifetime", () => {
  it.each(["interrupted", "failed", "completed"] as const)(
    "closes a native question when its owning turn is %s",
    async (status) => {
      await withTestHarness(async (harness) => {
        const { host, session } = seedHostSession(harness.deps);
        const { project } = seedProjectWithSource(harness.deps, {
          hostId: host.id,
        });
        const environment = seedEnvironment(harness.deps, {
          hostId: host.id,
          projectId: project.id,
        });
        const thread = seedThread(harness.deps, {
          projectId: project.id,
          environmentId: environment.id,
          providerId: "claude-code",
          status: "active",
        });
        const turnId = "turn-question-lifetime";
        const providerThreadId = "provider-question-lifetime";
        seedTurnStarted(harness.deps, {
          threadId: thread.id,
          turnId,
          providerThreadId,
        });
        const created =
          harness.deps.pendingInteractions.registerPendingInteraction({
            interaction: {
              threadId: thread.id,
              turnId,
              providerId: "claude-code",
              providerThreadId,
              providerRequestId: "request-question-lifetime",
              payload: createUserQuestionPayload(),
            },
          });
        if (created.outcome === "rejected") {
          throw new Error(created.reason);
        }
        const interactionId = created.interaction.id;
        const response = await harness.app.request("/internal/session/events", {
          method: "POST",
          headers: internalAuthHeaders(harness),
          body: JSON.stringify({
            sessionId: session.id,
            eventGroups: groupHostDaemonEvents([
              {
                threadId: thread.id,
                event: {
                  type: "turn/completed",
                  threadId: thread.id,
                  providerThreadId,
                  scope: turnScope(turnId),
                  status,
                },
              },
            ]),
          }),
        });
        expect(response.status).toBe(200);
        const afterCompletion =
          harness.deps.pendingInteractions.getThreadInteraction({
            interactionId,
            threadId: thread.id,
          });
        expect.soft(afterCompletion.status).toBe("interrupted");
        expect(() =>
          harness.deps.pendingInteractions.resolvePendingInteraction({
            interactionId,
            threadId: thread.id,
            resolution: createUserAnswerResolution(),
          }),
        ).toThrow();
      });
    },
  );
});

5. Root cause

The event handler dispatches turn/completed to the turn-completion service, which updates thread lifecycle and pruning but does not settle pending provider interactions: apps/server/src/internal/events.ts:494–511 and apps/server/src/internal/turn-completed-events.ts:34–73.

The interaction resolver checks row ownership, row status, and answer shape, then queues a resolution. It does not check whether the interaction's owning turn has completed: apps/server/src/services/interactions/pending-interactions.ts:762–807. Registration has a completed-turn guard, but that guard cannot close a question registered before the turn finishes: apps/server/src/services/interactions/pending-interactions.ts:430–458.

The result follows directly: a previously registered question retains pending status, so a subsequent submission is accepted. This is the demonstrated shared lifecycle bug. It does not, by itself, prove a model-delivery loss: apps/server/src/services/interactions/pending-interactions.ts:844–876 interrupts ordinary failed deliveries, retains host-unavailable deliveries, and treats some redelivered stale answers specially. The daemon registry also rejects an unknown request, while a delivered tombstone is idempotent: apps/host-daemon/src/interactive-request-registry.ts:178–213.

The plugin gate remains capability-based: plugins/ask-user-question/src/server.ts:131–139. Its configurable deadline belongs to the plugin request: plugins/ask-user-question/src/server.ts:75–85. However, the current ACP declaration sets supportsNativeUserQuestion: false: plugins/provider-acp/src/declaration.ts:8–17; OpenCode is listed as an ACP agent: plugins/provider-acp/src/known-agents.ts:87–103. There is no basis here to claim current main reproduces the legacy bridge's exact gating behavior.

6. Proposed fix and safety gate

A narrowly scoped follow-up should interrupt still-pending provider-origin questions for the exact completed turn and make resolution reject completed-turn questions atomically. Preserve asynchronous plugin cards, other turns' requests, and resolving answers already delivered or awaiting acknowledgement. Cover those races and scope boundaries before shipping. Late-answer conversion to a follow-up user message is a separate product behavior, not an assumption made by this report.

No production fix or pull request was attempted. The report is only partially reproduced, and the reported legacy provider path is absent from current main. A safe full-incident regression and verification of deadline cancellation versus successful delivery were not established, so the autopilot's reproduced-bug simple-fix gate is not satisfied. No linked open pull request was found in issue cross-references or the numeric open-PR search at investigation time.
