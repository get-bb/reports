#7697 · Redundant validation on successful daemon RPC sends

BugPriority: LowEffort: Lowhost · perf · confirmed-reproGitHub issue2026-11-17

Trusted base: 1320c88e8abdd3f145bc9a5c305eace269fb2f28. Verdict: REPRODUCED. Root-cause confidence: high.

1. TL;DR

Successful host RPC results incur redundant validation before leaving the daemon. The command router already normalizes the response, but the shared send path parses it again through the outgoing message union. A synthetic 322,599-byte plugin result passes through the real send method and triggers one additional parse, producing a new but deeply equal response. Both trusted checkouts fail the zero-additional-validation assertion for this exact reason. The measurements characterize a CPU cost, not a measured end-user latency or production throughput claim.

5. Root cause

The router parses a success response inside its try block, which also converts validation failures into error responses. Application wiring forwards that returned object without changing it to ServerConnection.sendMessage. The send method unconditionally parses it through the full outgoing union before serializing. For plugin results, the recursive JSON schema traverses and reconstructs the nested output again. These are two identified validation boundaries; this is not an exhaustive count of validation inside every command handler.

6. Proposed fix

Retain router validation and avoid repeating it when sending a router-validated success. Continue validating directly constructed failures and other messages. Any fast path must preserve the assumption that its successful responses have already crossed the router validation boundary; future producers must not bypass it. No wire-schema change is necessary.
