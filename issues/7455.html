#7455 · Plugin-attributed turn requests incorrectly acknowledge unread history

BugPriority: MediumEffort: Lowthreads · plugins · confirmed-repro GitHub issue2026-11-12

Verdict: REPRODUCED · Root-cause confidence: high

Trusted base: 030b1b729f28acedc6f86cd65a71cb3678da8124, fetched from the target repository's main branch.

1. TL;DR

A background plugin message can acknowledge thread history that nobody has read. The server assigns some plugin messages the same user initiator as human messages, but also records the plugin ID. Its automatic read acknowledgement looks only at the initiator and ignores that attribution. A real migrated SQLite regression reproduced the erroneous timestamp change twice on unchanged production code, including a fresh second checkout. The desktop divider consumes the affected timestamp; native desktop and phone rendering were not exercised.

5. Root cause

  1. The plugin-scoped send wrapper adds originPluginId to every send.
  2. Dispatch authorship defaults to user without a sender thread; the send path invokes this resolver.
  3. The event builder preserves originPluginId in the request data.
  4. The automatic read-state updater tests only event type and initiator before calling updateThread with Date.now(). The shared append transaction applies this to accepted turn requests.
  5. The app unread-divider placement suppresses the divider when the incorrectly advanced timestamp reaches latestAttentionAt, or uses the advanced value as its cutoff. This follows from source, not a captured UI run.
function applyUserTurnReadForEvent(
  db: DbTransaction,
  args: AppendThreadEventArgs,
): ThreadReadStateUpdate | null {
  if (args.type !== "client/turn/requested") {
    return null;
  }
  if (args.data.initiator !== "user") {
    return null;
  }

  const previousThread = getThread(db, args.threadId);
  const updatedThread = updateThread(db, noopNotifier, args.threadId, {
    lastReadAt: Date.now(),
  });
  if (!previousThread || !updatedThread) {
    return null;
  }

  return {
    changed: updatedThread.lastReadAt !== previousThread.lastReadAt,
    projectId: updatedThread.projectId,
    threadId: updatedThread.id,
  };
}

The underlying distinction is dispatch authorship versus actual human read acknowledgement. A plugin can legitimately produce a user-style prompt without representing a person reading existing history.

6. Proposed fix

Keep dispatch authorship and message delivery intact. At the existing read-state policy boundary, skip the implicit acknowledgement when the request data contains originPluginId. Ordinary user sends continue to advance the cursor, and agent sends continue not to. This changes neither a public schema nor a daemon protocol. Clients that intentionally acknowledge viewing a thread retain the explicit mark-read operation.
