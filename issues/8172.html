#8172 · Unbounded event batches lose queued data during retry

BugHigh priorityEffort: Lowhost · perfGitHub issue2026-11-25 · base fb045a046653cc127656ca3c7243d44ae4c94f3f

Verdict: REPRODUCED · Root-cause confidence: high · reproduction label: confirmed-repro.

1. TL;DR

The host daemon buffers thread events while its session is closed, then uploads all eligible events together. A transient upload failure should leave those events queued for retry, but a sufficiently large batch instead causes a JavaScript argument-count overflow while requeueing. In both clean trusted-base runs, a 150,000-event backlog produced one failed upload, a RangeError, zero deliveries, and no remaining queued thread IDs even after a second flush. A 1,000-event control successfully retried all events. The real server route also accepted a 150,000-event POST and delayed a zero-delay timer by more than eight seconds in both runs.

Full sink regression source
import { turnScope } from "@bb/domain";
import { expect, it } from "vitest";
import { createEventSink } from "./event-sink.js";

it.each([1_000, 150_000])(
  "retains %i offline deltas through a transient failure",
  async (count) => {
    let open = false;
    let attempts = 0;
    let largestPost = 0;
    const delivered: string[] = [];
    const errors: string[] = [];
    const sink = createEventSink({
      isSessionOpen: () => open,
      logger: { debug() {}, error() {}, warn() {} },
      postEvents: async (envelopes) => {
        attempts += 1;
        largestPost = Math.max(largestPost, envelopes.length);
        if (attempts === 1) {
          throw new Error("injected transient transport failure");
        }
        for (const envelope of envelopes) {
          if (envelope.event.type === "item/agentMessage/delta") {
            delivered.push(`${envelope.threadId}:${envelope.event.delta}`);
          }
        }
        return { acceptedEvents: [], rejectedEvents: [] };
      },
    });
    const expected: string[] = [];
    try {
      for (let index = 0; index < count; index += 1) {
        const threadId = `thr_repro_${index % 3}`;
        expected.push(`${threadId}:${index}`);
        sink.emit({
          threadId,
          event: {
            type: "item/agentMessage/delta",
            threadId,
            providerThreadId: "provider-repro",
            scope: turnScope("turn-repro"),
            itemId: "item-repro",
            delta: String(index),
          },
        });
      }
      open = true;
      for (let attempt = 0; attempt < 2; attempt += 1) {
        try {
          await sink.flush();
        } catch (error) {
          if (!(error instanceof Error)) throw error;
          errors.push(`${error.name}: ${error.message}`);
        }
      }
      const remainingThreads = sink.listUndeliveredThreadIds();
      console.log(
        JSON.stringify({
          count,
          attempts,
          largestPost,
          delivered: delivered.length,
          remainingThreads,
          errors,
        }),
      );
      expect(errors).toEqual([]);
      expect(delivered).toEqual(expected);
      expect(remainingThreads).toEqual([]);
    } finally {
      await sink.dispose();
    }
  },
);

5. Root cause

  1. takeEligibleBatch selects all eligible envelopes without a bound, and removes them from the queue. Its waiting-array argument spread is a second count-dependent hazard.
  2. deliverBatch correctly converts a retryable post error into zero delivered events.
  3. settleBatch first removes in-flight accounting, then attempts queue.unshift(...batch.slice(delivered)). Spreading 150,000 entries as function arguments exceeds this runtime's call argument capacity. No events are restored; queue and in-flight maps now both appear empty.
  4. The promise chain catches errors from delivery before, not after, settlement. The RangeError therefore rejects flush. A subsequent flush finds nothing left to send, as confirmed by the recording transport.
  5. The tick timer callback starts a batch without handling that rejected promise. This is a static finding; direct flush supplied the tested path.
  6. Session reconciliation explicitly flushes pending events after reopening, making an accumulated queue reachable in production.
  7. The request schema has no event-count maximum, and the route appends the request in one synchronous database transaction. The database appender processes the supplied event list on that synchronous path; no asynchronous yield divides it into short transactions.

The underlying coupling is that the entire offline backlog becomes one upload and one synchronous server work unit. Fixing only exception handling would not preserve lost data, and replacing only unshift would leave unbounded server work and the waiting-array overflow.

6. Proposed fix

Bound each daemon upload to a moderate event count, preserve per-thread ordering and existing cross-thread in-flight behavior, and compact the remaining queue without spreading an unbounded array into a function call. Retry the undelivered suffix ahead of newer events. Keep the regression at the real event sink boundary and exercise a large queue waiting behind an in-flight thread as well. A count bound does not bound bytes: oversized individual events and a possible independent byte budget need explicit treatment rather than silently dropping data.

No production repair was attempted by this run because an open PR already links this issue. The proposed repair here is not claimed as verified-after-fix.
