#6261 · Repeated host discovery work

Bug Priority: Low Effort: Low host · 2026-10-25 · GitHub issue

Verdict: REPRODUCED · Root-cause confidence: high for the repeated discovery mechanism; native macOS timing and process counts remain unverified.

Trusted base: a6fff60f53c615a109103075328bf7017431e792 on origin/main. The issue text was treated only as untrusted claims. No issue commands, linked code, or external issue links were executed or fetched.

1. TL;DR

Each identical request to the host's workspace-open-target endpoint performs application discovery again. The route invokes the enumerator on every request without retaining a result or an in-flight promise. Running the real HTTP route and macOS enumeration code with only the operating-system command boundary substituted produced three complete enumerations for three requests. The regression expects one enumeration and fails on unchanged main in two clean checkouts. This demonstrates repeated command dispatch, not the reported native latency, CPU consumption, or machine-pressure effects.

5. Root cause

The HTTP route constructs a new runtime and calls the target-list handler per request:

  get(
    "/workspace-open-targets",
    workspaceOpenTargetsQuerySchema,
    async (c, query) =>
      c.json({
        targets: await (
          options.listWorkspaceOpenTargets ??
          ((query) =>
            listWorkspaceOpenTargetsWithRuntime(
              workspaceOpenTargetRuntime(options),
              query,
            ))
        )(query),
      }),
  );

listWorkspaceOpenTargetsWithRuntime calls listKnownMacWorkspaceOpenTargets, which iterates every launch adapter. Each application lookup can dispatch mdfind; available applications additionally perform icon extraction using plutil and qlmanage. The only cache in the local API module is for client configuration, unrelated to target discovery. Therefore identical successful requests repeat the entire discovery chain.

The query can include a file path, which affects associated applications. The runtime also consumes a resolved shell PATH. Any result cache must distinguish these inputs rather than share an arbitrary first result with all callers.

6. Proposed fix

Retain a bounded, short-lived discovery-promise cache inside each local API server. Key by file-path query and effective executable PATH, share unresolved promises, start the TTL after successful completion and remove rejected entries. A bounded cache prevents file-path cardinality from growing memory indefinitely. Keep target-opening requests uncached and keep existing wire schemas and authentication unchanged. Add regression coverage for concurrent requests, expiry, failure recovery, input changes and server isolation. A short TTL is a contained alternative to a new filesystem watcher.
