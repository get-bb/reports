#7183 · Direct-server startup recovery gates

BugPriority: MediumEffort: Lowmobile GitHub issue2026-11-06

Trusted main commit: 14b3293254da0a3b4c858a01c5415d91f17aa7b5.

PARTIALLY REPRODUCED · Root-cause confidence: medium · Reproduction label: partial-repro

1. TL;DR

The report describes being unable to change servers during an unsuccessful iOS launch. Two executions of the actual shell-state functions confirm that a direct profile with a pending page load selects the WebView branch, not the native loading or error branch, and does not trigger early failure revelation. Source inspection shows that the corresponding native settings controls require an error, while the startup overlay can keep intercepting touches until its eight-second cap. This establishes the recovery-gating mechanism, not the observed pixels or elapsed time: no iPhone or iOS Simulator is available on this Linux host. In particular, the source includes a splash logo, so this investigation does not establish why the reporter saw a completely white screen.

5. Root cause

The direct connector starts with an idle session rather than requiring a Connect session. The shell resolver then merges loading and ready into the same WebView state. That is useful for keeping the WebView mounted, but it leaves pending network work without a separate native recovery affordance.

export function revealsShellFailure(
  screen: ShellScreenState,
  requiresSession: boolean,
): boolean {
  if (screen.kind === "error") return true;
  if (screen.kind !== "webview" || screen.serverErrorStatus === null) {
    return false;
  }
  return !(
    requiresSession &&
    (screen.serverErrorStatus === 401 || screen.serverErrorStatus === 403)
  );
}

6. Proposed fix and safety decision

Preserve the mounted WebView and expose the existing device-settings navigation during a prolonged initial load; coordinate that affordance with splash revelation so it is actually tappable. Do not simply map the pending load to the existing spinner branch: that branch does not mount the WebView and would prevent progress. A recovery control also avoids treating a slow-but-valid server as definitively unreachable.

Before implementation, run a native cold-launch test against a controlled endpoint that accepts but does not complete a request. Check light and dark launch art, immediate or bounded settings access, successful slow loading, retry, profile changes, and overlay touch handling. Capture actual native screenshots and elapsed timestamps.

No fix pull request: the issue is only partially reproduced, so the required trusted-main native reproduction and meaningful failing regression gate for the full symptom are not satisfied. There are no production changes, commits, or pushed fix branches. Classification effort is an estimate, not a claim that the simple-fix gates passed.
