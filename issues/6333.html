#6333 · System notices bypass the active-compaction queue

Bug Priority: Medium Effort: Medium threads provider-codex

GitHub issue · October 26, 2026 · Trusted base: dbb5945406f70a39d6622619349baa1971693263

Verdict: REPRODUCED at the server dispatch boundary · Root-cause confidence: high.

1. TL;DR

A system notice delivered while a provider-accepted compaction is running takes the active-turn steering path instead of waiting. Ordinary messages already have a compaction guard, but parent system notices bypass that path. A focused test against the real server and migrated SQLite reproduces the missing queue entry on trusted main, and the same agent repeats that failure in a second clean checkout. The small proposed fix reuses the existing compaction predicate and durable queue. A live Codex rejection, the rendered error, notification loss, and automation disablement are not claimed as experimentally verified.

    async (accepted) => {

        const { host, session, thread } = seedCompactableThread(harness, {
          providerId: "codex",
          providerThreadId: "provider-notice-compaction",
        });
        const responder = registerSuccessfulTurnResponder(harness, {
          hostId: host.id,
          sessionId: session.id,
        });
        const response = await harness.app.request(
          `/api/v1/threads/${thread.id}/compact`,
          { method: "POST" },
        );
        expect(response.status).toBe(200);
        const compactRequest = responder.requests.find(
          ({ command }) => command.type === "turn.submit",
        );
        if (
          !compactRequest ||
          compactRequest.command.type !== "turn.submit" ||
          !thread.environmentId
        ) {
          throw new Error("Expected compaction request and environment");
        }
        const turnId = "turn-notice-compaction";
        if (accepted) {
          seedAcceptedProviderTurn(harness, {
            clientRequestId: compactRequest.command.requestId,
            environmentId: thread.environmentId,
            providerThreadId: "provider-notice-compaction",
            threadId: thread.id,
            turnId,
          });
        }
        const input = [
          {
            type: "text" as const,
            text: "Child work is complete.",
            mentions: [],
          },
        ];
        const subject = {
          kind: "thread" as const,
          threadId: "child-notice",
          threadName: "Child",
        };
        expect(
          await queueParentSystemMessage(harness.deps, {
            input,
            parentThreadId: thread.id,
            systemMessageKind: "child-completed",
            systemMessageSubject: subject,
          }),
        ).toBe(true);
        expect(listQueuedThreadMessages(harness.db, thread.id)).toEqual([
          expect.objectContaining({
            content: JSON.stringify(input),
            senderThreadId: null,
          }),
        ]);
        expect(
          await sendNextQueuedMessageIfPresent(harness.deps, {
            threadId: thread.id,
          }),
        ).toBe(false);
        expect(
          responder.requests.filter(
            ({ command }) => command.type === "turn.submit",
          ),
        ).toHaveLength(1);
        if (!accepted) {
          seedAcceptedProviderTurn(harness, {
            clientRequestId: compactRequest.command.requestId,
            environmentId: thread.environmentId,
            providerThreadId: "provider-notice-compaction",
            threadId: thread.id,
            turnId,
          });
        }
        seedEvent(harness.deps, {
          threadId: thread.id,
          environmentId: thread.environmentId,
          providerThreadId: "provider-notice-compaction",
          sequence:
            getLatestThreadSequence(harness.db, { threadId: thread.id }) + 1,
          type: "turn/completed",
          scope: turnScope(turnId),
          data: {
            providerThreadId: "provider-notice-compaction",
            status: "completed",
          },
        });
        applyTurnCompletedEvent(harness.deps, {
          threadId: thread.id,
          providerThreadId: "provider-notice-compaction",
          type: "turn/completed",
          scope: turnScope(turnId),
          status: "completed",
        });
        expect(
          await sendNextQueuedMessageIfPresent(harness.deps, {
            threadId: thread.id,
          }),
        ).toBe(true);
        expect(listQueuedThreadMessages(harness.db, thread.id)).toEqual([]);
        await expect
          .poll(
            () =>
              responder.requests.filter(
                ({ command }) => command.type === "turn.submit",
              ).length,
          )
          .toBe(2);
        expect(
          responder.requests.filter(
            ({ command }) => command.type === "turn.submit",
          )[1]?.command,
        ).toMatchObject({
          input,
          target: { mode: "start" },
        });
        const notices = listEvents(harness.db, { threadId: thread.id })
          .filter((event) => event.type === "client/turn/requested")
          .map((event) =>
            turnRequestEventDataSchema.parse(JSON.parse(event.data)),
          )
          .filter((event) => event.initiator === "system");
        expect(notices).toEqual([
          expect.objectContaining({
            input,
            senderThreadId: null,
            systemMessageKind: "child-completed",
            systemMessageSubject: subject,
            target: { kind: "new-turn" },
          }),
        ]);
        expect(
          await sendNextQueuedMessageIfPresent(harness.deps, {
            threadId: thread.id,
          }),
        ).toBe(false);
      });
    },

5. Root cause

The ordinary send checkpoint already checks isManualCompactionActive before joining a turn. Automatic queue drains also refuse to dispatch during compaction. The predicate identifies a standalone built-in compaction request and its active turn from persisted events: thread-events.ts.

Parent notices use a separate delivery path. Its entry condition only tests for a pending interaction, then delivers immediately: parent-system-messages.ts. The active branch persists and submits this target:

target: {
  mode: "auto",
  expectedTurnId: expectedSteerTurnId,
}

Once compaction has a provider turn ID, this is a steer into that turn. The Codex bridge forwards turn/steer and propagates rejection; the server's failed-command settlement appends thread_command_failed. That explains the reported symptom without proving the provider rejection experimentally. No transport/protocol change is needed to prevent the observed misdispatch.

6. Proposed fix

Add the existing isManualCompactionActive predicate to the immediate-delivery condition in queueParentSystemMessage. Reuse the current durable queued-message fallback, which already stores the system notice kind and subject and waits on thread-busy. The queue drain already blocks active compaction and delivers the notice as a new system turn after completion. This changes three production text lines (two additions and one deletion), with no public fields, dependencies, migrations, or protocol changes.

The regression covers both pre-acceptance and accepted compaction. It verifies queue preservation during compaction and exactly one post-compaction delivery with the original taxonomy and sender. Existing tests cover active/idle status races and ordinary message dispatch. This focused repair does not claim to audit every possible concurrent dispatch race or automation behavior.
