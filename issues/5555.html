#5555 · Skill inspection rejects directory aliases

BugPriority: MediumEffort: Mediumprovidersprovider-piGitHub issue

Verdict: REPRODUCED · Root-cause confidence: high · reproduction label: confirmed-repro

1. TL;DR

A skill can be found successfully while its detail and file-list operations cannot read it. Discovery follows a linked directory, retains the logical filename and marks the skill linked. The server then uses that logical directory as the host file RPC root, but those RPCs deliberately reject symbolic-link roots. A four-case test reproduces both read failures on current main, while the equivalent ordinary-directory controls pass. The failure is in the shared filesystem path, not a missing skill document or a provider turn.

5. Root cause

  1. Discovery retains the logical filename even though canonical paths are used for deduplication. The linked bit describes the entry but does not supply a separately authorized read root.
  2. The server makes linked skills non-manageable, which restricts mutation; it does not block or repair content reads.
  3. The skill listing/read service derives rootPath from skill.filePath and forwards it unchanged to host.list_files or host.read_file_relative.
  4. listHostFiles validates the supplied root and readHostRelativeFile delegates to the relative reader. The latter reaches the same root validator via resolveRootPathOrThrowMissingPath.
  5. The validator checks lstat before realpath and throws invalid_path for a symbolic-link root. Discovery has accepted a category the generic file-root contract forbids.
  6. The server maps failed host RPC responses to HTTP 502. The shared skill content and file-list routes and CLI SDK calls explain why both inspection surfaces encounter the same failure.
export async function resolveNonSymlinkDirectoryPath(
  args: ResolveNonSymlinkDirectoryPathArgs,
): Promise<string> {
  const rootStat = await fs.lstat(args.path);
  if (rootStat.isSymbolicLink()) {
    throw new CommandDispatchError(
      "invalid_path",
      `${args.description} "${args.path}" must not be a symlink`,
    );
  }
  if (!rootStat.isDirectory()) {
    throw new CommandDispatchError(
      "invalid_path",
      `${args.description} "${args.path}" is not a directory`,
    );
  }

  return fs.realpath(args.path);
}

The deeper mismatch is between discovery policy and the generic file-root security contract. The guard is intentional; globally removing it would weaken unrelated callers. Resolution must occur on the host owning the filesystem, with containment retained below the resolved root.

6. Proposed fix

Define an explicit skill-read policy for following the selected root directory, resolve that root on its owning host, and then reuse existing containment and hidden-file validation. Keep generic filesystem callers strict and linked skills non-manageable. Verify nested references, traversal, hidden paths and nested escaping links before shipping. Any wire-contract change needs the host protocol version and compatibility validation required by repository guidance.

No production patch or new PR was created: open PR #5556 already links this issue. A change to root-following permissions or host protocol is also outside this autopilot rule’s simple-fix boundary.
