1. TL;DR

An ACP agent can advertise a method that it accepts, yet bb cannot start an authentication-gated session with it. Both ACP bridges select only two special method IDs; other IDs cause the authentication helper to return without making a request. The existing repository test agent reproduces this through the real bridge entry point, without running any issue-provided code. A recognized-method control succeeds, while a newly chosen opaque method fails with an authentication error. The same result was repeated from a second clean checkout by the same investigator.

5. Root cause

The original bridge's method selector and authentication helper only choose xai.api_key when its environment key exists, otherwise cached_token when advertised. Any other method produces undefined and the helper immediately returns:

if (env.XAI_API_KEY && methodIds.has("xai.api_key")) {
  return "xai.api_key";
}
if (methodIds.has("cached_token")) {
  return "cached_token";
}
return undefined;

if (methodId === undefined) {
  return;
}

The next bridge has the same selection and early return. The original bridge calls the helper after initialization at session setup, then sends session/new. The next bridge follows the corresponding initialization/authentication and session creation path.

The committed original fake agent's authentication gate rejects unauthenticated sessions with ACP error -32000. Its authenticate handler accepts any advertised ID, so the opaque ID is not itself an agent rejection. The special-ID control validates the working transport/session/turn path.

Existing coverage explicitly expects unsupported advertised methods to surface the agent's authentication error. That explains why existing tests pass despite the interoperability limitation, and makes changing generic authentication behavior a policy change rather than a safe mechanical replacement. A signed-in agent that does not require protocol authentication is outside the failing case. Session restoration and discovery share the helper but were not separately reproduced here.

6. Proposed fix and safety decision

Define the supported behavior for protocol-driven methods and method selection first. A follow-up can add a bounded, explicit authentication-required recovery path in both bridges, respecting method types and preserving existing special-ID handling. It must not blindly pass terminal methods to the protocol authentication RPC or initiate interactive login simply because a method was advertised. Cover single and multiple methods, optional authentication, terminal-only methods, rejected login, bounded retries, and session restoration.

No pull request was opened: the autopilot's simple-fix rules explicitly exclude authentication changes. This issue necessarily changes authentication behavior, and the current unknown-method behavior has intentional coverage. The local reproduction is test-only: 50 added-plus-deleted lines across two files; zero production changes. Its small size does not waive the authentication exclusion. No source branch was pushed.
