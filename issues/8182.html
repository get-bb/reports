#8182 · Status wait request amplification

BugLow priorityEffort: Mediumthreads · cli · perfGitHub issue2026-11-25 · base fb045a046653cc127656ca3c7243d44ae4c94f3f

Verdict: REPRODUCED · Root-cause confidence: high · reproduction label: confirmed-repro

1. TL;DR

Waiting for a thread to become idle repeatedly fetches its complete record instead of leaving a server request pending. The real SDK issued 21 thread GETs during five seconds of simulated waiting in each of two fresh trusted checkouts. Its default 20-minute deadline produced 4,801 GETs with a zero-latency transport fixture. This confirms the request-amplification mechanism, not the reported production byte counts or network latency. An existing open pull request already targets this issue, so this investigation creates no duplicate fix.

5. Root cause

The default interval is 250 ms and the deadline is 20 minutes: packages/sdk/src/areas/threads.ts:94. The status branch reads a thread before checking the target, reachability and deadline, sleeps, and starts the loop over. Therefore unchanged active status causes one full read per interval plus transport latency. This is request amplification rather than incorrect eventual status matching.

packages/sdk/src/areas/threads.ts:1803

    async wait(input) {
      const { pollIntervalMs, target, timeoutMs } =
        validateThreadWaitArgs(input);
      const deadline = Date.now() + timeoutMs;
      while (true) {
        if (target.kind === "status") {
          const thread = await getThread({
            signal: input.signal,
            threadId: input.threadId,
          });
          if (thread.status === target.status) {
            return {
              matched: true,
              target,
              thread,
              threadId: input.threadId,
            };
          }
…
          if (Date.now() >= deadline) {
            throw new ThreadWaitTimeoutError({
              pendingRetry,
              target,
              threadId: input.threadId,
            });
          }
          await sleep(pollIntervalMs);
          continue;

The helper is a normal GET, not a status-only query: packages/sdk/src/areas/threads.ts:1060. Its server handler uses buildThreadResponse: apps/server/src/routes/threads/base.ts:413. The reproduction counts SDK transport invocations; this full-response server cost is established from source, not timed in this test.

The event branch is different: packages/sdk/src/areas/threads.ts:1851. Its server route registers a waiter before a second lookup, preventing a missed notification in the lookup/register gap: apps/server/src/routes/threads/data.ts:403. The existing notification hub wakes thread waiters on changes: apps/server/src/ws/hub.ts:1099. Persisted event selection is not itself a safe replacement for current status: a historical event can match after the current status has changed again.

6. Proposed fix

Use a server-owned bounded status wait: check current state, register a notification waiter, recheck to avoid missed transitions, then wait until the condition changes or the deadline expires. The SDK should perform one initial read and consume the bounded wait rather than fetching at 250 ms intervals. Preserve unreachable-state and pending-retry handling, cancellation, queued-message wakeups, and compatibility with older servers. This crosses SDK, server routing and a public request contract; it is not an SDK-only sleep adjustment.
