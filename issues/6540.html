#6540 · Quadratic file-edit history reconstruction blocks the event loop

BugPriority: MediumEffort: Mediumthreads, perf

GitHub issue · October 29, 2026 · trusted main 3bacfac9ed69d42392076e5b3da2815bec822cd8

Verdict: REPRODUCED · Root-cause confidence: high for the synchronous projection hotspot. Live browser/API latency and the reporter's exact measurements were not tested.

1. TL;DR

A server rebuilding a long edit-heavy conversation runs the shared projection synchronously, so timers and other requests cannot progress until it returns. A newly written synthetic history of 6,000 file edits and 18,001 events blocked a zero-delay timer for approximately 989 ms. A second clean trusted checkout repeated the block at approximately 983 ms. Every file-change start/completion needlessly searched and copied the growing message array, even when the call was new or the existing rows were already updated in place. A bounded two-file fix skips those two unnecessary rebuilds; the same test then took approximately 135 ms and the existing thread-view suite passed.

Complete regression test

import { turnScope } from "@bb/domain";
import { expect, it } from "vitest";
import {
  buildEventProjection,
  type ThreadEventWithMeta,
} from "../src/build-event-projection.js";
import { getProjectionEntryMessages } from "../src/event-projection-flatten.js";

function editHistory(count: number): ThreadEventWithMeta[] {
  const history: ThreadEventWithMeta[] = [];
  function append(event: ThreadEventWithMeta["event"]): void {
    const sequence = history.length + 1;
    history.push({
      event,
      meta: { id: `event-${sequence}`, seq: sequence, createdAt: sequence },
    });
  }
  const common = {
    threadId: "responsiveness-thread",
    providerThreadId: "responsiveness-provider",
    scope: turnScope("responsiveness-turn"),
  };
  append({ ...common, type: "turn/started" });
  for (let index = 0; index < count; index++) {
    const item = {
      type: "fileChange" as const,
      id: `edit-${index}`,
      changes: [{ path: `src/file-${index}.ts`, kind: "update" as const }],
      approvalStatus: null,
    };
    append({
      ...common,
      type: "item/started",
      item: { ...item, status: "pending" },
    });
    append({
      ...common,
      type: "item/fileChange/outputDelta",
      itemId: item.id,
      delta: `saved-${index}`,
    });
    append({
      ...common,
      type: "item/completed",
      item: { ...item, status: "completed" },
    });
  }
  return history;
}

it("projects a long streamed edit history without a half-second synchronous stall", async () => {
  const options = {
    threadName: "Responsiveness fixture",
    threadStatus: "active" as const,
    turnMessageDetail: "full" as const,
  };
  buildEventProjection(editHistory(100), options);
  const history = editHistory(6000);
  const startedAt = performance.now();
  const pendingTimer = new Promise<number>((resolve) => {
    setTimeout(() => resolve(performance.now() - startedAt), 0);
  });
  const projection = buildEventProjection(history, options);
  const projectionMs = performance.now() - startedAt;
  const timerDelayMs = await pendingTimer;
  const edits = projection.entries
    .flatMap(getProjectionEntryMessages)
    .filter((message) => message.kind === "file-edit");
  console.log(
    JSON.stringify({
      events: history.length,
      edits: edits.length,
      projectionMs,
      timerDelayMs,
    }),
  );
  expect(edits).toHaveLength(6000);
  expect(edits[0]?.stdout).toBe("saved-0");
  expect(edits[5999]?.stdout).toBe("saved-5999");
  expect(edits.every((message) => message.status === "completed")).toBe(true);
  expect(projectionMs).toBeLessThan(500);
}, 30_000);

5. Root cause

The file-change upsert mutates reusable row objects, then calls replacement even when their identities and order did not change. For new calls it similarly filters the entire existing history before appending. With N independent edits the growing-array scans cost O(N²), allocating a new history array on each start/completion. The helper runs on the same JavaScript event loop as request handling.

Original replacement helper:

function replaceFileEditMessagesForCall(
  state: OperationProjectionState,
  callId: string,
  nextRows: readonly EventProjectionFileEditMessage[],
): void {
  const insertionIndex = state.messages.findIndex(
    (message) => message.kind === "file-edit" && message.callId === callId,
  );
  const messagesWithoutCallRows = state.messages.filter(
    (message) => message.kind !== "file-edit" || message.callId !== callId,
  );
  if (insertionIndex === -1) {
    messagesWithoutCallRows.push(...nextRows);
  } else {
    messagesWithoutCallRows.splice(insertionIndex, 0, ...nextRows);
  }
  state.messages = messagesWithoutCallRows;
}
  • Lifecycle upsert updates rows and invokes replacement.
  • The server invokes the shared projection synchronously in its timeline build.
  • Historical flush traversal and its callers: distinct remaining costs, not removed by the narrow fix.
  • Push scheduler pause and byte-budget statement preparation: source-confirmed contributors requiring separate measurement.

6. Proposed fix and measured validation

Use the existing call-to-rows map: append directly for a new call, and return when the same row objects remain in the same order. Their fields have already been updated. Preserve the original replacement fallback for structural changes, removals, and reordering; introduce no cached positions, additional state, or wire changes.
