#7900 · Long awake stalls are discarded by the duration-only suspension veto

Bug Medium Effort: Medium host, perf, confirmed-repro open on GitHub 2026-11-20 · base fab82665a3299fae8910f55d7519a3b034a03b9a

Verdict: REPRODUCED · Root-cause confidence: high

1. TL;DR

The core monitor can log a short event-loop stall but omit a much longer awake stall. Two clean checkouts of trusted main reproduced this using real timers and a CPU-busy main thread, without a BB server, database, plugin, or provider. A shared monotonic observer measured the long gap, while the sampler returned {"stall":null}. The loss happens because elapsed wall-clock time alone is treated as sufficient evidence of suspension. This report confirms the missing observation, not the cause of the reporter's production pauses.

import assert from "node:assert/strict";
import { resolve } from "node:path";
import { pathToFileURL } from "node:url";
import { uptime } from "node:os";

const sourceRoot = resolve(process.argv[2] ?? ".");
const sourceModule = (name) =>
  pathToFileURL(resolve(sourceRoot, "packages/process-utils/src", name)).href;
const { startEventLoopDelaySampler } = await import(sourceModule("event-loop-delay.ts"));
const { observeEventLoopGaps } = await import(sourceModule("event-loop-gaps.ts"));

async function measure(blockMs) {
  let largestObservedGapMs = 0;
  let blockMeasurement;
  const observer = observeEventLoopGaps((startedAt, endedAt) => {
    largestObservedGapMs = Math.max(largestObservedGapMs, endedAt - startedAt);
  });
  return await new Promise((resolveSample, rejectSample) => {
    const deadline = setTimeout(() => rejectSample(new Error("sampler deadline exceeded")), blockMs + 15_000);
    const sampler = startEventLoopDelaySampler({
      onSample(sample) {
        sampler.stop();
        observer.stop();
        clearTimeout(deadline);
        resolveSample({
          blockMs,
          ...blockMeasurement,
          largestObservedGapMs: Math.round(largestObservedGapMs),
          sample,
        });
      },
    });
    setTimeout(() => {
      const startedAt = process.hrtime.bigint();
      const wallAt = Date.now();
      const uptimeAt = uptime();
      const cpuAt = process.cpuUsage();
      const durationNs = BigInt(blockMs) * 1_000_000n;
      while (process.hrtime.bigint() - startedAt < durationNs) {}
      const cpu = process.cpuUsage(cpuAt);
      blockMeasurement = {
        wallElapsedMs: Date.now() - wallAt,
        monotonicElapsedMs: Math.round(Number(process.hrtime.bigint() - startedAt) / 1_000_000),
        uptimeElapsedMs: Math.round((uptime() - uptimeAt) * 1_000),
        processCpuMs: Math.round((cpu.user + cpu.system) / 1_000),
      };
    }, 150);
  });
}

const control = await measure(700);
console.log("control", JSON.stringify(control));
const long = await measure(66_000);
console.log("long", JSON.stringify(long));
try {
  assert.ok(control.sample.stall, "control stall must be reported");
  assert.ok(long.largestObservedGapMs >= 65_000, "must measure a real long gap");
  assert.ok(long.processCpuMs >= 10_000, "must demonstrate awake CPU execution");
  assert.ok(long.sample.stall, "long awake stall must be reported");
  console.log("PASS: both awake stalls retained");
} catch (error) {
  console.log(error.name + ": " + error.message);
  process.exitCode = 1;
}

5. Root cause

The shared gap observer uses process.hrtime.bigint() to notify observers of gaps. The sampler subscribes its histogram to that same observer. At each sample it flushes gaps and calls histogram.take(); histogram.take() resets the accumulated count, total, maximum and native histogram.

Only afterward does the sampler's classification condition require both a threshold-exceeding measured delay and a false suspension heuristic. The heuristic uses Date.now() elapsed time and tests gapMs - 5_000 >= 60_000. It never asks whether the system actually slept. Any sample window of at least 65,000 ms therefore rejects even a large monotonic stall, after the histogram has been consumed and reset.

export function isLikelySystemSuspensionDelay(args: {
  gapMs: number;
  intervalMs: number;
}): boolean {
  return args.gapMs - args.intervalMs >= LIKELY_SYSTEM_SUSPENSION_MIN_DELAY_MS;
}

The server monitor logs only when stall !== null; The host monitor does the same. Thus the null result suppresses the ordinary stall diagnostic in both consumers. The callback contract in this base has no separate suspension field. A large forward wall-clock adjustment is also a potential false positive of the same guard, but it was not exercised here.

6. Proposed fix

Do not veto measured awake stalls solely because the wall-clock sample window is long. Preserve the existing stall measurements and attribution; if suspension classification is needed, use corroborating platform clock/sleep evidence and expose it separately. Cover awake CPU-heavy and blocked-idle stalls, wall-clock jumps, actual or modeled suspension, unavailable evidence, and suspension followed by awake work. Platform-specific sleep detection requires its own verification; this Linux reproduction does not validate macOS behavior.
