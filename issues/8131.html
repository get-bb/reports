#8131 · CIMD parser ignores advertised public authentication alternatives

BugPriority: MediumEffort: Mediumremotesecurityconnect

GitHub issue · Investigated November 24, 2026 · trusted main 12eedb7562bd172fd69f86e25a28c1b6e456776d

Verdict: REPRODUCED at the source metadata boundary.
Root-cause confidence: high. A synthetic client advertising a public alternative is rejected by the real production parser in two clean checkouts. The hosted ChatGPT browser flow and live third-party metadata were not tested.

1. TL;DR

The reported connection fails before a remote MCP client can finish OAuth authorization. On trusted main, the hosted web service only examines the singular authentication-method field when admitting a client metadata document. If that field is non-public, it returns the reported rejection even when the document separately advertises public authentication as an alternative. An authored regression probe reproduces this exact result twice; six neighboring controls pass in each run, and the existing 77-test OAuth suite passes. This confirms the rejection mechanism, not the current deployed revision or a complete ChatGPT handshake.

5. Root cause

The relevant subsystem is the hosted OAuth service in apps/web, not provider execution or the Connect transport itself. Server metadata explicitly advertises public clients:

token_endpoint_auth_methods_supported: ["none"],
client_id_metadata_document_supported: true,

The document parser validates identity, name, and redirect-list structure, then applies this gate:

if (
  document.token_endpoint_auth_method !== undefined &&
  document.token_endpoint_auth_method !== "none"
) {
  return {
    ok: false,
    message:
      "only public clients (token_endpoint_auth_method none) are supported",
  };
}

No branch reads the plural supported-methods field. Consequently, changing that field cannot alter the rejection while the singular field remains non-public. The metadata fetch boundary passes the JSON into this parser. Authorization validation turns the failed metadata result directly into an error-page result before progressing to the remaining authorization checks. Consent preparation returns that error unchanged.

The deeper compatibility gap is lack of a selected-method contract: the metadata result contains the client identity, display name, and redirects, but no negotiated authentication method. This report does not claim that the plural client field is universally standardized or that accepting arbitrary non-public clients is safe. It establishes exactly which input is rejected and why.

6. Proposed fix and safety decision

Have the OAuth owner explicitly decide supported-method selection at the metadata boundary. If this compatibility extension is accepted, validate the alternatives list, select only the server-supported public method, and retain rejection of genuinely private-only or malformed clients. Keep PKCE, redirect validation, scope validation, resource binding, and token-exchange checks in place. Extend the owner suite for malformed lists, private-only documents, identity mismatch, and a full authorization/code-exchange/refresh flow using the selected public method; then validate a real external client against an isolated deployment.

No automatic fix PR: changing which OAuth clients are admitted changes authentication policy, explicitly outside this rule's simple-fix safety gate. No production patch or fix branch was created or pushed. An open-PR search and cross-reference check found no open PR directly linked to #8131 at investigation time; that does not make an authentication change eligible for autopilot.
