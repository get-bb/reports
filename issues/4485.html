Reports · Issue #4485

A placement option changes a positional argument from file path to thread ID

2026-09-30 · Bug · Medium priority · Medium effort

PARTIALLY REPRODUCED · High confidence in CLI parsing and outgoing request mismatch. No desktop pane or actual file opening was tested.

Claim, expected and observed

The issue concerns an explicit target thread being interpreted as a file when the caller already has a current-thread context. The actual Commander command and SDK request construction reproduce that ambiguity. With synthetic context thread-synthetic-green, a lone thread-synthetic-blue argument sends an open request to green with a workspace file path named thread-synthetic-blue. Adding --split replace to the same argument targets blue with file:null. The explicit-target desired-behavior assertion fails in both clean runs; six controls pass.

ConditionObserved request/result in both runs
Current context + lone other IDCurrent thread, workspace file named after other ID; command completes and prints success-shaped JSON
Same + --split replaceOther thread, no file
No current context + other IDOther thread, no file
Current context + synthetic relative fileCurrent thread, specified workspace file
Other ID + file + --split replaceOther thread, specified workspace file
Other ID + file without splitError, process.exit(1) intercepted by harness, no open request
HelpUsage advertises [id] [path]; --split describes placement but does not explain positional reinterpretation

Expected regression behavior: the explicit other-thread ID targets that thread without requiring a placement flag, or an ambiguity error prevents a misleading request. The regression asserts the explicit-thread interpretation. Existing relative-file behavior is separately retained as a control; a final CLI design must make the two intentions distinguishable.

Test boundary and limitations

The test uses trusted CLI registerOpenCommand, Commander parsing and real SDK request construction through the repository command-output harness. The harness stubs the server API, fetch, daemon lookup, console capture and process.exit. Its open handler deliberately returns delivered:1. Consequently, delivered:1 is a fixture response, not evidence of a real UI subscriber. The evidence is the actual request arguments and command output generated in response.

Thread IDs and file paths are synthetic strings. No file is opened, read or written by these command cases, and there is no real database, server, provider, agent shell or desktop instance. The fixture does not establish that a live server accepts the request or that a desktop pane displays a missing file. It does not measure an OS child-process exit status; normal completion and an intercepted exit call are tested. This is why the report is partial. No visual claim is made and no screenshot is presented.

apps/cli/src/__tests__/command-output/issue-4485.test.ts

import { describe, expect, it, vi } from "vitest";
import { setupCommandOutputTestEnvironment, collectLogPayloads, collectLogLines, getHelpOutput, runCommand, stubServerApi } from "../helpers/command-output-harness.js";
import type { CommandRegistrar } from "../helpers/command-output-harness.js";
import { registerOpenCommand } from "../../commands/thread/open.js";

const register: CommandRegistrar = program => registerOpenCommand(program.command("thread"), () => "http://127.0.0.1:49171");
const file = (name: string) => ({ source: "workspace", path: name, lineNumber: null });
const target = "thread-synthetic-blue";
const current = "thread-synthetic-green";
const cases = [
  { name: "explicit thread inside context without split", context: current, args: [target], expectedId: target, expectedFile: null, split: undefined },
  { name: "explicit thread inside context with split", context: current, args: [target, "--split", "replace"], expectedId: target, expectedFile: null, split: "replace" },
  { name: "explicit thread outside context", context: undefined, args: [target], expectedId: target, expectedFile: null, split: undefined },
  { name: "relative file inside current context", context: current, args: ["synthetic-note.md"], expectedId: current, expectedFile: file("synthetic-note.md"), split: undefined },
  { name: "explicit thread plus file with split", context: current, args: [target, "synthetic-note.md", "--split", "replace"], expectedId: target, expectedFile: file("synthetic-note.md"), split: "replace" },
];

describe("4485 positional target routing", () => {
  setupCommandOutputTestEnvironment();
  it.each(cases)("$name", async item => {
    vi.stubEnv("BB_THREAD_ID", item.context);
    const opened = vi.fn(async () => ({ delivered: 1 }));
    stubServerApi({ "v1.threads.:id.open.$post": opened });
    await runCommand(["thread", "open", ...item.args, "--json"], register);
    const payloads = collectLogPayloads(vi.mocked(console.log)).map(text => JSON.parse(text));
    process.stdout.write(JSON.stringify({ phase: item.name, context: item.context ?? null, args: item.args, requests: opened.mock.calls, output: payloads }) + "\n");
    expect(opened).toHaveBeenCalledExactlyOnceWith({ param: { id: item.expectedId }, json: {
      ...(item.split === undefined ? {} : { split: item.split }), file: item.expectedFile,
    } });
  });
  it("rejects a second positional file for another thread without split", async () => {
    vi.stubEnv("BB_THREAD_ID", current);
    const opened = vi.fn(async () => ({ delivered: 1 }));
    stubServerApi({ "v1.threads.:id.open.$post": opened });
    await expect(runCommand(["thread", "open", target, "synthetic-note.md", "--json"], register)).rejects.toThrow("process.exit:1");
    const errors = collectLogLines(vi.mocked(console.error));
    expect(errors.join(" ")).toContain("BB_THREAD_ID is set");
    expect(opened).not.toHaveBeenCalled();
    process.stdout.write(JSON.stringify({ phase: "two-positionals-without-split", errors, requestCount: opened.mock.calls.length }) + "\n");
  });
  it("captures actual help", async () => {
    const help = await getHelpOutput(["thread", "open"], register);
    expect(help).toContain("[id] [path]");
    expect(help).toContain("Thread ID. Omit inside a BB thread.");
    process.stdout.write(JSON.stringify({ phase: "help", help }) + "\n");
  });
});

The same agent personally ran both tests in separate clean checkouts, not an independent verifier. Both installs/builds exited 0; both final tests exited 1 with the same single regression failure. All seven evidence records are identical. There were no preliminary failed setup attempts for this fixture. The reported scope excludes unobserved desktop behavior.

Root cause at the tested boundary

  • Command target selection uses the presence of opts.split to set allowsExplicitThreadTarget before resolving the default replacement placement.
  • Context-dependent single-argument branch interprets the lone argument as an explicit thread when that boolean is true; otherwise the return below treats it as inputPath on the context thread.
  • SDK open request sends that resolved thread/file combination. Relative file resolution normalizes a relative path without a filesystem existence check; that is a source observation, not a test of a missing file in a live workspace.
  • Current help declaration documents thread/path arguments and placement but not the overloaded positional rule. The report contains the actual generated help output.
  • Existing command-output harness provides the isolated API boundary used here; Existing explicit-split test already treats that branch as intentional behavior. This report demonstrates the ambiguity; it does not characterize the rule as an accidental implementation typo.

Fix proposal and next test

Make thread targeting and file targeting explicit and independent of pane placement, while preserving or clearly migrating existing file-opening usage. At minimum, explain the contextual single-argument rule and the explicit-target requirement in generated help and the agent CLI reference. Add a regression matrix for contextual/non-contextual calls, explicit targets and file paths. No production fix was applied. Next integration test: connect an isolated CLI/server/browser fixture with two synthetic threads and a synthetic workspace, then verify the receiving thread and actual pane/file result, including a missing-file case.
