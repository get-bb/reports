#8297 · Existing daemon service settings are not reconciled

BugHighEffort: Mediumhostpartial-reproGitHub issue2026-11-27 · base b0ddaad731565d7e4de68d824120d802fc78f7d5

Verdict: PARTIALLY REPRODUCED · Root-cause confidence: high for the missing service-configuration reconciliation, not for an observed kernel OOM.

1. TL;DR

A package upgrade and a service-unit upgrade are different operations. The current installer writes OOM isolation settings into the systemd unit it creates, but the daemon package updater does not reconcile an existing unit. An isolated test exercised the real updater, verified its download and successful completion, and found the existing unit byte-for-byte unchanged. The same result occurred in a second clean checkout at the same trusted commit. This container has no systemd executable or service manager, so the reported kernel-OOM shutdown cascade and live reload behavior were not reproduced.

5. Root cause

The installer owns creation of the Linux service definition. Its service heredoc includes the protection settings and reloads systemd afterward: apps/server/src/assets/install-machine.sh:1199.

The bb-app package scripts have no install or postinstall lifecycle hook to reconcile the unit: packages/bb-app/package.json:64. This supports the static gap finding, while the intercepted npm boundary remains a limit of the dynamic test.

After verified download, the update path installs the package, writes its artifact digest, cleans the temporary download, and returns updated; it does not update the service unit: apps/host-daemon/src/protocol-self-update.ts:377. Daemon wiring reacts to that success by requesting a restart: apps/host-daemon/src/app.ts:948.

Normal startup currently schedules server-move activation, not service-default reconciliation: apps/host-daemon/src/app.ts:1131. The daemon's service-write path is used when moving the server and replaces the server URL arguments: apps/host-daemon/src/server-move/service.ts:1571. A project search of the daemon source finds neither OOM setting.

The underlying gap is lifecycle ownership: updating program files does not retroactively change persisted supervisor configuration. Consequently, an old unit retains its previous effective OOM policy. The reported whole-service shutdown is consistent with an effective stop policy, but this report does not independently measure that policy or reproduce the kernel event.

6. Proposed fix

During managed Linux daemon startup, discover the owned service definition, add only missing service-level defaults, preserve explicit operator choices and file permissions, and reload the correct systemd scope without restarting unrelated threads. Make this operation idempotent and serialize it with existing service-definition rewrites. A failed reload must remain diagnosable and retryable even after the file has already been updated.

Land a regression at that real lifecycle boundary, with existing-unit, already-current, explicit-override, unmanaged-service, and reload-failure cases. Complete the OOM validation on a disposable systemd machine using a bounded memory-limited test service, never by exhausting this shared host.
