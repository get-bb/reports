#5558 · Authenticated managed identities are discarded during credential discovery

Bug Priority: Medium Effort: Low workspaces confirmed-repro

GitHub issue #5558 · 2026-10-15 · trusted origin/main 05771e3c82404328854468f0fff7f0f8203e2076

REPRODUCED · root-cause confidence: high

TL;DR

The server can discard a successfully obtained GitHub credential solely because the authenticated login contains an underscore. Its identity validator permits letters, digits and hyphens, but not underscores. The validation error is swallowed and turned into an empty credential list; the health API consequently says the server is not configured. The settings server and UI translate that state into an unavailable automatic token. Two clean checkouts of the trusted main commit reproduce this mechanism with successful synthetic command responses; no real account, token, or running BB instance was used.

Complete regression test

import { describe, expect, it } from "vitest";
import { machineGitHealth, resolveGitCredentials } from "./git-credentials.js";

describe("automatic GitHub credentials preserve authenticated identities", () => {
  it.each([
    { login: "synthetic-user", email: null },
    { login: "synthetic-user", email: "synthetic@example.com" },
    { login: "synthetic_user", email: null },
    { login: "synthetic_user", email: "synthetic@example.com" },
  ])(
    "forwards credentials for $login with email $email",
    async ({ login, email }) => {
      const successfulCommands: string[] = [];
      const run = async (args: string[]) => {
        if (args.join(" ") === "auth token --hostname github.com") {
          successfulCommands.push("token lookup succeeded");
          return "synthetic-credential\n";
        }
        if (args.join(" ") === "api --hostname github.com user") {
          successfulCommands.push("identity lookup succeeded");
          return JSON.stringify({ login, id: 4242, email });
        }
        throw new Error("Unexpected credential lookup command");
      };
      const entries = await resolveGitCredentials(run);
      const health = await machineGitHealth(run);
      expect(successfulCommands).toEqual([
        "token lookup succeeded",
        "identity lookup succeeded",
        "token lookup succeeded",
        "identity lookup succeeded",
      ]);
      expect.soft(health.status).toBe("ready");
      expect.soft(entries.map((entry) => entry.name)).toContain("GH_TOKEN");
      expect
        .soft(entries.find((entry) => entry.name === "GIT_AUTHOR_NAME")?.value)
        .toBe(login);
      expect
        .soft(entries.find((entry) => entry.name === "GIT_AUTHOR_EMAIL")?.value)
        .toBe(email ?? `4242+${login}@users.noreply.github.com`);
    },
  );
});

Root cause

The credential discovery identity schema rejects the underscore before any environment entries are created:

const identitySchema = z.object({
  login: z.string().regex(/^[a-zA-Z0-9-]+$/u),
  id: z.number().int().positive(),
  email: z.email().nullable(),
});

The loader successfully reads a token, parses the user response, and constructs the forwarded identity only if schema validation succeeds. Its catch handles every error as no credentials:

    const token = z
      .string()
      .trim()
      .min(1)
      .regex(/^[^\s\x00]+$/u)
      .parse(await run(["auth", "token", "--hostname", "github.com"]));
    const user = identitySchema.parse(
      JSON.parse(await run(["api", "--hostname", "github.com", "user"])),
    );
    const email =
      user.email ?? `${user.id}+${user.login}@users.noreply.github.com`;
    return [
      ...githubGitConfiguration(),
      ...Object.entries({
        GH_TOKEN: token,
        GIT_AUTHOR_NAME: user.login,
        GIT_AUTHOR_EMAIL: email,
        GIT_COMMITTER_NAME: user.login,
        GIT_COMMITTER_EMAIL: email,
…
  } catch {
    return [];
  }

The health adapter bases readiness on the resulting entry count. The settings adapter converts non-ready health to not logged in. The automatic-token row then renders Not available and a login hint. This is why otherwise successful GitHub command responses become indistinguishable from a missing login. Neither token scopes nor a network error is necessary to trigger this result.

The automatic-token problem is downstream of the identity parser, not row visibility or primary-host selection. The server credential resolver itself already returns an empty list before host forwarding can occur. The failure is reproduced with both null and public email, so email fallback is not the differentiating input.

Proposed fix and automation safety

Have an authentication-aware maintainer expand the supported GitHub login grammar to cover managed identities while preserving validation against invalid identity data. Retain the existing numeric ID and email checks, and add the managed-login cases to the existing credential suite. Reuse the report's failing cases as regression evidence, keeping ordinary-login controls and malformed-response coverage.

No automatic PR: the required production repair changes the GitHub authentication identity schema. This rule explicitly excludes schema and authentication changes from simple fixes, regardless of line count. Production source was not modified, no fix branch was pushed, and no dependency or stored-data change was attempted.
