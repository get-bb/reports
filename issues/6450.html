1. TL;DR

The reported error text is generated by the Connect gate when request processing throws, not by the local thread API. Existing trusted-main tests reproduce that exact JSON 502 by injecting a failed gate label lookup; separate tests show unreachable or overloaded tunnel objects also produce 502 responses. A stalled request instead produces a stage-specific 504 after the gate deadline. These are controlled failure injections, not a reproduction of normal thread browsing becoming slow or unreliable. The production trigger, frequency, and affected population remain unverified; no infrastructure-capacity diagnosis or safe production fix follows from the message alone.

5. Root cause and limits

Verified mechanism

Gate label resolution awaits a database-backed routing lookup before forwarding to a tunnel. A rejected lookup escapes to the outer worker catch, which records a gate-side exception and returns gateErrorResponse:

export function gateErrorResponse(request: Request): Response {
  if (wantsHtml(request)) {
    return gatePage(
      `<h1>bb connect hit a temporary problem</h1>
       <p>This page retries automatically in a few seconds.</p>
       <button class="btn" onclick="location.reload()">Retry now</button>`,
      502,
      5,
    );
  }
  return Response.json(
    {
      code: "connect_gate_error",
      message: "bb connect hit a temporary problem. Try again in a moment.",
    },
    { status: 502 },
  );
}

That exception handler is a many-to-one mapping: the error text is not a unique signature for D1 overload or an overloaded relay. The existing unreachable/overloaded object tests demonstrate other failure sources. Tunnel replay policy intentionally avoids adding retry load to unreachable or overloaded objects; blindly retrying those cases is not a demonstrated safe fix.

withGateDeadline separately caps waiting and reports the progress stage, returning 504 rather than the generic 502. The ordinary limit is 30,000 ms. This bounds a stall; it does not establish the cause of the reported multi-second delays.

Production root cause remains unknown

The tests deliberately inject failures. They cannot establish that the reporter encountered D1 overload, a Durable Object reset, an unreachable tunnel, an origin exception, or a different dependency failure. Empty host logs are consistent with a pre-forwarding gate error, but do not prove it. No production telemetry was accessed.

Trusted history already contains commit 6b3fa9d0f444ef5fd1e7ae0ee141bd5c92e6d55b, merged October 20, 2026, coalescing concurrent gate lookups (SettledLookupCache). The existing 20-request burst test passes and performs one database select. That commit is also an ancestor of the desktop-v0.47.1 tag dated October 23, 2026. Neither the client tag nor the existing mitigation proves what code the hosted gate deployed or that this incident is already fixed.
