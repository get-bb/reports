#7833 · File-row matching scales quadratically

BugPriority: LowEffort: Lowthreads · perf · confirmed-reproIssue2026-11-19

Verdict: REPRODUCED · Root-cause confidence: high

1. Summary

Large edits spend disproportionate CPU time matching files while rebuilding a thread timeline. The implementation scans the accumulated row list separately for every incoming file, including rows already claimed during the same event. Two clean source checkouts at the same main commit show that increasing file count from 256 to 4,096 increases build time approximately 61–63× for unchanged order and 182–183× for reversed completion order, rather than roughly 16×. This blocks the calling JavaScript thread until the synchronous build finishes. Small edits are less affected; no live-service outage or data loss was reproduced.

Test source

import { turnScope, type ThreadEventFileChange } from "@bb/domain";
import { expect, it } from "vitest";
import { EMPTY_ACCEPTED_CLIENT_REQUEST_CONTEXT } from "../src/accepted-client-request-context.js";
import {
  buildThreadTimelineFromEvents,
  type ThreadEventWithMeta,
} from "../src/index.js";
import { workRowsOfKind } from "./timeline-test-harness.js";

function fileEvents(fileCount: number, reverse: boolean): ThreadEventWithMeta[] {
  const changes: ThreadEventFileChange[] = Array.from(
    { length: fileCount },
    (_, index) => ({ path: `generated/module-${index}.ts`, kind: "update" }),
  );
  return [
    {
      event: {
        type: "turn/started",
        threadId: "scaling-thread",
        providerThreadId: "scaling-provider",
        scope: turnScope("scaling-turn"),
      },
      meta: { id: "turn-start", seq: 0, createdAt: 0 },
    },
    ...(["item/started", "item/completed"] as const).map(
      (type, index): ThreadEventWithMeta => ({
        event: {
          type,
          threadId: "scaling-thread",
          providerThreadId: "scaling-provider",
          scope: turnScope("scaling-turn"),
          item: {
            type: "fileChange",
            id: "generated-edit",
            changes: index === 1 && reverse ? [...changes].reverse() : changes,
            status: index === 0 ? "pending" : "completed",
            approvalStatus: null,
          },
        },
        meta: { id: type, seq: index + 1, createdAt: index + 1 },
      }),
    ),
  ];
}

function build(events: ThreadEventWithMeta[]) {
  return buildThreadTimelineFromEvents({
    acceptedClientRequestContext: EMPTY_ACCEPTED_CLIENT_REQUEST_CONTEXT,
    contextWindowEvents: [],
    events,
    options: {
      completedTurnDisplay: "collapse",
      includeNestedRows: true,
      omitSettledDelegationChildRows: false,
      includeDiagnosticOperations: false,
      summarizeShellCommands: true,
      isLatestPage: true,
      threadStatus: "idle",
      threadName: "",
      workspaceRoot: null,
    },
  });
}

function minimumBuildTime(events: ThreadEventWithMeta[]): number {
  for (let warmup = 0; warmup < 4; warmup++) build(events);
  let minimum = Infinity;
  for (let sample = 0; sample < 3; sample++) {
    const start = performance.now();
    for (let repeat = 0; repeat < 3; repeat++) build(events);
    minimum = Math.min(minimum, (performance.now() - start) / 3);
  }
  return minimum;
}

it.each([false, true])(
  "keeps large file-change timeline builds within a linear scaling budget (reversed: %s)",
  (reverse) => {
    const small = fileEvents(256, reverse);
    const large = fileEvents(4096, reverse);
    expect(workRowsOfKind(build(large).rows, "file-change")).toHaveLength(4096);
    const smallMs = minimumBuildTime(small);
    const largeMs = minimumBuildTime(large);
    const ratio = largeMs / smallMs;
    console.log(JSON.stringify({ reverse, smallMs, largeMs, ratio }));
    expect(ratio).toBeLessThan(64);
  },
  30_000,
);

5. Root cause

File-row matching at the recorded commit calls record.fileRows.findIndex inside item.changes.map. Every change can scan every prior row, checking whether it has already been claimed and whether its historical path aliases overlap the current path or move path. Newly appended rows also enter the scanned list even though they are already claimed. This creates quadratic scanning even without changes to any public protocol or persistence layer.

const existing = record.fileRows.findIndex(
  (row, index) =>
    !used.has(index) &&
    row.matchKeys.some((key) => matchKeys.includes(key)),
);

Item application invokes the matcher for file-change events. The server's conversation-history projection calls the timeline builder inline, so this work occupies the JavaScript thread synchronously. The exact end-to-end HTTP impact remains unmeasured.

6. Proposed fix

Index existing row positions by their historical path keys once per event. Keep candidates ordered by original row position, discard already-claimed candidates lazily, and select the lowest candidate position across both incoming keys. Newly created rows must remain ineligible for reuse in the same event. Preserve historical aliases, duplicate-file identity, earliest-row preference across competing keys, and stale-row reappearance. The matching work then grows with indexed aliases and incoming changes rather than their product. Keep a focused scaling regression and an identity test for these edge cases.
