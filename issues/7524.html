#7524 · Redundant command output survives pruning

Bug Medium priority Low effort threads · perf · provider-pi

GitHub issue · November 13, 2026 · base faa89fb46f03f9a1cd83d60355ab94c48da76f80

Verdict: REPRODUCED · Root-cause confidence: high · reproduction label: confirmed-repro

1. TL;DR

A completed, archived command can retain its entire first output chunk in the events table even though the completed item already carries that output. The pruning code requires both a matching completion and an earlier delta before deleting a command delta. The first delta can never meet the second condition, even when a separate item-start event exists. A real SQLite reproduction confirms both an 8,192-character duplicate and a 40,000-character first delta surviving beside a completed-output preview of only 4,173 characters. The same two failures repeat in a second clean checkout; no production data or live provider session was used.

Complete regression test

The public reports repository excludes raw test artifacts and logs; the entire test is included here instead. Local originals and command logs are retained outside that repository.

import { turnScope } from "@bb/domain";
import { sql } from "drizzle-orm";
import { expect, it } from "vitest";
import { insertEvents, type InsertEventInput } from "../../src/data/events.js";
import { upsertHost } from "../../src/data/hosts.js";
import { createProject } from "../../src/data/projects.js";
import { advanceThreadPruning } from "../../src/data/thread-pruning.js";
import { archiveThread, createThread } from "../../src/data/threads.js";
import { noopNotifier } from "../../src/notifier.js";
import { createMigratedConnection } from "../../src/testing.js";

it.each([
  { size: 8192, laterDelta: "" },
  { size: 40000, laterDelta: "tail" },
])("releases a redundant first command delta ($size chars)", ({ size, laterDelta }) => {
  const db = createMigratedConnection();
  try {
    const host = upsertHost(db, noopNotifier, { name: "reproduction" });
    const { project } = createProject(db, noopNotifier, {
      name: "reproduction",
      source: { type: "local_path", hostId: host.id, path: "/tmp/reproduction" },
    });
    const thread = createThread(db, noopNotifier, {
      status: "idle",
      projectId: project.id,
      providerId: "pi",
    });
    const firstOutput = "z".repeat(size);
    const output = firstOutput + laterDelta;
    const command = {
      id: "command",
      type: "commandExecution",
      command: "synthetic output fixture",
      cwd: "/tmp/reproduction",
      approvalStatus: null,
    };
    const inputs: InsertEventInput[] = [];
    const add = (type: InsertEventInput["type"], data: object, commandItem = true) => {
      inputs.push({
        threadId: thread.id,
        scope: turnScope("turn"),
        sequence: inputs.length + 1,
        type,
        itemId: commandItem ? command.id : null,
        itemKind: commandItem ? "commandExecution" : null,
        parentToolCallId: null,
        data: JSON.stringify(data),
      });
    };
    add("turn/started", {}, false);
    add("item/started", { item: { ...command, status: "inProgress" } });
    add("item/commandExecution/outputDelta", { delta: firstOutput });
    if (laterDelta) add("item/commandExecution/outputDelta", { delta: laterDelta });
    add("item/completed", {
      item: { ...command, status: "completed", exitCode: 0, aggregatedOutput: output },
    });
    add("turn/completed", {}, false);
    insertEvents(db, noopNotifier, inputs);
    archiveThread(db, noopNotifier, thread.id);
    let finished = false;
    for (let call = 0; call < 200; call += 1) {
      const result = advanceThreadPruning(db, { threadId: thread.id });
      if (result.policy === "resolved-items" && result.action === "thread-complete") {
        finished = true;
        break;
      }
    }
    expect(finished).toBe(true);
    const measured = db.all<{ sequence: number; type: string; chars: number }>(sql`
      SELECT sequence, type,
        length(coalesce(json_extract(data, '$.delta'), json_extract(data, '$.item.aggregatedOutput'))) AS chars
      FROM events WHERE thread_id = ${thread.id}
        AND type IN ('item/commandExecution/outputDelta', 'item/completed')
      ORDER BY sequence
    `);
    console.log(JSON.stringify({ size, laterDeltaChars: laterDelta.length, measured }));
    expect(measured.find((row) => row.type === "item/completed")?.chars).toBe(
      size > 32768 ? 4173 : output.length,
    );
    expect(measured.filter((row) => row.type === "item/commandExecution/outputDelta")).toHaveLength(0);
  } finally {
    db.$client.close();
  }
});

5. Root cause

The support queries first find a matching completed item with aggregatedOutput, then search for an earlier delta of the same type, turn and item. The phase matcher deletes a delta only after that earlier-delta search succeeds. It does not accept an item-start event as an alternative ordering witness.

if (match) {
  if (args.kind === "background" || probe.probePhase === 1) {
    discarded.push(candidate.id);
    finished = true;
  } else {
    probe.probePhase = 1;
    probe.probeSequence = 0;
    probe.probeWitnessId = match.id;
  }
}

For the first delta, no earlier delta exists by definition. The command's completion qualifies, but the subsequent support scan ends without scheduling deletion. This is an intentional general retention rule, not an overdue sweep: the policy table explicitly retains first deltas, and the resting-pass documentation treats them as permanently settled.

The Pi path amplifies the storage cost: tool updates become cumulative command snapshots, and the shared assembler emits their text difference. The first snapshot therefore becomes a first delta containing all text accumulated so far. The terminal Pi event also extracts aggregated output.

The truncation bypass follows a separate code path: completed-output preparation only selects a retention target for item/completed, not outputDelta. The 32 Ki-character threshold and 2 Ki-character head/tail limits consequently do not bound the retained first delta. Full completed output also has a separately retained, expiring copy; this report measures raw events, not hydrated reads.

6. Proposed fix and safety boundary

Introduce a narrowly scoped command-output policy that can discard a first delta when a matching completion retains authoritative output and a same-scope item-start event preserves item ordering. Continue preserving unresolved output, delta-only item ordering, nested-tool scopes, and the latest-event safeguard. Add tests for missing starts, absent completion output, parent/turn collisions, bounded resumable probes, and long-output retention expiry.

Existing settled threads must be revisited deliberately: the global policy cursor enqueues all threads when its version becomes stale, and the per-thread resting cursor also needs an appropriate reset. Merely changing the delete predicate would leave previously settled first deltas untouched.

No automatic fix PR: this changes persisted event-retention policy and requires revisiting stored thread history, which is a stored-data change excluded by this rule's simple-fix conditions. No production fix, branch push, or pull request was created.
