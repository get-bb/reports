#6274 · Markdown fragment navigation

Bug Priority: Medium Effort: Medium ui · Issue · October 25, 2026

Trusted main: 3a2c49a267cd2a62a96ebff880068a7c37074251

Verdict: PARTIALLY REPRODUCED · Root-cause confidence: high · Reproduction label: partial-repro

1. TL;DR

The real Markdown renderer leaves same-document links targeted at a new browser context and does not cancel their click. Empty HTML anchor destinations are removed, rendered headings lack IDs, and relative file links lose non-line fragments before their open callback runs. Four focused behavior tests fail for these reasons in each of two clean checkouts of trusted main. The existing related tests still pass. This report stops short of claiming a live browser reproduction: Chromium is unavailable, so an actual new tab and scrolling in the complete application were not observed.

5. Root cause

  1. MarkdownAnchor renders every non-route link with target="_blank". Its click handler only handles local files, application routes, or a supplied open callback. It has no dedicated same-document fragment path.
  2. RouteAnchor preserves that target for non-route hrefs. This was observed directly in the test DOM, not just inferred from source.
  3. The same MarkdownAnchor returns <span>{children}</span> when href is absent. Consequently an HTML anchor's sanitized ID is dropped. The actual HTML sanitizer retains a div ID with the safe user-content- prefix. That prefix should not be disabled to implement navigation.
  4. Rendered headings have no destination IDs, independently demonstrated by the heading test. Same-document navigation needs both target discovery and contained scrolling, not just removing _blank.
  5. parseLineSuffix recognizes line-number fragments but deliberately strips a general fragment when constructing { lineRange: null, path }. The fragment is already absent by the time the production local-file callback is invoked.
  6. The Markdown file preview restores a nested preview container's scroll position, rather than implementing fragment navigation. Correct scrolling must work within that preview and avoid unrelated Markdown blocks.

6. Proposed fix and simple-fix gate

For same-document links, handle the decoded fragment before general link routing; cancel default navigation, resolve targets only in the owning document preview, and scroll the appropriate preview. Preserve sanitized HTML anchor IDs. Define stable heading slugs, including duplicate headings, Unicode, percent decoding, empty fragments, and missing destinations. Keep external links and sanitizer protections unchanged.

Cross-file links require carrying the fragment through file resolution and preview navigation, then revealing the destination after content is available. The current document-link routing sends only line ranges into the shared file intent. The public ExperimentalFileLocation contract supports line and range, not Markdown fragments. A complete repair through that shared path requires a public navigation-contract extension, which is outside this automation's simple-fix permission.

No fix branch or pull request was created. A renderer-only patch would leave the verified cross-file failure unresolved; no alternative end-to-end repair satisfying the no-public-schema-change gate was established. Live browser scrolling also remains unverified. There are no production modifications, dependency additions, or stopped fixes to push.
