#7459 · Selected skill hoisting removes an inline reference

BugMedium priorityLow effortproviders · provider-claude-codeIssue #7459

Verdict: REPRODUCED · Root-cause confidence: high · Reproduction label: confirmed-repro

1. TL;DR

A selected skill can still be invoked while the surrounding sentence loses its reference to that skill. The Claude bridge moves the skill to a leading slash command and unconditionally deletes its original token, even when prose precedes it. Two executions against unchanged production code reproduce this at the real bridge-to-SDK prompt boundary. A small local candidate preserves that reference and passes the ten focused cases. No pull request is safe under this automation's rules: the full provider suite fails six existing tests on pristine main and on the candidate.

5. Root cause

buildPromptText collects selected skill mentions with their original input-fragment index and validated text ranges. selectedSkillMentions requires the range to exactly match the selected command token, so the name disappearing is not a malformed mention or a tokenizer failure.

When exactly one skill was selected, the single-selection branch removes its whole token and prepends its command:

chunks[skill.chunkIndex] =
  `${chunk.slice(0, skill.start)}${chunk.slice(skill.end)}`;
const argumentsText = chunks.join("\n");

For a leading invocation, removing the token is appropriate: the remaining text really is the command's arguments. For an embedded or trailing mention, the same removal erases a word from the user's sentence. The new leading command does not restore that word to the argument text.

The existing prompt-boundary tests actually expected the missing name. Extending this table corrects the behavior contract without a new export, wrapper, production seam, or duplicate test layer. The harness replaces the SDK query, not the bridge serialization being asserted.

The behavior was introduced by trusted main commit 56c16ecf3f, which deliberately hoisted a single selected skill so it would expand. This explains why simply reverting hoisting would regress skill invocation.

6. Proposed fix and safety gate

Keep the leading slash invocation. If any non-whitespace content precedes the selection, retain its canonical skill name at its original position in the arguments, without the trigger. If it is the first meaningful content, keep the current invocation-only treatment. Leave the multiple-selection path unchanged.

A local candidate implements this only in the existing Claude bridge subsystem. It changes two files, with 64 additions and 4 deletions: 68 total text lines. It adds no dependency, generated file, stored-data change, protocol, or public API. The test was changed and demonstrated failing before the production edit; all ten focused cases pass afterward. Lint, typecheck, and git diff --check pass.

Stopped fix; no commit, push, or pull request. The full provider suite is not green. Pristine main reports 6 failed | 436 passed (442); the candidate reports 6 failed | 441 passed (447). The same failures concern installed-CLI discovery and permission assumptions under the test host, not skill serialization. A non-root user namespace reduces these to two CLI-discovery failures. An attempted private mount isolation was denied; no host files were changed. The automation requires passing relevant existing suites, so these failures are not waived and unrelated code is not modified.

7. Related work

No open pull request linking this issue was returned by issue cross-reference metadata or the open-PR search at investigation time. Earlier issue #6562 motivated keeping the selected invocation at the start. This report addresses the sentence loss caused by removing its original reference.

8. Verification

The same agent repeated the reproduction; this is not independent verification. The second checkout was created with git worktree add --detach SECOND_CHECKOUT 030b1b729f28acedc6f86cd65a71cb3678da8124. It was clean before applying only the regression patch, used a fresh frozen install, and built the SDK runtime through Turbo. The same focused command returned five failures and five passing controls, including identical trailing and namespaced prompt strings. No ports or application data directories were needed.

Afterward, the test patch was reversed in the second checkout and git status --porcelain was empty. Running the entire provider suite on that pristine checkout reproduced the same six unrelated failures as the candidate. The second reproduction supports the final root cause and required no correction to the claim. One initially incorrect whitespace-control expectation was corrected before the recorded first and second runs; neither run uses that false failure.
