#5617 · Automatic notices interrupt ACP prompts

Bug Priority: Medium Effort: Medium providers · threads · provider-acp

GitHub issue · October 16, 2026 · trusted base 01affc197dc621cddc7343e09b1c5c10a5b9efcb

Verdict: PARTIALLY REPRODUCED · Root-cause confidence: high for the server-to-ACP cancellation mechanism. Reproduction label: partial-repro.

1. TL;DR

An automatic background notice is dispatched immediately to an active ACP thread instead of waiting for its current turn. The server chooses the same automatic turn target that the host resolves into a steer; the ACP bridge implements a steer by cancelling its current prompt and resubmitting input. A repository fixture confirms that this sends session/cancel even while a permission request is pending, without any human rejection. A separate ingress test confirms that ordinary ACP diagnostics are stored while hidden from the timeline. These mechanisms reproduce in two clean checkouts, but this investigation does not run the reporter's custom Claude Code provider or reproduce its exact rejection wording, operating-system command termination, or overnight incident frequency; the overall verdict is therefore partial.

5. Root cause

  1. The child notification path calls the shared notice service: child-thread-notifications.ts.
  2. The active-parent branch records target.kind = auto and prepares target.mode = auto, with the active turn ID. It starts a live host command rather than parking the notice: parent-system-messages.ts. 
    target: {
  mode: "auto",
  expectedTurnId: expectedSteerTurnId,
}
  3. The host resolves an automatic target to the current live turn and invokes runtime.steerTurn: thread.ts. The runtime translates this into the provider's steer command: runtime.ts.
  4. The ACP turn/steer handler queues the new input and calls requestSteerCancel: bridge.ts steer handler. 
    session.cancelRequested = true;
cancelPendingPermissions(session);
session.connection.notify("session/cancel", {
  sessionId: session.providerThreadId,
});
    Cancellation implementation and pending permissions show that unresolved permission responders receive {outcome:{outcome:"cancelled"}}. A cancellation is not evidence that the human rejected the request. How a particular ACP agent verbalizes it is provider behavior not measured by this test.

The diagnostic observation has a separate cause: daemon ingress passes the validated event batch into persistence without checking the display setting. Timeline construction uses the setting to filter presentation instead. Hidden-but-stored diagnostics follow directly from this separation.

6. Proposed fix and safety decision

Keep human steering interruptible, but do not route passive notices into an interrupting ACP steer. Decide whether all passive notices should wait or whether providers should advertise non-interrupting delivery. Preserve notice taxonomy, queue ordering, exactly-once delivery, turn-start races, failed/interrupted turn drains, and notices needed to wake a waiting coordinator. A provider-specific prefix or plugin-ID check would miss third-party ACP plugins. No existing provider delivery-capability contract distinguishes these cases.

For diagnostics, first decide whether the setting is display-only or also a retention control. Suppressing events at persistence would change stored-data behavior and must preserve terminal/error evidence. It is not an automatic follow-on to fixing notice delivery.

No automated fix PR is opened. The exact real-provider failure is not yet reproduced, the safe delivery policy is unresolved, and treating the display flag as a retention flag changes stored-data behavior. These fail the requested simple-fix gates. No production patch, fix branch, or code push is made. The failing server regression and passing transport observation remain available inline for a scoped follow-up.

7. Linked PR review

PR #5618 was closed and unmerged at investigation time. GitHub reported 9 changed files, 210 additions and 215 deletions (425 text lines). There was no open PR linked to this issue in the issue timeline or open-PR search.

Static review only: the diff removes active-notice steering in favor of queueing and changes queue eligibility; that direction addresses the verified trigger. It also changes diagnostic persistence in server ingress and the database layer, which is a separate retention policy. No PR code, branch, test, or command was checked out or executed.

High-severity static finding: in the proposed apps/server/src/internal/events.ts, the new shouldPersistDaemonEvent helper (added block near lines 361–375) reads event.rawType.startsWith(...) before checking event.type. Most members of this event union, including turn-start events, have no rawType. Based on the diff, this dereference can throw for normal events before its later type guard. This is a source-level finding, not a result from executing untrusted PR code.

Verdict: not validated as a safe fix. Its nine-file, multi-subsystem scope also exceeds this autopilot's five-file/one-subsystem gate. All tests described in this report run trusted main plus our independently authored test-only additions, not the proposal.
