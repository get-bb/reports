#4368 · Cleanup uses stale worker eligibility

Bug · Medium priority · Low effort · plugins · workflows

2026-09-25 · Base 0baa605b32a00619c1d7e3f32be6553ebcf8244a · Issue

REPRODUCED · Root-cause confidence: high

TL;DR

A worker can become attached and running while cleanup is waiting for a different worker to stop. Cleanup then stops and archives that live worker using an outdated retirement decision. A new regression test demonstrates this with the actual workflow service and migrated in-memory database. Both trusted checkouts failed the same assertion.

Root cause

retiredWorkers includes a worker whose call does not yet reference its thread. Discovery can record that ownership before spawn returns. cleanupWorkers reads the candidates once and awaits each archive in order:

(): Promise<void> {
    for (const worker of retiredWorkers(db, Date.now())) {
      if (spawningCalls.has(worker.callId)) continue;
      recordWorkerCleanup(
        db,
        worker.threadId,
        await archiveRetiredWorker(worker.threadId),
      );
    }
  }

During the earlier await, spawn completion attaches the later worker and removes its spawning guard. The stale candidate remains in the loop. archiveRetiredWorker then stops and archives it without validating current ownership. The guards are evaluated at different times and neither proves retirement at the point of stopping.

Proposed fix

Recheck current retirement using a targeted database query immediately before stopping each candidate, retaining the spawning guard. Reuse the retirement predicate to avoid divergence between discovery cleanup and the recheck. Preserve cleanup of orphaned and cancelled workers.
