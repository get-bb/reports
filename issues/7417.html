#7417 · Cached usage hides a rejected pooled login

BugMedium priorityMedium effortprovidersGitHub issue

2026-11-11 · trusted main 365d7c5237ae270be0555b5b44ea61020252713e

Verdict: REPRODUCED · Root-cause confidence: high · Label: confirmed-repro

1. TL;DR

A pooled account can have a confirmed rejected OAuth refresh while Provider usage still returns its last successful usage as an ordinary healthy row. A deterministic integration test creates two synthetic Claude accounts, successfully measures both, advances one beyond expiry, and injects an HTTP 400 OAuth rejection through the real pool's transport seam. The real Account Pooler hub records the rejection, its real usage source collapses it to a generic collection error, and the real Provider usage server throws away that result while keeping the old measurement. The resulting group-wide warning cannot identify the account. The same agent repeated the test in a second clean checkout; both fail the intended row-status assertion in the same way.

5. Root cause

  1. The real pool records an OAuth refresh error through plugins/account-pool/src/hub.ts:1452. The source receives only the account's free-text error and maps every non-null error to one generic collection state at plugins/account-pool/src/usage-source.ts:143. This loses the authentication disposition before presentation.
  2. Provider usage interprets a valid per-account error state as a failed RPC refresh at plugins/provider-usage/server.ts:183:
    if (value.usage.status === "error")
  throw new Error("Usage could not be refreshed.");
    The new state is never stored; the previous healthy measurement stays in the cache.
  3. Failures are tracked per resource but projected onto the entire group's error field while cached usage is returned at plugins/provider-usage/server.ts:343. The sidebar turns that into generic stale-group feedback at plugins/provider-usage/app.tsx:612.
  4. The row already knows how to show expiredHint and source error text at plugins/provider-usage/app.tsx:329, but the source/server path prevents those states from reaching it. The contract at plugins/provider-usage/usage-source-contract.ts:126 explicitly treats authentication and collection failures as usage states.
  5. The panel RPC row schema at plugins/provider-usage/usage-schema.ts:16 has neither observation age nor a stale-values/error combination. Its error branch carries only a message, while windows exist only in the healthy branch.

6. Fix proposal and autopilot safety

Preserve a typed authentication disposition through Account Pooler's existing account/source boundary and emit the existing expired or unauthenticated usage state for a terminal login rejection. Do not infer this by matching arbitrary free-text errors. In Provider usage, distinguish source-reported account states from transport/inventory failures; keep the former attached to the row. Retaining previous windows for a non-authentication collection failure also requires an explicit stale/observation-time representation in the panel's RPC model and rendering.

No automatic PR: the complete repair spans two existing plugins and the requested stale-values/age presentation needs a panel RPC schema change. Both are outside the rule's simple-fix limits. Merely removing the throw would expose a generic error but would neither classify a rejected login nor preserve stale windows with an age. No production patch, commit, branch push, or PR was made.
