1. TL;DR

Ctrl-click does not preserve the browser's native new-tab behavior on the tested sidebar destinations. The navigation rail renders buttons, and its handler turns Ctrl/Meta into an in-app split request; the host's Plugins destination instead navigates the current app route. Thread rows already have real links, but explicitly cancel modified clicks when splitting is available and open an in-app pane. These are two related mechanisms, not a single missing anchor tag. Three browser-expectation tests fail on unchanged production code in each clean checkout; existing tests explicitly protect the current split behavior.

5. Root cause

  1. No native rail destination links. RailButton renders Button; RailItem sends modified clicks to host activation:
onClick={(event) =>
  actions.activate(item.id, {
    openInSplit: event.metaKey || event.ctrlKey,
  })
}

The TopList renderer uses the same button/activation pattern (source inspection only, not an added TopList reproduction). For Plugins and Skills, the host navigates the current route regardless of the split option; plugin panels can instead open a split.

Thread links are present but their native action is cancelled. The ThreadRow anchor handler contains:

<a href={thread.href}
  onClick={(event) => {
    ...
    if (splitAvailable && (event.metaKey || event.ctrlKey)) {
      event.preventDefault();
      openInSplit();
      return;
    }
    ...
  }}
/>

The split action calls openThreadInSplit. This is intentional existing behavior: the navigation test asserts modifier-click splitting, and the thread test explicitly asserts Ctrl/Meta cancellation and split navigation. That explains why the ordinary test suite passes despite the browser expectation failing.

6. Proposed fix and simple-fix decision

First decide how browser new-tab gestures should coexist with the existing Ctrl/Meta split shortcut. Then give true navigation destinations host-resolved URLs, render native anchors, and intercept only unmodified primary clicks for app navigation. Retain buttons for commands such as creating or searching threads. Keep splitting accessible through the existing menu/drag path or an explicitly chosen non-conflicting shortcut.

No automatic fix or pull request. Replacing an existing, explicitly tested shortcut requires a product decision. In addition, the public sidebar navigation item contract has no host-resolved destination URL; fixing the complete rail/list/thread report without duplicating route policy needs coordinated routing/SDK and renderer work. This fails the rule's no-product-decision and single-subsystem simple-fix conditions.
