#7696 · Pi command snapshots duplicate output in the diagnostic fallback

BugPriority: MediumEffort: Lowproviders · provider-pi · perfGitHub issue2026-11-17 · base 1320c88e8a

Verdict: REPRODUCED · Root-cause confidence: high

1. TL;DR

Pi command output is sent twice inside a single bridge update: once as the output snapshot and once inside a diagnostic copy of the original event. A synthetic 65,536-byte snapshot produced a 131,462-byte serialized delta array, with two complete copies of the output. The assembler displayed the output only once, so this is redundant transport and validation work, not duplicate text in the timeline. The same agent repeated the test in a second clean checkout at the same trusted main commit and obtained identical results. An existing open PR, #7703, already targets this root cause, so no duplicate fix PR was created.

5. Root cause

The command-update branch in delta-translation.ts:1178–1218 extracts text from partialResult and constructs:

text: snapshot,
noTurnFallback: noTurnFallbackFor(piEvent.data, context),

noTurnFallbackFor wraps the entire parsed Pi event as an sdk/message, including its original partialResult.content[].text. Its toRawEvent helper validates that raw event. Consequently JSON serialization cannot preserve shared string identity: it writes the text once in the snapshot and again in the fallback.

The Pi bridge sends the returned deltas without stripping the fallback, and createBridgeIo serializes them using JSON.stringify. The byte counts above measure the delta array, not the small additional notification envelope.

The runtime's bridge-protocol adapter validates the batch before assembly. Its fallback schema requires another raw-event validation. These call paths are static findings; this report does not time their CPU cost.

The snapshot assembler consults the fallback only when no turn is open. During the reproduced lifecycle it instead diffs the snapshot against prior command output, explaining why only one copy is visible. A cumulative snapshot of S ASCII bytes yielded 2S + 390 bytes for the tested synthetic identifiers; overhead depends on the event and identifiers.

6. Proposed fix

Do not attach the raw no-turn fallback to streamed command.outputSnapshot updates. The neighboring item.progress update path carries the same redundant raw-event pattern and can use the same policy. Keep lifecycle start/end fallbacks, normal output snapshots, and assembler behavior unchanged. The existing protocol field is already optional, and the documented contract permits dropping an out-of-turn delta when no fallback is attached. This proposal does not require a schema change.

Before landing, require the single-copy regression to pass, verify unchanged assembled in-turn events, and explicitly test the intended out-of-turn drop policy and retained lifecycle diagnostics. No production patch was applied in this investigation.
