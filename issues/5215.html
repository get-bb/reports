#5215 · Plugin selection missing from command catalog

BugPriority: MediumEffort: Mediumpluginsuiconfirmed-reproGitHub issue2026-10-08 · base f135a001e72942cee9118d2693208ec0725e2f18

Verdict: REPRODUCED · Root-cause confidence: high

1. TL;DR

The composer can advertise a plugin skill that the same thread would not receive. In the real built-in BB guide plugin, disabling the skill-creator setting removes that skill from runtime injection, but the project commands endpoint still returns it. The command catalog reads every manifest skill without consulting the plugin's per-session selection. A focused endpoint regression fails for both Codex and Claude Code, and a second clean checkout repeats the same failure. No automatic fix PR is safe under this run's simple-fix policy: the menu has no thread/model/origin context, while the public configure contract requires it.

import { commandListResponseSchema } from "@bb/server-contract";
import { expect, it } from "vitest";
import { resolveThreadRuntimeCommandConfig } from "../../src/services/threads/thread-runtime-config.js";
import { registerHostRpcResponder } from "../helpers/host-rpc.js";
import { readJson } from "../helpers/json.js";
import {
  seedEnvironment,
  seedHostSession,
  seedPrimaryHost,
  seedProjectWithSource,
  seedThread,
} from "../helpers/seed.js";
import { withTestHarness } from "../helpers/test-app.js";

it.each(["codex", "claude-code"])(
  "omits deselected plugin skills from commands for %s",
  async (providerId) => {
    await withTestHarness(async (harness) => {
      const entry = await harness.pluginService.install("builtin:bb-guide", {
        kind: "root",
      });
      expect(entry.status).toBe("running");
      const { host, session } = seedHostSession(harness.deps);
      seedPrimaryHost(harness.deps, host.id);
      const { project } = seedProjectWithSource(harness.deps, {
        hostId: host.id,
        path: "/tmp/issue-5215-workspace",
      });
      const environment = seedEnvironment(harness.deps, {
        hostId: host.id,
        projectId: project.id,
        path: "/tmp/issue-5215-workspace",
      });
      const thread = seedThread(harness.deps, {
        projectId: project.id,
        environmentId: environment.id,
        providerId,
      });
      registerHostRpcResponder(harness, {
        hostId: host.id,
        sessionId: session.id,
        handle: (request) => {
          switch (request.command.type) {
            case "host.list_files":
              return { ok: true, result: { files: [], truncated: false } };
            case "host.list_commands":
              return { ok: true, result: { commands: [] } };
            case "host.list_skills":
              return { ok: true, result: { skills: [] } };
            case "host.read_file":
              return {
                ok: false,
                errorCode: "ENOENT",
                errorMessage: "No workspace instructions",
              };
            default:
              throw new Error(`Unexpected RPC ${request.command.type}`);
          }
        },
      });
      const runtime = () =>
        resolveThreadRuntimeCommandConfig(harness.deps, {
          environment,
          thread,
          model: "test-model",
        });
      const commands = async () => {
        const response = await harness.app.request(
          `/api/v1/projects/${project.id}/commands?provider=${providerId}&environmentId=${environment.id}`,
        );
        expect(response.status).toBe(200);
        return commandListResponseSchema.parse(await readJson(response))
          .commands;
      };
      const isGuideSkill = (command: {
        name: string;
        pluginId: string | null;
      }) => command.name === "skill-creator" && command.pluginId === "bb-guide";
      expect((await commands()).some(isGuideSkill)).toBe(true);
      expect(
        (await runtime()).injectedSkillSources.map((source) => source.name),
      ).toContain("skill-creator");
      const settings = await harness.pluginService.updateSettings("bb-guide", {
        skillCreator: false,
      });
      expect(settings?.values.skillCreator).toBe(false);
      const injected = (await runtime()).injectedSkillSources.map(
        (source) => source.name,
      );
      expect(injected).not.toContain("skill-creator");
      const remaining = (await commands()).filter(isGuideSkill);
      console.log(
        JSON.stringify({
          providerId,
          skillCreator: settings?.values.skillCreator,
          injectedSkillNames: injected,
          menuEntries: remaining,
        }),
      );
      expect(remaining).toEqual([]);
    });
  },
);

5. Root cause

The project commands handler collects provider commands and workspace/shared skills, then calls the shared catalog with only those skill sources:

const skillCatalog = resolveSkillCatalog(deps, {
  projectSkillSources,
  sharedSkillSources: sharedSkills.runtimeSources,
});

The catalog selection filter deliberately includes manifest skills when no selection is supplied. That is why the omitted selection is observable, not merely unused context:

!args.pluginSkillSelections?.has(pluginId) ||
args.pluginSkillSelections.get(pluginId)?.has(source.name) === true

In contrast, runtime configuration invokes resolvePluginAgentConfiguration with actual thread, project, environment, host, provider/model and origin data, and passes selectedSkillIdsByPlugin to the catalog. BB guide selects skill-creator only when its setting is enabled. The test runs both actual paths and demonstrates their divergence.

A deeper contract gap prevents a safe one-route patch: the strict commands query schema accepts provider and workspace selectors but no thread or model. PluginAgentConfigurationContext requires a real thread ID, provider model and origin. Plugin configuration resolution also reads plugin metadata by that thread ID. It is not safe to invent an empty thread, pick an arbitrary thread on the environment, or substitute a model for arbitrary plugins.

Related static observation: the management skill-listing path likewise does not pass plugin selection; whether that inventory should show all installed skills or only a particular thread's effective skills needs an explicit policy, not an assumed blanket filter.

6. Proposed fix and simple-fix decision

Define effective catalog resolution for existing-thread and pre-thread composition. Existing threads need their validated thread/model/origin/metadata context, and a composer model override must have explicit semantics. New-thread composition needs a documented preview contract rather than fabricated required fields. Share this effective-selection resolver with runtime construction, feed its selection into resolveSkillCatalog, and preserve native/provider skills and name precedence. Update SDK, CLI, UI query keys and Plugin Guide surfaces together if their public contracts change.

No PR opened. This requires a product/context decision and likely a public query or plugin contract change; both are outside the authorized simple-fix gate. No production code was patched, no fix branch was pushed, and no schema workaround was attempted. No linked open PR was found in the issue timeline or an open-PR search at investigation time.
