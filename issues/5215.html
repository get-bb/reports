#5215 · Command discovery skips plugin skill selection

BugPriority: MediumEffort: Mediumuipluginsconfirmed-reproGitHub issue

2026-10-20 · Trusted origin/main: bd93d18896bab97c950c4fa3451b621c1e0569c1

Verdict: REPRODUCED · Root-cause confidence: high

1. TL;DR

Disabling a bundled plugin skill removes it from the server's thread runtime injection list but not from its command-discovery response. A focused test loads the real built-in BB guide plugin, changes its skill-creator setting, resolves a real thread's runtime configuration, and requests the public commands route. Both Codex and Claude Code return the disabled plugin skill in that route, even while their runtime configuration correctly omits it. The route builds the shared skill catalog without the plugin selection map that the runtime supplies. The same agent repeated this result in a second clean checkout; no provider turn, browser, or production instance was used.

6. Proposed fix and simple-fix decision

Use the same selection policy for runtime injection and command discovery, with a defined context for existing threads and for the composer before thread creation. Existing threads need their actual identity, model, origin, and plugin metadata. Pre-thread discovery needs an explicit preview contract rather than fabricated required fields. Keep native commands and non-plugin skills unaffected, and do not hard-code BB guide's setting in a generic route.

No fix PR is safe under the requested simple-fix rules. Resolving the missing context requires a product/public-contract decision; the strict query schema currently cannot express it. No production code was changed, no branch was pushed, and no PR was opened. No linked open PR was found via issue cross-reference metadata or a repository PR search. A future fix should make the embedded regression pass and additionally cover metadata-dependent plugins, existing-thread selection, and pre-thread behavior once that contract is defined.
