#8036 · Usage resources lose registered provider metadata without native usage support

BugPriority: LowEffort: LowprovidersIssue2026-11-23 · base 796cdcc0f4bf8a55e23664035c54e8db6fe9d272

Verdict: REPRODUCED · Root-cause confidence: high · reproduction label: confirmed-repro

1. TL;DR

A usage source can contribute a resource for an agent that has no native usage implementation. The real Provider Usage server entry loads and returns that resource, but asks the registry for metadata only for native usage-capable providers. Consequently its RPC response substitutes the provider ID for the name and returns null for the icon and logo. A focused regression reproduces those exact incorrect values in two clean trusted checkouts. Reading the complete provider registry fixes both global and host-selected requests without creating cards for providers that have no resource.

5. Root cause

The provider registry filter implements the usage capability as provider.maintenance.usage. That is a native maintenance capability, not a requirement for another plugin to supply usage resources.

In readUsage, source discovery and provider metadata are fetched independently, but the metadata request unnecessarily includes that usage filter:

bb.sdk.providers.list(
  hostId === undefined
    ? { capability: "usage" }
    : { capability: "usage", hostId },
)

resourceProvider searches that incomplete array by provider ID. If the match is absent, its fallback uses the ID as displayName and no logo; normalizedProvider also defaults the missing icon to null. The resource is not absent: source inventory remains the driver of visible entries.

The resource assembly loop creates provider entries from source resources, not registry entries. The settings view passes provider.displayName as the heading and feeds the returned provider into ProviderIcon. This statically explains the reported presentation; it is not a claim of browser verification.

The ACP native source has its own usage-capability filter. Removing the aggregator's metadata filter does not alter native source eligibility.

6. Proposed fix and verified result

Fetch all registered providers for display metadata, retaining the existing hostId selection. Leave source discovery and provider-owned native usage checks unchanged. Keep the fallback for resources whose provider really is not registered. This is one existing subsystem, two files, 85 changed text lines (80 additions and 5 deletions), with no dependency, schema, protocol, stored-data, packaging, or public API change.
