This is an environment-limited investigation, not a finding that the reported Android defect does not exist. Neither clean run exercised Android's native text-selection menu. No fix was attempted.

1. TL;DR

The report describes Android's native text-selection controls covering BB's reply and side-chat actions. Trusted source confirms a plausible collision path: touch selections use their live text range, while BB's menu prefers the top of that range with a six-pixel offset. However, a preferred position does not establish where Android placed its native controls or whether they occluded BB on the affected browser. Both clean checkouts passed all 70 existing selection tests; those tests do not create native Android UI. Android tooling was unavailable and the Browser Automation plugin could not open Chrome, so the native overlap, root cause, and a safe repair remain unverified.

5. Root cause: unverified, with a plausible positioning path

Touch release handling returns no pointer anchor for non-mouse pointers, leaving live range geometry to drive selection placement. In anchor construction, the default side is top and the default vertical coordinate is the selected rectangle's top. The component's default and popover configuration preserve that preference:

const side = selection.anchorSide ?? "top";
const pointTop =
  selection.anchorPoint?.y ??
  (side === "bottom" ? selection.rect.bottom : selection.rect.top);

const anchorSide = selection?.anchorSide ?? "top";

<PopoverPrimitive.Content
  {...portalScopeProps}
  side={anchorSide}
  align="center"
  sideOffset={6}
  collisionPadding={SELECTION_MENU_COLLISION_PADDING}
  collisionBoundary={collisionBoundary}

Inference, not a verified cause: if the native Android menu occupies the same area above the live text range, BB's preferred placement could overlap it. This component handles its viewport/timeline collision boundary, but does not supply native-toolbar geometry to that positioning calculation. Static source cannot establish the native menu's actual bounds, layering, hit testing, or browser-specific behavior. Raising a CSS z-index or forcing the opposite side without measuring the device is not a demonstrated root-cause repair.

6. Proposed next experiment and fix gate

Not confident enough to choose a fix. Obtain a real Android reproduction at this trusted base with the native menu left open; record exact versions and capture both menus. Compare above and below placement at viewport edges, multi-line selections, and handle dragging. Only after reproducing the occlusion should a placement change be selected and protected by a regression that fails before the repair. The current tests explicitly expect above-selection behavior for coarse pointers, so merely changing that expected value would not prove the Android defect was fixed.
