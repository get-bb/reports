#6990 · Transient upstream failures overwrite Claude session affinity

BugPriority: MediumEffort: Lowprovidersprovider-claude-codeconfirmed-reproIssueNovember 4, 2026

Verdict: REPRODUCED · Root-cause confidence: high. Both reproduction runs use trusted main commit 8d131a26dd17b589a06c3af3791d87a717c1eaef. Production source is unchanged.

1. TL;DR

An established Claude conversation switches to a second pooled account when its first account encounters a temporary upstream failure. A successful fallback overwrites the conversation's stored affinity, so the next request stays on the fallback even after the original account recovers. The routing code remembers that an account was attempted, but does not remember whether it failed transiently or was genuinely unable to serve the account. Seven deterministic cases reproduce the missing retry and lost original pin in two clean checkouts. This verifies routing, not a cache-billing amount or a live provider outage.

5. Root cause

  1. The selected account is marked attempted before upstream execution. That single set is later used to decide whether another account should replace its binding.
  2. Connection failures break the inner loop. HTTP transient statuses share a failover block with credential refusals. Non-auth transient statuses do not take a same-account retry path.
  3. The rebind predicate considers attempted membership sufficient, except for a model-family quota detour: 
    const rebind =
  affinityKey !== null &&
  !familyDetour(boundAccountId) &&
  (bound === undefined ||
    bound.account.id === selected.account.id ||
    (binding === routing.binding && attempted.has(bound.account.id)));
    There is no failure-reason distinction in that predicate.
  4. A successful fallback calls selected.accept(), which writes the fallback account into both the in-memory affinity map and PoolAffinityStore. The store upserts the account ID in SQLite. This explains why the following request has no reason to return to the recovered account.

The underlying defect is conflation of a temporary upstream detour with an account-specific routing disqualification. Merely adding a retry without preserving the original binding would leave the bug whenever a temporary outage outlasts those retries.

6. Proposed fix

Keep failure reasons in request-local routing state. For a pinned account, use bounded, cancellable retries for transient transport and server failures, respecting the pool's inline-wait limit and cancellation. If those retries exhaust, allow the request to complete on another account without replacing the established session binding. Keep authentication and account-wide quota refusals eligible for genuine rebinding. Preserve existing streaming rules: never replay an already-delivered response stream.

Existing family-quota detour handling provides a local precedent. The exact backoff policy is not established by this reproduction. Important follow-up tests include cancellation during backoff, long Retry-After values, all-accounts failure, new sessions, family limits and credential refusals.
