Verdict: NOT REPRODUCED · Root-cause confidence: low

1. TL;DR

The report describes a community renderer refusing screenshots saved outside the conventional Unix temporary directory. That renderer's implementation is not in the trusted bb main checkout, so its refusal and proposed cause cannot be verified under this investigation's source restrictions. The closest executable core check reads real fixture image bytes both from the operating-system temporary directory and from a separate directory outside /tmp; both reads succeed. A caller-supplied workspace root still rejects an image outside that root, as designed. This is an evidence limitation, not a finding that the reporter's plugin works correctly.

5. Root cause and boundaries

The external renderer's root cause is not established. Trusted repository documentation classifies genui as a community caller with no in-repo implementation: docs/api_to_audit.md:4328. A tracked-plugin inventory in each run also reports that it is absent. The built-in inline-vis plugin is a different subsystem: plugins/inline-vis/README.md:1 describes HTML/Markdown previews rather than the reported Image renderer.

The core disk-read command validates an absolute path and delegates to the transport helper; it does not introduce a workspace/storage/tmp allowlist: apps/host-daemon/src/command-handlers/host-files.ts:235.

  return readFileForTransport({
    ...(command.ifNoneMatch !== undefined
      ? { ifNoneMatch: command.ifNoneMatch }
      : {}),
    followRootSymlink: command.followRootSymlink,
    resolvedPath: command.path,
    resultPath: command.path,
    ...(command.rootPath !== undefined ? { rootPath: command.rootPath } : {}),
  });

The transport helper returns an unrestricted resolved path only when no caller-specified root is present. Otherwise it resolves the real paths and enforces containment: apps/host-daemon/src/command-handlers/file-read.ts:203.

async function resolveReadablePath(
  args: ReadFileForTransportArgs,
): Promise<string> {
  const rootPath = args.rootPath;
  if (!rootPath) {
    return args.resolvedPath;
  }

  const realRootPath = await resolveReadRootPath({ ...args, rootPath });
  const realResolvedPath = await fs
    .realpath(args.resolvedPath)
    .catch((error: unknown) => throwMissingTargetOrRethrow(args, error));
  if (!isPathWithinDirectory(realRootPath, realResolvedPath)) {
    throw new CommandDispatchError(
      "invalid_path",
      `Path "${args.resultPath}" escapes read root`,
    );
  }

  return realResolvedPath;
}

Consequently a rejection before this call could originate in a plugin's policy, but that is a hypothesis, not verified causation. Changing this core helper would not be justified by the observed successful reads.

6. Proposed next experiment and fix safety

First identify the installed community plugin version and obtain separately authorized, trusted source for its image loader. On an isolated macOS instance, inspect its canonical-path checks and reproduce the actual renderer using a fresh screenshot. Only then decide whether its documented access policy should accept the OS temporary directory, or whether a sanctioned copy into thread storage is appropriate. Test symlink escapes, prefix-confusable siblings, readable files outside approved roots, and the successful image path at that policy's owner.

No PR: the bug was not reproduced in trusted main, and the named renderer's code is absent. Expanding a file allowlist or automatically copying rejected files also changes a security boundary and is excluded from this rule's simple-fix allowance.
