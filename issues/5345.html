#5345 · Pre-provisioning provider discovery falls back to the primary machine

BugPriority: MediumEffort: Highproviders · workspaces · provider-acpGitHub issueOctober 10, 2026

Verdict: PARTIALLY REPRODUCED · Root-cause confidence: high for the provider-discovery path.

Trusted public repository: get-bb/bb · base 3912f4aaefb7dff55c7e0cb5003b26b5cf1457dc

1. TL;DR

A new machine does not yet have a host ID, but the New Thread composer treats its provider discovery as an ordinary unscoped request. The server consequently asks the primary machine which installed-only agents are available, rather than describing the machine that will be provisioned. When that primary machine lacks an agent, the agent is absent from the returned list; the same agent appears once discovery targets a connected machine that has it. Two clean trusted checkouts reproduce this server response difference. The custom image, actual provisioner, rendered picker, and real agent process were not exercised, so the full reported UI workflow is only partially reproduced.

import { describe, expect, it } from "vitest";
import { systemProviderInfoSchema } from "@bb/server-contract";
import { registerHostRpcResponder } from "../helpers/host-rpc.js";
import { seedHostSession, seedPrimaryHost } from "../helpers/seed.js";
import { withTestHarness } from "../helpers/test-app.js";

describe("issue 5345: discovery before a target machine exists", () => {
  it("cannot offer an installed-only target agent with the unscoped new-machine query", async () => {
    await withTestHarness({}, async (harness) => {
      const primary = seedHostSession(harness.deps, { id: "repro-primary" });
      seedPrimaryHost(harness.deps, primary.host.id);
      const registration = harness.deps.providerRegistry.get("acp-omp");
      expect(registration?.visibility).toBe("installed");

      const registerHealth = (
        machine: ReturnType<typeof seedHostSession>,
        hasAgent: boolean,
      ) => {
        registerHostRpcResponder(harness, {
          hostId: machine.host.id,
          sessionId: machine.session.id,
          handle: (request) => {
            if (request.command.type !== "provider.health") {
              throw new Error(`Unexpected command ${request.command.type}`);
            }
            const installed =
              hasAgent && request.command.providerId === "acp-omp";
            return {
              ok: true,
              result: {
                supported: true,
                health: {
                  status: installed ? "ready" : "not_installed",
                  statusMessage: null,
                  accountEmail: null,
                  planLabel: null,
                  installedVersion: null,
                  minimumSupportedVersion: null,
                  canInstall: false,
                  canUpdate: false,
                  loginCommand: null,
                },
              },
            };
          },
        });
      };
      registerHealth(primary, false);

      const list = async (query: string) => {
        const response = await harness.app.request(
          `/api/v1/system/providers${query}`,
        );
        expect(response.status).toBe(200);
        return systemProviderInfoSchema
          .array()
          .parse(await response.json())
          .map((provider) => provider.id);
      };
      const unscoped = await list("");
      const primaryScoped = await list("?hostId=repro-primary");
      const target = seedHostSession(harness.deps, { id: "repro-created-target" });
      registerHealth(target, true);
      const targetScoped = await list("?hostId=repro-created-target");
      console.log(
        JSON.stringify({ unscoped, primaryScoped, targetScoped }, null, 2),
      );

      expect(primaryScoped).not.toContain("acp-omp");
      expect(targetScoped).toContain("acp-omp");
      expect(unscoped).toContain("acp-omp");
    });
  });
});

6. Proposed fix and safe-fix decision

First settle how provisioning-time provider availability is represented and validated, including whether it depends on provider inputs or a specific image. Carry selected new-machine context to discovery and keep predictions separate from observed existing-host health. Once the machine connects, use its actual health and model catalog; do not retain stale primary-host results or weaken disabled-provider filtering.

No automatic product patch is safe under the simple-fix rule. The fix needs a product decision and a public contract across environment/plugin declarations, the discovery API, and the composer. Showing every installed-only provider or changing its visibility would violate the existing-machine negative control and worsen the related over-show problem. No fix branch, dependency, protocol change, or pull request was created.
