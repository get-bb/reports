#7256 · Personal child environment eligibility

Bug Priority: Medium Effort: Low threads workspaces

GitHub issue · November 7, 2026 · Base 55135d1e5045d6c5d3c24f5a4d5556ed3e11cb00

Verdict: REPRODUCED · Root-cause confidence: high

1. TL;DR

A Personal thread can be attached to an ordinary directory, but the automatic child-placement policy still treats its environment as a reusable personal workspace. Thread creation then rejects the automatically selected environment with a 409 compatibility error. A regression at the real server thread-creation boundary reproduces this for default placement, personal workspace sugar, and an explicitly selected personal provider on the same machine. The same agent repeated all three failures in a second clean checkout. The proposed fix checks the stored environment's eligibility before automatic reuse and otherwise leaves normal workspace creation in charge.

5. Root cause

  1. The directory-switch service creates an ordinary environment with providerOwnsPath: false and environmentProvider: null in the Personal project.
  2. The Personal-parent branch recognizes a personal request and automatically returns the parent's environment ID. Its only environment lookup is for an explicitly named machine; no check establishes that the parent still has a reusable personal workspace.
  3. The downstream compatibility check requires a Personal environment to have a non-null environmentProviderId. The automatically chosen ordinary directory has none and therefore raises an ApiError with status 409.
  4. The normal default branch can instead select the personal-workspace provider. The premature reuse return prevents reaching it.

The bug is in policy selection, not in the compatibility validator. Relaxing the validator would permit an unintended environment kind; it is not necessary to fix spawning.

6. Proposed fix and checked result

Look up the parent's stored environment once. Automatically reuse it only if it is ready, still in the Personal project, has provider metadata, has no teardown in progress, and matches any requested existing machine. Otherwise fall through to the existing fresh-workspace path. Using the same non-null-provider criterion as the compatibility validator preserves support for custom Personal workspace providers.

Keep all explicit reuse and path compatibility validation unchanged. Keep valid Personal-parent reuse and explicit other-machine placement unchanged. Correct the existing policy test fixture to include the personal provider metadata it claims to represent.
