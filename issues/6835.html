#6835 · Synchronous event persistence blocks timers during SQLite waits

BugHighEffort: Highhost · threads · perfGitHub issue2026-11-02 · base 93411e8e6afad9a8cf50244a2cd9f468543f859e

Verdict: PARTIALLY REPRODUCED · Root-cause confidence: high for synchronous event-loop blocking; unverified for the reported cold-read I/O attribution.

1. TL;DR

Database work on the server's JavaScript thread can prevent unrelated timers and request handlers from running while SQLite waits. Two clean-source runs at the same trusted main commit demonstrate this mechanism: a worker holds a real SQLite write lock for 700 ms while the server's event-append transaction runs, and a 20 ms timer fires after 739.2 ms and 739.1 ms. This is a controlled contention experiment, not a reproduction of multi-gigabyte cold reads or the reported 15–18 second outages. Main already contains the relevant covering index and incremental pruning, including a zero busy timeout during pruning. Those mitigations do not make the remaining synchronous database operations asynchronous.

function fixture() {
  const directory = mkdtempSync(join(tmpdir(), "bb-6835-"));
  const filename = join(directory, "fixture.sqlite");
  const template = createMigratedConnection();
  try {
    writeFileSync(filename, template.$client.serialize());
  } finally {
    template.$client.close();
  }
  const db = createConnection(filename);
  const host = upsertHost(db, noopNotifier, { name: "reproduction" });
  const { project } = createProject(db, noopNotifier, {
    name: "reproduction",
    source: { type: "local_path", hostId: host.id, path: directory },
  });
  const thread = createThread(db, noopNotifier, {
    projectId: project.id,
    providerId: "codex",
  });
  return {
    db,
    filename,
    thread,
    close() {
      db.$client.close();
      rmSync(directory, { recursive: true, force: true });
    },
  };
}

async function withWriterLock(filename: string, work: () => Promise<void>) {
  const worker = new Worker(
    `const { parentPort, workerData } = require("node:worker_threads");
const Database = require(workerData.modulePath);
const db = new Database(workerData.filename);
db.exec("BEGIN IMMEDIATE");
parentPort.postMessage("locked");
setTimeout(() => {
  db.exec("COMMIT");
  db.close();
}, 700);`,
    {
      eval: true,
      workerData: {
        filename,
        modulePath: createRequire(import.meta.url).resolve("better-sqlite3"),
      },
    },
  );
  try {
    await new Promise<void>((resolve, reject) => {
      worker.once("message", () => resolve());
      worker.once("error", reject);
    });
    await work();
  } finally {
    await worker.terminate();
  }
}

5. Root cause

The daemon-events route synchronously enters an immediate SQLite transaction before returning to the event loop. Its actual call boundary is internal/events.ts:1213–1218:

appendResult = deps.db.transaction(
  (tx) => appendDaemonEventsInTransaction(tx, eventInputs),
  { behavior: "immediate" },
);

createConnection constructs a synchronous better-sqlite3 database and sets busy_timeout = 5000. The transaction wrapper invokes the caller directly (connection.ts:340–346). A contended BEGIN IMMEDIATE therefore waits in the same thread that must run the timer. The reproduction releases that lock from a worker so progress does not depend on the blocked thread. Merely putting an await around a synchronous call would not move the database work off-thread.

This proves a mechanism capable of contributing to stalls, not the cause of the specific long SELECT timings. A single lock wait is bounded by the configured timeout; this experiment does not establish why the reported stalls exceeded it. WAL readers normally coexist with a writer. Slow reads, storage latency, page faults, and longer sequences of synchronous calls require their own evidence.

The thread/turn/type covering index is already defined at schema.ts:844–850 and installed by real migrations. The query-plan test asserts that SQLite selects it for the type lookup. Adding a redundant index is not justified by this reproduction.

Pruning already uses persistent progress, 32/500 batch limits, and a temporary zero busy timeout with restoration. The server calls it synchronously at event-pruning.ts:65–76. Bounded rows and no lock waiting reduce contention but cannot guarantee that an individual disk operation returns quickly.

6. Proposed fix and simple-fix decision

Preserve the existing index and bounded pruning. To guarantee that slow storage cannot stop server timers, design asynchronous database ownership: for example, a dedicated database worker with explicit request scheduling and transaction boundaries. Preserve ordering, commit notifications, synchronous internal assumptions, and shutdown behavior; then test both locked writes and cold reads while an unrelated request or heartbeat remains responsive.

No automatic fix or pull request: moving this synchronous database boundary off-thread requires an architecture decision and coordinated contracts. That fails the simple-fix criteria. Adding another index requires a migration and is unsupported by the observed access path; simply making a function async would not address the cause. The exact large-database read stall was also not reproduced. No fix branch was created or pushed.

No open pull request linked to #6835 was present in the issue's cross-reference metadata or the open-PR search at investigation time. No linked pull-request code was checked out.
