1. TL;DR

A desktop client connected to another machine's server can lose its own checkout's folder action because the app chooses the server as its path-picker machine. The actual React hook selects a connected remote primary ahead of a known, enrolled, connected local client. Project settings allow path editing only on that selected machine, so the local row is excluded. The same mistake suppresses native folder picking even when the local helper supports it. Two clean trusted-base test runs reproduce this logic failure; neither is a Windows desktop end-to-end test.

5. Root cause

apps/app/src/hooks/useLocalPathPicker.tsx:47 chooses the connected primary first. With distinct client and server identities, this both picks the wrong checkout-edit machine and makes the native-picker equality check false:

export function usePathPickerHost(): PathPickerHost {
  const { localDaemonHostId, supportsNativeFolderPicker } = useHostDaemon();
  const primaryHost = usePrimaryHost();

  const connectedPrimaryHostId =
    primaryHost?.status === "connected" ? primaryHost.id : null;
  const hostId = connectedPrimaryHostId ?? localDaemonHostId;
  const hostName =
    primaryHost && primaryHost.id === hostId ? primaryHost.name : null;
  const canUseNativeFolderPicker =
    supportsNativeFolderPicker &&
    localDaemonHostId !== null &&
    hostId === localDaemonHostId;

  return {
    canUseNativeFolderPicker,
    clientHostId: localDaemonHostId,
    hostId,
    hostName,
  };

apps/app/src/views/ProjectDetailSettingsView.tsx:400 computes isPickerHost from the returned ID and passes it as canEditPath. apps/app/src/views/ProjectDetailSettingsView.tsx:145 disables the row's action when this is false. This is a UI routing gate, not a server authorization rule.

apps/app/src/lib/system-config-atoms.ts:303 shows the helper identity and connection-aware identity are separate. A local helper alone is not sufficient proof that a host belongs to the server's enrolled connected host list. The proposed repair checks that list before preferring the helper's host and preserves the old fallback when no connected candidate exists.

apps/server/src/routes/hosts.ts:412 already validates usable hosts, requires picker host/client equality, and dispatches the native picker to the selected online daemon. Those existing server checks are unchanged.

6. Proposed fix

In the existing picker hook, prefer the helper's host only when that host is present and connected in the server's host list. Otherwise preserve the connected-primary and local-helper fallback order. Resolve the display name from the selected host rather than assuming it is the primary. Keep all existing server validation, SDK contracts, manual selection, and CLI behavior unchanged.

The local repair changes two files in the app picker subsystem. It introduces no dependency, protocol, schema, stored-data, permission, or architecture change. The regression protects metadata selection, native-picker routing/submission, manual entry, and fallback controls. The same six relevant existing suites pass after the repair: 30 tests across picker, host-query, quick-create, project menu, and path dialog behavior.
