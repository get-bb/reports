#5503 · Native download navigation lacks a file handoff

BugMedium priorityHigh effortmobile GitHub issueOctober 14, 2026

Trusted base: e5651418281c98e841d390eba5364e16f42bee40, fetched from main and checked against the target repository's main commit.

Verdict: PARTIALLY REPRODUCED · Root-cause confidence: medium · Reproduction label: partial-repro

1. TL;DR

The issue describes downloads replacing the iOS app or opening an unauthenticated system browser. Two clean source checkouts reproduce the routing decisions that permit those outcomes: a generated Tasks download URL is admitted as an ordinary page on a root-mounted profile, but selected for external browsing on a prefixed profile. The page uses an ordinary download anchor, while the native shell has no file-download handler or native file-transfer request. This investigation ran the actual URL builder, navigation predicates, and bridge parser, not an iOS WebView. Raw-byte rendering, Safari cookie behavior, the displayed filename, and recovery by force-quitting therefore remain unverified here.

5. Root cause

File actions are treated as ordinary navigation without a native file handoff. The Tasks builder returns a root-absolute API endpoint. The shell first admits any URL within its profile scope, and otherwise externally opens HTTP(S) URLs. There is no download-specific branch.

Tasks URL builder, lines 1–5:

return `/api/v1/plugins/tasks/http/attachments/download?attachmentId=${encodeURIComponent(attachmentId)}`;

Actual screen navigation callback, lines 342–348:

if (isShellNavigation(request.url, profile.serverUrl)) return true;
if (isExternallyOpenable(request.url)) {
  void Linking.openURL(request.url).catch(() => undefined);
}
return false;

Scope predicate, lines 28–43: an empty prefix admits every same-origin path; a non-empty prefix admits only that subtree. External URL predicate, lines 57–65: HTTP(S) and mailto are externally openable. The test invokes both actual functions in exactly the screen's branch order; it does not mount the screen or invoke the native linking API.

File preview Download, lines 1303–1307, and Tasks attachment anchor, lines 191–193, use ordinary anchors with a download attribute. The screen WebView configuration has no file-download/new-window handler and disables back/forward gestures.

The locally installed pinned iOS WebView implementation, apple/RNCWebViewImpl.m:1461, recognizes attachment disposition or a non-displayable MIME response. It cancels and emits a download event only when _onFileDownload is set. This is supporting source evidence for the missing interception, not a demonstration that WebKit renders every file as text.

Bridge schema, lines 15–56, has no file-save request and accepts only HTTP(S) share URLs. The share handler, lines 72–94, forwards share content to the native share API, not an authenticated file transfer.

Prefix handling is broader than this one helper: the web API client, lines 4–12, uses window.location.origin and returns pathname/search URLs. Correcting only the Tasks link would not provide a native download implementation. The Tasks response, lines 540–552, already sets download metadata; this investigation does not establish an additional server-response defect.

6. Proposed fix and safety gate

Introduce a capability-negotiated native file-save operation shared by web download sites, with bounded payload handling, explicit filename/MIME metadata, cancellation, and temporary-file cleanup. Network downloads need the correct profile session and URL scope; blob data must be transferred from the page rather than opened in Safari. Add WebView download and new-window interception for pages without the new capability, ensuring that unhandled downloads cannot replace the shell. Do not weaken the origin/prefix navigation boundary or forward credentials to arbitrary URLs.

Validate root/prefixed profiles, authenticated responses, blob files, user cancellation, and old/new bridge combinations on an actual iOS simulator or device. First capture a native before/download/after sequence to settle the raw-byte display and recovery claims.

No fix PR was attempted. A complete root-cause fix crosses web/native bridge contracts and authenticated file handling, which fails the autopilot's single-subsystem/no-protocol-or-security-boundary-change conditions. The native symptom was also only partially reproduced. Silently blocking downloads is not a substitute for saving files. No linked open PR was present in the issue timeline or the open-PR search at review time.
