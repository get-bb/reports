#7435 · Cleanup recovery blocked by unrelated private processes

BugPriority: MediumEffort: Highworkspaces · hostGitHub issueNovember 11, 2026

Verdict: REPRODUCED · Root-cause confidence: high · Reproduction label: confirmed-repro

1. TL;DR

Cleanup recovery can be blocked by a live same-user Linux process that has no working directory or mapped file in the workspace. The daemon scans all same-user processes, and an access-denied error while reading a process's working directory or mappings adds that process to a global uninspectable list. The server refuses recovery whenever that list is nonempty. A real process with dumpability disabled reproduces this with all four UIDs unchanged, so filtering on real UID alone cannot resolve the general case.

This is also a deliberate fail-closed deletion-safety guard: a non-dumpable process actually inside the workspace produces the same inspection result. Automatically ignoring access-denied errors would allow that genuinely active process through. No automatic fix or pull request is safe under the simple-fix rule without a reviewed safety/product decision.

5. Root cause

  1. Global enumeration and UID qualification, lines 43–58: every numeric procfs entry is considered, and any matching UID qualifies it. The algorithm reads cwd and maps before it can determine workspace membership.
  2. Unreadable-process classification, lines 63–81: a live process with EACCES goes into unreadablePids without evidence tying it to this workspace. Only genuine process disappearance is tolerated.
  3. Daemon RPC assembly, lines 134–149: the raw inspection is returned along with tracked setup/hook activity; no further workspace relevance filter is applied.
  4. Server recovery gate, lines 1073–1091: any unreadable PID triggers HTTP 409. This explains why zero positively identified workspace processes is insufficient.

The existing recovery route contract table explicitly expects 409 for an inspection with empty active PIDs and nonempty unreadable PIDs. The existing inspector test similarly enforces refusal for unreadable same-user processes. The new real-process experiment establishes the overlooked everyday source of that unreadability rather than pretending this was an untested conditional.

6. Proposed fix and safety decision

First choose an explicit recovery policy for processes whose workspace membership cannot be established. Preserve the fail-closed default until that policy is reviewed. A possible direction is an explicitly acknowledged, narrowly scoped operator recovery override that still blocks positively identified workspace users and active tracked hooks; it would require coordinated CLI/SDK/server/daemon contract and safety review as applicable. This report does not recommend or implement an unchecked ignore-EACCES change.

Testing only real UID is insufficient: both hidden helper cases retain the daemon's UID in all four positions. Ignoring unreadability also cannot distinguish the safe outside case from the unsafe inside case. A future regression contract must cover both outcomes and keep the active-process control.

Simple-fix decision: stopped before making a production change. Altering the fail-closed deletion-safety boundary or introducing an operator override violates the rule's no-security-boundary/no-product-decision conditions, regardless of patch size. No fix branch was pushed and no pull request was opened.
