#6277 · Catalog details omit close arbitration

BugPriority: MediumEffort: Lowui · desktop Issue · October 25, 2026 · base 3a2c49a267cd2a62a96ebff880068a7c37074251

Verdict: REPRODUCED · Root-cause confidence: high · reproduction label: confirmed-repro

1. TL;DR

The built-in catalog can display plugin details as tabs, but its view never registers a close-command handler or a desktop close-request listener. A renderer close request is consequently unhandled even with visible detail tabs. Desktop preload forwards that false result, and the main process closes the window. A renderer regression reproduces this for both close entry points and both viewport layouts; a second clean checkout repeats all four failures. Native macOS keyboard/menu dispatch was not exercised on this Linux host.

Without listeners, desktop preload computes false and sends it back:

apps/desktop/src/preload.ts:569

ipcRenderer.on(BB_DESKTOP_CLOSE_WINDOW_REQUEST_CHANNEL, () => {
  let handled = false;

  }
  ipcRenderer.send(BB_DESKTOP_CLOSE_WINDOW_RESPONSE_CHANNEL, handled);

The desktop main-process response handler closes the application window for that false response. This is intended fallback behavior; the missing integration is in the catalog, not in desktop IPC.

6. Proposed fix and validation

Add one local close-active-tab callback that returns false unless a detail panel is visible and active, otherwise calls the existing closeTab and returns true. Register that same callback with panel.close and onCloseWindowRequest, retaining effect cleanup. No public protocol, SDK, stored state, dependency, or desktop change is necessary.

The implementation changes two files in the existing catalog subsystem: 143 additions, zero deletions. The focused regression passes all four cases after the fix. The complete affected catalog test and three existing close-command suites pass: 87 tests in four files. App build, typecheck, and lint pass; lint emits 246 warnings and no errors.
