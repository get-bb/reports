1. TL;DR

The report describes a browser page that responds to clicks but does not accept typing. The production desktop view manager has no fallback that requests native keyboard focus when an unfocused page receives a pointer press. Its navigation guard can return focus to the host; a later pointer press only disarms that guard. Two new manager-boundary regression cases expose this missing recovery on unchanged trusted main in two clean checkouts. This is not a native macOS or Linear reproduction: the Electron objects are the repository's existing test doubles, so the actual platform event ordering and text-caret symptom remain unverified.

Complete test insertion

This code belongs in the existing manager test file, whose fixtures it uses; it is not a standalone test module.

  it.each([false, true])(
    "restores keyboard focus on pointer press after an unfocused reveal (rejected navigation focus: %s)",
    async (rejectNavigationFocus) => {
      vi.useFakeTimers();
      const focusHostWebContents = vi.fn(() => {
        requireFakeView(0).webContents.nativelyFocused = false;
      });
      const manager = createDesktopBrowserViewManager({
        partition: "persist:test",
        focusHostWebContents,
      });
      const hostWindow = new FakeHostWindow({
        contentBounds: { width: 700, height: 450 },
        webContentsId: 92,
      });
      try {
        manager.attach({
          hostWindow,
          request: {
            threadId: "thread-1",
            tabId: "browser:a",
            url: "https://example.com",
            bounds: { x: 0, y: 0, width: 700, height: 450 },
            visible: false,
          },
        });
        const view = requireFakeView(0);
        manager.setVisibleWithoutFocus({
          hostWindow,
          request: { tabId: "browser:a", visible: true },
        });
        expect(view.visible).toBe(true);
        expect(view.webContents.focusCalls).toBe(0);
        if (rejectNavigationFocus) {
          view.webContents.emitDidStartLoading();
          view.webContents.nativelyFocused = true;
          view.webContents.emitFocus();
          await vi.advanceTimersByTimeAsync(0);
          expect(focusHostWebContents).toHaveBeenCalledExactlyOnceWith(92);
        }
        expect(view.webContents.isFocused()).toBe(false);
        view.webContents.emitInputEvent("mouseDown");
        await vi.advanceTimersByTimeAsync(0);
        expect(view.webContents.focusCalls).toBe(1);
      } finally {
        manager.destroyAll();
        vi.useRealTimers();
      }
    },
  );

5. Root cause

The confirmed code-level gap is that permission to retain focus is not a request to acquire focus. The load and focus handlers arm a navigation guard, then defer rejecting native focus by one timer turn. The pointer listener only clears that guard:

const listener: PointerFocusListener = (_event, input) => {
  if (POINTER_PRESS_INPUT_TYPES.has(input.type)) {
    stopAwaitingPointerFocus(entry);
  }
};

When the timer has already returned focus to the host, clearing the listener cannot move keyboard focus back. Without a load-armed listener there is no corresponding pointer recovery at all. The actual focus operation exists in explicit focus handling, but the pointer path does not invoke it. Visibility handling intentionally skips that operation when asked to show without focus.

Existing coverage at the focus-event ordering table supplies native focus explicitly and delivers the press before the deferred rejection runs. It does not cover a press after completed rejection, or a press without native focus transfer. The focus guard originated in the self-reload focus-stealing fix; that protection must remain intact.

Overall confidence is medium, not high: the mechanism is deterministic under these inputs, but the unit fixture supplies the allegedly problematic native ordering. The test cannot establish whether Electron on macOS emits it during a real click, nor prove that this explains the original incident.

6. Proposed fix and safety gate

First confirm the native event sequence on a macOS development desktop with a local editable HTML page, recording guest document.hasFocus(), webContents.isFocused(), pointer events, and the host focus-return callback. Exercise both a revealed tab and a reload with the deferred rejection completed before the click.

If confirmed, preserve reload focus rejection and add a persistent pointer-press recovery path for the current, visible, live, user-controlled page only. It must not focus a hidden page, an inactive server, a controller-owned or leased tab, or a background host window, and must avoid duplicate notifications if native focus already arrived. Recheck those conditions when deferred work runs.
