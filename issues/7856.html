BugPriority: MediumEffort: Mediumproviders · workflowsGitHub issue

Verdict: REPRODUCED at the catalog-to-validation boundary, repeated in a second clean checkout by the same agent. Root-cause confidence: high. No live Cursor session was exercised; external catalog counts and reported versions remain unverified.

1. TL;DR

The default Cursor catalog is deliberately limited to six primary model identifiers in repository configuration. Other advertised models are retained separately as selected-only entries. Workflow overrides intentionally exclude those entries, while inherited origin-thread selections may use them. The reproducible defect is an unexplained literal-selection mismatch that does not distinguish an advertised selected-only model from an unknown identifier or explain the supported registration workaround. The proposed narrow fix improves that diagnostic and documents the existing policy rather than silently expanding which models workflows may select.

5. Root cause

Cursor's configured primary-model list puts other advertised models in selectedOnlyModels; workflow literal validation searches only models and emits an unexplained mismatch for an otherwise known model.

  1. Cursor primary catalog configuration supplies the six primary IDs.
  2. splitPrimaryModels partitions other advertised models into selectedOnlyModels, rather than dropping them.
  3. Workflow catalog adapter requests the ordinary provider catalog; literal validation searches only models and throws a generic mismatch:
    const model = models.models.find(
  (candidate) => candidate.id === selection.model || candidate.model === selection.model,
);
if (model === undefined) {
  throw new Error(
    `Model mismatch for literal workflow selection ${tupleDescription(selection)}`,
  );
}
  4. Worker dispatch admits selectedOnlyModels only for inherited selections. This is an intentional contract, also covered by existing lifecycle coverage.
  5. Selected-model discovery refines known catalog reasoning support without promoting entries between catalogs.
  6. Existing custom-model promotion moves a matching selected-only entry into the explicit catalog when registered. Custom model configuration documents registration and config refresh.

Consequently, a reasoning probe does not change workflow eligibility. Broadly accepting every selected-only entry would also change the existing treatment of retired models and is not part of this fix.

6. Proposed fix

Preserve the current selection rules. When a rejected literal model matches a selected-only entry, explain that it is outside the default provider catalog and point to customModels in config.json, or inheritance from the origin thread. Document the same rule in the shipped workflows authoring reference. Do not claim that unknown IDs are verified or that reasoning discovery promotes eligibility.

The candidate patch changes three existing workflows files, with 22 additions and 3 deletions: 25 total changed text lines. It adds no dependency, generated output, stored data, public protocol, schema, permission change, or selection-policy decision. It addresses the actionable-error alternative rather than automatically exposing more provider models.
