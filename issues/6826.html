#6826 · Retry admission accumulates recovery turns

Bug Priority: Medium Effort: Medium providers · threads · provider-retry

GitHub issue · 2026-11-02 · trusted base 916d684ac23d0b0de82c09cfc7553a50287d2188

Verdict: REPRODUCED · Root-cause confidence: high · Reproduction label: confirmed-repro

1. TL;DR

A thread with a future recovery retry still admits another message as a new turn. If that message also fails, retry admission permits another queued recovery because its request ID differs. Three distinct failures on one thread produced three pending retries, then three separate recovery turns. When the provider had accepted each input, all three rows contained the same continuation nudge; when it had accepted none, the three rows retained three different inputs. The mechanism reproduced twice against unchanged production code in clean trusted checkouts; production fleet quantities and actual subscription behavior were not tested.

5. Root cause

retryFailedTurn derives an original request ID from the most recent failed turn and uses thread.id:originalRequestId as its in-flight key. Its persistent duplicate check calls hasQueuedRetryOfTurnRequest, whose WHERE clause matches both thread ID and retryOfTurnRequestId. This correctly rejects a second live retry of the same original request, including claimed rows, but does not combine different original requests.

const originalRequestId = chain.originalRequestId;
const inFlightKey = `${thread.id}:${originalRequestId}`;
if (
  retriesInFlight.has(inFlightKey) ||
  hasQueuedRetryFor(deps, { threadId: thread.id, originalRequestId })
) {
  throw new ApiError(409, "retry_already_queued", ...);
}

Every later message admitted by the dispatch checkpoint receives a fresh original request ID. The built-in failure listener independently asks to retry each eligible failure; it has no pending-thread coalescing step. The test directly exercises that shared retry admission service, rather than mocking it.

retryInput deliberately replaces accepted input with a continuation nudge, but replays never-accepted input. Thus accepted failures accumulate indistinguishable nudges while rejected inputs accumulate distinct payloads. Each enqueue starts with groupWithNext: false, and the drain submits each separate group as a turn. The repeated-turn symptom follows directly.

The status command lists flat rows rather than per-thread aggregates. That is a separate diagnostics enhancement, not the cause of accumulation.

6. Proposed fix and simple-fix safety

A safe solution needs thread-level coordination among compatible pending recoveries, preservation of every never-accepted input in order, and a claim-safe handoff to the drain. Repeated accepted-input nudges can be redundant; newly rejected input is not. Simply widening the duplicate check to thread ID would suppress recovery of new inputs, while concatenating everything into one row loses input-group boundaries and retry provenance.

No automatic fix PR is safe under the decision-free simple-fix rule. Existing retries preserve the failed turn's model, reasoning level, service tier, and permission mode, and existing queue grouping explicitly requires matching execution tuples. A thread may change execution settings between failures. Choosing which route/tuple and original retry chain owns a combined recovery is a product-policy decision; an unconditional per-thread guard is not a lossless fix.

Next step: define the compatible execution envelope and recovery provenance, then extend this regression with mixed acceptance, changed execution tuples, concurrent claim/admission, and preserved input-group ordering. No production source was edited, no fix branch was pushed, and no pull request was opened. GitHub timeline and open-PR search showed no linked open PR during this run.
