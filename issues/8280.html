1. TL;DR

The reporter describes missing rectangular regions in a large desktop conversation window and attributes an apparent workaround to a larger Chromium GPU memory allowance. Trusted main does not explicitly configure Chromium switches in the desktop source, and its desktop package declares Electron 44.10.2. Those facts do not establish that a tile budget causes missing content. This environment cannot exercise the reported physical display and compositor path, so the rendering symptom, memory-pressure mechanism, and workaround remain unverified. There is no safe production change or regression test to propose as a confirmed fix.

5. Root-cause investigation

Root cause is not established. An absence of an application-level GPU override is not evidence that the compositor exhausted its tile budget. A measured budget, tile eviction trace, frame captures, and controlled comparison on the affected hardware are missing.

The desktop creates native Electron windows through a shared factory:

const browserWindowCreator: DesktopBrowserWindowCreator = {
  create(options) {
    return new BrowserWindow(options);
  },
};

main.ts at the trusted base. The native window options set window geometry and isolated, sandboxed web preferences; they do not encode a display-dependent GPU budget.

The shine style uses a mask and will-change: transform. That identifies a useful profiling target, not a demonstrated cause. The inspected timeline containment class is mobile-breakpoint-only, which also cautions against attributing a desktop symptom to it without a live trace.

Version evidence: desktop version declaration and the Electron dependency declaration in that same package. All permalinks were checked against the recorded base locally.

6. Proposed next experiment; no production fix

  1. Use a clean trusted build on a macOS workstation with a matching high-resolution display; record device pixel ratio, actual window pixel dimensions, display mode, and GPU feature status.
  2. Use an isolated application data directory and a deterministic updating timeline workload. Capture a painted baseline and the first missing-tile frame, plus renderer, GPU, and compositor telemetry.
  3. Compare a smaller window, the large window, and a reduced-animation condition. Measure raster pressure and tile allocation instead of inferring them from appearance.
  4. Only after observing the failure, choose an independently justified controlled memory-budget experiment and verify any improvement over repeated runs. Evaluate memory impact on other displays before selecting policy.
  5. Derive a regression test from the observed failure. Do not replace it with an assertion that a particular startup flag exists.

No PR: the bug was not reproduced on trusted main, its root cause is unknown, and no focused regression test can currently demonstrate failure before and success after a change. Increasing a global memory allowance without measurements would introduce an unverified product/resource policy. GitHub cross-reference metadata and an open-PR search returned no linked open PR.
