#7037 · Agent OOM ranking and service policy

BugHigh priorityEffort: MediumhostGitHub issue2026-11-04 · base 783a6062bd6f485597e66450a149069402780868

PARTIALLY REPRODUCED · Root-cause confidence: high for the observed policy gaps; host-wide OOM failure remains unverified.

1. TL;DR

Agent work is launched without an OOM-priority distinction from the runtime hosting it. A real bridge started through the trusted runtime has the same observed Linux OOM adjustment as its parent: both are zero here. Separately, running the actual machine installer in its isolated test fixture generates a systemd unit with no explicit OOM policy. These are distinct gaps: kernel victim preference and service-manager response. Both observations repeat in a second clean checkout, but no memory exhaustion or live service interruption was induced.

5. Root cause

Bridge launch does not distinguish agent work from its runtime

RuntimeProviderProcessManager.spawnProvider launches the bridge using command, arguments, cwd, and environment, without changing OOM adjustment:

const managed = spawnManagedProcess({
  command: processConfig.command,
  args: processConfig.args,
  cwd: this.args.workspacePath,
  env,
});
const { child } = managed;

spawnManagedProcess creates a process group for lifecycle handling, not an OOM priority class. The real bridge observation confirms unchanged adjustment at this boundary. Linux proc documentation describes how oom_score_adj affects victim selection. Leaving work at its runtime's adjustment supplies no explicit preference for sacrificing work to retain the runtime. This is not proof of which process a native kernel will choose.

Generated service delegates OOM response to manager defaults

The installer service definition sets Restart=always and RestartSec=2, but no OOMPolicy. Running the installer confirms that omission in its actual output. systemd documents that stop terminates the service after an OOM kill, whereas continue logs it and keeps the service running. Unspecified unit policy inherits the manager setting, subject to the Delegate exception; this investigation does not assume every manager uses stop.

Restart behavior provides recovery after stopping, not isolation from a workload death. The server maps daemon-restart interruption to a disconnected message, consistent with the proposed chain. The complete kernel-to-multiple-thread outage chain was not executed.

6. Proposed fix, from first principles

At the Linux provider launch boundary, prefer agent work as an OOM victim without changing the parent runtime or breaking unsupported platforms. Ensure priority is established before descendants launch, and test both the direct child and descendant inheritance. Explicitly select continuing OOM behavior in generated systemd units while preserving recovery if the main daemon dies. Priority is not a memory limit or a guarantee that bb can never be killed.

The next decisive experiment belongs on a disposable native Linux/systemd machine: use a bounded cgroup, distribute a fixed workload over child processes, verify the daemon remains responsive after a child OOM kill, then separately check recovery from a main-daemon kill. Never induce global OOM on a shared host.
