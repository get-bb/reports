#6435 · CLI override re-entry never reaches the bundled command

BugHighEffort: Lowhost · cli · automations GitHub issue2026-10-28 · base f8c0701e94ba74a09bf48b1dcc4f49aa22ce81b7

Verdict: REPRODUCED · Root-cause confidence: high · reproduction label: confirmed-repro

1. TL;DR

A CLI command fails to finish when its BB_CLI override points back to the installed public launcher. The packaged CLI entry follows that override, so the launcher starts another copy of the same entry instead of reaching the bundled CLI. Two clean trusted checkouts reproduced repeated entry with no version output; a control without the override printed the version once. Both experiments were deliberately capped at four launcher entries, so they did not exhaust memory. An open ready PR, #6436, already links this issue; no duplicate fix was opened.

5. Root cause

  1. packages/process-utils/src/host-toolchain.ts:318 resolves bb by checking BB_CLI_LAUNCHER ahead of BB_CLI and the CLI directory.
  2. plugins/automations/src/script-runner.ts:44 resolves and probes that candidate. plugins/automations/src/script-runner.ts:284 then puts that path into the script environment as BB_CLI.
  3. packages/bb-app/src/cli-launcher.ts:145 renders the public launcher to execute the bb entry with the installation runtime.
  4. packages/bb-app/src/launcher.ts:2750 chooses BB_CLI whenever nonempty and passes the environment into the child unchanged with respect to the re-exec guard. With a launcher-backed override, the child repeats the identical decision. Each parent waits for its child, so processes accumulate.
  5. apps/cli/src/bb-cli-reexec.ts:42 already bounds override delegation with BB_CLI_REEXEC=1, but the loop occurs in bb-app before the ordinary CLI is reached.
cliOverride: toOptionalString(args.env.BB_CLI) ?? null,
...
env: createCliEnv({ context: args.context, env: args.env }),

The bb-app CLI entry repeatedly spawns BB_CLI without checking or setting the existing re-exec guard; when BB_CLI resolves to its launcher, every child enters the same path again. The failure is not a script interpreter problem and does not require a running automation scheduler: the environment alone is sufficient to trigger the same real CLI entry path.

6. Proposed fix

At the bb-app CLI delegation boundary, honor the existing BB_CLI_REEXEC guard. Mark a child when following an override, and bypass the override on re-entry so execution reaches the bundled CLI. Preserve the initial override, arguments, exit status and inherited thread context. The regression above exercises those observable contracts with a bounded real child-process chain.

No automated fix was continued: open PR #6436 explicitly closes #6435. Opening another would violate the no-duplicate-PR condition.
