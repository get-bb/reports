Reports · Issue #4396

Current-main isolated timeline remount does not reproduce the reported stall

2026-09-30 · Bug · Medium priority · Medium effort

NOT REPRODUCED in the optimized component fixture. The full application issue remains unresolved by this experiment.

Confidence is high in the recorded fixture observations and low in generalizing them to the original workload. This is not an ALREADY FIXED finding.

Claim, experiment and limitations

The report describes multi-second switches between long threads, with a markdown pane affecting the delay. Here the unmodified current TimelineWindowedItems component is mounted inside a fresh scroll-root ref on each keyed A/B transition. The optimized fixture supplies 100, 1,000 or 5,000 simple text rows per thread, each 48 pixels high, a 600-pixel scrollport and a new measurement map on every mount. It exercises the pending-ref/remount path without persistent measurement caching.

Three cold component mounts and eight warm revisits were measured for each size in each of two clean checkouts: 66 samples total. Cold means a fresh document and first component mount, not a cold machine or complete application launch. Warm means alternating previously selected A/B labels in the same document after priming both; each keyed remount still gets a fresh measurement map. Browser HTTP cache was disabled. No CPU throttling was applied.

The measurement is elapsed time from programmatic click to the third subsequent requestAnimationFrame callback. It includes frame pacing and is not an exact time-to-paint, CPU, network or full thread-switch metric. A Long Animation Frame observer separately records overlapping blockingDuration. Zero observed blocking does not mean zero work. Realized row counts are settled samples, not peak mounts. Simple text rows do not model rich messages, expandable panels, markdown previews, secondary panels, plugins, server loading, workspaces with untracked files or production thread histories. Those remaining paths must be investigated before resolving the issue.

Expected and actual

Expected for this narrow fixture: a keyed remount stays windowed and does not incur a multi-second stall simply because the supplied key list is long. Actual: every sample had 21 realized rows; the largest measured click-to-third-frame interval across both runs was below 50 ms, and no overlapping long-frame blocking was observed. This does not disprove the original 2–9 second application-level observation.

Environment and trusted base

Fetched public origin/main: 79172bcaaaaadec37ae6ab7b098f25b06c7e6e99. Linux x86_64 execution container, Node 24.19.0, pinned pnpm 9.15.0, Vite production build, headless desktop Chromium 151.0.7922.173 at 1100×800 CSS pixels. Host load and display scheduling were uncontrolled. No macOS/Safari/iOS or reporter-machine replication. Dependencies came only from the frozen lockfile. Both clean detached checkouts used the identical three fixture source files and measurement script, separate node_modules, caches, browser profiles, HTTP ports and debugger ports.

The fixture uses a deliberately isolated Vite production entry instead of the full app or development server. It adds no dependencies, API proxy or application runtime access. The production component itself is unchanged. Minimal CSS supplies its existing relative-position and full-width utility semantics. An initial attempt omitted those rules; screenshot inspection exposed the malformed layout. Those measurements were discarded, and only the corrected first and second runs below are reported.

Same-agent second clean reproduction

The same agent personally repeated the corrected optimized fixture in a second clean checkout at the identical SHA. Both frozen installs, both production fixture builds and both browser measurement commands exited 0. Each run measured 33 samples and produced a genuine screenshot. No independent verifier or investigation agent was used. The second run supports the same narrow negative finding; it does not justify a broader fixed claim.

import { useCallback, useRef, useState } from "react";
import { createRoot } from "react-dom/client";
import { TimelineWindowedItems } from "../src/components/thread/timeline/TimelineWindowedItems";

const rowCount = Number(new URLSearchParams(location.search).get("rows") ?? 1000);
const keys = Array.from({ length: rowCount }, (_, i) => `synthetic-row-${i}`);
function Thread({ name }: { name: string }) {
  const scroll = useRef<HTMLDivElement>(null);
  const measurements = useRef(new Map<string, number>());
  const getScrollElement = useCallback(() => scroll.current, []);
  return <div ref={scroll} style={{ height: 600, overflow: "auto", border: "1px solid #777" }}>
    <TimelineWindowedItems itemKeys={keys} measurements={measurements.current} getScrollElement={getScrollElement}
      estimateItemHeight={() => 48} gap={0}
      renderItem={(index, state) => <div key={keys[index]} ref={state.itemRef} data-index={state.itemIndex}
        data-timeline-window-key={keys[index]} data-timeline-windowed-realized={String(state.isRealized)}
        style={state.itemStyle}>{state.isRealized ? <div style={{ height: 48, boxSizing: "border-box", padding: 10, borderBottom: "1px solid #ddd" }}>
          {name} — synthetic message {index}: ordinary fixture text</div> : null}</div>} />
  </div>;
}
function App() {
  const [thread, setThread] = useState<string | null>(null);
  return <main style={{ font: "16px system-ui", margin: "20px auto", maxWidth: 900 }}>
    <h1>Isolated timeline remount fixture</h1><p>{rowCount} synthetic rows per thread. Optimized component bundle; not the full bb app.</p>
    <button id="a" onClick={() => setThread("Thread A")}>Open A</button>{" "}
    <button id="b" onClick={() => setThread("Thread B")}>Open B</button>
    <p id="selected">{thread ?? "No thread mounted"}</p>
    {thread ? <Thread key={thread} name={thread} /> : null}
  </main>;
}
createRoot(document.getElementById("root")!).render(<App />);
