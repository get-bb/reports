#7656 · Native plugin child startup exceeds the Windows test budget

BugPriority: LowEffort: LowpluginsGitHub issueNovember 17, 2026

Trusted base: d2fd33885bb3923f3627bb35fd618908008f692e (origin/main at investigation time).

Verdict: PARTIALLY REPRODUCED · Root-cause confidence: medium · Reproduction label: partial-repro

1. TL;DR

A real Windows CI failure is confirmed by separately retrieved GitHub Actions metadata and logs from a push to main. Its native Node child did not reach the first post-import marker until 13.929 seconds of child uptime, while the enclosing test had a 15-second wall-clock budget. The database and service markers followed within 36 milliseconds, leaving about a second at most for plugin reload and shutdown. The current main implementation retains that same budget and source-loader path. However, all three native-loading cases passed in each of two clean Linux checkouts, so this report does not claim a new local reproduction of the Windows flake or a proven explanation for why Windows startup was slow.

5. Root cause and limits

Supported mechanism: the enclosing integration test's fixed wall-clock deadline includes child process launch, the tsx loader, evaluation of a broad source dependency graph, database creation, plugin reload and shutdown. A slow pre-marker phase can consume nearly the entire budget before the behavior under test completes. This explains the recorded deadline failure without establishing an underlying tsx defect.

  • Server Vitest configuration, lines 6–10 sets testTimeout: 15_000.
  • Child script, lines 75–86 places its first marker after static imports of the plugin service, AI registry, telemetry and database utilities.
  • Child work, lines 118–134 performs reload and shutdown after service-ready.
  • Process invocation and assertions, lines 137–172 use --conditions=source --import tsx, await child exit and do not supply a per-test timeout override.
  • Windows job selection, lines 334–345 confirms the runner family and shard policy.

Representative trusted source:

The same two relevant files are byte-identical between the historical main failure commit and the current trusted base (git diff 7fd9272e95010b0de4a1851d27b6c3c85d047da6 origin/main -- apps/server/test/services/plugins/plugin-native-server-loading.test.ts apps/server/vitest.config.ts produced no output). That does not prove the entire import graph or host conditions are unchanged. An empty exit/signal code means the child was alive when diagnosed; it does not prove eventual completion. The pre-marker measurement cannot distinguish filesystem latency, cache misses, CPU contention, loader overhead or slow module evaluation.
