#6025 · Rejected extension events retain unbounded diagnostics

Bug Priority: Medium Effort: Low threads plugins · GitHub issue

2026-10-21 · trusted origin/main b143a22860944a96bf183605dfb0ffe58b1de283

Verdict: REPRODUCED · Root-cause confidence: high · reproduction label: confirmed-repro.

1. TL;DR

The server correctly rejects extension payloads larger than 65,536 UTF-8 bytes, but its replacement diagnostic retains the rejected JSON in full. An independently authored integration regression submitted synthetic events through the real ingest route and read their persisted SQLite rows. The item and state diagnostics occupied 160,308 and 160,296 bytes respectively for a 160,016-byte payload. The same defect also occurs when ownership or declaration checks reject the event before size validation, and on the core state path. Validator messages, kind strings, and identity fields can independently exceed a proposed diagnostic cap.

This report verifies ingestion and persistence, not historical production storage, desktop behavior, or latency. The 65,536-byte payload acceptance limit exists in current code; a matching diagnostic budget is a regression target, not an existing documented guarantee.

5. Root cause

  1. Validation limits payload bytes for known schemas. Ownership and declaration checks may return before that measurement.
  2. The shared rejection converter unconditionally copies the payload into rawEvent.params: 
    params: { kind: site.kind, payload: site.payload, reason },
    There is no retained-payload check and no serialized diagnostic budget.
  3. Every rejected site reaches that converter while accepted events pass through unchanged.
  4. Persistence strips only scope, type, and thread ID before JSON serialization. The fallback's copied payload and large metadata therefore enter the stored data.

The deeper constraint is that diagnostic provenance itself is currently unbounded: provider-thread and parent identifiers are unconstrained strings, and kind validation restricts syntax, not length. The validator also concatenates messages without a bound. JSON escaping matters: the metadata tests include NUL plus a four-byte character so a character-count truncation would not establish a serialized byte bound.

6. Proposed fix and simple-fix decision

The correct owner is the shared rejection converter: measure the original serialized payload on every rejection path; omit oversized content with explicit original-byte-count metadata; preserve small rejected payloads only when the whole diagnostic fits; and budget serialized reason/kind text with an explicit truncation marker. Leave successful validation and event ordering unchanged. Do not introduce historical cleanup, dependencies, or producer-side changes.

No production fix or PR was pushed. The full repair did not satisfy the autopilot's “no product or protocol decision” condition. A strict total diagnostic cap and exact preservation of arbitrary-length provenance cannot both hold with the current event representation. The clean reproductions show a 21-byte rejected payload whose identity fields alone exceed the proposed cap, even with a short validator reason. Blindly truncating those fields changes identity and parent association; rejecting them or moving canonical provenance out of the diagnostic changes a contract. Decide whether the budget excludes canonical provenance or how canonical identity is preserved before implementing an absolute cap. A payload-only omission would address the common retention mechanism but would not complete the total-bound requirement.
