#5676 · Configured ACP agents cannot declare or discover fork support

BugMedium priorityLow effortprovidersprovider-acpIssue #56762026-10-17

Verdict: REPRODUCED · Root-cause confidence: high · Label: confirmed-repro

Trusted base: 6a639cfc0d66e0c789a1bd7309266973228d1a80.

1. TL;DR

A configured ACP provider is registered without fork support, even if the underlying agent could fork sessions. Configuration always resets its fork capability to none, and the strict settings validator rejects an explicit fork value. The capability service does not probe configured agents at all, so a positive agent response cannot fix their declaration. The defect reproduces through the real plugin entry point in two clean source checkouts, for both a new custom provider and an override of the shipped OpenCode provider. No external agent or live user instance is needed to demonstrate these registration and validation failures.

Complete reproduction test

The transport fixture offers a positive fork response for every command BB chooses to probe. It does not replace provider registration, settings validation, reconciliation, or the capability service. No fixture command is executed.

import { readFileSync } from "node:fs";
import { expect, it, vi } from "vitest";
import { z } from "zod";
import { createFakePluginHost } from "@get-bb/plugin-sdk/testing";
import acpProvidersPlugin from "./server.js";

const manifest = z.object({
  bb: z.object({
    branding: z.object({
      experimental_icons: z.record(z.string(), z.string()),
    }),
  }),
}).parse(JSON.parse(readFileSync(new URL("./package.json", import.meta.url), "utf8")));

async function load() {
  const commands: string[] = [];
  const host = createFakePluginHost({
    pluginId: "provider-acp",
    experimental_declaredIconNames: Object.keys(manifest.bb.branding.experimental_icons),
    experimental_callHostRpc: ({ input }) => {
      commands.push(z.object({ command: z.string() }).parse(input).command);
      return { reachable: true, fork: true };
    },
  });
  host.harness.sdk.stub("hosts.list", async () => [{ id: "fixture-host", status: "connected" }]);
  host.harness.sdk.stub("providers.catalog", async () => []);
  await acpProvidersPlugin(host.bb);
  return { host, commands };
}

it.each(["fork-check", "opencode"])("registers fork support for a capable configured agent: %s", async (id) => {
  const { host, commands } = await load();
  const providerId = "acp-" + id;
  await host.harness.setSettings({
    customAgents: JSON.stringify([{ id, displayName: "Fork check", command: "fixture-acp" }]),
  });
  await vi.waitFor(() => expect(host.harness.registrations.providerRegistrations.find(
    (provider) => provider.id === providerId,
  )?.experimental_bridgeOptions?.acpLaunchSpec).toMatchObject({ command: "fixture-acp" }));
  const run = host.harness.runService("acp-capability-probe");
  try {
    await vi.waitFor(() => expect(commands.length).toBeGreaterThan(0));
  } finally {
    run.controller.abort();
    await run.done;
  }
  const declaration = host.harness.registrations.providerRegistrations.find(
    (provider) => provider.id === providerId,
  );
  console.log(JSON.stringify({ providerId, fork: declaration?.capabilities.fork, customProbeCalls: commands.filter((command) => command === "fixture-acp").length }));
  expect(declaration?.capabilities.fork).toBe("tip");
});

it("accepts an explicit fork declaration through the plugin settings boundary", async () => {
  const { host } = await load();
  await expect(host.harness.setSettings({
    customAgents: JSON.stringify([{ id: "fork-check", displayName: "Fork check", command: "fixture-acp", fork: "tip" }]),
  })).resolves.toBeUndefined();
});

5. Root cause

  1. The strict custom-agent schema has no fork field, so explicit values are invalid.
  2. The custom-agent builder writes fork: "none", including when replacing a shipped definition.
  3. The probe inventory starts from shipped fork-capable agents only. Configured IDs are skipped before the RPC is invoked. Merely changing the probe helper would therefore not fix this bug.
  4. Probe application is intentionally narrowing-only. Existing coverage protects this no-widening policy.
  5. Provider declaration passes the disabled fork through. Core registration computes supportsFork: capabilities.fork !== "none"; The core fork guard rejects the false capability.

Relevant builder excerpt:

visibility: "always",
fork: "none",
supportsManualCompaction: agent.supportsManualCompaction,

The shipped OpenCode definition is present at this base and declares fork: tip. The custom override discards that value rather than preserving it.

6. Proposed fix and autopilot safety gate

Prefer a deliberate opt-in custom-agent fork setting, validated against the existing capability vocabulary, defaulting to disabled and carried into the provider declaration. Preserve the current narrowing-only policy, and separately decide how configured agents should participate in capability validation. Update the discoverable configuration guidance and add a settings-to-registration regression for both valid opt-in and invalid values.

No automatic fix or PR: the direct repair changes the public customAgents configuration schema, expressly excluded by the simple-fix rule. Automatic inference is not a safe loophole: it changes a capability policy protected by existing tests and would also need to change the probe inventory and custom-agent exclusion. No production patch, branch, or push was made.
