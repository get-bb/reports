#6628 · Draft submission ownership outlives a composer

Bug High priority Medium effort ui · GitHub issue · October 30, 2026

Trusted base: a1bf55b6a04c7948ae5ae0dcfcbdec27d2b507a2 · Linux x64 · Node 22.19.0 · pnpm 9.15.0

Verdict: REPRODUCED · Root-cause confidence: high

1. TL;DR

A draft survives its composer being recreated, but the ownership of its pending send does not. Two composer callbacks can therefore consume the same draft scope before either send finishes. If the first failed send restores its draft after the second callback emptied the newer draft, the older text wins. A directly authored component regression reproduces duplicate mutation dispatches and replacement of newer text on trusted main, in two clean checkouts. This is a deterministic component-lifecycle reproduction, not a claim that a provider accepted two messages or that this run exercised the physical viewport breakpoint.

5. Root cause

Draft state is shared by a normalized storage key. Its cache and subscriptions live outside the component, and its accessor continues working after unmount. Submission state, however, is derived from the mounted mutation observer, mounted create-thread mutation, and local shortcut state.

  • Shared draft cache and subscribers and restore-if-empty and normalized scope keys.
  • View-local pending calculation.
  • Ordinary submission clears the captured draft before awaiting transport, then restores on failure.
  • Modifier draft submission follows the same clearing/restoration pattern.
  • Each send hook constructs a mutation observer, not an atomic shared draft owner.
promptDraft.clearIfCurrentMatches(submittedDraft);
await sendMessage.mutateAsync(request);
...
promptDraft.restoreIfEmpty(submittedDraft);

The second callback empties the newer draft. The older request's rejection now sees an empty shared draft and restores its older snapshot. Restore-if-empty is functioning as designed; the missing exclusion before clearing is the underlying defect. Observer state alone also cannot block two callbacks in one JavaScript turn before React updates.

6. Proposed fix

Give each normalized draft storage key a same-renderer submission owner with synchronous exclusion. Keep it alive while transport is pending even when every view unmounts. Publish pending state to mounted/remounted siblings and release in a finally block on success or failure. Guard both ordinary draft consumption and modifier draft consumption with the same owner, leaving the no-input queued-head shortcut unchanged. Keep separate draft scopes independent; do not add a wire, provider, SDK or persistence contract. Cross-window/reload exclusion remains outside this local fix.
