#6505 · Automation process-group cleanup skips ordinary completion

BugPriority: HighEffort: Lowplugins · automations · confirmed-reproIssue2026-10-29

Trusted base: 0950d00f962029433790f9fed432c7061051a32e (origin/main fetched from get-bb/bb).

Verdict: REPRODUCED · Root-cause confidence: high

1. TL;DR

A script automation can finish successfully or fail while a worker it started keeps running. The runner starts a POSIX process group but kills that group at completion only when a timeout or output limit occurred. A child whose standard streams do not hold the runner's pipes open allows the runner to finish and cancel its timeout without stopping the child. Two independently created clean checkouts of the same trusted main commit reproduced this with an authored Node worker test. This establishes the lifecycle leak, not the reported macOS machine-wide resource exhaustion.

5. Root cause

Group signaling, lines 178–190, sends signals to -child.pid on POSIX, so it can kill remaining members even after the original group leader exits. Windows falls back to the direct child.

Spawn and termination, lines 208–221:

    const child = spawn(args.command, [args.scriptPath], {
      cwd: args.cwd,
      detached: process.platform !== "win32",
      env: args.env,
      stdio: ["ignore", "pipe", "pipe"],
    });

    const terminateGroup = (): void => {
      signalProcessGroup(child, "SIGTERM");
      if (forceKill) return;
      forceKill = setTimeout(() => {
        signalProcessGroup(child, "SIGKILL");
      }, 1_000);
      forceKill.unref();

Completion and timeout, lines 242–261:

    child.once("close", (code) => {
      clearTimeout(timeout);
      if (forceKill) clearTimeout(forceKill);
      if (timedOut || outputLimitExceeded) {
        signalProcessGroup(child, "SIGKILL");
      }
      const suffix = outputLimitExceeded ? "\n[output truncated]\n" : "";
      const stderr = Buffer.concat(stderrChunks).toString("utf8");
      resolve({
        exitCode: timedOut ? null : outputLimitExceeded ? 1 : code,
        output: `${Buffer.concat(stdoutChunks).toString("utf8")}${stderr}${suffix}`,
        stderr,
        timedOut,
      });
    });
    timeout = setTimeout(() => {
      timedOut = true;
      terminateGroup();
    }, args.timeoutMs);
    timeout.unref();

With ignored worker stdio, the script's pipes close immediately after its own exit. Neither limit flag is set. The close handler clears the timeout, omits process-group termination and resolves the result. The worker is not part of the direct child's lifetime and remains runnable. The SDK spawn wrapper forwards the detached option and observes executable-discovery failures; it adds no group reaping (observer, spawn).

6. Proposed fix

Use the existing process-group kill at the close boundary regardless of the two limit flags. Preserve the existing timeout/output handling, original exit code, and Windows direct-child fallback. Document that completed runs clean up remaining processes in their group. This is local lifecycle cleanup, not a new sandbox or permission boundary: explicitly detached new sessions can escape the group, and this proposal does not claim Windows tree termination. Children that retain the script's output pipes still use the existing timeout path; immediate exit-event cleanup is a separate lifecycle improvement.

Keep the focused regression at the existing containment-test owner and run the complete automations test suite, lint and typecheck before proposing a ready PR.
