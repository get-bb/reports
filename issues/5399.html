#5399 · Read-state events leave observed caches stale

Bug · Priority: Medium · Effort: Low · Area: ui · 2026-10-12
Trusted origin/main: 406c009502ad0f961fc6ce9c75c1d262cb3e3e7c · GitHub issue

Verdict: REPRODUCED · Root-cause confidence: high · Reproduction label: confirmed-repro

1. Summary

A read-state notification reaches the client cache owner, but observed thread-list and sidebar queries keep their previous read timestamp. The handler invalidates these queries with refetch disabled and does not patch their rows. A real TanStack Query observer therefore continues receiving old data even though the next fetch would return the new timestamp. A focused regression fails twice on unchanged production code in separate clean clones. This reproduces the backing-cache defect, not a macOS desktop or cross-device screenshot journey.

5. Root cause

At the trusted base, the read-state rule runs markThreadDetailQueryStale and markThreadListQueriesStale. The latter invalidates sidebar, project, and global list queries with refetchType: "none". No read-state patch handler updates cached rows.

The sidebar bootstrap query uses an infinite stale-time policy, so an active observer does not refresh just because its cached value was marked invalid. The read-state calculation compares the cached read timestamp with the latest attention timestamp, making stale data directly relevant to the unread indicator.

The trusted thread writer persists lastReadAt and emits the change plus project metadata, but does not transmit the timestamp. Refreshing observed queries is therefore the smallest repair that needs no wire-format change. Existing tests explicitly preserved stale-only read notifications; one is replaced with the behavioral regression and the project-scoping expectation is updated.

6. Fix and safety assessment

Reuse the existing dirtyActiveThreadListQueries handler for read-state events and delete the now-unused stale-only list helper. This refreshes subscribed sidebar, list, and search queries, retains project scoping, and keeps archived lists stale without fetching them. Thread detail remains stale-only to avoid needless active-conversation refreshes.

The change stays in the app realtime-cache subsystem: 2 text files, 95 additions + 113 deletions = 208 changed lines. No dependency, lockfile, generated file, data migration, stored-data shape, public protocol, authentication, authorization, or release change.
