1. TL;DR

The server sends thread-opening and pane-action commands to every connected UI socket, including clients subscribed to other threads. This was reproduced through the real HTTP routes and real WebSocket connections, twice, using separate clean checkouts and freshly migrated SQLite databases. A focused isolation regression also fails for both routes in each checkout. The frontend source then hands every open signal to its navigation action without checking a recipient. Actual browser navigation and multiple authenticated human identities were not exercised: the approved browser backend could not start because Chrome/Chromium is unavailable. This limitation is why the verdict is partial rather than a claim of a complete browser reproduction.

5. Root cause

The open and pane HTTP handlers validate the target thread and then ask the hub to deliver a command. The recipient is not a route parameter or payload field. Registration tracks subscriptions and visibility but no per-person recipient key; the command path does not consult either subscription or visibility. The send loop walks every registered socket and increments delivered for each send, so the returned number measures sockets, not people or acknowledgements.

6. Proposed fix and simple-fix decision

No production fix or PR was attempted. Establish the supported recipient and multi-user semantics first: which person/client should receive an agent-initiated command, how that identity is bound to the request and socket, and what to do when it is missing. Then use one server-owned routing contract shared by CLI, SDK, and UI, with cross-recipient negative tests and explicit disconnected/background-client behavior.

Filtering solely by current thread subscription is not equivalent to routing to a person: it can discard an intentional external navigation request, and same-person tabs may view different threads. A client-only navigation guard also leaves unsolicited commands and file metadata globally delivered. Implementing genuine recipient binding crosses protocol and identity/policy boundaries and needs a product/architecture decision, so it fails the rule's simple-fix conditions even if a small symptom patch is possible.

The existing route tests explicitly exercise broadcast semantics. Changing them without settling the intended contract would silently redefine supported behavior. No new dependency, production edit, public protocol change, stored-data change, branch, or fix push was made.
