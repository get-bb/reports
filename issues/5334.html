#5334 · Desktop server destination duplication

BugPriority: LowEffort: Lowdesktop · partial-reproGitHub issueOctober 10, 2026 · base e9ad6b0e3473628f96fa98378cf8528aac8984d2

Verdict: PARTIALLY REPRODUCED. Root-cause confidence: high for duplicate list entries and their labels. Native macOS rendering and real-account discovery were not reproduced.

1. TL;DR

The desktop server chooser can represent one remote destination twice, once as an account target and once as a saved custom URL. Both clean source checkouts returned the extra row, using synthetic servers and the real on-disk target store. The list builder concatenates the two sources rather than merging destinations, always includes the built-in target, and uses different naming rules for the two remote target types. The broader claim that discovery cannot enumerate multiple servers without the built-in runtime is not supported by the current implementation: it queries the gate directly when a cached credential is available. A small local deduplication candidate passed list and related tests, but was not pushed because Connect and custom targets use different authentication paths; merging their selectable identities needs an explicit policy decision.

describe("desktop server choices", () => {
  it.each(["connect", "custom", "builtin"] as const)(
    "merges duplicate destinations while preserving the %s selection",
    async (selection) => {
      const store = await createStore();
      await store.setConnectServer(accountServer);
      await store.setCustomServerUrl(accountServer.url);
      await store.setTarget(selection);
      const customUrl = store.getCustomServerUrl();

5. Root cause

buildDesktopServerChoices unconditionally starts with the built-in row, appends account rows by handle, then appends every custom URL using a URL-derived hash. There is no common destination identity or cross-source comparison. Because the two representations have unrelated IDs, saving the account destination as a custom URL produces a second row. Account rows use server.name; custom rows use new URL(url).host.

import { createHash } from "node:crypto";
import type { BbDesktopServerChoice } from "@bb/desktop-contract";
import {
  BUILTIN_SERVER_NAME,
  type ConnectServerRef,
  type ServerTargetStore,
} from "./server-target.js";

export function customServerId(url: string): string {
  return `custom:${createHash("sha256").update(url).digest("hex")}`;
}

export function buildDesktopServerChoices(
  store: ServerTargetStore | null,
  connectServers: readonly ConnectServerRef[],
): BbDesktopServerChoice[] {
  const target = store?.getTarget() ?? { kind: "builtin" };
  return [
    {
      id: "builtin",
      name: BUILTIN_SERVER_NAME,
      active: target.kind === "builtin",
    },
    ...connectServers.map((server) => ({
      id: `connect:${server.handle}`,
      name: server.name,
      active:
        target.kind === "connect" && target.server.handle === server.handle,
    })),
    ...(store?.getCustomServerUrls() ?? []).map((url) => ({
      id: customServerId(url),
      name: new URL(url).host,
      active: target.kind === "custom" && target.url === url,
    })),
  ];
}

Menu and app list assembly also appends the remembered account target if discovery did not return its handle. Local target naming explains the platform-specific built-in label. Existing custom URL normalization provides an existing canonical comparison function without collapsing different protocols, ports, paths or queries.

Discovery correction: fetchServers uses the local plugin RPC when a local runtime URL exists, otherwise enumerates account servers directly with the cached credential. selectTargetableConnectServers excludes only the credential's self handle, not all offline servers. The absence of other servers in a particular user's desktop therefore needs credential/sync-state evidence, not the blanket explanation tested here.

Safety constraint: Selection dispatch treats connect: and custom: as different target modes. Target activation authenticates Connect targets and starts session renewal, while custom targets load the destination directly. URL equality alone does not prove these selectable modes are interchangeable.

6. Proposed fix and simple-fix gate

First decide which target mode should represent a destination when both account and custom routes exist. Preserve the active mode, define inactive-mode selection behavior, and verify the intended authentication and renewal behavior before removing any alternative route. Separately decide whether built-in visibility should depend on active/running/previously-used state, and whether names should prefer handles or account display names. The current list/store contract does not encode usage or local runtime availability.

A stopped local candidate uses the existing URL normalizer, removes custom rows matching an account destination, preserves the active custom ID, and retains current account names and built-in visibility. Its 107-line diff spans two existing desktop files (100 additions, seven deletions), adds no dependency, generated module, lockfile, migration or stored-data change, and passes git diff --check. It is provided as investigation evidence, not as an approved fix.
