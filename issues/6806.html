#6806 · Execution validation reuses a cached discovery timeout

Bug Priority: Medium Effort: Medium providers · workflows

2026-11-02 · GitHub issue · trusted base 916d684ac23d0b0de82c09cfc7553a50287d2188

Verdict: REPRODUCED · Root-cause confidence: high · Reproduction label: confirmed-repro.

1. TL;DR

Workflow execution checks a model using an SDK lookup intended for a responsive model picker. A previous provider discovery timeout can therefore reject that check even after the host can list models again. An isolated test through the real SDK, HTTP route, model-catalog store, and migrated SQLite database reproduces this at both one and thirty-one seconds after the timeout. The server's validation-mode resolver succeeds immediately against the same recovered host fixture. Both cases repeat in a second clean checkout; historical macOS load and the original four failures were not recreated.

import { describe, expect, it } from "vitest";
import { resolveSystemExecutionOptionsForValidation } from "../../src/services/system/execution-options.js";
import { registerHostRpcResponder } from "../helpers/host-rpc.js";
import {
  catalogAnswer,
  errorAnswer,
  healthAnswer,
  installCatalogStore,
  modelList,
} from "../helpers/provider-model-catalogs.js";
import {
  seedEnvironment,
  seedHostSession,
  seedProjectWithSource,
} from "../helpers/seed.js";
import { withTestHarness } from "../helpers/test-app.js";

describe("issue 6806 recovered provider discovery", () => {
  it.each([1_000, 31_000])(
    "refreshes a failed SDK model lookup after recovery at age %i ms",
    async (failureAge) => {
      await withTestHarness(async (harness) => {
        const clock = { now: 1_800_000_000_000 };
        installCatalogStore(harness, { clock });
        const { host, session } = seedHostSession(harness.deps, {
          id: "host-issue-6806",
        });
        const { project } = seedProjectWithSource(harness.deps, {
          hostId: host.id,
          path: "/tmp/issue-6806-fixture",
        });
        const environment = seedEnvironment(harness.deps, {
          hostId: host.id,
          projectId: project.id,
          path: "/tmp/issue-6806-fixture",
        });
        let recovered = false;
        let modelRequests = 0;
        registerHostRpcResponder(harness, {
          hostId: host.id,
          sessionId: session.id,
          handle: (request) => {
            if (request.command.type === "provider.health") {
              return healthAnswer("ready");
            }
            if (request.command.type === "provider.list_models") {
              modelRequests += 1;
              return recovered
                ? catalogAnswer(modelList("recovered-model"))
                : errorAnswer("command_timeout");
            }
            throw new Error(`Unexpected RPC ${request.command.type}`);
          },
        });
        const sdk = createNodeBbSdk({
          baseUrl: "http://localhost",
          fetch: async (input, init) =>
            harness.app.request(new Request(input, init)),
        });
        const query = {
          environmentId: environment.id,
          providerId: "claude-code",
        };
        const initial = await sdk.providers.models(query);
        expect(initial.modelLoadError?.code).toBe("timeout");
        expect(modelRequests).toBe(1);

        recovered = true;
        clock.now += failureAge;
        const retried = await sdk.providers.models(query);
        const requestsAfterRetry = modelRequests;
        const validated = await resolveSystemExecutionOptionsForValidation(
          harness.deps,
          query,
          null,
        );
        expect(validated.modelLoadError).toBeNull();
        expect(validated.models.map((model) => model.model)).toContain(
          "recovered-model",
        );
        console.info(
          JSON.stringify({
            failureAge,
            initialError: initial.modelLoadError?.code,
            retryError: retried.modelLoadError?.code,
            requestsAfterRetry,
            validationError: validated.modelLoadError,
            totalModelRequests: modelRequests,
          }),
        );
        expect(retried.modelLoadError).toBeNull();
      });
    },
  );
});

5. Root cause

  1. Workflow validateSelection calls bb.sdk.providers.models, then throws whenever the response contains a model-load error. The exact source error template is Could not load models for provider ${requested.provider}: ${catalog.modelLoadError.code}.
  2. SDK providers.models uses readExecutionOptions, which sends a request to system/execution-options. The server route uses the picker resolver, not the validation resolver.
  3. The two server resolvers select different access semantics. Picker access returns promptly; validation access waits when no usable catalog exists.
  4. Catalog evaluate first handles a usable catalog or a completed refresh. With neither, validation waits. Picker access serves an active cached failure; after expiry, a timeout is still served while a refresh runs in the background. Thus waiting thirty seconds does not make that very lookup authoritative.
  5. Workflow agent identity calculation invokes selection validation. runAgentCall awaits that identity before accessing the stored call. A cached discovery failure therefore aborts this stage, rather than reaching a host that could now execute the agent.

This is an access-intent mismatch across the SDK boundary, not proof that the picker cache is broken. No cause for the original host timeout or environment-fingerprint churn was established. The introducing commit remains unknown.

6. Proposed fix and simple-fix safety

Expose explicit execution-validation intent through the existing SDK/server model lookup path, and use it for workflow selection. Reuse the catalog store's current validation semantics so a fresh provider failure still propagates, concurrent refreshes coalesce, and picker latency stays unchanged. Add coverage for recovered timeout, persistent fresh failure, cancellation, and ordinary picker responsiveness.

No automated pull request. The current SDK argument contract and public execution-options query have no validation-intent field. Correctly carrying that intent requires a public API/schema change across SDK, server contract, server route, and workflow caller. That exceeds this rule's one-subsystem/no-public-schema-change gate. A delayed polling workaround instead introduces an unsupported retry policy and still consumes picker responses; it is not the smallest demonstrated root-cause repair. No production patch was made or pushed.
