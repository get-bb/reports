#3281 · Resolved provider identities remain queued as fallbacks

Bug Medium Effort: Medium threads provider-codex open on GitHub 2026-09-08 · base 06047280e

Verdict: PARTIALLY REPRODUCED · Root-cause confidence: medium

1. TL;DR

Two clean checkouts reproduced an identity-registry defect that can pair one provider session with a checkpoint from another session. A thread registered as awaiting an identity remains in the fallback queue even after bb records its explicit provider identity. A later unmatched identity can therefore overwrite that resolved mapping, and event stamping preserves the checkpoint while substituting the wrong provider session. The reported edit failure and the exact live notification sequence were not reproduced, so the incident-level verdict remains partial rather than full.

6. Root cause

The identity registry at lines 63–94 appends a bb thread ID when an identity notification is expected. recordProviderThreadIdentity() later stores the resolved mapping but does not remove that thread ID from pendingIdentityThreadIds. By contrast, lines 170–187 show that pending entries are removed only by consuming the queue or forgetting the thread.

The runtime translation path at lines 1182–1207 consumes the oldest pending entry when a thread/identity event names no registered bb thread. It then records that event's provider identity against the dequeued bb thread without checking whether the thread already has a mapping. A stale entry can therefore overwrite a valid session association.

Runtime lines 1229–1234 read the registry mapping when stamping every translated event. The stamping helper at lines 191–205 spreads the provider event and replaces only its thread and provider-thread IDs. A checkpoint already carried by the event remains unchanged, producing the mismatched pair reproduced by the test.

Finally, the edit target resolver at lines 245–291 reads the session and checkpoint from the same preceding completion, and lines 459–488 forward both values into rewind preparation. This explains how a corrupted stored pair would reach a provider. The missing evidence is which real notification caused the fallback overwrite in the reported incident, so incident-level root-cause confidence is medium.

7. Proposed fix (first principles)

When recordProviderThreadIdentity() records an explicit mapping, remove every pending entry for that bb thread before returning. Keep the fallback limited to threads that still lack a provider mapping, and add the focused regression above. Run the complete @bb/agent-runtime test suite afterward, especially multi-thread and Codex topology coverage. A live follow-up should capture identity notification ordering across a source thread and side-chat fork before treating this as the confirmed cause of the reported UI failure.
