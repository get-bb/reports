#7895 · Blocking Claude SDK notices disappear from normal history

BugMedium priorityLow effortproviders · provider-claude-codeIssue2026-11-20

Verdict: REPRODUCED at the provider translation boundary. Root-cause confidence: high. Trusted base: 351cb84dc6391d3c6d16295e66578fe97232a25e.

1. TL;DR

A Claude SDK message that says execution cannot continue is converted to a diagnostic event instead of a visible error. A subsequent successful SDK result then marks the turn completed, even though the notice explains why execution stopped. Normal history excludes that diagnostic event, leaving no ordinary error or response for the user. The same provider-boundary regression fails in two clean checkouts of trusted main. This report verifies the translation failure without using a real account, running a hook, or accessing an existing bb instance.

5. Root cause

  1. The system-subtype mapper does not recognize informational messages; unknown system subtypes have unknown coverage.
  2. The system translator has no blocking-informational branch. After other parsers decline the event, it returns no deltas. The SDK-envelope fallback then produces an unhandled diagnostic.
  3. The result failure predicate considers only the result's error marker/subtype. The terminal result path has no remembered execution-stop state, so a success result completes successfully. Successful result text is not independently emitted as assistant output.
  4. The diagnostic-event SQL predicate excludes this ordinary unhandled message, and diagnostics default off. Thus no ordinary timeline event communicates the block.

The SDK declaration installed by the frozen lockfile describes informational messages as plaintext banners, including hook block feedback, and explicitly says prevent_continuation: true means execution stops. This supports using that existing signal rather than parsing natural-language content or treating every informational message as an error.

6. Proposed fix

Within the Claude provider, validate informational messages that have string content and prevent_continuation: true. Emit the existing visible provider-error event immediately, remember the block for the current turn, and use that state when processing the terminal result. Keep result token accounting intact, avoid duplicating the error on the success result, and reset the block state for the next turn. Preserve diagnostics for nonblocking or malformed informational messages rather than silently discarding them.

A local implementation of this approach makes the inline reproducer exit 0, producing:

[{"type":"provider/error"}]
[{"type":"turn/completed","status":"failed"}]
