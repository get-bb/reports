#5260 · OS-managed TLS roots omitted from hosted account requests

BugMedium priorityMedium effortdesktop · host · connect · partial-reproopen on GitHub

October 9, 2026 · trusted main 60eed057d07406bf273dc1fb60de38d54bc9f592

Verdict: PARTIALLY REPRODUCED · Root-cause confidence: high for the verified transport mechanism; macOS desktop behavior remains unverified.

1. TL;DR

Account sign-in uses Node's HTTPS transport, whose default trusted roots exclude an additional root that its system-root API can already read. A local HTTPS fixture signed by that root fails both a real fetch and the repository's actual account-link request function. The account wrapper turns the certificate failure into the generic network error used by the sign-in UI. Starting a fresh process with Node's system-root opt-in makes the identical request succeed without changing the application or disabling certificate validation. This was repeated by the same investigator in a second clean checkout; it was not a macOS, Electron, or corporate-proxy test.

5. Root cause

The affected trust decision is made by Node's TLS transport, before the application receives an HTTP response. In this controlled environment, the root is readable as a system certificate but absent from Node's defaults. The positive control changes only the process's trust selection; it keeps the certificate, server, URL, request, and production account code unchanged.

Desktop apps/desktop/src/bb-process.ts:217 preserves the parent environment and sets ELECTRON_RUN_AS_NODE for the packaged runtime without supplying a system-root default. Server apps/server/src/index.ts:1 and daemon apps/host-daemon/src/index.ts:77 install diagnostics and the socket guard but contain no system-root initialization.

The real sign-in path reaches startLink from plugins/bb-account/src/login.ts:100, which issues its request through plugins/bb-account/src/hosted.ts:204. The catch block at plugins/bb-account/src/hosted.ts:118 creates HostedRequestError with null status. Its getter at plugins/bb-account/src/hosted.ts:12 maps null to network, discarding the structured TLS cause while retaining a textual diagnostic. The Connect UI at plugins/connect/app.tsx:525 falls back to a generic connection suggestion.

Related but separately untested: the npm child environment at plugins/browser-automation/installer.ts:139 is an allowlist. An inherited system-root opt-in is absent from it. This cannot be repaired merely by changing the parent's default TLS state, because child processes choose their own trust settings.

6. Proposed fix and autopilot safety decision

Evaluate an explicit product policy for adding locally administered OS roots to Node's bundled roots before network clients are created, consistently across supported launch paths and runtime versions. Preserve certificate validation and deliberate user settings; test rejected chains, valid OS-managed roots, runtime capability differences, and child-process trust propagation. Define whether CA rotation requires process restart rather than assuming cached roots refresh automatically. Separately consider retaining a typed certificate-failure diagnostic through the account error boundary.

No automatic code fix or pull request: widening the accepted TLS root set changes a security trust boundary, expressly excluded by the simple-fix rule. Consistent coverage also crosses desktop, server, daemon, and installer subsystems. No production edit, fix branch, new dependency, commit, or push was made to the application repository.
