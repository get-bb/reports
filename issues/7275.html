#7275 · Non-ASCII capitalization changes path search matching

Bug Priority: Medium Effort: Low ui · GitHub issue · November 9, 2026

Trusted base: 55135d1e5045d6c5d3c24f5a4d5556ed3e11cb00 on origin/main.

Verdict: REPRODUCED · Root-cause confidence: high · Reproduction label: confirmed-repro

1. TL;DR

The workspace path matcher returns a lowercase Cyrillic filename for a lowercase query, but drops it when the same query is capitalized. The shared fuzzy matcher treats any Unicode uppercase character as a request for case-sensitive matching. The composer passes the query to that matcher without undoing this behavior, so changing capitalization can remove the desired mention candidate. A tiny in-memory path list reproduces the result without a vault, an index, a running server, or macOS. The same agent repeated the reproduction from a second clean checkout at the same trusted commit.

5. Root cause

The composer’s mention hook hands the text to path suggestions. The project path query forwards it through the SDK. The server route forwards it to host.list_paths, and the daemon’s path finalization calls the shared matcher.

In plain query matching, Fzf is configured with casing: "smart-case". The installed fzf dependency implements that option by comparing the query to its Unicode lowercase form; the following excerpt was inspected in its installed distribution:

case "smart-case":
  if (query.toLowerCase() !== query) {
    caseSensitive = true;
  }
  break;

Therefore a capitalized Cyrillic query is case-sensitive even against a lowercase filename. This is not isolated to one instantiation: structured segment matching and exact directory-prefix matching use smart-case too. Comparable-value normalization also preserves the original case whenever any uppercase character occurs. Changing only the plain Fzf option would leave directory and ranking behavior inconsistent.

The candidate prefilter is conservative for non-ASCII inputs and does not cause this failure. The package manifest declares fzf as an external dependency, not a vendored implementation.

6. Proposed fix and tested candidate

Normalize query case once at the fuzzyMatchPaths boundary when the query contains no ASCII uppercase letter. This gives all path-matching and relevance-ranking branches the same lowercase query for the reported non-ASCII case, while retaining existing ASCII smart-case opt-in. Original paths and highlight positions are not rewritten. A query containing ASCII uppercase continues to request case-sensitive matching, including mixed-script queries; this deliberately avoids changing that existing behavior.

The candidate changes only the shared matcher and its existing test file: 42 changed text lines (41 additions + 1 deletion), 2 files. It adds no dependency, generated output, data change, public contract, or protocol field. Three parameterized regression cases exercise plain and structured Cyrillic queries and Greek capitalization; a fourth test preserves the ASCII smart-case control.
