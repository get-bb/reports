#7345 · Scoped Git plugin checks use repository commits

BugPriority: MediumEffort: Mediumplugins GitHub issueNovember 10, 2026 · base 7c1353d80729983b86ea1555d18b42407f320406

Verdict: REPRODUCED · Root-cause confidence: high · reproduction label: confirmed-repro

1. TL;DR

A plugin installed from one directory of a Git collection is offered an update when a sibling directory changes. The update resolver compares repository commit IDs, not the installed plugin's directory tree. The server then temporarily clones and validates that unrelated candidate and persists its commit as an available update. Two clean checkouts of trusted main reproduced both the false result and the extra materialization. No permanent candidate artifact is created by this check: the temporary staging directory is removed.

Regression test (complete added block)

  it("ignores unrelated commits for a branch-tracking subdirectory plugin", async () => {
    const pluginDir = join(repo, "plugins", "updater");
    await mkdir(pluginDir, { recursive: true });
    await rename(join(repo, "package.json"), join(pluginDir, "package.json"));
    await rename(join(repo, "server.ts"), join(pluginDir, "server.ts"));
    await git(repo, ["add", "-A"]);
    await git(repo, ["commit", "-qm", "Move fixture into collection"]);
    const installedCommit = await git(repo, ["rev-parse", "HEAD"]);
    await service.install(`git:${repo}@main`, {
      kind: "subdirectory",
      path: "plugins/updater",
    });
    const installedMaterializations = materializationCount;
    const installedArtifacts = listPluginArtifacts(db, "updater").length;

    await mkdir(join(repo, "plugins", "sibling"));
    await writeFile(join(repo, "plugins", "sibling", "notes.txt"), "changed");
    await git(repo, ["add", "-A"]);
    await git(repo, ["commit", "-qm", "Change sibling fixture"]);

    expect.soft(await service.checkForUpdates("updater")).toMatchObject([
      {
        id: "updater",
        outcome: "current",
        installed: { version: installedCommit },
      },
    ]);
    expect.soft(materializationCount).toBe(installedMaterializations);
    expect(listPluginArtifacts(db, "updater")).toHaveLength(installedArtifacts);
    expect(getInstalledPlugin(db, "updater")).toMatchObject({
      gitResolvedCommit: installedCommit,
      availableCompatibleVersion: null,
    });

    await writeFile(
      join(pluginDir, "server.ts"),
      'export default function plugin() { return "changed"; }',
    );
    await git(repo, ["add", "-A"]);
    await git(repo, ["commit", "-qm", "Change plugin fixture"]);
    const nextCommit = await git(repo, ["rev-parse", "HEAD"]);
    expect(await service.checkForUpdates("updater")).toMatchObject([
      {
        id: "updater",
        outcome: "update-available",
        candidate: { version: nextCommit },
      },
    ]);
    expect(materializationCount).toBeGreaterThan(installedMaterializations);
  });

5. Root cause

resolveGitUpdate, lines 885–934 constructs a candidate from the branch head and uses repository commit equality as its sole currentness check:

if (resolved.commit === args.currentCommit) {
  return { outcome: "current", current };
}
return { outcome: "update-available", current, candidate };

resolveUpdateForRow, lines 509–522 does not provide the subdirectory to that resolver and stages every non-range candidate:

if (remote.outcome !== "update-available") return remote;
if (intent.selector.kind === "range") return remote;
const staged = await stageGitCandidate({
  row: args.row,
  commit: remote.candidate.version,
  promote: false,
});

The candidate materializer, lines 1206–1230 invokes the materialization hook and clones the candidate repository before resolving its plugin root. It validates the manifest, not tree equality. A successful clone therefore makes an unrelated branch commit look like a legitimate update. The stage is removed in finally; this is unnecessary work and false update state, not a durable staged installation.

6. Proposed fix and validation

For non-range branch updates with a plugin subdirectory, fetch the installed and candidate commit trees into an ephemeral bare repository and compare that subdirectory's tree IDs before candidate materialization. Equal IDs mean current. Different IDs continue normal validation. If commits or trees cannot be inspected, retain the existing validation path rather than suppressing updates. Keep pinned references, range selection, and repository-root installs unchanged.

The contained patch uses a shallow blob-filtered fetch and deletes its temporary repository in a finally block; it introduces no persistent mirror, dependency, migration, or protocol. The added owner-boundary regression fails before the production change and passes afterward. It also verifies that actual changes within the plugin directory are still reported. A separate test removes the installed commit from a replacement remote history and verifies that comparison failure still permits an update.
