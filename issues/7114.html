1. TL;DR

A clean topic worktree can show upstream-only changes in its committed branch comparison when its short base name resolves to an older local branch. A real-Git test at the Git plugin's workspace-read boundary reproduces two files for the short base and one for the explicit remote base. The resolver returns the first valid local revision; it never compares that revision with the available tracking revision. This is not a dirty-working-tree problem or an absent remote ref. Importantly, local-first resolution is currently an explicit documented and tested policy, so changing the default is not safe for the simple-fix autopilot without a product-policy decision.

Complete reproduction test
import fs from "node:fs/promises";
import { tmpdir } from "node:os";
import path from "node:path";
import { expect, it } from "vitest";
import { initRepo } from "@bb/test-helpers";
import { runGit } from "bb-environment-provider-host/workspace-git";
import { WorkspaceReads } from "./workspace-reads.js";

it("excludes upstream-only commits when a short base has a newer tracking ref", async ({
  onTestFinished,
}) => {
  const directory = await fs.mkdtemp(path.join(tmpdir(), "bb-base-repro-"));
  onTestFinished(() => fs.rm(directory, { recursive: true, force: true }));
  const repository = path.join(directory, "repository");
  const worktree = path.join(directory, "topic");
  await fs.mkdir(repository);
  await initRepo(repository);
  await runGit(["checkout", "-b", "upstream"], { cwd: repository });
  await fs.writeFile(path.join(repository, "upstream-only.txt"), "upstream\n");
  await runGit(["add", "."], { cwd: repository });
  await runGit(["commit", "-m", "Advance upstream"], { cwd: repository });
  await runGit(["update-ref", "refs/remotes/origin/main", "HEAD"], {
    cwd: repository,
  });
  await runGit(["checkout", "main"], { cwd: repository });
  await runGit(["worktree", "add", "-b", "topic", worktree, "origin/main"], {
    cwd: repository,
  });
  await fs.writeFile(path.join(worktree, "topic-only.txt"), "topic\n");
  await runGit(["add", "."], { cwd: worktree });
  await runGit(["commit", "-m", "Add topic work"], { cwd: worktree });
  const workspace = new WorkspaceReads(worktree, directory);
  const clean = await runGit(["status", "--porcelain"], { cwd: worktree });
  const [shortBase, remoteBase, explicitLocal] = await Promise.all(
    ["main", "origin/main", "refs/heads/main"].map(async (mergeBaseBranch) => {
      const result = await workspace.diffFiles({
        freshness: { work: mergeBaseBranch, refs: mergeBaseBranch },
        target: { type: "branch_committed", mergeBaseBranch },
        maxFiles: 100,
        ignoreWhitespace: false,
      });
      return result.files.map((file) => file.path).sort();
    }),
  );
  console.log(JSON.stringify({ clean: clean.stdout.trim(), shortBase, remoteBase, explicitLocal }));
  expect(clean.stdout.trim()).toBe("");
  expect(remoteBase).toEqual(["topic-only.txt"]);
  expect(explicitLocal).toEqual(["topic-only.txt", "upstream-only.txt"]);
  expect(shortBase).toEqual(["topic-only.txt"]);
});

5. Root cause

resolveMergeBaseBranch builds short-name candidates in local-first order and returns immediately on the first valid commit:

  const candidates =
    ref.startsWith("refs/") || ref.startsWith("origin/")
      ? [ref]
      : [ref, `refs/remotes/origin/${ref}`];
  for (const candidate of candidates) {
    const result = await runGit(
      ["rev-parse", "--verify", "--end-of-options", `${candidate}^{commit}`],
      {
        cwd,
        ...options,
        priority: options.priority ?? gitPriority(),
        allowFailure: true,
      },
    );
    if (result.exitCode === 0 && trimOutput(result.stdout)) {
      return trimOutput(result.stdout);
    }

When the old local main resolves, the newer origin/main is never considered. readMergeBaseRef then computes the common ancestor of that old base and HEAD. resolveTrackedDiffRange uses that ancestor through HEAD for branch_committed, so the upstream commit is necessarily included. WorkspaceReads merge-base resolution shares this resolver; status also calls the same ref selector. The controls hold workspace contents constant and change only the base selector, isolating ref precedence from freshness caching or uncommitted state.

Underlying contract conflict

The shipped Git skill explicitly documents requested-ref-first resolution. Existing coverage expects a newer local main to win over an older remote tracking ref. Trusted commit 01162cbdf079b708a75563ed202c61af48840fbe explicitly says it preserves local-ref precedence. Thus the reported surprise is real, but unconditional remote-first ordering changes an intentional caller contract beyond the stale-local case.

6. Proposed fix and simple-fix check

First settle whether short names should always mean the remote tracking branch, prefer only a strictly newer tracking descendant, or retain Git's local-name semantics while the Diff tab supplies an explicit remote default. Preserve explicit local refs and local-only repositories either way. Then add coverage for stale local, newer local, divergent refs, remote-only, local-only, and explicit refs before applying the chosen policy consistently to status and diff reads and updating the skill.

No autopilot PR: the no-product-decision condition fails because the current default is explicitly documented, tested, and intentional in trusted history. No production patch, branch, dependency, protocol, schema, stored-data change, commit, or push to get-bb/bb was made. An explicit origin/<branch> selector remains a verified workaround. The focused regression fails on unchanged production code and is retained here as evidence.
