#6786 · Compaction admission chooses a thread-wide event index

BugHigh Effort: Lowthreads · perf · confirmed-repro GitHub issueNovember 1, 2026

Trusted base: 916d684ac23d0b0de82c09cfc7553a50287d2188 · Verdict: REPRODUCED · Root-cause confidence: high

1. TL;DR

Sending into an already-running thread checks whether a provider compaction is active before admitting input. The database predicate is logically restricted to one turn, but SQLite selects an index that is restricted only to the thread. When the current turn contains no compaction, this synchronous lookup must inspect the thread's entire retained event history before returning false. Two clean checkouts of trusted main reproduce the same plan and growing warm-memory lookup time: about 0.02 ms with no history, 4.2 ms with 20,000 old events, and 34 ms with 100,000 old events. Forcing the existing turn index makes the same missing-compaction query stay near 0.02–0.03 ms in these fixtures, without changing its answer. The reported multi-second production stalls were not recreated or independently measured; this report confirms the underlying unbounded lookup, not those particular wall times.

5. Root cause

isStoredTurnProviderCompactionRunning executes this synchronous query before deciding whether a compaction is running:

select "type" from "events" where (("events"."thread_id" = ? and "events"."turn_id" = ?) and "events"."type" in (?, ?) and "events"."item_kind" = ? and "events"."parent_tool_call_id" is null) order by "events"."sequence" desc limit ?

The unique (thread_id, sequence) index satisfies the ordering, but cannot seek by turn. With no matching compaction in the current turn, SQLite walks all rows for that thread and consults their table records to reject them. The existing (thread_id, turn_id, type, item_id, sequence) index can narrow to the current turn and lifecycle types, at the cost of a temporary ORDER BY sort.

Trusted server evidence: isManualCompactionActive calls the predicate for the active stored turn; non-start dispatch admission calls that helper before proceeding. The same helper appears in queued message admission and child report admission, including a transaction-backed read.

Because better-sqlite3's .get() finishes synchronously, time spent scanning also occupies the server's JavaScript thread. This explains the direction of the reported responsiveness impact, although this reproduction does not measure an HTTP request or event-loop stall.

The later accepted-input probe cannot prevent the first query's scan. Reordering alone would also leave provider-started turns without accepted input exposed. Separately, getStoredTurnRequestEventForTurn has its own ORDER BY accepted-input lookup; its performance was not reproduced in this report.

6. Proposed fix

Make the compaction lifecycle lookup deterministically turn-bounded, using the already-migrated turn index or an equivalently selective query shape. Preserve the lifecycle ordering, top-level-only compaction condition and accepted-input behavior. Keep a regression at the DB query-plan owner boundary; it must catch a thread-only seek without relying on wall-clock thresholds.

Tradeoffs: forcing an index binds the query to its name, so dropping or renaming it must update this query. This index does not satisfy the complete ordering and therefore sorts the current turn's candidate rows. Large current turns and started/completed/nested/accepted-input semantics still need normal CI coverage.
