#7040 · Approval authority after steering

BugHighEffort: Mediumproviders · security · provider-codexGitHub issue

November 4, 2026 · trusted main 783a6062bd6f485597e66450a149069402780868

Verdict: PARTIALLY REPRODUCED · Root-cause confidence: high for the verified routing mechanism; the installed historical events and live Codex behavior remain unverified.

1. TL;DR

An incoming message can carry a different permission-escalation setting even when the visible permission mode remains accept-edits. The current runtime installs those options while steering, and a later approval request is denied without reaching the interaction callback when escalation is deny. A boundary-level reproduction demonstrates that suppression twice, using a scripted provider that emits an approval after the steer is accepted. However, the current Codex bridge interrupts and replaces the native turn when permission settings change: the tested native policies are on-request, then never, not a persistently stale on-request policy. Therefore the historical policy mismatch is not reproduced on current main; the remaining informational-input authority question needs a product/security decision, not an automatic permission relaxation.

Expected versus actual

Hypothesis being tested: if the incoming deny-valued input is informational, a human-authorized active turn should retain visible approval routing. That proposed invariant expects one callback in both runtime cases. The runtime API has no informational-versus-revocation signal here; an explicit revocation is indistinguishable at this boundary. The failing assertion alone therefore does not establish that preserving ask would be safe.

Actual output, identically observed in A and B (Turbo prefixes and timing omitted):

{"permissionEscalation":"ask","acceptedSteer":true,"interactionCallbacks":1,"denied":false}
{"permissionEscalation":"deny","acceptedSteer":true,"interactionCallbacks":0,"denied":true}
AssertionError: expected [] to have a length of 1 but got +0
Tests  1 failed | 1 passed (2)

{"nativePolicies":["on-request","never"],"interrupts":1,"nativeSteers":0}
Tests  1 passed (1)

The deny case also waits for the scripted agent message Denied before asserting the callback count, so this is not merely a timing race or a missing provider response. The ask control establishes that the callback and test provider are working.

5. Root cause

  1. Server initiator policy maps any non-user initiator to deny. The send path resolves that policy, and the submit payload carries it onward.
  2. steerTurn records the incoming options before waiting for the provider command to complete. recordThreadExecutionOptions replaces the thread configuration options; it does not preserve a separate initiator-authorized active-turn snapshot. This happens even before successful acknowledgement, a source observation not separately fault-injected here.
  3. Interactive routing reads the current thread configuration options. The runtime gate returns an encoded denial if a runtime-enforced approval policy denies escalation, or if the callback is absent. The gate predicate is exactly permissionEscalation === "deny".
  4. Host interaction registration lives in onInteractiveRequest. The early-denial branch does not call it and has no denial-provenance logging call of its own.
  5. Codex declares runtime-enforced approvals. But its current steer handler compares native settings, interrupts and waits for settlement, then starts a replacement native turn when those settings differ. User-reviewed escalation mapping maps deny to never. Thus the normal successful ask-to-deny transition now synchronizes native policy instead of silently leaving it on-request.

Historical scope: trusted main history attributes the native permission-changing steer repair to cd12e7a9dfb372432cd748eafcd73d142e15c16f (October 2, 2026; #4794). GitHub release metadata identifies desktop-v0.48.1 as published October 30, 2026 at e003e9510cbfd3bb6c26a28630b46ffb1c242a44, and GitHub compare confirms that fix commit is an ancestor. That establishes source inclusion, not an executed verification of an installed release or a remedy for informational-input authority.

6. Proposed fix and safety disposition

No production fix or pull request is attempted. Automatically retaining ask for every steer could weaken explicit revocations or non-user-started turns; the existing API does not express the distinction. A maintainer must first define an authorized, server-owned transition contract distinguishing informational input from a permission change. Any resulting design must keep native and runtime policy transitions consistent, preserve revocations and lifecycle cancellation, and avoid host-side inference of product authority. Separately, pre-callback denials should be observable through a privacy-safe reason/provenance event; no command contents are needed.

Autopilot simple-fix gate: failed. The unresolved repair changes permission/authorization semantics and needs a product decision. Those conditions disqualify it regardless of line count. No fix branch was created or pushed. GitHub cross-reference metadata and an open-PR search for 7040 showed no linked open PR at the time of this investigation.
