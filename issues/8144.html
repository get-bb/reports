#8144 · Idle timeline notices lack recovery without an applicable push

BugPriority: MediumEffort: MediumthreadsdesktopGitHub issue

2026-11-24 · trusted origin/main 75b35f027a98ae9ff84b7c27479dd7cda4430b04

Verdict: PARTIALLY REPRODUCED · Root-cause confidence: medium

1. TL;DR

An idle timeline can remain marked as behind when an event notice arrives without a usable timeline push. On current main, a controlled replay leaves the cached sequence at 7 and the unseen-event flag true for 60 simulated seconds, with zero fallback fetches. A matching push advances the cache to 8 and clears the flag. The missing recovery mechanism is verified, but neither spontaneous push loss nor the reported macOS desktop lifecycle was reproduced. This is a client-cache boundary reproduction, not proof that Pi cache warming or desktop visibility caused the original incident.

import { hasThreadTimelineUnseenEvents } from "../cache-owners/thread-timeline-unseen-events";
import { threadTimelineQueryKey } from "./query-keys";
import { useThreadTimeline } from "./thread-panel-queries";

vi.mock("@/lib/sdk", () => ({
  sdk: { threads: { timeline: vi.fn() } },
}));

vi.mock("@/hooks/useRealtimeSubscription", () => ({
  useThreadDetailRealtimeSubscription: vi.fn(),
  useThreadTimelineRealtimeSubscription: vi.fn(),

afterEach(() => {
  cleanup();
  vi.useRealTimers();
  vi.clearAllMocks();
  vi.restoreAllMocks();

it.each(["applied", "missing", "foreign"] as const)(
  "settles an idle timeline notice when its push is %s",
  async (delivery) => {
    vi.useFakeTimers();
    vi.spyOn(window, "matchMedia").mockImplementation((query) => ({
      matches: false,
      media: query,
      onchange: null,
      addListener: () => {},
      removeListener: () => {},
      addEventListener: () => {},
      removeEventListener: () => {},
      dispatchEvent: () => false,
    }));
    const before = makeThreadTimelineResponse({
      rows: [],
      maxSeq: 7,
      tag: "before-hidden-event",
    });
    const after = makeThreadTimelineResponse({
      rows: [],
      maxSeq: 8,
      tag: "after-hidden-event",
    });
    vi.mocked(sdk.threads.timeline).mockResolvedValue(after);
    const { queryClient, wrapper } = createQueryClientTestHarness();
    const queryKey = threadTimelineQueryKey("thread-1");
    queryClient.setQueryData(queryKey, before);
    renderHook(() => useThreadTimeline("thread-1", { staleTime: Infinity }), {
      wrapper,
    });
    const effects = createRealtimeCacheEffects({
      queryClient,
      visibility: {
        isDocumentVisible: () => true,
        subscribe: () => () => {},
      },
    });
    try {
      await act(async () => {
        effects.handleChanged({
          type: "changed",
          entity: "thread",
          id: "thread-1",
          changes: ["events-appended"],
          metadata: {
            eventTypes: ["provider/unhandled"],
            timelineSequence: 8,
          },
        });
        await vi.advanceTimersByTimeAsync(100);
      });
      expect(hasThreadTimelineUnseenEvents(queryClient, "thread-1")).toBe(true);
      await act(async () => {
        if (delivery !== "missing") {
          applyThreadTimelineSignal(queryClient, {
            type: "thread-timeline",
            target: {
              kind: "thread-timeline",
              threadId: "thread-1",
              segmentLimit:
                delivery === "foreign"
                  ? COMPACT_THREAD_TIMELINE_SEGMENT_LIMIT
                  : null,
              deferContent: true,
            },
            timeline: after,
          });
        }
        await vi.advanceTimersByTimeAsync(60_000);
      });
      console.log(JSON.stringify({
        delivery,
        cachedMaxSeq: queryClient.getQueryData<typeof before>(queryKey)?.maxSeq,
        unseen: hasThreadTimelineUnseenEvents(queryClient, "thread-1"),

      expect(hasThreadTimelineUnseenEvents(queryClient, "thread-1")).toBe(false);
      expect(queryClient.getQueryData(queryKey)).toMatchObject({ maxSeq: 8 });
    } finally {
      effects.dispose();
      queryClient.clear();
    }
  },

5. Root cause

  1. The active-timeline events-appended handler records the new sequence but does not fetch the active latest-timeline query. The remaining invalidations in that function concern the outline.
  2. The push owner immediately returns for a different segment limit or absent cache. Its refetch branch only runs after those gates for null or inapplicable deltas.
  3. The unseen predicate compares the announced sequence with cached maxSeq. With 8 announced and 7 cached, time passing alone cannot change it.
  4. The controller derives catch-up from the unseen predicate and nonempty rows; the surface shows it only when no other loading/error/ongoing state suppresses it. The label has a one-second reveal delay but no separate recovery mechanism.
  5. The server push path enumerates watched targets. That is a plausible source of a notice/push asymmetry, not proof that it caused this desktop incident.

Production excerpts:

if (target.segmentLimit !== (resolveThreadTimelineSegmentLimit() ?? null)) {
  return;
}

return sequence !== undefined && sequence > (timeline?.maxSeq ?? 0);

Verified mechanism: progress depends on a later applied push, fetch, or lifecycle recovery; a notice with no applicable push has no bounded repair at this owner. Unverified initiating cause: which desktop visibility/subscription/application transition prevented progress in the reported session. Consequently, confidence in the code-level liveness gap is high, while confidence that this is the complete incident root cause is medium.

6. Proposed fix / simple-fix decision

Not confident enough in the initiating trigger to ship a root-cause fix. Next experiment: trace the desktop visibility release/resume messages, subscription target segment limit, announced sequence, pushed sequence, and applied sequence together using synthetic data in a macOS desktop test. Then repair the demonstrated transition. If missed-push recovery is the intended policy, an owner-managed, cancellable stale-sequence recovery read should run only for an active timeline still behind, coalesce notices, cancel on catch-up/disposal, and avoid request storms during streaming.

No fix branch or pull request was created. The full reported bug was only partially reproduced: the test injects a missing/foreign push rather than demonstrating that desktop produces one. Existing coverage explicitly expects foreign windows to be ignored, so merely refetching every foreign push is not a justified root-cause change. Selecting a timeout and retry policy without the missing lifecycle evidence would require a product/lifecycle decision, failing the simple-fix gate.
