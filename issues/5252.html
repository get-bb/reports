#5252 · Claude plugin UI notifications generate diagnostics

BugPriority: LowEffort: Lowprovidersprovider-claude-codeGitHub issue2026-10-09 · base 9a47d42c78ca9689af0b78da9b3155a8c0b36251

Verdict: REPRODUCED at the provider translation boundary · Root-cause confidence: high

1. TL;DR

Seven plugin-UI system notification subtypes become diagnostic timeline events instead of being ignored. The provider first reduces an unrecognized system subtype to unknown, then converts that classification into provider/unhandled. Feeding independently authored notification envelopes through the real translator and shared event assembler reproduces the failure on trusted main. A second clean checkout gives the same seven failures. This report verifies the provider behavior, not the upstream CLI version at which these notifications first appeared.

5. Root cause

Subtype parsing uses a closed allow-list, so these notifications lose their subtype and become unknown:

    case "task_notification":
    case "task_progress":
    case "task_started":
    case "task_updated":
    case "thinking_tokens":
      return subtype;
    default:
      return "unknown";
  }

Visibility classification maps that case to { kind: "sdk/system", coverage: "unknown" }. The translator emits an unhandled delta whenever coverage is unknown:

  function unhandledDeltas(
    rawEvent: JsonRpcMessage,
    parentRef: string | undefined,
  ): ThreadDelta[] {
    const description = claudeCodeVisibilityMetadata.describeRawEvent(rawEvent);
    if (description.coverage !== "unknown") {
      return [];
    }
    return [
      {
        kind: "unhandled",
        raw: toRawEvent(rawEvent),
        rawType: description.kind,
        vouchedTurn: true,
        ...(parentRef ? { parentRef } : {}),
      },
    ];
  }

The existing shared event assembler converts the delta to provider/unhandled, which the regression asserts directly. The timeline parser constructs the diagnostic title:

  if (decoded.type === "provider/unhandled") {
    if (options?.includeDiagnosticOperations !== true) {
      return null;
    }

    return op(decoded, meta, "provider-unhandled", {
      opType: "provider-unhandled",
      title: `Unhandled ${providerDisplayName(
        decoded.providerId,
        options?.providerDisplayName,
      )} event`,
      detail: buildProviderUnhandledDetail(decoded),
      status: "completed",
    });
  }

The deeper maintenance risk is SDK subtype drift: new kinds need explicit coverage decisions. Globally suppressing unknown events would conceal unrelated unexpected or malformed envelopes.

6. Proposed fix and validation

Recognize the seven tested UI notification subtypes in the provider-local subtype union and parser, then classify them as noise in the existing visibility switch. Do not introduce a generic prefix rule or change the unknown fallback. The candidate changes only the provider visibility implementation and one regression test: 78 added text lines, zero deletions, two files; no protocol, schema, permission, dependency, packaging, or stored-data change.

The focused regression passes after the repair: 10/10. Provider lint and typecheck pass. The full provider suite initially reports five baseline failures under root; the same bridge failures occur in unchanged production code.
