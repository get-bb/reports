#6771 · PR visibility changes React hook order

BugPriority: LowEffort: Lowui · github · confirmed-reproGitHub issue

Verdict: REPRODUCED · Root-cause confidence: high

1. TL;DR

The GitHub PR Status plugin changes the sequence of React hooks when its show setting finishes loading or is toggled. Its visibility hook skips the thread-context hook while the setting is unavailable or disabled, then calls it after the setting becomes enabled. A focused test of the actual plugin hook emits React's hook-order warning on unchanged trusted main. The same agent repeated that failure in a second clean checkout. Calling the context hook unconditionally removes the warning without changing which PR segment is visible.

5. Root cause

The visibility hook combines the setting and a hook invocation using a short-circuiting expression. When the setting is unavailable or false, React never sees the context read. When it becomes true, React sees an extra context hook before the existing query lifecycle hooks.

const enabled = useSettings().values?.[SHOW_PULL_REQUEST_SETTING] === true;
const show = enabled && experimental_useThreadContextKind() === "banner";
return useThreadPullRequest(show ? input.environment : null) !== null;

The actual context-kind implementation calls usePaneState, which calls React useContext. The core Visibility component invokes the registered plugin hook in its own render, explaining why a live warning can name Visibility rather than the plugin function.

Existing tests mount separate instances with different setting values, but never rerender the same instance across settings changes. Their former context stub was a plain value getter, so it could not expose a React hook-order violation.

6. Proposed fix and proof

Read context kind unconditionally and apply the boolean gate only to its result. Retain the current query gating so disabled or card-mode segments do not request an environment PR. The production repair is two added lines and one deleted line. Including the regression test and fixture update, the change is 65 text lines across two files in one existing plugin subsystem, with no dependencies, generated files, persistence changes, public contracts, or release changes.

const enabled = useSettings().values?.[SHOW_PULL_REQUEST_SETTING] === true;
const contextKind = experimental_useThreadContextKind();
const show = enabled && contextKind === "banner";

After that repair, the focused test passes. The final complete plugin suite passes 183 tests in 10 files, along with typechecking and lint:
