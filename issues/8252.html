#8252 · Startup plugin gate can open before timeline readiness

BugPriority: MediumEffort: Mediumplugins · ui · perfGitHub issue2026-11-26

Trusted base: b0ddaad731565d7e4de68d824120d802fc78f7d5.

Verdict: PARTIALLY REPRODUCED · Root-cause confidence: high

1. TL;DR

The mechanism allowing background plugin imports before any timeline rows exist is reproduced on trusted main, twice. The screen gate observes critical code-loading promises and two animation frames, not timeline data readiness. Separately, its existing three-second page-age deadline opens the same gate even while a critical load remains pending. A focused test using the real pending timeline component, screen signal, gate, and reconciler observes one deferred import on each path while the timeline still has no rows. This is not a phone benchmark: the reported seconds saved, bundle totals, main-thread contention, and proposed scheduling improvement remain unverified.

5. Root cause

The plugin scheduler trusts a shared page-level promise

plugin-frontend.ts:830–850 awaits deps.whenScreenPainted() only for non-priority candidates, then reconciles and imports the candidate. The production dependency is the same real gate exercised by the test; the browser adapter connects importModule to dynamic import. The reproduction observes that adapter boundary, not browser download or evaluation.

if (!priorityPluginIds.includes(candidate.pluginId)) {
  await deps.whenScreenPainted();
}
untaken = index + 1;
prefetchAhead();
try {
  await reconcileCandidate(candidate, state, deps);

The signal tracks module readiness, not timeline readiness

ScreenPaintSignal.tsx:8–13 contains:

useEffect(() => {
  void whenCriticalLoadsSettled().then(markScreenPainted);
  startSplitPreloading();
}, []);

split-prefetch.ts:55–79 resolves settled waiters after two animation frames if the critical-load count is zero. App.tsx:286–293 tracks the thread view's preload, and define-split.tsx:82–100 completes that preload on module availability. None of these checks waits for timeline data or row commitment. The actual timeline render branch separately selects loading content whenever isThreadTimelinePending is true.

The existing fallback can release even earlier than code completion

screen-paint.ts:1–26 defines a 3000 ms page-age deadline. A waiter schedules:

deadline = setTimeout(
  markScreenPainted,
  Math.max(0, SCREEN_PAINT_DEADLINE_MS - performance.now()),
);

Therefore merely moving the existing signal to a later timeline event would not by itself guarantee late imports on a slow page: this fallback still opens the same gate. The existing deadline tests explicitly preserve that behavior. High confidence applies to this gate mechanism, not the magnitude of the reported phone slowdown.

Priority does not describe a complete registration footprint

plugin-surface-providers.ts:7–50 uses composer, thread-list, sidebar-navigation, thread-panel-tab, and the route owner. Entry scheduling is not driven by the complete set of message-renderer registrations. A gate change must avoid delaying a plugin that the visible content itself needs.

6. Proposed fix / safety decision

First decide the plugin-specific readiness contract: which content providers must be eager, which thread state releases nonessential entries, how empty/error/failed timelines escape the wait, and whether the deadline remains page-relative. Then route plugin scheduling through that contract without silently changing the shared split-preload signal, and measure cold and warm opens plus responsiveness after the first rows. A bounded or paced release may be preferable to moving all registration work into one post-row burst, but this has not been benchmarked here.

No fix PR: this changes plugin reveal, content-provider priority, and timeout policy, so it fails the simple-fix condition requiring no product or architecture decision. No production fix or branch was created, and no stopped fix was pushed. GitHub issue timeline metadata and an open-PR search found no linked open PR at investigation time. The reporter's prototype was neither fetched nor executed.
