#7753 · Synchronous SQLite waits and planner statistics

BugHighEffort: Mediumhost · threads · perfGitHub issue2026-11-18 UTC

Trusted main: ab7ad23bacb822445a1d7639d10318af86258148

Verdict: PARTIALLY REPRODUCED · Root-cause confidence: medium for the reported incident; high for the isolated mechanisms below.

1. TL;DR

On current main, a real SQLite writer lock makes a synchronous database update block a zero-delay JavaScript timer for approximately five seconds, using bb's default busy timeout. A fresh migrated database also starts without planner statistics. A synthetic, unhinted turn-item query picks an index that visits a whole thread's completed items instead of seeking one turn; supplying statistics changes that diagnostic query's plan. However, the closest current production DISTINCT query already pins the correct turn index, and both bounded and full analysis work on this small synthetic distribution. The original multi-second large-database reads, 62-second stalls and daemon disconnects were not reproduced, so these findings do not establish the cause or size of that production incident.

import { mkdtempSync, rmSync, writeFileSync } from "node:fs";
import { tmpdir } from "node:os";
import { join } from "node:path";
import { performance } from "node:perf_hooks";
import { and, eq, isNull, sql } from "drizzle-orm";
import { createConnection, SQLITE_BUSY_TIMEOUT_MS } from "./src/connection.js";
import { createMigratedConnection } from "./src/testing.js";
import { upsertHost } from "./src/data/hosts.js";
import { createProject } from "./src/data/projects.js";
import { createThread } from "./src/data/threads.js";
import { isStoredTurnContextCompactionOnly } from "./src/data/events.js";
import { events, hosts } from "./src/schema.js";
import { noopNotifier } from "./src/notifier.js";

const directory = mkdtempSync(join(tmpdir(), "bb-7753-"));
const databasePath = join(directory, "synthetic.sqlite");
const template = createMigratedConnection();
writeFileSync(databasePath, template.$client.serialize());
template.$client.close();
const observed: Array<{ sql: string; durationMs: number; cpuDurationMs: number }> = [];
const db = createConnection(databasePath, {
  slowQueryThresholdMs: 0,
  slowQueryLogger: {
    info(fields) {
      observed.push({
        sql: fields.sql,
        durationMs: fields.durationMs,
        cpuDurationMs: fields.cpuDurationMs,
      });
    },
  },
});
const blocker = createConnection(databasePath);

try {
  const host = upsertHost(db, noopNotifier, { name: "synthetic-host" });
  const { project } = createProject(db, noopNotifier, {
    name: "synthetic-project",
    source: { type: "local_path", hostId: host.id, path: directory },
  });
  const thread = createThread(db, noopNotifier, {
    status: "idle",
    projectId: project.id,
    providerId: "codex",
  });
  const insert = db.$client.prepare(`
    INSERT INTO events
      (id, thread_id, scope_kind, turn_id, sequence, type, item_id, item_kind, data, created_at)
    VALUES (?, ?, 'turn', ?, ?, 'item/completed', ?, 'contextCompaction', '{}', 1)
  `);
  const rowCount = 40000;
  db.$client.transaction(() => {
    for (let index = 0; index < rowCount; index += 1) {
      insert.run(`event-${index}`, thread.id, `turn-${index}`, index + 1, `item-${index}`);
    }
  })();
  const statisticsBefore = db.$client.prepare(
    "SELECT name FROM sqlite_schema WHERE name IN ('sqlite_stat1', 'sqlite_stat4') ORDER BY name",
  ).all();
  assert.deepEqual(statisticsBefore, []);
  observed.length = 0;
  assert.equal(isStoredTurnContextCompactionOnly(db, {
    threadId: thread.id,
    turnId: "turn-39999",
  }), true);
  const productionQuery = observed.find((entry) => entry.sql.startsWith('select distinct'));
  assert.ok(productionQuery);
  assert.match(productionQuery.sql, /INDEXED BY events_thread_turn_type_item_sequence_idx/);
  const comparison = db.selectDistinct({ itemKind: events.itemKind }).from(events).where(and(
    eq(events.threadId, thread.id),
    eq(events.turnId, "turn-39999"),
    eq(events.type, "item/completed"),
    isNull(events.parentToolCallId),
  )).toSQL();
  const pinned = db.selectDistinct({ itemKind: sql<string | null>`${events.itemKind}` })
    .from(sql`${events} INDEXED BY events_thread_turn_type_item_sequence_idx`)
    .where(and(
      eq(events.threadId, thread.id),
      eq(events.turnId, "turn-39999"),
      eq(events.type, "item/completed"),
      isNull(events.parentToolCallId),
    )).toSQL();
  const plan = (query: typeof comparison) => db.$client.prepare(
    `EXPLAIN QUERY PLAN ${query.sql}`,
  ).all(...query.params);
  const measure = (query: typeof comparison) => {
    const statement = db.$client.prepare(query.sql);
    const started = performance.now();
    for (let iteration = 0; iteration < 20; iteration += 1) {
      assert.deepEqual(statement.all(...query.params), [{ item_kind: "contextCompaction" }]);
    }
    return (performance.now() - started) / 20;
  };
  const before = { unhintedPlan: plan(comparison), unhintedMs: measure(comparison), pinnedPlan: plan(pinned), pinnedMs: measure(pinned) };
  db.$client.pragma("analysis_limit = 1000");
  db.$client.exec("ANALYZE");
  const bounded = { unhintedPlan: plan(comparison), unhintedMs: measure(comparison) };
  db.$client.pragma("analysis_limit = 0");
  db.$client.exec("ANALYZE");
  const full = { unhintedPlan: plan(comparison), unhintedMs: measure(comparison) };
  const statisticsAfter = db.$client.prepare(
    "SELECT name FROM sqlite_schema WHERE name IN ('sqlite_stat1', 'sqlite_stat4') ORDER BY name",
  ).all();
  blocker.$client.exec("BEGIN IMMEDIATE");
  let timerFired = false;
  const timer = new Promise<void>((resolve) => setTimeout(() => { timerFired = true; resolve(); }, 0));
  const started = performance.now();

  const blockedMs = performance.now() - started;

5. Root cause and limits

createConnection opens better-sqlite3 synchronously and configures busy_timeout = 5000. runTimedStatementOperation invokes args.work() directly and records elapsed time after it returns. A native lock wait therefore prevents JavaScript timers from running even when CPU usage is low. In the two induced updates, the logger measured 5021.9/5033.5 ms wall time and 10/10 ms thread CPU time.

The competing indexes offer either thread/type/item-kind access or thread/turn/type access. With no statistics, the unhinted DISTINCT shape favors the former on this distribution, filtering the turn after selecting thread-wide candidates. Analysis supplies information that changes the choice. This confirms a planner hazard, not a current-main failure of the closest production lookup.

isStoredTurnContextCompactionOnly already includes this protective clause:

.from(sql`${events} INDEXED BY events_thread_turn_type_item_sequence_idx`)

Git blame attributes that hint to 11175a0d52bb533f81ef29b54a4c245f968b33cd (2026-11-09), not a new change made for this report. The retry helper already uses inArray with a request-set subquery rather than the reported correlated EXISTS; history attributes that change to f024a372f0e1e0670f6fd7452ebcd1341f639c95 (2026-11-13).

The outline build still runs inside runEventLoopWorkSync. How much the reporter's incident comes from this path, disk contention, other queries or plugins remains unknown. The induced writer-lock experiment does not establish that production readers wait on writer locks; WAL behavior and actual statement/transaction context matter. No claim is made that analysis would reduce the reported stalls.

6. Proposed fix / next experiment

No new production patch is justified by this evidence. Keep the current targeted index protection. Next, run current main against an operator-controlled sanitized database copy, capture exact SQL with real bindings and per-statement diagnostics during an actual long stall, and compare both result correctness and query plans before/after bounded and full analysis. Measure cold I/O and timer/heartbeat impact separately from warm query timings.

A planner-statistics lifecycle changes stored database state and needs a deliberate bounded-maintenance policy; moving database work off the event loop is an architectural change. Neither qualifies under this run's simple-fix constraints. The remaining original symptom has no focused failing current-main regression here. No branch, source commit, push or fix PR was created.
