1. TL;DR

A depleted pooled Codex account can produce a generic rate-limit response advising the client to wait roughly a day. The real Account Pooler plugin produces that response in two clean-checkout test runs, even though its own quota state already identifies an exhausted subscription window. Its Codex adapter discards the cause and supplies the same error category used for generic request pacing; the reset deadline survives only as a header and prose. Existing retry and concurrency code makes the reported queue consequence plausible, but this investigation did not run Codex or replay two live threads. The confirmed finding is the provider-facing response defect, not a fresh end-to-end demonstration of a blocked Claude thread.

5. Root cause

Confirmed producer-side mechanism: accountAvailability and noEligibleResponse calculate an earliest usable time from quota reset and pacing holds. The refusal handler turns that into a potentially very long Retry-After and sends a 429 through a generic adapter API:

const availability = this.accountAvailability(accounts, family);
const next =
  availability.kind === "blocked" ? availability.retryAt : undefined;
const retryAfter = Math.max(
  1,
  Math.ceil(((next ?? now + 1_000) - now) / 1_000),
);

The Codex adapter's errorResponse then categorizes solely by status, without knowing whether the cause is subscription exhaustion, pacing or another eligibility condition:

error: {
  message,
  type: status === 429 ? "rate_limit_error" : "api_error",
  code: status === 429 ? "rate_limit_exceeded" : null,
}

The response retains a human-readable availability time but not a structured subscription-exhaustion cause/reset contract. Thus a consumer cannot distinguish those cases from this type/code pair.

Conditional downstream mechanism: if the external provider treats this as an internally retryable failure, the Codex bridge does not run quota recovery for a retrying error. Provider Retry waits for turn.failed. Meanwhile listRunningThreads includes starting and active threads, and the shared concurrency hook applies its overall cap to that whole list. This explains why the claimed internal wait could retain capacity; it does not establish that such a wait occurred in these runs.
