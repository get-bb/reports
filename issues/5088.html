Verdict: PARTIALLY REPRODUCED · Root-cause confidence: low for the LTE-specific failure; high for the conditional stalled-loading mechanism.

1. TL;DR

The report describes an Android native app that cannot finish pairing or loading on cellular, while the web app works on the same network. This investigation does not have an Android device, Android runtime, or that cellular network, so it does not confirm the native-versus-Chrome difference. On trusted main, both Connect redemption and session minting await fetch operations without an application deadline. A real local HTTP server that accepts requests but withholds responses leaves redemption pending and the mobile session scheduler authenticating, which maps to the shell’s “Signing in” loading state. Healthy responses succeed and HTTP failures enter the error path. This explains a conditional loading mechanism, not why this phone’s LTE transport stalls; no production fix or PR is justified yet.

  1. Healthy control: the server returns valid local redemption and session JSON. The production helpers accept it; the session scheduler authenticates.
  2. Failure control: the server returns HTTP 503. The production redemption helper rejects with its network code; the scheduler transitions to error.
  3. Stalled-response experiment: the server accepts both requests and never responds. The probe waits 2,000 ms, verifies both requests arrived and neither helper supplied an abort signal, and checks pending enrollment and authenticating session.
  4. The production shell-state resolver returns loading / Signing in. The harness then cancels its own transport signals so both operations can exit and all sockets and scheduler timers close.

Expected controls: healthy requests finish and failed requests expose errors. Diagnostic expectation: once a transport rejects, loading ends. Actual stalled observation: no application-controlled settlement occurred during the two-second window. The two seconds are an observation interval, not an existing product timeout contract. This diagnostic test deliberately passes when it observes that limitation; it is not a pre-fix failing regression for the Android LTE bug.

5. Root cause: verified mechanism, unknown LTE trigger

The enrollment screen enters redeeming and awaits the shared redemption helper before saving a profile. The helper awaits the HTTP response and then JSON without setting its own deadline. Likewise, the default session scheduler calls the shared desktop-session helper, remains authenticating until the awaited operation settles, and schedules a retry only inside its catch path. The shell explicitly maps authenticating to its loading presentation. Holding the HTTP response open therefore reproduces that conditional loading state without mocking the production clients or scheduler.

Not established: whether the reported phone stalls in DNS, TCP, TLS, request delivery, response headers, response body, cookies, WebView, or realtime; whether the request reaches Connect; and whether Android later emits a platform timeout. The local reproduction uses Node fetch, plain HTTP, and stubbed cookie/cache boundary stores; it does not execute React Native networking. A healthy server-side tunnel cannot establish health of the phone’s request path, and Chrome success alone does not identify a realtime or IPv6 defect.

6. Proposed fix and next experiment

No carrier/network workaround or transport-stack change is proposed without device evidence. Capture a sanitized native trace on an agent-controlled Android client for redemption and desktop-session minting, including timestamps for name resolution, connect/TLS, request delivery, response headers/body, and completion or rejection. Repeat Wi-Fi/native, LTE/native, and LTE/Chrome with the same fresh isolated test account and server; record native build commit, WebView version, address family and negotiated transport. Also distinguish session-loading from a WebView page load after a valid cached session.

A bounded, cancelable deadline could improve the failure presentation for stalled requests, but it would not establish or necessarily repair LTE reachability. Timeout policy and behavior after an ambiguous one-time redemption need separate design and verification. The simple-fix gate is not met: the reported Android LTE defect is not reproduced, and no focused regression demonstrably fails for its verified native root cause. No branch, commit, push, or PR for a production fix was made.
