#8246 · Mobile shell duplicates live WebView routes

BugPriority: MediumEffort: Mediummobile · remote · perf · partial-repro GitHub issue · November 26, 2026

Trusted origin/main: b0ddaad731565d7e4de68d824120d802fc78f7d5.

Verdict: PARTIALLY REPRODUCED · Root-cause confidence: high for JavaScript navigation; native process and memory behavior unverified.

1. TL;DR

The mobile shell handles a notification by pushing another WebView route, even when a WebView route already exists. A focused executable reproduction calls the real notification handler, obtains screen identity configuration from the real root navigator, and feeds its actions through the installed Expo stack router. Two notifications grow the route stack from one to two to three, retaining the original route. The same failure occurs in a second clean checkout at the trusted base commit. This Linux investigation cannot measure iOS WebContent processes, memory usage, document-load timing, or capture an authentic native screenshot; those parts of the report remain unverified.

5. Root cause

apps/mobile/src/notifications/PushNotificationsHost.tsx:80 submits each targeted notification as a new push:

      if (target.threadId === null) {
        if (profile.id === activeProfileIdRef.current) return;
        router.push(webViewShellHref({ profileId: profile.id }));
        return;
      }
      router.push(
        webViewShellHref({
          profileId: profile.id,
          path: getThreadLocationPath({
            threadId: target.threadId,

apps/mobile/src/screens/shell/RootNavigator.tsx:79 declares no stable screen identity. The reproduction reads these actual props rather than hard-coding their absence.

        <Stack.Screen name="index" options={hiddenHeader} />
        <Stack.Screen

The locked Expo Router implementation, expo-router/build/react-navigation/routers/StackRouter.js, looks up routeGetIdList[name] for PUSH. Without an identity it does not reuse the active route, and appends a newly keyed one. The reproduction runs this dependency, not a hand-written stack model. One original route plus two pushes produces three retained routes.

apps/mobile/app/webview.tsx:1 maps each route to the WebView-owning screen. apps/mobile/src/screens/webview/ProfileWebViewScreen.tsx:90 incorporates requestedPath in loadScope, and apps/mobile/src/screens/webview/ProfileWebViewScreen.tsx:350 uses that scope in the WebView key:

apps/mobile/src/app-shell/ThreadOpenSignalHandler.tsx:12 is a second native push source; apps/app/src/components/layout/AppLayout.tsx:516 already opens thread signals in the web page. This duplication is source evidence, not a separate executed signal test.

6. Proposed fix, from first principles

Give the WebView route stable identity, independent of requested destination. Separate a destination-change request from document identity: reuse a ready page for same-server navigation, and retain a safe single-view load fallback when navigation is unsupported, not ready, or the server changes. Ensure cold start and process recovery still load the intended thread, repeated identical requests remain consumable, and only one layer owns thread-open signals. Validate foreground/background notification taps, deep links, shares, server switching, process recovery, and old-server compatibility on native devices. Any cross-shell navigation capability would be a bridge contract change, outside the automation's simple-fix constraints.
