#8218 · Unbounded GitHub mention database reads

BugPriority: MediumEffort: Lowplugins · github · perf GitHub issue · November 26, 2026

Trusted main: b0ddaad731565d7e4de68d824120d802fc78f7d5

Verdict: REPRODUCED · Root-cause confidence: high

1. TL;DR

GitHub mention suggestions display at most eight issues and eight pull requests, but their database work is not bounded to that result budget. Calling the actual registered providers over a synthetic cache for 40 repositories materializes 4,000 open issues and 2,000 open pull requests before returning only 16 suggestions. Both queries scan the items table and sort in a temporary B-tree. A second clean checkout reproduced the same structural failure. This report proves the provider-level database defect, not a measured browser typing delay.

import { performance } from "node:perf_hooks";
import { expect, it, vi } from "vitest";
import { createFakePluginHost } from "@get-bb/plugin-sdk/testing";
import plugin from "./server";

it("keeps mention database materialization bounded by the result budget", async () => {
  const host = createFakePluginHost({
    pluginId: "github",
    sdk: { projects: { list: async () => [] } },
  });
  try {
    await plugin(host.bb);
    const database = host.bb.storage.database();
    const insert = database.prepare(
      "INSERT INTO items (repo, number, kind, title, state, author, labels, url, body, updated_at, assignees) VALUES (?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?)",
    );
    const providers = host.harness.registrations.mentionProviders;
    const observations: { sql: string; params: unknown[]; rows: number }[] = [];
    const prepare = database.prepare.bind(database);
    const prepareSpy = vi.spyOn(database, "prepare").mockImplementation((sql) => {
      const statement = prepare(sql);
      if (sql.startsWith("SELECT * FROM items ")) {
        const all = statement.all.bind(statement);
        vi.spyOn(statement, "all").mockImplementation((...params) => {
          const rows = all(...params);
          observations.push({ sql, params, rows: rows.length });
          return rows;
        });
      }
      return statement;
    });
    const results: object[] = [];
    let largestMaterialization = 0;
    for (const repositories of [1, 10, 40]) {
      database.prepare("DELETE FROM items").run();
      database.transaction(() => {
        for (let repository = 0; repository < repositories; repository += 1) {
          for (const [kind, openCount, closedCount] of [
            ["issue", 100, 50],
            ["pr", 50, 30],
          ] as const) {
            for (let number = 1; number <= openCount + closedCount; number += 1) {
              insert.run(
                `fixture/repository-${repository}`,
                number,
                kind,
                `Seed record ${number}`,
                number <= openCount ? "OPEN" : "CLOSED",
                "fixture",
                "[]",
                "https://github.com/fixture/fixture",
                "x".repeat(3500),
                new Date(Date.UTC(2026, 0, 1) + number * 1000).toISOString(),
                "[]",
              );
            }
          }
        }
      })();
      for (const query of ["", "seed", "unfindable-token"]) {
        observations.length = 0;
        const search = async () => {
          for (const provider of providers) {
            const matches = await provider.search({
              query,
              trigger: "@",
              projectId: "fixture-project",
              threadId: "fixture-thread",
              experimental_signal: new AbortController().signal,
            });
            expect(matches).toHaveLength(query === "unfindable-token" ? 0 : 8);
          }
        };
        await search();
        const captured = observations.slice();
        const plans = captured.map(({ sql, params }) =>
          prepare(`EXPLAIN QUERY PLAN ${sql}`).all(...params),
        );
        largestMaterialization = Math.max(
          largestMaterialization,
          ...captured.map(({ rows }) => rows),
        );
        const durations: number[] = [];
        for (let iteration = 0; iteration < 25; iteration += 1) {
          const started = performance.now();
          await search();
          if (iteration >= 5) durations.push(performance.now() - started);
          observations.length = 0;
        }
        durations.sort((left, right) => left - right);
        results.push({
          repositories,
          query,
          materializedRows: captured.map(({ rows }) => rows),
          plans,
          medianMs: Number(durations[10].toFixed(3)),
        });
      }
    }
    prepareSpy.mockRestore();
    console.log(JSON.stringify({ results, largestMaterialization }, null, 2));
    expect(largestMaterialization).toBeLessThanOrEqual(8);
  } finally {
    vi.restoreAllMocks();
    await host.harness.lifecycle.dispose();
  }
}, 60_000);

5. Root cause

The cache schema has a primary key beginning with repository, but mention search filters by kind and state and orders globally by update time. The key does not support that access path.

  bb.storage.migrate(db, [
    `CREATE TABLE IF NOT EXISTS items (
       repo TEXT NOT NULL,
       number INTEGER NOT NULL,
       kind TEXT NOT NULL,
       title TEXT NOT NULL,
       state TEXT NOT NULL,
       author TEXT NOT NULL,
       labels TEXT NOT NULL,
       url TEXT NOT NULL,
       body TEXT NOT NULL,
       updated_at TEXT NOT NULL,
       PRIMARY KEY (repo, kind, number)
     )`,
    `ALTER TABLE items ADD COLUMN assignees TEXT NOT NULL DEFAULT '[]'`,
  ]);

listCachedItems builds a SELECT * without a database result limit, runs .all(), then converts every matching row, including bodies and parsed arrays. A table scan examines candidate rows across the cache, including closed records before filtering. Not all scanned records are returned: only matching open records are materialized into JavaScript.

Both provider registrations share this helper for @ and # searches. The mismatch between a small suggestion budget and unbounded list retrieval explains the cache-size-dependent work.

6. Proposed fix

Push the suggestion budget into the SQL query and provide an index ordered by kind, state and update time, so matching open records can be visited newest first without a separate sort. Keep intentional full-list RPC and CLI behavior unchanged. Add a focused owner-boundary regression protecting bounded row materialization, and verify the selected plan. Preserve existing substring matching semantics; no-match searches still require examining candidates. The index must use the plugin's existing append-only migration mechanism.

No fix was attempted here: an existing open pull request already closes this issue, and the index migration would also exceed this autopilot's no-migration simple-fix constraints.
