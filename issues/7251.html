#7251 · Provider notices escape the running turn during timeline projection

BugLow priorityLow effortthreadsIssue2026-11-07

Base: 55135d1e5045d6c5d3c24f5a4d5556ed3e11cb00, fetched from trusted get-bb/bb origin/main.

Verdict: REPRODUCED · Root-cause confidence: high · Reproduction label: confirmed-repro.

1. TL;DR

A provider notice received before an assistant answer can appear after that answer in the timeline. The notice is not delayed in transport: its event sequence is earlier, but the projection treats thread-scoped notices as standalone entries. The row planner expands the whole earlier-starting turn, including its answer, before emitting the notice. The same ordering failure occurs in collapsed and flat output, with general, configuration and deprecation notices. Two clean checkouts reproduced the data-ordering failure without a model, desktop app, network request, custom theme or user database.

import { describe, expect, it } from "vitest";
import {
  createTimelineEventFactory,
  flattenTimelineRows,
  renderTimelineFixture,
} from "./timeline-test-harness.js";

const warningCases = [
  { location: "before the turn", seq: 10, scope: threadScope() },
  { location: "during the turn", seq: 40, scope: threadScope() },
  { location: "after the answer", seq: 90, scope: threadScope() },
  { location: "after the turn", seq: 110, scope: threadScope() },
  { location: "inside turn scope", seq: 40, scope: turnScope("turn-1") },
];

describe.each(["collapse", "flat"] as const)(
  "%s provider warning chronology",
  (completedTurnDisplay) => {
    describe.each(["general", "config", "deprecation"] as const)(
      "%s warnings",
      (category) => {
        it.each(warningCases)(
          "preserves sequence order for a warning $location",
          ({ seq, scope }) => {
            const event = createTimelineEventFactory({
              threadId: "thread-1",
              turnId: "turn-1",
            });
            const warning = event.providerWarning({
              seq,
              category,
              summary: "Provider notice",
            });
            const rendered = renderTimelineFixture({
              completedTurnDisplay,
              events: [
                event.turnStarted({ seq: 20 }),
                { ...warning, scope },
                event.assistantCompleted({ seq: 80, text: "Answer ready" }),
                event.turnCompleted({ seq: 100 }),
              ].sort((left, right) => left.seq - right.seq),
              projectionOptions: {
                threadStatus: "idle",
                turnMessageDetail: "full",
              },
            });
            const messageRows = flattenTimelineRows(rendered.rows).filter(
              (row) => row.kind === "system" || row.kind === "conversation",
            );

            expect(messageRows.map((row) => row.sourceSeqStart)).toEqual(
              seq < 80 ? [seq, 80] : [80, seq],
            );
          },
        );
      },
    );
  },
);

5. Root cause

Warning parsing maps provider notices to operation messages with type warning or deprecation, preserving thread scope. In the grouping eligibility check, only permission, plugin-form and user-question lifecycle messages can be associated with the turn running at their sequence. Warnings are excluded.

The thread-scope branch therefore puts the notice in a standalone projection entry. Entry sorting places the earlier-starting turn first. Finally, the row planner expands that whole turn before the standalone notice:

return projection.entries.flatMap((entry) =>
  entry.kind === "projected-message"
    ? [messagePlan(entry.message)]
    : planTurn(entry.turn, completedTurnDisplay, rowIdPrefix),
);

This explains why changing display mode cannot solve the problem. Sorting the final rows globally would be a weaker fix because summary rows span turns and must retain their existing grouping and lazy-details semantics.

6. Proposed fix

Extend the existing running-turn association to operation messages whose type is warning or deprecation. Keep their stored event scope unchanged. Reuse the existing sequence-based running-turn selection, so notices outside a turn remain standalone and notices after an answer remain after it. This is a local projection fix in the thread-view subsystem; no protocol, schema, stored data, dependencies or packaging changes are needed.

The local patch passes all 30 chronology cases, all 540 thread-view tests, thread-view typechecking, and 55 existing server timeline tests covering caching, window pagination, completed-turn display and lazy details. The test was added and observed failing before production code changed. The fix changes two files in one subsystem: 64 additions plus four deletions, 68 total changed text lines, with no binary changes. See the exact patch and verification logs below.
