#5973 · Thread deletion confirmation counts a different relationship than its cascade

BugPriority: MediumEffort: MediumthreadsGitHub issue2026-10-21 · base 04bdce8111ca3dbdd136c63fad3e36f56e5814c0

Verdict: REPRODUCED · Root-cause confidence: high · reproduction label: confirmed-repro.

1. TL;DR

The delete warning counts sidebar children and promises that those threads will also be deleted. The real delete route instead removes threads connected by lifecycle ownership, a separate relationship. A route-level reproduction against trusted main confirms that a sidebar-only child remains active and readable after confirmed parent deletion, while a lifecycle-owned child is deleted. Existing tests explicitly require sidebar-only children to survive, so simply broadening the delete query would reverse an established contract. One additional issue claim does not hold after cleanup on this checkout: the surviving child's parent reference is cleared when the parent row is physically removed.

Complete reproduction test
import { getThread } from "@bb/db";
import { describe, expect, it } from "vitest";
import { runThreadLifecycleSweep } from "../../src/services/system/periodic-sweeps.js";
import {
  seedHostSession,
  seedProjectWithSource,
  seedThread,
} from "../helpers/seed.js";
import { withTestHarness } from "../helpers/test-app.js";

describe("confirmed thread deletion", () => {
  it("deletes the assigned child counted by the confirmation guard", async () => {
    await withTestHarness(async (harness) => {
      const { host } = seedHostSession(harness.deps);
      const { project } = seedProjectWithSource(harness.deps, {
        hostId: host.id,
      });
      const parent = seedThread(harness.deps, { projectId: project.id });
      const assigned = seedThread(harness.deps, {
        projectId: project.id,
        parentThreadId: parent.id,
      });
      const owned = seedThread(harness.deps, {
        projectId: project.id,
        lifecycleOwnerThreadId: parent.id,
      });
      const unrelated = seedThread(harness.deps, { projectId: project.id });
      const summaryResponse = await harness.app.request(
        `/api/v1/threads/${parent.id}/child-summary`,
      );
      expect(summaryResponse.status).toBe(200);
      expect(await summaryResponse.json()).toMatchObject({
        nonDeletedChildCount: 1,
      });
      const remove = (confirmed: boolean) =>
        harness.app.request(`/api/v1/threads/${parent.id}`, {
          method: "DELETE",
          headers: { "content-type": "application/json" },
          body: JSON.stringify({ childThreadsConfirmed: confirmed }),
        });
      expect((await remove(false)).status).toBe(409);
      expect(getThread(harness.db, parent.id)?.deletedAt).toBeNull();
      expect((await remove(true)).status).toBe(200);
      for (let attempt = 0; attempt < 3; attempt += 1) {
        await runThreadLifecycleSweep(harness.deps);
      }
      const parentResponse = await harness.app.request(
        `/api/v1/threads/${parent.id}`,
      );
      const assignedResponse = await harness.app.request(
        `/api/v1/threads/${assigned.id}`,
      );
      const ownedResponse = await harness.app.request(
        `/api/v1/threads/${owned.id}`,
      );
      const surviving = getThread(harness.db, assigned.id);
      console.log(JSON.stringify({
        parentStatus: parentResponse.status,
        assignedChildStatus: assignedResponse.status,
        ownedChildStatus: ownedResponse.status,
        assignedArchivedAt: surviving?.archivedAt,
        assignedDeletedAt: surviving?.deletedAt,
        assignedStillReferencesParent: surviving?.parentThreadId === parent.id,
        parentPhysicallyRemoved: getThread(harness.db, parent.id) === null,
      }));
      expect(parentResponse.status).toBe(404);
      expect(ownedResponse.status).toBe(404);
      expect(getThread(harness.db, unrelated.id)?.deletedAt).toBeNull();
      expect(assignedResponse.status).toBe(404);
    });
  });
});

5. Root cause

The preview/confirmation and deletion use different edges in the thread graph:

  1. The child-summary route counts non-deleted assigned children using parentThreadId. The underlying count filters that column directly.
  2. The confirmation guard uses that same count, and returns early once confirmation is true. Confirmation does not change the deletion selector.
  3. The DELETE handler obtains listLifecycleThreadTree, marks that tree deleted, and schedules side effects only for those members.
  4. The recursive lifecycle selector follows only lifecycle ownership: 
    WITH RECURSIVE owned(id) AS (
  seed UNION SELECT t.id FROM threads t
  JOIN owned ON t.lifecycle_owner_thread_id = owned.id
)
    markThreadDeleted uses exactly that selector. Sidebar-only children are absent from both the persistent mark and downstream cleanup.
  5. After owner cleanup, the schema clears sidebar-parent references rather than cascading deletion. Lifecycle-owner references instead restrict deletion until dependents are removed.

Deeper contract conflict: the documented lifecycle contract declares ownership independent from sidebar parentage. More decisively, an existing fixture creates a sidebar-only child, and its assertions require that child to survive deletion of the parent. This is not a safe one-line omission in the recursive SQL: broadening it would destroy threads that existing policy preserves.

6. Proposed fix and simple-fix assessment

Choose one consistent product contract before changing production code: either explicitly delete sidebar descendants when confirmed, including correct nested cleanup and notifications, or preserve the lifecycle-only deletion contract and make the preview, confirmation count, and warning accurately describe it. The current warning is false for the tested parent-only relationship.

No automated fix PR: the requested sidebar cascade conflicts with documented independent ownership and passing regression tests that require sidebar-only threads to survive. Choosing destructive sidebar traversal versus correcting the confirmation semantics is a product decision, which fails the automation's simple-fix gate. No production patch, branch, commit, or pull request was created, and no dependency, migration, generated file, protocol, or stored data was changed.
