1. TL;DR

The issue describes hidden side conversations repeating work scheduled in their parent Claude conversation. A direct test of bb's real fork worker and the installed Anthropic SDK confirms that a fork after a synthetic scheduler operation contains both the original CronCreate tool call and its matching result, unchanged. A fork before that operation does not contain them. The bridge then resumes the copied session, which is a plausible route for a native scheduler to restore the same work. This investigation did not start a Claude scheduler or observe any timer fire, so transcript copying is established but duplicate execution and its exact restoration mechanism remain unverified.

const configDirectory = await mkdtemp(join(tmpdir(), "bb-7502-history-"));
try {
  const transcriptDirectory = join(configDirectory, "projects", "-tmp-synthetic");
  await mkdir(transcriptDirectory, { recursive: true });
  const sourceSessionId = randomUUID();
  const messageIds = Array.from({ length: 4 }, () => randomUUID());
  const callId = "synthetic-scheduler-call";
  const taskInput = {
    cron: "13 * * * *",
    prompt: "Synthetic diagnostic reminder",
    recurring: true,
  };
  const messages = [
    { type: "user", message: { role: "user", content: "Synthetic history fixture" } },

      type: "assistant",
      message: {
        id: "synthetic-assistant-message",
        type: "message",
        role: "assistant",
        model: "synthetic-model",
        content: [{ type: "tool_use", id: callId, name: "CronCreate", input: taskInput }],
        stop_reason: "tool_use",
        stop_sequence: null,
        usage: { input_tokens: 1, output_tokens: 1 },
      },
    },
    {
      type: "user",
      message: {
        role: "user",
        content: [{ type: "tool_result", tool_use_id: callId, content: JSON.stringify({ id: "synthetic-task", ...taskInput }) }],
      },
    },
    { type: "assistant", message: { role: "assistant", content: [{ type: "text", text: "Synthetic fixture complete" }] } },
  ];
  const sourceEntries = messages.map((message, index) => ({
    ...message,
    uuid: messageIds[index],
    parentUuid: index === 0 ? null : messageIds[index - 1],
    sessionId: sourceSessionId,
    timestamp: new Date().toISOString(),
    isSidechain: false,
  }));
  const sourcePath = join(transcriptDirectory, `${sourceSessionId}.jsonl`);
  const sourceText = sourceEntries.map(entry => JSON.stringify(entry)).join("\n") + "\n";
  await writeFile(sourcePath, sourceText, { mode: 0o600 });
  const forkIds = new Set();
  for (const [mode, upToMessageId, expectedCalls] of [
    ["full", undefined, 1],

    assert.notEqual(forkId, sourceSessionId);
    assert.ok(!forkIds.has(forkId));
    forkIds.add(forkId);
    const entries = (await readFile(join(transcriptDirectory, `${forkId}.jsonl`), "utf8"))

5. Root cause

Verified boundary: plugins/provider-claude-code/src/bridge/session-fork.ts:83 supplies a custom SessionStore to the SDK's forkSession. The store reads the source transcript and serializes the entries produced by that SDK into a new exclusive-create transcript file. There is no bb-specific scheduler-state separation at this boundary. The actual SDK preserved the synthetic CronCreate call and result in both post-operation forks.

const result = await forkSession(args.sourceSessionId, {
  sessionStore: createProjectTranscriptStore(args.configDirectory),
  ...(args.upToMessageId !== undefined
    ? { upToMessageId: args.upToMessageId }
    : {}),
});

Verified continuation: plugins/provider-claude-code/src/bridge/bridge.ts:2543 attaches the new provider session ID; plugins/provider-claude-code/src/bridge/sdk-session.ts:264 persists the session and passes that ID as resume. Side chat is one caller, rather than a separate transcript implementation.

Remaining causal gap: if the native Claude runtime reconstructs active timers from this copied history or related session state, independently resumed children can own the same work. That conditional mechanism fits the report, but this test does not identify which native records own scheduling, demonstrate reconstruction, or rule out SDK-side fork handling that distinguishes history from active timers. Merely finding CronCreate in a transcript is not sufficient evidence of the full bug.

6. Proposed fix / next experiment

First run an isolated, authorized native-provider experiment with a harmless in-memory notification, then observe the parent and two children through a real timer tick. Establish whether active tasks are stored separately or reconstructed from tool events; check deletion, resume, and checkpoint forks. A valid regression must fail on the unchanged provider and pass after removing inherited executable scheduling state while retaining useful conversation history.

Do not blindly strip all scheduler tool messages: doing so may damage tool-result pairing or context without affecting the real scheduler store. Disabling scheduling for every fork would also prevent legitimate new tasks in that fork and needs a deliberate behavior decision. No production patch or pull request is safe under this autopilot's simple-fix gate: live duplication has not been reproduced and no pre-fix failing behavioral regression exists.
