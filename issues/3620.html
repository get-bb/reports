#3620 · ACP catalog discards custom reasoning choices

Bug · Priority: Medium · Effort: High · providers · provider-acp

TL;DR

The catalog loses legal custom reasoning values. The source converts each advertised choice through a fixed table and discards values absent from that table. A custom-only option becomes an empty list, and the reverse map cannot select it. This was reproduced in two clean checkouts without contacting a provider; the live OpenCode catalog and picker were not verified.

Root cause

The forward and reverse tables recognize only fixed tokens. The conversion loop executes if (level === undefined) { continue; }. The fallback returns an empty list when the option exists but no values mapped. Discovery consumes this result, and selection uses the reverse map.

ACP accepts string option values, whereas the shared domain uses an eight-value enum. The limitation therefore extends beyond a missing display label.

Verification

The same agent repeated the harness in a second newly created detached checkout at the identical trusted commit. Both source trees remained clean. Both runs exited 1 at the same two-choice assertion, with identical mixed, custom-only, standard-control, and reverse-map results. No correction was needed. This is a repeated source-level check, not independent or end-to-end verification.

Proposed fix and simple-fix assessment

Preserve provider-native choice identity and display names through discovery and selection. This requires a shared contract change, or a product decision defining a reversible mapping onto the existing enum. An arbitrary alias would not solve the general string-value case. No production fix or PR was attempted because the rule excludes schema changes and product decisions. Normal package tests also remain blocked by the missing package manager.
