#6685 · Cached plan survives failed usage refresh

BugPriority: MediumEffort: Mediumprovidersprovider-claude-codeGitHub issue2026-10-30

Trusted base: 741decd0a145f5a8d982e014d16840575437a748. Verdict: PARTIALLY REPRODUCED · Root-cause confidence: medium (high for cached-label behavior; no evidence establishing subscription expiry as the trigger). Reproduction label: partial-repro.

1. TL;DR

A successful usage result can keep displaying a paid-plan badge after the next usage request fails. A synthetic HTTP 200 → 503 sequence reaches the real Claude maintenance code, its real usage-source adapter, the real provider-usage server cache, and the real settings renderer; the badge and percentages remain alongside a generic refresh warning. The plan label comes from local credential metadata, not an authoritative billing check. Keeping the last successful usage measurement is deliberate resilience behavior, but the display does not separately qualify the plan label as saved metadata. This investigation did not exercise a real subscription lapse or establish what Anthropic returns for one.

5. Root cause

  1. planLabel derives the badge from credential subscriptionType/rateLimitTier. normalizeUsage uses that label even though a successful usage response need not carry plan/entitlement data.
  2. getClaudeProviderHealth checks token presence/expiry, not paid subscription validity. getClaudeProviderUsage maps HTTP 401 to expired and other non-success HTTP responses to usage error, retaining known credential-derived metadata. None of that establishes an authoritative subscription-ended signal.
  3. The real usage source adapter returns the error measurement. fetchResource throws on status error before replacing the last successful measurement; the selected refresh loop marks the resource as failed.
  4. Machine assembly still emits the cached successful account object and assigns a machine-level refresh error. It loses the new error detail from the visible account data.
  5. ProviderUsageBlock renders the retained plan badge. Notice selection renders a generic last-update notice for the machine. The sidebar account renderer similarly uses usage.planLabel for successful retained measurements.

Key production excerpts (at the linked base commit):

const maxMatch = (credentials.rateLimitTier ?? "").match(/max_(\d+)x/u);
if (maxMatch) return `Max (${maxMatch[1]}x)`;

if (value.usage.status === "error")
  throw new Error("Usage could not be refreshed.");
measurements.set(key, { value, loadedAt: Date.now() });

Verified mechanism: credential-derived plan metadata travels inside a last-good usage snapshot; the refresh error is exposed only as generic machine-level state, so the displayed account has no separate plan-source or entitlement-freshness qualifier. This is not proof of a provider billing bug, a known subscription-ended response, or the actual cause of the reporter's refresh failure.

6. Proposed fix and simple-fix gate

Keep last-good usage resilience, but distinguish locally saved plan metadata from verified current entitlement. First obtain a redacted authoritative provider response for an actual lapsed subscription, and decide how plan provenance/freshness should be represented per account. Only consume an explicit subscription-ended signal if the provider contract supports one. An HTTP 403/429/503 or token expiration alone cannot safely be relabeled as a billing outcome.

No automatic PR: the actual entitlement transition was not reproduced, and selecting entitlement/provenance semantics requires provider evidence and a product/contract decision. That fails the no-product-decision simple-fix condition. No fix branch, production patch, new dependency, or push to the code repository was made. No open PR linked to this issue was found in timeline metadata or an open-PR search.
