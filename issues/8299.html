#8299 · Policy refusal recovery stops at the account-error classifier

BugHigh priorityMedium effortprovidersthreadsprovider-codex

GitHub issue · November 28, 2026 · trusted base b0ddaad731565d7e4de68d824120d802fc78f7d5

PARTIALLY REPRODUCED · Root-cause confidence: high for the missing recovery notification. The reported live model behavior remains unverified.

1. TL;DR

A terminal provider policy refusal reaches bb as a machine-readable policy error and a failed turn, but does not produce the separate recovery notification used for account problems. The bridge explicitly limits that notification to authentication and rate-limit errors. In two runs against the same trusted base, the recovery-hint regression failed while a check of policy metadata and the next turn passed. This supports the missing recovery signal, not the stronger claims that all typing is absent or bb makes subsequent messages impossible. No live model request, production instance, or user thread data was used.

import { tmpdir } from "node:os";
import { join } from "node:path";
import { afterEach, beforeEach, expect, it, vi } from "vitest";
import {
  BRIDGE_NOTIFICATION_METHODS,
  threadDeltaNotificationParamsSchema,
  type ThreadDelta,
} from "@get-bb/plugin-sdk/provider-bridge";
import {
  experimental_createBridgeJsonRpcTestHarness as createBridgeJsonRpcTestHarness,
  type BridgeJsonRpcTestHarness,
} from "@get-bb/plugin-sdk/provider-bridge/testing";
import { handleLine } from "./bridge.js";
import {
  FULL_ACCESS_SESSION_OPTIONS,
  stubFakeCodexAppServer,
} from "./fake-codex-app-server-harness.js";

const THREAD_ID = "thr_issue_8299";
const PROVIDER_THREAD_ID = "policy-repro-session";
const REFUSAL_MESSAGE = "Request declined by provider policy.";
let harness: BridgeJsonRpcTestHarness;
let workspaceDir: string;

function notifications(method: string): unknown[] {
  return harness.messages
    .filter((message) => message.method === method)
    .map((message) => message.params);
}

function deltas(): ThreadDelta[] {
  return notifications("thread/delta").flatMap(
    (params) => threadDeltaNotificationParamsSchema.parse(params).deltas,
  );
}

async function waitForBoundary(status: "failed" | "completed"): Promise<void> {
  await vi.waitFor(
    () => expect(deltas()).toContainEqual(expect.objectContaining({
      kind: "turn.boundary",
      status,
    })),
    { timeout: 10_000, interval: 20 },
  );
}

async function startTurn(requestId: number): Promise<void> {
  harness.sendRequest(requestId, "turn/start", {
    threadId: THREAD_ID,
    providerThreadId: PROVIDER_THREAD_ID,
    clientRequestId: requestId === 2 ? "creq_8299abcdef" : "creq_8299abcdeg",
    input: [{ type: "text", text: "Reply briefly.", mentions: [] }],
    options: { ...FULL_ACCESS_SESSION_OPTIONS },
  });
  expect((await harness.waitForResponse(requestId)).error).toBeUndefined();
}

beforeEach(async () => {
  workspaceDir = mkdtempSync(join(tmpdir(), "bb-policy-repro-"));
  const scriptPath = join(workspaceDir, "script.json");
  writeFileSync(scriptPath, JSON.stringify({
    turns: [
      [
        { method: "turn/started", params: {
          threadId: "x", turn: { id: "policy-turn", status: "inProgress" },

it("preserves policy error metadata and accepts the next turn", async () => {
  await startTurn(2);
  await waitForBoundary("failed");
  expect(deltas()).toContainEqual(expect.objectContaining({
    kind: "provider.error",

5. Root cause

The translator already recognizes the relevant provider code and preserves a typed policy category:

plugins/provider-codex/src/delta-translation.ts:683

      case "modelNotFound":
        return "bad-request";
      case "cyberPolicy":
      case "misalignmentPolicyViolation":
      case "tooManyDenials":
        return "policy";

The bridge delivers the translated deltas, then invokes the terminal account-error hint handler:

plugins/provider-codex/src/bridge/bridge.ts:791

  sendThreadDeltas(session, deltas);
  for (const delta of deltas) {
    if (delta.kind === "provider.error" && delta.willRetry !== true) {
      emitTerminalAccountErrorHint(session, delta);
    }
  }

That classifier returns no hint for any known category other than unauthorized or rate-limit. A policy category therefore exits before account-message fallback matching:

plugins/provider-codex/src/bridge/bridge.ts:340

function classifyTerminalAccountError(
  delta: Extract<ThreadDelta, { kind: "provider.error" }>,
): "authRequired" | "rateLimited" | null {
  const category = delta.errorInfo?.category;
  if (category === "unauthorized") {
    return "authRequired";
  }
  if (category === "rate-limit") {
    return "rateLimited";
  }
  if (category !== undefined && category !== "unknown") {
    return null;
  }

The caller exits without emitting provider/recovery and without setting the account-related rebuild flag:

plugins/provider-codex/src/bridge/bridge.ts:799

function emitTerminalAccountErrorHint(
  session: CodexBridgeSession,
  delta: Extract<ThreadDelta, { kind: "provider.error" }>,
): void {
  const kind = classifyTerminalAccountError(delta);
  if (kind === null) {
    return;
  }
  const message = delta.detail ?? delta.message;
  session.rebuildBeforeNextTurnReason =
    kind === "authRequired"
      ? "codex session restarted after an authentication failure so a new login can take effect."
      : "codex session restarted after a rate limit so a refreshed account state can take effect.";
  sendNotification(BRIDGE_NOTIFICATION_METHODS.providerRecovery, {
    threadId: session.bbThreadId,
    kind,
    message,
    retryable: false,
  });

This explains the notification gap, not a proven terminal session lockout. Normal failed completion is translated to turn.boundary with failed status; see completion translation. The canonical assembler also preserves typed error metadata; see provider.error assembly.

The existing UI has a policy-specific title rather than only a raw error label:

packages/thread-view/src/error-display.ts:19

  overloaded: "Provider overloaded",
  policy: "Provider policy blocked request",
  "rate-limit": "Provider rate limit reached",
  sandbox: "Provider sandbox error",
  "stream-disconnected": "Provider stream disconnected",

The recovery contract itself currently has no dedicated refusal variant:

packages/domain/src/provider-types.ts:146

export const providerRecoveryKindValues = [
  "sessionArchived",
  "authRequired",
  "restartRecommended",
  "staleTurn",
  "rateLimited",
] as const;
export const providerRecoveryKindSchema = z.enum(providerRecoveryKindValues);
export type ProviderRecoveryKind = z.infer<typeof providerRecoveryKindSchema>;

6. Proposed fix and safety assessment

Preserve errorInfo.category = policy and expose that existing signal to callers that need classification. A dedicated refusal recovery notification needs an explicit public contract and coordinated runtime/server/UI/orchestrator behavior; it must not masquerade as authentication or rate limiting. Do not automatically rephrase, retry, switch models, discard safety context, or reset sessions based solely on a refusal string.

The next diagnostic is a redacted event sequence showing whether the real provider sends cyberPolicy, only generic text, or a different failure path, together with the next turn's admission and terminal events. That distinguishes a presentation issue from provider behavior and transport termination.

No automatic pull request: the complete reported failure was only partially reproduced, and introducing a new refusal recovery kind changes a public schema/protocol and needs a product decision. Those changes are outside the simple-fix allowance. No linked open pull request was present in issue cross-reference metadata or an open-PR search at investigation time. No fix branch, production edit, dependency, or push to the application repository was made.
