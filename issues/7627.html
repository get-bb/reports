#7627 · Idle-session release waits for the sweep

Bug Priority: Medium Effort: Low host · 2026-11-16 · GitHub issue

Trusted base: da3e60b81d560e114a2bec724bb59c997aaaae7f

Verdict: REPRODUCED · Root-cause confidence: high

1. TL;DR

The host daemon checks idle provider sessions on a five-minute interval, rather than when an idle deadline arrives. Changing the timeout only changes the eligibility threshold supplied to that interval; zero does not request an immediate check. Two clean checkouts of trusted main produced the same deterministic scheduler trace: an eligibility deadline one millisecond after a sweep was not checked for another 299,999 milliseconds. This establishes the scheduling defect without using a real account or provider process; actual memory retention and the reporter's historical measurements were not measured. Existing configuration documentation already discloses the extra polling delay, despite also describing zero as ASAP.

5. Root cause

The interval constant is five minutes. The reaper has only one periodic trigger:

const timer = args.setIntervalFn(() => {
  if (running || timeoutMinutes === null) {
    return;
  }
  running = true;
  void args.runtimeManager
    .reapIdleProviderSessions({
      idleForMs: timeoutMinutes * 60_000,
      nowMs: args.nowMs(),
    })
    ...
}, IDLE_PROVIDER_SESSION_REAP_INTERVAL_MS);
...
setTimeoutMinutes(value) {
  timeoutMinutes = value;
}

The runtime records idle time when a turn completes or a non-retrying provider error arrives, and rejects candidates whose elapsed idle time is below the configured threshold. That bookkeeping does not itself schedule release. The daemon's runtime-event callback only forwards the event; it does not wake the reaper.

For a session idle from time 1 ms with a five-minute threshold, the 300,000 ms sweep sees only 299,999 ms of idleness and must reject it. The following sweep is at 600,000 ms. Zero still waits for the first sweep. This adds a polling-phase delay approaching five minutes under healthy scheduling; it is not a hard upper bound if the event loop or a sweep stalls.

The manager serializes release with thread control; the runtime retains active/pending, restorable-session, and background-work guards. Those safeguards explain why scheduling should be repaired without bypassing eligibility. The current documentation acknowledges polling delay.

6. Proposed fix

Arrange a host-local check when the actual runtime reports a turn has ended and an idle deadline is reached; zero should schedule a prompt check. Reuse the existing guarded manager pass, preserve per-thread serialization, re-arm on setting changes, avoid overlapping passes, and cancel local timers on shutdown. Retain a fallback sweep for sessions that become eligible without a normal completion event or remain busy at the first deadline. A landing regression should drive the daemon's real turn-ending event path and verify zero, positive deadlines, active-work protection, timeout updates, and shutdown.
