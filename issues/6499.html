#6499 · Shared acknowledgement outages expire host leases

Bug High priority Medium effort host connect perf · GitHub issue

Investigation completed October 29, 2026 · trusted main commit 0950d00f962029433790f9fed432c7061051a32e

PARTIALLY REPRODUCED · Root-cause confidence: medium · Reproduction label: partial-repro

1. TL;DR

A shared loss of server heartbeat replies can make otherwise responsive host clients reconnect together. Three real ServerConnection objects, using the repository's existing fake transport and controlled clock, all request reconnect at simulated time 35,000 ms during a 32-second acknowledgement blackout. Two shorter-blackout controls pass. This demonstrates the host lease mechanism, not the original server CPU stall, real daemon processes, Cloudflare resets, or 502/503/504 responses. The tunnel client already has separate stall grace; keeping that tunnel alive does not renew acknowledgements at remote hosts.

5. Root cause

Verified narrow mechanism: server constants advertise a 5-second heartbeat interval and a 30-second lease. The server message handler runs on the origin's event loop, updates session state, and sends the acknowledgement. If that loop cannot run, the replies cannot be produced by this handler.

The daemon's delayed-local-tick grace only applies when its own timer is delayed beyond the lease. A stalled origin does not delay a remote host's timer. The remote client's acknowledgement-age check therefore reaches:

if (
  lastAcknowledgedAt !== null &&
  now - lastAcknowledgedAt > session.leaseTimeoutMs
) {
  this.clearHeartbeat();
  this.websocket.reconnect(1013, "heartbeat-ack-timeout");
  return;
}

The excerpt omits only existing diagnostic logging. This is intentional current behavior, independently covered by the existing expiry test. A shared outage aligns expiry across hosts whose last acknowledgements are aligned; perfectly simultaneous disconnects are not guaranteed for every possible connection phase.

Separate tunnel mechanism: the tunnel constants use a 20-second heartbeat and 60-second deadline. Its late-tick grace restarts that tunnel's local deadline once until another acknowledgement arrives. This does not extend the daemon's lease. The existing 90-second-stall coverage passes. Separately, tunnel teardown abandons visitor streams, so a real tunnel transport loss has its own fan-out path.

Unresolved underlying cause: this investigation did not identify the production work that blocked the origin, reproduce a Cloudflare transport reset, or demonstrate that the same cause explains every reported disconnect reason. Overall confidence is medium; confidence in the host lease-expiry mechanism is high.

6. Proposed fix / next experiment

No automatic production fix is safe from this evidence alone. Increasing the advertised lease changes server/daemon wire-field meaning and failure-detection policy; coordinating that with tunnel deadlines crosses subsystems. A healthy remote client cannot distinguish a dead server from a server that has stopped replying using only these heartbeat messages. An arbitrary grace period would trade reconnect storms for delayed detection and requires a deliberate liveness budget, not a cosmetic timeout increase.

Next, use an isolated local multi-process setup with separate origin and daemon event loops. Reproduce a controlled 32-second origin block while the transport remains intact, capture each layer's monotonic heartbeat ages, then separately inject a tunnel reset. Profile the origin workload that produces the real stall. Keep actual-dead-peer and local-suspension regressions alongside any future resilience test. This report's failing test is a candidate acceptance test once that policy is chosen, not proof that deleting the existing expiry check is correct.
