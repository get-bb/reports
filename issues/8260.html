#8260 · ACP extension compaction notifications are discarded

BugLow priorityEffort: Mediumproviders · provider-acp · partial-repro GitHub issue2026-11-26base b0ddaad731565d7e4de68d824120d802fc78f7d5

Verdict: PARTIALLY REPRODUCED · Root-cause confidence: medium

1. TL;DR

The issue reports context shrinking without a compaction entry for a custom ACP agent. The provider bridge really does discard top-level notifications that are not session/update. An authored process-boundary reproduction replays the reported notification shapes through the repository's synthetic ACP peer: the standard control produces one compaction event, while the extension variant produces none. The same result repeats from a second clean checkout of trusted main. This establishes the transport gap, not whether the actual agent emits those notifications during automatic compaction: no vendor binary, authenticated session, long-context run, or live UI was exercised.

5. Root cause

The ACP notification handler returns for every method other than session/update, so reported top-level compaction notifications cannot reach compaction tracking or timeline translation. The handler is connected directly to incoming peer notifications in bridge.ts:2460–2474. Its method gate runs before any parsing or dialect normalization:

if (method !== "session/update") {
  return;
}

Method gate at the recorded commit. Valid standard session updates are then parsed as compaction updates, tracked, and emitted in bridge.ts:3806–3827. trackAgentCompaction deduplicates standard compaction identities and opens an agent turn when needed. The delta translator dispatches standard compaction updates. None of those paths can see a notification discarded at the method gate.

Confidence is high in that exact code mechanism and medium in the complete reported cause, because the upstream automatic-compaction emission has not been observed here. The report does not diagnose a UI rendering or token-accounting bug. There is no screenshot because this verification targets the provider-event boundary rather than claiming a live visual reproduction.

6. Proposed fix and automation decision

First capture automatic-compaction notifications from the actual agent. If the reported shape is confirmed and vendor support is intended, normalize a validated, dialect-scoped notification into the existing compaction pipeline, with identity, session scoping, and manual-echo deduplication tests. Do not infer compaction solely from a usage drop. Specify handling for malformed and wrong-session payloads, repeated terminal events, notifications after a manual prompt has ended, loading/stopping sessions, and coexistence with future standard updates.

No fix PR is safe in this run. The requested automatic-compaction bug is only partially reproduced. A vendor-specific production change would assume an unverified upstream automatic-notification contract. The automation's reproduced-on-trusted-main prerequisite is therefore not satisfied for that end-to-end claim. No production files, branch, dependency, protocol, stored data, or release behavior were changed; only disposable reproduction tests and published artifacts were created.
