#8170 · Codex event scans persist an unchanged cursor

BugPriority: LowEffort: Lowproviders · provider-codex · perfGitHub issue

2026-11-25 · trusted origin/main fb045a046653cc127656ca3c7243d44ae4c94f3f

Verdict: REPRODUCED · Root-cause confidence: high · reproduction label: confirmed-repro

1. TL;DR

The Codex plugin checks for asynchronous questions when a Codex thread receives an event notification. Even when that check returns no matching rows, it writes the same cursor to plugin storage. A reproduction built from repository evidence connects this handler to the real migrated SQLite database and records three row mutations for three empty scans. Both an absent cursor and an already stored cursor reproduce the defect in two clean checkouts. No user-visible delay, live Codex session, disk-WAL volume, or microsecond performance claim was measured.

5. Root cause

The async-question reader unconditionally persists its cursor after scanning, including when no extension-state rows advanced it. plugins/provider-codex/src/async-questions.ts:44 loads the persisted cursor, advances it only while iterating returned rows, then always sets it. With an empty page, the final value is exactly the loaded value (or zero for absence).

let cursor = (await bb.storage.kv.get<number>(cursorKey(threadId))) ?? 0;
...
for (const row of page) {
  cursor = Math.max(cursor, row.seq);
  ...
}
...
await bb.storage.kv.set(cursorKey(threadId), cursor);

plugins/provider-codex/src/async-questions.ts:109 registers this work on every Codex thread-event notification. apps/server/src/services/plugins/plugin-api.ts:739 serializes the value and synchronously calls the database setter. packages/db/src/data/plugin-storage.ts:33 executes an INSERT with conflict-update of value and updatedAt. There is no downstream no-op guard, so the unconditional plugin call produces real row mutations. The per-thread promise queue serializes the scans; it does not deduplicate their writes.

6. Proposed fix from first principles

Retain the cursor loaded at entry and persist only when the final scanned cursor is greater; preserve pagination and advancement for all scanned extension-state rows. Do not change the shared storage setter: callers elsewhere may intentionally depend on timestamp updates. Retain question delivery, pagination, cleanup on thread deletion, and serial execution. Follow-up coverage should include non-question extension rows that still advance the cursor and an exact full-page scan followed by an empty page.
