#8058 · Workflow selection skips per-model reasoning discovery

BugPriority: MediumEffort: Mediumproviders · provider-acp · workflowsGitHub issue

November 23, 2026 · trusted origin/main commit 02239e9e373fe8a74a75f91afbfb06016ed5a1ef

Verdict: REPRODUCED at the workflow plugin boundary · Root-cause confidence: high · reproduction label: confirmed-repro.

1. TL;DR

A workflow consults a model catalog before choosing a worker's reasoning level. When that catalog has not discovered a model's reasoning capabilities yet, the workflow treats the missing list as if discovery had already completed. An explicit high setting is rejected, while an inherited high setting launches a worker at the medium default without an error. Three focused regression cases reproduce these outcomes on trusted main in two separate clean checkouts; three corresponding pre-discovered catalog controls pass in each. This is a real workflow policy failure reproduced with an SDK transport fixture, not a claim that a live ACP process or the reporter's desktop environment was exercised.

5. Root cause

  1. packages/provider-bridge-acp/src/bridge/model-catalog.ts:180-L200 gives undiscovered models reasoningDiscovery: "unknown", no supported levels, and default medium. That is meaningful pending state, not evidence of no reasoning support.
  2. apps/server/src/services/providers/provider-model-catalog-store.ts:818-L829 only requests per-model refinement when selectedModel is present. apps/server/src/services/providers/provider-model-catalog-store.ts:631-L644 skips already-known models. apps/app/src/hooks/useThreadCreationOptions.ts:621-L629 supplies this field for an unknown selected model.
  3. plugins/workflows/src/workflow-input.ts:40-L49 calls the SDK without a selected model. plugins/workflows/src/workflow-validation.ts:58-L89 uses that catalog directly to reject unsupported literal levels.
  4. plugins/workflows/src/service.ts:740-L794 likewise loads only the provider catalog before resolving the worker's level, so neither explicit nor inherited runtime selection causes refinement.
  5. plugins/workflows/src/reasoning-selection.ts:7-L29 returns the default unconditionally for an unmatched inherited request, including unknown discovery, and returns null for an explicit unknown request. That directly explains both observed outcomes.
  6. packages/sdk/src/areas/providers.ts:22-L31 omits selectedModel from ProviderModelsArgs, although packages/sdk/src/areas/common.ts:19-L38 already forwards this query field internally. A correctly typed caller therefore needs the SDK argument exposed as well as the workflow discovery call.
Workflow unknown catalog → no selected-model refinement
  explicit high → no supported-level match → reject
  inherited high → no supported-level match → default medium
Workflow known catalog containing high → supported-level match → high

The wrong boundary decision is treating a not-yet-discovered list as authoritative. The regression checks observable validation, run failure, and worker spawn behavior rather than merely checking private helper calls.

6. Proposed fix

Expose the already-supported selected-model query in the SDK argument type, and have both workflow source validation and runtime selection request per-model refinement when discovery is unknown before applying supported-level checks. Reuse a shared workflow-level lookup to keep both paths consistent. Retain the existing known-empty native-default policy and unsupported-level checks. Decide and test what happens if refinement fails or remains unknown, rather than assuming that an empty pending catalog proves high is unsupported.

No production fix, branch, commit, or new pull request was created: an existing open pull request already closes this issue. The only source changes here are local reproduction tests.
