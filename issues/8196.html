1. TL;DR

The report describes a native automation tap missing a send button while the software keyboard changes the page geometry. Trusted main does place its animation wait before text entry in both send flows, then taps Submit without another explicit keyboard-readiness barrier. The shared launch helper stops the app but does not explicitly clear its state, and web drafts are stored by project and thread. Those facts make the timing and draft-reuse explanation plausible, but they do not prove a missed native tap. This Linux host has neither Xcode Simulator nor Maestro, so no native reproduction, screenshot, coordinate trace, or mixed-message send was obtained.

5. Root cause: observed preconditions, unverified mechanism

apps/mobile/e2e/flows/shell-send.yaml:55 places a 5-second animation-wait timeout before inputText and then taps the Submit text selector. apps/mobile/e2e/flows/shell-send-sidebar-swipe.yaml:33 uses the same ordering. A wait before typing does not itself establish keyboard readiness after typing. However, it may already settle the keyboard on some devices; the source alone cannot establish when native animation begins or how Maestro resolves tap coordinates.

apps/app/src/components/layout/useMobileVisualViewportHeight.ts:72 changes the shell height in response to visual viewport changes, so layout can change as keyboard visibility changes. That is normal UI behavior, not independently a product bug. No evidence here proves that Maestro actually reads stale bounds.

For the secondary claim, apps/app/src/hooks/usePromptDraftStorage.ts:86 writes non-empty drafts to localStorage and apps/app/src/hooks/usePromptDraftStorage.ts:229 reuses a project/thread key. The launch helper in apps/mobile/e2e/subflows/launch-app.yaml:15 cold-starts without an explicit app-data reset. This explains why stale draft reuse is possible in principle; native WebView persistence across the two runs and the combined outgoing message were not exercised.

Hypothesis: the automation lacks a post-input native-readiness barrier and fresh-state isolation. Confidence in this being the actual timeout cause remains low until a native trace supports it. There is no verified production root cause in this report.

6. Proposed next experiment

Run pristine main on an iOS simulator with a software keyboard enabled. Record the keyboard and accessible Submit geometry before and after text entry, then require the exact provider echo for a unique message. Repeat from a second clean simulator state. If the missed tap is observed, compare an explicit post-input keyboard/animation barrier and state reset, without changing product draft-persistence behavior. Measure that this repairs the failing run rather than merely delaying it.

No patch is proposed for merging from this investigation: the native failure has not been reproduced here and an open linked PR already owns the candidate fix.
