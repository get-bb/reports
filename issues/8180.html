#8180 · CLI read waterfalls and duplicate environment lookup

Bug Priority: Medium Effort: Medium cli perf

Issue #8180 · November 25, 2026 · Base fb045a046653cc127656ca3c7243d44ae4c94f3f

REPRODUCED · Root-cause confidence: high · Reproduction label: confirmed-repro

1. TL;DR

CLI context commands pay for successive network round trips even when several reads could run together. An HTTP fixture delaying every response by 100 ms shows six request rounds for status, four for text thread show, and five for JSON thread show. JSON thread inspection fetches the same environment twice. Both behaviors repeat in a second clean checkout of trusted main with a new listener and temporary home. This establishes scheduling and reuse defects without contacting a real user server.

3. Environment

  • Two separate clean clones of public get-bb/bb, both at fb045a046653cc127656ca3c7243d44ae4c94f3f, fetched from trusted origin/main. Main was fetched again and had not advanced.
  • Linux 4.19.0-gvisor; Node v22.19.0; pnpm 9.15.0. Frozen dependency installs and Turbo CLI builds succeeded in both clones.
  • Three samples per command per checkout, plus one assertion-mode sample per command in each checkout. Timing includes CLI startup; every HTTP response waits 100 ms.
  • A fixture-only HTTP listener binds atomically to 127.0.0.1:0. Each invocation gets a new OS-selected port and a new temporary home/data directory. No real bb server, database, enrolled machine, provider session, credential or production data is involved.
  • The probe closes its listener and deletes its scratch directory in finally. Checkout paths and ephemeral directory identifiers are omitted under this site's privacy policy; the separate clones are called A and B.

5. Root cause

CLI status serializes independent layers

status.ts:85–137 awaits configuration, then plugins, then SDK context, then environment display. Configuration gates presentation and failure handling but is not an input to plugin or context reads. This abbreviated excerpt preserves the await order; the link contains the complete guards and arguments:

const response = await cliFetch(`${getUrl()}/api/v1/system/config`);
const { plugins } = await createCliBbSdk(getUrl()).plugins.list();
const status = await sdk.status.get({ projectId: context.projectId, threadId: context.threadId });
environmentInfo = await fetchEnvironmentInfo({ environmentId: status.thread.environmentId, sdk });

The SDK adds another serial edge

SDK status.ts:77–130 already overlaps project and thread reads, but then awaits head-state before listing child threads. Both need only the known thread ID. Combined with the CLI, the request chain is configuration → plugins → project/thread → head-state → children → environment: six rounds and seven requests.

Thread inspection serializes annotations and bypasses its cache

show.ts:382–409 awaits pull-request lookup, environment display and pending items in sequence, after their inputs are already known. JSON then calls getEnvironment().

const fetchedPullRequest = thread.environmentId ? await fetchPullRequest(...) : null;
const environmentInfo = thread.environmentId ? await fetchEnvironmentInfo(...) : null;
const pendingTodos = await fetchThreadPendingTodos({ sdk, threadId });
if (opts.json) {
  const environment = await getEnvironment();
}

environment-helpers.ts:37–55 performs its own sdk.environments.get, while show.ts:283–295 caches only reads made through the local getter. The display helper does not fill that cache, so ordinary JSON mode reads the same resource again. Separate ownership of environment reads is the underlying reuse defect.

6. Proposed fix

Start configuration, plugins and context reads together, then consume their results while preserving existing output/error-selection rules. Fetch SDK head-state and children together once the thread is known. For thread inspection, share one environment read between display and JSON, and overlap pull-request, pending-item and environment reads. Cover absent resources, failed configuration and failed annotation reads so concurrency does not silently change graceful fallback or error precedence.

No production fix was attempted: open PR #8181 already has a closing reference to this issue. Opening another would violate the duplicate-fix guard.
