#7090 · Windows hosts cannot pass Browser Automation runtime preparation

BugPriority: MediumEffort: Highpluginsdesktop Issue #70902026-11-05 · base 2d912ea09011708b6a331c1ee7a15bea6ad32970

Verdict: REPRODUCED — deterministic host runtime rejection, repeated in two clean trusted checkouts. Root-cause confidence: high.

Scope: Linux-hosted tests supply the exact native Windows platform identifiers to the real host entry and resolver. No Windows machine, Electron desktop, CLI transport, or actual browser connection was launched. Native Windows end-to-end behavior remains untested.

1. TL;DR

Browser Automation cannot prepare its execution runtime when the selected host reports Windows x64. Its installer accepts only Linux and macOS platform identifiers, so the real runtime resolver throws before any artifact download or browser process starts. Both local headless opening and opening with an existing desktop WebSocket endpoint take this same runtime path. The pinned upstream release also lists only Linux and macOS executables, so removing the platform guard alone would not produce a working Windows runtime. The desktop connection is a transport endpoint, not a replacement JavaScript execution engine.

5. Root cause

The platform boundary is an explicit four-value enum. currentPlatform() validates process.platform and process.arch against it, returning null for Windows.

export type RuntimePlatform = (typeof runtimePlatforms)[number];
const platformSchema = z.enum(runtimePlatforms);

export interface RuntimeRelease {
  readonly package: string;
  readonly version: string;
  readonly registry: string;
  readonly repository: string;

plugins/browser-automation/installer.ts:66

export function currentPlatform(): RuntimePlatform | null {
  const parsed = platformSchema.safeParse(
    `${process.platform}-${process.arch}`,
  );
  return parsed.success ? parsed.data : null;
}

resolveRuntime() immediately rejects null. This happens before installRuntime(), so a desktop tab being present cannot make the host eligible.

6. Proposed fix and simple-fix decision

A runtime-based solution requires an upstream Windows build, verified Windows artifact pinning and installation/execution support, followed by native Windows tests for both backends. A fallback that does not use DevBrowser would instead require a new execution implementation while preserving the existing browser-control leases, endpoint restrictions, ownership, script/session behavior and preview lifecycle. Neither is an allowlist-only repair.

No pull request: Windows runtime packaging or a replacement execution backend is outside the authorized simple-fix conditions. The former changes packaging/release work; the latter needs product/architecture and security-boundary decisions. No production patch or fix branch was created or pushed. The focused availability assertion fails on unchanged main, but no valid post-fix pass can be claimed.

Read-only issue timeline, closing-PR references and open-PR search found no linked open pull request at investigation time. No pull request code was checked out.
