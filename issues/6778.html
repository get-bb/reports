#6778 · Thread attachment size validation and upstream error messages

BugPriority: MediumEffort: LowuiGitHub issue

2026-11-01 · trusted main 916d684ac23d0b0de82c09cfc7553a50287d2188

Verdict: PARTIALLY REPRODUCED · Root-cause confidence: high for the tested composer behavior; the original ingress failure remains unverified.

1. TL;DR

The existing-thread composer uploads files without first checking their size. When an upstream service rejects an upload with only a generic HTTP 413 reason, the composer has no attachment-specific explanation. Both behaviors reproduce at the actual composer upload-function boundary in two clean checkouts of trusted main. However, main already preserves descriptive server errors and uses a shared 35 MiB limit for images and other files; the older limits in the report do not describe this base. This investigation did not send the original video through a live relay and does not identify which ingress generated that user's 413.

import { describe, expect, it, vi } from "vitest";
import type { PromptDraftAttachment } from "@bb/client-core";
import { BbHttpError } from "@bb/sdk/browser";
import { PROMPT_ATTACHMENT_MAX_BYTES } from "@bb/domain";
import { uploadDraftAttachments } from "./useComposerAttachmentUploads";

const uploaded: PromptDraftAttachment = {
  type: "localFile",
  path: "uploads/old.txt",
  name: "old.txt",
  sizeBytes: 3,
};

function pending(name: string) {
  return { id: name, file: new File([name], name) };
}

describe("uploadDraftAttachments", () => {
  it.each(["video/mp4", "image/png"])(
    "rejects an oversized %s before upload and still attaches a valid file",
    async (mimeType) => {
      const file = new File(
        [new Uint8Array(PROMPT_ATTACHMENT_MAX_BYTES + 1)],
        "large-attachment",
        { type: mimeType },
      );
      const upload = vi.fn(async () => uploaded);
      const addAttachment = vi.fn();
      const settled = vi.fn();
      const target = { key: "bottom", addAttachment };

      const result = await uploadDraftAttachments({
        uploads: [{ id: "large", file }, pending("old.txt")],
        target,
        upload,
        getCurrentTarget: () => target,
        onUploadSettled: settled,
      });

      expect(upload).toHaveBeenCalledTimes(1);
      expect(upload).toHaveBeenCalledWith(expect.objectContaining({ name: "old.txt" }));
      expect(result.added).toEqual([uploaded]);
      expect(addAttachment).toHaveBeenCalledTimes(1);
      expect(settled).toHaveBeenCalledTimes(2);
      expect(result.failureMessage).toContain("large-attachment is 35.1 MB");
      expect(result.failureMessage).toContain("35 MB attachment limit");
    },
  );

  it.each(["", "Payload Too Large", "413"])(
    "explains an upstream 413 with generic reason %j",
    async (message) => {
      const upload = vi.fn(async () => {
        throw new BbHttpError({ body: null, code: null, message, status: 413 });
      });
      const target = { key: "bottom", addAttachment: vi.fn() };
      const result = await uploadDraftAttachments({
        uploads: [pending("clip.mp4")],
        target,
        upload,
        getCurrentTarget: () => target,
        onUploadSettled: vi.fn(),
      });

      expect(result.added).toEqual([]);
      expect(target.addAttachment).not.toHaveBeenCalled();
      expect(result.failureMessage).toContain("Upload rejected as too large");
      expect(result.failureMessage).toContain("35 MB");
    },
  );

  it("adds a late upload to the draft it started in after the composer moves to another draft", async () => {
    const addToThreadA = vi.fn();
    const addToThreadB = vi.fn();
    const threadA = { key: "thread-a", addAttachment: addToThreadA };
    let currentTarget = threadA;
    const settled: string[] = [];

    const result = await uploadDraftAttachments({
      uploads: [pending("old.txt")],
      target: threadA,
      upload: async () => {
        currentTarget = { key: "thread-b", addAttachment: addToThreadB };
        return uploaded;
      },
      getCurrentTarget: () => currentTarget,
      onUploadSettled: (upload) => settled.push(upload.id),
    });

    expect(result).toEqual({ added: [], failureMessage: null });
    expect(addToThreadA).toHaveBeenCalledWith(uploaded);
    expect(addToThreadB).not.toHaveBeenCalled();
    expect(settled).toEqual(["old.txt"]);
  });

  it("adds uploads to the target that is still current", async () => {
    const addAttachment = vi.fn();

    const result = await uploadDraftAttachments({
      uploads: [pending("old.txt")],
      target: { key: "bottom", addAttachment },
      upload: async () => uploaded,
      getCurrentTarget: () => ({ key: "bottom", addAttachment }),
      onUploadSettled: vi.fn(),
    });

    expect(result.added).toEqual([uploaded]);
    expect(addAttachment).toHaveBeenCalledWith(uploaded);
  });

  it("shows the server's reason when it refuses an upload", async () => {
    const message =
      "HEIC images are not supported. Convert the image to JPEG or PNG before attaching it.";
    const upload = vi
      .fn<(file: File) => Promise<PromptDraftAttachment>>()
      .mockRejectedValueOnce(
        new BbHttpError({
          body: { code: "invalid_request", message },
          code: "invalid_request",
          message,
          status: 400,
        }),
      )
      .mockRejectedValueOnce(new TypeError("Failed to fetch"));

    const result = await uploadDraftAttachments({
      uploads: [pending("IMG_0001.heic"), pending("shot.png")],
      target: { key: "bottom", addAttachment: vi.fn() },
      upload,
      getCurrentTarget: () => ({ key: "bottom", addAttachment: vi.fn() }),
      onUploadSettled: vi.fn(),
    });

    expect(result.failureMessage).toBe(
      `Failed to attach IMG_0001.heic, shot.png: ${message}`,
    );
  });

  it("names failed files without a reason when the failure is not a server refusal", async () => {
    const result = await uploadDraftAttachments({
      uploads: [pending("inline.txt")],
      target: { key: "bottom", addAttachment: vi.fn() },
      upload: async () => {
        throw new Error("inline failed");
      },
      getCurrentTarget: () => ({ key: "bottom", addAttachment: vi.fn() }),
      onUploadSettled: vi.fn(),
    });

    expect(result.failureMessage).toBe("Failed to attach: inline.txt");
  });

5. Root cause

The composer upload loop invokes upload(pendingUpload.file) unconditionally. Neither its pending-upload staging nor the shared mutation checks size before invoking the SDK. Consequently, even a file that exceeds the server's known limit consumes upload bandwidth and can hit a proxy rejection first.

Rejection formatting delegates every SDK HTTP error to the general mutation formatter. There is no special case for a generic 413. The SDK error reader deliberately uses status text for an empty body or HTML error, but preserves a useful JSON message. This is why a generic upstream refusal provides little guidance, while a descriptive application error already works.

The shared limit is 35 MiB. The server validation rejects oversize uploads with HTTP 400 and a descriptive envelope. The original 413 therefore cannot be attributed to that current validation branch alone. History records the shared-limit change in commit 76ae202c87 (PR #4046); no historic branch was executed.

6. Proposed fix

Keep the change inside the existing-thread composer upload subsystem: compare each file's size with the domain constant before invoking upload, collect a filename/actual-size/limit explanation, and continue processing valid files. Retain existing upload settlement and draft targeting. Preserve detailed server reasons; add a helpful fallback only for generic 413 responses, acknowledging that a proxy may impose a smaller limit. Do not change server protocols, SDK schemas, relay policy, storage, or the distinct task-attachment subsystem.

A local candidate implements this in the upload module and its existing test file. The initial focused post-fix check passed all 21 tests across upload behavior, pending upload lifecycle, and mutation error messages. The expanded run passed 86 tests in five files, including existing plugin/new-thread composer and queued-edit tests. Turbo app build, typecheck, and lint passed (lint reports warnings in existing files, with zero errors). The candidate changes 165 text lines in two files (134 additions + 31 deletions), with no binary or generated changes; git diff --check passed.
