#5204 · Personal child placement overrides an explicit machine

BugPriority: MediumEffort: Lowworkspaces, cli, confirmed-reproIssue on GitHubOctober 8, 2026

Trusted base: f135a001e72942cee9118d2693208ec0725e2f18 · Verdict: REPRODUCED · Root-cause confidence: high

1. TL;DR

A personal child thread can select a different execution machine yet still receive its parent's environment. The server's personal-child default policy returns a reuse decision before examining the requested machine. Both the host/personal request used by the CLI and an explicit personal-workspace provider request lose their machine selection. A regression at the owning server-policy boundary fails in the same three scenarios in two clean checkouts of main. This investigation verifies the placement decision, not an actual macOS-to-Windows agent session.

5. Root cause

apps/server/src/services/threads/thread-default-policy.ts:133 recognizes project-default, host/personal, and personal-workspace provider requests without considering their machine selection:

function isPersonalWorkspaceEnvironment(
  environment: CreateThreadEnvironment,
): boolean {
  return (
    environment.type === "project-default" ||
    (environment.type === "host" &&
      environment.workspace.type === "personal") ||
    (environment.type === "provider" &&
      environment.environmentProviderId ===
        DEFAULT_ENVIRONMENT_PROVIDER_ID.personalWorkspace)
  );
}

apps/server/src/services/threads/thread-default-policy.ts:314 unconditionally replaces those requests with reuse when parent and child are live Personal-project threads:

export async function resolveCreateThreadEnvironment(
  deps: WorkSessionDeps,
  args: ResolveCreateThreadEnvironmentArgs,
): Promise<ResolvedCreateThreadEnvironment> {
  const parentThread = args.parentThread;
  const hasLiveParent = isLiveParentThread({ parentThread });
  if (
    hasLiveParent &&
    parentThread?.projectId === PERSONAL_PROJECT_ID &&
    args.projectId === PERSONAL_PROJECT_ID &&
    isPersonalWorkspaceEnvironment(args.requestedEnvironment)
  ) {
    if (!parentThread.environmentId) {
      throw new Error("Personal parent thread is missing an environment");
    }
    return { type: "reuse", environmentId: parentThread.environmentId };
  }

The parent environment's host is never looked up or compared. This is not a host-daemon or provider execution failure: the placement intent has already lost the machine by the time it reaches those layers.

  • apps/cli/src/commands/thread/spawn.ts:149 shows how a personal host request carries hostId; apps/cli/src/commands/thread/spawn.ts:512 shows machine resolution and request construction.
  • apps/server/src/services/threads/thread-create.ts:645 routes actual thread creation through this policy.
  • apps/server/src/services/threads/thread-request-eligibility.ts:120 resolves an unreplaced personal host request to its selected host.
  • apps/server/src/services/threads/thread-environment-placement.ts:583 provisions a personal workspace using that resolved host. The existing provider path preserves its supplied machine selection.

Repository history attributes the current shared predicate and personal reuse block to commit 5f558957aa (September 8, 2026). This is supporting history only; the two failures on the current trusted base establish the defect.

6. Proposed fix (first principles)

Normalize only the requested machine selection inside the existing personal-child reuse block. Reuse when the request has no machine selection, or selects an existing host equal to the stored parent environment's hostId. Otherwise, including a request to create a new machine, fall through to the existing placement implementation. No CLI flags, public schemas, database storage, provider API, or server/daemon wire fields need to change.

The focused regression covers the credible risk: machine choice being silently discarded during default resolution. The existing coverage only tested reuse with a nonexistent environment ID and did not seed a parent environment on a distinct host. Updating that table with a real stored environment is sufficient; no production seam is needed.

Local fixed-code verification: Tests 137 passed (137). See the pull request for final verification commands and the change count; the report verdict itself is based on unchanged production code.
