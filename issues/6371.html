#6371 · Cross-bundle long-press ownership is not shared

Bug Priority: Medium Effort: Low ui · mobile · GitHub issue · October 27, 2026

Trusted base: b6743a36bd9eae1408c35cfc2c7ab1d2419dc79d (origin/main).

Verdict: REPRODUCED at the production component boundary · Root-cause confidence: high.

1. TL;DR

A touch press inside nested action menus should open only the innermost menu. The production component instead opens both menus when the outer and inner instances come from separately evaluated module copies. A module-local event claim is invisible to the other copy, so both timers expire and both open callbacks fire. The sidebar composes the host thread menu inside the plugin project menu, which supplies this module arrangement. The same regression failed in two clean trusted checkouts; the ten existing tests still pass. This is a DOM/component reproduction, not a verified physical iPhone recording.

// @vitest-environment jsdom

import { act, cleanup, fireEvent, render, screen } from "@testing-library/react";
import { afterEach, describe, expect, it, vi } from "vitest";
import { CompactViewportOverrideProvider } from "@bb/shared-ui/hooks/use-compact-viewport";
import { CompactLongPressMenu } from "@bb/shared-ui/compact-long-press-menu";
import { CompactLongPressMenu as BundledMenu } from "../../../../../packages/shared-ui/src/components/ui/compact-long-press-menu-repro-copy";
import { DropdownMenuItem } from "@bb/shared-ui/dropdown-menu";

afterEach(() => {
  cleanup();
  vi.useRealTimers();
});

describe("nested touch-menu ownership across bundle boundaries", () => {
  it.each([
    ["same module", CompactLongPressMenu],
    ["separately evaluated module", BundledMenu],
  ] as const)("opens only the inner drawer: %s", (_name, ProjectMenu) => {
    vi.useFakeTimers();
    const threadOpened = vi.fn();
    const projectOpened = vi.fn();
    render(
      <CompactViewportOverrideProvider isCompactViewport>
        <ProjectMenu
          label="Project actions"
          items={<DropdownMenuItem>Project settings</DropdownMenuItem>}
          onOpenChange={projectOpened}
        >
          <section>
            <CompactLongPressMenu
              label="Thread actions"
              items={<DropdownMenuItem>Pin thread</DropdownMenuItem>}
              onOpenChange={threadOpened}
            >
              <button type="button">Reproduction thread</button>
            </CompactLongPressMenu>
          </section>
        </ProjectMenu>
      </CompactViewportOverrideProvider>,
    );
    fireEvent.pointerDown(screen.getByRole("button", { name: "Reproduction thread" }), {
      pointerId: 17,
      pointerType: "touch",
      isPrimary: true,
      clientX: 60,
      clientY: 100,
    });
    act(() => vi.advanceTimersByTime(800));
    expect(threadOpened).toHaveBeenCalledWith(true);
    expect(projectOpened).not.toHaveBeenCalled();
  });
});

5. Root cause


The event claim WeakSet is owned by each evaluated module. The pointerdown handler checks and writes only that set, then starts a timer. An inner handler claims the event in its own set, but the bubbling outer handler consults a different empty set. Both schedule a long press. The timer opens state and invokes the externally visible onOpenChange callback.


const claimedPressEvents = new WeakSet<Event>();
if (claimedPressEvents.has(event.nativeEvent)) {
  return;
}
claimedPressEvents.add(event.nativeEvent);


The real composition is supported by the thread row SDK import, the host SDK binding, and the host compact thread wrapper. The project wrapper uses the plugin-imported CompactLongPressMenu. The build runtime-sharing allowlist does not include this module; sharing a source file does not imply shared runtime state across bundles.


The contextmenu handler separately checks event.defaultPrevented. This reproduction does not send that event. The existing nested-menu test imports a single component instance, explaining why it passes despite the bundle-boundary bug.


6. Proposed fix


Make press ownership live on the shared native event, rather than in a per-module collection, using a stable cross-bundle key. Keep current bubbling, cancellation, drag guards, click suppression, and release handling intact. Retain coverage for both same-module and separately evaluated menu instances. A desktop context menu or broad stopPropagation workaround would not repair this ownership contract.
