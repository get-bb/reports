#8002 · Pending mention searches outlive their response timeout

BugHigh priorityEffort: Lowplugins · perf · partial-repro GitHub issue2026-11-22 · base 35a03bbbb3f4d8dc814c1a152db5a463102b4250

Verdict: PARTIALLY REPRODUCED · Root-cause confidence: high for the search-accumulation mechanism.

1. TL;DR

A mention search can stop waiting for a plugin without stopping that plugin's work. The next search then calls the same registration again, even when the previous operation has not settled. Two clean trusted checkouts demonstrated six outstanding invocations after six search requests, where one would bound the outstanding work. A small registration-scoped guard prevents this accumulation, preserves healthy providers on subsequent requests, and permits another search after either fulfillment or rejection. This test does not recreate a macOS authorization stall or prove filesystem-worker exhaustion, so the overall incident is only partially reproduced.

5. Root cause

The mention search route calls the service on every request. The service loop invokes every matching registration without retaining its pending-operation state across requests:

        for (const record of [...plugin.handle.mentionProviders]) {
          if (!record.triggers.includes(args.trigger)) continue;
          tasks.push(
            (async () => {
              const outcome = await invokeWrapped(
                plugin,
                `mention search ${record.id}`,
                async () => {
                  const searchPromise = (async () =>
                    record.search({
                      trigger: args.trigger,
                      query: args.query,
                      projectId: args.projectId,
                      threadId: args.threadId,
                    }))();
                  searchPromise.catch(() => {});
                  const result = await raceTimeout(
                    searchPromise,
                    mentionSearchTimeoutMs,
                    `timed out after ${mentionSearchTimeoutMs}ms`,
                  );
                  return normalizeMentionSearchItems(record.id, result);

The timeout helper only races a response deadline against the original promise. Clearing its timer does not abort the promise or its plugin-owned resources:

  try {
    return await Promise.race([
      promise,
      new Promise<never>((_resolve, reject) => {
        timer = setTimeout(() => reject(new Error(message)), timeoutMs);
        timer.unref?.();
      }),
    ]);
  } finally {
    if (timer !== undefined) clearTimeout(timer);
  }

Consequently the caller finishes while plugin work remains pending, and subsequent searches create additional operations. Whether those operations occupy filesystem workers depends on the plugin and operating system; that escalation is plausible but not measured by this test. The default service search deadline is separate from the fixture's short 100 ms deadline; shortening it makes this concurrency defect repeatable without an OS stall.

6. Proposed fix and local validation

Keep a weak set of pending registration records inside the service. Skip a record already in flight; add it immediately before invoking its search. Remove the record in a finally attached to the underlying search completion, not the response timeout. Use registration identity rather than plugin ID so one slow provider does not suppress its siblings, and replacement registrations do not inherit a stale lock. Retain existing timeout and rejection handling.

The locally tested change touches only the service and its existing test file: 94 total changed text lines (87 additions + 7 deletions), across two files. No dependency, generated artifact, persisted data, public API, protocol, authorization, or packaging change is included. This bounds repeat work; it cannot cancel a blocked syscall or isolate a misbehaving plugin.
