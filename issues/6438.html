#6438 · Catalog tab closures overwrite earlier changes

BugPriority: LowEffort: Lowplugins · confirmed-repro GitHub issue2026-10-28

Trusted base: f8c0701e94ba74a09bf48b1dcc4f49aa22ce81b7, fetched from get-bb/bb main.

Verdict: REPRODUCED · Root-cause confidence: high. Four focused regressions fail for the intended persistence/selection assertions in each of two clean trusted-base checkouts.

1. TL;DR

The Plugins catalog can retain tabs that a bulk-close action should remove. Each individual close uses the tab array captured when the component last rendered, rather than the array produced by the previous close in the same event. The last replacement therefore restores earlier removals. When the original active tab is being removed, per-tab navigation can additionally override the survivor selected by the menu. This is a catalog workspace state bug, not a plugin installation failure.

5. Root cause

The shared tab-strip handler, lines 366–379, selects a survivor if necessary and invokes every candidate's onClose() in one event:

if (scope !== "self" && closesActiveTab) {
  tabs.find((tab) => tab.tab.id === tabId)?.onSelect();
}
for (const tab of tabsToClose) {
  tab.onClose();
}

The catalog's close callback, lines 527–539, derives each replacement from render-captured openIds and activePluginId:

const tabs = openIds.filter((id) => id !== closedPluginId);
const closedIndex = openIds.indexOf(closedPluginId);
const next = activePluginId === closedPluginId
  ? (tabs[Math.min(closedIndex, tabs.length - 1)] ?? null)
  : activePluginId;
setWorkspace({ tabs, activePluginId: next });
if (next !== null) selectPlugin(next);
else closePanel();

Starting with [GitHub, Automations, Tasks], closing GitHub writes [Automations, Tasks]; closing Automations then writes [GitHub, Tasks] from the original array. The second write undoes the first. The workspace atom persists this replacement to localStorage.

There is also a selection-order problem: selection initially navigates only, with the selected workspace recorded later by the route effect. The existing close callback navigates even for inactive-tab removal. A bulk command's intended survivor can therefore be replaced by stale active state, and the route effect can reopen a supposedly removed tab. Both mechanisms are observed by the four regression cases.

6. Proposed fix

Make each close consume the latest workspace instead of a render snapshot, so removals compose. Record the selected survivor synchronously before closing other tabs, and navigate only if closing the active tab changes the active selection. Preserve ordinary single-close neighbor fallback, closing the final tab, and harmless duplicate close requests. Keep this correction in the catalog workspace owner rather than changing shared menu semantics. The existing linked PR already targets this approach; this investigation does not create a competing fix.
