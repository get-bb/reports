#6079 · Host updater rejects successful installs when npm wrappers fail

BugMedium priorityLow efforthost GitHub issue2026-10-21 · base 2799d45ed869d09db739bbdf391950d2befd2c3e

Verdict: REPRODUCED · Root-cause confidence: high · reproduction label: confirmed-repro

1. TL;DR

A daemon can finish installing the replacement package but still report an unsuccessful update. The updater launches the shell command npm, including any Node version-manager wrapper around npm. When a wrapper runs a missing helper after npm succeeds, its final exit status is 127. The updater treats that as an installation failure, returns failed, and does not reach the connection layer's restart callback. This was reproduced twice on unchanged trusted main with real npm and a small generated wrapper; it does not rely on the reporter's shell script, runtime data, or downloads.

5. Root cause

defaultInstallTarball prepends the running Node directory to PATH, then calls:

await runProcess(
  "npm",
  ["install", "-g", BB_APP_ALLOW_SCRIPTS_ARG, ...prefixArgs, tarballPath],
  { env: { ...process.env, PATH: path } },
);

Adding Node to PATH makes npm discoverable but does not make a wrapper's separate version-manager binary discoverable. defaultRunProcess rejects on the shell launcher's nonzero status. The install and failure paths therefore return failed after the npm install, without recording a successful artifact digest. The connection layer only invokes onSelfUpdateInstalled when the result equals updated.

The generated LaunchAgent explicitly sets the prefix and data-directory environment, but no PATH. The general defect is executing extra launcher behavior instead of npm itself; it does not require a transport, authentication, or tarball failure.

6. Proposed fix and tested candidate

Prefer the npm JavaScript CLI belonging to the current Node installation and execute it with process.execPath. Check the conventional Unix and Windows sibling npm layouts. Keep the existing npm-on-PATH behavior when no such CLI exists. Preserve the installation arguments, native-script allowlist, configured prefix validation, subprocess environment, and rejection of real npm failures. Do not accept arbitrary nonzero installation statuses as success.

A candidate in the host-daemon subsystem implements this without protocol, schema, dependency, packaging, or release-process changes. The regression test and the relevant existing updater/connection tests pass:
