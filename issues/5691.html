#5691 · ACP launch settings discard non-restorable sessions

BugHigh priorityLow effortproviders · provider-acp Issue · 2026-10-17 · base 6a639cfc0d66e0c789a1bd7309266973228d1a80

Verdict: REPRODUCED · Root-cause confidence: high · Reproduction label: confirmed-repro.

1. TL;DR

When an ACP agent cannot load sessions, changing a launch-selected model or reasoning level replaces its running session anyway. The bridge accepts the turn and reports a replacement with contextLost: true, rather than rejecting the destructive change. This was reproduced for both settings using real child processes running the repository's fake ACP agent, in two trusted checkouts of main. The mechanism is confirmed; the reporter's particular third-party agent, desktop OS, idle duration, and historical frequency were not tested.

5. Root cause

The settings reconciliation compares launch arguments and unconditionally routes changed launch settings into a session rebuild. It does not first consult the old session's supportsLoadSession capability.

Thus a capability already known before the destructive action is used only after the rebuild decision. Both launch-selected model and launch-selected reasoning feed this same decision. Native in-session settings use a different path and need not be blocked.

6. Proposed fix

Before any cancellation, policy mutation, or process teardown, reject changes to launch model/reasoning when the live session does not support loading. Return an actionable error directing the user to a new thread; retain the live session so they can retry with original settings. Keep load-capable rebuilds, native in-session selection, permission handling, environment handling, and unexpected-exit recovery otherwise unchanged. No wire field or dependency is needed.
