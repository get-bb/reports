#6309 · Interrupted working-directory lookup aborts provider initialization

Bug High Effort: Medium providers provider-claude-code GitHub issue

2026-10-26 · trusted main 3540a699e29034b53da32bb7efa6f5b4055209eb

Verdict: PARTIALLY REPRODUCED · Root-cause confidence: high for the startup-failure mechanism; the native signal trigger remains unverified. Reproduction label: partial-repro.

1. TL;DR

A single failed working-directory lookup can prevent the Claude provider from starting. A deterministic injected EINTR at the real bundled SDK call makes the real bridge worker exit with status 1 before it reads a request. Healthy startup exits normally with the same empty input. The result repeats in a second clean checkout of the same trusted commit. This is not a reproduction of an operating-system signal interrupting getcwd: the native call is replaced only at the targeted SDK invocation.

cwd-fault.mjs

const originalCwd = process.cwd.bind(process);
const faultCode = process.env.BB_REPRO_CWD_FAULT;
let injected = false;

if (faultCode) {
  process.cwd = () => {
    const stack = new Error().stack ?? "";
    if (!injected && stack.includes("/provider-claude-code/.bundled-runtime/dist/host.js")) {
      injected = true;
      process.stderr.write(`injected one cwd failure: ${faultCode}\n`);
      process.stderr.write(`${stack.split("\n").find((line) => line.includes("/provider-claude-code/.bundled-runtime/dist/host.js"))?.trim()}\n`);
      throw Object.assign(new Error(`injected ${faultCode} at process.cwd`), {
        code: faultCode,
        syscall: "uv_cwd",
      });
    }
    return originalCwd();
  };
}

5. Root cause

The Claude SDK reads process.cwd() during module evaluation outside its realpath catch; an interrupted read rejects the provider import and the bridge worker exits. The provider host statically re-exports the bridge, which statically imports the SDK. The dependency declaration and frozen lockfile resolve SDK 0.3.245.

Relevant excerpt from the generated bundle, obtained from that locked dependency (minified identifier names are build-specific):

function jae(){let e="";if(typeof process<"u"&&typeof process.cwd==="function"&&typeof zF==="function"){let t=zae();try{e=jF(zF(t))}catch{e=jF(t)}}return IF({host:FF(),id:wU()??Rp(),project:{originalCwd:e,projectRoot:e,cwd:e}})}var $ae=jae();

The observed injected stack maps the cwd call to jae at host.js:224:102369. The SDK's zae alias invokes cwd before the realpath try/catch. The worker import catch removes its temporary directory, reports the error, and exits. Its start hook and line reader are reached only after successful evaluation.

Simply importing the same URL again is not recovery: ESM retains a failed module evaluation. The separate caching check verifies error-object identity across the two imports. The operating-system explanation for a naturally occurring EINTR has not been validated; no claim is made about a particular libuv implementation.

6. Proposed fix and simple-fix decision

The preferred root-owned repair is a bounded EINTR retry around the SDK's initial cwd read, while rethrowing other errors. Verify repeated EINTR exhaustion and permanent errors as well as success after an interruption. This call is owned by an external locked SDK, not repository-authored provider code.

No pull request: changing the dependency or its packaged artifact violates this run's simple-fix constraints. A process-wide process.cwd replacement or worker-restart policy needs broader runtime validation; a same-URL import retry demonstrably cannot recover. No production patch, branch, or fix commit was created. There were no linked open pull requests in the issue timeline or in an open-PR search for the issue number.
