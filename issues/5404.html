#5404 · Launcher continues startup after detecting a live runtime owner

BugHighEffort: Lowhost · cli · confirmed-reproIssueOctober 12, 2026 · base b5618353309df57e67794e64ca275dccc88b2d34

Verdict: REPRODUCED · Root-cause confidence: high

1. TL;DR

Starting a second launcher against a data directory already served by a live launcher prints a warning, but still starts a server child. The child fails because the first server already owns the local port. Both clean runs produced a new server uncaught-exception diagnostic containing EADDRINUSE; the original instance stayed healthy. The runtime-record claim detects the other live process, but its false return is only used to print a warning. A small launcher guard now checks the existing health endpoint and exits with status 1 before any server launch when that endpoint is healthy.

5. Root cause

claimBbAppRuntimeFile returns false when an existing record names another running process. runBbApp's runtime-record handling prints the warning but continues into full-stack supervision. That supervision reaches startFullStackServerProcess and spawns a real server before the health check can reject the foreign listener.

The child receives the same data directory, opens the store at initDb, and reaches startup recovery and listener creation in that order. Listener creation is asynchronous, so the listening log can occur before the bind error is known. The verified problem is missing launcher short-circuiting, not an in-process supervisor restart.

runStartupRecoverySweep re-drives environment and thread work. The in-flight thread guard does not prove inter-process coordination. The report does not claim observed corruption or duplicate thread starts.

6. Proposed fix and proof

When the runtime claim is rejected, use the launcher's existing validated health check against its configured local listener. If healthy, log the duplicate-instance error, set exit status 1 and return before constructing managed processes. Preserve startup when the record is unclaimed or the existing health check fails. This retains restart-on-failure takeover behavior while avoiding the doomed child and its shared-store initialization.

The implemented change stays within packages/bb-app: launcher, README, and one regression test. It changes 112 text lines across three files (13 production/documentation additions and 99 test additions), with no dependency, generated file, stored-data or public protocol change.
