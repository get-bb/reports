#7438 · Root composer browser ownership is not handed off

BugPriority: MediumEffort: Mediumdesktop · ui · partial-reproIssue2026-11-11 · base 365d7c5237ae270be0555b5b44ea61020252713e

PARTIALLY REPRODUCED · Root-cause confidence: high for the missing ownership handoff

1. TL;DR

The New thread composer and an existing conversation use separate panel state. A focused test of the real submission handler confirms that successful creation navigates to the conversation without moving its browser tab: the destination stays empty and closed, while the root composer retains its selected tab. Repeating this test in a second clean checkout produces the same three failed expectations. The native browser manager also deliberately rejects reattaching an existing tab under a different thread. A complete correction therefore needs coordinated UI-state and native-page ownership transfer, not just copying the saved URL. This Linux investigation did not launch the macOS desktop app, so native page continuity and the exact reported CLI output remain unverified.

5. Root cause

Successful creation never adopts the root panel

RootComposeView.tsx:408–420 awaits creation, records the new ID, resets placement, and navigates. There is no panel transfer or root-panel cleanup in this path:

const thread = await createThread.mutateAsync({ ...requestFields, ...placement, ... });
setLastCreatedThreadId(thread.id);
setPlacement(DEFAULT_THREAD_CREATION_PLACEMENT);
if (navigateToThreadAfterCreate) {
  navigateInPane({ projectId: thread.projectId, threadId: thread.id });
}

The root panel reads ROOT_COMPOSE_FIXED_PANEL_STATE_ID with syncThreadId=null (lines 697–701). Its native browser deck also receives that root ID (lines 1042–1055). Real conversation panels use their own thread ID; no implicit relationship joins the two stores.

Native ownership is a separate invariant

desktop-browser-view.ts:1705–1727 looks up an existing view by window/tab key and refuses both cold and warm entries when the supplied thread ID differs. The existing ownership-isolation test passes, confirming this is intentional behavior. Removing that guard would weaken thread isolation and is not an acceptable shortcut.

if (cold !== undefined && cold.threadId !== request.threadId) return;
...
if (existing !== null && existing.threadId !== request.threadId) {
  return;
}

Additionally, the desktop broker snapshot publisher emits host-facing tab updates only for raw thread IDs. Root-composer tabs are not automatically persisted as conversation tabs through that channel.

6. Proposed fix and simple-fix decision

Introduce an explicit, validated root-composer-to-created-thread handoff that preserves the native view, tab ID, page history, and control state. Coordinate that native ownership change with UI tab persistence, active selection, panel openness, and clearing the consumed root tab. Retain all ordinary cross-thread reattachment protections and cover failed creation and handoff failure without losing the page.

No pull request opened. A UI-only copy does not fix native ownership. A complete handoff spans app state and the desktop browser owner and needs an explicit cross-boundary contract or a deliberate change to its ownership semantics. That fails this rule's one-subsystem/no-protocol-or-security-boundary-change simple-fix gate. No production patch, fix branch, or dependency change was made. The authored test is published as evidence rather than committed as a failing test to the application repository.
