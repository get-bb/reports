#7021 · Pinned browser runtime truncates large piped results

Bug High Effort: Medium plugins · cli · confirmed-repro GitHub issue November 4, 2026 · base d060de8e30f3310417054a74510a774dd2909e2b

Verdict: REPRODUCED · Root-cause confidence: high at the native stdout and BB runtime lifecycle boundaries. The exact implementation defect inside the native executable is not established.

1. TL;DR

The pinned DevBrowser executable can end a large JSON result before its closing quote when stdout is a pipe. BB receives that incomplete line, fails JSON parsing, and deliberately closes the session on that exception. A 48,000-character result and a follow-up command succeed, while 70,000- and 100,000-character results fail and leave the session unusable. The same 100,000-character native result is intact when stdout is a regular file, isolating the loss to native piped-output delivery rather than the BB server/daemon RPC transport. Two separate trusted checkouts reproduce this behavior.

5. Root cause

  1. The runtime pin selects DevBrowser 1.0.0-rc.4 and verifies the platform binary digest. The experiment uses that exact release, not an issue-supplied executable.
  2. The process collector launches stdout as a pipe, concatenates received UTF-8 chunks, and resolves only on child close. Its configured output guard is 512,000 bytes. In the failing native control only 131,072 ASCII bytes arrive, so this guard has not fired.
  3. The native pipe control ends inside a duplicated result string and contains no completion frame. Sending the same command to the same warmed daemon with a regular-file stdout descriptor yields a complete 200,038-character result line and a done frame. This isolates the defect to native piped-output delivery before BB's JSON decoder or any server RPC. A missing stdout drain at native process exit is a plausible explanation, not a verified native-source diagnosis.
  4. decodeOutput calls JSON.parse(line), which correctly rejects the incomplete string.
  5. close() aborts the session controller, closes its supervisors, and removes session storage. The run catch invokes it for every thrown error. The next queued run checks that aborted signal and fails with This operation was aborted. The host run handler also closes on a runtime exception, explaining why a public session cannot simply retry.
process.ts: stdio: ["ignore", "pipe", "pipe"]
runtime.ts: const frame = frameSchema.parse(JSON.parse(line));
runtime.ts: catch (error) { await close(); throw error; }

Confidence is high for the native-output boundary and subsequent BB closure mechanism. Confidence in a specific native flush implementation defect is only medium without upstream source-level instrumentation. Exact observed byte cutoffs can vary with scheduling and pipe capacity.

6. Proposed fix and simple-fix decision

Repair native NDJSON output delivery so pending bytes are drained before process completion, validate both pipe and regular-file output on a warmed daemon, and publish a verified runtime release. Then update BB's pinned release and platform digests through the normal runtime release process. A runtime-level regression should verify an intact 100,000-character result and a successful subsequent command.

No PR opened: the verified producer defect is in the pinned external native runtime. Repairing that producer and adopting its release is outside this rule's one-subsystem, no-dependency/no-packaging-change simple-fix scope. Merely swallowing JSON errors or avoiding session closure does not recover lost output. A local file-spooling workaround would need a separate review of temporary-output ownership, cancellation and enforcement of the existing output guard; it is not treated as an automatically safe fix here.

No open linked PR appeared in either cross-reference metadata or the repository PR search. No production patch, fix branch, dependency change, or target-repository commit was made.
