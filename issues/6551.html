#6551 · Native goal states are rejected before projection

BugPriority: MediumEffort: Highproviders · provider-codexGitHub issueOctober 29, 2026

Verdict: REPRODUCED · Root-cause confidence: high

Trusted base: 3bacfac9ed69d42392076e5b3da2815bec822cd8, fetched from main and verified against the target repository’s main SHA.

1. TL;DR

A native goal can stop while BB still presents its previous active snapshot. Two status values already present in the repository’s generated Codex notification types, blocked and usageLimited, are absent from BB’s handwritten goal validators. Feeding either notification through the real translator and delta assembler produces provider/unhandled, not a goal state update; the real timeline projection consequently remains active. The server’s active-goal counter reads that projected status, so its existing counting policy is not the underlying defect. Repository inspection also finds only a clear-goal action, with no supported goal-resume action through the provider bridge, REST contract, SDK, or CLI.

Complete reproduction test 
import { describe, expect, it } from "vitest";
import { experimental_createDeltaAssembler as createDeltaAssembler } from "@get-bb/plugin-sdk/provider-bridge/testing";
import { extractThreadTimelineGoal } from "../../../packages/thread-view/src/goal-snapshot-extraction.js";
import { createCodexEventTranslator } from "./translator.js";
import type { ThreadGoalStatus } from "./generated/codex-app-server/schema/v2/ThreadGoalStatus.js";

describe("native goal status propagation", () => {
  const statuses: ThreadGoalStatus[] = [
    "paused",
    "budgetLimited",
    "complete",
    "blocked",
    "usageLimited",
  ];

  it.each(statuses)("replaces an active snapshot with %s", (status) => {
    const translator = createCodexEventTranslator({
      additionalWorkspaceWriteRoots: [],
    });
    const assembler = createDeltaAssembler({
      providerId: "codex",
      entropyPrefix: "goal-probe",
      textDeltaFlushMs: 0,
    });
    function translate(goalStatus: ThreadGoalStatus) {
      return assembler.assemble({
        threadId: "probe-thread",
        deltas: translator.translateEvent({
          jsonrpc: "2.0",
          method: "thread/goal/updated",
          params: {
            threadId: "native-thread",
            turnId: null,
            goal: {
              threadId: "native-thread",
              objective: "Boundary probe",
              status: goalStatus,
              tokenBudget: 1000,
              tokensUsed: 25,
              timeUsedSeconds: 5,
              createdAt: 0,
              updatedAt: 1,
            },
          },
        }),
      });
    }
    const initial = translate("active");
    const update = translate(status);
    const goal = extractThreadTimelineGoal(
      [...initial, ...update].map((event, index) => ({
        event,
        meta: { id: `event-${index}`, seq: index, createdAt: index },
      })),
    );
    console.log(JSON.stringify({
      inputStatus: status,
      emittedTypes: update.map((event) => event.type),
      projectedStatus: goal?.status,
      activeGoalCount: goal?.status === "active" ? 1 : 0,
    }));
    expect.soft(update).toEqual([
      expect.objectContaining({
        type: "thread/extensionState/updated",
        kind: "provider-codex/goal",
        payload: {
          objective: "Boundary probe",
          status,
          tokenBudget: 1000,
          tokensUsed: 25,
          timeUsedSeconds: 5,
        },
      }),
    ]);
    expect.soft(goal?.status).toBe(status);
    expect.soft(goal?.status === "active" ? 1 : 0).toBe(0);
  });
});

5. Root cause

  1. The generated native status type already includes six values. The handwritten incoming notification schema includes only four: 
    const codexThreadGoalStatusSchema = z.enum([
  "active",
  "paused",
  "budgetLimited",
  "complete",
]);
  2. Validation runs before dispatch; an invalid handled notification becomes an unhandled delta. Therefore the goal-update branch never emits the replacement extension state.
  3. The plugin extension schema and shared public timeline schema repeat the same incomplete enum. Changing only the incoming validator is insufficient: the projection validates payloads using the shared enum and ignores failures.
  4. The server counter correctly counts only the active status, but the latest accepted snapshot is still active: 
    activeGoalCount: goal?.status === "active" ? 1 : 0,
  5. Resume is a separate missing control path. The bridge method registry has only thread/goal/clear; the capability schema likewise has clear only. This is mirrored in the REST contract, SDK, and CLI. A project-wide search of non-generated source finds no goal set/resume method.

6. Proposed fix and autopatch decision

Align all three handwritten goal-status validators with the native notification contract and cover all six statuses at the translator/projection boundary. Keep the existing active-only counting policy. Separately design and implement a supported goal-resume action across the capability, daemon, provider bridge, REST contract, SDK, CLI, and discoverable documentation, preserving native usage instead of clearing/recreating the goal. Decide explicitly whether operators may edit objective and budget or only resume, and how inactive goals can be cleared: the current clear endpoint rejects requests when the active count is zero.

No automated fix or PR: even the status correction changes the shared public timeline schema; adding resume changes public contracts and crosses subsystems. Those changes violate this rule’s simple-fix constraints. No production patch, branch, or push was attempted. No linked open PR was found in cross-reference metadata or the open-PR search at investigation time.
