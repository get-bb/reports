#6912 · ACP pending-session cancellation gap

BugPriority: MediumEffort: Lowprovidersprovider-acpGitHub issue

November 3, 2026 · trusted main dbb247c60f46494579adb40b80efa7c8a861b35c

Verdict: REPRODUCED · Root-cause confidence: high

1. TL;DR

Stop can acknowledge success while an ACP session is still being constructed, yet that construction continues and becomes live. During a settings-driven replacement, the same gap allows the pending message to reach the replacement agent and finish normally. The stop handler only sees registered sessions; the constructing replacement is not yet registered. Two newly authored bridge-level tests exercise the real bridge and its repository-owned fake ACP subprocess, and both fail with the claimed behavior in two separate clean checkouts. No UI interaction or third-party agent was tested.

Complete new test block (77 added lines including insertion spacing)
describe("stop admission regression", () => {
  it("does not admit an initial session after acknowledging interruption", async () => {
    const launchFile = join(workspaceDir, "initial-session-launches.txt");
    const starting = startThread({
      envVars: { FAKE_ACP_LAUNCH_LOG: launchFile },
    });
    const threadId = `thread-${nextThreadSerial}`;
    const stopping = sendRequest("thread/stop", {
      threadId,
      providerThreadId: threadId,
      intent: "interrupt",
      activeTurnId: null,
    });
    const stopResult = await waitForResponse(stopping);
    const outcome = await starting.then(
      () => "ready",
      () => "cancelled",
    );

    expect({
      acknowledged: stopResult.result,
      outcome,
      launched: existsSync(launchFile),
    }).toEqual({
      acknowledged: { ok: true },
      outcome: "cancelled",
      launched: false,
    });
  });

  it("does not deliver a turn overtaken by interruption during permission relaunch", async () => {
    const promptFile = join(workspaceDir, "permission-relaunch-prompts.txt");
    const launch = {
      envVars: {
        FAKE_ACP_LOAD_SESSION: "1",
        FAKE_ACP_PROMPT_LOG: promptFile,
      },
      permissionCli: {
        full: ["--unrestricted"],
        workspaceWrite: ["--workspace-only"],
        insertAfterArgs: 1,
      },
    };
    const thread = await startThread(launch);
    const pendingTurn = sendTurnRequest("turn/start", thread.providerThreadId, {
      input: [{ type: "text", text: "cancellation probe", mentions: [] }],
      options: executionOptions({
        permissionMode: "accept-edits",
        providerOptions: launchProviderOptions(launch),
      }),
    });
    const stopping = sendRequest("thread/stop", {
      threadId: thread.bbThreadId,
      providerThreadId: thread.providerThreadId,
      intent: "interrupt",
      activeTurnId: null,
    });
    const stopResult = await waitForResponse(stopping);
    const turnResult = await waitForResponse(pendingTurn);
    if (!turnResult.error) {
      await waitForTurnCompleted();
    }

    expect({
      acknowledged: stopResult.result,
      deliveredPrompts: loggedPrompts(promptFile),
      completedNormally: threadEventsOfType("turn/completed").some(
        (event) => event.status === "completed",
      ),
    }).toEqual({
      acknowledged: { ok: true },
      deliveredPrompts: [],
      completedNormally: false,
    });
  });
});

5. Root cause

Construction first awaits shutdown of an existing session before the replacement has an identity in the session map:

async function startAgentSession(
  request: AcpSessionStartRequest,
): Promise<AcpThreadSession> {
  const params = request.params;
  const bbThreadId = params.threadId;

  const existing = sessionsByBbThreadId.get(bbThreadId);
  if (existing) {
    await stopSession(existing);
  }

It also awaits launch-argument resolution before creating the agent connection and before registering the replacement:

  const launch = await resolveAgentLaunchArgs(params);
  if (launch.warning) {
    emitStartNotification(ACP_WARNING_METHOD, {
      threadId: bbThreadId,
      summary: launch.warning,
    });
  }

    awaitingFirstPrompt: true,
  };
  sessionsByBbThreadId.set(bbThreadId, session);

  try {

Stop only looks up the registered session and always acknowledges success even when no session is found:

    case "thread/stop": {
      const session = sessionsByBbThreadId.get(request.params.threadId);
      if (session) {
        if (request.params.intent === "release") {
          await releaseSession(session);
        } else {
          await stopSession(session);
        }
      }
      sendResult(request.id, { ok: true });
      return;
    }

On initial start, the lookup is empty. During rebuild, it can still reference the old session, whose stop operation already has its stopping flag set and returns immediately to a second stop. No per-thread pending-construction cancellation state carries that request forward. The replacement therefore resumes after its await, launches, registers, and receives the pending turn. The late session.stopping guard cannot help because it checks the new object, not the old object that stop saw.

This is a lifecycle/admission ordering gap, not agent refusal to honor session/cancel. The fresh-start test proves the gap without dynamic model discovery; an asynchronous launch-resolution boundary alone suffices.

6. Proposed fix

Track pending session constructions by bb thread before the first await. Stop should mark those constructions cancelled as well as stop any registered session. Check the cancellation state after awaited shutdown and launch-argument resolution, before launching/registering a replacement, and remove pending entries in a finally block. Preserve existing cancellation once a session is registered. Validate fresh start, settings relaunch, failed construction cleanup, and concurrent starts for the same thread.

No production fix was applied here: an open pull request already links this issue, so the autopilot duplicate-PR gate prevents creating another.
