#8256 · Native menu activation during layout switching

BugPriority: MediumEffort: Mediumdesktopno-reproGitHub issue2026-11-26

Trusted base: b0ddaad731565d7e4de68d824120d802fc78f7d5.

Verdict: NOT REPRODUCED · Root-cause confidence: low. Native Windows verification is unavailable; this is not evidence that the issue is invalid or fixed.

1. TL;DR

The report describes Windows keyboard-layout switching taking focus away from a text input and activating the desktop application's native menu. Trusted main does install an application menu and sets autoHideMenuBar: true for non-macOS application windows. The installed Electron API declaration explicitly says this hides the menu unless Alt is pressed, so hiding the menu is not equivalent to disabling its Alt activation. The application renderer's input hook handles reload shortcuts, not a general layout-switch policy. These facts make native menu activation a plausible explanation, but the Windows event stream, successful layout change, and focus transfer were not observed on this Linux host.

5. Root cause: plausible mechanism, not established

The first necessary condition is a native menu: installApplicationMenu builds a menu and calls Menu.setApplicationMenu(menu). The second is the non-macOS window configuration in createWindowOptions:

...(args.isMac
  ? {
      frame: false,
      titleBarStyle: "hiddenInset" as const,
      trafficLightPosition: MACOS_TRAFFIC_LIGHT_POSITION,
    }
  : { autoHideMenuBar: true }),

The installed Electron 44.10.2 declaration at apps/desktop/node_modules/electron/electron.d.ts:4208 documents automatic menu hiding unless Alt is pressed. This supports the configuration's meaning, not the claimed Windows key delivery sequence.

The application window wires the renderer hook in main.ts. The hook implementation returns when the reload resolver produces null; it only prevents default for a resolved reload command. The production resolver evaluates reload bindings only. No examined part of this path supplies a layout-switch-specific native-menu policy.

Unresolved causal link: whether Windows consumes part of a layout chord and Electron consequently activates its menu remains unverified. The composer itself has not been shown to cause the focus loss. Other native input handlers and actual user keybindings may affect delivery. Low confidence refers to the end-to-end root cause, not the observed source configuration.

6. Proposed fix / next experiment

Not confident enough to ship a fix. First capture Windows native keydown/keyup, layout-change, menu-activation, and focus events for both release orders. If that establishes the mechanism, use the existing desktop input path to suppress only the verified layout-switch menu activation, preserving deliberate menu access and normal text/AltGr input. Simply deleting the application menu or blocking every Alt event could break accessibility and existing shortcuts.

No pull request: main did not yield a native reproduction or a focused regression test that fails for the reported focus transfer. The simple-fix gate therefore fails before production edits. No production files, dependency versions, or stored data were changed.
