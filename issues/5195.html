#5195 · Windows teardown rejects a terminated root before exit notification

BugHighEffort: Mediumhostclipartial-repro Issue on GitHubOctober 8, 2026 · base 8d9195d8e0f123ea32b21eb9eb1104b35d97b916

Verdict: PARTIALLY REPRODUCED · Root-cause confidence: medium.

The delayed-notification failure is verified in two clean checkouts on Linux. Native Windows turn submission and the native CLI assertion are not reproduced.

1. TL;DR

A submission can await stopping an old provider bridge, and the Windows stop helper can reject even after the operating system has removed the root process. A focused test uses a real child process, verifies its PID no longer exists, and delays only the lifecycle notification exposed to the Windows helper. That helper still fails after its fixed one-second deadline; the same result occurs in a second clean trusted checkout. The managed-stop wrapper also insists on exit metadata, so changing only the helper to return early would not address the entire caller path. These findings support a teardown timing hypothesis, but do not establish the reporter's Windows timing or connect it to the separate native CLI crash.

import { ChildProcess, execFile, spawn } from "node:child_process";
import { EventEmitter, once } from "node:events";
import { expect, it, onTestFinished, vi } from "vitest";
import { stopWindowsProcessTree } from "../src/windows-process-tree.js";

vi.mock("node:child_process", async (importOriginal) => {
  const actual = await importOriginal<typeof import("node:child_process")>();
  return { ...actual, execFile: vi.fn() };
});

async function startChild(notificationDelayMs: number) {
  const child = spawn(
    process.execPath,
    ["-e", 'process.stdout.write("ready"); setInterval(() => {}, 1000);'],
    { stdio: ["ignore", "pipe", "ignore"] },
  );
  const notifications = new EventEmitter();
  let notified = false;
  let notificationTimer: NodeJS.Timeout | undefined;
  const exited = once(child, "exit");
  child.once("exit", (code, signal) => {
    notificationTimer = setTimeout(() => {
      notified = true;
      notifications.emit("exit", code, signal);
    }, notificationDelayMs);
  });
  onTestFinished(() => {
    clearTimeout(notificationTimer);
    vi.restoreAllMocks();
    child.kill("SIGKILL");
    vi.mocked(execFile).mockReset();
  });
  await once(child.stdout, "data");
  const visibleChild = new Proxy(child, {
    get(target, property, receiver) {
      if (property === "exitCode") return notified ? target.exitCode : null;
      if (property === "signalCode") return notified ? target.signalCode : null;
      if (property === "once") return notifications.once.bind(notifications);
      if (property === "off") return notifications.off.bind(notifications);
      return Reflect.get(target, property, receiver);
    },
  });
  return { child, exited, visibleChild };
}

function arrangeTaskkill(child: ChildProcess, success: boolean) {
  vi.mocked(execFile).mockImplementationOnce((...args: unknown[]) => {
    const callback = args.at(-1);
    queueMicrotask(() => {
      if (success) child.kill("SIGKILL");
      if (typeof callback === "function") {
        callback(success ? null : new Error("termination unavailable"), "", "");
      }
    });
    return new ChildProcess();
  });
}

it("accepts a terminated root while its Windows exit notification is delayed", async () => {
  const { child, exited, visibleChild } = await startChild(1_500);
  arrangeTaskkill(child, true);
  const stopping = stopWindowsProcessTree(visibleChild);
  const outcome = stopping.then(
    (result) => ({ status: "resolved", result }),
    (error: Error) => ({ status: "rejected", message: error.message }),
  );
  await exited;
  const rootPid = child.pid;
  if (rootPid === undefined) throw new Error("Child did not receive a PID");
  expect(() => process.kill(rootPid, 0)).toThrowError(
    expect.objectContaining({ code: "ESRCH" }),
  );
  expect(visibleChild.exitCode).toBeNull();
  expect(visibleChild.signalCode).toBeNull();
  const result = await outcome;
  console.log(JSON.stringify({ kernelRootGone: true, ...result }));
  expect(result).toEqual({
    status: "resolved",
    result: { treeTermination: "confirmed" },
  });
});

it("accepts a root whose exit notification arrives within the deadline", async () => {
  const { child, visibleChild } = await startChild(50);
  arrangeTaskkill(child, true);
  await expect(stopWindowsProcessTree(visibleChild)).resolves.toEqual({
    treeTermination: "confirmed",
  });
});

it("still rejects when root termination fails and the root remains alive", async () => {
  const { child, visibleChild } = await startChild(0);
  arrangeTaskkill(child, false);
  vi.spyOn(child, "kill").mockReturnValue(false);
  await expect(stopWindowsProcessTree(visibleChild)).rejects.toThrow(
    "Process did not exit after termination",
  );
  const rootPid = child.pid;
  if (rootPid === undefined) throw new Error("Child did not receive a PID");
  expect(() => process.kill(rootPid, 0)).not.toThrow();
});

5. Root cause

Observed mechanism: absence of a lifecycle notification is treated as failed termination

The Windows helper runs the tree killer, attempts a root kill if exit metadata is absent, then waits for an exit event. Its one-second timer unconditionally rejects; it does not distinguish a still-live PID from a terminated root whose notification is pending. The reproduction separates those two facts with a real kernel liveness check.

packages/process-utils/src/windows-process-tree.ts:46

function waitForRootExit(child: ChildProcess): Promise<void> {
  if (hasExited(child)) return Promise.resolve();
  return new Promise((resolve, reject) => {
    const onExit = (): void => {
      clearTimeout(timer);
      resolve();
    };
    const timer = setTimeout(() => {
      child.off("exit", onExit);
      reject(new Error(`Process did not exit after termination: ${child.pid}`));
    }, 1_000);
    child.once("exit", onExit);
  });
}

export async function stopWindowsProcessTree(
  child: ChildProcess,
): Promise<ProcessStopResult> {
  if (child.pid === undefined || hasExited(child)) {
    return { treeTermination: "unverified" };
  }
  const terminated = await terminateWindowsProcessTrees([child.pid]);
  if (!hasExited(child)) child.kill("SIGKILL");
  await waitForRootExit(child);
  return { treeTermination: terminated ? "confirmed" : "unverified" };

The wrapper imposes a second metadata requirement

Managed stop caches its first stop promise and checks exit metadata again after the lower-level stop returns. An early return from the helper alone can still trigger the same error here. The Linux model directly tests the helper; this wrapper finding is static.

Why this can surface during a submit rather than only an explicit stop

The daemon's submit handler awaits starting or steering a turn. Starting a turn can await a recommended bridge restart, which awaits provider shutdown and then the managed stop. Thus a stop rejection can propagate through a submit path. Whether this is the exact branch used in the reported session is unverified: no provider-specific restart hint or native trace was supplied.

  • Submit dispatch awaits the runtime operation; runSubmittedTurn awaits runTurn.
  • runTurn awaits a recommended bridge restart.
  • Restart logic checks active/busy sessions and awaits shutdownProvider.
  • shutdownProvider awaits termination; termination awaits managed stop.

The companion CLI assertion is not explained

The CLI contains explicit exit branches in plugin-command proxying and error handling, but their existence is not evidence of a double-close or of the reported native failure. This investigation neither runs the Windows native event loop nor exercises successful plugin/network command shutdown. It would be unsafe to claim that the root-exit timeout explains the companion assertion.

CLI proxy completion and explicit exit branch. The source's native dependencies and the reporter's executable packaging also have not been compared.

6. Proposed fix and next experiment

No automatic patch is justified until a native Windows run reproduces the reported failure on trusted main. Capture the real root's liveness, taskkill status, exitCode/signalCode, and monotonic timestamps around its exit/close notifications while submitting tiny consecutive turns. Preserve the process-start identity to avoid confusing a recycled PID with the original child; distinguish access-denied probes from confirmed absence. Capture an assertion stack or dump separately for the CLI.

If native evidence confirms the modeled state, align the Windows stop helper and managed-stop wrapper around the same bounded definition of completed root termination. Retain independent descendant-tree verification, keep live-root termination failures fatal, and do not silently convert every timeout into success. A longer bounded wait may be appropriate, but its budget should be based on the native timeline rather than an arbitrary universal increase.

No PR: the automatic-fix gate requires reproducing the reported bug on trusted main. Only a modeled helper state is reproduced; native Windows turn submission and the CLI assertion remain unverified. No fix branch is created or pushed.
