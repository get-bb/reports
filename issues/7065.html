1. TL;DR

The reported symptom is a terminal being selected without opening its desktop side panel. A focused test mounts the real thread view, closes the panel through the plugin panel controller, and calls the real plugin terminal-navigation hook with an existing terminal session. On unchanged main, the call returns true, the terminal becomes active, and the panel state becomes open. A second clean checkout repeats that result. The proposed compact-drawer explanation overlooks a separate state setter that already opens the desktop panel. A real-browser check was blocked by environment prerequisites, so this does not claim the visual symptom is impossible.

5. Root-cause assessment

No defect root cause was established. The missing-desktop-reveal explanation does not account for the complete selection path:

  1. The plugin navigation hook retrieves the session and forwards it to the current app surface.
  2. Terminal open and select call setActiveTerminal before invoking reveal.
  3. The terminal-tab state setter upserts the terminal tab and writes isOpen: true in the same update.
  4. Desktop panel visibility derives visibility from that persisted open bit; compact viewports use the drawer bit instead.
setSecondaryPanelTabsInState({
  state: current,
  tabs: upsertTerminalTab(current.secondary.tabs, terminalId, target),
  activeTabId: createTerminalFixedPanelTab({ terminalId, target }).id,
  isOpen: true,
})

Git blame attributes the explicit open bit to existing history before the report date, not a new fix landed during this investigation. A final fetch still resolves origin/main to the recorded base. Therefore the verdict is NOT REPRODUCED, not ALREADY FIXED.
