#8174 · Unnecessary core initialization during plugin dispatch

Bug Priority: Medium Effort: Low cli · perf · confirmed-repro

GitHub issue · November 25, 2026 · trusted base fb045a046653cc127656ca3c7243d44ae4c94f3f

Verdict: REPRODUCED · Root-cause confidence: high

1. TL;DR

A command owned by a plugin completes successfully, but first imports every core CLI command group and JSON shape help that the plugin does not use. A fresh CLI process connected to an isolated local fixture resolves all 20 core group chunks before completing plugin dispatch. Both clean trusted checkouts show the same result, while version and thread-help controls load zero and one core group respectively. The defect is startup ordering rather than incorrect plugin output. This report confirms avoidable initialization, not a particular CPU or wall-time saving.

  }

      .filter((url) => url.includes("/index-chunks/"))

5. Root cause

Command selection returns all core groups whenever the first token does not name a core group. A plugin name therefore enters the full-core fallback rather than a selective import.

The main startup sequence awaits every selected loader, registers each group, and adds JSON help before attempting plugin dispatch:

const [contextEnv, ...registrars] = await Promise.all([
  import("./context-env.js"),
  ...groups.map((group) => group.load()),
]);
...
for (const register of registrars) {
  register(program, deps);
}
await addJsonShapeHelp();
...
await tryPluginCommandProxy(candidate, deps.getUrl, aliasTarget !== undefined);

Known core names already come from the static group table. The plugin proxy uses that classification, server contributions and process arguments; after running an owned command it calls process.exit(exitCode). The earlier registration and help initialization are consequently wasted on this path.

The trace records module resolution rather than per-module CPU or evaluation timing. The awaited dynamic imports and registrar calls in trusted source explain why this is real startup work, not merely a list of available files. The fixture supplies server responses only; it does not replace the CLI entry point, proxy, loader, or group registration.

6. Proposed fix

Attempt plugin ownership and dispatch after creating the context dependencies but before loading or registering core groups. Successful plugin dispatch exits early. If no plugin owns the token, retain the existing full-core fallback and soft-alias behavior. Preserve top-level/version help, unknown-command suggestions, disabled-plugin diagnostics, unreachable-server handling, plugin-owned help, and argument passthrough.
