#7461 · Checkpoint contention invalidates a pinned-WAL test observation

BugPriority: LowEffort: Lowhost GitHub issue2026-11-12 · base 030b1b729f28acedc6f86cd65a71cb3678da8124

Verdict: REPRODUCED · Root-cause confidence: high · Reproduction label: confirmed-repro.

1. TL;DR

A database test assumes that a PASSIVE checkpoint always returns usable WAL frame counts. Its background checkpoint worker is still active, so the observation can encounter SQLite's exclusive checkpoint lock instead. SQLite then reports a busy checkpoint with frame counts of minus one, and the test mistakes that sentinel for a small WAL. On two clean checkouts of trusted main, taking the real checkpoint lock in a separate process reproduced the exact assertion failure, with production code unchanged. The uninstrumented five-test suite passed in each checkout; this investigation demonstrates the contention mechanism, not the natural Windows failure frequency.

5. Root cause

The pinned-reader test runs the following after waiting 250 ms, while its checkpointer is still attached:

const [pinned] = db.$client.pragma(
  "wal_checkpoint(PASSIVE)",
) as CheckpointRow[];
expect(pinned?.log).toBeGreaterThan(32_768);
expect(pinned?.checkpointed).toBeLessThan(pinned?.log ?? 0);

The worker checkpoint and rescheduling path issues the same PASSIVE pragma. A fixed sleep does not establish checkpoint ownership or exclude the worker's next attempt. The observation therefore needs to distinguish checkpoint-lock contention from a valid frame count.

The installed, lockfile-pinned SQLite amalgamation corroborates the mechanism: SQLITE_SHM_NLOCK is 8, UNIX_SHM_BASE is 120, and WAL_CKPT_LOCK is slot 1, giving byte offset 121. sqlite3WalCheckpoint takes that exclusive lock; a competing holder returns SQLITE_BUSY before frame outputs are filled. sqlite3_wal_checkpoint_v2 initializes those outputs to -1. The helper uses this actual OS lock; the observed pragma row then confirms the result through better-sqlite3.

This does not indicate that the write loop generated too few frames: -1 is the unavailable-output sentinel, not a positive WAL size. The worker pause ordering and main-thread fallback and resume ordering also explain why the same uncoordinated observation is specific to the test rather than evidence of a new production policy defect.

6. Proposed fix

Keep the existing substantive assertions, but obtain the checkpoint observation with a bounded asynchronous retry when busy === 1. Yield between attempts so the worker can release its lock; preserve a deadline so persistent contention still fails. Do not “fix” the assertion by accepting negative frame counts, lower the frame threshold, or change production checkpoint scheduling to accommodate an observation-only race.

A cross-platform regression should exercise genuine transient checkpoint contention through an appropriate repository-owned harness. The Linux lock-holder here is intentionally only diagnostic and should not be added to the Windows test suite unchanged.
