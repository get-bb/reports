#5880 · Connect transport continuity after tunnel loss

BugMedium priorityMedium effortremote · connect · partial-reproGitHub issue

2026-10-20 · trusted base bd93d18896bab97c950c4fa3451b621c1e0569c1

Verdict: PARTIALLY REPRODUCED. Root-cause confidence: low for spontaneous idle loss; high for downstream stream teardown.

1. TL;DR

The reported recurring idle disconnects were not reproduced: this investigation cannot attribute them to ATL, TLS termination, Durable Object resets, deployment, or the local network. A real local Workers runtime does reproduce the consequence: when a tunnel closes, Connect immediately closes an established visitor WebSocket, and a replacement tunnel does not revive that socket. Even replacing a still-live tunnel closes the visitor. New visitor connections work after redial, so this demonstrates transport interruption, not logout or loss of authentication. Healthy heartbeat probes succeed, and the existing client heartbeat tests cover both normal idle operation and deliberate termination when acknowledgements are missing.

async function upgrade(
  runtime: Miniflare,
  path: string,
): Promise<ClientWebSocket> {
  const response = await runtime.dispatchFetch(`https://relay.test${path}`, {
    headers: { Upgrade: "websocket" },
  });
  if (!response.webSocket)
    throw new Error(`upgrade failed: ${response.status}`);
  response.webSocket.accept();
  return response.webSocket;
}

function nextMessage(socket: ClientWebSocket): Promise<string | ArrayBuffer> {
  return new Promise((resolve) => {
    socket.addEventListener("message", (event) => resolve(event.data), {
      once: true,
    });
  });
}

function nextClose(
  socket: ClientWebSocket,
): Promise<{ code: number; reason: string }> {
  return new Promise((resolve) => {
    socket.addEventListener(
      "close",
      (event) => resolve({ code: event.code, reason: event.reason }),
      { once: true },
    );
  });
}

function echoVisitorMessages(tunnel: ClientWebSocket): void {
  tunnel.addEventListener("message", (event) => {
    if (typeof event.data === "string") return;
    const frame = decodeFrame(event.data);
    if (frame.type === "ws-data") tunnel.send(encodeFrame(frame));
  });
}

5. Root cause

Unknown for the primary reported defect. This evidence does not establish the cause of recurring idle drops. It establishes why an actual tunnel drop is visible downstream: TunnelDO calls abandonStreams on loss, and also during every new tunnel admission, so an already accepted visitor cannot remain attached across redial.

Idle heartbeats are configured through the Workers auto-response API. The client sends every 20 seconds and terminates after the acknowledgement age exceeds 60 seconds; with ordinary timer cadence the first such check occurs at 80 seconds. This is a consequence of lost acknowledgements, not an explanation of why they were lost. Closures with a much fresher acknowledgement cannot be attributed to that normal deadline check alone.

6. Proposed fix / next experiment

No root-cause patch is justified yet. Correlate the reported timestamps and request IDs with stored Workers Logs, Durable Object invocation outcomes, deployment history, and transport/TLS telemetry. Never attach a production real-time tail: that itself resets tunnel objects. Then run a long-duration authenticated staging tunnel with timestamped heartbeat send/ack and event-loop measurements, and a phone browser, to distinguish transport loss from authentication or UI recovery.

If the desired product behavior is transparent recovery, first specify whether to reconnect and restore application state or introduce resumable tunneled streams. The latter changes stream lifecycle and potentially protocol and identity guarantees; it is not a safe contained patch. Existing HTTP redial grace does not imply resumability for already-open WebSockets.

Simple-fix decision: skipped. The spontaneous idle trigger was not reproduced on trusted main, and transport continuation is not a verified sub-500-line repair within the existing contract. No linked open pull request was found in the issue timeline or the numeric PR search. No fix branch or product pull request was created.
