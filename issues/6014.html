#6014 · Untracked directory attaches interrupted by recovery

BugMedium priorityLow effortworkspacesIssue2026-10-21 · base b143a22860944a96bf183605dfb0ffe58b1de283

Verdict: REPRODUCED · Root-cause confidence: high

1. TL;DR

A thread moving to a newly attached directory can receive an error even after the host reports a successful attach. The server starts the command without registering it in the environment lifecycle's active-operation map. A recovery pass then mistakes the pending environment for abandoned work and marks it as failed. Its later successful result cannot legally move that failed row to ready. A deterministic route-level regression reproduces this for both periodic sweeps and host-resume recovery, in two separate clean trusted checkouts.

5. Root cause

  1. The directory-move path creates a provisioning environment without a path or owner, then directly awaits the live attach RPC. That bypasses the environment-operation registry.
  2. The sweep advances every provisioning row. Host resume advances those rows for the resumed host, too.
  3. The recovery guard skips tracked operations, but this attach is not tracked. Recovery cannot rebuild a request without a path, so it interrupts the row as unrecoverable.
  4. The later attach result tries provision.succeeded, but the lifecycle allows success only from provisioning, not error. The tool then returns the not-ready error.
environment.status !== "provisioning" ||
map.has(environment.id) ||
findHostDataDir(deps, environment.hostId) === null

if (environment.path === null) return null;

The underlying problem is split ownership of in-flight provisioning: the tool launches work, but the lifecycle engine has no record that it is live. Relaxing the error-state transition or disabling orphan recovery would mask the ownership bug and weaken recovery.

6. Proposed fix and local verification

Run the directory attach through the existing engine-owned tracked-operation mechanism, keyed by environment ID and marked as attach. Await its completion so command failures still propagate to the tool. Retain the existing five-minute timeout, host interruption behavior, schemas, and orphan recovery. This requires no protocol, stored-data, dependency, or product-policy change.
