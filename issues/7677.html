1. TL;DR

The report concerns HTTP server authentication, not an HTML sign-in form or imported cookies. Trusted main creates native browser views without a literal Electron login registration anywhere in desktop source. A focused extension to the existing view-manager test emits that challenge at the WebContents boundary: the production manager leaves its default cancellation intact, in both clean checkouts. Electron 44.10.2’s installed API declarations document cancellation as the default unless the event is prevented and credentials supplied through its callback. This is strong evidence of a missing integration, but it is not a native visual reproduction: Electron could not start on this host because libglib-2.0.so.0 is absent.

Scope limit: No real HTTP navigation, Windows desktop session, visible credentials prompt, authenticated retry, or screenshot was verified here. The unit test uses the repository’s Electron fake. It verifies cancellation ownership, not prompt usability or successful authentication.

5. Root cause

The native view manager creates the view and calls its event wiring at createEntry. wireWebContents starts registering page and input events, and the rest of that function never takes ownership of HTTP authentication. ensureHardenedSession handles downloads and media permissions, not HTTP credentials. desktop main creates this manager supplies no credential-request integration. These links were checked against the recorded base commit.

A TypeScript AST inventory of every desktop source file found the following literal event registrations. This supplements manual inspection; it is not a proof about dynamically constructed event names:

The repository pins Electron 44.10.2. Its installed electron.d.ts documents app.login: default behavior cancels authentication; an application must prevent that default and call the callback with credentials. The WebContents login documentation delegates to that same contract. The test’s event payload matches this installed API, including navigation and first-attempt fields.

Inference: without a challenge handler and a credential-entry path, Electron’s default cancellation is the likely cause of the reported inability to authenticate. The test directly demonstrates that the manager does not prevent cancellation. Medium confidence is intentional because the actual Electron navigation and app-wide native lifecycle could not be exercised on this host.

6. Proposed fix and safety

Add an explicitly scoped credential-request flow for the native tab’s login event, prevent cancellation synchronously, and resolve its callback exactly once on submission or cancellation. Bind the request to its originating tab, origin, and challenge; cancel stale requests on navigation, tab destruction, or host/server changes. Keep credentials out of logs and persisted state. Define proxy challenges, repeated failures, automation-controlled tabs, and non-Basic schemes explicitly rather than silently extending trust.

Before implementation, run a real loopback challenge through a visible native tab, verify unauthenticated and explicit-credential controls, submit generated throwaway credentials, and confirm the authenticated retry. Then cover cancel, wrong credentials, navigation, and tab-close behavior. Windows integrated authentication is a separate test, not established by a Basic-only test.

const typescript = require("typescript");
const handlers = [];
let filesScanned = 0;

function inspect(directory) {
  for (const entry of readdirSync(directory, { withFileTypes: true })) {
    const filename = join(directory, entry.name);
    if (entry.isDirectory()) {
      inspect(filename);
      continue;
    }
    if (!/\.[cm]?tsx?$/.test(entry.name)) continue;
    filesScanned += 1;
    const source = typescript.createSourceFile(
      filename,
      readFileSync(filename, "utf8"),
      typescript.ScriptTarget.Latest,
      true,
    );
    function visit(node) {
      if (
        typescript.isCallExpression(node) &&
        typescript.isPropertyAccessExpression(node.expression) &&
        ["on", "once", "addListener"].includes(node.expression.name.text) &&
        node.arguments[0] &&
        typescript.isStringLiteralLike(node.arguments[0]) &&
        node.arguments[0].text === "login"
      ) {
        handlers.push({
          file: relative(root, filename),
          line: source.getLineAndCharacterOfPosition(node.getStart(source)).line + 1,
        });
      }
      typescript.forEachChild(node, visit);
    }
    visit(source);
  }
}
