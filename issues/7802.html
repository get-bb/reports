#7802 · Panel setup repeats during thread changes

Bug Priority: Medium Effort: Low ui perf · GitHub issue · 2026-11-19

Trusted base: 49d0b57a8c0fd2e1ea99f5323444c0ebcc03713c (origin/main at investigation start).

Verdict: REPRODUCED · Root-cause confidence: high

1. TL;DR

The right-hand panel initializes the selected thread's Info content twice when switching threads with a visibility-aware plugin tab registered. The first render uses a plain panel because visibility for the new thread has not been reported yet. A layout-effect report then enables the split-panel wrapper, replacing the content tree and running its setup again. A new focused component test exercises the real panel, built-in Info registration, plugin registration, and visibility hook: every one of ten thread switches produces two content effect activations. The same test in drawer mode produces one activation per switch.

            areFixedTabsReady={fixed.isReady}
            fixedTabs={[

                createThreadFixedTabDescriptor(entry, threadId, null, noop),

            tabs={[]}
            isConversationCollapsed={false}
            isOpen
            metadataContent={<Content threadId={threadId} />}
            onClose={noop}
            onCollapse={noop}
            onTabReorder={noop}
            onOpenNewTab={noop}
            onPanelFocus={noop}
            onToggleConversationCollapse={noop}
            renderAsDrawer={drawer}
            splitPanelStateId={threadId}
          />
        </PanelGroup>
      </TooltipProvider>
    </>
  );
}

beforeEach(() => {
  setups.length = 0;
  markPluginFrontendsSettled();
  setPluginSlotRegistrations(
    "mount-check",
    collectPluginAppRegistrations(
      definePluginApp((app) => {
        app.slots.experimental_tab({
          context: { kind: "thread" },
          availability: "fixed",
          id: "details",
          title: "Details",
          icon: "Info",
          useVisible: () => true,
          component: () => null,

      }),
    ),

});

afterEach(() => {
  cleanup();
  resetPluginSlotStoreForTest();
  resetPluginFrontendBootStateForTest();
  window.localStorage.clear();

it.each([false, true])(
  "activates content once per thread switch (drawer=%s)",
  (drawer) => {
    const { wrapper } = createQueryClientTestHarness();
    const view = render(<Host threadId="thr_first" drawer={drawer} />, {
      wrapper,
    });
    setups.length = 0;
    const counts: number[] = [];
    for (let index = 0; index < 10; index += 1) {
      const threadId = index % 2 === 0 ? "thr_second" : "thr_first";
      const previousCount = setups.length;
      view.rerender(<Host threadId={threadId} drawer={drawer} />);

    console.log(JSON.stringify({ drawer, activationsPerSwitch: counts }));
    expect(counts).toEqual(Array.from({ length: 10 }, () => 1));
  },

5. Root cause

  1. The thread view passes the real fixed-tab readiness flag and a thread-specific split-state ID to the panel.
  2. Readiness requires each applicable visibility-aware slot's report to match the new context key. Reports for the previous thread do not satisfy it.
  3. The observer reports from a layout effect, after the first new-thread tree has committed.
  4. Split eligibility includes readiness. Until readiness is true, the alternate branch renders a live flat surface. The next commit replaces it with SidebarSplitContainer, destroying and recreating the content subtree.
const shouldEnableSidebarSplits =
  !renderAsDrawer && splitPanelStateId !== undefined && areFixedTabsReady;
const panelSurface = shouldEnableSidebarSplits ? (
  <SidebarSplitContainer ... />
) : (
  renderPanelSurface(...)
);

This is not evidence that React StrictMode double invocation is responsible: the test does not enable StrictMode, and the drawer control under the same environment remains single. The underlying design problem is conflating stable split eligibility with transient tab-list readiness.

6. Proposed fix

Keep the panel's split-enabled identity independent of visibility readiness, and avoid mounting live content until its complete fixed-tab list is available. An existing loading skeleton can bridge that interval. Preserve the readiness guard on mounting/reconciling saved split state; merely removing the guard can restore layouts against an incomplete tab list. Preserve the drawer's flat path. Validate one-time setup, saved multi-pane restoration, pending plugin tabs, and repeated thread changes.

No production fix is made in this investigation: an existing open PR already closes this issue, so opening another would violate the duplicate-PR guard.
