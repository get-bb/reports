#7510 · Installed catalog metadata repeats screenshot validation warnings

BugMedium priorityLow effortpluginsIssue2026-11-13 · base 88cf8f644c81fca797ad80bc31bb36a61ce5cc9b

Verdict: REPRODUCED · Root-cause confidence: high

1. TL;DR

Listing installed plugins also reads their marketplace discovery metadata. For a git or path marketplace with a relative screenshot, that read calls the screenshot resolver with the server warning logger on every list invocation. The resolver omits the unsupported screenshot and emits the same diagnostic each time, even though the manifest itself is cached. Two clean checkouts reproduced exactly three warning calls for three installed-plugin list calls, for both git and path sources; the HTTPS control emitted none. This confirms the log-amplification mechanism, not the reporter's historical percentages or retention duration.

5. Root cause

PluginService.list() calls installedCatalogData(rows) for each list request. cachedMarketplaceManifest() caches only manifest parsing keyed by marketplace name and JSON. After that cache lookup, installedCatalogData() resolves metadata again with the live warning callback:

...catalogEntryMetadata({
  manifest,
  entry,
  base: marketplaceRowIconBase(marketplace),
  warn: (message) => logger.warn(message),
})

catalogEntryMetadata() passes that callback to entryScreenshotUrls(). marketplaceRowIconBase() maps every non-HTTPS source to a directory base. entryScreenshotUrls() warns and returns no screenshot for each relative declaration with that base. Nothing here remembers that the same diagnostic was already issued. The number of warning calls therefore grows with list calls × installed catalog entries × omitted relative screenshots.

The underlying lifecycle error is passing validation diagnostics through a frequently repeated metadata read. The existing marketplace materialization boundary already validates screenshot declarations with its own warning callback when a marketplace is loaded. The catalog-list metadata caller already omits a warning callback. Neither new global deduplication state nor protocol changes are necessary.

6. Proposed fix

Remove the optional warning callback from catalogEntryMetadata and its installed-plugin caller. Resolve screenshots without diagnostics during metadata reads, retaining the existing callback and validation behavior in entryScreenshotUrls at marketplace materialization. This removes repeated read-time logging without changing returned screenshots, introducing an unbounded warning cache, or suppressing unrelated parser and loading errors.

A local implementation makes one line replacement and two line deletions across two existing server modules. Its regression passes all three source-kind cases. All 202 relevant tests across nine service/catalog suites pass, and server typechecking passes. A broader run also found an unrelated generator timestamp-format assertion failure (UTC Z versus +00:00); the same assertion fails on the unchanged production baseline in the second checkout. That pre-existing generator test was not changed. The two logging reproductions below are against unchanged production.
