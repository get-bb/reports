#6968 · ACP prompt usage is not forwarded

BugPriority: MediumEffort: Mediumproviders · provider-acpGitHub issue

Verdict: REPRODUCED · Root-cause confidence: high · Reproduction label: confirmed-repro

1. TL;DR

The ACP bridge completes a prompt with a valid token-usage object but emits no token-usage event. A subprocess fixture delivering usage through the real bridge reproduces this on trusted main, while its context-window notification is forwarded successfully. The bridge validates only the prompt stop reason and handles Grok-specific context metadata; it never converts the standard prompt usage object into a usage delta. A second clean checkout produces the same failure. This confirms the bridge defect, not the reporter's installed Copilot version, Burn UI, or monetary totals.

5. Root cause

The bridge uses its own prompt-result schema, not the SDK response schema. It types only stopReason and passes through everything else without a typed usage contract:

export const acpPromptResultSchema = z
  .object({
    stopReason: acpStopReasonSchema,
  })
  .passthrough();

After a normal prompt resolves, the only usage-related action is grokContextUsageFromPromptResult(result). The compaction path has the same omission. The Grok helper reads _meta, not top-level usage.

Separately, usage_update translation emits context-window deltas, including optional cost, not token-count deltas. The shared assembler already knows how to produce token events when a kind: "usage" delta arrives. The missing producer is inside ACP, not in that assembler or the UI.

6. Proposed fix and safety decision

Validate optional prompt usage at the ACP boundary and translate accepted samples into the existing usage-delta contract, including both ordinary prompts and compaction. Retain context-window size and define how totals survive resume, session replacement, and cancellation. Missing or malformed optional usage must not break an otherwise valid prompt.

No automatic fix or PR: the “no product or architecture decision” simple-fix condition is not satisfied. The pinned SDK's generated types.gen.d.ts describes PromptResponse.usage as turn usage, but Usage.inputTokens and Usage.outputTokens as totals across all turns. Blindly summing cumulative samples double-counts, while treating per-turn samples as cumulative loses usage. Cache-inclusive versus cache-exclusive counters also need a defined dialect policy before subtraction is safe. The repository's AcpDialect does not currently define these accounting semantics.

The next bounded experiment is to capture two successive prompt responses from an approved test provider, plus cache-hit and session-resume cases, and resolve the counter contract before implementing the mapper. The dropped event itself is high-confidence; the correct monetary and cumulative mapping is not established by this reproduction.
