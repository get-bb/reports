#6311 · Navigation updates replace Markdown media elements

Bug Priority: Medium Effort: Low ui plugins · 2026-10-26 · GitHub issue

Trusted base: 3540a699e29034b53da32bb7efa6f5b4055209eb

Verdict: REPRODUCED · Root-cause confidence: high · Reproduction label: confirmed-repro

1. TL;DR

The SDK Markdown renderer replaces a video even when its content and source do not change. Changing only the host's openTab capability reproduces the defect through the real SDK implementation. The previous video is disconnected, its parent paragraph survives, and the new video's playback-position property starts at zero. The renderer builds component functions inside a factory that reruns when link routing changes, so React receives a new component type instead of merely new props. This is a deterministic DOM lifecycle reproduction, not a native macOS playback recording.

Full reproduction test
// @vitest-environment jsdom

import { cleanup, fireEvent, render, screen } from "@testing-library/react";
import { afterEach, beforeAll, expect, it, vi } from "vitest";
import { LazyMarkdownHtml } from "@/components/ui/lazy-markdown-html";
import { AppNavigationHostProvider } from "./app-navigation-host";
import { pluginSdkAppImplementation } from "./plugin-sdk-app-impl";

beforeAll(() => LazyMarkdownHtml.preload());
afterEach(cleanup);

it("retains SDK Markdown media when unrelated navigation capabilities change", () => {
  const Markdown = pluginSdkAppImplementation.Markdown;
  const content = 'Watch <video src="/media/lifecycle.mp4" title="Lifecycle"></video> and [navigate](/review).';
  const openUrl = vi.fn(() => true);
  const initialOpenTab = vi.fn(() => false);
  const nextOpenTab = vi.fn(() => true);
  const view = (openTab: typeof initialOpenTab) => (
    <AppNavigationHostProvider capabilities={{ openUrl, openTab }}>
      <Markdown content={content} />
    </AppNavigationHostProvider>
  );
  const { container, rerender } = render(view(initialOpenTab));
  const video = container.querySelector("video");
  expect(video).not.toBeNull();
  if (!video) throw new Error("Expected rendered video");
  const paragraph = video.parentElement;
  video.currentTime = 9;
  rerender(view(initialOpenTab));
  expect(container.querySelector("video")).toBe(video);
  rerender(view(nextOpenTab));
  const replacement = container.querySelector("video");
  const findings = {
    sameVideo: replacement === video,
    originalConnected: video.isConnected,
    sameParent: replacement?.parentElement === paragraph,
    sameSource: replacement?.getAttribute("src") === video.getAttribute("src"),
    currentTime: replacement?.currentTime,
  };
  console.log(JSON.stringify(findings));
  fireEvent.click(screen.getByRole("link", { name: "navigate" }));
  expect(openUrl).toHaveBeenCalledWith({ url: "/review" });
  expect(findings).toEqual({
    sameVideo: true,
    originalConnected: true,
    sameParent: true,
    sameSource: true,
    currentTime: 9,
  });
});

5. Root cause

  1. AppNavigationHostProvider recreates its resolved context value when any capability changes.
  2. PluginMarkdown depends on the entire navigation object for its open-link callback, so even an unrelated openTab change produces a new callback and linkRouting object.
  3. MarkdownPreview's components memo depends on linkRouting and rebuilds its component map.
  4. MarkdownVideo and MarkdownSource are function declarations inside buildMarkdownComponents, not stable module-level component types.
  5. The map is passed to the Markdown renderer. React reconciles a new video component type by replacing its subtree, while the stable paragraph renderer survives.
const markdownComponents = useMemo(
  () => buildMarkdownComponents({ ..., linkRouting, ... }),
  [..., linkRouting, ...],
);

function buildMarkdownComponents(...) {
  function MarkdownVideo(...) { ... }
  function MarkdownSource(...) { ... }
  return { ..., source: MarkdownSource, video: MarkdownVideo };
}

The excerpt is abbreviated; the permalinks contain the exact source. New component-map identity alone is not sufficient to explain remounting: the important detail is the newly allocated function types inside it. Reducing one SDK dependency would avoid some triggers but would leave other real routing/policy changes capable of destroying the media subtree.

6. Proposed fix

Keep renderer component types stable and supply changing render configuration through a render-scoped context or equivalent typed props. Do not freeze the initial routing configuration or use a global mutable object: links must continue using the current host handlers, and separate Markdown instances must not share configuration. Preserve current HTML sanitization and text-only media suppression. The attached identity regression should pass after repair; extend coverage to routing updates rather than merely memoizing one context producer.

No production fix, branch, or upstream PR was created.
