#7847 · Docs fork loses Markdown callback types

BugHighEffort: Lowplugins · docsopen issue2026-11-19

Trusted base: df9619d8e8aac4aff00c0c3ff9b8ef4e2823e4f2 (fetched from the public target repository's main branch).

Verdict: REPRODUCED · Root-cause confidence: high · Reproduction label: confirmed-repro.

1. TL;DR

The Docs plugin fails typechecking when copied out of the workspace and installed with current npm dependencies. The workspace's frozen dependency graph still typechecks. The fork resolves a newer Markdown implementation with bundled ESM declarations that do not support the namespace-as-instance-type import used by tiptap-markdown. That invalid library type removes the contextual types of two local renderer callbacks, producing four implicit-any errors. Two fresh checkouts at the same trusted main commit reproduced the failure without modifying production code.

5. Root cause

The fork checker resolves npm dependencies outside the workspace before running npm run typecheck. It is deliberately not the monorepo's frozen pnpm graph. Current installation resolves prosemirror-markdown@1.14.0, whose installed manifest allows markdown-it: ">=14 <=15".

bb-plugin-simple-notes@0.2.3
├─┬ @tiptap/pm@2.27.3
│ └─┬ prosemirror-markdown@1.14.0
│   └── markdown-it@15.0.3
└─┬ tiptap-markdown@0.8.10
  ├── @types/markdown-it@13.0.9
  ├── markdown-it@14.3.3
  └── prosemirror-markdown@1.14.0 deduped

The installed tiptap-markdown declaration imports import * as MarkdownIt from "markdown-it" and uses MarkdownIt as the setup callback's parameter type. Its nested 14.3.3 package has no matching TypeScript declaration. The resolver then finds the hoisted 15.0.3 package's own ESM types before falling back to the external @types package. Those ESM declarations export a named instance type and a default callable value; the namespace import is not that instance type.

With skipLibCheck enabled, the TS2709 errors inside the dependency are suppressed, but the local callbacks still lack contextual parameter types. The affected assignments are html_inline and html_block:

markdown.renderer.rules.html_inline = (tokens, index) => {
  const source = tokens[index]!.content;

markdown.renderer.rules.html_block = (tokens, index) => {
  const source = tokens[index]!.content;

Thus each of two callbacks produces two implicit-any errors. The shared CI fork-check step reaches this same path. The underlying dependency declaration mismatch is distinct from the local code's reliance on inferred callback parameters.

6. Proposed fix

Use explicit structural token-array and numeric-index parameter types at the two renderer assignments, reusing the existing local token interface. That keeps the code's actual input contract independent of the upstream declaration shape without changing dependencies or runtime behavior. An upstream declaration correction remains desirable. Validate any candidate against this external-fork reproduction as well as the Docs tests and workspace typecheck; a workspace-only typecheck does not exercise this failure.

No new fix branch or PR is created: an open linked PR already addresses this issue.
