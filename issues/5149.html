#5149 · Empty catalog persistence and query recovery

BugPriority: MediumEffort: Lowproviders · ui · provider-piGitHub issue2026-10-07 · base 7ea48db13

Verdict: PARTIALLY REPRODUCED · Root-cause confidence: medium overall; high for empty-cache persistence, low for the reported permanent lock.

1. TL;DR

A successful catalog response with no models is indeed saved to renderer localStorage. However, an enabled execution-options query still fetches after a simulated renderer restart and replaces that empty placeholder with a healthy catalog. This happened in both clean checkouts of trusted main. Explicitly disabling the query produces the reported combination of successful placeholder data, idle fetch status, no prior fetch, and isStale: false; enabling it starts the fetch. Empty persistence alone therefore does not explain the permanent failure, and this investigation does not establish which missing condition held in the desktop incident.

5. Root cause and limits

Confirmed persistence mechanism: the response write path checks only response.modelLoadError === null before saving the catalog. An empty successful catalog therefore qualifies. The placeholder resolver can read those empty arrays and presents them with no load error.

if (response.modelLoadError === null) {
  const catalog = {
    models: response.models,
    selectedOnlyModels: response.selectedOnlyModels,
  };
  writeCachedModelCatalog(
    modelCatalogCacheKey({ environmentId, hostId, providerId }),
    catalog,
  );
}

This is not proof of a permanent lock: the public query hook defaults to enabled and supplies the saved data as placeholderData, not as fetched query data. The installed TanStack queryObserver.ts loads an enabled query on mount when query.state.data === undefined. Its isStale calculation also explicitly returns false for a disabled query. Both behaviors were exercised rather than inferred solely from source.

Unresolved routing risk: stored provider selection precedes availability checking, and ready-provider discovery only runs for an empty stored selection. The issue's additional stale-provider allegation is a separate hypothesis, not a verified explanation for why a Pi-only recovery would never fetch.

6. Fix proposal and simple-fix gate

No production fix or pull request is offered. The reported permanent failure has not been reproduced on trusted main, and there is no focused regression that fails before a fix for that failure. Merely skipping empty writes would not explain or repair an explicitly disabled query or an incorrectly routed provider request.

The next decisive experiment is an isolated desktop reproduction that records the mounted composer's execution-options enabled value, actual query key/provider route, observer identity, and request activity before and after credential repair. If an empty response overwrites a useful prior catalog, deciding whether to retain it is a separate cache-policy question: a legitimate zero-model response must not silently become an indefinitely stale nonempty catalog.
