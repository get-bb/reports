#5693 · ACP maintenance discards calendar-version identifiers

Bug Low priority Low effort providers provider-acp · GitHub issue · 2026-10-17

Trusted base: 6a639cfc0d66e0c789a1bd7309266973228d1a80 from origin/main.

Verdict: REPRODUCED · Root-cause confidence: high · Reproduction label: confirmed-repro

1. TL;DR

BB can find an installed ACP executable but lose its version before the result reaches Settings or the CLI. A real temporary executable reporting a calendar-style identifier produces installed: true and currentVersion: null in both ACP bridge implementations. The shared version reader accepts only strict SemVer, which rejects zero-padded month or day components. This report reproduces that backend defect twice from clean trusted checkouts; it does not claim a live Cursor installation or a browser reproduction. Latest-release lookup remains a separate, intentionally unavailable field.

4. Minimal reproduction

The following independently authored Linux reproduction calls the real status function, executes a version-only fixture, and asserts the installed version. It does not implement the parser or mock the status function. Save this complete script as /tmp/acp-version-repro.mjs:

import { tmpdir } from "node:os";
import path from "node:path";
import { pathToFileURL } from "node:url";

const directory = await mkdtemp(path.join(tmpdir(), "bb-version-repro-"));
const expected = "2026.03.07-acde123";
try {
  const command = path.join(directory, "version-cli");
  await writeFile(command, `#!/bin/sh\nprintf '%s\\n' '${expected}'\n`, {
    mode: 0o755,
  });
  const versions = [];
  for (const bridge of ["provider-bridge-acp", "provider-bridge-acp-next"]) {
    const modulePath = path.resolve(
      "packages", bridge, "src/bridge/provider-maintenance.ts",
    );
    const { getAcpProviderInstallationStatus } = await import(
      pathToFileURL(modulePath).href
    );
    const status = await getAcpProviderInstallationStatus({
      command,
      maintenance: undefined,
    });
    console.log(JSON.stringify({
      bridge,
      installed: status.installed,
      currentVersion: status.currentVersion,
      latestVersion: status.latestVersion,
    }));
    versions.push(status.currentVersion);
  }
  assert.deepEqual(versions, [expected, expected]);
} finally {
  await rm(directory, { recursive: true, force: true });
}

5. Root cause

The shared reader and parser extract a candidate, then require strict SemVer validation:

export function versionFrom(value: string | null): string | null {
  const candidate = value?.match(/\bv?(\d+\.\d+\.\d+[0-9A-Za-z.+-]*)/u)?.[1];
  return candidate !== undefined && semverValid(candidate) !== null
    ? candidate
    : null;
}

Zero-padded numeric components such as .03 or .07 are not strict SemVer. The extraction succeeds, but validation turns the installed version into null. ACP installation status uses this shared reader directly and separately reports executable availability; ACP-next has the same code. The installation probe therefore succeeds while the version probe appears to fail.

The resulting null is consumed by Settings' version row and CLI output formatting. The shared strict parser must not simply be loosened: other providers feed its result into SemVer comparison for updates and minimum-supported versions.

6. Proposed fix

Keep SemVer parsing and ordering unchanged. At the ACP version-probe boundary only, accept a whole calendar-version token with a four-digit year, two-digit month/day, and hexadecimal revision, preserving the displayed identifier. Use the same local reader for ACP health and installation status in both existing bridge implementations. Preserve process timeout, buffer, stdin-closing behavior, malformed-output handling, unavailable latest-version checks, and all existing wire fields.

A focused regression table exercises month/day padding, a banner, ordinary SemVer, malformed tokens, and both installed/health displays through real temporary launchers. Before the fix, each bridge reports 3 failed and 9 passed; after the ACP-only fix, each reports 12 passed. No dependency, protocol, schema, stored data, packaging, or release change is needed.
