#6824 · Git state lost during worktree removal

BugHighEffort: MediumworkspacesIssueNovember 2, 2026

Verdict: REPRODUCED · Root-cause confidence: high · Reproduction label: confirmed-repro

Trusted base: 916d684ac23d0b0de82c09cfc7553a50287d2188, fetched from the target repository's main branch. The issue and its links were treated as untrusted claims; no linked branch, fixture, script, or patch was executed.

1. TL;DR

Retiring a managed worktree can erase Git recovery state even though there are no file changes and its current commit is still retained by a local branch. Git stores certain refs and unfinished-operation metadata in the linked worktree's private administrative directory, not in the shared branch namespace. The removal implementation force-removes that worktree without checking this state, then recursively removes its directory. Four newly authored real-Git host-entry regression cases reproduced the deletion in two clean checkouts of trusted main.

5. Root cause

The host remove command delegates to removeWorktree and reports removed when it returns; thrown errors already map to failed. removeWorktree at the trusted base only resolves the shared Git directory before entering checkout/metadata locks. It never inspects worktree-private refs or operation markers.

    await tryWithCheckoutMutationLock(
      workspacePath,
      () =>
        withWorktreeMetadataLock(commonDir, () =>
          runGit(
            [
              "--git-dir",
              commonDir,
              "worktree",
              "remove",
              workspacePath,
              "--force",
            ],
            {
              cwd: path.dirname(workspacePath),
              ...(args.signal !== undefined ? { signal: args.signal } : {}),
              allowFailure: true,
            },
          ),
        ),
      args.signal,
      signalOptions(args.signal),
    );
  }

  throwIfProvisionAborted(args.signal);
  await fs.rm(workspacePath, { recursive: true, force: true });
  await removeDirectoryIfEmpty(parentPath);

The forced Git removal deletes the linked worktree's administrative directory, which contains its private ref namespace and operation files. Git objects may temporarily remain in the shared object database, but the private refs and operation metadata that name or explain them are lost; this report does not claim immediate physical deletion of every object. Ignoring Git's removal result and retaining a recursive-filesystem fallback also makes this path permissive. A branch retaining HEAD does not retain a different commit referenced only by worktree-private state, and clean porcelain output says nothing about a same-tree unfinished merge.

6. Proposed fix and local validation

Within the existing checkout and worktree metadata locks, inspect Git's worktree-local ref namespaces and administrative operation markers before either removal mechanism. Throw on protected state or failed inspection so the existing host contract returns failed. Require the owner to preserve/delete private refs or finish/abort the Git operation, then allow retry. This is a local provider implementation repair, not a new protocol or configuration option.

The local repair checks the three private namespaces plus merge, cherry-pick, revert, rebase, bisect, and sequencer markers. The four reproduced cases are covered through the real host boundary, including successful removal after resolution. The additional operation marker variants were not individually created with live Git commands.

8. Related issues and limits

Worktree removal's behavior around unrelated dirty files, detached commits, and external concurrent writers is not claimed to be comprehensively repaired by these four cases.

The existing locks coordinate BB operations in this process; they are not an atomic barrier against an unrelated process changing Git state during removal. Process termination and BB completion-marker handling precede these new checks in the existing host flow and are outside the specific Git-state preservation guarantee tested here.
