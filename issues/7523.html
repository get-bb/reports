#7523 · File-change lifecycle retains duplicate diff payloads

Bug Priority: Medium Effort: Medium threads perf provider-pi GitHub issue

November 13, 2026 · trusted origin/main commit faa89fb46f03f9a1cd83d60355ab94c48da76f80

Verdict: REPRODUCED · Root-cause confidence: high · Reproduction label: confirmed-repro

1. TL;DR

A completed pi file edit leaves the same unified diff in two database event rows: the pending item and its completion. The pi translator carries the original file-change shape through both lifecycle stages, and the shared assembler builds a full diff for each event. Database ingestion persists both payloads; none of the existing maintenance policies removes or compacts this pair. A new regression test reproduces that storage behavior for both edit and write through the real translator, assembler, migrated SQLite database, and all four pruning policies. The same test fails for the same reason in a second clean trusted checkout. This verifies the duplication mechanism, not the reporter's private database sizes or macOS installation.

Complete reproduction test

import { describe, expect, it } from "vitest";
import { and, eq, sql } from "drizzle-orm";
import { type ThreadEvent } from "@bb/domain";
import { createPiDeltaTranslator } from "../../../../plugins/provider-pi/src/delta-translation.js";
import { createDeltaAssembler } from "../../../provider-bridge-protocol/src/assembler/delta-assembler.js";
import { createMigratedConnection } from "../../src/testing.js";
import { noopNotifier } from "../../src/notifier.js";
import { upsertHost } from "../../src/data/hosts.js";
import { createProject } from "../../src/data/projects.js";
import { createThread } from "../../src/data/threads.js";
import { appendDaemonEventsInTransaction } from "../../src/data/events.js";
import { deriveStoredEventItemFields } from "../../src/stored-event-item-fields.js";
import { advanceThreadPruning, THREAD_PRUNING_POLICIES } from "../../src/data/thread-pruning.js";
import { events } from "../../src/schema.js";

describe("completed file-change storage", () => {
  it.each(["edit", "write"])("retains one diff after %s completes and maintenance finishes", (toolName) => {
    const db = createMigratedConnection();
    try {
      const host = upsertHost(db, noopNotifier, { name: "repro-host" });
      const { project } = createProject(db, noopNotifier, {
        name: "repro-project",
        source: { type: "local_path", hostId: host.id, path: "/tmp/repro-project" },
      });
      const thread = createThread(db, noopNotifier, {
        status: "idle", projectId: project.id, providerId: "pi",
      });
      const translator = createPiDeltaTranslator({ resolveModelContextWindow: () => null });
      const assembler = createDeltaAssembler({
        providerId: "pi", entropyPrefix: "storage-repro", textDeltaFlushMs: 0,
      });
      const persist = (providerEvent: unknown) => {
        const translated: ThreadEvent[] = assembler.assemble({
          threadId: thread.id,
          deltas: translator.translate(providerEvent, { threadId: thread.id, cwd: "/tmp/repro-project" }),
        });
        db.transaction((transaction) => appendDaemonEventsInTransaction(transaction, translated.map((event) => {
          const { scope, type, threadId: unstampedThreadId, ...data } = event;
          return {
            threadId: thread.id, scope, type, environmentId: null, providerThreadId: null,
            ...deriveStoredEventItemFields(event), data: JSON.stringify(data),
          };
        })));
      };
      const readFileChanges = () => db.select({
        type: events.type,
        sequence: events.sequence,
        status: sql<string>`json_extract(${events.data}, '$.item.status')`,
        changes: sql<string>`json_extract(${events.data}, '$.item.changes')`,
        diff: sql<string>`json_extract(${events.data}, '$.item.changes[0].diff')`,
      }).from(events).where(and(eq(events.threadId, thread.id), eq(events.itemKind, "fileChange"))).orderBy(events.sequence).all();
      const oldText = Array.from({ length: 128 }, (_, index) => `entry-${index}: previous\n`).join("");
      const newText = Array.from({ length: 128 }, (_, index) => `entry-${index}: revised\n`).join("");
      persist({ type: "agent_start" });
      persist({
        type: "tool_execution_start", toolCallId: "file-operation", toolName,
        args: toolName === "edit"
          ? { path: "storage-sample.txt", oldText, newText }
          : { path: "storage-sample.txt", content: newText },
      });
      const pending = readFileChanges();
      expect(pending).toHaveLength(1);
      expect(pending[0]?.status).toBe("pending");
      expect(pending[0]?.diff).toContain("entry-127: revised");
      persist({
        type: "tool_execution_end", toolCallId: "file-operation", toolName,
        result: { content: [{ type: "text", text: "operation complete" }] }, isError: false,
      });
      persist({ type: "agent_end", messages: [] });
      for (const policy of THREAD_PRUNING_POLICIES) {
        let finished = false;
        for (let pass = 0; pass < 1000; pass += 1) {
          if (advanceThreadPruning(db, policy).action === "cycle-complete") {
            finished = true;
            break;
          }
        }
        expect(finished).toBe(true);
      }
      const retained = readFileChanges();
      const completed = retained.find((row) => row.type === "item/completed");
      expect(completed?.status).toBe("completed");
      expect(completed?.diff).toContain("entry-127: revised");
      console.log(JSON.stringify({
        toolName,
        maintenancePolicies: THREAD_PRUNING_POLICIES,
        rows: retained.map(({ type, sequence, status, diff }) => ({ type, sequence, status, diffChars: diff?.length ?? 0 })),
        identicalChanges: retained.length === 2 && retained[0]?.changes === retained[1]?.changes,
      }));
      expect(retained.filter((row) => row.diff?.length > 0)).toHaveLength(1);
    } finally {
      db.$client.close();
    }
  });
});

5. Root cause

  1. Pi tool classification turns a valid edit/write argument into a fileChange shape containing oldText/newText (or newText for a write).
  2. Pi lifecycle translation remembers that shape when opening the tool item and reuses the remembered shape at successful completion. It is not merely a status update.
  3. buildFileChanges constructs the unified diff from the carried text. Item open emits that full item in item/started; item close builds and emits the full completed item again.
  4. Server envelope conversion serializes the whole event payload. The test mirrors this narrow conversion, using the real thread identity because assembler output is runtime-stamped downstream. Daemon-event append then inserts both lifecycle events. Its terminal-event deduplication prevents repeated completions, not a start/completion payload pair.
  5. The pruning event-type allowlist does not include either file-change lifecycle event. Resolved-item delta kinds cover text, reasoning, and command output, not file changes. Documented retention expressly keeps fileChange events.

The underlying problem is a missing post-completion storage compaction policy for redundant file-change snapshots, not an accidental double call to the insert function. Both lifecycle messages have legitimate live behavior; retaining their complete payloads forever is what creates the duplicate storage.

6. Proposed fix and autopilot safety decision

Introduce bounded server/database compaction only after a matching terminal event proves that the started diff is redundant. Preserve the pending diff before completion and preserve the completed diff. Require matching thread, item, turn, and parent scope; preserve differing payloads and unfinished operations. Audit timeline reconstruction, log readers, pagination anchors, rewrite-generation invalidation, restarted/reused item identities, failure/interruption, and latest-event safeguards before deciding between compacting the started payload and removing the started event. Add witness-mismatch and still-open-item coverage alongside this regression.

No fix PR is opened. A storage-layer repair changes persisted-event retention/data, which this autopilot explicitly excludes. Dropping the diff at provider start instead would alter live event meaning and pending behavior, so it is not a safe substitute. There were no linked open PRs in issue metadata and no open PR search match for the numeric issue at the final check. No production file was changed, committed, or pushed.
