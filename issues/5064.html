#5064 · Inline edits do not reserve queued messages

BugPriority: MediumEffort: HighthreadsuiGitHub issue2026-10-06

Verdict: REPRODUCED · Root-cause confidence: high

Trusted origin/main base: 587ac3e908468c7b2b6aafd81ea1e84975211162

1. TL;DR

Starting an inline edit does not reserve the queued message against automatic claiming. The editor stores a separate unsaved draft while the database continues to hold the previous saved text. When a busy thread becomes idle, the real automatic eligibility predicate and transactional queue claimer accept that saved message, despite the open edit session. A save then receives the database's claimed result; after the claim is consumed and the queue snapshot refreshes, the actual React hook discards its editing state. Two fresh source checkouts reproduce this lifecycle; provider delivery and a live desktop session were not exercised.

6. Proposed fix and simple-fix gate

Introduce server-recognized edit admission ordered atomically against dispatch claiming. If dispatch has already claimed the item, do not open an editable session; if editing wins, exclude the held row and its dispatch group until Save or Cancel. Save must atomically update the payload and release the hold; Cancel must release the hold without changing the saved payload. Group membership and explicit-send behavior must respect the same admission rule.

The ownership, disconnected-client cleanup, expiry/recovery, and multi-client behavior require an explicit lifecycle design. Reusing the existing manual-stop pause would block unrelated messages and does not implement per-item admission. Merely retaining the React draft would leave the saved payload dispatchable.
