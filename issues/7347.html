#7347 · Question cancellation misattributes lifecycle interruptions to the user

Bug Medium priority Low effort plugins ask-user-question

GitHub issue · 2026-11-10 · base 7c1353d80729983b86ea1555d18b42407f320406

Verdict: REPRODUCED · Root-cause confidence: high · reproduction label: confirmed-repro

1. TL;DR

A pending question can end because its plugin is disposed, without any answer or dismissal from the user. The question tool nevertheless reports that the user dismissed it and tells the model it may proceed using its own judgement. Its cancellation handler treats timeout specially but collapses every other reason into the user-dismissal message. A regression exercising the real tool registration and the SDK harness disposal lifecycle fails identically in two clean checkouts. A two-file, 24-changed-line repair preserves actual user-dismissal and timeout behavior while describing lifecycle interruptions truthfully.

5. Root cause

The tool cancellation handler distinguishes only timeout:

result.reason === "timeout"
  ? buildTimeoutMessage(Date.now() - askedAt)
  : "The user dismissed the question without answering. Proceed with your best judgement, or ask again in your reply."

The SDK cancellation contract distinguishes user, request-aborted, thread-stopped, thread-deleted, plugin-disposed, server-restarted, and timeout. Only user indicates deliberate dismissal. The harness disposal implementation resolves the actual pending request with plugin-disposed; it does not manufacture the tool's text. The real interaction service disposal path uses the same reason. Its startup path records server-restarted for interrupted active plugin rows.

The lost distinction is inside this plugin's result translation, not its public contract. Existing tests cover deliberate dismissal but do not cover disposal while awaiting an answer.

6. Proposed fix and local validation

Use the dismissal message only for explicit user cancellation. Keep the existing timeout message. For all remaining reasons, return a neutral interruption error that identifies the reason and states that the user has not responded. Do not prescribe a new retry/stop/continue policy. No protocol, schema, stored data, permissions, dependencies, packaging, or public API changes are needed.
