#7360 · Concurrent server startup removes another live server's pending fork

BugHighEffort: Mediumhost · confirmed-reproGitHub issue2026-11-10 · base 7c1353d80729983b86ea1555d18b42407f320406

Verdict: REPRODUCED · Root-cause confidence: high

1. TL;DR

A second real server process can start against a directory already used by a healthy server. On a different port, both processes answer health checks after the newcomer soft-deletes a pending fork. On the same port, the newcomer still soft-deletes the fork before reporting a listener conflict. These observations were repeated by the same investigator from a second clean checkout, using fresh data directories and new temporary ports.

import {
  createConnection,
  createThread,
  ensurePersonalProject,

  migrate,

} from "@bb/db";

const serverDir = dirname(fileURLToPath(import.meta.url));

async function freePort() {
  const listener = createServer();
  await new Promise((resolve) => listener.listen(0, "127.0.0.1", resolve));
  const address = listener.address();
  assert(address !== null && typeof address === "object");
  await new Promise((resolve) => listener.close(resolve));
  return address.port;
}

async function healthy(port) {
  try {
    const response = await fetch(`http://127.0.0.1:${port}/health`, {
      signal: AbortSignal.timeout(500),
    });
    return response.ok;
  } catch {
    return false;
  }
}

async function until(predicate) {
  const deadline = Date.now() + 30_000;
  while (Date.now() < deadline) {
    if (await predicate()) return;
    await sleep(50);
  }
  throw new Error("Timed out waiting for a server outcome");
}

async function runCase(mode) {
  const directory = await mkdtemp(join(tmpdir(), "bb-7360-data-"));
  const home = join(directory, "home");
  await mkdir(home);
  const db = createConnection(join(directory, "bb.db"));
  migrate(db);
  setPluginSafeMode(db, true);
  const project = ensurePersonalProject(db);
  const firstPort = await freePort();
  const secondPort = mode === "same-port" ? firstPort : await freePort();
  const hostPort = await freePort();
  const children = [];
  const outputs = [];
  const launch = (port) => {
    const child = spawn(process.execPath, ["dist/index.js"], {
      cwd: serverDir,
      env: {
        PATH: process.env.PATH,
        HOME: home,
        NODE_ENV: "test",
        BB_DATA_DIR: directory,

    child.stderr.on("data", (chunk) => output.push(chunk.toString()));

      assert.equal(first.exitCode, null, outputs[0].join(""));

      projectId: project.id,
      providerId: "codex",
      status: "pending",

        kind: "pending",

        historyCopy: "copying",
        startedOnBehalfOf: null,
        titleProvided: false,

    assert.notEqual(getThread(db, pending.id), null);

      if (second.exitCode !== null) return true;
      if (mode === "different-port") return healthy(secondPort);
      return outputs[1].join("").includes("EADDRINUSE");
    });
    await sleep(100);
    const logs = [];
    for (const name of await readdir(join(directory, "logs"))) {
      if (/^server\.\d+\.log$/.test(name)) {
        logs.push(await readFile(join(directory, "logs", name), "utf8"));
      }
    }

      line.includes("Deleted forks whose history copy"),

    const result = {
      mode,
      firstPort,
      secondPort,
      firstAlive: first.exitCode === null,

5. Root cause

Server startup does not acquire data-directory ownership before migrations and recovery; recovery treats every copying fork as abandoned, even while another server is alive.

  • apps/server/src/start-server.ts:133 creates the logger, checks interrupted-import state, initializes the database, and applies import boot with no exclusive data-directory claim.
  • apps/server/src/db.ts:32 executes migrate(db) during initialization.
  • apps/server/src/start-server.ts:504 awaits startup recovery before starting the HTTP listener.
  • apps/server/src/services/system/periodic-sweeps.ts:881 runs interrupted-fork cleanup and queued-claim release.
  • apps/server/src/services/threads/thread-create.ts:419 marks each copying fork deleted and requests its storage deletion, without checking whether another process owns the work.
  • apps/server/src/services/threads/queued-messages.ts:747 protects only this process's active claim tokens when releasing stale claims.
  • packages/bb-app/src/launcher.ts:4206 refuses only after an occupied runtime record and a healthy response at the candidate's own listener URL. The reproduction bypasses the launcher through the real standalone server entrypoint.

The deeper invariant is single live ownership of recovery-sensitive state, not uniqueness of a listening TCP port. SQLite's normal write locking does not express ownership of the entire server lifecycle.

6. Proposed fix and autopilot gate

Introduce atomic OS-backed lifetime ownership before database initialization, retain it until all server work stops, and release it on startup failure and shutdown. Reuse the shared native-lock implementation rather than adding a second dependency or relying on a racy PID probe.

No automatic PR: the available OS-backed lock is private to the shared configuration subsystem and scoped to short file mutations. Safely reusing it needs a new shared locking contract plus server-lifecycle integration, beyond this rule's one-existing-subsystem limit. A PID-only probe would leave simultaneous-start races and standalone servers uncovered.

The reusable native lock currently lives in packages/config/src/file-lock.ts:50 and is called by packages/config/src/managed-json-file.ts:11. It is not exposed through a config package subpath, and the server does not declare the native locking dependency. Do not deep-import it or introduce an undeclared dependency to force a smaller diff. A proper change must also test concurrent starts, startup failure, abrupt exit, stale artifacts, separate directories, and import/move/shutdown interactions. No production patch or fix branch was created or pushed.

9. Appendix and limits

The copying marker is inserted through the real database API while the first server is healthy; this is not a real provider performing a concurrent history transfer. The test demonstrates erroneous classification and destructive recovery against another live owner's state, not completed user-data loss or a live queued-message duplicate. Database initialization/import ordering is established by source, without fabricating a pending migration or imported data set.

The initial whole-repository build failed because the GitHub plugin required missing plugin-SDK runtime entries. Building SDK types alone did not resolve that unrelated prerequisite; a Turbo SDK runtime build followed by the focused server build succeeded. The second checkout also completed the focused build. No dependency or lockfile was changed. Existing tests: 17 passed in three files. The new regression fails on unchanged production code in both clean runs. Tracked diffs passed git diff --check.
