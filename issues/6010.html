#6010 · Cold-start signal wait expires before valid worker readiness

BugPriority: LowEffort: LowhostGitHub issue2026-10-21

Trusted base: b143a22860944a96bf183605dfb0ffe58b1de283.

Verdict: REPRODUCED · Root-cause confidence: high · Reproduction label: confirmed-repro.

1. TL;DR

The environment-overlap tests wait for a handler-start signal using a one-second polling timeout, even though the real worker is allowed ten seconds to become ready. The first call must start a new process and import the plugin before that signal can exist. A regression extending the existing overlap test with a real 1.5-second plugin initialization reproduces the zero-signal assertion in two separate clean checkouts, without changing production code. Giving the fixture's signal wait an explicit ten-second budget makes the same delayed case pass. This proves the test-harness timing defect; the original downstream CI logs and its natural load profile were not independently verified.

5. Root cause

The test fixture has fifteen-second commands but leaves vi.waitFor at its one-second default:

const waitForStart = (id: string) =>
  vi.waitFor(() => expect(onSignal).toHaveBeenCalledWith(started(id)));

The two cold overlap tests start waiting immediately after their first manager.call. Manager dispatch awaits worker readiness, after artifact preparation and the child-process fork. The worker imports the plugin before sending ready. Only afterward can the environment handler emit its start signal. Therefore any valid initialization longer than a second exhausts the test's wait before the handler can run.

The manager's ten-second startup limit is enforced by its startup timer. This is a mismatch in test timing, not evidence for changing the production timeout, protocol, or cancellation policy.

6. Proposed fix

Give this fixture's shared start-signal wait an explicit ten-second timeout, consistent with the worker's existing startup allowance and below the fixture's fifteen-second call deadline. Retain the table-driven 0ms/1500ms overlap case as the regression: it exercises the real child-process import and continues checking environment retention through overlapping cancellation. No production seam, dependency, or runtime behavior needs to change.

const waitForStart = (id: string) =>
  vi.waitFor(() => expect(onSignal).toHaveBeenCalledWith(started(id)), {
    timeout: 10_000,
  });

A local candidate with exactly this wait change passed both focused cases after the two red runs. Broader validation is required before opening a fix PR.
