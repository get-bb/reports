#7739 · Usage refresh failures retain previous readings

Bug Medium priority Medium effort providers plugins · Issue · 2026-11-17

Trusted base: 8d99f6dc2fd7430ee65f550828e1670fa9f5dfbe

PARTIALLY REPRODUCED · Root-cause confidence: high for silent refresh failures; disabled-source persistence is not reproduced on current main.

1. TL;DR

A failed usage request can leave the last successful reading looking healthy. Through the real Account Pooler server entry and its published usage RPC, HTTP 401, HTTP 429, malformed usage data, and a thrown network error all returned the previous successful measurement without logging anything. The same four regression cases failed at the missing-warning assertion in two separately installed clean checkouts. However, current Provider Usage and core plugin-service tests remove disabled sources correctly: the reported persistent disabled-source group was not reproduced on this main commit. Account Pooler supplies an observation timestamp, but Provider Usage does not carry that timestamp into its display snapshot.

  async (failure) => {

    let usageRequests = 0;

      source: "oauth",
      options: {
        claudeLogin: async () => claudeCredentials(),
        usageUrl: "https://usage.invalid/usage",

          usageRequests += 1;
          if (!failing)
            return Response.json({ five_hour: { utilization: 37 } });
          if (failure === "transport") throw new Error("Synthetic network failure");
          if (failure === "schema") return Response.json({ five_hour: [] });
          return Response.json({}, { status: failure });
        },
      },
    });
    const read = async () => usageMeasurementSchema.parse(
      await fixture.host.harness.behavior.callRpc(usageFetchMethod, {
        resourceId: fixture.account.id,

5. Root cause

Claude usage adapter: non-OK responses cancel the body without throwing or notifying the logger. JSON parse failure is converted to null. A successful HTTP response whose payload produces no quota also returns normally.

if (response.ok) {
  const payload = await response.json().catch(() => null);
  ...
  if (quota !== null) context.quotas.put(quota);
} else {
  await response.body?.cancel();
}

Usage validation returns null for invalid or absent usage data, leaving the previous stored quota untouched. Hub refresh suppresses thrown transport errors too:

if ((this.inFlightByAccount.get(account.id) ?? 0) > 0) return;
...
.catch(() => undefined)
.finally(() => this.usageRefreshes.delete(account.id));

The source RPC then sees an existing observation and no stored account error, so it returns status ok and the old timestamp/windows. This explains the unchanged successful RPC measurement; it does not establish the historical disabled-source incident.

Provider Usage normalization and its strict snapshot schema omit the source observation timestamp. The cache's loadedAt is separate from the upstream observation time.

Important counter-evidence: readUsage rediscovers live sources on every call and evicts missing inventories. The core disable/discovery test calls the real plugin service, disables a plugin, and verifies its published RPC disappears. Both checks passed.

6. Proposed fix and simple-fix decision

Separate last successful observation from last refresh attempt. For logging, turn unsuccessful usage HTTP responses and invalid payloads into bounded, credential-free failures and report them through the plugin logger; include only the numeric HTTP status, not bodies or authorization headers. Preserve known usage values when a refresh fails, but expose failure/freshness rather than presenting them as newly observed. A refreshed successful reading should clear the transient failure indication.

To show age in Provider Usage, carry observedAt through its RPC snapshot and render it for every source. Keep the current disabled-source eviction behavior; investigate the historical environment before changing plugin disable policy.

No production fix or PR was attempted. The complete issue repair crosses Account Pooler and Provider Usage and needs a user-facing RPC schema/UI freshness change, violating the one-subsystem/no-public-schema simple-fix limits. A logging-only PR would not safely close the broader issue. No linked open PR was found in the issue timeline or the open-PR search. The only target-repository change is a 43-line reproduction test addition; no production source, dependency, stored data, or protocol was modified.
