#6841 · Global instruction scope and unverified instruction provenance

BugMedium priorityMedium effortthreadsIssue2026-11-02 · base f2ca46c3da7f67121967bea93781ef021f34f405

Verdict: PARTIALLY REPRODUCED · Root-cause confidence: high for the loading mechanism; the provenance of the reported global file is unverified.

1. TL;DR

A nonempty instruction file in bb's data directory is included in unrelated projects' runtime prompts. Two clean trusted checkouts confirm that behavior with synthetic content, while a workspace instruction remains local to its own project. This is the documented purpose of the global file, not an accidental traversal into the bb source repository. A fresh test data directory does not contain a prewritten instruction file, and no production writer installing the reported repository rules was identified. The report therefore verifies cross-project loading, but not the claim that bb ships or creates those repository-specific global contents, nor any particular model response.

Reproduction source

import { access, mkdir, writeFile } from "node:fs/promises";
import path from "node:path";
import { expect, it } from "vitest";
import { resolveThreadRuntimeCommandConfig } from "../../src/services/threads/thread-runtime-config.js";
import {
  seedEnvironment,
  seedHostSession,
  seedProjectWithSource,
  seedThread,
} from "../helpers/seed.js";
import { withTestHarness } from "../helpers/test-app.js";

it("observes global instruction reuse across unrelated projects and workspace isolation", async () => {
  await withTestHarness(async (harness) => {
    const hostId = "host-6841-repro";
    seedHostSession(harness.deps, { id: hostId });
    const globalPath = path.join(harness.config.dataDir, "AGENTS.md");
    await expect(access(globalPath)).rejects.toMatchObject({ code: "ENOENT" });
    const globalMarker = "SYNTHETIC_GLOBAL_MARKER_6841";
    const workspaceMarker = "SYNTHETIC_WORKSPACE_MARKER_6841";
    for (const projectName of ["alpha", "beta"]) {
      const workspacePath = path.join(harness.config.dataDir, projectName);
      await mkdir(path.join(workspacePath, ".bb"), { recursive: true });
      if (projectName === "alpha") {
        await writeFile(
          path.join(workspacePath, ".bb", "AGENTS.md"),
          workspaceMarker,
        );
      }
      const { project } = seedProjectWithSource(harness.deps, {
        hostId,
        path: workspacePath,
      });
      const environment = seedEnvironment(harness.deps, {
        hostId,
        projectId: project.id,
        path: workspacePath,
      });
      const thread = seedThread(harness.deps, {
        projectId: project.id,
        environmentId: environment.id,
        providerId: "codex",
      });
      const resolve = () =>
        resolveThreadRuntimeCommandConfig(harness.deps, {
          thread,
          model: "test-model",
          environment: {
            hostId: environment.hostId,
            id: environment.id,
            path: environment.path,
            status: environment.status,
          },
        });
      await writeFile(globalPath, "");
      const emptyGlobal = await resolve();
      expect(emptyGlobal.instructions).not.toContain(globalMarker);
      expect(emptyGlobal.instructions).not.toContain("<dataDir>/AGENTS.md");
      await writeFile(globalPath, globalMarker);
      const populatedGlobal = await resolve();
      expect(populatedGlobal.instructions).toContain(globalMarker);
      expect(populatedGlobal.instructions).toContain(
        "The following user instructions come from <dataDir>/AGENTS.md:",
      );
      expect(populatedGlobal.instructions.includes(workspaceMarker)).toBe(
        projectName === "alpha",
      );
      console.log(
        projectName +
          ": empty-global=absent; populated-global=included; workspace=" +
          (projectName === "alpha" ? "included" : "absent"),
      );
    }
    console.log("Fresh data directory: no AGENTS.md was preinstalled.");
  });
});

5. Root cause

The server deliberately reads the same nonempty data-directory AGENTS.md for every project and appends it as user instructions; workspace-specific files use a separate scoped path. The origin of the reported repository-specific global contents is unverified.

The file reader ignores missing/empty files and otherwise returns trimmed file contents. It does not provide repository-specific default text:

  const trimmed = content.trim();
  return trimmed.length > 0 ? trimmed : null;
}

export function readDataDirAgentInstructions(
  logger: ServerLogger,
  dataDir: string,
): string | null {
  return readAgentInstructionsFile(
    logger,
    path.join(dataDir, DATA_DIR_AGENT_INSTRUCTIONS_RELATIVE_PATH),
  );
}

The runtime builder reads from the server's data directory, without a project selector:

  const dataDirAgentInstructions = readDataDirAgentInstructions(
    deps.logger,
    deps.config.dataDir,
  );

The prompt assembly attributes those contents as user instructions and separately appends workspace-scoped instructions:

  if (dataDirAgentInstructions) {
    instructionSections.push(
      `The following user instructions come from <dataDir>/${DATA_DIR_AGENT_INSTRUCTIONS_RELATIVE_PATH}:`,
      dataDirAgentInstructions,
    );
  }
  if (workspaceAgentContext.agentInstructions) {
    instructionSections.push(
      `The following workspace instructions come from ${WORKSPACE_AGENT_INSTRUCTIONS_RELATIVE_PATH}:`,
      workspaceAgentContext.agentInstructions,
    );
  }
  const instructions = instructionSections.join("\n\n");

This distinction is explicitly documented in the CLI guide and configuration documentation. Existing runtime tests protect the ordering. Git history traces this deliberate feature to commit 55289654987f07060909b04d61668230765756fa, which introduced data-directory instruction support.

If project rules are placed in the global file, their cross-project application follows directly from this contract. The investigation cannot determine who or what placed the reporter's contents there. No claim is made that a fresh production installation ships those rules.

6. Proposed fix and safety decision

First establish the provenance of the populated global file: which installation, import, backup restoration, user action, or external tool last wrote it. Repository-specific rules belong in that repository's workspace instruction file; global preferences can remain in the data-directory file. Any corrective migration must preserve intentional global preferences and must not silently rewrite user-owned files.

No automated source PR. No production regression requiring a code change was established. Scoping all data-directory instructions to bb would alter documented user-facing configuration and requires a product decision. The provenance needed for a narrower safe fix is missing. No fix branch, commit, or target-repository push was made.
