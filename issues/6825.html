#6825 · Latest-state reads scan unrelated extension snapshots

BugHigh priorityHigh effortthreads · perf · confirmed-repro IssueNovember 2, 2026 · base 916d684ac23d0b0de82c09cfc7553a50287d2188

Verdict: REPRODUCED · Root-cause confidence: high

1. TL;DR

Looking for a thread state whose kind is missing or old still reads every newer extension-state snapshot for that thread. The earlier query rewrite removed repeated scans across the outer result set, but the remaining descending lookup does not have an indexed kind to seek to. With one synthetic thread and 6,000 unrelated 22 KB snapshots, the actual production function took 46.6–58.8 ms for an absent kind, versus about 0.1 ms when the newest row matched. The exact emitted SQL also consumed 48,053 SQLite VM instructions for the absent kind, increasing by eight instructions for every additional unrelated row. Both clean-checkout runs reproduced this behavior; the reported whole-server pause cadence and proxy resets were not tested.

5. Root cause

The forced partial index keys only thread and sequence; kind remains a JSON predicate evaluated while scanning newer state rows. SQLite seeks to a thread, then walks candidates in descending sequence until the kind predicate accepts one. LIMIT 1 limits returned rows, not rejected rows visited. Every newer extension-state candidate must expose its JSON kind before SQLite can reject it; an absent kind exhausts that thread's state range. Cost is proportional to the number of candidates examined and the payload parsing work, not merely the number of requested threads.

6. Proposed fix and automation boundary

Add an indexed, kind-aware state access path through the existing Drizzle schema and generated migration pipeline. Query native goal events and extension-state events of the requested kind separately, then pick the newest candidate by sequence so the current cross-type semantics remain intact. An expression or stored kind index must match the actual JSON expression and partial predicate. Verify absent kinds, old kinds, native update/clear precedence, variable batching, and migration behavior on existing databases. Index creation on large histories requires operational consideration.
