#5004 · Injected question visibility after turn completion

BugPriority: MediumEffort: Mediumui · plugins · ask-user-question · provider-piIssue2026-10-06 · base df913a79dc687341d9bec06e483ff545376225de

Verdict: NOT REPRODUCED · Root-cause confidence: low · Reproduction label: no-repro

1. TL;DR

The report describes a multiple-choice question that never appeared in a visible Pi thread, although the server recorded a pending interaction. I tested the real bundled Ask User Question plugin through the authenticated injected-tool route, on a visible thread whose provider is Pi. In two clean trusted-main checkouts, the public interaction API retained the question after a completed turn and through the last millisecond before the configured 30-minute timeout. The timeout and non-blocking tool result are expected server behavior, not evidence that a form rendered. The missing desktop card remains unverified: this host lacks Chrome/Chromium, so Browser Automation could not open a browser, and no actual Pi CLI session or desktop AppImage was exercised.

This verdict does not invalidate the reported occurrence, close the issue, or claim an existing fix. No visual reproduction, screenshot, or root cause for the missing card is established.

Full reproduction test
import { eq } from "drizzle-orm";
import { events, pendingInteractions } from "@bb/db";
import { turnScope } from "@bb/domain";
import { groupHostDaemonEvents } from "@bb/host-daemon-contract";
import { describe, expect, it, vi } from "vitest";
import { PLUGIN_TOOL_CALL_AWAITING_USER_RESULT_TEXT } from "../../../src/services/plugins/plugin-tool-calls.js";
import { internalAuthHeaders } from "../../helpers/commands.js";
import {
  seedEnvironment,
  seedHostSession,
  seedProjectWithSource,
  seedThread,
  seedTurnStarted,
} from "../../helpers/seed.js";
import { withTestHarness } from "../../helpers/test-app.js";

describe("issue 5004 injected question lifecycle", () => {
  it("keeps the real plugin question discoverable after a Pi turn completes, until its 30-minute timeout", async () => {
    await withTestHarness(async (harness) => {
      const installed = await harness.pluginService.install(
        "builtin:ask-user-question",
        { kind: "root" },
      );
      expect(installed.status).toBe("running");
      const { host, session } = seedHostSession(harness.deps);
      const { project } = seedProjectWithSource(harness.deps, { hostId: host.id });
      const environment = seedEnvironment(harness.deps, {
        hostId: host.id,
        projectId: project.id,
      });
      const thread = seedThread(harness.deps, {
        projectId: project.id,
        environmentId: environment.id,
        providerId: "pi",
        status: "active",
        visibility: "visible",
      });
      const turnId = "turn-question-repro";
      const providerThreadId = "provider-question-repro";
      seedTurnStarted(harness.deps, { threadId: thread.id, turnId, providerThreadId });
      const notify = vi.spyOn(harness.hub, "notifyThread");
      vi.useFakeTimers();
      try {
        const startedAt = Date.now();
        const toolResponse = await harness.app.request("/internal/session/tool-call", {
          method: "POST",
          headers: internalAuthHeaders(harness),
          body: JSON.stringify({
            sessionId: session.id,
            threadId: thread.id,
            providerThreadId,
            turnId,
            callId: "call-question-repro",
            tool: "AskUserQuestion",
            arguments: {
              questions: [{
                header: "Choice",
                question: "Which sample should run?",
                options: [
                  { label: "First", description: "Run the first sample." },
                  { label: "Second", description: "Run the second sample." },
                ],
              }],
            },
          }),
        });
        expect(toolResponse.status).toBe(200);
        expect(await toolResponse.json()).toMatchObject({
          success: true,
          contentItems: [{ type: "inputText", text: PLUGIN_TOOL_CALL_AWAITING_USER_RESULT_TEXT }],
        });
        expect(notify).toHaveBeenCalledWith(thread.id, ["interactions-changed"], {
          hasPendingInteraction: true,
          projectId: project.id,
        });
        const list = async () => {
          const response = await harness.app.request(`/api/v1/threads/${thread.id}/interactions`);
          expect(response.status).toBe(200);
          return response.json();
        };
        const expectedQuestion = [{
          status: "pending",
          origin: { kind: "plugin", pluginId: "ask-user-question", rendererId: "ask-user-question" },
          payload: { kind: "plugin", data: { questions: [{ prompt: "Which sample should run?" }] } },
          expiresAt: startedAt + 30 * 60_000,
        }];
        expect(await list()).toMatchObject(expectedQuestion);
        await vi.advanceTimersByTimeAsync(7_000);
        const completed = await harness.app.request("/internal/session/events", {
          method: "POST",
          headers: internalAuthHeaders(harness),
          body: JSON.stringify({
            sessionId: session.id,
            eventGroups: groupHostDaemonEvents([{
              threadId: thread.id,
              event: {
                type: "turn/completed",
                threadId: thread.id,
                providerThreadId,
                scope: turnScope(turnId),
                status: "completed",
              },
            }]),
          }),
        });
        expect(completed.status).toBe(200);
        expect(await list()).toMatchObject(expectedQuestion);
        await vi.advanceTimersByTimeAsync(30 * 60_000 - 7_001);
        expect(await list()).toMatchObject(expectedQuestion);
        await vi.advanceTimersByTimeAsync(1);
        expect(await list()).toEqual([]);
        const stored = harness.db.select().from(pendingInteractions)
          .where(eq(pendingInteractions.threadId, thread.id)).all();
        expect(stored).toMatchObject([{ status: "interrupted", statusReason: "timeout" }]);
        const lifecycle = harness.db.select().from(events)
          .where(eq(events.threadId, thread.id)).all()
          .filter((event) => event.type === "system/interaction/lifecycle")
          .map((event) => JSON.parse(event.data));
        expect(lifecycle.map((event) => event.interaction.status)).toEqual(["pending", "interrupted"]);
      } finally {
        notify.mockRestore();
        vi.useRealTimers();
      }
    });
  });
});

5. Root cause

The missing-card root cause is not established. The observed server sequence has an expected explanation, but that explanation does not account for a card being absent:

  • The tool registers a suppressed transcript presentation and a 30-minute UI request. Suppressing its tool row does not suppress the separately rendered interaction form.
  • requestInput creates the interaction and detaches the provider-facing tool call. This allows a normal turn completion before the user responds.
  • The returned acknowledgement is fixed server text. It is not a client-side rendering receipt and cannot establish that the user saw the form.
  • The lifecycle persists a plugin-scoped interaction, schedules its expiry, and notifies clients. Its turnId is null. The new test verifies retention across the completion route and the timeout.
  • Interaction-change events invalidate the pending-interaction query, and the active thread queries the public list API.
  • The prompt footer renders the active interaction independently of a completed turn's transcript row. An unavailable or still-loading renderer has fallback content, so a missing plugin slot alone does not explain an entirely absent card.

The matching production timestamps therefore support creation and timeout, not a Pi-specific renderer failure. A lost/refused list fetch, missed real-time notification, wrong active-thread state, footer geometry, or an AppImage-specific frontend state is still possible; none was reproduced here.

6. Proposed fix / next experiment

No production patch is justified yet. On a fresh actual Pi session with a working desktop/browser, call the injected tool while the thread is open and capture: the pending-list HTTP response immediately after creation and after turn completion; the delivered WebSocket interactions-changed notification; the selected query key; frontend plugin renderer state; and a full-window screenshot including the composer/footer. Compare that with a reload of the same still-pending interaction. These observations distinguish transport/cache loss from renderer mounting or layout. Only then add a failing regression at the responsible boundary.
