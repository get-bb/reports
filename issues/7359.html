#7359 · Legacy composer preferences are ignored after compatibility retirement

BugPriority: LowEffort: Lowuiconfirmed-reproGitHub issue2026-11-10 · base 7c1353d80729983b86ea1555d18b42407f320406

Verdict: REPRODUCED · Root-cause confidence: high

1. TL;DR

A browser profile containing only the old global model and reasoning preferences does not restore those preferences on current main. The saved provider survives, but both selection hooks return an empty string, allowing the composer to use its catalog defaults. The old values remain in localStorage; this is selection non-restoration, not deletion of their bytes. Importantly, the original per-provider change did include compatibility reads: a later cleanup deliberately removed them. Reinstating that retired upgrade policy is outside this automation's simple-fix scope.

Complete reproduction test:

// @vitest-environment jsdom

import { cleanup, renderHook } from "@testing-library/react";
import { createStore, Provider } from "jotai";
import type { ReactNode } from "react";
import { afterEach, beforeEach, describe, expect, it } from "vitest";
import {
  usePromptBoxModelPreference,
  usePromptBoxProviderPreference,
  usePromptBoxReasoningLevelPreference,
} from "./persisted-selection-fields";

beforeEach(() => {
  window.localStorage.clear();
  window.sessionStorage.clear();
  window.localStorage.setItem("bb.promptbox.provider", "codex");
  window.localStorage.setItem("bb.promptbox.model", "remembered-model");
  window.localStorage.setItem("bb.promptbox.reasoning", "high");
});

afterEach(() => {
  cleanup();
  window.localStorage.clear();
  window.sessionStorage.clear();
});

function renderRememberedSelection(providerOverride?: string) {
  const store = createStore();
  const wrapper = ({ children }: { children: ReactNode }) => (
    <Provider store={store}>{children}</Provider>
  );
  return renderHook(
    () => {
      const provider = usePromptBoxProviderPreference();
      const providerId = providerOverride ?? provider.value;
      return {
        provider: provider.value,
        model: usePromptBoxModelPreference(providerId).value,
        reasoning: usePromptBoxReasoningLevelPreference(providerId).value,
      };
    },
    { wrapper },
  );
}

describe("legacy composer upgrade compatibility", () => {
  it.each([
    { field: "model", expected: "remembered-model" },
    { field: "reasoning", expected: "high" },
  ] as const)(
    "retains the legacy $field for its saved provider",
    ({ field, expected }) => {
      const { result } = renderRememberedSelection();
      expect(result.current.provider).toBe("codex");
      expect(result.current[field]).toBe(expected);
    },
  );

  it("prefers existing provider-scoped selections over legacy selections", () => {
    window.localStorage.setItem("bb.promptbox.model-codex-1", "newer-model");
    window.localStorage.setItem("bb.promptbox.reasoning-codex-1", "low");
    const { result } = renderRememberedSelection();
    expect(result.current).toEqual({
      provider: "codex",
      model: "newer-model",
      reasoning: "low",
    });
  });

  it("does not transfer the saved provider's choices to a different provider", () => {
    const { result } = renderRememberedSelection("claude-code");
    expect(result.current).toEqual({
      provider: "codex",
      model: "",
      reasoning: "",
    });
  });
});

5. Root cause

Current scoped model read derives a versioned key from the provider, then reads through a string codec that only falls back to its initial empty string. The reasoning read similarly uses only its scoped key. No legacy fallback is present.

return `${storageKey}-${encodeURIComponent(providerId.trim())}-${PROVIDER_SELECTION_STORAGE_VERSION}`;
parse: (value, initialValue) => value ?? initialValue

The shared tab-scoped storage reader looks first in sessionStorage, then localStorage for that same scoped key, parses the result, and snapshots the resulting default into sessionStorage. It never searches the old key.

Historical correction: the original per-provider commit (04953f96ac, August 11, 2026) did read the legacy keys when the saved provider matched. Commit 3f28c07f25, September 30, 2026, removed those functions as expired compatibility. Its trusted commit description explicitly includes unscoped model/reasoning migrations among the retired one-shot localStorage paths. The symptom exists, but attributing its origin to the initial per-provider change is incorrect.

6. Proposed fix and safety decision

If maintaining direct upgrades from the pre-per-provider format is still product policy, restore guarded compatibility at this existing preference-storage boundary. Preserve modern local/session values, require a matching saved provider, validate reasoning, and define one-time migration/removal behavior so a provider switch cannot import another provider's stale data.

No automatic fix or PR: main deliberately retired this compatibility. Reinstating it changes legacy stored-data upgrade policy and needs a product decision, violating the rule's simple-fix conditions. No production code was modified, no fix branch was created or pushed, and no replacement test was copied from issue text. No open PR linked to this issue was found in its cross-reference metadata or an open-PR search at investigation time.
