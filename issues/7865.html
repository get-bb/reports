#7865 · Docs editor has no link activation path

Bug Medium priority Low effort ui · docs

Issue #7865 · November 19, 2026 · trusted base 1ed5e771bbee1d050c6654b52a7aff05b7cd3d59

Verdict: REPRODUCED · Root-cause confidence: high

1. TL;DR

Docs displays Markdown links, but its editor has no working activation path for them. The actual plugin component renders a relative document link, yet clicking it does not call the existing Docs navigation API. An HTTPS link likewise never reaches bb's URL opener, even with Control or Command held. Tiptap's built-in link opening is explicitly disabled, and no replacement click handler or document-navigation callback is supplied to the editor. Six focused interaction checks fail in each of two clean trusted checkouts with production code unchanged.

5. Root cause

The Tiptap initialization registers Link.configure({ openOnClick: false, autolink: true }). Its editor props handle Escape, image paste, and image drop, but provide no link click handler. The editor receives document path and preview context but no callback for following another vault document. Links therefore remain editable content without triggering application navigation.

Link.configure({ openOnClick: false, autolink: true })

NotePane already receives an onOpen callback, but only invokes it after saving a copy. It does not pass that callback through SavedDocumentEditor to TiptapEditor. Merely enabling Tiptap's default opening would not repair vault-relative routing: relative URLs need the document's directory and vault, not the page's browser URL.

The app's existing URL-opening capability already owns desktop/browser preferences. The fix should use it rather than introducing a second opener. The issue is in plugin client wiring, not daemon transport, vault storage, or permissions.

6. Proposed fix

Add one shared editor click handler. Resolve supported relative Markdown document paths against the current note directory and call the existing vault navigation callback; pass that callback from the vault panel and inline/thread document surfaces. Send HTTP(S) URLs through useBbNavigate().openUrl. Read current callbacks through refs so a mounted editor does not retain stale navigation state. Preserve right-click editing/context-menu behavior. Keep fragment/query handling and relative links outside vault-backed contexts out of this narrow repair.

Focused coverage should exercise all three vault-backed surfaces, ordinary/Control/Command clicks, parent and nested directories, URL-encoded filenames, unsupported hrefs, and context-menu clicks. No dependency, public API, protocol, schema, storage, or authorization change is needed.
