#8033 · Provider archive rejection is not surfaced

BugPriority: MediumEffort: Mediumthreads · providers · provider-codex

GitHub issue · 2026-11-23 · trusted main 796cdcc0f4bf8a55e23664035c54e8db6fe9d272

Verdict: PARTIALLY REPRODUCED · Root-cause confidence: high for BB's server-side failure visibility and repeat-archive behavior; no conclusion about the external lock owner.

1. TL;DR

BB archives a thread in its own database before its provider archive command settles. A failed provider command is logged, but the archive response remains successful and the ordinary thread-detail response does not contain the failure. Repeating the archive request on that archived thread returns an empty success and does not send another provider archive command. This mechanism was reproduced twice against unchanged production code using a real migrated SQLite database and an injected negative host-RPC response. The Windows/Desktop active-writer conflict, native archive state, and Desktop lists were not reproduced on this Linux host.

Complete reproduction test
import { getThread } from "@bb/db";
import { expect, it, vi } from "vitest";
import {
  listQueuedThreadCommands,
  reportQueuedCommandError,
  waitForQueuedCommand,
} from "../helpers/commands.js";
import { seedThreadFixture, seedThreadIdentity } from "../helpers/seed.js";
import { withTestHarness } from "../helpers/test-app.js";

it("makes a rejected provider archive visible to the archive caller", async () => {
  await withTestHarness(async (harness) => {
    const { environment, thread } = seedThreadFixture(harness, {
      environment: { path: "/tmp/archive-provider-repro", status: "ready" },
      thread: { status: "idle", providerId: "codex" },
    });
    seedThreadIdentity(harness.deps, {
      environmentId: environment.id,
      threadId: thread.id,
      providerThreadId: "synthetic-provider-thread",
    });
    const warning = vi.spyOn(harness.deps.logger, "warn");
    try {
      const response = await harness.app.request(
        `/api/v1/threads/${thread.id}/archive-all`,
        { method: "POST" },
      );
      const archiveResult = await response.json();
      const command = await waitForQueuedCommand(
        harness,
        ({ command }) =>
          command.type === "thread.archive" && command.threadId === thread.id,
      );
      const providerFailure = "synthetic provider refused archival";
      await reportQueuedCommandError(harness, command, {
        errorCode: "synthetic_archive_rejection",
        errorMessage: providerFailure,
      });
      await vi.waitFor(() =>
        expect(warning).toHaveBeenCalledWith(
          expect.objectContaining({ threadId: thread.id }),
          "Live thread archive command failed",
        ),
      );
      expect(response.status).toBe(200);
      expect(archiveResult).toEqual({
        ok: true,
        archivedThreadIds: [thread.id],
      });
      expect(getThread(harness.db, thread.id)).toMatchObject({
        archivedAt: expect.any(Number),
        status: "idle",
      });
      const retry = await harness.app.request(
        `/api/v1/threads/${thread.id}/archive-all`,
        { method: "POST" },
      );
      const retryResult = await retry.json();
      expect(retryResult).toEqual({ ok: true, archivedThreadIds: [] });
      expect(
        listQueuedThreadCommands(harness, "thread.archive", thread.id),
      ).toEqual([]);
      const detail = await harness.app.request(`/api/v1/threads/${thread.id}`);
      expect(detail.status).toBe(200);
      const detailResult = await detail.json();
      console.log(
        JSON.stringify({
          archiveHttpStatus: response.status,
          archiveOk: archiveResult.ok,
          archivedLocally: getThread(harness.db, thread.id)?.archivedAt !== null,
          providerFailureLogged: true,
          retryArchivedCount: retryResult.archivedThreadIds.length,
          retryProviderCommandCount: listQueuedThreadCommands(
            harness,
            "thread.archive",
            thread.id,
          ).length,
          providerFailureInThreadDetail: JSON.stringify(detailResult).includes(
            providerFailure,
          ),
        }),
      );
      expect(JSON.stringify(detailResult)).toContain(providerFailure);
    } finally {
      warning.mockRestore();
    }
  });
});

5. Root cause

  1. Local archive precedes asynchronous provider forwarding: archiveThreadAndReleaseChildren commits local archive state; dispatchSettledArchivedThreadProviderArchiveCommand is then called without any returned provider outcome.
  2. The provider archive error callback only logs a warning. startLiveHostCommand runs detached and returns void.
  3. Live result settlement has no thread.archive handler: an archive success or failure returns empty side effects rather than recording a synchronization outcome.
  4. The archive route returns ok true with local archive IDs; the CLI derives success from local metadata only. The API/CLI success is therefore not proof of native-provider success.
  5. Already-archived candidates skip provider archive dispatch, explaining the observed no-op repeat request.
  6. The daemon awaits runtime archive; Codex maintenance forwards unrecognized failures and only retries rename; archive invokes native thread/archive. These source paths explain how a native rejection can reach BB's logged-only failure handler; they were inspected, not run against a live provider.

The root cause is a missing product-level synchronization outcome and recovery contract, not proof that BB owns the native writer lock. A valid local archive can coexist with a failed provider archive. Rolling back local archive, bypassing writer protection, or stopping unrelated runtimes is not justified by this evidence.

6. Proposed fix and simple-fix assessment

Define explicit provider-sync states and an idempotent retry action for an already locally archived thread. Surface the settled failure through the shared API/SDK path and user-facing controls, while preserving intentional local-archive and running-turn grace semantics. Specify behavior for offline hosts, unsupported providers, repeated requests, and delayed settlement before implementation.

No fix PR: a durable, recoverable cross-surface synchronization result requires a product/API or persistence decision and spans the lifecycle plus its presentation surfaces. That fails the autopilot's no-product-decision / single-subsystem simple-fix gate. A wording-only change would not make the failure recoverable. No production code was changed, and no fix branch was pushed.
