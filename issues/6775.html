#6775 · ACP completion infers success from unfinished tool work

BugPriority: MediumEffort: Mediumproviders · provider-acp · partial-reproIssue2026-10-31 · base 916d684ac23d0b0de82c09cfc7553a50287d2188

PARTIALLY REPRODUCED · Root-cause confidence: medium for the reported Kimi incident; high for the demonstrated bridge behavior.

1. TL;DR

The real ACP translator and event assembler can mark an unfinished tool as completed and display its last progress text as its result when a prompt ends. A synthetic argument preview reproduces the argument-shaped result without any model or provider account. The same path treats every stop reason except cancellation as completed, including synthetic failed and error values, with a warning for those unfamiliar values. However, explicit ACP failed-tool updates and provider errors do retain failure status. No ACP trace of the reported Kimi incident is available here, so this does not establish that Kimi transmitted a failure signal which bb discarded.

import { describe, expect, it } from "vitest";
import { createDeltaAssembler } from "@bb/provider-bridge-protocol/assembler";
import type { ProviderRuntimeEvent } from "@bb/provider-bridge-protocol/bridge-kit";
import {
  ACP_TURN_COMPLETED_METHOD,
  ACP_TURN_STARTED_METHOD,
  ACP_UPDATE_METHOD,
} from "./bridge-protocol.js";
import { createAcpDeltaTranslator } from "./delta-translation.js";
import { acpPromptResultSchema } from "./wire.js";

const threadId = "synthetic-acp-failure";
const argumentsText = JSON.stringify({ key: "sample" });
const failureText = "Synthetic provider operation could not finish";

function harness() {
  const translator = createAcpDeltaTranslator({ cwd: "/workspace" });
  const assembler = createDeltaAssembler({
    providerId: "acp",
    entropyPrefix: "repro",
    textDeltaFlushMs: 0,
  });
  function send(method: string, params: Record<string, unknown>) {
    const event: ProviderRuntimeEvent = {
      jsonrpc: "2.0",
      method,
      params: { threadId, ...params },
    };
    return assembler.assemble({
      threadId,
      deltas: translator.translateAcpEvent(event, { threadId }),
    });
  }
  send(ACP_TURN_STARTED_METHOD, {});
  send(ACP_UPDATE_METHOD, {
    update: {
      sessionUpdate: "tool_call",
      toolCallId: "operation-1",
      title: "Lookup record",
      kind: "other",
      status: "in_progress",
      rawInput: { key: "sample" },
      content: [
        { type: "content", content: { type: "text", text: argumentsText } },
      ],
    },
  });
  return { send };
}

5. Root cause

  1. The prompt response boundary accepts any string as a stop reason: packages/provider-bridge-acp/src/wire.ts:378. The actual session/prompt response is read and its stop reason forwarded unchanged: packages/provider-bridge-acp/src/bridge/bridge.ts:3124 and packages/provider-bridge-acp/src/bridge/bridge.ts:3019.
  2. packages/provider-bridge-acp/src/delta-translation.ts:866 maps cancellation to interrupted and every other string to completed:
    return stopReason === "cancelled" ? "interrupted" : "completed";
    Unrecognized values produce a warning, not a provider error (packages/provider-bridge-acp/src/delta-translation.ts:893). Therefore synthetic failed/error stop reasons still complete successfully in the timeline.
  3. packages/provider-bridge-acp/src/delta-translation.ts:605 drains unfinished calls with the inferred turn status, rather than requiring a terminal tool update. packages/provider-bridge-acp/src/delta-translation.ts:911 invokes that drain during completion.
  4. Tool close uses the accumulated content as result text (packages/provider-bridge-acp/src/delta-translation.ts:597). Content extraction prefers the latest textual content over rawOutput (packages/provider-bridge-acp/src/tool-classification.ts:119). The assembler chooses shape.result ?? close.resultText for generic tools (packages/provider-bridge-protocol/src/assembler/delta-assembler.ts:1032). Consequently, an argument preview can become the final result if no actual result update replaces it.
  5. This does not demonstrate blanket failure suppression. Terminal failed tool updates use their received status (packages/provider-bridge-acp/src/delta-translation.ts:724). A rejected prompt enters the bridge error path (packages/provider-bridge-acp/src/bridge/bridge.ts:3162), and error envelopes settle the turn as failed (packages/provider-bridge-acp/src/delta-translation.ts:937).

The causal gap is provider-internal failure versus the ACP messages bb actually receives. If Kimi returns ordinary end_turn while omitting failed-tool updates, there is no transmitted error text for bb to recover. If it rejects session/prompt, existing bridge behavior should already expose that error. A captured isolated ACP exchange is needed to choose between these paths.

6. Proposed fix and safety decision

No production fix or pull request is published. First capture a fresh isolated Kimi failure at the ACP transport boundary and compare the complete prompt response and tool notifications with bb's events. If that trace contains failed/error stop reasons, add a narrowly evidenced mapping and focused regression test. If it contains normal completion and no terminal notifications, correct the provider failure propagation and decide how incomplete tool progress should be represented rather than inventing an error message or treating preview text as proof of success.

Existing coverage explicitly preserves normal completion plus notices for unfamiliar non-cancellation reasons (packages/provider-bridge-acp/src/delta-translation.test.ts:1293). Reclassifying all unfamiliar reasons or unfinished tools without provider evidence would be a behavior/product decision, not the fully demonstrated contained fix this automation permits. No dependency, protocol, schema, stored data, security boundary, or production file was changed. No linked open PR was found in cross-reference metadata or an open-PR body search.
