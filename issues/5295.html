#5295 · Cached runtime executable breaks new provider workers

BugPriority: MediumEffort: Mediumhostproviders GitHub issue2026-10-09 · base 635711463bc2e2dbeb9e0158acd25cdcb30ba279

Verdict: REPRODUCED · Root-cause confidence: high · reproduction label: confirmed-repro

1. TL;DR

A running BB agent runtime can keep serving an existing provider worker while failing to start a new one after its original Node executable disappears. BB records the resolved executable filename, not the stable alias used to start the process. Retargeting that alias to an identical replacement does not change the recorded filename. The real BB model-discovery path then rejects the new worker with an ENOENT startup error, while launching a fresh runtime through the replacement alias restores discovery. This was reproduced twice on trusted main at the shared agent-runtime boundary, not against a real enrolled Mac or authenticated Codex/Claude processes.

Regression test

import { spawnSync } from "node:child_process";
import { copyFileSync, mkdtempSync, rmSync, symlinkSync } from "node:fs";
import { tmpdir } from "node:os";
import { join } from "node:path";
import { fileURLToPath } from "node:url";
import { expect, it } from "vitest";

it("loads a new provider catalog after the runtime alias is replaced", () => {
  const fixtureRoot = mkdtempSync(join(tmpdir(), "bb-runtime-alias-"));
  try {
    const originalPath = join(fixtureRoot, "original-node");
    const replacementPath = join(fixtureRoot, "replacement-node");
    const stablePath = join(fixtureRoot, "stable-node");
    copyFileSync(process.execPath, originalPath);
    copyFileSync(process.execPath, replacementPath);
    symlinkSync(originalPath, stablePath);
    const result = spawnSync(stablePath, [
      "--conditions=source", "--import", "tsx",
      fileURLToPath(new URL("./runtime-node-replacement.repro.ts", import.meta.url)),
      "replace", fixtureRoot,
    ], { encoding: "utf8", timeout: 30_000 });
    console.log(result.stdout);
    expect(result.error).toBeUndefined();
    expect(result.stderr).toBe("");
    expect(result.stdout).toContain("fresh runtime through replacement alias: catalog loaded");
    expect(result.status).toBe(0);
  } finally {
    rmSync(fixtureRoot, { recursive: true, force: true });
  }
}, 35_000);

The test deletes only the executable copies it created. The second launch uses a different artifact digest so it requests a genuinely new provider process rather than reusing the first worker. Baseline and recovery controls exercise real catalog loading and would catch a broken fixture. The desired-behavior assertion fails on unchanged production code, not on a mocked spawn response.

5. Root cause

  1. runtime.ts:312–318 constructs the provider-process manager with bridgeNodeExecutablePath: process.execPath. The fixture proves that process.execPath is the removed target even though process.argv0 records the stable alias.
  2. provider-registry.ts:25–48 sets the adapter command to that explicit filename. Its fallback to node is irrelevant because the runtime supplied a filename.
  3. runtime-provider-process.ts:364–381 sends that command to the real managed-process spawner. After unlinking the original target, the OS cannot open it.
  4. runtime-provider-process.ts:534–545 rejects pending requests with the provider startup error containing ENOENT. In this reproduction the bridge artifact exists, the initial catalog works, and no cwd changes: the missing file is the BB runtime executable, not a provider CLI or working directory.
bridgeNodeExecutablePath: process.execPath,
command: adapterOptions.bridgeNodeExecutablePath ?? "node",
command: processConfig.command,

The host connection is separate from provider worker creation. This test confirms continuing parent and existing-worker activity, but does not itself establish network connectivity. A stable invocation alias alone is not an end-to-end remedy: launcher.ts:2789–2802 starts an intermediate server using process.execPath, and shim-support.ts:60–80 does the same for a supervised child. At that boundary the alias is no longer the child command. plugin-host-manager.ts:450–466 also uses fork without explicit execPath. These inspected paths establish cross-subsystem work required for comprehensive recovery; their replacement behavior was not separately executed.

6. Proposed fix and simple-fix decision

Preserve a stable, trusted runtime reference across the launcher/supervisor/daemon/runtime chain, and validate a replacement before spawning a new worker. Compatibility and startup validation must account for runtime version/ABI/architecture and any native-addon or shared-library constraints; an existing alias is not proof of compatibility. Keep the explicit executable behavior for GUI environments and the Electron mode handled by defaultBridgeNodeEnv. Do not silently switch to PATH discovery. Report runtime unavailability separately from a missing provider executable or cwd.

No automatic PR: a root-cause repair is not confined to one existing subsystem and needs an end-to-end runtime-selection/compatibility contract. A runtime-only argv0 fallback cannot recover an alias already lost by an intermediate launcher. Changing the launcher/runtime propagation and replacement policy exceeds the simple-fix gate. No production patch, branch, push, or pull request was created.
