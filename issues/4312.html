TL;DR

A protected PR with pending checks is summarized as Blocked even though its check badge remains pending. The server computes both facts correctly, then gives generic blocking precedence over specific waiting reasons. The app renders that attention value using the destructive color token. This is reproduced using the actual server and display functions; the original desktop screenshot and live auto-merge workflow were not reproduced.

Root cause

Server mergeability and attention maps BLOCKED/BEHIND/HAS_HOOKS to blocked, then returns blocked before examining review or pending checks. Failing checks and requested changes run earlier and are not masked.

Display mapping assigns Blocked the text-destructive token. Badge mapping independently reads checks.state, explaining the two different signals.

Host requested fields omit auto-merge and merge-queue state. Sidebar contract provides only the rolled-up state and attention.

Proposed fix and simple-fix decision

Define which known waiting reasons take precedence over generic blocking, preserve failure/conflict precedence, and decide the presentation for automatic merging. Add tests for protected pending, protected review, failed, clean-ready and queued states. Auto-merge and queue support require host data and SDK contract work. No PR was opened: the complete remedy crosses existing subsystems and public contracts and needs display-policy decisions, outside the rule's simple-fix criteria. A precedence-only change would leave the automatic-merge and contract gaps unresolved.
