#6131 · ACP forms lose optional-property semantics

BugMedium priorityLow effortproviders · provider-acpGitHub issue2026-10-22 · base 6e5fb6e

Verdict: REPRODUCED · Root-cause confidence: high · reproduction label: confirmed-repro

1. TL;DR

An ACP agent can mark only some form properties as required, but bb converts every property into a mandatory user question. The planner neither reads the required-property list nor distinguishes optional answers when decoding a response. It also checks the four-question cap against the raw property count, so four choices accompanied by four optional text fields are refused before planning. Two newly authored regression assertions fail on unchanged main in two clean checkouts. These are source-level reproductions; no real provider, desktop app, or production thread was used.

Complete reproduction test
import { describe, expect, it } from "vitest";
import { planAcpElicitation } from "./elicitation.js";

describe("ACP optional form properties", () => {
  it("accepts required answers without inventing optional content", () => {
    const plan = planAcpElicitation({
      mode: "form",
      requestedSchema: {
        type: "object",
        required: ["delivery"],
        properties: {
          delivery: { type: "string", enum: ["standard", "express"] },
          instructions: { type: "string" },
        },
      },
    });

    expect(plan.kind).toBe("questions");
    if (plan.kind !== "questions") {
      throw new Error("Expected a supported form");
    }
    expect(
      plan.toResponse({
        kind: "user_answer",
        answers: { delivery: { selected: ["express"] } },
      }),
    ).toEqual({ action: "accept", content: { delivery: "express" } });
  });

  it("supports four choices accompanied by optional text properties", () => {
    const names = ["region", "size", "schedule", "service"];
    const properties = Object.fromEntries(
      names.flatMap((name) => [
        [name, { type: "string", enum: ["default", "other"] }],
        [name + "_other", { type: "string" }],
      ]),
    );
    const plan = planAcpElicitation({
      mode: "form",
      requestedSchema: { type: "object", required: names, properties },
    });

    expect(plan.kind).toBe("questions");
  });
});

5. Root cause

The planner reads requestedSchema.properties, but never reads requestedSchema.required. It limits the number of raw entries before planning, then emits one question per entry. During response conversion, a missing answer makes decodeAnswer return null and immediately declines the complete form, regardless of whether that property was required.

const entries = isJsonObject(properties) ? Object.entries(properties) : [];
if (entries.length > USER_QUESTION_MAX_QUESTIONS) { ... }

if (!decoded) {
  return { action: "decline" };
}

The deeper constraint is not confined to ACP decoding. The shared question schema has no optional/required marker. The server requires every question to have an answer, and rejects an empty selection with no text. Thus allowing omissions only in the adapter would not fix the UI/CLI submission path.

The bridge call site invokes this planner and returns its decoded response after the user interaction. In a real submitted interaction, server validation may reject the request earlier; this report does not claim that a live submission always reaches the planner's decline path.

6. Proposed fix and autopilot safety

Preserve the required-property set at the ACP boundary, omit genuinely unanswered optional properties from accepted content, and continue rejecting missing required or invalid supplied answers. Define how optional inputs are presented and skipped end to end. Where a recognized companion field is folded into a choice's free-text answer, count planned questions after folding and decode free text back into the correct companion property. Do not silently remove arbitrary optional fields or infer conditional requirements solely from a suffix.

No automated fix PR: a faithful generic repair needs either shared question-schema/server/UI changes to carry optionality or a product decision about a skip/presentation convention. Both fall outside this rule's one-subsystem, no-public-schema-change, no-product-decision safety gate. Changing only the adapter would leave server validation rejecting the same required-only answer. No production patch or fix branch was pushed.
