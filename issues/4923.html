#4923 · ACP skill metadata is lost at the prompt boundary

BugMediumEffort: Lowprovidersprovider-acpopen on GitHubOctober 5, 2026 · base ca5fe0ba9f1337f6c8e40f897a4492c0f7e3b188

Verdict: PARTIALLY REPRODUCED · Root-cause confidence: medium

1. TL;DR

A bb skill chip is intended to ask the model to use a reusable instruction folder, not to invoke an unrelated provider command. The real ACP bridge currently sends the chip's slash-prefixed text unchanged and discards the metadata identifying it as a skill. A focused boundary regression fails for that reason in two fresh checkouts of trusted main. The repository-owned ACP fixture echoes this text normally, so these runs do not prove the reported OpenCode-specific silent empty turn. No OpenCode executable is available here; that missing provider-level reproduction prevents a safe automatic production fix.

Complete regression test

  it("keeps bb skill chips out of the ACP slash-command namespace", async () => {
    const skillName = "audit-bb-skill";
    const promptLog = join(workspaceDir, "skill-namespace-prompts.jsonl");
    await waitForResponse(
      sendRequest("skills/configure", {
        roots: [
          {
            id: "audit-root",
            path: workspaceDir,
            skills: [{ name: skillName, description: "Describe a module." }],
          },
        ],
      }),
    );
    try {
      const { providerThreadId } = await startThread({
        envVars: { FAKE_ACP_PROMPT_LOG: promptLog },
      });
      const inputs = [
        { type: "text", text: "Warm up the session.", mentions: [] },
        { type: "text", text: `${skillName} Describe a module.`, mentions: [] },
        {
          type: "text",
          text: "/status",
          mentions: [
            {
              start: 0,
              end: "/status".length,
              resource: {
                kind: "command",
                trigger: "/",
                name: "status",
                source: "command",
                origin: "user",
                label: "status",
                argumentHint: null,
              },
            },
          ],
        },
        {
          type: "text",
          text: `/${skillName} Describe a module.`,
          mentions: [
            {
              start: 0,
              end: skillName.length + 1,
              resource: {
                kind: "command",
                trigger: "/",
                name: skillName,
                source: "skill",
                origin: "user",
                label: skillName,
                argumentHint: null,
              },
            },
          ],
        },
      ];
      for (const [index, input] of inputs.entries()) {
        expect(
          (
            await waitForResponse(
              sendTurnRequest("turn/start", providerThreadId, {
                input: [input],
              }),
            )
          ).error,
        ).toBeUndefined();
        await waitFor(
          () => threadEventsOfType("turn/completed")[index],
          `completion ${index + 1}`,
        );
      }
      const prompts = loggedPrompts(promptLog);
      expect(prompts[1]).toBe(`${skillName} Describe a module.`);
      expect(prompts[2]).toBe("/status");
      expect(prompts[3]).toContain(skillName);
      expect(prompts[3]).toContain("Describe a module.");
      expect(prompts[3]).not.toMatch(/^\s*\//u);
    } finally {
      await waitForResponse(sendRequest("skills/configure", { roots: [] }));
    }
  });

5. Root cause

The server's skill suggestions have source: "skill". The command resource built by the composer preserves that source. Its plain-text representation is the trigger plus the name. A leading slash is therefore real submitted text, not just a decorative chip.

buildPromptContentBlocks handles text as follows, with no mention-based normalization:

case "text":
  blocks.push({ type: "text", text: item.text });
  break;

runTurn places those blocks directly in session/prompt. Skill-vs-command metadata is no longer available to the provider. Separately, buildAcpSkillsInstructions lists skill paths in instructions; it does not install a provider-local command.

The initial instruction block is consumed only once. It can change whether the very first combined prompt begins with a slash, depending on the provider's block handling. Testing a follow-up turn isolates the namespace collision without claiming first-turn behavior.

If a provider returns end_turn without producing output, the stop-reason mapping and turn boundary translation would mark it completed. That explains the reported visible symptom conditional on the unverified provider behavior; it does not establish that OpenCode actually took that path here.

Confidence is high for the observed bridge-side metadata loss and medium for the overall proposed mechanism because the external provider step remains untested.

6. Proposed fix and safety gate

First run a real OpenCode session using a trusted installed runtime and observe the unknown-command result. If it confirms this behavior, normalize bb-owned skill invocations at the ACP prompt boundary into ordinary model-directed text, keeping genuine provider commands unchanged. Add coverage for first and subsequent turns, native provider skills, overlapping skill/command names, and malformed mention offsets before selecting the narrowest repair. Do not globally strip all slashes or infer skill intent from arbitrary raw text.
