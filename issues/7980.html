#7980 · ACP prompt settlement and unfinished commands

BugPriority: MediumEffort: Mediumproviders · provider-acp · provider-retry · workflows Issue #7980 · 2026-11-21

Trusted main commit: 35a03bbbb3f4d8dc814c1a152db5a463102b4250

PARTIALLY REPRODUCED · Root-cause confidence: high for the bridge mechanism; vendor and end-to-end reproduction remain unverified.

1. TL;DR

BB can mark a command and its turn complete as soon as an ACP agent resolves its prompt, even when that agent last described the command as in progress. A self-authored ACP process demonstrates this on trusted main: BB emits both command completion and successful turn completion before the fixture is allowed to send a terminal command update. A second probe shows that an overload-like assistant reply followed by a successful ACP response remains ordinary successful output. The bridge trusts the prompt response, and the workflow text-result path trusts a worker becoming idle. These are verified compatibility mechanisms, not a live reproduction of Antigravity or proof that arbitrary diagnostic-looking text should always be treated as an error.

  } else if (request.method === "session/new") {
    reply(request.id, { sessionId: "settlement-session" });
  } else if (request.method === "session/prompt") {

        update({ sessionUpdate: "agent_message_chunk", content: { type: "text", text } });
      }
      reply(request.id, { stopReason: "end_turn" });

      writeFileSync(process.env.SETTLEMENT_READY, "ready");
      while (!existsSync(process.env.SETTLEMENT_RELEASE)) {
        await new Promise((resolveTick) => setTimeout(resolveTick, 10));

      writeFileSync(process.env.SETTLEMENT_DONE, "done");
    }
  } else if (request.id !== undefined) {

5. Root cause

Prompt settlement unconditionally calls finishTurn after the successful ACP response. There is an empty-output warning but no unfinished-execute guard or ordinary-assistant-text error classification on this path. finishTurn clears the active prompt and emits the completion notification.

finishTurn(session, stopReason);
return;

The stop-reason mapping maps every non-cancelled stop reason to completed. Completion translation flushes open work using that successful status, then emits the turn boundary. Draining open tool calls closes any still-open tool items with the supplied turn-derived status. This explains the stronger observed symptom: BB marks the command itself complete before receiving a terminal tool event.

const status = turnStatusForStopReason(stopReason);
return [
  ...flushOpenTurnWork(context, itemStatusForTurnStatus(status)),
  ...,
  { kind: "turn.boundary", status, claimIfIdle: true },
];

For the diagnostic-text case, no actual JSON-RPC error was sent, so generic ACP success mapping is internally consistent. Built-in dialect selection has no Antigravity-specific adapter on this base. Text recognition therefore needs a deliberate vendor-specific contract rather than a generic keyword rule that would misclassify quotations or valid explanations.

Workflow idle reconciliation distinguishes structured output from plain output, but the plain-output branch stores idle output as succeeded without interpreting its meaning:

settleCall(db, {
  id: call.id,
  status: "succeeded",
  result: output ?? "",
  error: null,
});

This downstream acceptance is established by source inspection, not a live archival reproduction. The bridge result is enough to explain why a downstream consumer treating completed as authoritative cannot recover missing lifecycle or error semantics.

6. Proposed fix and simple-fix gate

First establish an authoritative vendor lifecycle trace: prompt return, execute status changes, cancellation, queued steering, late output, and disconnect. For a vendor that actually yields early, keep its existing turn open until observable execute work reaches a terminal state, while preserving interruption and shutdown behavior. Classify a verified capacity-only vendor diagnostic at the provider boundary as a typed retryable error, instead of teaching every workflow consumer to parse arbitrary prose. If a launcher already says completed, require an additional provider lifecycle signal before tracking hidden internal work. Document native-worker launch permissions only after verifying the vendor's accepted configuration.

No autonomous fix PR: the demonstrated generic bridge behavior is clear, but safely overriding prompt-completion authority and interpreting assistant prose require an unresolved provider-specific policy decision. The complete report also spans ACP settlement, workflow result policy, and native-worker permission configuration. This does not satisfy the single-subsystem/no-product-decision simple-fix gate. No production patch, fix branch, or push was made. The 84 added lines in two test/fixture files are local evidence only, not a proposed production repair.
