#7185 · Uninitialized SDK messages overwrite the Claude session identity

BugHighEffort: Lowprovidersprovider-claude-codeconfirmed-repro

Issue #7185 · 2026-11-06 · trusted base 14b3293254da0a3b4c858a01c5415d91f17aa7b5

Verdict: REPRODUCED · Root-cause confidence: high · Scope: deterministic provider-bridge reproduction, not a physical sleep/wake experiment.

1. TL;DR

A failed Claude startup can change the identity that bb uses to resume a conversation. The bridge accepts a changed session ID from an SDK error result even when the SDK never announced an initialized session. It then marks that ID restorable, probes context against it, and uses it to restart the next process. Two runs on unchanged trusted production code demonstrate all three consequences. A local root-cause fix passes the expanded regression, but was not pushed because the existing provider suite has six failures on both baseline and candidate.

5. Root cause

The bridge treats a session_id field as proof that the session is initialized. The assignment occurs before any message-type guard. plugins/provider-claude-code/src/bridge/bridge.ts:1625–1632:

    const providerThreadId = message.session_id?.trim() ?? "";
    if (
      providerThreadId.length > 0 &&
      threadSession.attachment.providerThreadId !== providerThreadId
    ) {
      threadSession.attachment.providerThreadId = providerThreadId;
      sendThreadIdentity(args.threadIdRef.current, providerThreadId);
    }

plugins/provider-claude-code/src/bridge/bridge.ts:1040–1049 marks the emitted identity sessionRestorable: true. The runtime records that identity through packages/agent-runtime/src/runtime.ts:1271–1283. This is not a failure in the idle-session reaper: no reaper or host process runs in the reproduction.

The same callback-local ID is used for an isolated context query at plugins/provider-claude-code/src/bridge/bridge.ts:1670–1681:

      if (providerThreadId) {
        void threadSession.contextUsageCollector.capture({
          read: (signal) =>
            readIsolatedClaudeContextUsage({
              sessionOptions: threadSession.attachment.sessionOptions,
              providerSessionId: providerThreadId,
              dynamicTools:
                threadSession.attachment.sessionConstructionConfig
                  .dynamicTools ?? [],
              signal,
            }),
          providerSessionId: providerThreadId,

When the failed SDK stream ends, plugins/provider-claude-code/src/bridge/bridge.ts:1491–1505 prefers the overwritten attachment ID for replacement. Thus even a later caller supplying the previously saved ID cannot prevent the resident attachment from resuming the wrong one.

The lower SDK session cache also accepts IDs from every message: plugins/provider-claude-code/src/bridge/sdk-session.ts:488–494. That cache supplies outgoing user messages. The expanded local regression leaves the stream open in a second case and observes the same incorrect session_id on the next prompt. The SDK's installed type declaration identifies system/init as the session metadata message; startup errors are not evidence that a restorable conversation was loaded.

6. Proposed fix and safety gate

Adopt changed IDs only from a nonempty system/init announcement, in both the bridge attachment and SdkSession cache. Context probes should use the retained authoritative attachment identity rather than arbitrary incoming result IDs. Keep forwarding execution errors. Add positive coverage showing that a subsequent genuine init still updates identity, context probes, and outgoing prompts.

A local three-file candidate implements that policy without dependencies, protocols, migrations, or stored-data changes. The original expanded regression fails on unchanged production code (two cases) and passes after the candidate (two cases). Lint and typecheck pass; the complete build passed before production changes. Candidate size: 145 changed text lines, additions plus deletions; no binary changes; git diff --check passes.

Fix stopped; no commit, push, or pull request. The full existing provider suite does not pass: candidate 429 passed / 6 failed, baseline 427 passed / 7 failed including the new one-case reproduction.
