#5332 · Pi command-shim launch mismatch

BugHighEffort: Lowprovidersprovider-pipartial-reproGitHub issue2026-10-10 · base e9ad6b0e3

Verdict: PARTIALLY REPRODUCED · Root-cause confidence: medium

The Windows/npm installation and the Windows extra-pipe failure were not reproduced. Two Linux runs verify only the version-probe boundary and its explicit-Node positive control.

1. TL;DR

The report describes a Pi provider that cannot enumerate models on Windows despite a working terminal command. Trusted main sends the default bare command directly to Node's execFile for the version check, while the RPC child uses a different, portable spawn path. A synthetic PATH containing only a Node-backed command shim produces the reported ENOENT version failure through the real provider probe in two clean Linux checkouts; explicitly supplying Node and the same entrypoint succeeds. This is an analogous boundary experiment, not an end-to-end Windows reproduction: Linux does not resolve batch shims as executables either. The extension also requires descriptors 3 and 4, so fixing only the version check would not establish session correctness.

import { copyFileSync, mkdtempSync, rmSync, writeFileSync } from "node:fs";
import os from "node:os";
import path from "node:path";
import { fileURLToPath } from "node:url";
import { afterEach, expect, it, vi } from "vitest";
import { probePiVersion } from "./provider-maintenance.js";
import { PI_BRIDGE_ARGS_ENV, PI_BRIDGE_COMMAND_ENV } from "./rpc-child.js";

const temporaryDirectories: string[] = [];

afterEach(() => {
  vi.unstubAllEnvs();
  for (const directory of temporaryDirectories.splice(0)) {
    rmSync(directory, { recursive: true, force: true });
  }
});

function prepareShimOnlyPath(): string {
  const directory = mkdtempSync(path.join(os.tmpdir(), "pi-shim-probe-"));
  temporaryDirectories.push(directory);
  const entrypoint = path.join(directory, "cli.mjs");
  copyFileSync(
    fileURLToPath(new URL("./fake-pi-rpc.mjs", import.meta.url)),
    entrypoint,
  );
  writeFileSync(
    path.join(directory, "pi.cmd"),
    `@echo off\r\n"${process.execPath}" "${entrypoint}" %*\r\n`,
  );
  vi.stubEnv("PATH", directory);
  vi.stubEnv("FAKE_PI_VERSION", "0.84.0");
  vi.stubEnv(PI_BRIDGE_COMMAND_ENV, "");
  vi.stubEnv(PI_BRIDGE_ARGS_ENV, "");
  return entrypoint;
}

it("loads the provider version when PATH contains only a Node-backed command shim", async () => {
  prepareShimOnlyPath();
  const result = await probePiVersion();
  console.log("shim-only version probe:", JSON.stringify(result));
  expect(result).toEqual({ version: "0.84.0", failure: null });
});

it("loads the same entrypoint when explicitly launched through Node", async () => {
  const entrypoint = prepareShimOnlyPath();
  vi.stubEnv(PI_BRIDGE_COMMAND_ENV, process.execPath);
  vi.stubEnv(PI_BRIDGE_ARGS_ENV, JSON.stringify([entrypoint]));
  const result = await probePiVersion();
  expect(result).toEqual({ version: "0.84.0", failure: null });
});

5. Root cause

The default launch resolver returns the bare command pi and no arguments unless explicit launch overrides are supplied. It contains no provider-local entrypoint resolution.

The version probe passes that command directly to execFileAsync without a shell or the portable process helper:

const launch = resolvePiLaunch(process.env);
({ stdout } = await execFileAsync(
  launch.command,
  [...launch.args, "--version"],
  { timeout: VERSION_PROBE_TIMEOUT_MS },
));

When no native executable with that bare name can be launched, the resulting error is formatted as the version-probe failure. Both executions establish this boundary result. Applicability to the reported Windows/npm installation is supported by the source's lack of a shim-aware launch path, but is not verified on that operating system.

In contrast, RPC startup uses experimental_spawnPortableProcess with five pipes. That helper delegates to cross-spawn. The extension reserves descriptors 3 and 4, and its Node branch attaches a Socket to descriptor 4. A batch intermediate process must preserve that contract; whether it does so on Windows remains untested.

6. Proposed fix and safety decision

Next experiment: a native Windows test using a locally generated npm-style installation, including both normal shims, followed by a bridge exchange over descriptors 3 and 4. Compare the current default launch with direct Node-and-entrypoint launch, checking version, catalog, session startup, channel input/output, paths containing spaces, missing packages, and explicit overrides. A shell-based version-check repair alone does not establish a repaired RPC transport.

If Windows confirms the hypothesis, resolve the provider's executable/entrypoint in the existing Pi launch path and reuse it for maintenance and RPC, preserving custom overrides and non-Windows behavior. No dependency should be necessary. This is a proposal, not a verified patch.
