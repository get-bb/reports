#6171 · Pooled Codex launch retains native authentication

Bug Priority: Medium Effort: Medium providers security provider-claude-code provider-codex

Issue #6171 · October 23, 2026 · trusted origin/main base 1e80ca7b44bccd06c6da75ed9ca6ba497bd380f5

PARTIALLY REPRODUCED · Root-cause confidence: high for the launch configuration, not for untested upstream side effects.

1. TL;DR

Account Pooler gives a routed Codex process a hub URL and a machine-token header, but bb also explicitly enables the provider's native OpenAI authentication. A new regression assertion observes the actual child arguments produced by the real bridge during a pooled model-catalog request and fails because requires_openai_auth=true is present. The same failure occurs in two clean checkouts of trusted main, without real accounts or credentials. Claude's routing and environment assembly also leave its existing configuration location available, but this investigation did not run the upstream Claude or Codex executables to prove credential refresh, file modification, or analytics behavior. Consequently this report verifies a launch-boundary defect, not the complete end-to-end incident.

5. Root cause

Endpoint routing is not credential isolation. Account Pooler's provider-specific environment contributions supply the URL and hub token. The Codex bridge then builds a named provider that includes both an environment-backed custom hub header and requires_openai_auth=true. Neither a different configuration home nor a separate authentication mechanism is established by that launch builder. The model-catalog reproduction captures this configuration at the actual spawn boundary, not by grepping the source.

  • Routing/bypass selection: only the selected provider's contribution plus nested-server markers is returned for routed requests.
  • Provider environment contributions: Claude and Codex receive separate routing entries.
  • Codex launch arguments and environment: the native-auth option is emitted unconditionally once both pool routing variables are present; environment assembly starts with the inherited environment.
  • Shared child-spawn boundary and model-list caller: catalog processes pass through the same launch builder.
  • Claude environment assembly copies the inherited environment and overlays provider entries.
  • Bridge runtime filtering removes runtime-specific entries, not the home directory; child environment sanitization similarly does not isolate provider credential files.
"model_providers.bb-account-pool.requires_openai_auth=true",
...
'model_providers.bb-account-pool.env_http_headers.x-bb-account-pool-token="CODEX_POOL_AUTH_TOKEN"',

The configuration can therefore select a pooled endpoint without defining hub-token-only authentication. The exact behavior of an installed upstream CLI after receiving it is outside this reproduction. In particular, this report does not claim to have observed a real host bearer, OAuth refresh, credential-file write, or analytics request.

6. Proposed fix and auto-fix decision

Establish a supported, routed-only credential boundary at the provider-launch layer and provide a supported path for cross-provider child commands. Verify it against the actual supported upstream CLI versions before selecting the mechanism. Preserve native behavior for unrouted sessions and ensure resume, model catalog, and tool capabilities survive. Test file-byte and modification-time preservation with disposable credentials, missing credential stores, new/resumed/forked sessions, model discovery, subagents, and both ordinary and login-shell child commands.

No pull request is safe under this rule. The required change affects authentication and a security boundary, which are explicitly excluded from the simple-fix policy. It also spans provider integrations and needs upstream compatibility validation. The supplied test is a useful failing launch-boundary guard, not a complete credential-isolation acceptance test.
