Verdict: NOT REPRODUCED · Root-cause confidence: low

1. TL;DR

The reported Windows deployment loses Connect and remote commands repeatedly; its unauthenticated persistent HTTPS requests reportedly stall too. I could not reproduce that failure on trusted main in this Linux environment. In each of two clean source checkouts, the real TunnelSession and real TunnelDO stayed connected for over 90 seconds, served 49 HTTPS requests on one reused TLS connection, and delivered 46 WebSocket echo replies. The local gate acknowledged heartbeats, and all 37 selected existing tests passed. These results do not test the reporter’s Windows network stack or the deployed account edge, and do not invalidate the reported symptoms.

const agent = new Agent({ keepAlive: true, maxSockets: 1, rejectUnauthorized: false });

let tunnel;

async function request() {
  return await new Promise((resolve, reject) => {
    const pending = get(`https://127.0.0.1:${gatePort}/probe`, { agent }, (response) => {
      const chunks = [];
      localPorts.add(response.socket.localPort);
      response.on("data", (chunk) => chunks.push(chunk));
      response.on("error", reject);
      response.on("end", () => {
        assert.equal(response.statusCode, 200);
        assert.equal(Buffer.concat(chunks).toString(), "fixture-ok");
        reused.push(pending.reusedSocket);
        resolve();
      });
    });
    pending.setTimeout(5000, () => pending.destroy(new Error("request timeout")));
    pending.on("error", reject);
  });
}

  visitor.send(`probe-${index}`);
  const [data] = await Promise.race([
    incoming,
    delay(5000).then(() => { throw new Error("echo timeout"); }),
  ]);
  assert.equal(data.toString(), `probe-${index}`);
  replies += 1;
}

5. Root cause: not established

No initiating defect was reproduced on trusted main. No claim is made that the deployed edge, an ISP, Windows, or a VPN driver is at fault. The following source facts constrain the next investigation:

  • Heartbeat constants set a 20-second send interval and 60-second deadline. Session startup and acknowledgement handling initializes the acknowledgement deadline on start, records actual acknowledgements separately, and terminates only when the deadline is exceeded. An absent recorded acknowledgement does not by itself establish why a connection ended.
  • Durable Object constructor installs a WebSocketRequestResponsePair for the exact heartbeat request/response constants. Real workerd handled these successfully in both runs. This checks source behavior locally, not the version or configuration of a deployed Worker.
  • Close-event diagnostics computes lastHeartbeatAckAgeMs from lastHeartbeatAckAt, leaving it null before any acknowledgement arrives. Null is an observation, not proof of a faulty acknowledgement implementation.
  • Anonymous sign-in response constructs a 401 response. Cookie check before tunnel forwarding returns that response for an anonymous request before forwarding it into TunnelDO. Therefore an anonymous 401-path keep-alive stall cannot, by itself, be assigned to the local bb server or its tunnel heartbeat handling. Account lookup and outer edge/request handling remain outside this local fixture.
  • Tunnel-loss handling abandons proxied streams when the tunnel disappears; Client disposal closes origin WebSockets too. That explains the downstream symptom once the upstream tunnel is lost, but not why the loss occurred.

6. Proposed next experiment / fix safety

No speculative fix or pull request is safe: there is no failing regression on trusted main, and the actual Windows/deployed-edge fault is not reproduced. In particular, increasing heartbeat timeouts or forcing Connection: close would only hide a transport symptom and would not explain an anonymous HTTPS response stalling.

Next, compare the affected Windows machine on another network with another machine on the affected network, using a credential-free repeated-request probe written independently from the report. Compare HTTP/1.1 connection reuse with fresh sockets, then HTTP/2 where supported. Correlate exact request times with sanitized Worker request identifiers and stored Workers Logs (never attach production live tail). A controlled Windows test with the VPN background driver fully removed would help isolate a driver effect; merely closing its UI does not do so. Packet captures should be private and scrubbed of identities and credentials before any sharing.

The GitHub cross-reference/connected-event timeline contained no linked pull request at review time. A text-search PR hit was unrelated and did not link this issue; it was not run or checked out.
