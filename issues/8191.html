#8191 · MCP forms are declined before reaching the Claude provider interaction bridge

BugPriority: MediumEffort: Mediumprovidersprovider-claude-codeGitHub issue2026-11-25 · base fb045a046653cc127656ca3c7243d44ae4c94f3f

Verdict: REPRODUCED · Root-cause confidence: high · reproduction label: confirmed-repro.

1. TL;DR

The Claude Code provider does not connect MCP elicitation requests to bb's user-question interactions. The real provider bridge and the locked real Claude Agent SDK were exercised with a small local subprocess that speaks the SDK control protocol. A valid form request immediately received a successful control response containing action: decline, with zero interaction requests emitted by bb. The session passes a tool-permission callback but no MCP elicitation callback; the SDK therefore applies its documented automatic refusal. The same failure was repeated by the same agent in a second clean checkout, without real credentials, a live model, or the user's app.

it("waits for a bb interaction instead of declining an MCP form without user input", async () => {
  const directory = mkdtempSync(join(tmpdir(), "bb-elicitation-wire-"));
  const wireResult = join(directory, "wire-result.json");
  const childPath = fileURLToPath(
    new URL("./elicitation-wire-child.mjs", import.meta.url),

  const sdk = await vi.importActual<

  >("@anthropic-ai/claude-agent-sdk");
  const children: ChildProcess[] = [];
  queryMock.mockImplementation(

      sdk.query({
        ...args,
        options: {
          ...args.options,
          env: { HOME: directory, PATH: process.env.PATH },
          spawnClaudeCodeProcess: () => {
            const child = spawn(process.execPath, [childPath, wireResult], {
              cwd: directory,
              env: { HOME: directory, PATH: process.env.PATH },
              stdio: ["pipe", "pipe", "pipe"],

            children.push(child);
            return child;
          },
        },
      }),
  );

  try {

      cwd: directory,
      instructionMode: "append",
      threadId: "elicitation-wire-repro",
      options: {
        permissionMode: "accept-edits",

        message.method === BRIDGE_INBOUND_REQUEST_METHODS.interactionRequest,

      ? JSON.parse(readFileSync(wireResult, "utf8"))
      : null;

      JSON.stringify({
        wireResponse: observed,

elicitation-wire-child.mjs

import { createInterface } from "node:readline";
import { writeFileSync } from "node:fs";

function send(message) {
  process.stdout.write(`${JSON.stringify(message)}\n`);
}

createInterface({ input: process.stdin }).on("line", (line) => {
  const message = JSON.parse(line);
  if (message.type === "control_request") {
    send({
      type: "control_response",
      response: {
        subtype: "success",
        request_id: message.request_id,
        response: { commands: [], models: [], mcp_servers: [] },
      },
    });
    if (message.request.subtype === "initialize") {
      send({
        type: "control_request",
        request_id: "elicitation-repro",
        request: {
          subtype: "elicitation",
          mcp_server_name: "local-repro",
          message: "Choose a deployment destination",
          mode: "form",
          requested_schema: {
            type: "object",
            properties: {
              destination: { type: "string", enum: ["staging", "production"] },
            },
            required: ["destination"],
          },
        },
      });
    }
  }
  if (
    message.type === "control_response" &&
    message.response.request_id === "elicitation-repro"
  ) {
    writeFileSync(process.argv[2], JSON.stringify(message, null, 2));
  }
});

5. Root cause

  1. attachThreadSession installs canUseTool but never an elicitation handler.
  2. SdkSessionOptions has no onElicitation field; the SDK options builder forwards canUseTool, sandbox, and hooks but not elicitation. query receives those options.
  3. SDK 0.3.318 treats an elicitation control request separately from tool permissions. Its installed Options.onElicitation documentation states that unhandled requests are automatically declined, and the wire fixture proves that fallback actually runs.
  4. The existing Claude user-question lifecycle is reached by AskUserQuestion tool permission handling, not by MCP elicitation. Consequently no interaction enters bb's question pipeline. This is upstream of UI rendering.
sessionOptions.canUseTool = createCanUseTool(threadIdRef);

...(this.options.canUseTool
  ? { canUseTool: this.options.canUseTool }
  : {}),

The existing ACP form planner parses schemas and maps answers, and the ACP handler routes questions through the interaction protocol. That adapter is not currently exposed by the public provider-bridge SDK facade. Sharing it safely requires work across the ACP adapter, SDK authoring surface, and Claude provider rather than simply adding a query option.

6. Proposed fix and simple-fix gate

Introduce a shared MCP form adapter through the supported SDK boundary, then thread an onElicitation handler from the Claude bridge through SdkSession to query. Map supported fields to existing user-question interactions and convert resolutions back to elicitation results. Keep unsupported schemas distinct from user refusal, and settle or withdraw pending questions on abort/stop. Do not blindly return accept, route elicitation through tool-permission answers, or silently discard unsupported fields.

No automatic PR: the safe non-duplicating repair crosses the existing ACP planner, public SDK facade, and Claude provider, so it does not satisfy this rule's one-existing-subsystem/no-architecture-decision gate. Copying the current 498-line planner into the provider, before adding wiring or regression coverage, would exceed the under-500-total-lines limit. No production fix was attempted, no fix branch was pushed, and no PR was opened. GitHub issue connections and open-PR search for 8191 returned no linked open PR at investigation time.

Test-authoring gate: the regression protects the observable bridge interaction/wire-response contract. Omitting the elicitation callback is the credible regression. Existing session/bridge tests mock SDK query behavior and do not drive its automatic elicitation fallback. This test needs no production-only seam; it uses the SDK's existing subprocess injection option only in the harness.
