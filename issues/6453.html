#6453 · Codex session catalogs diverge from model discovery

BugPriority: MediumEffort: Mediumproviders · provider-codex · confirmed-repro GitHub issueOctober 28, 2026 · base 1a4a1d254c7b1f70d340ef9c800dad77dbeb8e66

Verdict: REPRODUCED · Root-cause confidence: high

1. TL;DR

A new Codex session can successfully read a catalog containing an additional model while BB's discovery API still returns the older list. The session's catalog is retained for session-specific behavior, but is not published to the server catalog that feeds the model picker. Discovery separately reuses a persistent app-server with no age-based replacement, so even another successful model-list request can repeat the older catalog. A hermetic regression against unchanged main reproduces that divergence, including proof that the new session actually consumed the updated response. The same agent repeated the failure in a second clean checkout; no production account, inference request, or live BB instance was used.

6. Proposed fix and simple-fix gate

Route validated session catalogs to the same host/provider/route-scoped server catalog store used by discovery, retaining model metadata and reasoning options and reusing the existing picker-change notification after storage. Preserve route and account isolation, and do not let stale in-flight discovery replace a newer session catalog. Also give the dedicated discovery process an explicit freshness policy so manual refresh is not indefinitely tied to one process snapshot.

No pull request: the complete repair crosses the provider bridge/runtime and server catalog subsystem boundary. Existing bridge notifications do not include a catalog-update event, so choosing a publication path requires shared-contract or cross-subsystem work and fails the one-existing-subsystem/no-public-protocol simple-fix constraints. Merely restarting discovery would not deliver a session catalog to the picker immediately. No partial production fix, branch, or push was made.
