#7332 · Code-fence host schedules a synchronous portal follow-up commit

Bug Priority: Medium Effort: Medium plugins · ui · perf · GitHub issue · November 10, 2026 · base f39378659a

PARTIALLY REPRODUCED · Root-cause confidence: medium

1. TL;DR

A plugin-rendered fence is initially an empty placeholder. The host receives its content in a layout effect, then performs another synchronous React commit to render the portal, even when the plugin produces no visible output. A deterministic test confirms that behavior twice on the current trusted main commit. This establishes the extra commit in the fence subsystem, not the reported wall-clock regression: no browser trace or two-pane layout-duration comparison was collected. The claimed 1.2–1.3 second cost and repeated ancestor row measurements remain unverified, so no production fix or PR is proposed as already validated.

Complete reproduction test
// @vitest-environment jsdom

import { Profiler } from "react";
import { cleanup, render } from "@testing-library/react";
import { afterEach, expect, it } from "vitest";
import type { PluginCodeFenceRendererSlot } from "@/lib/plugin-slots";
import {
  buildCodeFenceRendererRegistry,
  CodeFencePlaceholder,
  CodeFenceRendererHost,
  type CodeFenceRendererRegistry,
} from "./markdown-code-fence-renderers";

function EmptyFence() {
  return null;
}

const registration: PluginCodeFenceRendererSlot = {
  id: "commit-probe",
  pluginId: "repro",
  generation: 1,
  languages: ["ui"],
  component: EmptyFence,
};

function fenceTree(registry: CodeFenceRendererRegistry) {
  return (
    <CodeFenceRendererHost
      registry={registry}
      message={{ id: "message", threadId: "thread", turnId: null, projectId: null }}
      streaming={false}
    >
      Before
      <CodeFencePlaceholder
        closed={true}
        code="sample payload"
        language="ui"
        offset={0}
        original={<pre>sample payload</pre>}
      />
      After
    </CodeFenceRendererHost>
  );
}

afterEach(cleanup);

it("mounts a null fence renderer without a synchronous follow-up commit", () => {
  const controlPhases: string[] = [];
  const control = render(
    <Profiler id="control" onRender={(_id, phase) => controlPhases.push(phase)}>
      {fenceTree(buildCodeFenceRendererRegistry([]))}
    </Profiler>,
  );
  expect(control.container.textContent).toContain("sample payload");
  control.unmount();
  const rendererPhases: string[] = [];
  const renderer = render(
    <Profiler id="renderer" onRender={(_id, phase) => rendererPhases.push(phase)}>
      {fenceTree(buildCodeFenceRendererRegistry([registration]))}
    </Profiler>,
  );
  expect(renderer.container.textContent).toContain("Before");
  expect(renderer.container.textContent).not.toContain("sample payload");
  expect(controlPhases).toEqual(["mount"]);
  expect(rendererPhases).toEqual(controlPhases);
});

5. Root cause

The host starts with an empty entry Map and a reducer. On the first render there are no entries to turn into portals. The placeholder then attaches and updates in layout effects:

host.attach(offset, element);
...
host.update(offset, { closed, code, language, original });

attach creates an entry whose block is null. update replaces that block and always schedules the first follow-up:

const previous = entry.block;
entry.block = block;
if (
  previous === null ||
  previous.code !== block.code ||
  previous.closed !== block.closed ||
  previous.language !== block.language
) {
  rerender();
}

The follow-up render materializes the portal, even if the plugin component itself returns null. This causally explains the observed nested-update phase. It does not establish a 1.2-second delay, one commit per fence, ancestor layout-effect execution, or full-page reflow.

Root-cause confidence is high for this narrow bridge lifecycle and medium for its relationship to the full reported performance defect. The current timeline already has a ResizeObserver measurement path; the more general suggestion to replace all measurement effects is not a validated fix.

6. Proposed fix / next experiment

Next, create a synthetic two-pane fixture on current main and capture Chromium traces with and without the registration, attributing layout work to exact stacks. Separate initial code-block UI updates from host updates. If the portal lifecycle is responsible, move enough fence metadata into the initial render to eliminate the extra update, while retaining per-language indices, streaming state across markdown-region transitions, Original fallback, crash isolation, and delayed detach cleanup. Those invariants are already exercised by the existing renderer suite; a one-line effect deferral is not established as safe.

No fix PR: only the scheduling mechanism was reproduced, not the full performance defect on trusted main. The rule's reproduction prerequisite for a simple production fix is therefore not met. No fix branch was pushed. No linked or matching open PR was found in the issue timeline or the issue-number search.
