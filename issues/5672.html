#5672 · Resumed child lifecycles lose delegation correlation

BugPriority: MediumEffort: Lowprovidersprovider-codexIssue2026-10-17 · base 6a639cfc0d66e0c789a1bd7309266973228d1a80

Verdict: REPRODUCED (translator lifecycle defect) · Root-cause confidence: high

1. TL;DR

A resumed Codex child can be mistaken for the main conversation when its turn-start notification arrives before its follow-up activity notification. After the first child turn ends, the translator clears active parent links but still knows the child's identity; it does not consult that identity when the next turn starts. The resulting start lacks a parent marker, which the runtime uses to distinguish a child from a root turn. A second mapping defect prevents the resumed delegation from closing correctly after the late activity arrives. A new regression reproduces the lifecycle failure in two clean trusted checkouts; no real account, user thread, or live Codex process was used.

5. Root cause

Completion removes transient provider-thread and turn-to-call links but retains the tracked child identity. When the same child's next turn arrives before follow-up activity, attachCodexDelegationParentLink checks only the cleared transient links. The pending root-thread queue is not a substitute for the distinct child-thread identity, so it emits turn.open without parentRef.

6. Proposed fix and checked implementation

Use retained child identity as a fallback only for a distinct child provider thread, preserving normal root/native-start behavior. When starting a replacement delegation for that child, retarget existing turn associations from the previous call to the new call. Keep the change inside the Codex translator; no protocol, public API, schema, stored data, permission, or dependency change is needed.

The locally authored implementation changes two files: 17 production additions + 1 production deletion, and 60 test additions: 78 changed text lines total. Both ordering cases pass after the fix.
