#6810 · Pi error events omit retry classification

Bug Priority: Medium Effort: Medium providers provider-pi provider-retry

November 2, 2026 · GitHub issue · trusted base 916d684ac23d0b0de82c09cfc7553a50287d2188

Verdict: REPRODUCED · Root-cause confidence: high

1. TL;DR

Pi forwards failure text but does not classify its error events. A synthetic gateway failure reaches the real retry policy with errorInfo: null, so the policy declines to retry. This reproduces at the actual Pi translation and delta-assembly boundary without an account, a network outage, or a live user thread. The same failure was repeated in a second clean checkout by the same agent. Timeline text is not simply discarded: existing core formatting already reads the detail, and long details intentionally collapse to a generic title; the reported visual appearance was not independently driven in a browser.

4. Minimal reproduction

  1. Check out the public repository at the recorded commit and run pnpm install --frozen-lockfile --prefer-offline.
  2. Save this investigator-written regression test as plugins/provider-pi/src/delta-translation.errors.test.ts. It exercises real production translation and assembly; it does not mock the classifier or retry policy.
import { expect, it } from "vitest";
import { experimental_createDeltaAssembler as createDeltaAssembler } from "@get-bb/plugin-sdk/provider-bridge/testing";
import { createPiDeltaTranslator } from "./delta-translation.js";

const message = "502 Bad Gateway";
const assistant = {
  role: "assistant", content: [], stopReason: "error", errorMessage: message,
};
it.each([
  { jsonrpc: "2.0", method: "error", params: { message } },
  { type: "agent_end", messages: [assistant] },
  { type: "agent_end", messages: [assistant], willRetry: true },
  { type: "agent_end", messages: [assistant], deferSettlement: true,
    settlementSuperseded: true },
  { type: "compaction_end", reason: "overflow", aborted: false,
    errorMessage: message },
])("preserves actionable Pi failure information", (event) => {
  const translator = createPiDeltaTranslator({
    resolveModelContextWindow: () => null,
  });
  const assembler = createDeltaAssembler({ providerId: "pi" });
  assembler.assemble({
    threadId: "error-test",
    deltas: translator.translate({ type: "agent_start" }),
  });
  const events = assembler.assemble({
    threadId: "error-test", deltas: translator.translate(event),
  });
  expect(events).toContainEqual(expect.objectContaining({
    type: "provider/error", detail: message,
    errorInfo: { category: "internal", httpStatusCode: 502, providerCode: null },
  }));
});

5. Root cause

The RPC translation branch and assistant settlement branches construct provider.error deltas containing only a generic message, detail, and lifecycle flags. The compaction branch has the same omission.

{
  kind: "provider.error",
  message: "Provider error",
  detail: errorEnvelope.data.params?.message ?? "unknown error",
  settlesTurn: true,
}

The server's turn.failed builder reads that event and defaults absent errorInfo to null. The retry policy correctly requires classification or HTTP status, so the unclassified 502 becomes not-retryable.

Separately, core timeline formatting already uses raw detail for unclassified short errors and category-specific titles for classified errors. An arbitrary text dump is not required in the collapsed title. The patch preserves detail and allows the existing categorized display path to work.

6. Proposed fix and verified local patch

Classify Pi error text once at the translator boundary using existing ProviderErrorInfo categories and HTTP status, and attach it on all five error paths. Preserve existing text and settlement/retry flags. Map unavailable 5xx responses to internal, connection/timeouts to connection-failed, explicit overload to overloaded, 429 to rate-limit, authorization errors to unauthorized, and context overflow to context-window-exceeded. Keep unknown and non-retryable 4xx conservative; do not treat an unqualified 422 as transient.

No public schema, protocol, dependency, stored data, or retry-policy change is needed. Do not invent a quota reset: a 429 category alone still does not provide resettable rate-limit state to provider-retry. This bounded fix does not add that state or claim to solve every rate-limit recovery.

With the local patch, the identical policy probe returns:

{
  "errorInfo": {
    "category": "internal",
    "providerCode": null,
    "httpStatusCode": 502
  },
  "decision": {
    "kind": "retry",
    "sendAt": 60000,
    "reason": "Provider unavailable"
  }
}
