#8015 · Explicit reuse selection omits environment validation

BugPriority: MediumEffort: Mediumui, plugins Issue2026-11-22 · base 796cdcc0f4bf8a55e23664035c54e8db6fe9d272

Verdict: REPRODUCED · Root-cause confidence: high · reproduction label: confirmed-repro

1. TL;DR

A caller can explicitly select an existing environment, yet the new-thread composer settles on the project's checkout instead. The composer builds its reuse list from sidebar threads and only supplements that list with a direct environment lookup for component seeds. Navigation targets and runtime selection changes do not feed that lookup. Consequently, an existing environment with no sidebar threads is treated as an unavailable reuse target. The failure is reproduced through the real root compose route and the real composer host selection API, in two clean trusted checkouts. This is a behavioral selection defect, not a pixel-level rendering claim.

5. Root cause

Navigation toCompose and sidebar openNewThread both forward an explicit environment ID in route state. RootComposeView applies that target through the composer's raw environment-selection setter.

NewThreadComposer reuse options originate from project threads in sidebar navigation. The direct lookup target is derived only from the optional seed, not from explicit navigation or runtime selections:

const seededReuseEnvironmentId = useMemo(() => {
  if (environmentSeed === null) return null;
  const parsed = parseEnvironmentValue(environmentSeed.selectionValue);
  return parsed?.type === "reuse" ? parsed.environmentId : null;
}, [environmentSeed]);
const seededReuseEnvironmentQuery = useEnvironment(seededReuseLookupId);

reuseSelectionSurvives accepts a thread-derived target, a still-loading sidebar, or the matching non-missing seed; otherwise it returns false. The effective-value resolver then chooses the checkout provider when a local project source is available. The runtime host API uses the same environment-changing path, explaining the identical settled result on both host surfaces.

The deeper mismatch is using sidebar membership as evidence of environment existence for explicit requests while a live environment lookup already exists for seeds. The defaultEnvironment declaration is stale about the seed behavior.

6. Proposed fix

Feed explicit reuse targets through the existing direct environment lookup and option hydration, just like seeds. Keep the target pending until lookup completion; preserve existing ready environments and continue falling back for missing or destroyed environments. Wait for that validation before returning a settled host selection. Update the seed documentation without adding a public API, wire field, or dependency.

A local bounded fix implements this in the existing new-thread composer subsystem. The regression that fails on main passes after that change. Additional shared contract cases cover delayed lookup and missing/destroyed fallback on both composer surfaces. The final change is 165 added-plus-deleted text lines across three files (composer implementation, its existing contract tests, and SDK declaration documentation). All 219 relevant tests pass; app and SDK lint/typecheck and the final app build pass. There are no dependency, generated-file, schema, or wire changes.
