#8279 · Cursor catalog curation prevents CLI discovery

BugPriority: MediumEffort: Mediumproviders · cli · provider-acpIssue2026-11-27 · base b0ddaad731565d7e4de68d824120d802fc78f7d5

Verdict: REPRODUCED · Root-cause confidence: high · reproduction label: confirmed-repro

1. TL;DR

Cursor families can be fully discovered and retain their reasoning metadata while being absent from both default CLI output formats. A fixed six-family policy separates the catalog into primary and selected-only pools; the CLI normally prints only the first pool. The SDK-backed CLI command includes a selected-only family immediately when given its exact ID. Two clean checkouts reproduce this with the repository's existing sample catalog, without a Cursor account or changes to production code. This proves the discoverability defect, not the reporter's current account inventory or a rendered picker screenshot.

5. Root cause

Cursor's fixed primary family list moves discovered nonmatching families into selectedOnlyModels; the CLI emits only primary models unless an exact selected-model ID is supplied.

Policy enters through the built-in provider declaration

plugins/provider-acp/src/known-agents.ts:49 sets the six-ID policy. plugins/provider-acp/src/declaration.ts:69 copies it into bridge options.

    primaryModels: [

      "gpt-5.6-sol",
      "claude-opus-5",
      "claude-fable-5",
      "composer-2.5",
    ],

The bridge keeps discovery but splits visibility

packages/provider-bridge-acp/src/bridge/bridge.ts:3949 normalizes the catalog, then applies the primary split. packages/provider-bridge-acp/src/bridge/model-catalog.ts:442 matches IDs exactly and sends other discovered models to selectedOnlyModels. Its fallback exposes everything only when zero primary IDs match; Auto normalizes to default, so it keeps the curated branch active even when all other preferred families are absent.

CLI discards the second pool unless its ID is already known

apps/cli/src/commands/provider.ts:163 chooses the output model array before either JSON or table rendering. With no selectedModel the helper returns only the primary array; the SDK response had retained both pools.

This is not evidence of a failed parser, missing reasoning support or lost model metadata. Existing catalog tests deliberately cover splitting, and the built-in-agent test fixes the six IDs in its expected declaration. The defect is the interaction between an explicit curation policy and the absence of a general CLI enumeration path.

6. Proposed fix and simple-fix decision

Choose an explicit catalog policy: expose all discovered families by default, or retain curated primary picks while adding a documented all-models enumeration path through the SDK and CLI. Avoid another one-off allowlist update.

No automated pull request. Removing the allowlist changes the primary picker policy; retaining it while adding enumeration changes a user-facing CLI/SDK contract and its documentation. These are different product choices, and existing tests explicitly preserve curation. The simple-fix rule forbids making a product decision. No production patch, fix branch, commit or push was made to get-bb/bb. A tiny one-off addition to the allowlist would only postpone the same failure.

GitHub cross-reference/connection metadata and an open-PR search for issue 8279 found no linked open pull request at investigation time. No pull-request code was checked out or executed.
