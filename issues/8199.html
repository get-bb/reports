#8199 · Pending machine recovery delays HTTP readiness

BugHighEffort: Mediumhost Issue · 2026-11-25 · trusted main 9f72ff5aeb4a6a73048c3ab21a8d9fa484e592b5

Verdict: REPRODUCED · Root-cause confidence: high · Reproduction label: confirmed-repro

1. TL;DR

A pending Manual machine makes a normal server restart miss the launcher's 60-second health deadline. The server is not crashing: its HTTP listener is blocked behind a recovery sweep that awaits machine creation. Manual creation waits for enrollment, which a user may not have completed; the generic sweep detaches that work only after 60 seconds. Two fresh source checkouts reproduced the timeout with the real Manual provider, real SQLite storage, and the launcher's actual health-wait function. An empty database was healthy in about 1.4 seconds; restarting with one pending machine became healthy only after about 61.1 seconds.

5. Root cause

  1. Server startup, lines 504–520 awaits recovery before opening the HTTP listener.
  2. Startup recovery, lines 910–915 awaits the machine lifecycle step after the other startup repairs.
  3. Creating-machine recovery, lines 1383–1387 awaits the tracked create operation. Machine sweep, lines 1525–1552 passes that promise through the item sweep.
  4. Manual provider, lines 27–43 checkpoints the resource and waits for enrollment for up to 15 minutes.
  5. Sweep detach constant is 60,000 ms, and the item runner races this timer against completion.
  6. Launcher deadline is also 60,000 ms; waitForServerHealth reports failure when the server has not yet answered. Desktop startup deadline has the same duration, checked statically only.
await runStartupRecoverySweep(sweepDeps);
const server = startHttpListener(...);

await runStartupRecoveryStep(deps, "machine-provider-lifecycle", () =>
  sweepMachineLifecycles(deps),
);

if (row.phase === "creating") {
  await startCreate(deps, record, row).done;
}

The excerpts abbreviate surrounding error handling but preserve the relevant ordering. The health clock starts when the child is launched; the sweep's separate 60-second clock starts later, after initialization. Thus equal timeout constants do not leave a usable startup window. This is not a listener bind error or an early process exit.

6. Proposed fix and safety

Launch the existing machine lifecycle recovery step without awaiting it in runStartupRecoverySweep. Keep the existing error-catching wrapper, tracked-operation deduplication, item failure recording and periodic sweep semantics unchanged. All earlier thread/environment startup repairs remain awaited.

This is a contained scheduling correction, not a new policy, public protocol or persisted-data change: a machine operation already outlives the startup sweep after the generic detach deadline, and Manual setup needs the HTTP listener in order to receive enrollment. Avoid increasing the launcher's timeout, which merely moves the same readiness dependency to another deadline.

The repair changes only the machine step's await to void. Existing error handling stays in runStartupRecoveryStep; no callback, setting, API, schema, authentication, or stored-state change is introduced. The regression also verifies that creation resumes and reaches active when the provider is released.
