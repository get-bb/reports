#7356 · Partial vacuum progress is omitted after contention

BugPriority: LowEffort: Lowhost GitHub issueNovember 10, 2026 · base 7c1353d80729983b86ea1555d18b42407f320406

Verdict: REPRODUCED · Root-cause confidence: high · Reproduction label: confirmed-repro

1. TL;DR

The maintenance sweep can reclaim some free database pages and then encounter another writer before its next chunk. The completed work remains effective, but the sweep logs only a failure and omits all progress figures. An actual SQLite write lock reproduced this for both the core database and plugin-database entry points. Two clean checkouts at the same trusted main commit produced the same two failing assertions, while four failure-classification controls passed.

2. Claims vs findings

Complete regression source

import Database from "better-sqlite3";
import { mkdtempSync, rmSync } from "node:fs";
import { tmpdir } from "node:os";
import { join } from "node:path";
import { describe, expect, it, vi } from "vitest";
import {
  createConnection,
  getDatabaseFreelistStats,
  startWalCheckpointer,
} from "@bb/db";
import { createMigratedConnection } from "@bb/db/testing";
import {
  runDatabaseMaintenanceSweep,
  runPluginDatabaseMaintenanceSweep,
} from "../../src/services/system/periodic-sweeps.js";

describe.each(["core", "plugin"] as const)(
  "%s vacuum contention",
  (surface) => {
    it.each(["first chunk", "later chunk", "unexpected error"] as const)(
      "reports %s without losing the outcome",
      async (failure) => {
        const directory = mkdtempSync(join(tmpdir(), "bb-vacuum-contention-"));
        const databasePath = join(directory, "maintenance.db");
        const template = createMigratedConnection();
        try {
          await template.$client.backup(databasePath);
        } finally {
          template.$client.close();
        }
        const db = createConnection(databasePath);
        const writer = new Database(databasePath);
        const logger = {
          debug: vi.fn(),
          error: vi.fn(),
          info: vi.fn(),
          warn: vi.fn(),
        };
        const checkpointer = startWalCheckpointer({ logger });
        checkpointer.attach(db.$client);
        let interrupted = false;
        try {
          db.$client.exec("CREATE TABLE vacuum_payload (payload BLOB)");
          const insert = db.$client.prepare(
            "INSERT INTO vacuum_payload VALUES (zeroblob(8192))",
          );
          db.$client.transaction(() => {
            for (let row = 0; row < 1200; row += 1) insert.run();
          })();
          db.$client.exec("DELETE FROM vacuum_payload");
          const before = getDatabaseFreelistStats(db.$client);
          expect(before.freelistCount).toBeGreaterThan(1024);
          if (failure === "first chunk") writer.exec("BEGIN IMMEDIATE");
          const unexpectedError = new Error("Checkpoint interrupted");
          const walCheckpointer = {
            ...checkpointer,
            async checkpoint(database: Database.Database): Promise<void> {
              await checkpointer.checkpoint(database);
              if (
                failure !== "first chunk" &&
                !interrupted &&
                getDatabaseFreelistStats(database).freelistCount <
                  before.freelistCount
              ) {
                interrupted = true;
                if (failure === "unexpected error") throw unexpectedError;
                writer.exec("BEGIN IMMEDIATE");
              }
            },
          };

          if (surface === "core") {
            await runDatabaseMaintenanceSweep({ db, logger, walCheckpointer });
          } else {
            await runPluginDatabaseMaintenanceSweep({
              logger,
              walCheckpointer,
              plugins: {
                listOpenPluginDatabases: () => [
                  { database: db.$client, pluginId: "contention-test" },
                ],
              },
            });
          }

          const after = getDatabaseFreelistStats(db.$client);
          expect(after.freelistCount).toBeGreaterThan(0);
          if (failure === "first chunk") {
            expect(after).toEqual(before);
          } else {
            expect(interrupted).toBe(true);
            expect(after.freelistCount).toBeLessThan(before.freelistCount);
          }
          if (writer.inTransaction) writer.exec("ROLLBACK");
          expect(db.$client.pragma("integrity_check", { simple: true })).toBe(
            "ok",
          );
          expect(logger.info).not.toHaveBeenCalled();
          expect(logger.warn).toHaveBeenCalledExactlyOnceWith(
            expect.objectContaining({
              ...(surface === "plugin" ? { pluginId: "contention-test" } : {}),
              err:
                failure === "unexpected error"
                  ? unexpectedError
                  : expect.objectContaining({ code: "SQLITE_BUSY" }),
              ...(failure === "later chunk"
                ? { result: { before, after } }
                : {}),
            }),
            failure === "later chunk"
              ? "Incremental database vacuum stopped early"
              : "Incremental database vacuum failed",
          );
        } finally {
          if (writer.inTransaction) writer.exec("ROLLBACK");
          writer.close();
          await checkpointer.stop();
          db.$client.close();
          rmSync(directory, { recursive: true, force: true });
        }
      },
    );
  },
);

5. Root cause

The chunk loop saves the first and last successful results, but returns them only on normal completion. There is no local handling for contention at the incremental-vacuum call:

    if (last !== null) {
      await new Promise<void>((resolve) => setImmediate(resolve));
    }
    await walCheckpointer.checkpoint(client);
    last = runIncrementalVacuum(client, {
      maxPages: Math.min(
        DATABASE_INCREMENTAL_VACUUM_CHUNK_PAGES,
        DATABASE_INCREMENTAL_VACUUM_MAX_PAGES - vacuumedPages,
      ),
    });
    await walCheckpointer.checkpoint(client);
    first ??= last;
    if (last.after.freelistCount === 0) {
      break;
    }
  }
  if (first === null || last === null) {
    throw new Error("Incremental vacuum ran no chunks");
  }
  return { before: first.before, after: last.after };

runIncrementalVacuum executes the actual SQLite pragma. Its maintenance timeout wrapper limits the busy wait to 100 milliseconds and restores the connection timeout afterward; it does not suppress errors.

The exception therefore leaves the loop before its aggregated result is returned. The outer handler logs only the error as a failed run. The already completed pragma is not rolled back: chunks are separate synchronous operations, with an event-loop yield between them.

Both core and plugin maintenance use that same reporting boundary, explaining the matching observations.

6. Proposed fix

Represent a later SQLITE_BUSY as an interrupted outcome carrying the first before statistics, last successful after statistics, and actual error. Let the existing reporting boundary log that outcome once as stopped early, retaining plugin identity and suppressing the completed log. Catch only the incremental-vacuum operation; first-chunk busy errors, checkpoint failures, and non-busy errors must retain the existing failure path. Keep the normal successful result unchanged. No database schema, stored data, public protocol, or dependency change is needed.

9. Appendix and limits

All root-cause links were checked against the recorded commit. The reproduction is nonvisual, so no screenshot is applicable. Extended SQLITE_BUSY variants are accounted for in the proposed prefix check but were not induced in this reproduction. A non-busy checkpoint failure is injected as an explicit control; actual contention always comes from SQLite itself.

The first full build encountered a clean-install SDK build-order failure in the GitHub plugin. Building the existing SDK runtime first, then repeating the normal full build, passed all 73 build tasks in each checkout. No dependency was added or modified to address this setup issue.

Repository policy keeps raw logs and test artifacts out of the public report repository, so the reproducible source and exact expected-versus-actual evidence are embedded above. Raw evidence is retained locally. Issue content was treated as untrusted claims only; no issue-supplied code, commands, or instructions were executed.
