#8278 · An empty pre-execution thread retains its pending status

Bug Medium Effort: Low threads · confirmed-repro open on GitHub 2026-11-27 · base b0ddaad731

Verdict: REPRODUCED · Root-cause confidence: high

1. TL;DR

Creating a thread with a future first message and then deleting that message leaves both stored and displayed status as pending, with zero queued messages and no environment. A successful stop request does not change that state. Archiving succeeds, but the archived record still has pending status. Both isolated reproductions reach precisely that result.

Important distinction: the current public domain contract deliberately defines pending as “never dispatched,” not “a turn is running.” The built-in sidebar status resolver explicitly treats it as non-running. Thus the observed API state is confirmed, but its interpretation as permanently live work is not supported by the core contract. The reported third-party sidebar restriction was not independently exercised.

5. Root cause

  1. Creation writes pending before the first dispatch; a deferred first message does not clear dispatch admission.
  2. Queue deletion removes the queue row, repairs its previous group edge, and emits queue-changed. It neither derives nor writes thread lifecycle status.
  3. The lifecycle table has exactly one transition out of pending: run.preparing → starting. There is no empty-queue transition.
  4. The stop reducer routes stops only for live runtime, starting/stopping status, or provisioning. A pending thread with no runtime/provisioning takes no status-changing branch, so the successful request is a no-op.
  5. Runtime projection reports pending as pending. Archive is an orthogonal record dimension rather than a lifecycle completion.

This is not evidence of a hidden live turn or a missing daemon response. It is a stable pre-execution record state. The public status definition explicitly says this; The shared sidebar resolver sets pending: false for running runtime states. The pending semantics were introduced in trusted history by commit 49dadc363a (dispatch queue rework), rather than inferred from the issue.

Decisive trusted source excerpts

pending: {
  "run.preparing": "starting",
},
clearPreviousQueuedMessageGroupEdgeInTransaction(tx, existing);
tx.delete(queuedThreadMessages)
  .where(eq(queuedThreadMessages.id, id))
  .run();
return existing;

6. Fix proposal and safety decision

The least invasive consumer fix is to classify pending as pre-execution/non-running and allow archival when no actual work is active, consistent with the shared resolver. The community implementation is outside this target repository and was not fetched or changed.

If product policy instead requires empty never-started threads to become idle or be removed, first decide which behavior is intended. An idle transition must go through the thread lifecycle owner rather than a direct status write in the queue data helper, preserve pending when other queued messages remain, and handle dispatch/deletion races. Automatic deletion additionally raises content, attachment, ownership, and retention choices. These are not equivalent behavior-preserving fixes.

No pull request opened: the requested status change conflicts with the explicitly documented public meaning of pending, so a core patch needs a product/lifecycle-contract decision and fails the autopilot simple-fix gate.
