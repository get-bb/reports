#7694 · Repeated timeline normalization and unstable cached row projections

BugPriority: LowEffort: Mediumthreads · perf GitHub issue2026-11-17 · base 1320c88e8abdd3f145bc9a5c305eace269fb2f28

Verdict: REPRODUCED · Root-cause confidence: high

1. TL;DR

Changing only the current assistant response creates new view objects for an earlier completed turn and a closed delegation, even when their input objects are identical and the same cache is reused. Their contents remain correct; this is unnecessary computation rather than lost messages. A separate probe confirms that a normalized turn's child array is iterated twice again on a subsequent merge of the same snapshot. The UI comparator and signature cache make these identities consequential, but this investigation does not measure visible lag, frame time, or CPU usage in the app.

5. Root cause

Repeated recursive joining

packages/client-core/src/timeline/timeline-merge.ts:443 looks up every incoming row by ID, then calls the child-joining routine whenever a loaded row exists. There is no special case for an identical, already-normalized input.

  const currentRowsById = new Map(current.rows.map((row) => [row.id, row]));
  const latestRows = latestTimeline.rows.map((row) => {
    const loaded = currentRowsById.get(row.id);
    return loaded === undefined
      ? row
      : prependOlderTimelineRows({
          olderRows: [loaded],
          loadedRows: [row],
        })[0]!;
  });

packages/client-core/src/timeline/timeline-merge.ts:180 recursively joins turn children and delegation child rows. packages/client-core/src/timeline/timeline-merge.ts:232 constructs deduplication arrays, sets, and a map before returning the original loaded object when children are unchanged. Returning the same row object therefore does not imply that recursive work was avoided. The separate safety case proves that the normalization must not simply be removed.

Cache granularity and closed-step wrappers

packages/thread-view/src/timeline-view.ts:926 uses an outer-array WeakMap and unconditionally spreads turn and delegation rows into new projections when that outer array is new.

function toTimelineViewRow(
  row: TimelineRow,
  cache: TimelineViewRowsCache,
): ThreadTimelineViewRow {
  switch (row.kind) {
    case "conversation":
    case "system":
      return row;
    case "work":
      return toTimelineViewWorkRow(row, cache);
    case "turn":
      return {
        ...row,
        children: row.children
          ? buildTimelineViewRows(row.children, {
              cache,
              closedScope: true,
            })
          : null,
      };
    default:

packages/thread-view/src/timeline-view.ts:983 misses its cache for a new outer array. packages/thread-view/src/timeline-view.ts:874 additionally creates a fresh singleton closed-step work wrapper. Caching only the delegation conversion would leave that wrapper allocation unresolved.

function closeOpenStepAtBoundary(
  work: TimelineWorkSummaryChild[],
): ThreadTimelineViewRow[] {
  if (work.length === 0) return [];
  if (!work.some((row) => row.kind === "work")) return work;
  if (work.length === 1) {
    return work.map((row) =>
      row.kind === "work" ? { ...row, inClosedStep: true } : row,
    );
  }
  return [buildStepSummaryRow(work)];
}

Downstream consequence, not a full UI benchmark

apps/app/src/components/thread/timeline/ThreadTimelineRows.tsx:416 uses row identity as a short circuit before comparing render signatures. packages/client-core/src/timeline/timelineRowSignatures.ts:330 caches signatures by view-object identity. New equivalent view objects miss that cache. This code path explains additional signature work when the comparator reaches this branch; the investigation does not assert that every mounted row necessarily reaches it on every render.

6. Proposed fix

Remember immutable row objects that have completed recursive normalization, and skip only subsequent self-joins of those same objects. Keep joining changed rows and retaining recursive duplicate removal. Reuse per-input-row view projections, including singleton closed-step work wrappers, while preserving grouping and open/closed-scope behavior. Add a scope-sensitive regression if changing cache keys or scope handling. No production fix was attempted here because an open pull request already links the issue.
