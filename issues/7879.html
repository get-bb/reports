#7879 · Plugin command transport bypasses configured proxies

Bug Priority: Medium Effort: Low cli · plugins

November 20, 2026 · Issue #7879 · base 9f4c15646d3d7d9320191d4a2cd76199471a1ddc

Verdict: REPRODUCED · Root-cause confidence: high

1. TL;DR

Plugin command execution selects a dedicated HTTP dispatcher that does not read proxy environment variables. On a network where the server name is resolvable only by a configured proxy, the command therefore fails with fetch failed. A real local HTTP origin and CONNECT proxy reproduce the failure without a bb server, user credentials, or a sandbox. Repeating the same test in a second clean checkout gives the same DNS failure; direct and proxy-bypass controls pass. Replacing only the dispatcher implementation with the already-installed environment-aware agent fixes both uppercase and lowercase proxy settings while retaining the long command timeout.

5. Root cause

getPluginCliDispatcher constructs and caches a plain undici.Agent with a 65-minute headers timeout. That agent handles direct connections; it does not consume proxy environment settings. runPluginCliCommand supplies it explicitly on the POST, overriding any global fetch dispatcher. cliFetch forwards the dispatcher unchanged to fetch.

pluginCliDispatcher ??= new Agent({
  headersTimeout: PLUGIN_CLI_HEADERS_TIMEOUT_MS,
});
...
dispatcher: getPluginCliDispatcher(),

This explains the observed direct DNS error: the proxy can route the reserved destination, but the explicit direct agent attempts local DNS first. This is a transport-policy inconsistency, not a server authorization failure or plugin execution failure. The existing long-response timeout is intentional and must not be removed; an existing regression test protects it.

6. Proposed fix and validation

Use the existing undici EnvHttpProxyAgent for the cached command dispatcher, retaining the same headers timeout. It routes according to HTTP_PROXY / HTTPS_PROXY and NO_PROXY, including their lowercase forms, and uses a direct agent when no proxy applies. No dependency, protocol, schema, or stored-data change is needed. Document the command transport's environment handling in the existing networking documentation.
