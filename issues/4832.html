#4832 · Connect response deadline includes request upload

BugHighEffort: Mediumbug · remote · connect · partial-reproGitHub issue2026-10-04

Trusted base: c201f6490a63b10fd3d72561f89516134444c266

Verdict: PARTIALLY REPRODUCED · Root-cause confidence: high for the transport mechanism; unmeasured for the reported live model call.

1. TL;DR

Connect can return a gateway-generated HTTP 504 while a request is still uploading, or while a healthy origin is taking longer than 30 seconds to send headers. The existing Durable Object HTTP path and the optional worker-held relay path both start a fixed 30-second response deadline before uploading the body. A deterministic test against unchanged main reproduces the exact gateway error in both paths, including a case with a completely uploaded body. Fast requests succeed in the same harness. This does not prove that a particular large model context caused the reported live failure: no provider credentials, private thread context, production logs, or actual model timing were used.

class ReproSocket extends EventTarget {
  binaryType = "arraybuffer";
  readyState = 1;
  readonly sent: Frame[] = [];
  closed = false;

  accept(): void {}

  deserializeAttachment(): null {
    return null;
  }

  send(data: Uint8Array): void {
    if (this.closed) throw new Error("socket closed");
    this.sent.push(decodeFrame(data));
  }

  close(): void {
    this.closed = true;
  }

  deliver(frame: Frame): void {
    const event = new Event("message");
    Object.defineProperty(event, "data", { value: encodeFrame(frame) });
    this.dispatchEvent(event);
  }
}

5. Root cause

The default HTTP forwarding path defines RESP_HEAD_TIMEOUT_MS = 30_000. In proxyHttp, it starts the timer while registering a pending response, before sending the open-http frame and before calling the request-body pump:

const timeout = setTimeout(() => {
  this.failHttpStream(streamId, 504, "timed out waiting for the tunnel client");
}, RESP_HEAD_TIMEOUT_MS);
...
if (hasBody) {
  void this.pumpRequestBody(streamId, request.body!, tunnel);
}

The pending stream therefore shares one deadline across upload and all origin work before response headers. failHttpStream resolves an HTTP 504 with the observed error text and removes the pending entry. Subsequent response headers are too late.

The optional worker-held implementation is not a workaround. RELAY_RESP_HEAD_TIMEOUT_MS is also 30,000 ms. relayResponse deadline precedes pumpRequestBody invocation, and timeout closes the relay and settles the HTTP 504. Both implementations enforce this without a model-route-specific budget.

The upstream path is plausible but not sufficient to establish context-size causality. Account Pool contributes ANTHROPIC_BASE_URL via a serverPath; the host resolves contributed paths using BB_SERVER_URL. Account Pool parses the request, defines a 20,000 ms inline hold limit, can wait for an eligible quota hold, and awaits upstream fetch. These steps consume the same relay pre-header budget when the configured server URL traverses Connect. No assumption about the affected machine's actual server URL is needed for the transport reproduction.

6. Proposed fix and simple-fix decision

Separate a bounded request-upload deadline from the response-header deadline, and decide an appropriate finite model-route header budget. Preserve disconnect, cancellation and stalled-upload cleanup in both Connect HTTP implementations. Instrument body completion and upstream-header timing on an isolated synthetic model endpoint first, then compare representative real requests only with appropriate access and consent.

No pull request is safe under this rule's simple-fix criteria. Increasing or removing the model-route deadline requires a timeout-policy decision; moving the existing timer alone does not fix the already-uploaded, delayed-header case and can remove the only bound on a stalled upload. Changing the model-routing architecture is unnecessary for confirming the transport mechanism and is outside this investigation. The report is partial because the claimed context-size relationship has not been measured. No production patch, source branch, source commit, dependency, protocol or stored-data change was made.

GitHub issue timeline and open-PR search had no linked open pull request at investigation time. No linked PR branch or code was executed.
