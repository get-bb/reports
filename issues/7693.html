#7693 · Repeated preview mapping discards stable row identity

BugPriority: LowEffort: Lowthreads, perf, confirmed-reproGitHub issue2026-11-17 · base 1320c88e8abdd3f145bc9a5c305eace269fb2f28

Verdict: REPRODUCED · Root-cause confidence: high

1. TL;DR

Timeline updates can repeat work for old command-output previews even when those commands have not changed. At the trusted main commit, two preview passes over the same input turn produce equal content but different command and parent objects. The later reuse pass restores the first objects only after a recursive content comparison. The reproduction demonstrates this allocation-and-reuse cycle directly; it does not measure live-stream latency or CPU impact.

5. Root cause

Preview shortening remaps stable input rows on every build, allocating replacement leaves and ancestors before structural reuse deep-compares and restores the prior subtree. The preview threshold is 4,000 characters; the separate inline truncation cap is 32,000. Our 6,000-character input isolates preview allocation, without exercising cap truncation.

apps/server/src/services/threads/timeline-output-shortening.ts:80 allocates a new work row whenever the output exceeds the preview threshold:

export function previewTimelineRowOutput(row: TimelineRow): TimelineRow {
  if (row.kind !== "work") {
    return row;
  }
  if (
    (row.workKind !== "command" && row.workKind !== "tool") ||
    row.output.length <= TIMELINE_INLINE_OUTPUT_PREVIEW_THRESHOLD_CHARS
  ) {
    return row;
  }
  return {
    ...row,
    output: buildTimelineOutputPreview(row.output),
    outputPreview: row.outputPreview ?? {
      experimental_fullOutputAvailability: "available",
      totalChars: row.output.length,
    },
  };

apps/server/src/services/threads/timeline-output-shortening.ts:105 creates a new tree mapping on every invocation without a memo for the original rows:

export function shortenTimelineResponseOutputs(
  response: ThreadTimelineWindow,
  { maxInlineOutputChars, preview }: ShortenTimelineResponseOutputsOptions,
): ThreadTimelineWindow {
  const shorten = (rows: TimelineRow[]) =>
    mapTimelineRowTree(rows, (row) => {
      const truncated = truncateRowOutputs(row, maxInlineOutputChars);
      return preview ? previewTimelineRowOutput(truncated) : truncated;
    });
  const rows = shorten(response.rows);
  const updates = response.timelinePage.olderRowUpdates;
  const olderRowUpdates = updates && shorten(updates);

packages/server-contract/src/thread-timeline-operations.ts:10 copies a parent when its mapped children change. This identity loss propagates through every ancestor on the affected path; unaffected short-output branches can still retain identity. It is not accurate to say every timeline row is always rebuilt.

apps/server/src/services/threads/thread-timeline-windows.ts:181 runs shortening immediately before unchanged-window reuse. apps/server/src/services/threads/timeline-window-reuse.ts:19 and apps/server/src/services/threads/timeline-window-reuse.ts:52 show that different references enter the recursive JSON-value comparison. For an equal turn subtree, comparison succeeds at the parent and restores that subtree; this does not imply a separate comparison of every nested row afterward.

6. Proposed fix

Memoize the mapped row subtree by original immutable row identity and both transformation options, so an unchanged subtree skips both preview construction and descendant walking. Use weak identity keys to avoid retaining discarded input trees. Test option separation, changed child rows, older-row updates, and truncation-only paths. A leaf-only memo would leave the repeated parent-tree walk unresolved.

No fix branch or duplicate PR is created: the open linked PR #7700 already closes this issue. Its branch was not checked out or run.
