Reports · Issue #4492

Image “Open in editor” can prepare a terminal directory launch

2026-09-30 · Bug · Low priority · Low effort

PARTIALLY REPRODUCED · High confidence in the tested UI, target selection and invocation preparation.

Claim, expected and actual

The issue describes an image preview action labelled “Open in editor” opening a terminal at the containing directory. Expected: either open the image in a suitable app or label the action to reflect the actual target behavior.

In both clean runs, an actual FilePreview displays a synthetic SVG and the action remains labelled “Open in editor”. Clicking it runs the real buildOpenInEditorHandler and useLocalOpenTargets hook. With the file target explicitly set to Ghostty, the hook sends the image path and Ghostty target to a controlled loopback adapter. That adapter invokes the real macOS routing implementation against a temporary image file with process execution replaced by a recorder. With no terminal editor available, the recorded invocation is open -a Ghostty /SYNTHETIC/images: the image filename is absent.

Current main has separate workspace and file preferences. Setting only the workspace preference to Ghostty does not reproduce that routing in this fixture: automatic image-file selection chooses the available default app. This qualification materially narrows the issue’s original setup. The current button label is generic; a parenthesized suffix in this source is a keyboard shortcut, not a target name.

No real editor or terminal process was launched. The observed invocation is the actual output delivered to the injected execution boundary, not proof that macOS or Ghostty opens a window. The Vim case records a proposed command and does not execute it or establish useful image viewing.

Root cause and proposed change

The preview header uses the generic “Open in editor” label whenever a callback exists, including image state. The handler constructs an absolute path without selecting an image-specific action. The real hook resolves the preferred file target for that path. An explicit available file target wins even for an image; automatic fallback ranks native/default apps ahead of terminals for image extensions. The fixture verifies that distinction.

Terminal invocation preparation resolves the configured or available terminal editor. Ghostty launch argument construction uses the containing directory when no editor command is available, and an editor command plus file path otherwise. The tested directory-only result follows this branch; it should not be generalized to every terminal configuration.

Proposed fix: make the image action target-aware, for example “Open in Ghostty” when an explicit terminal target is selected, and offer a distinct “Open with default app” action for images. Preserve explicit target intent unless product policy deliberately changes it. Avoid describing a containing-directory action as image editing. Add integration coverage for other terminal targets, native invocation and actual image-viewing behavior. No production fix or PR was created.

Limits, corrections and trust boundary

The test uses a synthetic SVG image and text control, not the reporter’s JPEG or files. It does not exercise the full thread controller, plugin-file-opener integration, real daemon transport, native app discovery, actual macOS/terminal windows, other terminal products, original 0.44.0 behavior, or OS default image viewing.
