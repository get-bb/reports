#8115 · Selected plugin installs materialize unrelated files

BugPriority: MediumEffort: MediumpluginsperfGitHub issue2026-11-24 · base af25b0b5a604addd91e70d855c4020fd70ac56bb

Verdict: REPRODUCED · Root-cause confidence: high · reproduction label: confirmed-repro

1. TL;DR

Installing one plugin from a git collection successfully loads that plugin, but also writes a sibling plugin and unrelated repository content into the managed checkout. The server fetches one commit and performs an unrestricted checkout before resolving the requested directory. Limiting history depth therefore does not limit the working tree. Both a named collection entry and an explicit subdirectory reproduce the defect through the real plugin service in two clean checkouts. This report verifies the extra materialization, not the reporter’s machine-specific timing or network savings.

5. Root cause

The shallow-fetch helper, lines 150–184, receives only URL, staging directory, commit, and an error hint. It has no selection information. After fetching the commit it performs an unrestricted detached checkout:

    await runInstallCommand("git", [
      "-C",
      stagingDir,
      "fetch",
      "--quiet",
      "--depth",
      "1",
      "--no-tags",
      url,
      commit,
    ]);
    await runInstallCommand("git", [
      "-C",
      stagingDir,
      "checkout",
      "--quiet",
      "--detach",
      "FETCH_HEAD",
    ]);

cloneGitCommit, lines 187–224, verifies the commit and removes the git metadata; it does not narrow the materialized tree. Its full-clone fallback is also unrestricted. The install caller, lines 843–864, resolves the selected path only after cloneGitCommit finishes:

      await mkdir(dirname(targetDir), { recursive: true });
      try {
        deps.onArtifactMaterialize?.({ path: targetDir });
        await cloneGitCommit(
          parsed.url,
          stagingDir,
          resolvedCommit,
          '"git" was not found on PATH — git: plugin installs require git',
        );
        const stagedSubdirectory = await resolveSelectedSubdirectory({
          checkoutDir: stagingDir,
          selection,
          sourceLabel: source,
        });
        const stagedRegistrationIdentity = identityFor(stagedSubdirectory);
        const stagedTargetRoot = pluginRootDir(targetDir, stagedSubdirectory);
        const stagedRealRoot = await realPathInside(
          stagingDir,
          pluginRootDir(stagingDir, stagedSubdirectory),
          "git plugin subdirectory",
          stagedSubdirectory === null,
        );

The first installation promotes the staging checkout as a whole when no target exists (promoteGitPluginArtifact, lines 555–571). Selecting a plugin changes which directory is built and registered, not which repository files have already been fetched and written. That is why unrelated content remains in the immutable cache even though only one plugin is active. The defect is in managed plugin artifact materialization, not the provider or CLI wait loop.

6. Proposed fix

Make the managed git checkout aware of the selected plugin before writing the full tree. Resolve explicit subdirectories directly; for collection entries, obtain the collection manifest first and then include the selected tree. Preserve the behavior of root installs, fallback servers, cancellation, shared-cache promotion, recorded-subdirectory updates, and in-repository symlink targets. A blob-filtered fetch can reduce transfer where supported, but restricting the working tree is a separate requirement. Treat symlinked directories and collection metadata outside the initial sparse tree as compatibility cases, not reasons to weaken path containment checks.

No production fix is included: GitHub metadata confirms that ready, open PR #8116 already declares this issue in its closing references. Opening another PR would duplicate active work.
