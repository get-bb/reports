#7092 · Stop loses cancellation before delayed Codex activation

BugMedium priorityMedium effortproviders · threads · provider-codexGitHub issue

November 5, 2026 · trusted main 2d912ea09011708b6a331c1ee7a15bea6ad32970

Verdict: REPRODUCED at the provider-bridge boundary · Root-cause confidence: high · reproduction label: confirmed-repro.

1. TL;DR

Stop can fail after an accepted Codex turn has not yet become natively interruptible. The bridge waits five seconds for native activation, returns the early interrupt rejection, and leaves the session alive without a deferred cancellation. A repository-owned fake app-server delayed by 6.5 seconds demonstrates the failure, while its 350 ms control stops normally. A second Stop after delayed activation succeeds. This report does not establish how frequently real Codex activation is delayed and does not reproduce the full UI remaining at “stopping.”

5. Root cause

  1. Accepted start-response handling opens a bb turn from the accepted native response and tracks it as not yet natively started.
  2. interruptCodexTurn recognizes the specific premature interrupt rejection and waits only INTERRUPT_SETTLEMENT_TIMEOUT_MS = 5_000. At timeout it returns the original failure.
  3. waitForNativeTurnStart removes its waiter at timeout. There is no retained cancellation intent.
  4. handleThreadStop returns the error before reaching interrupted settlement or releaseSession, leaving the app-server alive to activate later.
  5. Server stop settlement returns an interrupt-command failure while a thread is still stopping; the public stop entry point does not throw that failure unless a stopped result was required. This explains the reported UI symptom as a source-supported inference, not a fresh UI observation.

The defect is not a long-running interrupt after native activation. It is an accepted turn whose activation arrives after a bounded retry has been discarded.

6. Proposed fix and validation

For explicit Stop only, recognize the exact premature-interrupt error while the response-opened turn is still awaiting native activation. Once its five-second wait expires, use the already-existing interrupted-boundary and session-release path instead of returning early. Awaiting release kills the session before returning Stop success, preventing later native work. This deliberately avoids an unbounded retry or a new background-cancellation lifecycle. Permission-change steering retains its existing failure semantics; unrelated interrupt errors and post-activation errors still propagate.

The local fix changes 102 text lines (63 additions + 39 deletions) across three files in the existing Codex bridge subsystem. There are no dependencies, protocol/schema changes, persistent-data changes, generated files, or packaging changes.

  • The focused regression was added first: unchanged production code failed the 6,500 ms case and passed 350 ms in both clean checkouts.
  • With the fix, all 24 zero-work/stop tests pass, including permanent non-activation, second rejection, unrelated rejection, completion races, and native-start timing.
  • Full plugin suite: 45 files, 562 tests pass. Turbo lint and typecheck pass.
