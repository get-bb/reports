#6172 · Pool recovery leaves retry decisions stale

BugPriority: MediumEffort: Highproviders · threads · provider-retryGitHub issue2026-10-23

Base: 1e80ca7b44bccd06c6da75ed9ca6ba497bd380f5, trusted origin/main.

Verdict: REPRODUCED · Root-cause confidence: high. The same agent repeated the reproduction in a second clean trusted checkout. This is not an independent review.

1. TL;DR

Account Pooler can become usable while an automatic retry still waits for an old quota reset. The real Provider Retry entry point queries the real pool once, when the turn fails, then records either a fixed queue schedule or a decline. Enabling a previously disabled reserve account changes the pool's answer to ready, but neither pending nor declined decisions are revisited. A plugin reload also leaves that decision unchanged. Four focused integration scenarios reproduce this on current main with a real migrated core database, real pool storage, and no live provider accounts.

5. Root cause

The decision has no refresh lifecycle

Provider Retry server entry, lines 52–110, performs discovery and availability reads only inside turn.failed. It either returns after recording a decline or submits a fixed sendAt through threads.retry. There is no scheduler service, startup queue scan, account-change subscription, or message.dispatch hook in this entry.

bb.events.on("turn.failed", async (event) => {
  ...
  const decision = decideRetry({ availability, failure: event, ... });
  ...
  if (decision.kind === "decline") {
    await recordDecision();
    return;
  }
  await bb.sdk.threads.retry({
    threadId: event.threadId,
    turnRequestId: event.requestId,
    sendAt: decision.sendAt,
    reason: decision.reason,
  });
});

Retry policy, lines 53–60, fixes the timestamp to the later of reset and now, plus a 15-second buffer and up to 30 seconds of jitter. Lines 126–143 immediately decline unavailable sources and resets beyond maximumWait. The server stores only one diagnostic under a per-thread key, not a recovery-candidate lifecycle.

The pool recovers correctly, but the retry plugin never learns it

PoolOperations.enable enables the account and clears its error and hold, then notifies its callbacks. The server callback wiring publishes a realtime client signal and refreshes usage. PluginRealtime is an ephemeral client-WebSocket broadcast, not a server plugin event subscription. Config changes similarly publish a client signal in config.set.

Account availability correctly returns ready when any enabled, nonerrored account is usable. Both runs directly verified this after enable, ruling out a stale pool answer as the cause.

A complete repair crosses the queue boundary

Core retry creation enforces one live row and the current failed request. Queued-message update accepts a concurrency timestamp and prompt input, not a replacement schedule. Sending now is not an equivalent reschedule: its contract bypasses all plugin waits. The queue drain forwards the stored retry reference; the separate stale-request dispatch concern was inspected but not dynamically exercised.

6. Proposed fix and simple-fix gate

A complete repair needs a cross-plugin availability-change path, Provider Retry reconciliation of still-current candidates at recovery and startup, and bounded missed-signal recovery. It must reschedule a live row without incrementing attempts or bypassing ordinary dispatch hooks. Candidate retention, original-failure maximum-wait accounting, jitter, later resets, and due-time request validity need explicit semantics and tests.

No automatic code PR is safe under this rule. The end-to-end repair spans Account Pooler, Provider Retry, and core queued retry behavior, and needs a rescheduling/notification contract decision. It fails the one-existing-subsystem and no-public-contract/product-decision gates. No production patch, fix branch, push, or code PR was attempted. GitHub issue timeline and open-PR search showed no linked open PR during this run. A narrow send-now workaround would violate plugin wait policies.
