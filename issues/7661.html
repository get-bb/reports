#7661 · Cookie lifetime at the desktop persistence boundary

BugPriority: MediumEffort: Highdesktop · partial-reproGitHub issue2026-11-17

Trusted base: 64c272a16e68ddac62b3303014c8f95032815d3c. Verdict: PARTIALLY REPRODUCED · Root-cause confidence: medium.

1. TL;DR

The import path preserves the distinction between temporary session cookies and cookies with an explicit expiration. A real synthetic Chromium database passed through the actual reader and writer produces a session-cookie write without an expiration, alongside an unchanged persistent expiration, and invokes a disk flush. Electron’s installed API declarations document that cookies without an expiration are not retained between sessions; the desktop Browser uses a persistent partition without a separate session-cookie restoration path in the inspected code. This supports the proposed restart mechanism but does not demonstrate a live sign-out. Two clean checkouts produced the same boundary results, while both attempts to launch the real Electron restart test stopped before application code because this host lacks libglib-2.0.so.0.

const { DatabaseSync } = require("node:sqlite");
const { app, session } = require("electron");

const phase = process.argv[2];
app.setPath("userData", process.argv[3]);
app.disableHardwareAcceleration();

app.whenReady().then(async () => {
  const browserSession = session.fromPartition(BB_BROWSER_PARTITION);
  const filter = { url: "https://cookie-probe.invalid/" };
  if (phase === "seed") {
    const database = new DatabaseSync(":memory:");
    database.exec("CREATE TABLE meta (key TEXT, value TEXT); INSERT INTO meta VALUES ('version', '23'); CREATE TABLE cookies (host_key TEXT, name TEXT, value TEXT, encrypted_value BLOB, path TEXT, expires_utc INTEGER, is_secure INTEGER, is_httponly INTEGER, samesite INTEGER, top_frame_site_key TEXT)");
    const insert = database.prepare("INSERT INTO cookies VALUES (?, ?, ?, ?, ?, ?, ?, ?, ?, ?)");
    const future = (11644473600 + Math.floor(Date.now() / 1000) + 3600) * 1000000;
    insert.run("cookie-probe.invalid", "transient_control", "synthetic", Buffer.alloc(0), "/", 0, 1, 1, 1, "");
    insert.run("cookie-probe.invalid", "durable_control", "synthetic", Buffer.alloc(0), "/", future, 1, 1, 1, "");
    const read = readChromiumCookieDatabase(database, {});
    database.close();
    assert.equal(read.cookies.length, 2);
    assert.equal(read.cookies.find((cookie) => cookie.name === "transient_control").expirationDate, undefined);
    const outcome = await writeCookies(browserSession, read);
    assert.equal(outcome.imported, 2);
    assert.equal(outcome.skipped, 0);
    const cookies = await browserSession.cookies.get(filter);
    assert.equal(cookies.length, 2);
    assert.equal(cookies.find((cookie) => cookie.name === "transient_control").session, true);
    assert.equal(cookies.find((cookie) => cookie.name === "durable_control").session, false);

5. Root cause

The verified portion is an import-to-lifetime contract, not an expiry conversion error. Chromium expiry conversion maps zero expiry to absence, and the reader’s output carries it through. The writer then intentionally omits the expiration property:

...(cookie.expirationDate === undefined
  ? {}
  : { expirationDate: cookie.expirationDate })

Successful imports already flush. Flushing is a storage operation, not an instruction to change cookie lifetime. The installed electron@44.10.2/electron.d.ts CookiesSetDetails.expirationDate declaration (lines 22031–22036) explicitly documents that omission makes a session cookie that is not retained between sessions. That declaration is inspected local dependency evidence; Electron’s native persistence flags were not independently inspected or exercised here.

The partition constant is persist:bb-browser. The manager chooses that default, and creates the session with fromPartition. The import handler supplies the manager’s session. Source inspection of these paths found no separate session-cookie snapshot/restore mechanism. Therefore a persistent partition alone does not address the documented session-cookie lifetime. This mechanism is a supported explanation for the restart report, but its runtime consequence and Chrome comparison remain unverified.

6. Proposed fix and safety gate

First run the supplied Electron regression on a host with the existing runtime prerequisites and a disposable profile. It should distinguish missing session cookies from lost persistent storage before any repair is attempted. If confirmed, decide the intended desktop restoration policy, then design scoped encrypted persistence with restoration before navigation and durable deletion/replacement handling. Test logout, expiration, replacements, normal exit and any supported crash recovery; a flush-only change would not change the lifetime contract.

No product patch or pull request is safe under this rule. Restart loss was not reproduced. Also, implementing durable session-cookie retention introduces stored authentication-bearing data and needs a product/security persistence decision, independently failing the simple-fix restrictions.
