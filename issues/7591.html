The Linux installer knows its home directory, but the systemd unit it writes does not preserve that directory in the service environment. 5. Root cause

Installer HOME recovery and root/system scope selection happen in the installer process. Later, the generated unit includes only these environment entries:

Environment="BB_APP_NPM_PREFIX=$escaped_bb_app_npm_prefix"
Environment="BB_DATA_DIR=$escaped_data_dir"

A newly started system service does not inherit the installer’s shell environment merely because the installer called systemctl. If the manager supplies no HOME, this unit supplies none either. No User directive requests account-context initialization on that root system-unit path. The missing value can then reach child CLIs: child-environment sanitization copies existing variables and removes BB_* and NODE_ENV, but does not populate HOME. Provider spawning and terminal environment assembly use this inherited environment plus explicit overrides. An override or login shell can mask the omission; none is guaranteed by the unit itself.

The deeper boundary error is treating recovery in the short-lived installer as recovery in a separately supervised daemon. The isolated Git probe verifies the resulting configuration-lookup mechanism, without claiming to have run the reporter’s actual enrolled machine.

6. Proposed fix and autopilot decision

Persist the intended home in the generated systemd Environment directive using the existing systemd escaping helper. Do not alter the service’s execution user as a shortcut. Check whitespace, percent, quote and backslash escaping, and preserve a deliberately configured home. Consider a separately reviewed POSIX daemon-start fallback for already-installed services, since an installer-only repair will not rewrite existing units.
