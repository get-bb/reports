#6118 · Child execution defaults bypass parent history

Bug Medium priority Medium effort providers cli · GitHub issue · October 22, 2026

Verdict: REPRODUCED · Root-cause confidence: high · Reproduction label: confirmed-repro

Trusted base: cc292b975fc35e16d7480cd9b8d55eff0ed88d8f

1. TL;DR

Creating a child without execution flags starts it with remembered project settings rather than its parent's last execution. This happens even when parent and project use the same provider: model and reasoning still come from the project. A real server creation test reproduces both variants, and the same test fails again in a second clean checkout. Provider selection has no parent input, and execution planning consults parent history only for permission mode. No real provider invocation or user runtime data is needed to demonstrate the wrong outbound start command.

Complete reproduction test
import { upsertProjectExecutionDefaults } from "@bb/db";
import { describe, expect, it } from "vitest";
import { createThreadFromRequest } from "../../src/services/threads/thread-create.js";
import { waitForQueuedCommand } from "../helpers/commands.js";
import { textInput } from "../helpers/prompt-input.js";
import {
  seedEnvironment,
  seedHostSession,
  seedProjectWithSource,
  seedThread,
  seedThreadRuntimeState,
} from "../helpers/seed.js";
import { withTestHarness } from "../helpers/test-app.js";

describe("child creation execution defaults", () => {
  it.each(["codex", "claude-code"])(
    "inherits %s parent execution ahead of remembered project defaults",
    async (parentProviderId) => {
      await withTestHarness(async (harness) => {
        const { host } = seedHostSession(harness.deps);
        const { project } = seedProjectWithSource(harness.deps, {
          hostId: host.id,
        });
        const environment = seedEnvironment(harness.deps, {
          hostId: host.id,
          projectId: project.id,
        });
        const parent = seedThread(harness.deps, {
          projectId: project.id,
          environmentId: environment.id,
          providerId: parentProviderId,
        });
        seedThreadRuntimeState(harness.deps, {
          threadId: parent.id,
          environmentId: environment.id,
          providerThreadId: "parent-session",
          model: "parent-model",
          reasoningLevel: "low",
          permissionMode: "auto",
        });
        upsertProjectExecutionDefaults(harness.db, {
          projectId: project.id,
          providerId: "codex",
          model: "project-model",
          reasoningLevel: "medium",
          permissionMode: "auto",
          serviceTier: "default",
        });

        const child = await createThreadFromRequest(harness.deps, {
          projectId: project.id,
          parentThreadId: parent.id,
          environment: { type: "reuse", environmentId: environment.id },
          input: textInput("Check execution defaults"),
          origin: "cli",
          startedOnBehalfOf: null,
        });
        const start = await waitForQueuedCommand(
          harness,
          ({ command }) =>
            command.type === "thread.start" && command.threadId === child.id,
        );
        expect(start.command.type).toBe("thread.start");
        if (start.command.type !== "thread.start") {
          throw new Error("Expected child start command");
        }
        expect({
          providerId: child.providerId,
          model: start.command.options.model,
          reasoningLevel: start.command.options.reasoningLevel,
        }).toEqual({
          providerId: parentProviderId,
          model: "parent-model",
          reasoningLevel: "low",
        });
      });
    },
  );
});

5. Root cause

The CLI forwards omitted execution fields as omissions and keeps the parent link (spawn.ts lines 602–619). The server validates and loads the parent, but calls its create-default resolver without that parent (parent validation; default resolver call).

Project create defaults consult only caller-owned input and project defaults. Provider policy then chooses:

args.requestedProviderId ?? storedProviderId ?? requireDefaultProviderId(registry)

The provider becomes immutable at creation. Later, execution planning loads parent history but model/reasoning candidates contain only request, child override, child last execution, and project execution. Only permission policy uses parentExecution. Thus an empty child history cannot supply the parent's selections, even when provider IDs match.

The guide contract is broader than the implementation. The introducing history added the parent-default wording while implementing only permission-history inheritance; this report does not infer that model/provider inheritance ever worked. The issue's separate claim about every CLI spawn updating remembered preferences is not true at this base: the remember policy accepts only app-origin creation outside reused environments and source-derived forks.

6. Proposed fix

Resolve creation defaults on the server using the already validated parent and its last recorded execution. Prefer caller-owned provider flags; otherwise select the parent's execution provider before project defaults. For a matching provider, use the parent's model and reasoning ahead of remembered project values, while leaving explicit model/reasoning overrides intact. Do not carry model or reasoning across an explicitly different provider. Keep the existing fallback when the parent has no recorded execution. Do not change permission policy, host protocol, stored schema, service-tier policy, or the public CLI/SDK contracts.

A focused regression should also cover explicit matching/different providers, explicit model/reasoning, source-aware stale picker values, and parents without history. Existing creation, runtime configuration, default policy, and execution-plan suites are the relevant sibling checks.
