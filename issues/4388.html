Reports · Issue #4388

Older-row updates repeatedly remove and reload visible history

2026-09-30 · Bug · Medium priority · Medium effort

PARTIALLY REPRODUCED · High confidence in the measured pagination/merge/renderer loop.

Claim and actual result

Previously loaded history should remain usable while an older background delegation changes. A Node fixture calls the real server paginateTimelineRows function on five synthetic projected rows, with two logical user-message segments and a one-segment latest page. Advancing the older delegation’s sourceSeqEnd generates a latest page with two rows and a higher olderRowsSourceSeqEnd marker.

In an optimized Chromium fixture, the real mergeLoadedTimelineWithLatest reduces five loaded rows to those two rows. The real ThreadTimelineSurface and useAutoLoadOlderRows observe the restored older cursor and invoke the fixture’s delayed reload. The visible surface shows “Loading older messages…” and only the latest page, then restores five rows. Four updates produced four visible drop/load/restore cycles in each clean run. A control advancing the latest answer’s source sequence retained five rows on all four updates in each run and never started an older-page reload.

Scope and limitations

This joins the actual pure server pagination function, client merge, timeline surface and IntersectionObserver auto-loader. It does not execute the server HTTP route, event projector, real provider/background process or full application controller. History-snapshot strings and source-sequence changes are synthetic inputs. The reload callback restores the full synthetic projected rows after an intentional 700 ms delay; it is not a real older-page network fetch. No running subagent is created: the row depicts synthetic background work only.

The BottomAnchorContext exposes the real fixture scroll element, but its scroll-adjustment callbacks are no-ops. Consequently this report establishes disappearance/loading/reappearance of history, not production scroll-jump magnitude or frequency. Four updates are applied sequentially after restoration, not at measured provider streaming cadence. No production latency, “many times per second” frequency, multi-megabyte transfer or real-provider claim is inferred. These integration gaps keep the verdict partial.

Expected versus observed

Expected: retain or reconcile loaded older rows while updating them, without repeatedly removing already visible history. Actual in both runs: sequence 12, 13, 14 and 15 each produces 5 → 2 → 5 visible top-level rows; the latest-page cursor is anchorSeq 10. The old-row marker advances to 12–15 and exceeds the prior client tip each time. In the latest-row control, the marker stays 3; all four merges keep five rows and a null loaded older cursor. Browser assertions check row count, loading text, restoration and control stability; no runtime exceptions occurred.

Trusted base and environment

Both frozen installs and builds succeeded. Two clean detached worktrees used separate node_modules, caches, browser profiles and loopback ports. Dependency downloads were shared. The second checkout regenerated its own pagination snapshots from the same source, rather than reusing the first output.

Root cause and proposed next change

Pagination computes the maximum source end among omitted rows. The advanced-snapshot merge rejects preservation when that marker exceeds the previous latestWindowEndSequence; the merge rebuilds from the latest page. The real sentinel effect starts loading again and the surface displays loading text. The fixture observes the resulting repeated reset/reload sequence.

Proposed fix: reconcile changed older rows through bounded updates or targeted invalidation without dropping all loaded history. Preserve correctness when older grouping or contents change; simply ignoring the marker risks stale rows. Add real event-projection/HTTP delta tests for background updates, then a full controller/browser streaming test with real pagination and scroll anchoring. No production fix or PR was created.
