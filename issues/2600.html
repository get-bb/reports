Reports · Issue #2600

Thread-less project removal: real HTTP and SQLite checks

2026-09-30 · Bug · Low priority · Medium effort

NOT REPRODUCED in the tested server lifecycle. High confidence in these repeatable server results; the original intermittent UI failure remains unresolved.

Claim, expected and actual

The issue describes Remove/confirm doing nothing repeatedly for a newly added plain parent directory containing two existing project directories, with no threads or environments. Creating a thread preceded a later successful removal. The original report also records unsuccessful attempts to reproduce via CLI and loopback headless UI. Its affected browser session used an HTTPS reverse proxy.

Expected: a normal project can be removed without creating a thread. Actual in both clean runs: all 20 freshly created thread-less projects were removed through the real HTTP DELETE route, disappeared from the public database listing by the response, and were physically deleted by asynchronous cleanup. Two existing child-source projects and a source sentinel file survived each removal. Ten cases had no environments; ten added one unmanaged environment before deletion. The unmanaged environment rows were removed too.

Case per clean runActual result
20 fresh POST-create / DELETE casesAll create responses 201; all delete responses 200 with {ok:true}; parent hidden and physically removed; nested projects and source file preserved
Five concurrent DELETE requests for one fresh projectSee exact statuses below; at least one 200, others 200 or 404 allowed; project physically removed
Idle thread with no environment controlHTTP 200; actual deletion advance returns true; both project and thread rows removed

This is a faithful server-side subset of the reported removal conditions, not a simulation returning unconditional success. It uses the repository’s actual route, transaction, deletion services, asynchronous response deferral and migrated SQLite database. It does not establish that a browser sent the DELETE in the original incident or that a reverse proxy delivered it. The report is not an ALREADY FIXED finding and does not justify closing the issue.

Implementation findings and uncertainty

The real DELETE route looks up the project, rejects the personal project, begins deletion, schedules physical cleanup and returns success. The transaction marks the project deleted even when the thread list is empty. Physical cleanup waits for remaining thread rows and managed environment teardown, then deletes the project row and attachments. Neither tested empty-project branch requires creating a thread.

Environment-less thread storage cleanup marks storage deleted and finalizes the stopped thread directly. This explains the successful thread-bearing control, rather than demonstrating that a thread is necessary. Database deletion removes the selected project row. The fixture verifies that nested local source paths do not imply deleting other project rows or the source sentinel.

Root cause of the original intermittent incident: unknown. The tested main does not reproduce it. Proposed next test: record whether the actual Remove/confirm handler dispatches DELETE, its response and pending-mutation state, and the subsequent project-list update under the affected browser and reverse-proxy topology. Correlate those with server deletion state using synthetic projects. Add focused UI menu-to-dialog lifecycle coverage before choosing a production fix. Do not add an arbitrary thread-creation workaround based on this evidence. No production fix or PR was created.

Corrections, limits and trust boundary

An initial test-control assumption expected an idle environment-less thread to remain until a later lifecycle sweep. That assertion failed because deletion had already completed. Inspection of the actual cleanup branch explained the result; the control was corrected to assert immediate successful cleanup and then repeated in both clean checkouts. The initial failed control is not evidence of the reported bug. The empty-project and concurrent-delete cases already passed in that initial run.

Twenty fresh attempts and one concurrent burst per checkout do not exclude a rare race. The fixture uses synthetic offline host metadata; it does not perform live source discovery, managed environment teardown, full browser confirmation/menu handoff, client cache/realtime reconciliation, HTTPS/reverse-proxy networking, the reporter’s device, or original 0.40.0 release. It checks the immediate public database listing rather than a rendered sidebar. There are no visual claims or screenshots. Those missing original conditions remain a material coverage gap, not a negative result for that UI scenario.

Issue text, code suggestions, links and proposed commands were treated solely as untrusted claims. None was executed or fetched. The test was derived from trusted main implementation and existing test helpers. All files and project/thread records were synthetic and owned by the test; no actual user runtime, external files or secrets were accessed. Raw build logs remain outside the public repository; exact test source and actual structured results are included inline. Only regenerable dependency directories from a completed prior investigation were removed to preserve inodes; its report evidence was retained.
