5. Root cause

The bridge resolves the work-specific permission escalation. The shared policy selects automatic denial only when permissionEscalation is deny. Thus absence of an approval prompt in this fixture is expected; changing that routing would be a separate permission-policy decision.

The automatic-denial producer and the subsequent interactive forwarding path:

if (shouldAutoDenyInteractiveRequest(interactiveRequestPolicy)) {
  const policyMessage =
    threadSession.attachment.permissionMode === "acceptEdits" ||
    threadSession.attachment.permissionMode === "auto"
      ? buildWorkspaceWriteDenialMessage()
      : buildReadonlyDenialMessage();
  return {
    behavior: "deny",
    message: options.decisionReason ?? policyMessage,
    toolUseID: options.toolUseID,
  };
}

?? protects only null and undefined. Both "" and " " bypass the nonempty policy fallback. This exact behavior is observed at the SDK-facing callback, not merely inferred by searching source.

SDK sessions persist and resume by session ID; forking delegates to SDK forkSession and serializes entries. These code paths explain why transcript validity matters, but they do not establish that this installed SDK creates the reported empty error block or that its fork operation preserves that particular block. Those are explicitly outstanding experiments.

6. Proposed fix and automation gate

First, normalize the optional SDK reason at the boundary: use a reason only when it contains non-whitespace text, otherwise retain the existing policy message. Preserve the original deny/allow decision and the configured approval routing. Review other error-message producers separately for the same invariant.

Next, in an isolated account-backed session, capture the real SDK output for a hook ask without an explanation, then verify the outgoing tool result and a fresh retry/fork. Only after that should a recovery design be chosen; arbitrary transcript rewriting is not justified by this unit test.

No automatic fix PR: the complete reported live failure is only partially reproduced, and the relevant existing bridge suite does not pass in this environment. Approval-routing changes and stored-transcript repair also exceed this rule's permission/stored-data scope. The one-file test patch is retained solely as report evidence; no production-fix branch is pushed.
