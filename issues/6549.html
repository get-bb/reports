1. TL;DR

A direct test of the production viewport hook shows that a shorter visual viewport can shrink an otherwise full-height standalone shell without any keyboard focus. With the 852/793 geometry already documented in the repository's standalone CSS, the hook writes a 793px inline height and publishes that height to body-portaled panels. That creates a conditional 59px loss relative to the supplied full-height containing block. This is not a reproduction of the reported foldable iPhone's actual viewport values or its approximately 50pt band. No production fix is justified until the device's viewport and safe-area values distinguish this mechanism from ordinary inset padding.

No device screenshot was produced. Browser Automation could not open because this host lacks a runnable Chrome installation; a temporary official Chrome binary also could not start because a required system library is absent. No system or repository dependency was added. No attachment URLs were fetched. This report deliberately does not present a mock image as visual evidence.

Complete diagnostic test
// @vitest-environment jsdom

import { cleanup, render } from "@testing-library/react";
import { useState } from "react";
import { afterEach, expect, it, vi } from "vitest";
import { useMobileVisualViewportHeight } from "./useMobileVisualViewportHeight";

function Shell() {
  const [shell, setShell] = useState<HTMLDivElement | null>(null);
  useMobileVisualViewportHeight(shell, true);
  return <div ref={setShell} data-testid="shell" />;
}

afterEach(() => {
  cleanup();
  vi.restoreAllMocks();
  vi.unstubAllGlobals();
});

function installViewport(height: number) {
  const viewport = Object.assign(new EventTarget(), {
    height,
    width: 393,
    offsetTop: 0,
    offsetLeft: 0,
    pageTop: 0,
    pageLeft: 0,
    scale: 1,
  });
  vi.stubGlobal("visualViewport", viewport);
  vi.spyOn(document.body, "clientHeight", "get").mockReturnValue(852);
  vi.stubGlobal("matchMedia", (query: string) => ({
    matches: query === "(display-mode: standalone)",
    media: query,
    onchange: null,
    addListener: vi.fn(),
    removeListener: vi.fn(),
    addEventListener: vi.fn(),
    removeEventListener: vi.fn(),
    dispatchEvent: vi.fn(),
  }));
}

it("leaves the shell full height when viewport and containing block agree", () => {
  installViewport(852);
  const { getByTestId } = render(<Shell />);
  expect(getByTestId("shell").style.height).toBe("");
  expect(document.body.style.getPropertyValue("--bb-shell-height")).toBe("");
});

it("preserves a standalone full-screen shell without keyboard focus", () => {
  installViewport(793);
  const { getByTestId } = render(<Shell />);
  const shell = getByTestId("shell");
  console.log(JSON.stringify({
    containingBlock: document.body.clientHeight,
    visualViewport: window.visualViewport?.height,
    shellHeight: shell.style.height,
    inheritedShellHeight: document.body.style.getPropertyValue("--bb-shell-height"),
    keyboardFocused: document.activeElement !== document.body,
  }));
  expect(shell.style.height).toBe("");
});

5. Root cause and limits

The standalone CSS sets the root shell to 100lvh to avoid a documented iOS short viewport. However, the visual-viewport hook compares the body's full containing-block height with visualViewport.height, and publishes the latter whenever they differ by more than one pixel. This path requires neither keyboard focus nor standalone detection.

const visualViewportHeight = Math.round(visualViewport.height);
shellContainingBlockHeight = document.body.clientHeight;
...
shell.style.height = `${visualViewportHeight}px`;
viewportStyleRoot.style.setProperty("--bb-shell-height", `${visualViewportHeight}px`);

AppLayout invokes the hook for both compact and wide views. The inline shell height and inherited body variable can therefore counteract the full-screen intent of the standalone CSS. If the platform supplies a shorter visual viewport while still displaying the full standalone screen, a bottom gap follows. Whether that premise holds for this phone is unknown.

Separately, the content shell owns the safe-area padding outside main; SettingsView uses PageShell’s nested overflow-y-auto viewport. Moving that padding is not proved safe: it would affect other routes, keyboard behavior, and genuine home-indicator protection. Header top padding directly follows the platform inset; a zero inset alone does not prove a bug.
