#7839 · Constraint-specific handling of failed memory writes

BugLow priorityLow effortplugins · memory · confirmed-reproGitHub issue2026-11-19

Trusted base: df9619d8e8aac4aff00c0c3ff9b8ef4e2823e4f2 (origin/main).

Verdict: REPRODUCED · Root-cause confidence: high

1. TL;DR

A failed history write can tell the user that a memory name is already taken even when it is not. The add operation performs two inserts in one transaction, then classifies every SQLite uniqueness failure as a name collision. A fault-injection trigger makes the history insert collide with a real history row, demonstrating the misleading diagnostic. The same regression fails in two separate trusted-base checkouts. This confirms an error-classification defect, not that ordinary memory additions naturally produce history collisions.

3. Run the focused regression through Turbo:

pnpm exec turbo run test --filter=bb-plugin-memory -- --testNamePattern='preserves history uniqueness errors'

Expected: exit code 1 from the failed CLI operation, with the underlying history constraint preserved in stderr. The enclosing regression should pass when this behavior is implemented.

Actual at the trusted base: the regression fails (Turbo exit code 1), because the CLI gives an unrelated duplicate-name explanation. The assertion's expected and received diagnostic lines are:

- UNIQUE constraint failed: memory_history.memory_id, memory_history.version
+ an active global memory named "history-conflict" already exists

The failing assertion runs before the rollback and retry assertions. Those later assertions are verified by the passing post-fix run, not by the failing base run.

5. Root cause

The add transaction and catch wrap both the memory insertion and the subsequent history insertion. The catch checks only a substring:

error instanceof Error &&
error.message.includes("UNIQUE constraint failed")

It then replaces the error with the duplicate-name CLI message. The history writer is inside that catch, and the schema has two distinct relevant uniqueness rules:

CREATE UNIQUE INDEX IF NOT EXISTS memories_active_scope_name
  ON memories(scope_key, name) WHERE deleted_at IS NULL;

UNIQUE(memory_id, version)

The trigger inserts the history key first. The real history writer attempts the same key, causing a genuine SQLite uniqueness error from the history table. Transaction rollback occurs, but the catch loses the original diagnostic. The deeper defect is choosing domain behavior from generic database error text rather than identifying the actual name-conflict operation.

6. Proposed fix and observed result

Handle only the existing partial active-name index at the memory INSERT itself: append ON CONFLICT(scope_key, name) WHERE deleted_at IS NULL DO NOTHING, then report a duplicate name only when that statement inserts zero rows. Remove the broad transaction catch. Preserve the enclosing transaction so history and full-text updates still roll back atomically.

The local candidate changes two files in the existing memory plugin: 79 additions and 39 deletions, 118 changed text lines. It changes no stored schema, migration, dependency, public protocol, or CLI flag. With the candidate applied, the new regression passes; its rollback assertions find no residual memory/history rows, and adding the same name succeeds after removing the trigger. The existing duplicate-name test still passes.

7. Linked pull request review

PR #7841 is closed and unmerged, so it is not an open competing fix. Its metadata and diff were read only after the new regression and candidate repair were designed and executed. Its branch and test were never checked out or run.

Static finding: its plugins/memory/server.ts change checks the SQLite uniqueness code and queries for an actual active name before translating the error. This appears to avoid the demonstrated false message because the failed transaction leaves no matching name. No blocking static finding was identified for this reported scenario, but this is not runtime verification of that patch. The candidate described above instead uses an explicit SQL conflict target and avoids inferring the constraint from a later lookup.
