#6015 · Desktop notification activation and renderer lifecycle

Bug Priority: Medium Effort: Medium desktop remote partial-repro

GitHub issue · October 21, 2026 · trusted main b143a22860944a96bf183605dfb0ffe58b1de283

PARTIALLY REPRODUCED · Root-cause confidence: medium

1. TL;DR

The reported problem is a Windows notification-history click that no longer opens its thread after the banner expires. This investigation could not exercise Windows Notification Center: the available host runs Linux. Trusted main does use a renderer-owned web Notification and its JavaScript click callback, rather than a durable notification activation route. A related lifecycle defect is reproduced: changing the navigation object's identity disposes delivery, closes outstanding notifications, and makes their retained click callbacks return without navigating. That defect repeats in two clean trusted checkouts; it does not establish the separate Windows timeout/COM mechanism.

Complete reproduction test
// @vitest-environment jsdom
import { act, cleanup } from "@testing-library/react";
import { useMemo } from "react";
import { loadPluginApp, renderSlot } from "@get-bb/plugin-sdk/testing/app";
import { afterEach, beforeEach, describe, expect, it, vi } from "vitest";
import { CLIENT_NOTIFICATION_CHANNEL } from "./contract.js";

const route = vi.hoisted(() => ({ revision: 0 }));

vi.mock("@get-bb/plugin-sdk/app", async (importOriginal) => {
  const actual = await importOriginal<typeof import("@get-bb/plugin-sdk/app")>();
  return {
    ...actual,
    useBbNavigate() {
      const navigation = actual.useBbNavigate();
      return useMemo(() => ({ ...navigation }), [navigation, route.revision]);
    },
  };
});

class NotificationProbe {
  static permission = "granted";
  static instances: NotificationProbe[] = [];
  onclick: (() => void) | null = null;
  onclose: (() => void) | null = null;
  close = vi.fn();

  constructor(
    readonly title: string,
    readonly options: NotificationOptions,
  ) {
    NotificationProbe.instances.push(this);
  }
}

const app = await loadPluginApp(() => import("./app.js"));
const message = {
  id: "repro-event-1",
  title: "Turn complete",
  body: "Ready to read",
  threadId: "thr_repro",
  channels: ["desktop"],
};

beforeEach(() => {
  route.revision = 0;
  NotificationProbe.instances = [];
  localStorage.clear();
  vi.stubGlobal("Notification", NotificationProbe);
  vi.stubGlobal("isSecureContext", true);
  vi.stubGlobal("bbDesktop", { platform: "windows" });
  vi.spyOn(window, "focus").mockImplementation(() => undefined);
});

afterEach(() => {
  cleanup();
  vi.unstubAllGlobals();
  vi.restoreAllMocks();
});

async function mountDelivery() {
  const overlay = app.appOverlays[0]!;
  const view = renderSlot(overlay, {}, { settings: { desktopEnabled: true } });
  await view.behavior.emitRealtime(CLIENT_NOTIFICATION_CHANNEL, message);
  expect(NotificationProbe.instances).toHaveLength(1);
  return { view, overlay, notification: NotificationProbe.instances[0]! };
}

describe("issue 6015 renderer boundary", () => {
  it("opens the target when Windows delivers the renderer click callback", async () => {
    const { view, notification } = await mountDelivery();
    act(() => notification.onclick?.());
    expect(view.inspection.navigateCalls).toEqual([
      { method: "toThread", threadId: "thr_repro" },
    ]);
    expect(window.focus).toHaveBeenCalledOnce();
  });

  it("does not itself invalidate the click callback on an OS close event", async () => {
    const { view, notification } = await mountDelivery();
    act(() => notification.onclose?.());
    act(() => notification.onclick?.());
    expect(view.inspection.navigateCalls).toEqual([
      { method: "toThread", threadId: "thr_repro" },
    ]);
  });

  it("preserves an outstanding notification across navigation identity changes", async () => {
    const { view, overlay, notification } = await mountDelivery();
    const Overlay = overlay.component;
    route.revision += 1;
    view.lifecycle.rerender(<Overlay />);
    expect.soft(notification.close).not.toHaveBeenCalled();
    act(() => notification.onclick?.());
    expect(view.inspection.navigateCalls).toEqual([
      { method: "toThread", threadId: "thr_repro" },
    ]);
  });
});

5. Root cause

Verified lifecycle cause: NotificationDelivery's effect depends on the entire navigation object:

useEffect(() => {
  const next = createClientDelivery((id) => navigate.toThread(id));
  delivery.current = next;
  return () => {
    delivery.current = null;
    next.dispose();
  };
}, [navigate]);

toCompose depends on location.pathname, and the returned navigation object depends on toCompose. When that identity changes, React runs cleanup. dispose() sets disposed and closes active notifications:

disposed = true;
for (const notification of active) notification.close();
active.clear();

The old click handler returns immediately when disposed. Thus the thread target can remain in a callback that is no longer usable.

Primary Windows cause remains a hypothesis: desktop delivery uses new Notification and onclick. Native focusWindow is requested only for Linux. Inspection of desktop main/preload found no dedicated durable toast activation route. These facts explain dependence on a live renderer callback; they do not prove that Windows timeout removes Chromium's listener or that a specific native activation design will resolve the report. In particular, bb's own onclose handler only removes the active-set entry, which is why the close-event control still navigates.

6. Proposed fix and safety decision

For the verified lifecycle defect, keep delivery alive across unrelated navigation-object changes while dispatching through the latest navigation callback. Preserve cleanup on actual overlay unmount. The included failing case is the owner-boundary regression target.

For the primary report, first run a real Windows packaged desktop session, capture whether the renderer receives the post-timeout click, and trace native activation arguments for both a visible banner and notification history. Keep the renderer alive and do not navigate during this experiment, to separate timeout from the verified route-change defect. Then decide whether durable main-process notification activation is required, including server/window selection and restart behavior.

No pull request: the primary Windows timeout path was not reproduced on the available Linux host. Shipping a platform activation change without that proof would fail the requested simple-fix gate. No production patch, fix branch, or pull request was created.
