#8164 · Native text preferences do not reach hosted typography

BugPriority: MediumEffort: MediummobileuiIssueNovember 25, 2026 · base fb045a046653cc127656ca3c7243d44ae4c94f3f

Verdict: PARTIALLY REPRODUCED · Root-cause confidence: medium · Reproduction label: partial-repro

1. TL;DR

The reported problem concerns text in the hosted web app, not the native settings interface. Trusted main has no native font-preference forwarding in its WebView screen, and the hosted stylesheet fixes text adjustment at 100%. An executable probe of the real handshake parser and injected bridge confirmed that a valid iOS handshake installs successfully, supported reinjection updates safe-area data, and neither installation nor reinjection updates document typography. The same probe produced identical results in a second clean checkout. This is code-path evidence for a missing integration, not a repeat of the reported iOS visual experiment: no iOS Simulator or working browser runtime was available, so the report deliberately retains a partial verdict.

5. Root cause

The actionable integration gap is between native accessibility preferences and web typography. The shell neither reads the system font scale in this screen nor injects a corresponding typography update on preference changes. Its injected handshake has safe-area and capability data but no font scale. The hosted app therefore has no explicit native text-scaling input through this path.

  • WebView handshake construction: no typography preference; dependencies are profile, safe area and source URL.
  • Load-time WebView injections: the iOS after-load script constrains viewport zoom; document-start injection installs the bridge. Neither forwards text size.
  • Strict handshake parser and shell-to-page events: no current font-preference field or event.
  • Bridge installation and apply/receive logic: native metadata is copied and supported events are delivered, without applying typography to the document.
  • Hosted base stylesheet fixes both text-adjustment properties at 100%.
html {
  -webkit-text-size-adjust: 100%;
  text-size-adjust: 100%;
}

Important distinction: text-size-adjust controls browser text adjustment; the presence of 100% is not, by itself, proof that every iOS Dynamic Type implementation must fail. The native preference forwarding gap is verified; its causal explanation for the full pixel-level report remains medium confidence until checked in WKWebView.

6. Proposed fix and next experiment

Read the native preference at the mobile shell boundary and apply it to hosted typography on document load, reload, resume and preference changes. Keep normal browser clients and the default scale unchanged. A shell-local injection can avoid changing the public bridge handshake; do not weaken the strict parser merely to satisfy this diagnostic. Validate composer editors and compact controls separately, since fixed heights and non-root-relative editor sizes can clip enlarged text even when general text adjustment works.

The next decisive experiment requires an iOS Simulator or device: compare a populated thread and a new-thread composer at default and enlarged accessibility settings, return from Settings without restarting, then reload and verify text sizes and control reachability. Capture genuine before/after screenshots and native settings as a positive control. That experiment was not performed here.
