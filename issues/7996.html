#7996 · Agent follow-up dispatch disables interactive approvals

Bug Priority: Medium Effort: High providers security provider-acp

GitHub issue · 2026-11-21 · trusted base 35a03bbbb3f4d8dc814c1a152db5a463102b4250

Verdict: REPRODUCED at the server-to-host dispatch boundary, repeated in a second clean checkout. Root-cause confidence: high. Reproduction label: confirmed-repro.

1. TL;DR

An agent sending follow-up work to a child thread changes the dispatched approval policy even when that thread remains in accept-edits mode. A real server harness produces permissionEscalation: "ask" for a human follow-up and "deny" for the otherwise equivalent agent follow-up. The host runtime can then refuse approval requests without invoking the callback that would persist and display an interaction. This is an explicit current policy, covered by existing tests, rather than an accidental missing conditional. Relaxing it safely requires a permission/delegation decision, so this investigation does not open an automatic fix PR.

5. Root cause

  1. Dispatch author resolution classifies a non-null sender as agent-originated.
  2. Follow-up dispatch passes the resolved sender to that classifier. It then calls the escalation resolver with only the initiator; the resolver cannot consider a sender or delegate.
  3. The resolver explicitly denies all non-user initiators: 
    export function resolvePermissionEscalation(
  args: ResolvePermissionEscalationArgs,
): PermissionEscalation {
  if (args.initiator !== "user") {
    return "deny";
  }

  return "ask";
}
  4. The actual host command builder serializes the resulting policy into turn.submit.options. This is the transport boundary asserted by the reproduction, not a mocked policy function.
  5. ACP's bridge handshake declares runtime-owned approvals. The runtime handler reads the current execution policy, sends a denial response, and returns before invoking the interactive-request callback. That explains why no pending-interaction entry is created by this path.

Underlying design issue: the existing server permission matrix deliberately expects agent/system denial. Separately, needs-attention notices use the thread's structural parent, not a per-turn sender. Simply returning ask would neither define delegated authority nor implement sender-specific routing.

The first-spawn asymmetry is consistent with the CLI's creation payload and creation author resolution. This supporting finding is static; it is not presented as a live spawn/approval test.

6. Proposed fix and simple-fix decision

Maintainers should first define the authority and lifetime of delegated approval for a non-user turn. Any implementation must connect that policy to the same authorization, interaction persistence, and notification paths used by normal approvals, rather than treat a structural parent notification as permission to approve. The first implementation experiment should extend the dispatch and interaction boundary tests together, with explicit negative authorization cases and unchanged unattended/system behavior.

No automatic fix PR: the required change alters a permission/security boundary and needs a product-policy decision; both are excluded by this automation's simple-fix criteria. Existing tests explicitly lock in the current deny behavior. No production patch, fix branch, or push to the application repository was made. No linked open PR was found in issue cross-reference metadata or the open-PR search at investigation time.
