#7422 · Browser execution omits its host deadline override

Bug Priority: Medium Effort: Low plugins cli

GitHub issue · November 11, 2026 · trusted base 365d7c5237ae270be0555b5b44ea61020252713e

Verdict: REPRODUCED at the plugin-to-host RPC boundary. Root-cause confidence: high. Reproduction label: confirmed-repro.

1. TL;DR

The browser plugin accepts script execution budgets longer than 30 seconds but does not put that budget into its host-call options. A focused test invoking the real plugin entry and public RPC handler observes the script budget in the host input and an absent host deadline override. The server therefore chooses its 30-second default, and the daemon enforces that shorter deadline; the plugin then stops the session when the call throws. The same omission reproduces in two separate clean checkouts of trusted main. These are boundary-level reproductions, not measurements of a live browser: the issue's exact elapsed times, installed release behavior, and browser-process teardown were not re-measured here.

5. Root cause

  1. The public run schema accepts 1,000–120,000 ms and defaults to 30,000 ms.
  2. The run implementation passes that value only in the host method input. Its separate host-call options contain hostId and signal, but no timeoutMs: 
    await host.call(
  "run",
  { sessionId: input.sessionId, script: input.script, timeoutMs: input.timeoutMs },
  { hostId: record.session.hostId, signal },
);
  3. The server host-RPC implementation computes args.timeoutMs ?? COMMAND_TIMEOUT_MS and sends it to the daemon. The constant is 30,000 ms. Its separate 6,000 ms transport grace does not enlarge the daemon's work budget.
  4. The daemon deadline timer rejects unfinished work with the host-call deadline error. The run catch path then marks the session stopped. This explains the reported failure and subsequent unavailable session, without asserting an exact CLI wall time.

The options contract already supports an explicit deadline: ExperimentalHostCallOptions. No protocol extension is required. The pages and screenshot handlers reuse run with a 30-second budget, so equal script and host deadlines also create a race for those operations.

The SDK fake host currently omits timeout options from its recorded host-call envelope. This test therefore observes the actual public host client before that lossy test adapter, rather than falsely treating the adapter's missing field as production evidence.

6. Proposed fix

At the shared run implementation, set the host-call timeout to the validated script budget plus a bounded cleanup/response allowance. Preserve the existing script budget and cancellation signal; do not raise the global server default. This also covers pages and screenshots. Keep the maximum below the existing 30-minute options cap. Add coverage for the default and maximum budgets and confirm real short-timeout cancellation still works.
