#7838 · Interaction payload error classification

BugPriority: LowEffort: LowpluginsGitHub issueNovember 19, 2026 · base df9619d8e8aac4aff00c0c3ff9b8ef4e2823e4f2

Verdict: REPRODUCED · Root-cause confidence: high · Reproduction label: confirmed-repro

1. TL;DR

A plugin requesting an input form should receive the same JSON-serializability error whenever encoding its payload fails. Instead, an exception whose message includes 64 KiB escapes unchanged. The normalizer catches its own size-limit exception alongside arbitrary serializer failures, then distinguishes the two by searching the exception text. Two fresh checkouts of the trusted main commit produce identical failing assertions. This is a narrow error-reporting defect, not evidence of a process crash, payload acceptance, or a demonstrated security-boundary bypass.

Complete regression test

import { describe, expect, it } from "vitest";
import { normalizeInteractionRequest } from "./host-policy.js";

describe("interaction request payload validation", () => {
  it.each([
    "encoding failed",
    "encoding failed at 64 KiB",
    "ui.requestInput payload exceeds 64 KiB",
  ])(
    "normalizes serialization failures regardless of their message: %s",
    (message) => {
      expect(() =>
        normalizeInteractionRequest({
          threadId: "thread-test",
          rendererId: "form",
          title: "Form",
          payload: {
            get value(): string {
              throw new Error(message);
            },
          },
        }),
      ).toThrow(new Error("ui.requestInput payload must be JSON-serializable"));
    },
  );

  it("accepts exactly 64 KiB of JSON and rejects larger UTF-8 payloads", () => {
    const request = {
      threadId: "thread-test",
      rendererId: "form",
      title: "Form",
      payload: "a".repeat(65_534),
    };

    expect(normalizeInteractionRequest(request).payload).toBe(request.payload);
    expect(() =>
      normalizeInteractionRequest({
        ...request,
        payload: `${request.payload}a`,
      }),
    ).toThrow(new Error("ui.requestInput payload exceeds 64 KiB"));
    expect(() =>
      normalizeInteractionRequest({
        ...request,
        payload: "\u20ac".repeat(21_845),
      }),
    ).toThrow(new Error("ui.requestInput payload exceeds 64 KiB"));
  });
});

The controls include a nonmatching serialization error, the exact ASCII byte boundary including JSON quotes, an ASCII overflow, and a multibyte overflow. This distinguishes exception misclassification from a real byte-limit failure.

5. Root cause

The shared production request normalizer wraps serialization, byte validation, and parsing in a single try/catch. Its catch rethrows any Error whose message includes the limit string:

try {
  const json = JSON.stringify(request.payload);
  if (json === undefined) throw new Error();
  if (Buffer.byteLength(json, "utf8") > PLUGIN_INTERACTION_MAX_PAYLOAD_BYTES) {
    throw new Error("ui.requestInput payload exceeds 64 KiB");
  }
  payload = JSON.parse(json) as JsonValue;
} catch (error) {
  if (error instanceof Error && error.message.includes("64 KiB")) {
    throw error;
  }
  throw new Error("ui.requestInput payload must be JSON-serializable");
}

JSON.stringify can execute getters and custom conversion hooks. Their exceptions are indistinguishable from the normalizer's own size error under that text-based test. An error containing the substring therefore escapes even though no serialized byte count exists. The byte cap itself remains correct.

The live plugin UI request implementation and the testing host both invoke this normalizer. The existing limit is 64 × 1024 bytes. The reproduction targets the actual shared owner directly; it adds no test-only production seam.

6. Proposed fix

Catch only JSON.stringify failures and map them unconditionally to the serializability error. Reject an undefined serialization result explicitly. Run the existing byte-size check afterward, outside the catch, and parse only after the byte check passes. This removes exception-text classification without changing the public API, payload limit, protocol, or persistence.
