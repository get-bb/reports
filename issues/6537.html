1. TL;DR

The thread-history command reaches an endpoint that silently clamps requested limits to 50: two regression assertions fail on unchanged main, while the 50-entry control passes. Plugin update and install tests confirm the moved-tag refusal and source-replacement refusal; removal clears settings, but the plugin KV value survives removal and reinstall in the direct test. Task-list cursors intentionally reject continuation after a mutation. Two other claims do not reproduce at this base: fresh worktree teardown removes the attempt parent, and plugin CLI output is accepted up to 32 MiB, not 1 MiB. These findings were repeated by the same agent in a second clean checkout; the remaining visual, macOS, historical, and third-party-runtime claims are not established by these tests.

  it.each([50, 51, 200])("honors a requested limit of %i", async (limit) => {

      const { host } = seedHostSession(harness.deps);
      const { project } = seedProjectWithSource(harness.deps, {

        await readJson(globalResponse),
      );
      expect(globalHistory.entries).toHaveLength(60);
      const response = await harness.app.request(
        `/api/v1/threads/${thread.id}/prompt-history?limit=${limit}`,
      );
      expect(response.status).toBe(200);
      const history = await readJson(response);
      console.log(
        JSON.stringify({
          requested: limit,
          stored: globalHistory.entries.length,
          returned: Array.isArray(history) ? history.length : null,
        }),
      );
      expect(history).toHaveLength(Math.min(limit, 60));
    });

5. Root cause

Silent history clamp

The CLI advertises a maximum entry count and forwards it. The thread endpoint sets both default and maximum to PROMPT_HISTORY_ENTRY_LIMIT, which is 50. The common parser clamps with Math.min without returning a truncation signal. The new global history endpoint separately allows up to 1,000; the control proves the data exists and the thread route, not insertion or global retention, causes this result.

const limit = parseBoundedPositiveOptionalInteger({

Source transitions and data removal

The update resolver deliberately rejects tag movement. Independently, registration rejects a mismatched source intent. The prescribed removal path deletes schedules, settings, and secret files. Ordinary removal does not call the KV deletion used by a separate retired-builtin handover path. The KV schema has no installed-plugin cascading foreign key, agreeing with the observed retained value. Therefore the report's seat-binding loss cannot be attributed to ordinary KV deletion on current main.

Cursor consistency contract

The tasks store compares the cursor's revision with the current task-list revision and raises stale_cursor on mismatch. The existing mutation coverage verifies all four mutation types. This deliberately prevents continuing a changed ordering; live keyset pagination would need an explicitly different consistency contract.

Two claims that do not hold in the tested current paths

Plugin CLI output is now 32 MiB, with boundary tests. The constant changed in d23374da733792081ef1eb6da91f3961f4e70293 on 2026-10-26. This is not evidence of what binary the reporter actually ran. Worktree removal removes the parent only when empty; the host first removes its completion marker. The real teardown test confirms the root is empty. Leftover nonempty directories, older writers, and a lost registry record need separate experiments.

Other source-only observations: launcher tab identity lookup, params serialization, and strict acquire-control schema. They are explicitly not live reproductions.

6. Proposed fix and safety decision

Split this omnibus into independently scoped changes, preserving the reporter's numbering. First decide whether thread history should disclose the composer-sized cap or offer a separate paginated thread-filtered API; do not globally uncap shared UI history behavior. A future regression should retain the real-route test's above-50 data control. For plugin replacement, design an explicit, atomic source-transition operation that preserves settings, secrets, storage, and rollback state without silently trusting rewritten release tags. For task cursors, choose snapshot-consistent or mutation-tolerant semantics before changing the revision check.

No fix branch or PR: the verified report spans multiple subsystems and includes security checks and public API/consistency-policy decisions, failing the simple-fix guardrails. A broad PR with Fixes #6537 would also falsely imply the unverified macOS and visual reports were resolved. No production code, public schema, dependency, migration, or stored data was changed.
