#7418 · Busy accounts cannot refresh obsolete quota windows

BugPriority: LowEffort: Lowproviders Issue #74182026-11-11 · base 365d7c5237ae270be0555b5b44ea61020252713e

Verdict: REPRODUCED · Root-cause confidence: high · reproduction label: confirmed-repro

1. TL;DR

A pooled account can retain an obsolete short-term usage window while serving a long-running response. Partial response headers preserve the last short-term observation, but the hub refuses to ask the usage endpoint for authoritative data whenever that account has a request in flight. This refusal also affects an explicit CLI refresh, which reports success without updating the usage snapshot. A deterministic regression reproduced the stale window in two separate checkouts of trusted main, and a one-line removal of the busy-account guard makes the same test pass without ending the active stream.

5. Root cause

Responses may legitimately omit a window. The header merger therefore keeps the previous value instead of treating absence as evidence that a limit was removed.

  );
  const resetAt = parseReset(headers.get(`${PREFIX}${header}-reset`));

    resetAt: resetAt ?? prior?.resetAt ?? null,

}

The actual defect is refresh starvation: the busy-account guard returns before refresh deduplication, throttling, and the adapter request. Forced refresh bypasses the interval but not this guard. A continuously active account can therefore never obtain the usage snapshot needed to clear the obsolete value.

6. Proposed fix and safety

Remove only the in-flight early return in AccountPoolHub.refreshAccountUsage. Keep the existing refresh single-flight map, refresh intervals, credential refresh serialization, response-header merge semantics, and authoritative usage parser. This allows both forced and due periodic refreshes during streaming without canceling active responses or guessing what an absent header means.

The verified change is two files, 93 additions and one deletion: 94 changed text lines. It changes one existing subsystem, adds no dependency or stored-data change, and changes no public protocol, authentication contract, permission boundary, packaging, or release behavior.
