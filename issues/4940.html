#4940 · Enable lifecycle failures remain success-shaped

BugPriority: MediumEffort: Lowplugins · cliGitHub issue

2026-10-05 · trusted origin/main base f7f106dabbed96a7399b3ff428194f050b8116e8

Verdict: REPRODUCED · Root-cause confidence: high · Reproduction label: confirmed-repro

1. TL;DR

Enabling an installed plugin can finish with no running plugin while both command-line output modes still return exit code 0. The server records the loader failure correctly, but its enable endpoint returns HTTP 200 and ok: true whenever it finds the installed plugin. The CLI trusts that success field, prints the error state, and never signals failure to the shell. A real SDK enable call likewise resolves with an error-state plugin instead of rejecting. Two source checkouts at the same trusted main commit reproduced this outcome; a safe-mode-held enable remained successful, as it should.

Complete reproduction test
import { spawn } from "node:child_process";
import { mkdir, writeFile } from "node:fs/promises";
import { join } from "node:path";
import { fileURLToPath } from "node:url";
import { afterEach, beforeEach, describe, expect, it } from "vitest";
import { createBbSdk } from "@bb/sdk/core";
import { createHttpTransport } from "@bb/sdk/node";
import {
  startTestServer,
  type RunningTestServer,
} from "../../helpers/test-app.js";

const CLI_ENTRY = fileURLToPath(
  new URL("../../../../cli/dist/index.js", import.meta.url),
);
const LOAD_ERROR = "enable lifecycle fixture rejected";

describe("plugin enable outcome reproduction", () => {
  let server: RunningTestServer;
  let rootDir: string;

  beforeEach(async () => {
    server = await startTestServer();
    rootDir = join(server.config.dataDir, "fixtures", "bb-plugin-enable-check");
    await mkdir(rootDir, { recursive: true });
    await writeFile(
      join(rootDir, "package.json"),
      JSON.stringify({
        name: "bb-plugin-enable-check",
        version: "0.1.0",
        bb: {
          name: "Enable check",
          description: "Enable lifecycle outcome fixture.",
          branding: { icon: "Zap" },
          server: "./server.ts",
        },
      }),
    );
    await writeFile(join(rootDir, "server.ts"), "export default function plugin() {}\n");
    const installed = await server.pluginService.installPath(rootDir);
    expect(installed.status).toBe("running");
    await server.pluginService.setEnabled("enable-check", false);
  });

  afterEach(async () => {
    await server.close();
  });

  async function runCli(extraArgs: string[]) {
    const child = spawn(
      process.execPath,
      [CLI_ENTRY, "plugin", "enable", "enable-check", ...extraArgs],
      {
        env: {
          PATH: process.env.PATH,
          HOME: server.config.dataDir,
          BB_DATA_DIR: server.config.dataDir,
          BB_SERVER_URL: server.baseUrl,
          BB_CLI_ERROR_LOG: "0",
          NO_COLOR: "1",
        },
        stdio: ["ignore", "pipe", "pipe"],
      },
    );
    let stdout = "";
    let stderr = "";
    child.stdout.on("data", (data: Buffer) => {
      stdout += data.toString();
    });
    child.stderr.on("data", (data: Buffer) => {
      stderr += data.toString();
    });
    const exitCode = await new Promise<number | null>((resolve, reject) => {
      child.once("error", reject);
      child.once("close", resolve);
    });
    return {
      exitCode,
      stdout: stdout.replaceAll(server.config.dataDir, "<isolated-data-dir>"),
      stderr: stderr.replaceAll(server.config.dataDir, "<isolated-data-dir>"),
    };
  }

  it("reports a load failure to CLI callers instead of claiming success", async () => {
    await writeFile(
      join(rootDir, "server.ts"),
      `export default function plugin() { throw new Error(${JSON.stringify(LOAD_ERROR)}); }\n`,
    );
    const response = await fetch(`${server.baseUrl}/api/v1/plugins/enable-check/enable`, {
      method: "POST",
    });
    const api: unknown = await response.json();
    expect(api).toMatchObject({
      plugin: { enabled: true, status: "error", statusDetail: LOAD_ERROR },
    });
    await server.pluginService.setEnabled("enable-check", false);
    const human = await runCli([]);
    await server.pluginService.setEnabled("enable-check", false);
    const json = await runCli(["--json"]);
    await server.pluginService.setEnabled("enable-check", false);
    const sdk = createBbSdk({
      transport: createHttpTransport({ baseUrl: server.baseUrl, runtime: "node" }),
    });
    const enabled = await sdk.plugins.enable({ pluginId: "enable-check" });
    console.log(JSON.stringify({
      instance: { port: server.config.serverPort },
      api: { httpStatus: response.status, body: api },
      human,
      json,
      sdk: { enabled: enabled.enabled, status: enabled.status, statusDetail: enabled.statusDetail },
    }).replaceAll(server.config.dataDir, "<isolated-data-dir>"));
    expect(json.exitCode).toBe(1);
    expect(human.exitCode).toBe(1);
    expect(JSON.parse(json.stdout)).toMatchObject({ ok: false, error: LOAD_ERROR });
  });

  it("keeps a safe-mode-held enable successful", async () => {
    await server.pluginService.setSafeMode(true);
    const result = await runCli(["--json"]);
    console.log(JSON.stringify({ safeMode: result }));
    expect(result.exitCode).toBe(0);
    expect(JSON.parse(result.stdout)).toMatchObject({
      ok: true,
      plugin: { enabled: true, status: "disabled" },
    });
  });
});

5. Root cause

  1. The loader catches the factory error, disposes the failed candidate, and records status: error with the error message when no previous instance exists. The loader itself is not concealing the failure.
  2. setEnabled persists the enabled flag and awaits loadOne, then returns the installed-plugin view. A load error does not make that view absent; it appears in its status fields.
  3. The enable route only checks whether the view exists: 
    const plugin = await plugins.setEnabled(context.req.param("id"), true);
if (!plugin)
  return context.json({ ok: false, error: "unknown plugin" }, 404);
return context.json({ ok: true, plugin });
    Thus a known installed plugin with a failed load still receives the successful HTTP and JSON envelope.
  4. The CLI checks only the envelope and plugin presence. JSON output exits nonzero only for a false ok field. Human-readable output prints the returned status without converting an error status into command failure.
  5. The SDK enable method returns the parsed plugin; it has no load-outcome check. Its successful resolve was observed directly, not inferred only from source.

Crucially, safe-mode suppression records disabled, not error. A repair must distinguish a failed load from a deliberately held enabled plugin. Checking only for status !== "running" would reject the legitimate control case.

6. Proposed fix and automation safety

Make the server's enable outcome represent the completed load result: retain successful responses for an enabled plugin held by safe mode, but return an unsuccessful mutation envelope carrying the load detail when the resulting status is error. HTTP 422 is consistent with the existing reload route. Preserve the plugin view so callers can still diagnose its state. Verify unknown IDs, successful enable, safe-mode-held enable, failure details, and transport/SDK error behavior.

No pull request was opened. The root repair changes the public enable endpoint's success/error semantics and SDK-visible HTTP behavior. Public protocol changes are explicitly excluded from this autopilot's simple-fix gate, even when the source edit is small. A CLI-only normalization would leave the observed server/SDK problem in place and shift outcome policy into the client. No production code was changed, no fix branch was pushed, and no dependency or stored-data change was made.
