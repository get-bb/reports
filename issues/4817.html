#4817 · Inactive secondary-panel fallback remains mounted

BugPriority: LowEffort: Lowui2026-10-03GitHub issue

Verdict: PARTIALLY REPRODUCED · Root-cause confidence: high

1. TL;DR

The actual secondary-panel component inserts an unavailable-view diagnostic into the DOM even when closed and there is no active panel tab. Both desktop and drawer presentations fail a regression asserting that this diagnostic must be absent when closed. The same authored test fails at the same assertion in two clean checkouts of trusted main. This proves the component DOM defect, not the reported browser innerText behavior or a failure of the main plugin view. No third-party plugin code was needed or executed.

5. Root cause

The final renderPanelSurface fallback has no open-state guard. Empty active/fixed tabs reach it even when the panel is closed. The aside still mounts panelSurface and sets aria-hidden and inert, neither of which deletes descendant DOM nodes. The component already computes isLayoutOpen from the panel state and optional host suppression; other content, such as diff activity, uses that value.

... : (
  <EmptyStatePanel className="m-4 rounded-lg">
    This panel view is unavailable.
  </EmptyStatePanel>
)

The plugin right-panel host supplies the same panel component, and can supply empty tab lists. Important scope correction: LazyThreadSecondaryPanel does not initially realize a never-opened closed panel. Once realized, it deliberately retains the component after closing. The owner-level test starts at that realized component boundary; this report does not claim every fresh plugin navigation always contains the diagnostic.

6. Proposed fix

Gate only the final unavailable-view fallback on the existing effective isLayoutOpen value. Preserve retained tab/browser content and the panel shell. A genuinely open panel with no supported view must continue showing the diagnostic. This needs no product decision, public API, protocol, storage, dependency, or accessibility-boundary change.
