#7344 · Cancellation cleanup lacks adoption provenance

BugHigh priorityHigh effortworkspacesconfirmed-reproGitHub issue2026-11-10 · base 7c1353d80729983b86ea1555d18b42407f320406

Verdict: REPRODUCED · Root-cause confidence: high

1. TL;DR

A thread can take over a workspace record that already exists and is still provisioning. Cancelling that thread invokes the provider's removal callback for the old workspace and records the workspace as destroyed, even with automatic retirement disabled. The equivalent ready-workspace control is preserved. The server loses the distinction between adoption and fresh allocation when it persists ownership. This is a deterministic service-level reproduction, not evidence of production frequency or actual filesystem data loss: the removal callback is a test double and deletes nothing.

5. Root cause

  1. bindEnvironmentPath, lines 551–560 accepts existing ready or provisioning records, tombstones the reservation, and gives the existing record the new owner while retaining its status.
  2. creation adoption tracking, lines 452–506 tracks adoption only in a local variable used while applying the create result. persisted environment fields, lines 526–575 contains ownership and lifecycle fields, but no durable adopted-versus-created provenance.
  3. cancellation, lines 638–665 marks the preparation for teardown and immediately sweeps it.
  4. release and cancellation guards, lines 890–944 releases an owned cancellation only for shared records or ready records with paths. The unshared provisioning record retains ownership and is classified as cancelled. The no-retirement policy check is explicitly bypassed for cancellations.
  5. provider removal and lifecycle destruction, lines 756–799 calls the provider with the old path and instance key, then records successful teardown and destruction.
Release guard:
(shared || (row.status === "ready" && row.path !== null))

Cancellation classification:
const cancelled = row.ownerThreadId !== null && row.teardownStatus !== null;

Automatic-retirement exemption applies only when:
!cancelled && record.provider.policy.retireGraceMs === null && row.status !== "destroyed"

The dangerous distinction is ownership of a temporary preparation claim versus ownership of an underlying pre-existing resource. The stored state does not explicitly preserve that distinction for subsequent cleanup or restart recovery.

6. Proposed fix and safety gate

Persist an explicit lifecycle provenance contract so cancellation can release an adoption claim without deleting a prior resource, while still removing a newly allocated provisioning resource. Define what happens to prior provisioning metadata, retirement policy, restart recovery, attachment, and machine removal. Add paired adoption-versus-fresh-allocation cancellation tests, including a restart boundary. A durable provenance field would require a schema migration and stored-data semantics; rejecting all provisioning adoption instead would change admission policy. Neither is a safe automatic change under this rule.

No fix branch or pull request: the simple-fix gate prohibits schema/migration/stored-data changes and product-policy decisions. Extending the release predicate to every provisioning path cannot distinguish adoption from a fresh allocation that must still be cleaned up. No production code was changed or pushed.
