#6022 · MCP configuration changes stay outside resident sessions

Verdict: PARTIALLY REPRODUCED · Root-cause confidence: medium

1. TL;DR

A persistent Claude Code SDK session did not discover a newly persisted user MCP server during the observation window. A second session immediately connected to the same local server and discovered its ping tool, ruling out a broken server or configuration. Importantly, calling the SDK's existing reconnectMcpServer also loaded the new server into the original process: restarting the entire application is not a technical requirement of the provider. BB retains resident sessions, filters the native MCP command out of its catalog, and exposes no equivalent reconnect path. This verifies the configuration-refresh gap, not the OAuth claim or a complete macOS BB UI reproduction.

5. Root cause

plugins/provider-claude-code/src/bridge/sdk-session.ts:248 constructs the SDK query with user/project/local sources. This wrapper has no MCP refresh operation. The experiment shows that a fresh query loads the new config, while the existing query does not automatically refresh in the observed interval.

plugins/provider-claude-code/src/bridge/bridge.ts:1450 returns the resident session unless its stream ended or BB queued a restart. plugins/provider-claude-code/src/bridge/bridge.ts:2397 also keeps a same-provider session when construction settings match. External MCP edits do not enter that comparison.

plugins/provider-claude-code/src/bridge/provider-commands.ts:30 filters mcp through HIDDEN_COMMANDS. plugins/provider-claude-code/src/bridge/bridge.ts:2209 dispatches bridge requests without an MCP refresh action. Source inspection finds no provider caller of reconnectMcpServer or setMcpServers.

The deeper gap is a product refresh lifecycle and user trigger, not inability of the SDK to attach a newly added server. The successful live reconnect means an unconditional restart is not justified. Wholesale replacement of dynamic MCP servers could also disrupt BB's own bridge server.

6. Proposed fix and safety decision

Define a per-thread refresh action, or explicitly choose an automatic file/state observation policy. For an explicit action, expose provider reconnect through the supported control path with visible status/errors and matching UI, SDK, and CLI access. Preserve scopes, approvals, bridge tools, and in-flight turns. Test additions, reauthentication, deletion, failed reconnect, and unaffected sibling sessions.

No fix PR: the full report is only partially reproduced. A safe implementation needs a product/API contract and likely server/daemon wire work, outside the no-protocol-change, one-subsystem simple-fix gate. No production patch or fix branch was made.
