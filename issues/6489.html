#6489 · Panel visibility changes detach existing controls

Bug Priority: Medium Effort: Low ui · perf · 2026-10-28 · GitHub issue

Trusted base: 991b99020a7bf369d47a1a444e0b83af8716f4ec, fetched from origin/main.

Verdict: PARTIALLY REPRODUCED · Root-cause confidence: medium · Reproduction label: partial-repro

1. TL;DR

The desktop thread header removes its panel-toggle button when the right panel opens, and the table-of-contents component removes its rail when its measured content width drops below 896 CSS pixels. Two new component regressions demonstrate these node detachments against unchanged production code, and both fail identically in a second clean checkout of the same trusted commit. Existing tests explicitly allow the header control to disappear and therefore do not protect DOM continuity. The claim that these mutations cause page-wide Chromium :has() restyling and long animation frames remains unverified here: the required Browser Automation backend could not start because Chrome/Chromium is absent. This is a partial reproduction of the proposed trigger, not a measurement of the reported rendering stall. An existing open draft PR already closes the issue, so no competing fix was created.

5. Root cause

Verified structural cause: visibility is implemented through conditional subtree existence. In the header visibility policy, a non-compact panel with no separate panel host makes showRightPanelToggle false once open. The conditional button rendering then unmounts the existing button rather than just changing its visibility.

const showRightPanelToggle =
  secondaryPanelHost === null && (!isSecondaryPanelOpen || isCompactViewport);

{showRightPanelToggle ? (
  <Button ... />
) : null}

The TOC ResizeObserver callback converts content width to a Boolean using the fixed width/message thresholds. That Boolean controls the rail subtree. Its outer root remains, but its button and descendants do not.

setVisible(inlineSize >= TOC_MIN_VISIBLE_WIDTH_PX);

{tocVisible ? (
  <div className="relative">...rail...</div>
) : null}

Hypothesized browser consequence, not measured: structural mutations can interact with relational selectors in user/plugin stylesheets. These verified mutation sites are consistent with the proposed explanation, but do not establish how much of a particular page Chromium invalidates. The confidence is medium for the issue's full root cause; confidence in the two DOM-detachment facts is high.

6. Proposed fix

Separate mounting policy from visibility for both controls. Retain the already-created header button and TOC rail, and hide only their own elements when unavailable. Preserve keyboard/accessibility behavior, compact-header behavior, and the existing TOC outline-query gating. Avoid hiding or making the app root inert. A follow-up browser measurement must compare child-list mutations, style recalculation, and input-to-first-frame timing under the same relational CSS workload before claiming a performance fix.
