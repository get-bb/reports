#5479 · Persistent Claude discovery retains previous tool contracts

BugPriority: MediumEffort: Mediumproviderspluginsprovider-claude-codeIssue #5479

October 20, 2026 · trusted main bd93d18896bab97c950c4fa3451b621c1e0569c1

Verdict: REPRODUCED · Root-cause confidence: high at the BB/CLI boundary. Upstream cache internals are not established.

1. TL;DR

A Claude conversation can keep advertising the previous tool schema after BB stops and resumes its runtime with a replacement registration. This was reproduced on current trusted main with the real BB JSON-RPC bridge, real Agent SDK, and installed CLI 2.1.284. A deterministic local API requests a real exact-name ToolSearch on each turn; it never fabricates MCP definitions or ToolSearch results. Both searches succeed, but the resumed main model request still carries the old description and lacks the new required property. The same source, SDK, and reproduction pass when only the executable changes to the already-installed SDK CLI 2.1.245. A second clean checkout repeats both outcomes.

5. Root cause

The production server resolves current dynamic tool contributions; the daemon resumes a missing runtime with those definitions. In the Claude bridge, attachThreadSession constructs a new bb-bridge MCP server from the supplied dynamicTools. tools/list maps those current definitions, rather than loading schemas from BB storage. The resume reuse check includes construction configuration, so an explicit resume with changed dynamicTools also replaces a resident query.

Stop forgets the live runtime, but deliberately does not clear the provider conversation. SdkSession uses persistSession: true and resume: the same provider ID. With CLI 2.1.284, the resumed model-facing deferred catalogue retains the discovered generation-1 entry even after another successful exact-name search. Swapping only the executable to the already-installed SDK CLI 2.1.245 makes the same script pass. This localizes the failure to version-dependent Claude CLI session/discovery behavior; it does not identify a particular private cache implementation.

6. Proposed fix and simple-fix gate

Validate an upstream discovery-catalogue invalidation or refresh that preserves the provider conversation, then rerun this real-CLI regression across affected and control versions. Rebuilding BB's MCP object already happens and is insufficient. Automatically clearing the conversation would lose context; versioning public tool names or changing CLI selection globally requires a product/compatibility decision. There is no verified safe context-preserving production patch confined to the existing implementation, so no fix branch is pushed and no PR is opened. No open PR referencing this issue was found in the final metadata check.
