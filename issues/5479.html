#5479 · Resumed Claude CLI sessions retain stale deferred tool contracts

BugPriority: MediumEffort: Mediumproviderspluginsprovider-claude-codeIssue #5479

October 14, 2026 · trusted main a7d5dfcc8c27df1fea42847526ee62a338fe8052

Verdict: REPRODUCED · Root-cause confidence: high at the provider/CLI boundary. The upstream cache implementation itself was not inspected.

1. TL;DR

A stopped BB Claude provider session can resume with its original model-facing tool description and schema even after BB constructs a bridge with a replacement definition. A deterministic local probe drives the real BB JSON-RPC bridge, real Agent SDK, and installed Claude CLI; its simulated API chooses which tool to call, not the tool definitions or search results. On CLI 2.1.284, a fresh exact-name ToolSearch succeeds, but subsequent main model requests still contain generation 1 instead of generation 2. The same probe passes with the already-installed SDK-bundled CLI 2.1.245, with BB source and SDK unchanged. Both outcomes repeat in a second clean checkout; no account, paid model request, or live BB instance is used.

5. Root cause

Confirmed boundary: the model-facing deferred tool catalog restored by the BB-configured Claude CLI 2.1.284 session remains stale across identity-preserving resume. BB supplies generation 2 and the CLI emits it in an auxiliary request while its main requests retain generation 1. Exact-name ToolSearch returns references into that stale main catalog; searching again does not invalidate its schema.

  1. The server resolves current selected plugin contributions in thread-runtime-config.ts:213–218 and includes tools in resume context in thread-commands.ts:328–350. These are static evidence, not executed by this probe.
  2. The bridge reconstructs MCP from supplied dynamicTools and restarts with the preserved identity: bridge.ts:2221–2252. It already compares construction-scoped configuration, including tools: bridge.ts:2285–2333.
  3. The MCP handler serves supplied descriptions/schemas verbatim: tool-proxy-mcp.ts:27–41.
  4. The SDK passes the current MCP server while persisting/resuming Claude identity: sdk-session.ts:262–298.
  5. The provider prefers an explicit or PATH-discovered executable: session-options.ts:208–239. Changing only this executable to existing 2.1.245 makes both checkouts pass.

The version-specific behavior is established by execution, not an invented upstream cache variable. Its introducing upstream commit is unknown. Existing bridge tests mock the SDK (bridge.test.ts:24–38) and cannot demonstrate real CLI restoration.

6. Proposed fix and simple-fix decision

The affected CLI needs a supported way to replace restored model-facing definitions while retaining conversation history. A narrow experiment reconnected the SDK MCP server on resume before yielding input; the real probe still returned generation 1. That experiment was completely reverted.

No safe product PR: no local repair has a passing regression. Silently changing/clearing provider identity loses context; renaming tool/server identifiers affects contracts and permissions; forcing a provider version changes packaging/release policy. These violate the simple-fix gate. Next, provide this executable/version comparison upstream and validate a supported catalog invalidation or upstream repair against the probe. The 2.1.245 run is a laboratory control, not a production downgrade recommendation.

No open linked PR was found through issue metadata or an open-PR search for this number. No source branch was pushed; no product PR opened; production source is unchanged.
