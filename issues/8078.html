#8078 · ACP local image reads lose their image classification

BugPriority: MediumEffort: Lowproviders · provider-acpIssue2026-11-24 · base 48f57bc89633f1f7cb2c679922195cc2f25e4b0b

Verdict: REPRODUCED · Root-cause confidence: high

1. TL;DR

ACP read notifications for local image paths are translated into ordinary file-read items. The app deliberately has no expandable body for that kind of item, whereas its existing image-view body supports previews. A regression test at the translator-to-assembler boundary reproduces the wrong kind and presentation for six image formats/path sources without any image output blocks. The same agent repeated the failure in a second clean checkout of the exact trusted main commit. This is a data-boundary reproduction; it does not claim a live Antigravity or browser reproduction.

2. Claims vs findings

5. Root cause

The read dispatch always calls fileReadItem, whose return value is unconditional:

item: { type: "fileRead", path },
presentation: fileReadPresentation(path),

There is no image-path branch. The shared path resolver also preserves tilde-prefixed strings, and the title fallback does not pass through cwd resolution. Finally, TimelineRowDetails explicitly renders the image preview for image-view and nothing for file-read. Therefore the wrong emitted kind prevents the existing image UI from being selected.

6. Proposed fix

In ACP read classification only, extract the candidate path before resolving it. Preserve URI/network-address candidates as ordinary reads; expand the current-user home prefix and resolve relative local paths against the session cwd. Recognize supported image extensions only on absolute local paths, emitting the already-supported imageView shape and image presentation. Keep other reads unchanged. Do not change host permission/path primitives, protocol fields or UI. The regression test must then pass through the full item lifecycle without duplicate completion.
