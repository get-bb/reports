1. TL;DR

The reported surviving Claude runtime and duplicate actions were not reproduced on the trusted main commit below. The actual agent-runtime reaper was exercised with real bridge-worker processes using the repository's scripted provider fixture; three completed-turn, reap, and resume cycles left each old worker dead before the next worker started. Separately, the actual Claude bridge's stop/drain and replacement-serialization tests passed with a controlled SDK boundary. Both checks were repeated by the same agent in a second clean checkout, without a workflow or another agent. These Linux fixture results do not establish that the reported macOS/real-Claude behavior is absent; its root cause remains unknown.

5. Root cause assessment

Not established; root-cause confidence: low. No failing lifecycle assertion supports a production fix. The current source already awaits the relevant shutdown path:

  1. The reaper awaits stopThread and excludes failed releases from its success list.
  2. stopThread awaits the bridge response, forgets the attachment, and releases an idle provider process.
  3. A bridge is shut down only when its attachment set becomes empty. A shared bridge can intentionally survive another thread's release; bridge survival by itself is not sufficient evidence of a leak. This does not explain the reported duplicated actions.
  4. Provider shutdown awaits process termination and finalization; unverified descendant cleanup produces a diagnostic.
  5. The Claude stop handler awaits closeThreadSession before replying; SDK shutdown interrupts and drains, with abort/close fallback on timeout.
