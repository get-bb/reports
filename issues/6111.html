5. Root cause analysis

No root cause of the reported incident is established. The tested implementation separates custom sections from project and machine-derived groups. A thread's original section is not an immutable assignment.

  1. Foreign-project destination guard: a drop onto another project's group returns no decision when dragged threads do not belong to that project.
  2. Collision filtering also removes those foreign-project destinations before an affordance is offered. Existing tests explicitly require no SDK call for those drops. This restriction could match the report if its groups were projects; their type is unknown.
  3. Custom-section moves instead generate an update whenever the destination section differs: 
    if (sectionId !== undefined && (detach || thread.sectionId !== sectionId)) {
  return [
    detach
      ? { threadId: thread.id, parentThreadId: null, sectionId }
      : { threadId: thread.id, sectionId },
  ];
}
  4. The hook commits updates through sdk.threads.update. The public update route validates the destination and puts its section ID into the metadata update. The live persistence checks confirm this is not an accepted-but-ignored field.

6. Proposed next step

Do not remove the project guard or change persisted ownership based on this report. First establish the organization mode, whether the target is a custom section, project, machine, or worktree group, and whether the gesture lands on a header or a thread row. A macOS screen recording plus those group types would distinguish an unsupported cross-project move from a custom-section pointer bug. For custom sections, the next experiment is a real pointer drag on a fresh macOS instance while recording the outgoing update and reloaded sidebar. Only a failing supported-path reproduction should drive a regression test and fix.

No pull request was opened: there is no failing reproduction on trusted main, and changing project ownership would require a product/contract decision rather than a simple local fix.
