#4990 · Async choice metadata is lost during provider translation

Bug Priority: Medium Effort: Medium providers provider-codex · GitHub issue

PARTIALLY REPRODUCED · Root-cause confidence: medium overall; high for the adapter's metadata loss

1. TL;DR

The Codex adapter turns an asynchronous assistant-message item into an ordinary text-only message. A locally authored fixture containing choice metadata loses both choices at the real provider translation boundary, identically in two clean trusted checkouts. Existing synchronous question RPCs already work, including the nonblocking flag exercised by the repository's bridge tests; that flag is not the same transport as an async assistant message. This verifies a concrete adapter gap, but does not verify the wire payload produced by Codex 0.160.1 or the reported desktop appearance. No production patch or pull request was created: durable asynchronous answering requires shared interaction/lifecycle behavior, not merely another synchronous RPC name.

5. Root cause

The incoming agent-message schema accepts unknown extra metadata via passthrough, so this is not rejection by the parser. The translation switch then rebuilds the shape and drops everything except the message text:

case "agentMessage":
  return {
    kind: "translated",
    shape: { type: "agentMessage", text: parsedItem.text },
    presentation: AGENT_MESSAGE_PRESENTATION,
    status: "completed",
    approvalDenied: false,
  };

The shared delta contract likewise represents agentMessage as type plus text. Adding metadata to that shared contract would be a public schema/protocol change, which the simple-fix rule forbids.

By contrast, item/tool/requestUserInput is an inbound request with a question payload, turn ID, and live request ID. Its bridge response path resolves the original provider RPC. An async message notification has no such waiting responder. A question card needs a persisted interaction and an answer delivery policy that can resume an idle thread or steer an active one, with cancellation and stale-answer handling.

Confidence boundary: metadata loss for the authored input is proven. Whether Codex 0.160.1 produces this exact questions field is not proven; the committed generated ThreadItem type declares delivery="async" but not a questions field. That limits the overall verdict to PARTIALLY REPRODUCED.

6. Proposed fix and simple-fix decision

First capture a real async tool exchange from the reported provider version in a clean isolated instance and validate its metadata schema. Then add a provider-neutral durable async question lifecycle, define active/idle answer delivery, preserve stable native IDs across replay, and handle stop/cancellation/stale answers through the existing CLI/SDK interaction endpoints. The implementation must preserve daemon compatibility or bump the host protocol when its wire contract changes.

No safe simple PR: a provider-only renderer change cannot establish the missing answer path. A complete repair needs a shared interaction contract and server/runtime lifecycle work, spanning subsystems and potentially public protocol/schema behavior. Those violate the automation's simple-fix conditions. No production patch was attempted, committed, or pushed. The failing regression is published only as a report artifact.
