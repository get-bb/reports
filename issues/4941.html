#4941 · RPC handlers cannot observe caller departure

BugPriority: MediumEffort: HighpluginsGitHub issueOctober 5, 2026

Trusted origin/main base: f7f106dabbed96a7399b3ff428194f050b8116e8

Verdict: REPRODUCED · Root-cause confidence: high · Reproduction label: confirmed-repro

1. TL;DR

A plugin calling another plugin gets a timeout after approximately 75 seconds, but the receiving handler remains alive. The handler receives caller identity without any cancellation signal, so even a cooperative implementation cannot learn that the caller has stopped waiting. In two clean checkouts, an actual plugin-to-plugin HTTP call timed out and a gated handler subsequently persisted a row in its own SQLite storage. Explicit caller cancellation produced the same server-side behavior. The timeout itself is deliberate; the defect is the missing handler-side lifetime notification, not the presence of a deadline.

5. Root cause

The injected SDK times out its fetch, but the RPC route does not forward request cancellation and the handler context exposes only caller identity. Caller cancellation affects only the fetch promise; it does not stop JavaScript already executing in the receiving handler. The route awaits the service invocation without reading context.req.raw.signal. The service creates a context containing only experimental_caller, exactly matching the public handler-context type. The runtime wrapper awaits the handler without imposing a handler deadline; after successful completion it records success even if the HTTP caller has already disconnected.

The normal Node SDK supports transport-wide timeout configuration, but the SDK injected into plugins uses a fixed wrapper with the default timeout. PluginRpcArgs exposes a signal, not a per-call timeout. Signals and deadlines are composed, not alternatives. These are separate policy choices from the verified missing lifetime notification.

6. Proposed fix and safety gate

Design and document cooperative request-lifetime cancellation for the public RPC handler context, propagate the HTTP request signal through the service, and retain the existing caller-identity validation. Verify transport disconnect notification and both reproduced scenarios. Cancellation must be cooperative: it cannot undo completed effects, and merely rejecting an outer promise is not cancellation of a running handler.

Decide separately whether callers need a configurable per-call deadline; do not silently reinterpret an existing caller signal as an unlimited timeout. Document the default deadline and the recommended job/status pattern for long-running work.

No automated fix PR: repairing this at the root requires a public Plugin SDK contract change and lifetime/timeout policy decisions. The new-issue-autopilot simple-fix gate expressly excludes public protocol/schema changes and product/architecture decisions. No production patch or fix branch was created or pushed. The pre-fix regression is retained as a report artifact for a deliberately designed change.
