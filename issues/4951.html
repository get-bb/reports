#4951 · New-thread command panel routing

Verdict: REPRODUCED · Root-cause confidence: high · reproduction label: confirmed-repro

1. TL;DR

A plugin command cannot open its panel while the New thread screen is focused. The screen already supports plugin panel tabs through its launcher, but does not publish the opener that commands use. Rendering the actual New thread view and invoking the production palette-command builder returns false instead of accepting the panel. A focused behavioral regression fails with the same refusal in two separate checkouts of trusted main. The fix should publish this screen's existing panel-opening capability only while its pane is focused.

5. Root cause

  1. CommandPalette reads the active panel opener for both keyboard handlers and palette entries.
  2. The plugin command context declines immediately when that opener is null. This is the warning observed in both tests.
  3. The registry hook registers focused panes in an effect and removes their opener when inactive or unmounted.
  4. ThreadDetailView publishes an opener; RootComposeView already owns openPluginPanel and the new-thread action registrations, but does not publish an opener anywhere on the base commit.
  5. New-thread launcher execution uses the existing shared panel-action opener, including JSON validation and default title handling. The tab owner preserves deduplication and activation.

The missing publication explains why a valid action id and available New thread panel never reach the existing tab-opening code. The registry is intentionally focus-scoped; registering an unfocused screen would route commands to the wrong pane, so the fix must preserve that invariant.

6. Proposed fix

Publish a focus-scoped RootComposeView handler in the existing registry. Resolve the action within the calling plugin's newThreadPanelActions registrations, reuse the launcher's existing createPanelActionOpenPanel helper for JSON validation and title handling, then open the compact drawer only after acceptance. Keep the existing tab owner for persistence, activation, and deduplication. Do not invoke an action's launcher run callback for a targeted command open. Document that command action ids select threadPanelAction on thread screens and experimental_newThreadPanelAction on New thread screens; no SDK signature or wire field needs changing.
