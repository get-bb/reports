#7830 · Native browser close-command interception

BugPriority: MediumEffort: Lowdesktopconfirmed-repro Issue · November 19, 2026 · base df9619d8e8aac4aff00c0c3ff9b8ef4e2823e4f2

Verdict: REPRODUCED at the production shortcut-routing boundary. Root-cause confidence: high for the missing interception. The final macOS native window-close outcome was not exercised on this Linux host.

1. TL;DR

The desktop app embeds web pages in a separate native browser view. When that view owns keyboard focus, app shortcuts must be forwarded to the host renderer rather than reaching native menu handling. The production resolver rejects the default close-panel binding because it has no browser-focus condition and is absent from the resolver's explicit exception list. A focused test reproduced this missing dispatch twice on unchanged trusted main, in separate clean checkouts. The narrow repair admits the existing close-panel command; it does not alter menu policy, keybinding conditions, or any public interface.

Evidence boundary: these runs prove that Command+W returns null instead of panel.close at the real resolver. They do not prove that every macOS menu path always closes the whole window. No screenshot or live macOS result is claimed.

Complete reproduction test

import { describe, expect, it } from "vitest";
import type { AppKeybindings } from "@bb/domain";
import { resolveDesktopBrowserAppCommand } from "../src/desktop-browser-shortcuts.js";

describe("native browser close shortcut routing", () => {
  const closeBinding: AppKeybindings[number] = {
    command: "panel.close",
    desktopOnly: false,
    shortcut: {
      key: "w",
      mod: true,
      meta: false,
      control: false,
      alt: false,
      shift: false,
    },
    when: { all: ["mainSurface"], none: ["modalOpen"] },
  };
  const input = {
    key: "w",
    code: "KeyW",
    metaKey: true,
    ctrlKey: false,
    altKey: false,
    shiftKey: false,
  };

  it("dispatches the close-panel command for macOS Command+W", () => {
    expect(
      resolveDesktopBrowserAppCommand({
        input,
        platform: "darwin",
        keybindings: [closeBinding],
      }),
    ).toBe("panel.close");
  });

  it("does not dispatch a command for an unrelated shortcut", () => {
    expect(
      resolveDesktopBrowserAppCommand({
        input: { ...input, key: "q", code: "KeyQ" },
        platform: "darwin",
        keybindings: [closeBinding],
      }),
    ).toBeNull();
  });

  it("routes an existing browser-scoped command", () => {
    expect(
      resolveDesktopBrowserAppCommand({
        input: { ...input, key: "l", code: "KeyL" },
        platform: "darwin",
        keybindings: [
          {
            ...closeBinding,
            command: "browser.focusLocation",
            shortcut: { ...closeBinding.shortcut, key: "l" },
            when: { all: ["mainSurface", "browserFocus"], none: [] },
          },
        ],
      }),
    ).toBe("browser.focusLocation");
  });
});

This is a keyboard-routing defect, not a rendering defect. No simulated image is used. Reproduction source and output are inline because this reports repository forbids committed test files and raw log artifacts.

5. Root cause

Server binding context and default panel bindings define close-panel as a main-surface shortcut, not a browser-only action:

const mainWithoutModal = {
  all: ["mainSurface"],
  none: ["modalOpen"],
};
binding("panel.close", "w", { mod: true }, mainWithoutModal)

The native-browser resolver eligibility filter skips bindings lacking browserFocus unless they belong to its explicit navigation exceptions. Close-panel is not an exception. Consequently it never reaches shortcut matching, including when rebound.

The native before-input-event handler then takes this branch:

if (command === null) return;
event.preventDefault();
...
args.dispatchAppCommand({ command, hostWebContentsId: hostWindow.webContents.id });

Returning null therefore leaves the keystroke unconsumed and prevents app-command dispatch. The native close menu item and its main-process close handler are the fallback path. Renderer close requests have a window-close timeout; an unhandled renderer response also closes the window. These are verified source paths, not proof of which native branch the reporter reached.

The renderer's existing close-panel and close-window handling already owns tab selection and closure. The fix must reuse that path rather than add a second native tab-closing implementation.

6. Proposed fix and regression proof

Admit panel.close beside the existing panel-navigation exceptions in the native-browser resolver. Leave the shortcut, context, renderer command handling, and native close-window fallback unchanged. Do not broaden this fix to other panel commands without their own evidence.

The candidate patch changes 26 text lines across two files: one production addition and 25 test additions. It extends the existing rebound-command table and adds the default Command+W regression in the established resolver test file. No dependencies, generated files, protocols, persistence, packaging, permissions, or public API are changed.
