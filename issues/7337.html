#7337 · Reconnect retries storage deletion after cleanup has completed

BugHigh priorityLow efforthost · threads · perfGitHub issue2026-11-10 · base 7c1353d80729983b86ea1555d18b42407f320406

Verdict: REPRODUCED · Root-cause confidence: high for redundant reconnect commands. The reported macOS process counts and outage duration were not measured here.

1. TL;DR

Deleting a thread removes its host storage before a budgeted database purge removes the thread row. Reconnecting a host incorrectly treats those retained rows as unfinished storage cleanup, even when the database already records successful removal. A regression test using the real server reconciliation path and migrated SQLite database emits two deletion requests when only one thread still needs cleanup. The same result occurs for all five eligible lifecycle states in two clean trusted checkouts. The daemon-side process-scanning path explains the amplification risk, but this Linux investigation does not establish the reported macOS outage duration.

Complete regression test

import {
  getThread,
  markThreadDeleted,
  markThreadStorageDeleted,
  requestThreadPurge,
} from "@bb/db";
import { expect, it } from "vitest";
import { reconcileDaemonReportedThreads } from "../../src/services/threads/thread-lifecycle.js";
import {
  listQueuedCommands,
  reportQueuedCommandSuccess,
  waitForQueuedCommand,
} from "../helpers/commands.js";
import {
  seedEnvironment,
  seedHostSession,
  seedProjectWithSource,
  seedThread,
} from "../helpers/seed.js";
import { withTestHarness } from "../helpers/test-app.js";

it.each(["idle", "error", "active", "starting", "stopping"] as const)(
  "does not repeat completed storage deletion on reconnect for %s threads",
  async (status) => {
    await withTestHarness(async (harness) => {
      const { host } = seedHostSession(harness.deps);
      const { project } = seedProjectWithSource(harness.deps, {
        hostId: host.id,
      });
      const environment = seedEnvironment(harness.deps, {
        hostId: host.id,
        projectId: project.id,
      });
      const completed = seedThread(harness.deps, {
        projectId: project.id,
        environmentId: environment.id,
        status,
      });
      const pending = seedThread(harness.deps, {
        projectId: project.id,
        environmentId: environment.id,
        status: "idle",
      });
      for (const thread of [completed, pending]) {
        markThreadDeleted(harness.db, harness.deps.hub, {
          threadId: thread.id,
        });
      }
      markThreadStorageDeleted(harness.db, { threadId: completed.id });
      if (status === "idle" || status === "error") {
        requestThreadPurge(harness.db, {
          now: Date.now(),
          threadId: completed.id,
        });
      }

      await reconcileDaemonReportedThreads(harness.deps, {
        hostId: host.id,
        activeThreadIds: [],
        undeliveredEventThreadIds: [],
        sameDaemonInstance: false,
      });
      const retry = await waitForQueuedCommand(
        harness,
        ({ command }) =>
          command.type === "thread.storage.delete" &&
          command.threadId === pending.id,
      );
      const commands = listQueuedCommands(harness, "thread.storage.delete");
      await reportQueuedCommandSuccess(harness, retry, {
        providerCheckpointId: null,
      });
      expect(commands).toEqual([
        expect.objectContaining({ threadId: pending.id }),
      ]);
      expect(getThread(harness.db, completed.id)?.storageDeletedAt).not.toBeNull();
    });
  },
);

5. Root cause

Host session attachment invokes reconciliation with the reported active thread IDs. Reconciliation selects retained deleted rows across active, idle, error, starting and stopping states, but neither selects nor checks their storage-deletion timestamp. It then requests host cleanup for every deleted row.

for (const thread of pendingThreads) {
  if (thread.deletedAt !== null) {
    requestThreadStorageDeletion(deps, thread, {
      hostId: args.hostId,
      id: thread.environmentId,
    });
    continue;
  }
}

The in-flight guard deduplicates only the same thread; it does not cap concurrent cleanup across distinct threads. The periodic finalization sweep already checks storageDeletedAt and finalizes completed cleanup instead of asking the host to repeat it. Purge-queued rows are excluded from that sweep but remain eligible for reconnect reconciliation.

The daemon deletion handler scans process working directories before removing storage. The Unix lsof scanner spawns a machine-wide lookup, and Every list call chooses a fresh platform lookup before filtering directories. The kill loop can repeat the lookup up to five rounds. This makes redundant reconnect commands unnecessary host work, even if storage is already absent. No shared scan promise exists in this code.

6. Proposed fix

Select storageDeletedAt in reconnect reconciliation. For a deleted thread with completed cleanup, call the existing stopped-thread finalizer and continue; otherwise preserve the existing storage-delete retry. This removes the verified root cause while recovering finalization without a new protocol, stored-data format, or daemon policy. Keep the regression as a server lifecycle test.

Cross-thread RPC throttling and shared platform scans would be separate hardening work. They are not required for the small reconnect fix, and this report does not claim to verify or ship them.
