#6802 · Plugin update checks lack per-plugin failure isolation

BugMedium priorityLow effortplugins · cli GitHub issue2026-11-02 · base 916d684ac23d0b0de82c09cfc7553a50287d2188

Verdict: REPRODUCED · Root-cause confidence: high

1. TL;DR

An installed plugin whose Git source disappears makes the shared update-check API return HTTP 422 without a results array, even with a healthy installed plugin. This is not an installation failure: both plugins install successfully before one source directory is moved away. A real Git process rejects the source lookup, and the update worker lets that rejection escape its shared Promise.all. Branch selectors and semantic-version ranges both reproduce the failure. The same agent repeated the test in a second clean checkout before testing a small per-plugin isolation repair.

5. Root cause

runInstallCommand rejects nonzero process exits, retaining the stderr tail:

      if (code === 0) {
        resolve();
        return;
      }
      const tail = stderr.trim().slice(-1000);
      reject(
        new Error(
          `${command} ${args[0]} failed (exit ${code ?? "signal"})${tail ? `: ${tail}` : ""}`,
        ),
      );
    });

The Git ref lookup and semver tag listing await that command without converting failures to an unavailable resolution. The service checkRows worker awaits resolution before persistence with no per-row error conversion:

          const resolution = await resolveUpdateForRow({
            row: current,
            npmRun: npmRunForRow(current),
          });
          const checked = checkEntryFromResolution(
            current.id,
            installedUpdateVersion(current),
            resolution,
          );
          persistUpdateEntry(checked);
          return checked;

Any rejection escapes the lifecycle lock and rejects the Promise.all sweep. The HTTP route catches that aggregate failure and sends 422, not partial results. A successful sibling can still have its state persisted; Promise.all does not cancel its work.

Other callers: CLI outdated calls SDK checkUpdates; Settings Updates uses the update-check query; periodic checker calls the same service and logs a sweep failure. These are source-level implications, not separately observed live CLI/UI runs.

History inspection attributes the unguarded worker resolution to ba2e359bc2a; the recorded main still contains it. No linked open pull request was found in the issue timeline or the open-PR search at investigation time.

6. Proposed fix

Catch only the per-row resolveUpdateForRow call in checkRows. Convert the thrown value to the existing unavailable resolution with its message, then pass it through the normal check-entry conversion and persistence path. Leave lifecycle/database failure handling outside that catch and leave actual update execution unchanged. No public contract, protocol or stored-data shape changes are needed.

The local candidate changes two files, 55 total added/deleted text lines (16 production and 39 tests). The regression is table-driven over branch and semver selectors, checks the shared route, persisted results and recovery after the source returns. Both cases pass with the candidate repair.
