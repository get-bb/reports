#8206 · Unread attention lost during sidebar activity

BugPriority: MediumEffort: MediumuiIssueNovember 26, 2026 · base 6bd871bad87ec407154e3058c1a0df0f570c8ffc

Verdict: REPRODUCED · Root-cause confidence: high · reproduction label: confirmed-repro

1. TL;DR

An unread reply on a root thread can become visually indistinguishable from a read thread while activity is displayed. The actual resolver and actual glyph component render byte-identical markup for read and unread roots when their own runtime, a collapsed child's runtime, or a plugin running status takes the slot. An idle control changes from no glyph to the unread dot, so the fixture is sensitive to unread state. The title supplies no independent unread styling. This is established presentation policy, also asserted by existing tests; choosing how to change it requires a product decision rather than a safe precedence-only patch.

5. Root cause

  1. The attention guard counts unread only for completed root threads. This explains why an unread child alone produces no attention cue.
  2. The single-indicator priority function returns runtime before unread-success. Collapsed child activity and root unread attention therefore resolve to runtime, losing unread information from both the indicator and accessible label.
  3. The plugin override set protects runtime, unread-error and waiting-for-input, not unread-success. The renderer returns the plugin glyph early, so even a resolver result containing unread-success displays the plugin glyph instead.
  4. The runtime glyph receives only a fixed working color class. Its props have no separate unread state. The shared working color is muted, while plugin-running uses its own fixed success tone. Neither varies with read state.
  5. ThreadRow folds hidden activity through that resolver; its title wrapper and the shared title component add no unread-dependent typography.

The deeper issue is that activity and unread attention are independent state dimensions, but the row presentation compresses them into a single priority winner. This is not evidence of a pi-provider, Connect, or server timestamp failure.

Existing contract evidence: runtime over unread success; collapsed parents intentionally ignore child unread attention; the public result contract documents plugin override priority.

6. Proposed fix and safety decision

Agree a separate unread-attention signal alongside activity rather than swapping the existing priority order. Decide root-versus-child attention semantics first, then share the signal across the SDK resolver, glyph renderer, and thread-list title, preserving error/input precedence and one-glyph layout.

No fix PR was opened. Changing only the priority would replace the spinner and conceal work rather than show both dimensions. A complete repair needs an agreed activity-plus-attention presentation and a decision about the existing root-only child policy, spanning the shared SDK contract, app glyph renderer and thread-list UI. This fails the rule's no-product-decision and one-existing-subsystem conditions. Production code is unchanged; there is no stopped fix branch or pushed partial fix.
