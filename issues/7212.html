#7212 · Injected Claude skills depend on privileged directory symlinks

BugHigh priorityLow effortprovidersprovider-claude-codeIssueNovember 7, 2026 · base 3a2be262104da791f9112decc518582889410bc7

PARTIALLY REPRODUCED · Root-cause confidence: high for the code path; native Windows occurrence unverified.

1. TL;DR

The Claude provider turns injected skill folders into local plugins by creating directory symlinks. Both the plugin-root link and the links used after duplicate-skill filtering request the directory-symlink type without a fallback. On the trusted main commit, injecting an EPERM at that filesystem boundary makes both skill-delivery tests fail, while the same tests pass with real Linux symlinks. Plugin assembly catches this failure and drops the root; partial duplicate filtering instead rejects before assembly can catch it. This report does not claim a native Windows reproduction, an actual Claude session failure, or verified absence of user-visible logs.

5. Root cause

The first link is created after the manifest, with no alternative link type or copy fallback. Throwing here leaves ensureClaudeSkillPlugin without a usable return value. Its caller catches the error and leaves the root out of the assembled list.

plugins/provider-claude-code/src/bridge/bridge.ts:394

function assembleSkillPlugins(
  roots: readonly { id: string; path: string }[],
): ClaudeCodeSkillRoot[] {
  const takenNames = new Map<string, string>();
  const assembled: ClaudeCodeSkillRoot[] = [];
  for (const root of roots) {
    try {
      assembled.push({
        id: root.id,
        localPluginPath: ensureClaudeSkillPlugin({
          pluginsRoot: requireSkillPluginsRoot(),
          root: { id: root.id, path: root.path },
          takenNames,
        }),
      });
    } catch (error) {
      process.stderr.write(
        `claude bridge: skipping injected skill root "${root.id}": could not assemble its plugin: ${error instanceof Error ? error.message : String(error)}\n`,
      );
    }
  }
  return assembled;

The second link path is reached only when filtering retains some but not all scanned skills. This distinction matters: a root containing only an identical native skill is entirely omitted without making a link. Our reproduction supplies one identical skill and one distinct retained skill. Only EEXIST is tolerated at this link call, so EPERM propagates.

plugins/provider-claude-code/src/bridge/skill-plugins.ts:145

  for (const root of args.roots) {
    const files = await scanSkillFiles({
      path: root.path,
      shape: "skill",
      boundaryPath: null,
    });
    const retained = files.filter((file) => {
      if (seen.has(identity(file))) return false;
      seen.add(identity(file));
      return true;
    });
    if (retained.length === 0) continue;
    if (retained.length === files.length) {
      filtered.push(root);
      continue;
    }
    const hash = createHash("sha256")
      .update(
        JSON.stringify(
          retained.map((file) => [
            file.name,
            file.realPath,
            file.contentSha256,
          ]),
        ),
      )
      .digest("hex");
    const filteredPath = join(args.pluginsRoot, "filtered", hash);
    mkdirSync(filteredPath, { recursive: true });
    for (const file of retained) {
      const linkPath = join(filteredPath, file.name);
      try {
        symlinkSync(dirname(file.realPath), linkPath, "dir");
      } catch (error) {
        if (
          !(
            error instanceof Error &&
            "code" in error &&
            error.code === "EEXIST"
          )
        )
          throw error;
      }
    }
    filtered.push({ id: root.id, path: filteredPath });
  }
  return filtered;
}

6. Proposed fix and safe-fix decision

A contained candidate is to select an unprivileged directory-link strategy on Windows at both production call sites while preserving ordinary symlinks elsewhere. Validate absolute target handling and existing-link comparisons on Windows, including junction readlink normalization and repeated setup. Do not infer that a successful Linux junction argument proves Windows junction semantics.
