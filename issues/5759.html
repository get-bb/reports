Verdict: REPRODUCED · Root-cause confidence: high

1. TL;DR

Host terminal listing and default-title generation during host terminal creation read terminal history across all hosts before filtering in JavaScript. Both real server routes generate a SQLite plan containing SCAN terminal_sessions, even though a suitable host-and-status index exists. This makes work depend on retained history rather than just the requested host's visible sessions. The same two regression cases fail in a second clean trusted checkout. The query-plan defect is confirmed; the reported production freeze frequency and CLI timings were not measured or independently established.

5. Root cause

Host terminal listing invokes the database list with the all scope, then filters host, thread, environment, and optional cwd after materialization. Host creation and existing-session counting does the same before allocating the default title. Thus every host-path creation pays for that query, even when a title is explicitly supplied.

Scope construction intentionally contributes no host predicate for all, whereas host adds host_id equality. The list implementation adds only visible statuses, sorts by creation time and ID, and synchronously materializes the results. Existing terminal indexes includes the composite host/status index but no status-leading index. The observed plan scans the table and uses a temporary sort tree. Filtering after the synchronous query cannot reduce the rows SQLite must inspect or the cross-host rows materialized.

Before: all scope + visible statuses → SCAN terminal_sessions
After: host scope + visible statuses → host-constrained index lookup
Unchanged: thread/environment/cwd filtering, visibility, order, result mapping, numbering

6. Proposed fix and validation

Use the existing host scope at the two host-specific call sites, with the already validated or supplied target host identifier. Preserve the remaining JavaScript predicates. This uses the existing index without a migration, new index, dependency, protocol change, or terminal-retention decision. Counting still materializes matching visible sessions, so a future count-only optimization is separate work; it is not necessary to remove these full-history scans.

The local fix is two production-line replacements and one table-driven regression addition in the same terminal subsystem: 87 changed text lines across two files (85 additions, 2 deletions). Both focused cases fail before the fix and pass after it. After the fix, the public terminal and flow-control suites pass all 50 tests, the terminal database suite passes all 8 tests, and the server typecheck completes with 5/5 Turbo tasks successful. Git diff whitespace validation passes. No public contract changes.
