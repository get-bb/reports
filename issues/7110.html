#7110 · ACP title input ordering and regeneration diagnostics

BugPriority: MediumEffort: Mediumthreads · provider-acp · partial-reproGitHub issue2026-11-05 · base fa30b0a7dcdf745f7baf8e41721f754b7d3198fe

PARTIALLY REPRODUCED · Root-cause confidence: medium

1. TL;DR

There are two distinct title paths: an ACP agent can supply its own session title, while manual regeneration uses bb's separately selected AI service. A real bridge subprocess test confirms that bb puts system instructions before the user's first message in the ACP prompt; a translation test confirms that an instruction-shaped provider title is forwarded unchanged. A server test then supplies that synthetic title and confirms that regeneration fails when the configured AI service is not ready, while leaving the actual stored title untouched. The text after the error's final colon is the AI service diagnostic, not a different stored title. The actual external ACP provider choosing instruction text as its title was not reproduced, so the complete original symptom and exact provider-side cause remain unverified.

5. Root cause

Confirmed input ordering and title acceptance

packages/provider-bridge-acp/src/bridge/bridge.ts:1803 appends a pending instruction text block before processing the user input blocks. ACP therefore receives system context as ordinary prompt text before the actual message. This makes an agent that naively titles from the start of the first prompt susceptible to an instruction-derived title; that provider behavior remains a hypothesis, not an observed fact here.

packages/provider-bridge-acp/src/delta-translation.ts:853 forwards any nonblank, changed session title as an agent-sourced name. apps/server/src/internal/events.ts:457 sanitizes that name and calls the generated-title owner. apps/server/src/services/threads/title-generation.ts:314 accepts the first nonempty title if the thread has no current title. This acceptance route is confirmed in isolated pieces, not by a real external provider end-to-end.

Confirmed regeneration failure explanation

apps/server/src/services/ai/ai-tasks.ts:95 chooses services from the per-task AI selection, independent of the conversation provider. apps/server/src/services/ai/ai-tasks.ts:170 constructs a service-name/readiness diagnostic; apps/server/src/services/ai/ai-tasks.ts:212 skips unavailable services. plugins/provider-codex/src/host.ts:45 supplies a primary-machine authentication diagnostic when its credentials are missing. apps/server/src/services/threads/title-generation.ts:375 appends the diagnostic to the preservation message. apps/server/src/services/threads/title-generation.ts:407 throws on failure before updating the stored title. Therefore a Codex readiness error does not imply the conversation uses Codex, nor does the suffix identify a retained title.

apps/server/src/services/threads/title-generation.ts:153 additionally skips bb's automatic title AI call for ordinary text below five words. A short greeting is thus consistent with a provider-supplied title rather than bb's helper model selecting the wrong message.

6. Proposed Fix / Next Experiment

No production patch or pull request is justified by this partial reproduction. First capture sanitized first-prompt content and session_info_update events from an isolated setup of the same ACP agent/version to establish whether it actually derives the title from injected context. Then decide whether to change provider title selection or bb's title-source policy. Removing or relocating instruction delivery without that evidence could change agent behavior and crosses the simple-fix safety boundary. A wording clarification could reduce toast ambiguity, but would not establish or repair the reported title-selection root cause.

Simple-fix gate: not satisfied. The external provider's bad title selection is not reproduced on trusted main; there is no demonstrated pre-fix failing regression for that selection. No branch, production edit, dependency, stored-data change, push, or pull request was created for bb.
