#6858 · Retired plugin route state remains reachable after reload

BugMedium priorityLow effortplugins · perf · confirmed-reproGitHub issue

November 2, 2026 · trusted main d448d87f2033f7c253b64370c321ea9e7500c81d

Verdict: REPRODUCED · Root-cause confidence: high

1. TL;DR

A plugin reload stops the old instance but leaves its route-owned objects reachable. A new test installs a real plugin, reloads it three times, forces garbage collection through the local Node inspector, and checks weak references to four separately created payloads. Trusted main retains all four payloads in two clean-checkout runs, rather than only the current payload. The failure helper closes over the previous instance even though it needs only a boolean. Capturing that boolean instead releases the three retired payloads while the current HTTP route continues working.

import { mkdir, writeFile } from "node:fs/promises";
import { Session } from "node:inspector";
import { join } from "node:path";
import { setTimeout } from "node:timers/promises";
import { expect, it, vi } from "vitest";
import { createTestAppHarness } from "../../helpers/test-app.js";

it("releases retired route state while keeping the current plugin active", async () => {
  const references: WeakRef<object>[] = [];
  const harness = await createTestAppHarness();
  const inspector = new Session();
  try {
    inspector.connect();
    vi.stubGlobal("__bbObserveReloadPayload", (payload: object) => {
      references.push(new WeakRef(payload));
    });
    const root = join(harness.config.dataDir, "collection-fixture");
    await mkdir(root);
    await writeFile(
      join(root, "package.json"),
      JSON.stringify({
        name: "bb-plugin-collection-fixture",
        version: "0.1.0",
        bb: {
          name: "Collection fixture",
          description: "Exercises retired plugin state collection.",
          branding: { icon: "Zap" },
          server: "./server.ts",
        },
      }),
    );
    await writeFile(
      join(root, "server.ts"),
      `export default function plugin(bb) {
        const payload = { value: 42 };
        globalThis.__bbObserveReloadPayload(payload);
        bb.http.route("GET", "/value", context => context.json(payload));
      }`,
    );
    expect((await harness.pluginService.installPath(root)).status).toBe(
      "running",
    );
    for (let reload = 0; reload < 3; reload++) {
      expect(
        await harness.pluginService.reload("collection-fixture"),
      ).toMatchObject({
        ok: true,
      });
    }
    for (let collection = 0; collection < 3; collection++) {
      await setTimeout(0);
      await new Promise<void>((resolve, reject) => {
        inspector.post("HeapProfiler.collectGarbage", (error) => {
          if (error) reject(error);
          else resolve();
        });
      });
    }
    expect(references).toHaveLength(4);
    expect(
      references.map((reference) => reference.deref() !== undefined),
    ).toEqual([false, false, false, true]);
    const response = await harness.app.request(
      "http://127.0.0.1/api/v1/plugins/collection-fixture/http/value",
    );
    expect(response.status).toBe(200);
    expect(await response.json()).toEqual({ value: 42 });
  } finally {
    inspector.disconnect();
    try {
      await harness.cleanup();
    } finally {
      vi.unstubAllGlobals();
    }
  }
});

5. Root cause

The runtime reads the previous LoadedPlugin and the nested pre-factory failure function references that object. The new plugin API receives callbacks created in the same activation. That retained closure context can therefore keep the previous LoadedPlugin, whose handle includes the retired HTTP route handler and payload, reachable. Each replacement repeats the link. This explanation is supported by trusted source and the narrowly controlled fail/pass change; a heap snapshot was not taken in this investigation.

Disposal invalidates the old handle and stops work; it does not make an otherwise strongly reachable object collectable. The relevant code is the API method retaining its options callback, the retained route records, and instance disposal.

6. Proposed fix and verification

Keep the previous instance available locally for disposal and rollback, but compute const isReload = previous !== undefined and let the failure helper capture only that boolean. This preserves failed-reload behavior without introducing mutable lifecycle state, public APIs, or protocol changes. The production patch is two added lines and one removed line in the existing plugin runtime.

The focused regression passes after the change, including a successful response from the current route. Existing plugin tests and the server typecheck/build were run through Turbo:
