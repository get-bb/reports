Complete diagnostic source
import {
  deleteQueuedThreadMessage,
  getQueuedThreadMessage,
} from "@bb/db";
import { expect, it } from "vitest";
import { textInput } from "../helpers/prompt-input.js";
import { seedQueuedMessage, seedThreadFixture } from "../helpers/seed.js";
import { withTestHarness } from "../helpers/test-app.js";

it("explains the HTTP error when a queue snapshot outlives its row", async () => {
  await withTestHarness(async (harness) => {
    const { thread } = seedThreadFixture(harness);
    const queued = seedQueuedMessage(harness.deps, {
      content: textInput("diagnostic follow-up"),
      threadId: thread.id,
    });
    deleteQueuedThreadMessage(harness.db, harness.hub, queued.id);
    expect(getQueuedThreadMessage(harness.db, queued.id)).toBeNull();

    const response = await harness.app.request(
      `/api/v1/threads/${thread.id}/queued-messages/${queued.id}/send`,
      {
        method: "POST",
        headers: { "content-type": "application/json" },
        body: JSON.stringify({ mode: "auto" }),
      },
    );
    const body = await response.json();
    expect(response.status).toBe(404);
    expect(body).toMatchObject({
      code: "invalid_request",
      message: "Queued message not found",
    });
    console.info(`diagnostic HTTP ${response.status}: ${JSON.stringify(body)}`);
  });
});

5. Root-cause analysis and uncertainty

The incident's root cause remains unconfirmed. The trusted path is: queued-send UI action → SDK mutation → POST /api/v1/threads/:id/queued-messages/:queuedMessageId/send → queue service. The route first checks thread writability and pending interactions. Its error can therefore be a lifecycle rejection before dispatch, a queue lookup failure, a dispatch failure, or a transport problem before any response.

  • UI queued-send action: catches the error and provides a common fallback title. Its local queue guard does not by itself prove the server still has that ID.
  • Toast presentation: uses the fallback as the title and the extracted error as its description when available.
  • Transport recognition: fetch/network failures are distinguished from HTTP errors and displayed with a reachability explanation.
  • Public send route: validates thread state before sending the queue ID.
  • Queue claim/error handling: returns 404 when no claim and no corresponding row exist; releases claims on dispatch exceptions.

The diagnostic verifies only the missing-row branch. It does not induce automatic delivery racing a click, reproduce a dropped network connection, invoke the browser hook, or prove message loss. Neither a successful prior delivery nor a benign deletion can be inferred from the HTTP 404 alone. Describing this result as the Windows/Tailscale incident's cause would overstate the evidence.

6. Proposed fix or next experiment

No production fix is justified yet. Capture the full toast description and the failing queued-send request's status and response body, with credentials redacted. Establish whether the queue entry remained pending, reached the timeline, or disappeared without delivery; record whether the thread was awaiting an interaction and whether the request reached the server. Then distinguish a server-side state/dispatch rejection from a browser transport failure by comparing local access and the remote route under the same workload. If a stale-row race is confirmed, add a focused failing regression at the observed boundary before deciding how an already-delivered or genuinely deleted row should be handled.
