#8294 · Catalog replacement after a smaller successful discovery

BugPriority: MediumEffort: Mediumprovidersprovider-acpGitHub issue2026-11-27

Trusted base: b0ddaad731565d7e4de68d824120d802fc78f7d5

Verdict: REPRODUCED at the server catalog-store boundary. Root-cause confidence: high for catalog replacement. The live OpenCode activation race and vendor model counts were not reproduced.

1. TL;DR

A successful model refresh can remove previously available picker choices immediately, even when the returned IDs are a strict subset of the previous catalog and the launch fingerprint has not changed. A focused test against trusted main advertises three synthetic OpenCode models, advances the catalog clock by one minute, then advertises only one. The next picker read loses two IDs, SQLite is rewritten with a newer timestamp, a host change notification is sent, and the refresh is logged as successful. The same test fails for the same reason in a second clean checkout. This establishes the server-side loss mechanism, not the reported live OpenCode startup condition.

5. Root cause

ACP discovery opens a session and builds a model list from its configuration options or session models. handleModelList sends a nonempty discovery result as success. That does not prove any particular upstream list was incomplete, but it establishes the route into the store.

nextGood() preserves reasoning attributes only on matching incoming IDs. It does not preserve missing IDs. The successful settlement branch unconditionally promotes that replacement:

if (settlement.ok) {
  entry.good = nextGood(entry, {
    fingerprint: refresh.fingerprint,
    models: settlement.models,
    selectedOnlyModels: settlement.selectedOnlyModels,
    fetchedAt: refresh.markedStale ? 0 : now,
  });
  entry.failure = null;
  entry.unavailableDetail = null;
  persistGood(deps, entry.key, entry.good);

The SQLite upsert replaces the serialized arrays and timestamp. Changed picker state triggers a push. This explains all observed diagnostics.

Cached reads use picker access. Validation waits only when stale and missing a required model, which is consistent with, but does not experimentally verify, the reported recovery behavior.

The deeper ambiguity is in the host response contract:

const providerListModelsResultSchema = z.object({
  models: z.array(availableModelSchema),
  selectedOnlyModels: z.array(availableModelSchema),
});

It carries no indication that discovery is still warming up. An unchanged launch fingerprint does not prove the provider still offers every previous model. A smaller list can equally represent genuine removal or transient discovery. This test establishes destructive replacement of a smaller snapshot, not an objective completeness signal.

6. Proposed fix and safety decision

First establish an authoritative readiness/completeness signal for OpenCode discovery, or explicitly choose a bounded server-side retention policy for suspicious smaller snapshots. Incomplete results should not replace last-good state; confirmed real removals must eventually become visible. Any retention design also needs bounded retry behavior and cases for recovery, actual removals, mixed additions/removals, and fingerprint changes.

No automatic pull request: choosing how long to retain missing models, how to confirm removal, and whether to specialize the policy by provider is a product/architecture decision. Those semantics are not established by the existing result contract. An unconditional merge would retain obsolete models indefinitely, while changing the wire contract falls outside the simple-fix gate. Therefore no production patch, branch, or pull request was pushed. GitHub metadata showed no linked open pull request at investigation time.
