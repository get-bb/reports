#5191 · Browser session denies local connection permissions

BugPriority: MediumEffort: MediumdesktopsecurityGitHub issue

October 8, 2026 · trusted origin/main: 53c1e870d128c792dd3a0e469077cc4e6157b40d

PARTIALLY REPRODUCED · root-cause confidence: high for permission denial

1. TL;DR

The desktop browser installs a permission policy that grants only sanitized clipboard writes. Its real request and check handlers deny all three local-connection permission names supported by the pinned Electron version. A focused test exercised those production handlers after creating a browser tab, and the same three failures occurred in a second clean checkout. This establishes the local-connection blocker, not a complete Okta sign-in failure: this Linux environment has neither macOS Okta Verify nor an enrolled Okta test account. A safe repair needs an explicit local-network permission policy rather than a silent global grant, so no automated fix PR is opened.

5. Root cause

The fixed browser permission predicate has one allowed value:

function isAllowedBrowserPermission(permission: string): boolean {
  return permission === "clipboard-sanitized-write";
}

Session hardening registers the same predicate for requests and checks:

const browserSession = session.fromPartition(partition);
browserSession.setPermissionRequestHandler((_wc, permission, callback) => {
  callback(isAllowedBrowserPermission(permission));
});
browserSession.setPermissionCheckHandler((_wc, permission) =>
  isAllowedBrowserPermission(permission),
);

Tab creation calls session hardening before creating its view. Therefore requests reaching this browser session cannot obtain local-network or loopback permission, regardless of origin. The pinned Electron declarations recognize all three tested permission names; the input was not an invented unknown permission. The deeper gap is a hardened default-deny browser without a local-connection consent/exception mechanism at this boundary. Whether the reported FastPass installation reaches this specific Chromium permission gate remains an end-to-end experiment.

Trusted package version evidence: desktop version and Electron dependency. Existing permission test: current allow/deny contract.

6. Proposed fix and simple-fix decision

Decide how a human grants local-connection access to a specific requesting origin while preserving default denial for arbitrary sites and automation. Then make both permission handlers consult the same grant decision and test approved, denied, and unapproved origins, including loopback. Avoid a global local-network grant: it expands website access to host-local services, not just sign-in. The regression expectation should be adapted to an explicitly approved origin once that policy is selected.

No fix branch or PR: any repair changes a permission/security boundary and requires a product policy decision, both explicitly outside this rule's simple-fix conditions. End-to-end macOS verification is also incomplete. No production code was changed, no dependency was added, and no branch was pushed. GitHub cross-reference metadata and an open-PR search for the numeric issue found no existing linked open PR during investigation.
