#5695 · Plugin HTTP disconnect lifecycle

Bug Priority: Medium Effort: Low plugins · GitHub issue · October 17, 2026

Trusted base: 6a639cfc0d66e0c789a1bd7309266973228d1a80

Verdict: REPRODUCED · Root-cause confidence: high · Reproduction label: confirmed-repro

1. TL;DR

A plugin can keep resources allocated after its HTTP client disconnects while the handler is awaiting work. BB forwards the request without materializing the adapter's lazy abort signal, so reading the signal after the disconnect can report a live request. Independently, a response stream returned after the connection has already closed never receives cancellation. A regression using the real BB app, plugin installation/runtime, migrated SQLite, and a real loopback HTTP socket reproduces both failures. The same agent repeated the test in a second clean checkout at the trusted base; no issue-supplied code or external links were executed or fetched.

Full regression test
import { once } from "node:events";
import { mkdir, writeFile } from "node:fs/promises";
import { createServer, request } from "node:http";
import { join } from "node:path";
import { getRequestListener } from "@hono/node-server";
import { describe, expect, it } from "vitest";
import { createTestAppHarness } from "../../helpers/test-app.js";

describe("plugin HTTP disconnect cleanup", () => {
  it.each(["before", "after"])(
    "aborts the signal and cancels a late response when first accessed %s disconnect",
    async (access) => {
      const harness = await createTestAppHarness();
      const server = createServer(getRequestListener(harness.app.fetch));
      const root = join(harness.config.dataDir, "disconnect-plugin");
      await mkdir(root);
      await writeFile(
        join(root, "package.json"),
        JSON.stringify({
          name: "bb-plugin-disconnect",
          version: "0.1.0",
          bb: {
            name: "Disconnect fixture",
            description: "Exercises HTTP disconnect cleanup.",
            branding: { icon: "Zap" },
            server: "./server.ts",
          },
        }),
      );
      await writeFile(
        join(root, "server.ts"),
        `export default function plugin(bb) {
          const state = { entered: false, returned: false, aborted: null, cancelled: false };
          let finish;
          const pending = new Promise(resolve => { finish = resolve; });
          bb.http.route("GET", "/stream", async context => {
            state.entered = true;
            if (context.req.query("access") === "before") void context.req.raw.signal;
            await pending;
            state.aborted = context.req.raw.signal.aborted;
            state.returned = true;
            return new Response(new ReadableStream({
              start(controller) { controller.enqueue(new TextEncoder().encode("first")); },
              cancel() { state.cancelled = true; },
            }), { headers: { "content-type": "text/event-stream" } });
          });
          bb.http.route("GET", "/state", context => context.json(state));
          bb.http.route("GET", "/finish", context => {
            finish();
            return context.text("released");
          });
        }`,
      );

      const readState = async () => {
        const response = await harness.app.request(
          "http://127.0.0.1/api/v1/plugins/disconnect/http/state",
        );
        return response.json();
      };
      const finish = async () => {
        await harness.app.request(
          "http://127.0.0.1/api/v1/plugins/disconnect/http/finish",
        );
      };

      try {
        const entry = await harness.pluginService.installPath(root);
        expect(entry.status).toBe("running");
        server.listen(0, "127.0.0.1");
        await once(server, "listening");
        const address = server.address();
        if (address === null || typeof address === "string") {
          throw new Error("Expected a listening TCP server");
        }
        harness.config.serverPort = address.port;
        const disconnected = new Promise<void>((resolve) => {
          server.once("request", (_incoming, outgoing) => {
            outgoing.once("close", resolve);
          });
        });
        const client = request(
          `http://127.0.0.1:${address.port}/api/v1/plugins/disconnect/http/stream?access=${access}`,
        );
        client.on("error", () => undefined);
        client.end();
        try {
          await expect.poll(readState).toMatchObject({ entered: true });
          client.destroy();
          await disconnected;
          await finish();
          await expect.poll(readState).toMatchObject({ returned: true });
          expect.soft(await readState()).toMatchObject({ aborted: true });
          await expect
            .poll(readState, { timeout: 1_000 })
            .toMatchObject({ cancelled: true });
        } finally {
          client.destroy();
        }
      } finally {
        await finish();
        server.closeAllConnections();
        await new Promise<void>((resolve) => server.close(() => resolve()));
        await harness.cleanup();
      }
    },
  );
});

5. Root cause

The HTTP dispatcher does not access the request signal before authentication or plugin execution, and returns the plugin's response directly:

app.all("/plugins/:id/http/*", async (context) => {
  const id = context.req.param("id");
  ...
  return plugins.invokeHttpRoute(id, fresh.value, context);
});

invokeHttpRoute awaits the real handler and adopts its response, but adds no disconnect cleanup. Response adoption preserves streaming and forwards cancellation when cancellation is actually requested.

The pinned adapter lazily creates its AbortController. In its installed dist/request.mjs, getRequestCache constructs the controller on first signal/body access. In dist/index.mjs, the response close listener only aborts a controller that already exists. A controller created after that event misses it permanently.

The adapter's installed dist/index.mjs also returns immediately from writeFromReadableStream when its writable is destroyed, before attaching the stream reader's cancellation listeners. If the close event predates response creation, there is no later event to clean up the abandoned stream. This explains why eager signal access alone is insufficient.

Account Pooler's request tracking forwards abort to the upstream controller, while its response wrapper performs release from body completion, error, or cancellation. A dropped body skips these cleanup paths; the reported six-hour account incident was not independently observed.

6. Proposed fix

At the existing plugin HTTP dispatcher boundary, materialize the incoming signal before the first await. Await the plugin response; if the captured signal is already aborted, cancel its body with the abort reason before returning it to the adapter. Leave active-response streaming and all existing authentication/reload checks unchanged. This needs no adapter upgrade, public API, wire change, or Account Pooler policy change.

The local fix changes two files and 115 total text lines (114 additions + 1 deletion), including the regression. The focused regression fails on base and passes with the fix. The existing plugin wire suite covers normal requests, authentication, error paths, cross-realm streaming, RPC, reloads, and WebSockets; its 26 tests pass, alongside the two new cases. Server typechecking passes.

Production change:

const signal = context.req.raw.signal;
...
const response = await plugins.invokeHttpRoute(id, fresh.value, context);
if (signal.aborted) {
  await response.body?.cancel(signal.reason);
}
return response;
