#6302 · Background unread events reset sidebar collapse state

BugPriority: MediumEffort: LowuiGitHub issue2026-10-26 · base 3540a699e29034b53da32bb7efa6f5b4055209eb

Verdict: REPRODUCED · Root-cause confidence: high · reproduction label: confirmed-repro

1. TL;DR

The sidebar uses the same reveal path for deliberate navigation and for background unread activity. When an unread thread first appears after the initial thread snapshot, the reveal state machine requests that thread be revealed even though the user did not open it. The effect consuming that request removes its group IDs from the saved collapse preferences. This explains why a collapsed project, custom section, machine, or pinned group can unexpectedly reopen. Navigation should still reveal a destination; unread activity should use the existing collapsed-header indicators instead.

function thread(id: string, overrides: SidebarThreadOverrides = {}) {
  return makeSidebarThread({

    projectId: "proj_personal",

interface RevealInputs {
  selectedThreadId: string | undefined;
  threads: SidebarThread[];
  threadsReady: boolean;
  preferencesReady: boolean;
}

function startReveal(
  initial: Partial<RevealInputs> & { threads: SidebarThread[] },
) {
  let state = INITIAL_SIDEBAR_THREAD_REVEAL_STATE;
  const current: RevealInputs = {
    selectedThreadId: "first",
    threadsReady: true,
    preferencesReady: true,
    ...initial,
  };
  const reveal = (next: Partial<RevealInputs> = {}) => {
    Object.assign(current, next);
    const step = stepSidebarThreadReveal(state, {
      ...current,
      threadById: new Map(current.threads.map((item) => [item.id, item])),
    });
    state = step.state;
    return [...step.revealIds];
  };
  return { initial: reveal(), reveal };
}

5. Root cause

The app's sidebar adapter derives isUnread from actual read state. In the reveal step, newly unread IDs are added alongside the navigation target:

  const navigationRevealId = pendingNavigation;
  if (navigationRevealId && threadById.has(navigationRevealId)) {
    revealIds.add(navigationRevealId);
    pendingNavigation = undefined;
  }
  const unreadIds = new Set<string>();
  for (const thread of threads) {
    if (thread.isHidden || !thread.isUnread) {
      continue;
    }
    unreadIds.add(thread.id);
    if (
      state.previousUnreadIds &&
      !state.previousUnreadIds.has(thread.id) &&
      thread.id !== selectedThreadId
    ) {
      revealIds.add(thread.id);
    }
  }
  return {
    state: {
      previousThreadId,
      pendingNavigation,
      previousUnreadIds: unreadIds,
    },

The hook's effect then expands ancestors and environments and removes the destination machine, custom-section, project, or built-in section ID from its collapsed preference. It does not distinguish an explicitly opened destination from a background unread event before mutating those preferences. The lower-level expansion helpers are behaving correctly for navigation; the erroneous background reveal request is the cause.

The collapsed section header already rolls pending, working, unread, error, draft, split, and plugin status into its header. This mechanism does not require expansion.

6. Proposed fix

Remove background unread detection from the sidebar reveal state machine. Keep the queued navigation target, readiness gating, and containing-group expansion for explicit navigation. Remove obsolete unread baseline state and the unused thread-list input, replace the prior test that expected automatic unread expansion, and document the existing preference semantics. The implementation is contained in the thread-list plugin, with no new configuration, data migration, dependency, or protocol change.

The prepared fix changes 97 text lines across 3 files (additions plus deletions). The focused test passes after the fix (6 tests). The existing plugin suite passes 468 tests across 37 files; plugin typecheck and lint pass. git diff --check and focused formatting checks pass. Mobile Recents is a separate reveal mechanism and is deliberately not changed by this sidebar fix.
