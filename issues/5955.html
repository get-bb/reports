#5955 · Unix provider updates bypass current-directory PATH entries

Bug Medium priority Low effort providers · 2026-10-21 · GitHub issue

Trusted base: 405592c0b71b1655a6ab2e1cc7498b5beeb78caa (origin/main).

Verdict: REPRODUCED · Root-cause confidence: high · Reproduction label: confirmed-repro

1. TL;DR

On Linux, provider installation can silently run a different executable, or report that an executable is missing, when PATH contains an empty component. The real host-daemon installation stream reproduces both outcomes with disposable shell executables. Its new unconditional command resolver drops empty PATH components, whereas Unix process lookup treats them as the working directory. The first and a second clean trusted checkout both fail three focused regression cases. Limiting installer pre-resolution to Windows restores the Unix process lookup without changing the shared portable execution helper.

5. Root cause

The installer spawner resolves every command before spawning node-pty:

const command = resolvePortableCommand(args.command, { cwd, env });
if (command === undefined) {
  throw new Error(`Command not found: ${args.command}`);
}
const pty = spawnPty(command, args.args, { ... });

resolvePortableCommand passes the supplied PATH to whichCommandSync. The installed which-command dependency deliberately skips empty components in its candidatePaths implementation. Thus a bare Unix command no longer reaches execvp lookup: the spawner either rejects it first or supplies an already selected fallback absolute path.

Dependency inspection confirms that Linux node-pty calls execvp after changing to its supplied cwd. Its macOS spawn helper also calls execvp, but that platform was not run. The helper's stricter lookup may be intentional for other consumers; the installer is the inappropriate cross-platform caller. No change to execPortableFile is needed.

6. Proposed fix and verification

Keep pre-resolution on Windows, where executable extensions matter, and pass the original command to node-pty on Unix:

const command =
  process.platform === "win32"
    ? resolvePortableCommand(args.command, { cwd, env })
    : args.command;

The local fix changes only the existing host-daemon spawner and its tests: 2 files, 62 changed text lines (56 additions + 6 deletions). No dependency, lockfile, generated output, stored data, public schema, protocol, packaging, or permission changes. A genuinely absent Unix command again terminates through node-pty with an unsuccessful completion; the existing missing-command test now checks that platform-specific behavior. Windows keeps its resolver-generated error.
