#5080 · Session restoration uses the wrong request deadline

BugHighEffort: Lowproviders · provider-pi · confirmed-reproIssue on GitHubOctober 7, 2026 · base 68a1e8b7aa84fbd836eb8825e4d042ae0c52e74a

Verdict: REPRODUCED · Root-cause confidence: high

1. TL;DR

Restoring an existing provider session can fail even when the provider is healthy and eventually answers. The runtime gives new and forked sessions a two-minute construction deadline, but leaves restoration on the transport's shorter 30-second deadline. Two fresh checkouts reproduced this mismatch through the real runtime, bridge worker, JSON-RPC transport, and repository scripted-echo provider. Restoration also ignores an explicitly configured construction deadline: a request configured for 500 ms incorrectly succeeds after that deadline. A one-line runtime correction makes both restoration cases behave as specified while keeping the existing new-session behavior.

5. Root cause

The runtime's construction timeout setting defaults to 120,000 ms. The start and fork call sites forward that value to sendCommand. The resume call forwards only the command, result schema, and recovery metadata:

const result = await sendCommand({
  proc,
  message: plan,
  resultSchema: threadIdentityResultSchema,
  recovery: {
    providerId,
    providerThreadId: adapterCommand.providerThreadId,
    threadId,
  },
});

sendCommand forwards an optional timeout only when supplied. The JSON-RPC request timer therefore selects its 30,000 ms fallback. This also explains the opposite configured-deadline failure: choosing a shorter construction limit has no effect on resume.

On pi, constructPiThreadSession awaits session.start() at line 777. The resume construction handler does not send its result until that construction finishes. Thus, a construction that takes between 30 seconds and the intended two-minute limit is rejected prematurely. The test reaches the same runtime/transport boundary without depending on a private large session. The scripted resume handler already uses afterStartDelay, so no new test support is required.

6. Proposed fix and verified result

Forward the existing construction deadline in the resume sendCommand call, just as start and fork do. Do not change the transport default, command schema, bridge protocol, provider implementation, or daemon wire contract. Extend the existing lifecycle regression rather than adding a mock call-shape test.

After this correction, the focused test passes all three cases. The complete agent-runtime suite passes 309 tests in 23 files; package lint and typecheck also pass. The diff is 127 changed text lines in two files: one production addition, plus 82 test additions and 44 test deletions. No dependencies, generated files, binary files, migrations, stored data, or public contracts change.
