#6251 · Reconnect leaves terminal interaction waits unresolved

Bug High priority Medium effort host threads provider-claude-code ask-user-question

GitHub issue · October 25, 2026 · trusted base 7f3414a707a54519749d098165e3a98ff73a4b88

Verdict: REPRODUCED · Root-cause confidence: high

Scope: reproduced at the real server lifecycle and daemon reconnect boundaries using deterministic tests. A live Claude process, real network interruption, and multi-hour user incident were not replayed.

1. TL;DR

A provider can remain blocked waiting for a user response after the server has already ended the interaction. Main still allows an undeliverable answer to interrupt the interaction without ending its active turn. The daemon keeps its own unresolved provider promise, and opening a replacement session does not compare that promise with server state. A focused daemon test fails on main in two clean checkouts because the provider remains waiting after reconnect; a separate real-database server test confirms the terminal interaction, active thread, and rejected registration replay. Reusing the existing registration endpoint on reconnect releases terminal waits without changing the protocol.

5. Root cause

Failed interactive.resolve command settlement interrupts the interaction on every failed report:

if (!args.report.ok) {
  this.interruptPendingInteractionInTransaction(args.deps, {
    interactionId: args.command.interactionId,
    reason: args.report.errorMessage,
  });
  return;
}

Terminal settlement updates the interaction timeline and listeners; it does not end the host-local provider promise. The server test confirms that the thread remains active.

InteractiveRequestRegistry stores a promise per provider request. Registration and resolution can settle it, but no reconciliation runs when a session is replaced. onSessionOpened reconciles plugins, environments, watches, event delivery, and outbound interruptions, not these surviving waits.

The missing link is not a new endpoint: registration already returns existing for open requests and rejected for ended requests. The daemon simply does not ask again. This is a split lifecycle state: the server no longer exposes an answerable question while the provider still waits for its answer.

6. Proposed fix and verification

Replay the outstanding registrations when a session opens, using the existing endpoint and the current session ID. Share terminal-response handling with initial registration. Preserve still-pending/resolving waits and retain them on transient replay errors. Ignore late responses for entries already delivered, interrupted, or replaced. Return the provider promise immediately so reconciliation can settle it safely even while the original registration is still in flight.

The local repair stays inside the host-daemon subsystem and changes no wire fields, schema, dependency, stored data, CLI surface, or packaging. The original failing app test passes after the repair. Additional tests cover pending and resolving requests, transient failures, and late/in-flight registration races.
