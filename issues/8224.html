#8224 · Repeated token resolution during foreground reconciliation

Bug · Priority: Medium · Effort: Low · mobile, remote, perf · 2026-11-26

Issue #8224 · Base b0ddaad731565d7e4de68d824120d802fc78f7d5

Verdict: REPRODUCED · Root-cause confidence: high · Reproduction label: confirmed-repro

1. TL;DR

The mobile controller requests the Expo push token even when an existing server registration is fresh and the returned token is unchanged. The foreground and reconnect paths each request reconciliation, and overlapping calls deliberately schedule a trailing reconciliation. Three simulated foreground/reconnect cycles caused six token resolutions but no server registration writes. The installed Expo implementation makes an HTTP POST on each resolution; physical-device traffic and real AppState delivery were not measured.

5. Root cause

The host has two independent reconciliation triggers: the connected effect calls sync, and AppState active refreshes permission then calls sync. Neither should be removed because reconnection and permission changes still need reconciliation.

  useEffect(() => {
    if (!activeProfile || !connected) return;
    void controller.sync(activeProfile);
  }, [controller, activeProfile, connected, activeEnabled]);

  useEffect(() => {
    const onChange = (state: AppStateStatus) => {
      if (state !== "active") return;
      void controller.refreshPermission().then(() => {
        if (activeProfile) void controller.sync(activeProfile);
      });
    };
    const subscription = AppState.addEventListener("change", onChange);
    return () => subscription.remove();
  }, [controller, activeProfile]);

The controller coalesces an overlapping sync into a trailing run, rather than dropping it. Each run calls syncPushRegistration.

Token resolution precedes the freshness comparison. Therefore an up-to-date result avoids the server write but cannot avoid the already completed native/Expo request.

  let expoPushToken: string;
  try {
    expoPushToken = await notifications.getExpoPushToken(
      notifications.projectId ?? "",
    );
  } catch (error) {
    return { action: "failed", step: "token", error: describeError(error) };
  }
  const platform = notifications.platform;
  if (
    !shouldReregister({
      existing,
      expoPushToken,
      platform,
      serverUrl: profile.serverUrl,
      now: now(),
      refreshAfterMs,
    })
  ) {
    return { action: "skipped", reason: "up-to-date" };
  }

The native adapter calls getExpoPushTokenAsync. In installed expo-notifications 58.1.8, src/getExpoPushTokenAsync.ts:78-96 constructs the default Expo URL and unconditionally calls fetch with POST. This network conclusion is source-backed, not a captured HTTP trace. Token events already request reconciliation, but the controller has no token-result cache to invalidate.

6. Proposed fix

Cache successful Expo token resolution for the controller process while preserving permission checks and registration-age checks on every sync. Invalidate on genuine device-token changes and Android token release. Preserve cold-start resolution, failed-fetch retry, shared-profile behavior, and the existing 24-hour server re-registration. Exercise token-roll-during-fetch ordering before claiming broader lifecycle correctness.
