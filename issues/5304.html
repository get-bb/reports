1. TL;DR

The issue describes headless browser operations waiting indefinitely on one macOS machine. Trusted BB main launches its own Chrome with a small, platform-independent argument list that does not request a mock Keychain. A fresh diagnostic executable captured that actual argument list in two separate clean source checkouts. This investigation has only a Linux host and cannot exercise Apple Keychain or establish that the missing switch causes the reported cookie-key stall. No actual browser cookie read or HTTPS navigation was performed, so no production fix or pull request is justified by these results.

5. Root cause and limits

The product-side finding is precise: findChrome() resolves the executable override before system Chrome candidates, and createRuntime() sends a fixed headless argument list to the real supervisor. The list contains no macOS-specific keychain handling:

"--headless=new",
"--no-sandbox",
"--remote-debugging-port=0",
"--remote-debugging-address=127.0.0.1",
`--user-data-dir=${profile}`,
"--no-first-run",
"--no-default-browser-check",
"--window-size=1280,720",
"about:blank"

There is no platform branch in this launch block. This leaves any platform-native credential-store behavior to the selected browser. A native macOS cookie-key load blocking could therefore explain the symptoms, but that causal step is still a hypothesis in this investigation. The machine-specific reason for a blocked key load is unknown. The executable capture proves what BB sends, not what Chrome does with those arguments.

The probe stops before DevBrowser startup or its initial page listing. Its intentional startup error is not evidence of the reported cookie/navigation timeout. Existing runtime output-boundary tests passing likewise do not establish native Keychain compatibility.
